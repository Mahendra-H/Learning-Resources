Why this module matters

The substrate that everything else runs on

When PingFederate validates credentials, it queries Active Directory. When the adaptive auth engine evaluates group membership for policy, it queries LDAP. When Saviynt provisions a new joiner, it writes to Active Directory and PingDirectory. When SCIM synchronizes user accounts, it reads and writes to directory stores. When Kerberos issues a ticket, it reads from Active Directory.

Every authentication protocol (M03a, M03b), every MFA system (M04a), every IGA platform (M07), every PAM solution (M08), and every cloud identity service (M10) depends on a directory. Directories are not just storage — they are the identity substrate. Architects who treat them as a black box cannot design enterprise IAM systems that behave predictably under load, failure, or organizational change.

This module covers directory services at the depth an IAM architect needs: LDAP protocol mechanics, Active Directory architecture, Entra ID hybrid topology, PingDirectory's role, SCIM provisioning, and identity data modeling.

LDAP protocol depth

LDAP — the wire protocol beneath every enterprise directory

LDAP (Lightweight Directory Access Protocol, RFC 4511) is the query language and wire protocol used to read and write directory information. Every enterprise directory — Active Directory, PingDirectory, OpenLDAP, 389 Directory Server — speaks LDAP. Understanding it at protocol depth is the difference between knowing a directory exists and knowing how to diagnose, scale, and optimize it.

The Directory Information Tree (DIT) — how data is structured
LDAP organizes entries in a tree structure called the Directory Information Tree. Every entry has a Distinguished Name (DN) — a globally unique path from the entry to the tree root. Example: cn=Alice Smith,ou=Finance,dc=company,dc=com

Components: cn (Common Name), ou (Organizational Unit), dc (Domain Component). The tree mirrors the DNS namespace in enterprise deployments. Each entry has an objectClass that defines which attributes it must and may have. The person objectClass requires cn and sn. The inetOrgPerson objectClass adds mail, uid, telephoneNumber. The user objectClass (AD-specific) adds Windows-specific attributes like sAMAccountName, userPrincipalName, objectSid.
Core LDAP operations
The 8 operations every architect must know
Bind — Authenticate to the directory (simple bind = DN + password; SASL bind = Kerberos/GSSAPI)
Search — Query entries matching a filter within a search base and scope
Compare — Test if an attribute has a specific value (used for password checks in some deployments)
Add — Create a new entry
Modify — Change attribute values on an existing entry
Delete — Remove an entry
ModifyDN — Rename or move an entry
Unbind — Close the LDAP connection
LDAP search anatomy
The most common LDAP operation — deep
Every LDAP search has four parameters:

Base DN — where to start searching: ou=Users,dc=company,dc=com
Scope — base (just the base entry), one (one level below), sub (entire subtree)
Filter — RFC 4515 boolean expression: (&(objectClass=user)(mail=alice@corp.com)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))
Attributes — which attributes to return: cn sn mail memberOf

Performance: always index attributes used in filters. sAMAccountName, mail, and memberOf are indexed in AD by default. Custom attributes are not.
⚠️Performance gotchaUnindexed LDAP searches under load cause directory brownouts — the most common IAM outage pattern
When an application performs LDAP searches on unindexed attributes, the directory must scan every entry in the search scope. A search on department=Engineering with 100,000 users and no department index means 100,000 entry reads per search. Under authentication load (morning login surge, post-holiday return), this causes directory response times to spike from milliseconds to seconds, cascading into authentication timeouts across all integrated applications. Every LDAP attribute used as a search filter must be indexed in the directory. This is an architectural requirement, not a tuning recommendation.
Active Directory architecture

Active Directory — forests, domains, trusts & Kerberos

Active Directory is not just an LDAP directory — it is an integrated identity platform combining a directory service (LDAP), an authentication service (Kerberos), a DNS service, a replication system, and a policy engine (Group Policy). Understanding its architecture is essential because every enterprise IAM decision either integrates with AD or works around it.

Diagram 1 — Active Directory forest, domain & trust architecture
Forest vs Domain
The critical boundary distinction
Forest is the security boundary — the outermost unit of trust. Objects in different forests do not trust each other by default. The schema is shared across the entire forest and cannot be independently administered per domain.

Domain is the replication and administration boundary. Each domain has its own set of domain controllers. Domains within a forest share a common schema but have independent password policies, group policies, and admin teams.

OU is the delegation boundary — where Group Policy is applied and where administrative delegation is configured. OUs do not affect authentication; they affect management and policy application.
Kerberos in AD
How Windows authentication actually works
Active Directory's Key Distribution Center (KDC) issues Kerberos tickets. The flow:

1. User logs on → AS-REQ sent to KDC with pre-auth (encrypted timestamp)
2. KDC validates → issues TGT (Ticket Granting Ticket) encrypted with krbtgt key
3. Client requests service ticket: TGS-REQ with TGT → KDC issues ST (Service Ticket) encrypted with service account's key
4. Client presents ST to service → service decrypts with its own key → access granted

The krbtgt account is the most sensitive account in AD — if compromised, an attacker can forge any ticket (Golden Ticket attack).
FSMO Roles
5 operations master roles
Schema Master — Controls schema modifications. One per forest.
Domain Naming Master — Controls adding/removing domains. One per forest.
PDC Emulator — Password changes, time sync, Group Policy. One per domain. Most performance-sensitive role.
RID Master — Allocates pools of RIDs for SID generation. One per domain.
Infrastructure Master — Manages cross-domain references. One per domain.

Architects need to know FSMO role placement because: PDC Emulator failure causes authentication degradation. Schema Master must be accessible for any AD schema change (e.g., adding custom attributes for IGA).
Entra ID & hybrid identity

Microsoft Entra ID — hybrid identity architecture

Microsoft Entra ID (formerly Azure AD) is not just "AD in the cloud." It is an entirely different directory architecture — multi-tenant, REST API-first, OIDC/OAuth-native, with no support for the full LDAP protocol or Kerberos. Understanding the hybrid identity model — how on-premises AD and Entra ID coexist and sync — is one of the most important architectural topics in enterprise IAM today.

Diagram 2 — Entra ID hybrid identity topology & sync options
The three hybrid identity authentication options — when to use each
Password Hash Sync (PHS): The most resilient option. A hash of the on-premises password hash is synced to Entra ID. Authentication happens in the cloud even if on-premises AD is unavailable. Entra ID Protection can detect leaked credentials by comparing synced hashes against breached password databases. Recommended for most enterprises.

Pass-Through Authentication (PTA): Authentication requests are forwarded to a lightweight on-premises agent that validates credentials against AD. No password data stored in the cloud. Requires high availability of on-premises agents — if agents fail, cloud authentication fails. Choose when compliance mandates no password data in the cloud.

Federation (AD FS / PingFederate): Entra ID redirects all authentication to an on-premises federation server. Enables smart card, certificate-based auth, complex claims transformation, and custom MFA logic at the IdP layer. Highest complexity, highest maintenance burden. Choose when authentication requirements exceed what PHS/PTA can support.
PingDirectory & virtual directories

PingDirectory — why it exists alongside Active Directory

Your environment uses both Active Directory and PingDirectory. Understanding why both exist — and what each is optimized for — is essential for designing directory architecture in your enterprise.

Active Directory — optimized for
Windows workstation & enterprise authentication
AD is optimized for Windows domain authentication — Kerberos, Group Policy, device management, and Windows-ecosystem services. Its LDAP implementation is robust but carries AD-specific attributes and schema. It is the authoritative source for employee identities in most enterprises.

Weaknesses for consumer/API scenarios: Not designed for millions of concurrent LDAP connections, very high read throughput on consumer identity data, or storing consent and preferences data. AD schema changes are forest-wide, risky, and irreversible — adding custom attributes for CIAM is impractical.
PingDirectory — optimized for
High-volume LDAP, API-first identity, consumer IAM
PingDirectory is a purpose-built, LDAP-compliant directory designed for high-throughput, low-latency identity data access. Strengths:

Scale: Handles millions of concurrent LDAP connections. Horizontal replication across data centres with sub-second consistency.
API: Full REST/JSON API alongside LDAP — can be queried as a service, not just a directory.
Consent management: Built-in consent data model for GDPR/CCPA compliance.
Schema flexibility: Per-entry schema extensions without forest-wide impact.
PingFederate integration: Native adapter — PingFederate uses PingDirectory as its datastore for consumer identities.
Virtual Directory — the abstraction layer for complex directory landscapes
A virtual directory (VD) is a proxy layer that presents a unified LDAP view of identity data from multiple underlying sources — AD, PingDirectory, an HR database, a customer database — without actually storing data itself. Applications query the virtual directory and receive a merged, normalized view.

When you need a virtual directory: Your enterprise has identity data in multiple directories (AD for employees, PingDirectory for customers, an HRMS database for contractors). Each application would need to be coded to query multiple sources and merge results. A virtual directory provides a single LDAP endpoint that does the merging transparently.

PingDataGovernance and Radiant Logic VDS are enterprise virtual directory products. The tradeoff: virtual directories add a network hop and a potential performance bottleneck, but they dramatically simplify application integration in heterogeneous environments.
SCIM provisioning

SCIM 2.0 — the provisioning protocol

SCIM (System for Cross-domain Identity Management, RFC 7643/7644) is the REST/JSON protocol for automating user provisioning and deprovisioning between identity systems. Where LDAP is the read/write protocol for directory data, SCIM is the API-native provisioning protocol for pushing identity lifecycle events between systems.

SCIM vs LDAP — the right tool for each job
LDAP is a query protocol — optimized for reading and searching identity attributes in real-time during authentication. An application queries LDAP to retrieve a user's group memberships on every login.

SCIM is a provisioning protocol — designed for push-based synchronization of identity records between systems. An IGA system uses SCIM to create, update, and delete user accounts in a SaaS application when lifecycle events occur.

They are complementary, not competing. A typical enterprise flow: IGA uses SCIM to provision a user account in Salesforce → Salesforce uses LDAP (or Entra ID) to look up group memberships at login time.
1
SCIM service provider discovery
The SCIM consumer (IGA, IdP) discovers the target's capabilities via the /ServiceProviderConfig endpoint — which operations are supported (create, read, update, delete, search), which authentication methods are accepted (OAuth bearer token, HTTP Basic), and which schema extensions are supported.
GET /scim/v2/ServiceProviderConfig → { "schemas":["urn:ietf:params:scim:schemas:core:2.0:ServiceProviderConfig"], "filter":{"supported":true}, "bulk":{"supported":true,"maxOperations":100} }
2
Create user (Joiner provisioning)
When a new employee joins (Joiner event from M02), the IGA system sends a SCIM POST to the target application. The request body contains a User resource with core schema attributes and any enterprise extensions the target requires.
POST /scim/v2/Users → { "schemas":["urn:ietf:params:scim:schemas:core:2.0:User"], "userName":"alice.smith@company.com", "name":{"givenName":"Alice","familyName":"Smith"}, "emails":[{"value":"alice@company.com","primary":true}], "groups":[{"value":"sales-team"}], "active":true }
3
Update user (Mover — attribute or group change)
When a user's department or role changes (Mover event), the IGA sends a SCIM PATCH with only the changed attributes — efficient and precise. The PATCH body uses JSON Patch operations: add, replace, remove.
PATCH /scim/v2/Users/{id} → { "Operations":[{"op":"replace","path":"department","value":"Engineering"},{"op":"add","path":"groups","value":[{"value":"eng-team"}]},{"op":"remove","path":"groups","value":[{"value":"sales-team"}]}] }
4
Disable / delete user (Leaver deprovisioning)
On a Leaver event, the IGA first disables the account (PATCH active: false) — preserving audit history and allowing recovery if the termination was in error. After the retention period, a DELETE removes the record entirely.
PATCH /scim/v2/Users/{id} → { "Operations":[{"op":"replace","path":"active","value":false}] } // Then after 90 days: DELETE /scim/v2/Users/{id}
⚠️Provisioning gotchaSCIM bulk operations — the deprovisioning race condition
When a Leaver event fires and the IGA sends SCIM disable requests to 50 target systems simultaneously, a race condition can occur: if a SCIM request fails silently (network timeout, target system unavailable), the account remains active in that system. SCIM deprovisioning must implement reconciliation — periodic full scans comparing IGA's expected state against actual target system state, with alerts on discrepancies. Real-time SCIM is fast but not reliable enough to be the sole deprovisioning mechanism for security-critical systems. Always pair SCIM with scheduled reconciliation jobs.
Identity data modeling

Canonical identity schema design

Every enterprise directory contains the same fundamental object types but represents them differently across systems. Active Directory uses sAMAccountName. PingDirectory uses uid. SCIM uses userName. Workday uses an employee ID. Salesforce uses a username. An architect's job is to design the canonical identity schema — the authoritative data model that all other systems map to.

The Employee ID — the most important attribute in enterprise IAM
The Employee ID (or HR system unique key) is the one attribute that should be immutable and authoritative across all identity systems. It is the correlation anchor — the single value that ties the same person's accounts across AD, Entra ID, Salesforce, Workday, Saviynt, and every other system.

Why it matters architecturally: Users change their names (marriage), change their UPN (department transfer), change their email address — but their Employee ID never changes. When an IGA system needs to reconcile a user's accounts across 50 target systems, it does so by matching Employee IDs, not usernames. Every enterprise identity architecture must designate a single authoritative, immutable identifier as the canonical anchor. If your enterprise doesn't have one, your first IGA project should create it.
Knowledge check

Test your directory depth

Q1 Your company acquires another company with its own Active Directory forest. Design the identity integration architecture — including trust model selection, user account strategy, and how PingFederate handles authentication from both forests. ▼
Three integration models — select based on acquisition strategy:

Option A — Cross-forest trust (fastest, least disruption): Establish a cross-forest trust between company.com and acquired.com. Users in acquired.com can authenticate to resources in company.com using their acquired.com credentials via Kerberos referral. PingFederate is configured with two AD adapters — one for each forest — and a home realm discovery policy that routes users to the correct adapter based on their email domain. No account migration required. Risk: Perpetuates two management boundaries, two schema versions, two patch cycles. Technical debt accumulates.

Option B — Migration to single forest (most complete, highest effort): Use AD Migration Tool (ADMT) to migrate user and computer objects from acquired.com to company.com, preserving SIDs in sIDHistory for resource access continuity. Migration happens in waves by department. PingFederate adapter updated after each wave. Timeline: 12–24 months for a large acquisition.

Option C — Entra ID as federation hub (modern, cloud-first): Sync both forests to a single Entra ID tenant via Entra ID Connect. Entra ID becomes the unified identity plane — all SSO flows go through Entra ID regardless of which forest the user object lives in. PingFederate configured to trust Entra ID as IdP. This decouples authentication from on-premises AD architecture.

Recommended hybrid: Cross-forest trust immediately for day-1 authentication. Parallel migration to single Entra tenant over 6 months. Long-term forest consolidation as a separate project tied to the hardware refresh cycle.
Q2 An application team says their app queries LDAP for every single API request to get the user's group memberships for authorization decisions. There are 50,000 API requests per minute. What is the architectural problem and what is the correct design? ▼
Two distinct architectural problems:

Problem 1 — LDAP is the wrong protocol for per-request authorization: LDAP is a network call with latency (typically 1–5ms on LAN). 50,000 requests/min = ~833 LDAP queries/second. Under load spikes (2x–5x), this becomes 4,000+ LDAP queries/second against the directory, causing connection pool exhaustion and directory performance degradation that affects all other systems using the same directory (PingFederate, other apps, workstation authentication).

Problem 2 — LDAP result caching is absent: Group memberships do not change on every request — they change on provisioning events (Mover/Joiner/Leaver). Querying the directory on every API request ignores this.

Correct design:
(1) Embed group memberships in the access token at issuance time. When the user authenticates, the authorization server queries LDAP once, retrieves group memberships, and embeds them as claims in the JWT access token. The API validates the JWT and reads claims — zero LDAP calls per request.
(2) For dynamic/fine-grained authorization: Use an externalized authorization service (OPA, Casbin) with a short-TTL cache of group data. The authorization service refreshes from LDAP every 60–300 seconds via a background process, not on each request.
(3) For very dynamic data: Subscribe to LDAP changelog/change notification to push group membership updates to the authorization cache in near-real-time, eliminating polling overhead.
Q3 Your enterprise chooses Password Hash Sync over Pass-Through Authentication for Entra ID. Your security team raises a concern: "Our password hashes are in Microsoft's cloud." How do you address this concern accurately? ▼
Accurate technical clarification — the concern is based on a misunderstanding of what is actually synced:

PHS does NOT sync passwords or password hashes to Entra ID in a recoverable form. The sync process: (1) On-premises AD stores NTLM hash of password (MD4(password)). (2) Entra ID Connect takes this NTLM hash, applies a per-user salt, and computes MD5(salt + MD4(password)) — a hash of a hash with a salt. (3) This derived value is what is synced to Entra ID. Microsoft cannot reverse this to recover the original password. Even if Entra ID's storage were breached, the attacker would have salted hashes of hashes — not usable to authenticate to on-premises AD, which expects the original NTLM hash.

The actual security benefit of PHS: Microsoft runs synced hashes through their leaked credential detection service (part of Entra ID Protection). If a user's credentials appear in a known breach database, Entra ID can flag the user for forced password reset — a security capability that PTA and Federation cannot provide because no hash is stored in the cloud.

Remaining concern to address: The Entra ID tenant's security posture matters — if the tenant is compromised (Entra admin account takeover), an attacker could potentially trigger authentication attempts. Mitigation: enable Entra ID Protection, conditional access on admin accounts, PIM for admin roles, and audit logging of all authentication events.
Q4 Design the SCIM provisioning architecture for a new SaaS CRM application integrating with Saviynt (your IGA platform). Include the authoritative source chain, provisioning trigger, attribute mapping, error handling, and reconciliation strategy. ▼
Complete SCIM provisioning architecture for CRM integration:

Authoritative source chain: Workday (HR system) → Saviynt IGA → CRM (Salesforce). Workday is the source of truth for employee identity. Saviynt is the orchestration layer. The CRM is the target system.

Provisioning triggers: Joiner event → Saviynt creates CRM account with Sales-User role (birthright for Sales department). Mover event (into Sales) → Saviynt creates CRM account. Mover event (out of Sales) → Saviynt deactivates CRM account. Leaver event → Saviynt immediately deactivates; deletes after 90 days. Access Request → Saviynt creates CRM account with requested permission profile after manager approval.

Attribute mapping: Workday Employee_ID → SCIM externalId (anchor). Workday Preferred_Name → SCIM displayName. Workday Email → SCIM emails[primary] and userName. Workday Department → SCIM urn:ietf:params:scim:schemas:extension:enterprise:2.0:User:department. Saviynt entitlement CRM-SalesManager → SCIM roles[value:"SalesManager"].

Error handling: SCIM responses with 4xx (client error — bad request) → alert IGA admin, hold provisioning. 5xx (server error) → retry with exponential backoff (3 retries: 1min, 5min, 15min). After 3 failures → create helpdesk ticket, mark provisioning task failed in Saviynt, alert IAM operations team.

Reconciliation: Saviynt runs a nightly full reconciliation job: GET /scim/v2/Users (paginated) from CRM → compare against Saviynt's expected state → flag discrepancies (accounts in CRM not in Saviynt, accounts active in CRM but should be disabled). Discrepancies generate tickets for IAM operations review. Weekly automated reconciliation report to IAM governance team.

Key takeaways — M04b · Directory Services & Identity Stores
  • LDAP is the substrate protocol beneath every enterprise directory. Eight operations cover all directory interactions. Search filters, base DN, scope, and indexed attributes are the performance levers architects must control. Unindexed searches on high-traffic directories cause cascading authentication failures.
  • Active Directory is not just a directory — it is an integrated platform combining LDAP, Kerberos, Group Policy, DNS, and replication. The forest is the security boundary. The domain is the administration boundary. The OU is the delegation boundary. FSMO roles determine which DC is authoritative for specific operations.
  • Entra ID hybrid identity has three authentication models: PHS (resilient, cloud-native), PTA (no cloud hash, requires on-prem agents), Federation (full control, highest complexity). PHS is recommended for most enterprises. PHS does not store recoverable passwords — it stores salted hashes of NTLM hashes.
  • PingDirectory exists alongside AD because AD is optimized for Windows/Kerberos authentication, not high-volume consumer identity, API-first access, or per-entry schema flexibility. Virtual directories provide a unified LDAP abstraction across multiple underlying stores.
  • SCIM is the provisioning protocol, not the authentication protocol. IGA systems use SCIM to push identity lifecycle events to target systems. SCIM must be paired with reconciliation — real-time SCIM is insufficient as the sole deprovisioning mechanism for security-critical systems.
  • The Employee ID is the most important attribute in enterprise IAM — the immutable correlation anchor that ties identity across all systems. Every enterprise must designate one authoritative, immutable identifier as the canonical anchor.
Architect Review Senior-level directory design challenges
  • 01 Your enterprise's Active Directory has grown organically over 20 years — 12 child domains, 4 forests (2 from acquisitions, 1 from a divested business unit that was re-acquired), inconsistent OU structures, no standard naming convention, and 3 different FSMO role placement strategies. The CISO wants a "clean directory" before the Entra ID migration. Design a 3-year directory rationalization program: assessment approach, domain consolidation strategy, OU standardization, FSMO placement, and how you migrate without disrupting the 600 applications currently bound to the directory.
  • 02 Your IGA platform (Saviynt) provisions accounts via SCIM to 80 SaaS applications. Three months after go-live, your audit team discovers that 23 terminated employees still have active accounts in 7 of the 80 applications. The SCIM deprovisioning events were sent but evidently not processed. Design a root cause analysis framework and a resilient deprovisioning architecture that makes this class of failure detectable within 4 hours and self-healing within 24 hours.
  • 03 Your enterprise is designing a canonical identity schema to span on-premises AD, Entra ID, PingDirectory (consumer identities), and a newly acquired company's OpenLDAP directory. Design the canonical schema: identify the 12 most critical attributes, define the authoritative source for each, specify the transformation rules where attribute formats differ, and design the correlation strategy for users who exist in multiple directories with different identifiers.
