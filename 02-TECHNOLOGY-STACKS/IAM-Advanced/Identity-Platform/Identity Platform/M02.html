Why this module matters

Precision over familiarity

You already know what authentication and authorization mean in a working sense. The problem is that in architecture discussions — with engineers, product teams, vendors, and executives — imprecise language creates real design errors. When a Principal Engineer conflates a session with a token, or describes an assertion as a credential, it signals a gap that undermines credibility.

This module defines every foundational IAM term with architectural precision. Not dictionary definitions — working definitions that you'll use to design, communicate, and evaluate systems every day. By the end, when M03a asks you to design an OAuth authorization server, you'll have the exact vocabulary to describe what it issues, what it validates, and why the trust chain holds.

The foundational split

Authentication vs Authorization

These two words end in similar suffixes and are used interchangeably in casual conversation. In architecture, they are entirely different concerns, solved by entirely different systems, at entirely different points in a request lifecycle.

Authentication (AuthN)
"Who are you?"
  • Proves identity — verifies a claimed identity against stored credentials
  • Result: a verified principal with proven identity
  • Systems: PingFederate, LDAP, Kerberos, FIDO2
  • Outputs: session token, ID token, Kerberos ticket, SAML assertion
  • Happens once per session (ideally)
Real-world: "Is this person really alice@company.com?"
Authorization (AuthZ)
"What can you do?"
  • Grants or denies access — evaluates permissions against policy
  • Result: allow or deny decision for a specific action on a specific resource
  • Systems: OPA, Casbin, Zanzibar, Saviynt (entitlements)
  • Inputs: verified identity + resource + action + context
  • Happens on every request — potentially thousands per session
Real-world: "Can alice@company.com delete this financial record?"
⚠️ Gotcha Conflating AuthN and AuthZ causes real system design errors
A system that grants access based solely on authentication ("if you can log in, you can see everything") has no authorization layer. This is an extremely common mistake in legacy enterprise applications. Another version: using group membership as both an authentication mechanism AND an authorization signal in the same system — which creates an untestable, unauditable mess. Architects who understand this distinction design systems where AuthN and AuthZ are always separate, independently scalable, and independently auditable.

Core identity primitives

The vocabulary every module uses

These eight terms appear in every IAM protocol, product, and architecture discussion. Define them with precision now — every M03 through M16 concept is built on top of them.

Principal
Any entity that can be authenticated and to which access can be granted. Principals are not just humans — they include service accounts, applications, devices, and workloads. In OAuth: the resource owner. In Kerberos: the subject in the ticket. Key insight: machine identities (M09a) are principals with the same lifecycle requirements as human identities — but most organizations govern them as second-class citizens.
Credential
A secret or cryptographic artifact that a principal uses to prove its identity. Credentials include passwords, private keys, certificates, TOTP codes, hardware security keys, and biometric templates. Credentials are not identity — they are evidence of identity. Key insight: credential theft does not mean the principal's identity is compromised permanently — only that the credential presented for that session was stolen. Credential rotation and revocation are the remediation tools.
Claim
A statement about a principal made by an authoritative source. Claims are the data payload of identity tokens. In a JWT: {"sub":"alice","email":"alice@corp.com","roles":["admin"]} — each key-value pair is a claim. Claims can be about identity (who you are), attributes (what you look like), or entitlements (what you can do). Key insight: claims are assertions, not facts — they are only as trustworthy as the issuer. An expired, tampered, or spoofed token carries invalid claims regardless of their content.
Assertion
A digitally signed statement from an identity provider that carries claims about a principal. In SAML: the XML <saml:Assertion> element signed by the IdP's private key. In OIDC: the ID token (a signed JWT). The signature makes assertions tamper-evident — a relying party can verify the assertion came from a trusted source. Key insight: assertion != credential. A credential proves who you are to the IdP. An assertion proves to a third party (SP) that the IdP already verified who you are.
Token
A time-limited, signed artifact that carries authorization context for a principal. Tokens are the currency of modern IAM systems. Key types: Access token (OAuth — authorizes API calls), ID token (OIDC — carries identity claims), Refresh token (OAuth — gets new access tokens), Session token (cookie-based — maintains browser sessions). Key insight: tokens have three critical properties — issuance (who created it), validity (when it expires), and scope (what it authorizes). Architects design token policies around all three.
Session
A stateful context maintained between a client and a server across multiple requests, established after successful authentication. Sessions are maintained server-side (session store) or client-side (encrypted cookies or JWTs). Key architectural distinction: JWT-based "sessions" are actually stateless — the server holds no state, which makes revocation hard. Traditional server-side sessions are stateful — revocation is instant (delete the session), but the session store becomes a scalability concern.
⚠️ Gotcha Tokens are not sessions — and this distinction matters for revocation design
A JWT access token is valid until it expires — period. If a user is terminated or a breach is detected, a short-lived access token (15 min) issued before the termination event is still technically valid at the resource server. This is why Continuous Access Evaluation (CAE) was invented — it allows resource servers to check token validity in near-real-time. If your access tokens are 24 hours long and you have no CAE: your offboarding process has a 24-hour window of risk. Architects who understand this design token lifetimes deliberately.
Identity Provider (IdP)
The authoritative system that authenticates principals and issues assertions or tokens about them. The IdP is the trust anchor — everything downstream trusts the IdP's word. In enterprise IAM: PingFederate, Okta, Microsoft Entra ID, ADFS. The IdP maintains the credential store (or delegates to a directory) and issues signed artifacts that relying parties accept. Key insight: an organization can have multiple IdPs for different principal types — a workforce IdP, a machine identity IdP (SPIRE), and a customer IdP (PingOne) — all participating in the same Identity Fabric.
Relying Party / Service Provider (RP/SP)
Any system that accepts identity assertions from an IdP and makes access decisions based on them. In SAML: the Service Provider. In OIDC: the Relying Party. In OAuth: the Resource Server. The SP/RP never verifies credentials directly — it trusts the IdP to have done so and validates the assertion's signature. Key insight: trust is directional. The SP trusts the IdP. This trust must be explicitly established (SAML metadata exchange, OIDC client registration, OAuth trust configuration) — it is never automatic.
Identity lifecycle

Joiner · Mover · Leaver

The Joiner-Mover-Leaver (JML) model is the operational backbone of enterprise IGA. Every M07 concept — provisioning workflows, certification campaigns, SoD policies — operates within this lifecycle. Build the lifecycle model here; M07 will build the governance program on top of it.

Diagram 2 — Identity Lifecycle: Joiner → Mover → Leaver and re-entry loops
J
Joiner — onboarding a new identity
Triggered when HR creates a new employee record. The IGA engine receives the event, creates a digital identity, determines birthright access based on role/department/location, and provisions accounts across all target systems. Timing is critical — late provisioning costs productivity; early provisioning (before start date) creates security risk.
Key design decision: how far in advance do you provision? Best practice: provision AD/email 48hrs early, app access on day 1, privileged access after role confirmation (typically week 2+).
M
Mover — identity changes during tenure
Triggered when an employee changes role, department, location, or reporting line. The most under-governed lifecycle event. Movers accumulate access over time — each move adds new access, old access rarely gets removed. This access accumulation is called privilege creep and is one of the primary IGA hygiene problems in enterprise environments.
Key design decision: must the Mover event trigger automatic removal of old entitlements, or a certification campaign to review them? Automatic removal is safer; review campaigns are less disruptive but slower.
L
Leaver — deprovisioning departing identities
Triggered on termination. The highest-urgency lifecycle event from a security perspective. All accounts must be disabled immediately. All active sessions must be revoked. All tokens must be invalidated. All privileged accounts in PAM must be rotated. Shared accounts the leaver had access to must be identified and rotated. The "how fast" question is answered by the risk profile — involuntary terminations require immediate, simultaneous deprovisioning across all systems.
Key design decision: disable vs delete? Best practice is always disable first, archive after 90 days, delete after retention period. Immediate deletion destroys audit trail.
⚠️ Gotcha Privilege creep is the silent IGA failure mode — Movers accumulate access, nobody removes old access
The statistic that makes auditors nervous: in organizations without automated Mover workflows, the average employee who has been with the company 5+ years has 3–7× more access than their current role requires. Each role change added access; none removed the old. This is not a human failure — it is a process design failure. IGA platforms solve this with role transition policies: when a Mover event fires, the system calculates the delta between old-role entitlements and new-role entitlements, automatically removes orphaned access, and optionally raises a certification campaign for edge cases.
Trust architecture

What trust means in IAM — precisely

In IAM, "trust" is not a vague concept — it is a specific, configurable, and auditable relationship between systems. Understanding trust precisely is what allows architects to design federation, cross-domain access, and cloud identity patterns correctly.

Trust type 1
Transitive trust
If A trusts B and B trusts C, then A trusts C. Active Directory forest trusts are transitive by default within a forest. This is powerful — and dangerous. A transitive trust chain that includes a poorly governed domain effectively extends that domain's security posture to all trusting domains. Architects must audit every trust relationship and justify transitivity explicitly.
Trust type 2
Federated trust
An explicitly established trust relationship between two independent identity domains, governed by protocol (SAML metadata, OIDC discovery). Unlike transitive trust, federated trust is one-hop only — A trusts B does not mean A trusts what B trusts. This is the foundation of enterprise SSO: your company's IdP is trusted by SaaS providers you've explicitly configured. No automatic extension.
Trust type 3
Cryptographic trust
Trust established through public key infrastructure. A verifying party trusts a signing CA's root certificate, and therefore trusts any certificate signed by that CA. PKI-based trust underpins TLS, JWT signature verification, SAML assertion validation, and SSH certificate authority patterns. Architects design the CA hierarchy to control which systems can issue trusted credentials.
Trust type 4
Delegated trust (OAuth)
A principal grants a third-party client permission to act on their behalf within defined scope limits. OAuth 2.0 is the canonical delegated trust protocol. The resource owner does not share credentials — they issue a scoped, time-limited token. This is architecturally distinct from impersonation (acting AS someone) vs delegation (acting FOR someone, within explicit boundaries).
Authentication factors & assurance

Factors, assurance levels, and why they matter architecturally

NIST SP 800-63B defines three Authenticator Assurance Levels (AAL). These are not academic — they determine what authentication mechanisms are acceptable for a given system, and they directly drive MFA architecture decisions in M04a.

Factor typeDefinitionExamplesResistanceNIST AAL
Something you know A secret memorized by the principal Password, PIN, security questions Low — phishable, guessable, reusable AAL1 alone
Something you have A physical device or token generating OTPs or signatures TOTP app, hardware key (YubiKey), SMS OTP, push notification Medium — device theft; SMS is phishable AAL2 (with password)
Something you are A biometric characteristic of the principal Fingerprint, Face ID, voice recognition Medium — device-bound; not a standalone factor AAL2 (with hardware binding)
FIDO2 / Passkey Hardware-bound public key credential — no shared secret WebAuthn with platform authenticator or hardware key High — phishing-resistant, no server-side secret AAL2 or AAL3
Certificate-based Client presents a valid X.509 cert in mTLS or smart card flow Smart card (PIV), mTLS client cert, SSH certificate High — hardware-bound, CA-issued, revocable AAL3
Architect's insight on MFA design
Not all MFA is equal. SMS OTP is MFA — and it is phishable via real-time phishing proxies (EvilProxy, Modlishka). Push notification fatigue attacks have been used to compromise Microsoft and Uber. The only phishing-resistant MFA options at enterprise scale are FIDO2/WebAuthn (passkeys) and certificate-based authentication. Architects designing MFA programs must distinguish between "we have MFA" (any second factor) and "we have phishing-resistant MFA" (FIDO2 or cert-based). M04a covers the full architecture of each.
Threat landscape overview

The five identity attack categories

Identity is the primary attack surface in modern enterprise breaches. M11 covers identity security in full depth — but architects need to understand the threat landscape from Module 2, because every design decision has a threat model implication.

Category 1
Credential attacks
Password spraying (few passwords, many accounts), credential stuffing (breached credential lists), brute force, phishing for credentials. The most common entry vector. Defense: phishing-resistant MFA, breached credential detection, lockout policies.
Category 2
Token / session attacks
Token theft (stealing JWTs from local storage or memory), session hijacking (stealing cookies), replay attacks (reusing tokens after expiry via clock manipulation). Defense: short token lifetimes, DPoP (sender-constrained tokens), secure cookie flags (HttpOnly, Secure, SameSite).
Category 3
Privilege escalation
Gaining higher-privilege access than authorized — via misconfigured permissions, role misconfiguration, RBAC gaps, or exploiting admin workflows. Defense: least privilege, JIT access (PAM), entitlement certifications (IGA).
Category 4
Lateral movement via identity
Using stolen credentials or tokens to move across systems within the enterprise — from a compromised user account to a service account to a privileged admin account. Defense: zero trust (verify every hop), micro-segmentation, PAM session isolation.
Category 5
Supply chain / delegation abuse
Compromising an OAuth client, service account, or machine identity that has broad delegated access. The SolarWinds breach was partly a supply chain identity attack — a compromised build system had service account credentials that gave broad access. Defense: machine identity governance (M09a/b), secrets management, minimal OAuth scopes.
Category summary
Every domain is a defense layer
AuthN (M03a/b) defends Category 1. Token architecture (M03a) defends Category 2. Authorization design (M06) + PAM (M08) defend Category 3. Zero trust (M11) defends Category 4. Machine identity (M09a/b) defends Category 5. This is why all 12 domains must work together.
Knowledge check

Test your precision

Q1 A developer says: "We store the user's role in the JWT and check it at the API — that handles both authentication and authorization." What is architecturally wrong with this statement, and what does a correct design look like? ▼
Two problems: First, conflating AuthN and AuthZ in a single token is problematic — the JWT proves identity (AuthN) but the role claim being used for access decisions is a static snapshot baked into the token at issuance time. If the user's role changes, all existing tokens carry the stale role until expiry. Second, checking roles in the API means authorization logic is hardcoded and scattered. Correct design: JWT proves identity (AuthN). Authorization decisions are made by an external policy engine (OPA, Casbin, or a dedicated authz service) that receives the principal's identity and evaluates current policy — not a cached role from a token. This separates the concerns, allows instant policy changes without token re-issuance, and makes authorization independently testable and auditable.
Q2 A user is terminated at 9am. Your access tokens are valid for 8 hours. Your IGA system runs deprovisioning workflows that complete by 9:15am and disables their AD account. Are they fully locked out? What is the residual risk window? ▼
No — they are not fully locked out. The AD account is disabled at 9:15am, which prevents new authentications and new token issuance. However, any OAuth access tokens issued before 9am are still valid at resource servers until they expire (up to 5pm). If those resource servers use bearer token validation (JWT signature check only, no revocation check), the terminated user can still access those resources with pre-existing tokens for up to ~8 hours. Residual risk window: up to 8 hours minus time elapsed since last token issuance. Solutions: (1) Reduce access token lifetime to 15 minutes, (2) Implement Continuous Access Evaluation (CAE) — resource servers subscribe to identity events and immediately invalidate sessions when a disable event fires, (3) Maintain a token revocation list that resource servers check on each request. Architects choose based on the sensitivity of the resource and the operational cost of each approach.
Q3 Explain the difference between a credential, a claim, and an assertion using a single real-world login flow as your example. ▼
Using a SAML SSO login to a SaaS app: (1) Credential — Alice types her password into PingFederate's login page. The password is the credential — a secret she knows, used to prove her identity to the IdP. It is never shared with the SaaS app. (2) Claims — After PingFederate verifies Alice's password against PingDirectory, it assembles a set of claims: NameID=alice@corp.com, Department=Finance, Role=Analyst, SessionIndex=abc123. These are statements about Alice made by the authoritative IdP. (3) Assertion — PingFederate packages those claims into a signed SAML Assertion XML document and sends it to the SaaS app (via the browser). The assertion is digitally signed with PingFederate's private key. The SaaS app validates the signature using PingFederate's public key (from shared metadata) and trusts the claims — because the signature proves they came from the trusted IdP, not from Alice herself.
Q4 An employee moves from Finance to Engineering. Their IGA system grants Engineering group membership and SaaS app access. Three months later you discover they still have Finance data warehouse access. What lifecycle design failure caused this, and how do you prevent it architecturally? ▼
The failure is incomplete Mover workflow design — specifically, no orphaned access detection. The IGA system correctly granted new-role entitlements but did not reconcile against old-role entitlements. This is privilege creep — the most common IGA failure pattern. The Finance data warehouse access was either: (a) not mapped to the Finance role in the IGA system (so the system didn't know to remove it), or (b) mapped to the role but the removal step was not included in the Mover workflow, or (c) the warehouse was not connected to the IGA system at all (a coverage gap). Architectural fix: (1) Map all entitlements to roles in IGA (role engineering — M07 covers this), (2) Design Mover workflows that explicitly calculate the delta between old-role and new-role entitlement sets and remove the difference, (3) Run quarterly entitlement certifications (certification campaigns) where managers review all access for their team, (4) Implement birthright access governance — any access not attributable to the current role requires an active justification or it is automatically revoked.

Key takeaways — M02 · Identity Fundamentals
  • AuthN and AuthZ are completely separate concerns — separate systems, separate timing, separate failure modes. Never conflate them in design or conversation. AuthN happens once per session; AuthZ happens on every single request.
  • Eight primitives power all of IAM: Principal, Credential, Claim, Assertion, Token, Session, IdP, and Relying Party. Every protocol from SAML to OAuth to Kerberos is a different way of handling these same eight concepts.
  • The JML lifecycle is the operational core of IGA. Joiner (provision), Mover (reconcile), Leaver (deprovision). Privilege creep — the accumulation of access across Mover events — is the primary IGA hygiene problem in large enterprises.
  • Trust is specific, configurable, and auditable. Four trust types: transitive, federated, cryptographic, delegated. Each has different security implications and scope boundaries. Architects must justify every trust relationship and its type.
  • Not all MFA is equal. SMS OTP is phishable. Only FIDO2/WebAuthn and certificate-based authentication are phishing-resistant. The distinction matters for compliance (NIST AAL) and for actual security posture.
  • Token lifetime is a security design decision. Long-lived tokens create revocation windows. Short-lived tokens create operational load. CAE is the modern answer — but it requires resource servers that participate in the protocol. Design token policies deliberately.
