Why this module matters

Protocols are envelopes. Factors are what go inside.

M03a and M03b taught you how identity assertions travel between systems. But neither OAuth nor SAML specifies how strongly the identity must be proven before the assertion is issued. That is the job of the authentication layer — and it is where most enterprise identity breaches occur.

Attackers do not break OAuth. They phish credentials. They steal session cookies. They fatigue users with push notification floods. They compromise TOTP seeds. The protocol is not the vulnerability — the authentication factor is.

This module covers the architecture of MFA systems from the ground up: factor types and their actual security properties (not marketing claims), FIDO2/WebAuthn at protocol depth, PingID's architecture, adaptive risk engines, and the only migration path to phishing-resistant enterprise authentication that actually works at scale.

Factor taxonomy

MFA factors — real security properties, not marketing

Not all MFA is equal. The security industry spent a decade saying "any MFA is better than no MFA" — which was true then. Now attackers have adapted. Real-time phishing proxies (EvilProxy, Modlishka) defeat password + TOTP in seconds. MFA fatigue attacks bypassed Uber and Microsoft. Architects must distinguish between MFA that reduces friction and MFA that is actually phishing-resistant.

Architects designing MFA architectures must distinguish between "MFA deployed" and "phishing-resistant MFA deployed" — and document this distinction explicitly in security design documents.
FIDO2 & WebAuthn

FIDO2 architecture — why it is cryptographically unphishable

FIDO2 is a set of two specifications: W3C WebAuthn (the browser API) and CTAP2 (the Client-to-Authenticator Protocol). Together they enable hardware-bound, phishing-resistant authentication without passwords or shared secrets. Understanding the cryptographic basis is essential — it's not just "more secure MFA"; it's a fundamentally different trust model.

Diagram 1 — FIDO2/WebAuthn: Registration flow (left) & Authentication flow (right)
The origin-binding property — the cryptographic phishing defence
When the authenticator signs the assertion, it includes rpIdHash (the SHA-256 hash of the relying party's domain) and the origin (the exact URL where the credential was created). The signature covers these values.

A phishing site at evil-company.com can display an identical login page. When the user is redirected there and tries to authenticate, the authenticator creates a signature bound to evil-company.com — not company.com. When that signature arrives at the real RP server, the rpIdHash verification fails. The attack is defeated cryptographically — not by user vigilance. The user does not need to spot the fake domain. The authenticator enforces it.
Passkeys — FIDO2 for the enterprise mainstream
Passkeys are FIDO2 credentials that are synced across devices via the platform's cloud keychain (Apple iCloud Keychain, Google Password Manager, Microsoft Hello for Business). Unlike hardware security keys (YubiKey), passkeys are software-managed and device-portable — providing phishing resistance without the friction of carrying a physical token.

Enterprise deployment model: Managed passkeys (bound to device management — MDM/Intune/Jamf) provide stronger assurance than synced passkeys because the private key is bound to a specific managed device's TPM/Secure Enclave, not synced to a cloud keychain. Architects designing enterprise passkey deployments must define the policy boundary between managed passkeys (hardware-bound) and synced passkeys (cloud-synced) and which resource tiers each is acceptable for.
PingID architecture

PingID — your current MFA platform at architectural depth

You work with PingID daily. This section covers how it is architecturally designed — the components, the integration patterns, and the capabilities that go beyond the default push notification flow most operators know.

PingID core architecture
Cloud-brokered MFA service
PingID is a cloud-hosted MFA service. PingFederate integrates with PingID via the PingID adapter (a PingFederate IdP adapter plugin). The authentication flow: user authenticates with password at PingFederate → PingFederate calls PingID API to initiate MFA → PingID sends the factor challenge (push/TOTP/SMS) → user responds → PingID returns success/failure to PingFederate → PingFederate issues the token/assertion.

PingFederate never sees the MFA response — PingID validates it and returns a simple allow/deny signal. This separation means PingID can be updated (new factor types, new security policies) without changing PingFederate configuration.
RADIUS integration
PingID for infrastructure MFA
PingID integrates with RADIUS via the PingID RADIUS PCV (Pluggable Credential Validator) or PingID Integration Kit for RADIUS. This enables MFA for VPN authentication, network device access (via TACACS+ bridge), and legacy systems that only speak RADIUS.

Flow: User connects to VPN → VPN sends RADIUS Access-Request to PingID RADIUS proxy → PingID RADIUS proxy validates password against AD, triggers PingID MFA → User approves push → RADIUS Access-Accept returned to VPN → User gets access. This is the pattern that extends PingID MFA to infrastructure that predates web-based auth.

Policies & adaptive integration
PingID authentication policies
PingID supports authentication policies that determine which factor is required based on: user group, application risk level, device trust (managed vs unmanaged), network location (on-corp vs external), and time of day.

Integration with PingOne Risk (PingID's risk engine) enables fully adaptive authentication — step up to a stronger factor when the risk score exceeds a threshold. Risk signals: geolocation anomaly, new device, impossible travel, known malicious IP, behaviour deviation from baseline.
Adaptive authentication

Risk-based adaptive authentication engine design

Adaptive authentication — also called risk-based authentication — applies the minimum authentication friction required for the assessed risk level. Low-risk logins (known device, corporate network, normal time, familiar location) get SSO with no second factor. High-risk logins (new device, foreign country, off-hours, anomalous behaviour) get strong MFA or are blocked entirely. The challenge is designing the risk engine correctly.

Diagram 2 — Adaptive authentication risk engine decision flow
Adaptive auth design principle — calibrate false positive rate, not just false negative rate
Most risk engine discussions focus on false negatives (legitimate threats not caught). But false positives (legitimate users incorrectly challenged or blocked) are equally damaging — they destroy user trust in the system and create pressure to lower thresholds. The architect's job is to calibrate the engine for both. Monitor: (1) step-up rate per user group (should be <5% for low-risk users), (2) challenge bypass rate (users abandoning sessions on challenge — should be <2%), (3) false positive reports from help desk. Use these metrics to tune thresholds continuously, not set-and-forget.
Step-up authentication

Step-up flows — elevating authentication within a session

Step-up authentication is the pattern of requiring stronger authentication mid-session when a user attempts a sensitive action — without requiring them to log out and back in. It bridges the OAuth/OIDC protocol layer with the risk engine.

1
User authenticates normally (AAL1 or AAL2)
User logs in with password + push notification. IdP issues an access token with acr: urn:mace:incommon:iap:silver (AAL2). The token is valid for normal operations.
OIDC acr_values: "urn:mace:incommon:iap:silver" — moderate assurance
2
User attempts sensitive action (financial transfer, admin action)
The resource server checks the access token's acr claim. The action requires urn:mace:incommon:iap:gold (AAL3 — hardware-bound MFA). Current token is insufficient.
RS returns HTTP 401 with WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="gold"
3
Application initiates step-up re-authorization
The client redirects to the authorization server with acr_values=urn:mace:incommon:iap:gold and prompt=login. The IdP recognizes the existing session but requires additional authentication to meet the requested ACR.
GET /authorize?acr_values=gold&prompt=login&scope=payment:write&max_age=0
4
IdP challenges for the stronger factor
PingFederate/PingID presents the FIDO2 or hardware certificate challenge. User taps their security key or uses biometric. The IdP verifies the higher-assurance factor.
5
New access token issued with elevated ACR
IdP issues a new access token with acr: gold and the specific scope required for the sensitive action. The new token is short-lived (5–10 minutes) — privilege elevation should never be long-lived.
access_token: { acr: "gold", scope: "payment:write", exp: now+300, auth_time: now }
⚠️Design gotchaStep-up tokens must be short-lived — elevated assurance should not persist
A step-up token issued for a payment operation with a 1-hour expiry means the elevated assurance is valid for an hour — the user could initiate multiple high-risk actions without re-authenticating. Design step-up tokens with 5–15 minute TTLs at most, scoped to the specific sensitive operation. The inconvenience of re-authenticating for each high-value action is the point — it is both a security control and an implicit confirmation that the user is intentionally performing the action.
Passwordless rollout

Enterprise passwordless migration — the realistic path

Every enterprise wants passwordless authentication. Most attempts fail because they try to eliminate passwords overnight. The realistic path is a phased migration that progressively moves users to stronger factors while maintaining backward compatibility for systems that cannot support FIDO2.

PhaseWhat changesEnd stateWho is readyTimeline
Phase 0 — Baseline Audit current factor usage. Identify FIDO2-capable devices. Map apps to auth requirements. Complete inventory — no user-facing change Architecture team Month 1–2
Phase 1 — Register passkeys Enable passkey registration alongside existing MFA. Users optionally register a passkey on their managed device. Passkey registered, password + push still works Early adopters, IT staff Month 2–4
Phase 2 — Passkey preferred IdP policy: if passkey available, use it by default. Password + TOTP is fallback for passkey-less devices. Most modern-device users authenticate passwordlessly General workforce Month 4–8
Phase 3 — Password optional Users with registered passkeys can delete their password. IdP policy enforces passkey for FIDO2-capable clients. No password for modern device users FIDO2 device users only Month 8–14
Phase 4 — Legacy handling RADIUS + certificate for infra. Legacy SAML apps get passkey via SAML authn context mapping. End-to-end passwordless for all but irreplaceable legacy systems Architects + platform team Month 12–24
The account recovery problem — the hardest passwordless design challenge
In a password-based system, account recovery is "reset your password via email." In a passwordless system, this fallback reintroduces the exact vulnerability you eliminated. Account recovery is the most commonly overlooked design challenge in passwordless deployments.

Enterprise solutions: (1) Multiple passkeys per user (laptop passkey + hardware key as backup), (2) HR-verified identity recovery process (in-person verification with helpdesk, not email), (3) Temporary access code with immediate passkey re-enrollment requirement, (4) Recovery codes printed and stored in physical safe (for privileged accounts). The design of account recovery is a risk-based decision — the recovery path's security determines the floor of the entire passwordless system's assurance level.
Knowledge check

Test your MFA architecture depth

Q1 Your CISO says "we have MFA — all users use push notifications via PingID." A red team just demonstrated bypassing this MFA using a phishing kit. Explain what happened technically and design a remediation roadmap. ▼
What happened — two possible attacks:

Option A — Real-time phishing proxy: The attacker deployed a reverse proxy (EvilProxy, Modlishka) in front of your login page. The user enters credentials on the phishing page → proxy forwards them to the real PingFederate → PingFederate triggers a PingID push → user approves on their phone (they think they're logging in) → proxy captures the session cookie from the real server → attacker has an authenticated session. The push notification was approved because the user thought the login was legitimate.

Option B — MFA fatigue: Attacker obtained valid credentials (phishing or breached list). They repeatedly attempt login, triggering push notifications. Eventually the user taps Approve to stop the notifications, or taps accidentally during off-hours.

Remediation roadmap:
Immediate (week 1): Enable number matching in PingID push notifications — user must type a code shown on the login screen into the push notification. This defeats real-time proxies (the code is tied to the session). Enable "additional context" — show IP address and location in push notification.
Short-term (month 1–3): Enable PingOne Risk adaptive authentication — impossible travel and new device detections will catch proxy-sourced authentication attempts. Implement FIDO2 registration for all IT staff and privileged users.
Strategic (month 3–18): Migrate general workforce to passkeys via the phased migration approach. Passkeys are origin-bound — the phishing proxy cannot obtain a valid credential even if the user is deceived, because the signature is cryptographically bound to the real domain.
Q2 Design the MFA architecture for a financial services application that requires: (a) normal employee access at AAL2, (b) payment approval operations at AAL3, (c) system admin access at AAL3, (d) VPN access for remote employees, and (e) API access from backend services. ▼
(a) Normal employee access — AAL2: Password + PingID push with number matching. TOTP as backup for offline scenarios. Managed device trust elevates the implicit risk score, reducing step-up frequency. OIDC flow with acr_values="silver".

(b) Payment approval — AAL3 step-up: FIDO2 hardware security key (YubiKey) or managed device passkey (hardware-bound TPM passkey, not synced). Short-lived step-up token (5 min TTL) scoped specifically to payment:approve. The acr_values="gold" OIDC parameter triggers step-up from the resource server when a payment operation is attempted.

(c) System admin access — AAL3: Certificate-based authentication via PIV smart card or hardware-bound certificate on managed device. CyberArk PSM session recording for all privileged sessions. JIT access via PAM — admin role not permanently assigned. PingID FIDO2 as alternative where smart card infrastructure is not deployed.

(d) VPN — AAL2 with device trust: PingID RADIUS integration on the VPN concentrator. Username/password + PingID push with number matching. Device compliance check via MDM (Intune/Jamf) — non-compliant devices blocked regardless of correct credentials. RADIUS Access-Accept only issued when both factors and device posture are validated.

(e) API backend services — no MFA (M2M): Client credentials grant with mTLS client certificate. No user factor possible — this is machine identity. Service accounts stored in CyberArk, rotated on schedule. Scope limited to minimum required API surface. Audit all client credential grants quarterly.
Q3 Explain why a FIDO2 credential registered on company.com cannot be used on evil-company.com, even if the phishing page looks identical. Walk through the cryptographic mechanism. ▼
The origin-binding mechanism — step by step:

During registration: When the passkey was created on company.com, the browser included the rpId (Relying Party ID = "company.com") and the origin ("https://company.com") in the clientDataJSON. The authenticator stored the key pair bound to this rpId. The private key is only accessible to the authenticator when the browser confirms the correct origin is requesting authentication.

During the phishing attack: The user navigates to https://evil-company.com. The phishing page calls navigator.credentials.get() requesting authentication. The browser creates a new clientDataJSON with origin: "https://evil-company.com". The browser passes this to the authenticator via CTAP2.

The cryptographic rejection: The authenticator will only sign using a key if the rpIdHash matches a stored credential's rpId. The rpIdHash in the authentication request = SHA256("evil-company.com"). The stored credential's rpIdHash = SHA256("company.com"). These do not match. The authenticator either returns no credential (the passkey for company.com is not shown as an option) or explicitly rejects the request.

Even if somehow a signature was produced: If a malformed authenticator signed with the wrong rpId, the relying party server verification would fail — it checks that the rpIdHash in authenticatorData matches SHA256(expected_rpId). A mismatch fails verification.

The result: The phishing site cannot obtain a valid FIDO2 assertion for company.com. It is not user vigilance that prevents the attack — it is a cryptographic property enforced by the authenticator and verified by the server.
Q4 Your adaptive auth engine has a 15% step-up rate — 15% of all logins trigger an additional factor challenge. Business users are complaining about friction. How do you diagnose the problem and what do you tune? ▼
15% step-up is too high for a well-calibrated adaptive auth engine — target for most enterprise deployments is 2–5% for the general workforce. Here is the diagnostic and tuning process:

Step 1 — Segment the step-up data: Break down the 15% by: which signal is triggering challenges most frequently (device fingerprint? geolocation? time pattern?), which user populations are being challenged most (frequent travelers? field workers? executives?), what time patterns dominate (Monday morning surges? VPN logins?).

Most common causes of inflated step-up rates:
(1) Device fingerprint sensitivity: Browser updates, clearing cookies, or private/incognito mode all change the fingerprint → tune device trust to use MDM enrollment status as primary signal rather than browser fingerprint alone.
(2) IP reputation overreach: If your corporate VPN IPs are classified as "suspicious" by the threat intel feed, or users are on hotel WiFi that shares ranges with known bad actors → tune IP reputation weight down, rely more on device trust.
(3) Time pattern miscalibration: Employees working across time zones, flextime workers, or on-call staff all show "anomalous" time patterns → feed shift schedules into the engine or widen the acceptable window.
(4) New device threshold: If every new corporate device triggers a step-up before MDM enrollment completes → integrate MDM enrollment status so enrolled devices are trusted immediately on first auth.

Tuning approach: Use a dry-run mode — log what would have been challenged without actually challenging users. Review the distribution. Adjust signal weights. Re-evaluate after 2 weeks. Target: <5% step-up for managed-device users, <15% for BYOD.

Key takeaways — M04a · MFA, Passwordless & Adaptive Auth
  • Not all MFA is equal — there is a critical distinction between "MFA deployed" and "phishing-resistant MFA deployed." TOTP and push notifications are phishable via real-time proxy attacks. Only FIDO2/WebAuthn and certificate-based authentication are cryptographically phishing-resistant.
  • FIDO2 is unphishable because credentials are origin-bound. The private key is hardware-bound and never leaves the authenticator. The signature covers the rpIdHash (domain hash) — a phishing site on a different domain cannot produce a valid assertion for the real domain.
  • PingID architecture: Cloud-brokered MFA adapter for PingFederate. Integrates with RADIUS for infrastructure MFA. Supports push with number matching, TOTP, FIDO2, biometric, and SMS. Number matching mitigates MFA fatigue attacks.
  • Adaptive authentication calibrates friction to risk. The risk engine collects signals (geolocation, device fingerprint, impossible travel, threat intel, behaviour baseline), scores them, and applies policy — SSO for low risk, step-up for medium, strong MFA for high, block for critical. Tune for both false negatives (missed threats) and false positives (annoyed legitimate users).
  • Step-up authentication elevates assurance mid-session without logout. OIDC acr_values requests a specific assurance level; the IdP challenges for the appropriate factor. Step-up tokens must be short-lived (5–15 min) and scoped to the specific sensitive operation.
  • Passwordless migration requires a phased approach — register passkeys alongside existing factors, make passkeys preferred, then optional password removal. Account recovery design is the hardest challenge and determines the floor assurance of the entire passwordless system.
