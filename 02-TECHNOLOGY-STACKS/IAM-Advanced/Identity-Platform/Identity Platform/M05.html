Why this module matters

The ungoverned attack surface

After a successful credential attack, an attacker doesn't stay where they landed. They move laterally — across the network, onto servers, escalating privileges at every hop. The path typically goes: phished user credential → VPN access → lateral movement to a Linux server → privilege escalation via a misconfigured sudo rule → access to a privileged service account → domain compromise.

Every step in that path involves infrastructure identity — the authentication mechanisms below the application layer that most IAM programs never touch. RADIUS governs VPN and Wi-Fi authentication. 802.1X governs network port access. PAM governs Linux login. SSSD connects Linux systems to Active Directory. SSH keys are the privileged credentials that enable lateral movement.

Architects who cannot describe infrastructure identity cannot design a complete zero trust architecture. This module covers it at the depth needed for architecture and design decisions — not as a sysadmin configuration guide, but as an IAM architect's threat model and integration pattern reference.

RADIUS architecture

RADIUS — enterprise network authentication hub

RADIUS (Remote Authentication Dial-In User Service, RFC 2865) is the protocol used to authenticate network access requests from VPN clients, Wi-Fi associations, and network device logins. Despite its age (1997), it is the dominant protocol for network authentication in enterprise environments.

RADIUS AAA — Authentication, Authorization, Accounting
RADIUS provides three services: Authentication (verifies the identity of the network access requester), Authorization (determines what network access the requester is permitted), and Accounting (logs session start, stop, bytes transferred — the audit trail for network access).

The RADIUS server (NPS on Windows, FreeRADIUS on Linux, PingID RADIUS proxy) receives Access-Request packets from the Network Access Server (NAS — the VPN concentrator, Wi-Fi controller, or network switch) and returns Access-Accept, Access-Reject, or Access-Challenge. The NAS never sees the user's credentials being validated — it only receives a pass/fail decision from the RADIUS server.
Diagram 1 — RADIUS proxy chain architecture with PingID MFA integration
TACACS+ vs RADIUS
Which protocol for which use case
RADIUS — network access authentication (VPN, Wi-Fi, 802.1X). Uses UDP. Encrypts only the password in the packet. Combines Authentication + Authorization in a single exchange. Industry standard for end-user network access.

TACACS+ (Cisco-developed) — privileged device management (SSH to routers, switches, firewalls). Uses TCP. Encrypts the entire packet body. Separates Authentication, Authorization, and Accounting into independent exchanges. Provides per-command authorization — an admin can be allowed to run show interface but not reload. The right protocol for managing network infrastructure.

Architect's rule: RADIUS for user network access. TACACS+ for admin device access.
EAP method selection
Which EAP method for which scenario
EAP-TLS — Client presents X.509 certificate. Mutual authentication (server also presents cert). Phishing-resistant. Highest security. Requires PKI infrastructure and client certificate deployment. Use for managed corporate devices where certificates can be deployed via MDM/GPO.

PEAP-MSCHAPv2 — Username/password inside a TLS tunnel. No client certificate required. Most widely deployed EAP method for enterprise Wi-Fi. Vulnerable to credential harvesting via rogue access points if the server certificate is not strictly validated.

EAP-TTLS — Similar to PEAP but more flexible inner authentication. Less common in enterprise.

Decision: EAP-TLS for high-security (certificate-based, managed devices). PEAP-MSCHAPv2 for general workforce Wi-Fi with strict server cert validation enforced via MDM policy.
Network access control

802.1X — port-based network access control

IEEE 802.1X is the standard for port-based network access control — the mechanism that prevents an unmanaged device from connecting to the corporate network simply by plugging in an Ethernet cable or connecting to a Wi-Fi SSID. It uses RADIUS as the backend authentication protocol.

802.1X three-party model — Supplicant, Authenticator, Authentication Server
Supplicant — the client device (laptop, phone, IoT device) attempting network access. Runs the EAP protocol client. Windows built-in 802.1X supplicant, Apple's native 802.1X, or Cisco AnyConnect for managed devices.

Authenticator — the network access device (managed switch port or Wi-Fi access point). Controls the port — in "unauthorized" state, only EAP traffic is allowed through. Once authentication succeeds, the port opens for regular traffic. The authenticator does not validate credentials — it passes EAP messages to the authentication server.

Authentication Server — the RADIUS server (NPS, FreeRADIUS, Cisco ISE). Validates credentials, makes policy decisions, and returns the port authorization state to the authenticator including VLAN assignment.
NAC use case 1
Corporate wired access
Managed laptop connects to ethernet → switch port in unauthorized state → 802.1X supplicant sends EAP-Identity → RADIUS validates certificate (EAP-TLS) → RADIUS returns Access-Accept with VLAN=Corporate → port opens. Unmanaged device: no certificate → Access-Reject → port stays in guest VLAN or blocked.
NAC use case 2
Enterprise Wi-Fi (WPA3-Enterprise)
Employee connects to SSID=Corp-WiFi → AP requires 802.1X → PEAP-MSCHAPv2 with AD credentials + PingID MFA via RADIUS proxy → RADIUS returns VLAN assignment → user on corporate VLAN. Guest SSID uses pre-shared key (no 802.1X) → isolated internet-only VLAN.
NAC use case 3
Device posture + VLAN segmentation
Cisco ISE or similar NAC platform evaluates device posture (MDM enrolled? Antivirus current? OS patched?) alongside authentication. Non-compliant device authenticated successfully but placed in Remediation VLAN with only update server access. Posture re-evaluated periodically via RADIUS CoA.
⚠️Architecture gotcha802.1X without server certificate validation enables credential harvesting via rogue APs
In PEAP-MSCHAPv2 deployments, if the supplicant is not configured to validate the RADIUS server's certificate, an attacker can deploy a rogue access point broadcasting the same SSID. The supplicant connects, the attacker's AP responds to EAP-Identity, and the inner tunnel is established against the rogue server — handing the attacker the user's MSCHAPv2 challenge/response, which can be cracked offline. Enforce server certificate validation via MDM/GPO policy on all managed devices. Configure the trusted CA and expected server name. Without this, PEAP-MSCHAPv2 provides false assurance.
Linux authentication

PAM — the Linux authentication framework

PAM (Pluggable Authentication Modules) is the framework that governs authentication on every Linux and Unix system. Every login, every sudo, every SSH session, every su command goes through PAM. Understanding PAM architecturally — not as a config file author, but as an IAM architect — is what allows you to design centralized Linux authentication and enforce MFA on infrastructure access.

PAM's architectural role — the authentication delegation framework
Instead of each application implementing its own authentication logic, PAM provides a common API. Applications (sshd, sudo, login, su) call pam_authenticate() and delegate the decision entirely to the PAM stack configured in /etc/pam.d/servicename.

The PAM stack is a sequence of module calls, each with a control flag: required (must pass; failure doesn't abort immediately), requisite (must pass; failure aborts immediately), sufficient (if passes, stack is satisfied), optional (result doesn't affect overall outcome). The final result is a combination of all required/requisite module outcomes.

Key modules architects care about: pam_sss (delegates to SSSD for centralized auth), pam_krb5 (Kerberos authentication), pam_ldap (LDAP authentication), pam_mkhomedir (creates home dir on first login), pam_limits (resource limits), pam_google_authenticator / pam_pingid (MFA modules).
PAM MFA integration
Adding MFA to Linux SSH
PingID and other MFA solutions provide PAM modules (pam_pingid.so). Inserting this module into the SSH PAM stack requires both password authentication and MFA approval before SSH access is granted.

Stack design: auth required pam_sss.so (password via AD)
auth required pam_pingid.so (PingID push/TOTP)
auth required pam_deny.so (deny if above fail)

This extends PingID MFA to server SSH access — the same user experience as web app MFA, applied to infrastructure access. This is a critical gap in most enterprise PAM programs.
sudo governance via PAM
Privilege delegation on Linux
sudo is the primary privilege delegation mechanism on Linux. Its configuration (/etc/sudoers or /etc/sudoers.d/) defines which users can run which commands as which principals.

Architecture principle: sudoers rules should be managed centrally, not per-server. Options: (1) Deploy via configuration management (Ansible/Puppet) from a central repository, (2) Use AD group membership to drive sudo access (SSSD + sssd.conf sudo provider), (3) Use CyberArk PSM for Linux to proxy all privilege commands through the PAM vault.

Unmanaged local sudoers files across hundreds of servers are an unauditable privilege sprawl problem — the Linux equivalent of unmanaged local admin accounts.
Centralized Linux auth

SSSD — enterprise Linux identity bridge

SSSD (System Security Services Daemon) is the component that makes Linux a first-class citizen of the enterprise identity ecosystem. It bridges Linux systems to Active Directory, LDAP, and Kerberos — handling authentication, group membership lookup, and caching for offline scenarios.

SSSD's three critical functions
1. Identity resolution (NSS): When a Linux command runs getpwnam("alice") or id alice, SSSD answers — returning user attributes and group memberships from AD/LDAP. This makes AD users visible to the Linux OS without local /etc/passwd entries.

2. Authentication delegation (PAM): The pam_sss module asks SSSD to authenticate a user. SSSD validates credentials against AD/Kerberos/LDAP and returns pass/fail. The application (SSH, sudo) never touches AD directly.

3. Offline caching: SSSD caches the last successful authentication result. If the domain controller is unreachable (network outage, DNS failure), users can still authenticate against the local cache. The cache_credentials = true option in sssd.conf enables this. Cache TTL is configurable — default 24 hours.
1
realm join — joining Linux to Active Directory
The realm join company.com command (using the realmd utility) enrolls the Linux system as a computer object in AD, configures Kerberos (/etc/krb5.conf), configures SSSD (/etc/sssd/sssd.conf), and modifies PAM and NSS to use SSSD. This single command replaces what previously required manual configuration of five separate files.
realm join -U admin@company.com company.com
2
User authenticates via SSH
SSH daemon receives login attempt for alice@company.com. sshd calls PAM → PAM calls pam_sss → SSSD checks its cache. Cache miss: SSSD sends Kerberos AS-REQ to the AD KDC with Alice's credentials. KDC validates and returns TGT. SSSD caches the result and returns success to PAM.
3
Group-based access control
SSSD's access_provider = ad + ad_access_filter allows access control based on AD group membership. Only users in the linux-admins@company.com AD group are permitted to log in. No local /etc/group management needed — group changes in AD propagate automatically within SSSD's cache TTL.
access_provider = ad, ad_access_filter = memberOf=CN=linux-admins,OU=Groups,DC=company,DC=com
4
Offline login (DC unreachable)
SSSD returns credentials from its local cache when the domain controller is unreachable. The user authenticates against the cached credentials. Security consideration: the cache only contains credentials from the last successful online authentication — if a user's account is disabled in AD, they can still authenticate offline until the cache expires or is manually cleared.
sss_cache -u alice # Flush Alice's cache entry — forces re-authentication against AD on next login
⚠️Security gotchaSSSD offline cache creates a deprovisioning window — terminated users can still log in
When a user is terminated in AD (account disabled), the PAM authentication check against SSSD will use the cached credentials for the duration of the cache TTL (default 24 hours). An attacker with the terminated employee's credentials can still authenticate to Linux servers where SSSD has a cached entry. Remediation: (1) Reduce SSSD cache TTL for privileged servers, (2) Run sss_cache -u username as part of the termination runbook on all critical servers, (3) Implement Leaver automation that flushes SSSD caches via Ansible/Salt at termination time. This is a common IGA-to-infrastructure deprovisioning gap.
SSH certificate authority

SSH CAs — replacing key sprawl with certificate governance

SSH public key authentication is the dominant method for privileged server access — and it is one of the most poorly governed credential types in most enterprises. Understanding SSH certificate authorities is essential for any architect designing infrastructure PAM or zero trust for Linux.

The SSH key sprawl problem — why authorized_keys fails at scale
In the traditional SSH model: each user generates a key pair. The public key is added to ~/.ssh/authorized_keys on each server the user needs to access. With 200 servers and 50 engineers, that is 10,000 potential key entries to manage. Problems: (1) No central revocation — disabling an engineer requires removing their key from 200 servers. (2) No expiry — keys last forever unless manually removed. (3) No audit trail — which key was used when is often not logged. (4) Shared keys — the same key pair used everywhere means one compromise affects everything.
Diagram 2 — SSH Certificate Authority: issuance & authentication flow
Automatic expiry — 8-hour certs expire. No manual cleanup. Compromise window is bounded. ✓ Instant revocation — rotate CA key and ALL certificates become invalid. One operation, all servers. ✓ No per-server config — servers trust the CA public key, not individual user keys. One TrustedUserCAKeys config line. ✓ Audit identity — key_id in every session log. Know exactly whose certificate was used and when it was issued. ✓ MFA enforcement — SSH CA only issues cert after AD auth + MFA. Every certificate issuance is a MFA-verified action. ✓ Scalability — 1,000 servers need zero configuration changes when onboarding a new engineer. Just issue a cert.
Threat model

Infrastructure identity attack surface

Infrastructure identity is consistently the most exploited layer in enterprise breaches. Understanding the attack surface is what connects this module to M11 (Identity Security) and justifies the architectural controls covered above.

Attack vector 1
SSH key harvesting & lateral movement
Attacker compromises one Linux server → finds SSH private keys in ~/.ssh/ or deployment pipelines → uses keys to authenticate to other servers (the key may be in authorized_keys on hundreds of systems).

Why it works: No expiry on SSH keys. No central visibility into which keys exist where. Keys often shared between environments (dev → prod same key).

Architectural defence: SSH certificate authority (short-lived certs + MFA-gated issuance). Remove all long-lived SSH keys from servers. Require cert-based auth only.
Attack vector 2
sudo misconfiguration — privilege escalation
Attacker with a low-privilege account finds a misconfigured sudo rule — ALL=(ALL) NOPASSWD: /bin/bash or an overly permissive wildcard. Single sudo command → root shell.

Why it works: Local sudoers files diverge from policy over time. Configuration drift is invisible without central auditing. NOPASSWD rules are convenient and never reviewed.

Architectural defence: Central sudoers management (Ansible, SSSD sudo provider). Audit all NOPASSWD rules quarterly via IGA certification. CyberArk PSM for Linux proxies all privilege commands — no direct sudo to root.
Attack vector 3
RADIUS shared secret compromise
The RADIUS protocol uses a shared secret between the NAS and the RADIUS server to protect packets. If the shared secret is weak, reused, or extracted from a network device config backup, an attacker can forge Access-Accept responses or decrypt RADIUS traffic.

Architectural defence: Generate cryptographically random shared secrets (32+ characters) per NAS. Store in PAM vault (CyberArk). Rotate annually or on NAS replacement. Use RadSec (RADIUS over TLS, RFC 6614) for transit encryption instead of relying on the shared secret alone.
Attack vector 4
SSSD cache — offline authentication after termination
As detailed in the SSSD section — terminated employee credentials can authenticate to Linux servers for up to 24 hours after account disable in AD, if SSSD cache is not flushed.

Architectural defence: Automated cache flush as part of Leaver runbook. Reduce cache TTL to 4 hours on sensitive servers. Integrate IGA termination workflow with infrastructure automation (Ansible/Salt) to flush SSSD cache on critical server groups.

Q1 Your enterprise has 3,000 Linux servers. Engineers currently use long-lived SSH key pairs stored in their home directories. Design a migration to SSH certificate-based authentication with MFA-gated issuance. ▼
SSH Certificate Authority migration — phased approach:

Phase 1 — Build the CA service (Month 1–2): Deploy an SSH CA service (HashiCorp Vault SSH secrets engine, or open-source Teleport, or a custom CA using OpenSSH ssh-keygen -s with AD auth + PingID integration). The CA service: (1) authenticates the requesting engineer against AD, (2) verifies MFA via PingID API, (3) signs a short-lived certificate (8 hours) with the engineer's AD UPN as the principal, (4) returns the certificate. Store the CA private key in an HSM or Vault transit engine.

Phase 2 — Server-side trust (Month 2–3): Deploy the CA public key to all 3,000 servers via Ansible: add TrustedUserCAKeys /etc/ssh/ca.pub to /etc/ssh/sshd_config. This enables certificate-based auth alongside existing key auth — no disruption yet.

Phase 3 — Engineer migration (Month 3–5): Communicate the new workflow. Engineers request certs via CLI tool or web UI (authenticates → issues cert → loads into ssh-agent automatically). Document the workflow. Run in parallel — both key-based and cert-based auth accepted.

Phase 4 — Disable legacy keys (Month 6): Audit which servers still have authorized_keys entries (via Ansible scan). Set a deadline. Disable AuthorizedKeysFile in sshd_config on all servers. Only certificate-based auth accepted.

Monitoring: Alert on any SSH authentication using a long-lived key after Phase 4. Any key-based auth attempt is now anomalous and indicates a misconfigured server or a compromised endpoint.
Q2 A security audit finds that the corporate Wi-Fi (WPA2-Enterprise, PEAP-MSCHAPv2) has been successfully attacked using a rogue access point to harvest employee credentials. What happened, why, and what is the remediation architecture? ▼
What happened: An attacker deployed a rogue Wi-Fi access point broadcasting the same SSID as the corporate Wi-Fi. Employee devices configured to "auto-connect to known networks" connected to the rogue AP. The rogue AP initiated an 802.1X EAP handshake. Since the supplicants were not configured to validate the RADIUS server's TLS certificate, the PEAP tunnel was established against the attacker's server. The inner MSCHAPv2 challenge/response was captured by the attacker. Offline cracking of MSCHAPv2 (via Asleap or similar) recovered plaintext credentials.

Root cause: Supplicant certificate validation was either disabled or not configured. Employees' devices accepted any certificate presented by a "RADIUS server" — including a self-signed cert from the attacker's laptop.

Remediation architecture:
Immediate: Force password resets for all employees who connected to corporate Wi-Fi in the affected time window (RADIUS accounting logs identify who was connected).

Short-term (2–4 weeks): Push MDM/GPO policy to all managed devices: (1) Configure the trusted CA for RADIUS server validation (the internal CA that signed the NPS/RADIUS certificate), (2) Specify the expected server name in the certificate CN/SAN, (3) Set "Do not prompt user to authorize new servers or trusted certification authorities" to prevent users from approving rogue certs.

Strategic: Migrate corporate Wi-Fi from PEAP-MSCHAPv2 to EAP-TLS (certificate-based). Deploy client certificates to managed devices via MDM. EAP-TLS is immune to rogue AP attacks because the attacker cannot produce a valid client certificate even if they have a valid server certificate.
Q3 Design the complete Linux authentication architecture for a 500-server fleet where: engineers need SSH access from managed laptops, service accounts run automated jobs, and all privileged access must be audited. Integrate with your existing AD, PingID, and CyberArk environment. ▼
Three distinct identity flows — each needs separate architecture:

Flow 1 — Engineer interactive SSH access: All 500 servers joined to AD via SSSD realm join. SSH CA service (Vault or Teleport) integrated with AD auth + PingID MFA. Engineers request short-lived certificates (8-hour TTL). SSH cert presented at login → sshd validates against CA pubkey → SSSD maps to AD user → PAM session started. No long-lived SSH keys. Every session logged with cert key_id (engineer identity + issuance time). Group-based access control via SSSD (only members of linux-access AD group can SSH).

Flow 2 — Service account automation (no interactive MFA): Service accounts use long-lived certificates (30-day) issued by the CA, stored in CyberArk as managed credentials. Automation pipelines (Jenkins, Ansible, GitLab CI) retrieve fresh certificates from CyberArk before each run via the Conjur/CyberArk API. Certificate rotation automated by CyberArk CPM. Service accounts have no interactive shell access (AllowUsers in sshd_config restricts them to specific source IPs).

Flow 3 — Privileged access (root/admin) via CyberArk PSM: No direct root SSH from engineer workstations. Engineers request privileged access via CyberArk PVWA → JIT approval workflow → CyberArk PSM SSH proxy session → audited session recording. PSM connects to target server using a managed privileged account. Engineer never sees the privileged credential. All commands recorded and indexed for SOC review.

SSSD HA design: Configure two AD domain controllers per site in sssd.conf. Offline cache TTL = 4 hours for privileged servers, 24 hours for non-critical. Cache flush automation integrated into Leaver termination runbook via Ansible.
Q4 TACACS+ vs RADIUS — a network engineer says "we use RADIUS for everything including device management." As the IAM architect, what is your response and what is the correct architecture? ▼
RADIUS for device management is a common and architecturally incorrect pattern.

What RADIUS is missing for device management: (1) Per-command authorization — RADIUS handles authentication and returns a static authorization level (privilege level 1–15 in Cisco terms). It cannot say "this engineer can run show commands but not configure commands." TACACS+ provides per-command authorization as a first-class feature. (2) Accounting completeness — RADIUS accounting for device management captures session start/stop but not individual commands. TACACS+ logs every command executed during the session — essential for compliance auditing of network device changes. (3) Encryption — RADIUS encrypts only the password. TACACS+ encrypts the entire packet body. On management plane traffic, full encryption is appropriate.

Correct architecture: RADIUS for end-user network access (VPN, Wi-Fi, 802.1X). TACACS+ for privileged device management (SSH to routers, switches, firewalls, load balancers). Deploy a TACACS+ server (Cisco ISE, tac_plus) alongside the RADIUS infrastructure. Define command authorization sets: read-only operators get show commands only. Network engineers get configuration commands. Network architects get global config access. All command executions logged to SIEM.

The business case to make to the network team: In a SOX or PCI audit, "who changed this network ACL and when?" requires TACACS+ command accounting. RADIUS cannot answer that question. The cost of deploying TACACS+ is far lower than the cost of a compliance finding.

Key takeaways — M05 · Infrastructure Identity
  • Infrastructure identity is the most exploited and least governed IAM layer in most enterprises. SSH key sprawl, unmanaged sudo rules, SSSD cache gaps, and weak RADIUS shared secrets are consistently exploited in real breaches. Architects who don't govern this layer leave the highest-risk attack surface open.
  • RADIUS is the network authentication protocol for VPN, Wi-Fi, and 802.1X. PingID integrates via RADIUS proxy — password validation against AD + MFA trigger in a single RADIUS exchange. RADIUS CoA enables mid-session policy enforcement (network-layer equivalent of CAE).
  • TACACS+ is the correct protocol for privileged device management — per-command authorization, full packet encryption, and complete command audit logging. RADIUS lacks all three for device admin use cases.
  • 802.1X PEAP-MSCHAPv2 requires server certificate validation enforced via MDM — without it, rogue access points can harvest credentials. EAP-TLS (certificate-based) is phishing-resistant and the long-term target for managed device environments.
  • PAM is the Linux authentication delegation framework — all authentication goes through the PAM stack. Adding PingID MFA to the PAM stack extends enterprise MFA to SSH access on Linux servers.
  • SSSD bridges Linux to Active Directory — centralized auth, group-based access control, and offline caching. SSSD cache creates a deprovisioning window: terminated user credentials remain valid until cache expiry. Flush via Leaver automation.
  • SSH Certificate Authorities replace key sprawl with governed, short-lived credentials. MFA-gated issuance, 8-hour TTL, automatic expiry, instant CA rotation = revocation. One TrustedUserCAKeys config line on all servers. No per-server authorized_keys management.
