Why this module matters

From consumer to architect

Every engineer who has built an API integration has used OAuth. Very few have had to design the authorization server itself, architect the token service, or justify grant type selection under adversarial conditions. At Principal Engineer and IAM Architect level, you will be asked all three — and the answers require understanding OAuth at a depth most practitioners never reach.

This module covers OAuth 2.0 and OIDC as design disciplines, not configuration exercises. You will understand why PKCE was invented (the exact attack it prevents), what DPoP adds that bearer tokens cannot provide, how the authorization server's token endpoint is engineered at scale, and how OIDC sits on top of OAuth without replacing it.

Your 5 years of OAuth experience means we skip the basics entirely. We start at the architectural and security decision layer — grant type selection logic, advanced specifications, token service architecture, and the engineering of OIDC discovery. Everything in M04a through M16 assumes fluency with what this module covers.

The OAuth 2.0 framework

What OAuth actually is — and isn't

OAuth 2.0 (RFC 6749) is an authorization framework — not an authentication protocol. This distinction, which M02 introduced conceptually, has concrete architectural consequences: OAuth defines how a resource owner grants a client limited access to a resource server on their behalf. It says nothing about who the resource owner is.

The four roles are foundational to every OAuth flow:

Role 1
Resource Owner
The entity capable of granting access to a protected resource. Usually a human user, but can be the application itself (in client credentials flows). The resource owner authorizes — they do not authenticate to the resource server directly.
Role 2
Authorization Server (AS)
Issues access tokens after successfully authenticating the resource owner and obtaining authorization. The AS is the trust anchor. PingFederate, Okta, Entra ID all function as authorization servers. This is the component architects design — it has the most architectural complexity.
Role 3
Resource Server (RS)
Hosts the protected resources and accepts access tokens. The RS validates the token (signature, expiry, scope, audience) on every request and enforces authorization based on claims. The RS is stateless in modern architectures — it validates JWTs without calling back to the AS.
Role 4
Client
The application requesting access on behalf of the resource owner. Clients are classified as confidential (can securely hold a secret — server-side apps) or public (cannot hold a secret — SPAs, mobile apps). This classification drives every security decision about which grant type is safe to use.
The critical architectural insight: public vs confidential clients
Any client running code that a user can inspect (browser JavaScript, mobile app binary) is a public client — it cannot hold a client secret securely. This is not a policy limitation; it is a physical reality. This single fact is why PKCE was invented, why implicit flow was deprecated, and why every SPA must use authorization code + PKCE with no client secret. Architects who don't understand this distinction make the same recommendation for SPAs and server-side apps — which produces vulnerable systems.
Grant types

Six grant types — selection logic

Grant types are not features to pick by preference — they are security designs that match specific client types and use cases. Selecting the wrong grant type is a security vulnerability, not a configuration choice. Here is the complete selection framework.

G1 Authorization Code + PKCE Recommended
The gold standard for any flow involving a human user. The browser redirects to the AS, the user authenticates, an authorization code is issued, and the client exchanges the code for tokens via a back-channel request. PKCE (Proof Key for Code Exchange) prevents authorization code interception attacks for public clients.
Use when: User is present. Any client type — confidential or public. Web apps, SPAs, mobile. The default choice for all interactive flows.
G2 Client Credentials M2M flows
The client authenticates directly to the AS using its own credentials (client ID + secret, or mTLS, or private key JWT). No user is involved. The client IS the resource owner. This is the grant type for service-to-service API calls, background jobs, and daemon processes.
Use when: No user present. Confidential client only. Machine-to-machine. Microservice calling an API. Never for public clients — they cannot hold a client secret.
G3 Device Authorization (Device Code) Input-limited
Designed for devices with no browser or limited input (Smart TVs, CLI tools, IoT). The device gets a device code and displays a URL and user code. The user authenticates on a separate device. The device polls the AS until the user completes authentication.
Use when: Device has no browser or limited input. CLI tools (AWS CLI, GitHub CLI use this). Smart TV apps. IoT devices requiring user authorization.
G4 Refresh Token Lifecycle
Not a standalone grant — used in combination with other grants to obtain new access tokens without requiring the user to re-authenticate. Refresh tokens are long-lived, scoped, and must be stored securely. Rotation (issuing a new refresh token on each use) is the current best practice to detect theft.
Use when: Need to maintain user sessions beyond access token lifetime. Confidential clients: store in secure backend. Public clients: use refresh token rotation + sender-constraint (DPoP).
G5 Token Exchange (RFC 8693) Advanced
Allows one token to be exchanged for another — enabling impersonation, delegation, and cross-service identity propagation. Service A receives a user's token, exchanges it for a new token scoped for Service B, without the user re-authenticating. Critical for microservice architectures where identity must propagate through service call chains.
Use when: Microservice-to-microservice with user context. Identity propagation across service boundaries. Impersonation flows for support tooling. Federation between different AS instances.
G6 Implicit (DEPRECATED) Do not use
Issued tokens directly in the redirect URL fragment. No code exchange, no back-channel. Deprecated in OAuth 2.1 because tokens in redirect URLs are exposed in browser history, referrer headers, and server logs. Any system still using implicit flow is carrying a known vulnerability. Migrate to authorization code + PKCE.
Never use. Retained here only because you will encounter it in legacy systems. The only correct action is migration to G1. There is no secure configuration of implicit flow.
⚠️GotchaResource Owner Password Credentials (ROPC) — the seventh grant nobody should use
ROPC (not listed above) allows the client to collect the user's username and password directly and exchange them for tokens. It completely bypasses the AS redirect flow. It is the single most dangerous OAuth grant type. It cannot support MFA (the client handles credentials, not the AS). It trains users to enter their password into third-party apps. It was removed from OAuth 2.1. If you encounter a system using ROPC, treat it as a critical security finding.
PKCE — deep dive

Why PKCE exists — the exact attack it prevents

PKCE (RFC 7636 — pronounced "pixy") is not just a "security enhancement." It is the specific cryptographic mechanism that makes authorization code flow safe for public clients. Understanding the attack it prevents is the only way to understand why it is mandatory.

The authorization code interception attack (the problem PKCE solves)
On mobile operating systems, multiple apps can register as handlers for a custom URL scheme. A malicious app can register the same redirect URI as the legitimate app. When the AS redirects with the authorization code to myapp://callback?code=abc123, the OS may deliver it to the malicious app instead. The malicious app now has the authorization code and can exchange it for tokens — the legitimate app gets nothing. This attack is impossible to prevent at the network level because it happens at the OS redirect layer.

⚡ Why PKCE works
The code_verifier is generated by the legitimate client and never transmitted until the token exchange (step 7). When the malicious app intercepts the authorization code (step 6), it has no knowledge of the code_verifier that the legitimate client holds. When the malicious app attempts to exchange the code, it cannot produce the correct verifier — the AS rejects it. The legitimate client exchanges successfully. The authorization code is now useless without the paired verifier.
Advanced OAuth specifications

PAR, DPoP, RAR & CIBA

The OAuth ecosystem has evolved significantly beyond the base RFC 6749 specification. These four advanced specifications are increasingly required for enterprise-grade deployments, regulated industries, and high-security environments. Understanding them positions you as an architect who is ahead of current enterprise adoption.

PAR — RFC 9126
Pushed Authorization Requests
Problem it solves: In standard auth code flow, authorization parameters (scope, redirect_uri, client_id, state) are sent in the browser's URL — they're exposed to the browser history, referrer headers, and intermediary proxies. A malicious script on the page can read or manipulate them.

How PAR works: Before the browser redirect, the client POSTs all authorization parameters directly to the AS's PAR endpoint (/as/par). The AS returns a short-lived request_uri. The browser redirect only carries this opaque URI — no parameters are visible.

Architectural benefit: Authorization parameters are transmitted server-to-server, validated by the AS before the browser is involved. Required by FAPI 2.0 (Financial-grade API).
DPoP — RFC 9449
Demonstration of Proof-of-Possession
Problem it solves: Bearer tokens are like cash — whoever holds them can use them. If a token is stolen from memory, a log file, or a network intercept, it is immediately usable by the attacker.

How DPoP works: The client generates an asymmetric key pair. When requesting a token, it sends a signed DPoP proof (a JWT containing the HTTP method, URI, timestamp, and a nonce). The token is bound to the client's public key. On each API request, a fresh DPoP proof is sent alongside the token. The RS verifies both the token and the proof's signature.

Architectural benefit: A stolen token is useless without the private key. Sender-constrained tokens are now required for high-security OAuth deployments and FAPI 2.0.
RAR — RFC 9396
Rich Authorization Requests
Problem it solves: OAuth scopes are strings — read:accounts, payment:initiate. They are inherently coarse-grained and cannot express fine-grained authorization intent such as "transfer exactly £500 to account 12345 on behalf of user X between 9am–5pm."

How RAR works: Introduces an authorization_details parameter that carries a structured JSON object describing the exact authorization requested — type, actions, locations, identifiers. The AS validates the request and embeds corresponding claims in the token.

Architectural benefit: Enables authorization requests as rich as the application's business logic requires. Required for Open Banking, payment APIs, and healthcare data sharing (SMART on FHIR).
CIBA — OpenID CIBA spec
Client-Initiated Backchannel Authentication
Problem it solves: Standard OAuth requires the user to be present at a browser. Many enterprise scenarios need to authenticate a user on a separate channel — a bank teller initiating a transaction that the customer approves on their phone, or a call center authenticating a caller.

How CIBA works: The client sends an authentication request directly to the AS (no browser redirect). The AS contacts the user's device (push notification, SMS, email). The user authenticates on their device. The AS notifies the client (poll, ping, or push delivery). The client exchanges for tokens.

Architectural benefit: Decouples the authentication session from the user's current device. Enables step-up authentication in call center flows, POS terminals, and IoT contexts.
OpenID Connect

OIDC — the identity layer on OAuth

OpenID Connect 1.0 adds an identity layer on top of OAuth 2.0. It does not replace OAuth — it extends it. Understanding exactly what OIDC adds (and what it leaves to OAuth) is essential for designing systems that correctly handle both authentication and authorization.

What OIDC adds to OAuth — precisely
OAuth 2.0 issues an access token that authorizes API calls — it says nothing about who the user is. OIDC adds three things: (1) An ID token (a signed JWT containing identity claims about the authenticated user — sub, email, name, nonce, auth_time). (2) A UserInfo endpoint (/userinfo) for retrieving additional identity claims. (3) A Discovery document (/.well-known/openid-configuration) that publishes the AS's endpoints and public keys, enabling clients to configure themselves automatically.
Diagram 2 — Authorization Server internal architecture

The Token Issuance Service inside the AS is the highest-value component from a platform engineering perspective. It must: sign tokens with the correct algorithm (RS256 preferred, ES256 for smaller tokens), embed the correct claims based on scope and client, enforce token TTL policy, and handle key rotation transparently. In M12 (Platform Engineering) you will design this component as a Java microservice.

JWT architecture

JWT — structure, validation & security

JWTs are the token format used by OAuth access tokens (when self-contained) and OIDC ID tokens. Understanding JWT at the byte level is essential for architects who design validation services and debug token failures.

JWT structure — three Base64URL-encoded segments
A JWT is three Base64URL strings joined by dots: header.payload.signature

Header: Algorithm and token type — {"alg":"RS256","typ":"JWT","kid":"key-2024-01"}. The kid (key ID) tells the verifier which public key to use for signature validation.

Payload: Claims about the principal and token. Registered claims: iss (issuer), sub (subject/principal ID), aud (audience — who the token is for), exp (expiry Unix timestamp), iat (issued at), jti (JWT ID — unique token identifier for replay detection).

Signature: RS256(base64url(header) + "." + base64url(payload), private_key). The signature is verifiable by anyone with the AS's public key. If a single byte of header or payload is modified, the signature fails.
1
Verify the signature first
Fetch the AS's JWKS (JSON Web Key Set) from /.well-known/jwks.json. Match the token's kid header to the correct key. Verify the signature. If this fails, reject immediately — do not read claims from an unverified token. Cache JWKS with a TTL of 1 hour; refresh when a new kid is encountered.
GET https://as.company.com/.well-known/jwks.json → { "keys": [{kid, kty, n, e, alg}] }
2
Validate expiry and not-before
Check exp > current Unix time. Check nbf (not before) < current time if present. Allow a clock skew tolerance of no more than 60 seconds. Tokens with any clock manipulation beyond tolerance must be rejected. This prevents replay attacks using expired tokens on systems with clock drift.
if (claims.exp < (now - 60)) reject("Token expired")
3
Validate issuer and audience
The iss claim must exactly match the expected AS URL. The aud claim must include this resource server's identifier. A token valid for one RS must not be accepted by a different RS — this prevents token substitution attacks where a token issued for Service A is presented to Service B.
if (claims.iss !== EXPECTED_ISSUER) reject("Wrong issuer") if (!claims.aud.includes(THIS_RESOURCE_SERVER)) reject("Wrong audience")
4
Validate scope and make authorization decision
Check that the token's scope claim authorizes the requested operation. A token with scope: read:profile must not be accepted for a write operation. This is the boundary where token validation ends and authorization begins — both the RS (PEP) and the policy engine (PDP) participate in this step.
if (!claims.scope.includes(required_scope)) reject("Insufficient scope")
⚠️GotchaThe alg:none attack and algorithm confusion — never trust the header's alg claim blindly
A JWT library that accepts the algorithm from the token's own header is vulnerable. An attacker can forge a token with {"alg":"none"} and no signature — some libraries accept this. Similarly, an attacker can change RS256 to HS256 and sign the token with the RS's public key (treating it as the HMAC secret). Fix: always specify the expected algorithm explicitly in your validation configuration, never derive it from the token header. This is a configuration issue, not a code issue — but it has caused significant real-world vulnerabilities.

Knowledge check

Test your depth

Q1 A React SPA is using client credentials grant with a client secret embedded in the JavaScript bundle. Describe all the security failures in this design and provide the correct architecture. ▼
Three distinct failures: (1) Wrong grant type: Client credentials is for machine-to-machine flows with no user involved. A React SPA has a user — the correct grant is authorization code + PKCE. (2) Public client treated as confidential: React code running in the browser is a public client — the client secret is exposed to anyone who opens DevTools. There is no secure way to embed a secret in browser JavaScript. The secret is compromised the moment the app is deployed. (3) No user identity: Client credentials tokens have no user context — the token identifies the application, not the user. Any authorization decisions downstream cannot distinguish between users.

Correct architecture: Remove the client secret entirely (the client ID alone identifies the public client). Use response_type=code with code_challenge_method=S256 and PKCE. The SPA redirects to the AS, the user authenticates, and the code is exchanged via a back-channel call (from the SPA, since there is no backend). Store tokens in memory only (not localStorage — XSS risk). Use a BFF (Backend For Frontend) pattern for highly sensitive applications to move token handling to the server side completely.
Q2 A microservice chain has Service A calling Service B calling Service C. All calls require the originating user's identity for audit logging. How do you propagate user identity through this chain without re-authenticating the user at each hop? What are the security risks? ▼
Solution: Token Exchange (RFC 8693) combined with scoped, audience-constrained tokens.

Flow: The user authenticates and receives an access token (aud: service-a). Service A validates the token. To call Service B, Service A exchanges its token at the AS (grant_type=urn:ietf:params:oauth:grant-type:token-exchange, presenting the original token as the subject_token). The AS issues a new token with aud: service-b, sub: original_user, and optionally an act (actor) claim identifying Service A as the intermediary. Service B repeats the exchange for Service C.

Security risks to mitigate: (1) Token amplification: Service A could exchange for a token with broader scope than it received — the AS must enforce that exchanged tokens cannot exceed the original token's scope. (2) Confused deputy: A compromised Service A could exchange for tokens on behalf of any user it has ever seen — mitigate with tight scope constraints and short TTLs on exchanged tokens. (3) Audit chain integrity: The act claim provides the delegation chain, but if any service is compromised, the chain is poisoned — use mTLS for service-to-service calls to bind tokens to the calling service's certificate.
Q3 Your authorization server issues RS256-signed JWTs. You need to rotate the signing key without breaking existing valid tokens. Design the key rotation procedure with zero downtime. ▼
The kid (Key ID) claim makes zero-downtime rotation possible. Here is the procedure:

Step 1 — Publish new key: Generate a new RSA key pair. Add the new key's public key to the AS's JWKS endpoint alongside the old key — both are now published with different kid values (e.g., key-2024-01 and key-2025-01). Resource servers that cache JWKS will pick up the new key on their next cache refresh.

Step 2 — Switch issuance to new key: Configure the AS to sign all newly issued tokens with the new private key (kid: key-2025-01). Existing tokens signed with the old key are still valid — resource servers find the old public key in JWKS by matching kid.

Step 3 — Wait for old token expiry: Wait until the maximum access token TTL has elapsed (e.g., 60 minutes). All tokens signed with the old key will have expired.

Step 4 — Remove old key: Remove the old key from the JWKS endpoint. Any token still presenting the old kid will fail validation (key not found) — but all legitimate tokens have expired.

Critical detail: Resource servers must be able to handle an unknown kid by refetching JWKS (not hard-failing), with a rate-limited retry to prevent thundering herd against the JWKS endpoint.
Q4 Explain the difference between the OIDC ID token and the OAuth access token. When does a resource server need to call the /userinfo endpoint vs reading claims from the access token directly? ▼
ID token vs Access token — two different audiences, two different purposes:

The ID token is issued to the client application — its audience (aud) is the client ID. It contains identity claims about the authenticated user (who logged in, when, how, with what ACR). The client uses the ID token to establish a local session for the user. The ID token must never be sent to a resource server — it is not intended for API authorization.

The access token is issued for the resource server — its audience is the RS identifier. It authorizes API calls within the token's scope. It may or may not contain identity claims depending on AS configuration.

When to call /userinfo: (1) The RS needs identity attributes (email, display name, department) that are not embedded in the access token because the AS is configured to keep access tokens minimal. (2) The RS needs up-to-date attributes — access token claims are a snapshot at issuance time; /userinfo returns current data. (3) The access token is opaque (not a JWT) — the RS has no way to read claims without introspection or UserInfo.

Performance trade-off: Calling /userinfo on every request adds a network hop and makes the RS stateful. The architectural preference is to embed sufficient claims in the access token at issuance time, keeping the RS stateless and fast. Reserve /userinfo for attributes that change frequently or don't fit the token.

Key takeaways — M03a · OAuth 2.0 & OIDC
  • OAuth 2.0 is an authorization framework, not an authentication protocol. It answers "what can this client do on your behalf?" not "who is this user?" OIDC adds the identity layer — the ID token — on top of OAuth. The two work together but solve different problems.
  • Public vs confidential client is the most important classification in OAuth. Every grant type selection, every security recommendation, and every token storage decision flows from this distinction. SPAs and mobile apps are always public clients — they cannot hold secrets.
  • Authorization code + PKCE is the only correct grant for user-facing flows. Implicit is deprecated. ROPC is dangerous. The default answer for any interactive flow is auth code + PKCE, full stop.
  • PKCE prevents authorization code interception at the OS redirect layer by binding the code to a secret verifier that only the legitimate client knows. Interceptors get the code — but not the verifier — making it useless.
  • JWT validation has four mandatory steps: verify signature (using the correct kid from JWKS), validate exp and nbf, validate iss and aud, validate scope. Missing any step is a security vulnerability.
  • Advanced specs are now enterprise requirements: PAR protects auth parameters from browser exposure. DPoP sender-constrains tokens so stolen tokens are useless. RAR enables fine-grained authorization requests. CIBA enables backchannel flows for call centers and IoT. FAPI 2.0 mandates PAR + DPoP for financial APIs.
  • Key rotation is a zero-downtime operation when JWKS + kid are used correctly. Publish new key, switch issuance, wait for old token expiry, remove old key. Resource servers match kid to the correct public key automatically.
