Model Evaluation & Market Intelligence

A new AI model launches every few weeks. Every single one claims to be the best — at reasoning, at coding, at context length, at cost efficiency. Benchmark leaderboards are gamed. Press releases are written by marketing teams. And your engineering team is asking you: "Should we switch?" This playbook gives you the critical reading skills and a repeatable framework to answer that question confidently — in about ten minutes, for any model that ever launches. 🎯

🟢 What this playbook assumes
You've completed Playbook 1 and have working mental models of tokens, context windows, training vs inference, RAG, agents, and SLMs. This playbook applies all of that vocabulary to the practical question of how to compare, evaluate, and choose between real models and products. If a term feels unfamiliar, Module 1.x in the sidebar is the reference. 🗺️
2.1

📐 The Eight Evaluation Dimensions

What is it?

When someone says "Model A is better than Model B," the immediate next question should be: better at what, for what purpose, under what constraints? There is no single "best" model in 2025-26 any more than there is a single "best" database engine — the best choice depends on the specific workload. The eight dimensions below are the axes along which models actually differ in ways that matter to enterprise architecture decisions. Together they form your evaluation framework. 🔍

The eight dimensions where models meaningfully differ — cost-colored by category

Let's walk through each dimension with the specificity that actually helps in a real evaluation:

1️⃣ Context Window — The Conversation Budget

As established in Playbook 1 Module 1.3, this is the total token budget shared across system prompt, conversation history, retrieved documents, and the response. For enterprise applications, the relevant question isn't just "how large is the context window?" — it's "how large does it need to be for my specific workflow?" An internal Q&A bot answering short policy questions may never need more than 16K tokens. A contract-review assistant working on 200-page documents may need 200K+ and still want to implement chunking strategies. Bigger isn't always better, and larger contexts cost more to process even when you don't use the full capacity. 📏

2️⃣ Pricing — The Token Economics Reality

Most models price input and output tokens separately — output typically 3-5× more expensive. Beyond that, look for: caching (does the model offer discounts on repeated/cached prompt prefixes — hugely valuable for system prompts that get sent identically with every request?), batch pricing (lower rates for async, non-real-time processing — great for nightly report generation), and rate limits (tokens per minute, requests per minute at your tier). A model that looks cheap per-token can be effectively unusable if its rate limits cap your real-world throughput at production scale.

3️⃣ Latency — Time to First Token and Streaming Speed

There are actually two distinct latency numbers that matter for different use cases. Time to first token (TTFT) — how long from sending the request to the first character appearing in the response — is the one that feels "slow" to a human user waiting for a chat response. Tokens per second (TPS) — the generation speed once output starts — matters more for long-form generation tasks where you're waiting for the full document, not just the first word. A model with fast TTFT but slow TPS feels responsive but makes you wait for completion; the reverse feels slow to start but finishes quickly once it does. For real-time user-facing applications, TTFT dominates. For batch processing, TPS dominates. Many evaluations only report one without the other. ⏱️

4️⃣ Reasoning — The Judgment Quality Dimension

"Reasoning" in AI evaluation means: how well does the model handle multi-step problems where you can't get the right answer without correctly completing several prior steps? How does it handle ambiguous instructions? Does it catch its own logical errors? Does it know when it doesn't know something? This is notoriously hard to benchmark accurately (more in Module 2.3), and the honest answer is that the only reliable test is evaluating on your actual complex use cases, not any published leaderboard number.

5️⃣ Coding Ability — Not Just "Can It Write Code"

Coding ability has several distinct sub-dimensions that often diverge: writing new code from a spec, completing partially-written code (the GitHub Copilot use case), debugging existing code, reviewing code for correctness and style, and understanding large existing codebases. A model that's excellent at writing new Python from scratch may be mediocre at understanding a complex multi-file TypeScript codebase. For enterprise evaluations, identify which coding task you actually need — then test specifically for that, using your own real codebase or close analogues. 💻

6️⃣ Tool Calling & MCP Support — The Integration Reliability Dimension

Tool calling isn't just "does this model support it" — they all do now. The real question is: how reliably? Does the model call tools when it should, with correctly-formatted arguments, without hallucinating argument values? Does it handle tool-call errors gracefully (retrying with corrected arguments vs. giving up or silently skipping)? Does it support MCP natively, or does your application layer need to bridge an older function-calling format? Reliability here often isn't visible in published benchmarks at all — it shows up in production as "the bot tried to query a field that doesn't exist in ServiceNow" incidents. 🔧

7️⃣ Multimodal Capability — Which Modalities, At What Quality

"Multimodal" now means many things: reading images, reading PDFs (which are different from images of PDFs), understanding diagrams and charts in documents, generating images, processing audio, understanding video. Most enterprise use cases today primarily need reading multimodality — understanding what's in an uploaded image or document — not generating images. Evaluate only the modalities you'll actually use, because quality varies significantly across modalities even within the same model family. A model that's excellent at reading photographs may be significantly worse at reading and extracting data from complex tables or engineering diagrams. 🖼️

8️⃣ Enterprise Fit — The Often-Deciding Dimension That Benchmarks Never Measure

This is the dimension that often ends up being the deciding factor for enterprise adoption, despite being the least discussed in leaderboard conversations: data handling policies (does the vendor retain your inputs for training? What are the DPA terms?), compliance certifications (SOC 2, ISO 27001, HIPAA BAA availability, FedRAMP for government), SLAs (uptime guarantees, support response times, what's the remediation for breaches?), audit logging (can you get logs of every API call for a given period?), and dedicated deployment options (shared infrastructure vs. provisioned capacity vs. private cloud deployment). A model that leads every benchmark and fails the enterprise-fit dimension may simply not be deployable in your organization, regardless of its capability scores. 🏢

🔥 Analogy — Buying a Fleet Vehicle vs. A Sports Car

The fastest car in the world might be completely wrong for a corporate fleet — it fails on maintenance cost, driver training requirements, cargo capacity, and insurance premiums, even though it clearly "wins" on the single dimension of top speed. Most enterprise AI model selections work the same way. A model that tops the reasoning benchmark might fail on data residency requirements, pricing at your actual call volume, or simply doesn't have the compliance certification your legal team requires. The benchmark is the sports car's 0-60 time — real, meaningful, but only one dimension of the actual purchase decision. The eight dimensions above are your full fleet-purchase checklist. 🚗

🏢 ENTERPRISE USE CASE The Model Selection That Wasn't About Model Quality 😅

A financial services firm's AI task force spent three weeks evaluating Claude, GPT-4o, and Gemini Ultra for an internal document-analysis assistant. On pure capability metrics (reasoning, understanding complex financial documents, extraction accuracy), Model A was the clear winner — noticeably better on every capability test the team ran.

In week four, Legal reviewed the vendor DPA (Data Processing Agreement) and compliance certifications. Model A's provider didn't yet have SOC 2 Type II certification, offered no HIPAA BAA (relevant because some documents contained employee health benefit information), and had ambiguous terms about using API inputs for model improvement. The firm's compliance requirements — which pre-existed this evaluation — were non-negotiable.

They went with Model B — the second-place capability performer — because it had full SOC 2 Type II, an available HIPAA BAA, clear contractual data-handling commitments, and an enterprise support tier with defined SLAs. The team's capability evaluation was genuinely valuable, but the enterprise-fit dimension made the final decision. This is the norm for regulated industries, not the exception. Always run the enterprise-fit evaluation in parallel with capability testing, not after. 📋

✅ Quick Lab — 10 minutes
Take one AI system your organization is currently using or evaluating. Score it honestly across the eight dimensions: for each dimension, is it excellent / adequate / weak / unknown for your specific use case? Notice which dimensions you can actually answer — and which you realize you've never specifically investigated (often Enterprise Fit is the one nobody has checked). 📊
2.2

🏆 Benchmark Tour — The Leaderboard Landscape

What is it?

AI benchmarks are standardized test suites — collections of questions or tasks with known correct answers — that allow researchers and developers to measure a model's performance on a specific capability dimension in a reproducible way. They serve a genuine purpose: without any benchmark, comparing models would require entirely bespoke evaluation every time, making it impossible to track progress or make informed comparisons. But benchmarks also have systematic weaknesses that make them dangerous if read uncritically — that's Module 2.3. First, let's know what the major ones actually test. 📋

🔥 Analogy — Standardized Tests for AI Models

Think of AI benchmarks the way you'd think of standardized tests for college admissions — SAT, ACT, GRE. They provide a common yardstick that makes comparison possible across millions of students (or dozens of models) who you can't evaluate individually in depth. And they have exactly the same limitations: they measure performance on a specific kind of problem in a controlled setting, which is correlated with but not identical to actual capability in real contexts. High SAT scores genuinely correlate with academic ability — but students can also specifically prepare for the test format in ways that inflate their score beyond underlying ability. AI benchmarks have exactly the same vulnerability, at an industrial scale, as we'll see in Module 2.3. 📝

How to read a benchmark number in a press release

When a model's announcement says "achieves 87.3% on GPQA Diamond" — here's how to read that:

  1. What subset? Many benchmarks have variants (GPQA has "Diamond," "Extended," "Main" — all different difficulties). Make sure you're comparing the same subset across models.
  2. With or without tools? Reasoning models given access to a code interpreter score dramatically higher on math benchmarks than the same model without it — these are sometimes reported side-by-side, sometimes not.
  3. At what temperature / sampling settings? A "pass@1" (get it right in one try) vs "pass@100" (get it right in at least 1 of 100 tries) score can differ by 30+ percentage points for the same model on the same task.
  4. Self-reported or third-party? Numbers from the provider's own report are often generated under the most favorable conditions. Numbers from independent evaluators (HELM, LiveBench, external researchers) are typically more conservative and more trustworthy.
🏢 ENTERPRISE USE CASE The "Best Coding Model" That Couldn't Handle Our Codebase 😬

A platform engineering team, tasked with evaluating AI coding assistants, led their decision with SWE-Bench Verified scores. Model X had recently topped the leaderboard at 49% — impressively ahead of the previous leader. The team selected it for a 30-day pilot for their internal developer tooling.

Pilot feedback was mixed at best. The model struggled with the team's TypeScript monorepo (SWE-Bench is Python-heavy), had difficulty navigating internal abstractions and custom-built libraries that appear nowhere in public training data, and was notably worse than the leaderboard number suggested on refactoring tasks (which aren't well-represented in the benchmark's issue distribution).

The lesson: SWE-Bench measures performance on real GitHub issues from specific well-known open-source Python repos. Your private TypeScript monorepo with custom abstractions is a genuinely different test. The benchmark was useful as a signal of general coding sophistication — but it wasn't a substitute for actually testing on representative tasks from your own codebase. Benchmarks are a starting filter, not a final answer. 🔍

✅ Quick Lab — 10 minutes
Go to any current AI benchmark leaderboard (LMSYS Chatbot Arena, LiveBench, or any provider's published benchmarks) and find the current top 3 models. For each one: identify which benchmark it leads on, which benchmarks it doesn't lead on, and whether you can find the specific evaluation conditions (temperature, tools available, subset). Notice how much uncertainty remains after just five minutes of looking — that uncertainty is the point. 🧐
2.3

⚠️ Why Benchmarks Lie

What is it?

This module is, arguably, the most important one in this entire playbook. AI benchmarks are genuinely useful — and they're also systematically misleading in ways that aren't immediately obvious from looking at a leaderboard table. Understanding how they mislead gives you a significant advantage in any model evaluation conversation, because you can identify which claims to trust and which to probe further. Here are the six major ways benchmark numbers lie, with examples of each. 🔎

🔴 Analogy — Goodhart's Law, Applied to AI at Industrial Scale

Goodhart's Law: "When a measure becomes a target, it ceases to be a good measure." This principle was originally about economic policy indicators, but it applies with almost eerie precision to AI benchmarks. Once a benchmark becomes the target that determines model rankings, press coverage, and marketing — the pressure to optimize specifically for that benchmark's format becomes enormous, even when doing so adds no real capability. A model can be specifically trained on examples that look exactly like benchmark questions, producing a score that reflects "familiarity with this specific test format" rather than "genuine ability at the underlying skill." This is called benchmark contamination, and it's rampant. 🎯

Six Ways Benchmarks Mislead

1 — Benchmark Contamination / Data Leakage

The most fundamental problem. During training, a model may have been trained on text that includes benchmark questions and their answers — sometimes deliberately (to boost scores), sometimes accidentally (because benchmark question sets are published online and naturally appear in web crawls). A model that has "seen" the answers to MMLU questions during training isn't demonstrating general knowledge — it's demonstrating recall of training data. Most labs publish contamination analysis for major evaluations, but these analyses are imperfect and the definitions of "contamination" vary enough to make direct comparisons difficult.

2 — Benchmark Saturation

When top models score 90%+ on a test designed for humans who score ~40-60%, the benchmark is no longer differentiating — it's just confirming everyone passed. MMLU, HumanEval, and several others have effectively saturated for frontier models. A press release claiming "our model achieves 92% on MMLU" in 2025-26 is announcing that it passed a test that most frontier models pass — not that it's meaningfully better than alternatives. This is why newer, harder benchmarks (GPQA, LiveBench, SWE-Bench) keep being created — saturation is a recurring problem, not a one-time issue.

3 — The Benchmark Doesn't Measure What You Actually Need

This is the most practically important failure mode for enterprise evaluators. Even a perfectly clean, non-contaminated benchmark measures a specific, defined task in a controlled setting — which may or may not correlate with performance on your actual task. MMLU measures broad academic knowledge across 57 subjects. If your use case is analyzing semiconductor supply chain contracts, "57-subject breadth" is nearly irrelevant. SWE-Bench measures resolving GitHub issues in popular Python repos. If you write ABAP or Terraform, that correlation is weak at best. The only way to measure "how well does this model handle our specific task" is to actually test on representative examples of that task — there is no shortcut. 🎯

4 — Cherry-Picked Metrics and Subset Selection

Model providers choose which benchmarks to report. They almost universally choose the ones where their model performs best and omit or downplay the ones where it doesn't. Additionally, most benchmarks have multiple subsets (GPQA has Diamond, Extended, and Main variants with meaningfully different difficulty levels), and a provider may report the subset variant where they score highest. Reading a comparison table where every row was selected by a different provider for a different advantage is not the same as reading an objective comparison. Third-party evaluation platforms (HELM, LMSYS Chatbot Arena, LiveBench) are more trustworthy specifically because the benchmark selection isn't made by the party being evaluated.

5 — Evaluation Conditions Are Not Standardized

The same model on the same task can score radically differently depending on: the temperature setting (0 = deterministic, 1 = more varied); whether it was allowed to use a code interpreter or web search; how many "shots" were given (zero-shot vs few-shot examples in the prompt); whether the evaluation used the model's chat interface or raw API; and how long the model was allowed to "think" (chain-of-thought). These conditions are often buried in footnotes or appendices of evaluation reports, and provider announcements almost never highlight the conditions that most favor their result. ⚙️

6 — Benchmark Scores Don't Predict User Experience

Perhaps the most uncomfortable truth: the model that users and developers consistently prefer in head-to-head comparisons often doesn't lead on standard capability benchmarks. The LMSYS Chatbot Arena (where humans vote on which of two blind responses they prefer) regularly produces rankings that don't match benchmark leaderboards. "Human preference" is itself an imperfect measure — it can favor verbosity or confident tone over accuracy — but it captures something real about practical usefulness that multiple-choice academic tests don't. 💬

🟣 The One Benchmark Most Worth Trusting — And Why
LiveBench is currently the most contamination-resistant major benchmark because it continuously generates new questions monthly based on recent events, new mathematical theorems, and freshly published coding challenges — material that couldn't have been in any model's training data at the time of evaluation. This directly addresses the contamination problem. It's not perfect (nothing is), but it's the closest available approximation to "a test the model genuinely hasn't seen before." For a quick cross-model comparison, LiveBench scores are the ones worth weighting most heavily. 🏅
🏢 ENTERPRISE USE CASE The MMLU Argument That Wasted Two Weeks 📅

A procurement review was comparing two models for an internal knowledge-management assistant. An engineer on the team built a slide showing that Model A scored 3.7 percentage points higher on MMLU than Model B. The procurement team asked for a second look at whether that gap was meaningful and why.

On investigation: both models scored above 88% on MMLU, meaning both were operating in the benchmark's saturation zone. The 3.7 point gap was statistically within the range of measurement variance across evaluation runs. Neither score had independent third-party verification. MMLU's "57 academic subjects" had minimal overlap with the company's actual knowledge base (internal HR policies, IT procedures, product documentation). And the evaluation conditions for each score were reported differently.

Two weeks into the discussion, an engineer ran a much more useful test: they fed 50 representative real questions from the company's IT helpdesk to both models and had three subject-matter experts rate the answers blind. That test took one afternoon and produced more actionable signal than three weeks of benchmark argument. The MMLU conversation was real work — it just wasn't the right work. 🎯

✅ Quick Lab — 10 minutes
Pick any recent major model launch announcement. Find its benchmark claims. For each benchmark cited, identify: (1) was this a self-reported number or third-party verified? (2) which subset or variant was used? (3) does the benchmark relate to your actual use case? (4) has this benchmark saturated for frontier models? This exercise, done once carefully, makes every future model announcement much easier to read critically. 🔍
2.4

⚡ The 10-Minute Model Triage Framework

What is it?

A new frontier model launches. The internet explodes with takes. Your team sends a Slack message asking if you should switch. You have a meeting in 20 minutes. This is the framework — a structured, repeatable, 10-minute process you can run on any model, any time, using freely available information. It doesn't replace a full evaluation — it tells you whether a full evaluation is even warranted. Think of it as triage, not diagnosis. 🏥

🟢 Analogy — The Security Vulnerability Triage You Already Know

When a CVE drops, your security team doesn't immediately shut everything down and patch every system — they run a triage: what's the CVSS score, does it affect components we actually run, is there a known exploit in the wild, what's the patch availability? That structured initial filter determines whether "respond now," "schedule for next patch cycle," or "not applicable to us" is the right call — before any real remediation work begins. The 10-minute model triage is exactly this: a fast initial filter that routes to "evaluate seriously," "note and monitor," or "not relevant to our use case" — in minutes, not weeks. 🛡️

🟢 Architect's Take — What Triggers "Evaluate Seriously" vs. "Monitor"
Route to "evaluate seriously" when at least two of the following are true: (1) an established provider — with track record and enterprise-fit credibility — releases the model, (2) pricing is meaningfully below current alternatives at comparable claimed capability, (3) a specific claimed capability (context window, tool-calling reliability, a specific domain) directly addresses a known pain point in your current stack, (4) third-party benchmark data already exists and shows clear differentiation. A brand-new provider with only self-reported numbers almost never warrants immediate serious evaluation — wait for independent validation. ⚖️

Then check whether your organization has already made any decision about this model — and compare your triage conclusion to whatever happened. This simulation is as close as you can get to the real thing without waiting for the next launch. 🔬
2.5

🛠️ Evaluating AI Products, Not Just Models

What is it?

An AI product is distinct from an AI model in a critical way: a product bundles a model (or multiple models) with a user experience, an integration layer, an access-control model, and a business relationship. When your developers ask "should we use GitHub Copilot, Cursor, or Claude Code?" — they're asking a product question, not a model question. The underlying models may be similar or even identical (multiple products are built on the same foundation models); what differs is everything around the model. This requires a completely different evaluation framework from the model-level one in Modules 2.1-2.4. 📦

🔥 Analogy — Buying a Database Engine vs. Buying a Managed Database Service

Evaluating PostgreSQL vs MySQL vs SQL Server (database engines) is a technical capability comparison — schema features, query planner performance, replication models. Evaluating RDS vs Aurora vs Cloud SQL vs Azure Database (managed database services) is a product comparison — operational overhead, pricing model, scaling limits, compliance certifications, support SLAs, migration complexity. You might well be comparing products that use identical underlying engines (RDS for PostgreSQL and Cloud SQL for PostgreSQL both run PostgreSQL — the engine is the same). What differs is everything the vendor has built around it, and the business terms. AI product evaluation works the same way. 🗄️

The AI Product Evaluation Checklist — One Page

🔵 Before any pilot, answer these in order
  1. Data handling: Can we get a signed DPA? Is our code/data used for training? (If "no" to DPA or "yes" to training — stop here for most enterprises)
  2. Compliance certification: SOC 2 Type II exists? Required compliance certs available? (If not — stop or wait)
  3. Enterprise controls: SSO available? Audit logs available? Admin console for provisioning? (Required for IT/security sign-off)
  4. Cost model at scale: What is the true fully-loaded cost at our expected number of users and usage pattern?
  5. Integration: Does it connect to our existing toolchain without requiring significant custom work?
  6. Capability fit: Having passed the above — does the underlying model capability actually fit our task? (Run a task-specific pilot, not a demo)
  7. Lock-in risk: If we want to switch in 18 months, what do we lose and what does migration cost?
🟣 Analogy — This Is How You Already Evaluate SaaS for IAM

Notice that the checklist above is almost identical to how a mature enterprise evaluates any SaaS product for IAM or security tooling: compliance certs first, DPA next, SSO/SCIM requirements, audit logging, then capability and fit. The same evaluation discipline that serves you for evaluating a new PAM vendor or a new SIEM platform applies directly to AI products. The specific vocabulary differs (you're asking about "prompt logging" rather than "network traffic logging") but the structure of the evaluation is the same. Your existing enterprise SaaS evaluation framework is a near-perfect template for AI product evaluation — you may not need to start from scratch. 🔐

Pick one AI product currently in use or under consideration at your organization. Run it through the 7-question checklist above — in order, stopping honestly if any question can't be answered with confidence. How far did you get before hitting an "unknown"? 📋 What To Remember Forever

The one-page executive summary of Playbook 2. Your evaluation Bible. 🎯

📐 Eight Model Dimensions

Context window · Pricing · Latency · Reasoning · Coding · Tool calling · Multimodal · Enterprise fit. No model wins all eight. Enterprise fit often makes the final decision regardless of capability scores.

🏆 Benchmarks Are Starting Filters

Trust LiveBench (contamination-resistant) and LMSYS Arena (human preference) over self-reported numbers. Treat all scores as signals, not verdicts. Always test on your actual tasks.

⚠️ Six Ways Benchmarks Lie

Contamination · Saturation · Wrong task · Cherry-picked metrics · Unstandardized conditions · Poor UX prediction. Ask "self-reported or third-party?" before believing any score.

⚡ The 10-Min Triage

Provider + tier → Pricing snapshot → Third-party benchmark check → Task-fit hypothesis → Verdict: Evaluate seriously / Monitor / Not relevant. "Monitor" is not "ignore" — set a revisit trigger.

📦 Products ≠ Models

Model benchmarks don't evaluate data handling, SSO, audit logs, cost at scale, or lock-in risk. Run product evaluation in parallel with capability testing — never after.

🔐 DPA First, Demo Second

The evaluation order that saves the most time: compliance certs → DPA review → enterprise controls → cost model → capability fit. Most enterprise rejections happen at step 1 or 2.

📊 Your Tasks > Any Benchmark

50 real representative questions from your actual use case, scored by domain experts, always beats 50 MMLU percentage points on a saturated benchmark. Build your own test set before committing to any model.

🔥 When "Monitor" Is the Right Answer

New provider with no track record + only self-reported benchmarks + no third-party validation = monitor, not evaluate. Wait for LiveBench data. Set a 30-day revisit. Speed of evaluation ≠ quality of decision.
