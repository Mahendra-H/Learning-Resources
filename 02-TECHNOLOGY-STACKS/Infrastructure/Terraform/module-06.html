The compute model

How EC2, Launch Templates, and ASGs relate

Before writing any Terraform, understand the three-layer compute model. Each layer has a distinct role, and confusing them leads to misunderstanding what Terraform manages vs what AWS manages autonomously.

Three-Layer Compute Model — Terraform's Scope
Launch Template
The blueprint
Defines what every instance will look like when launched — AMI, type, storage, networking, identity, bootstrap script. Terraform creates and versions it. When the AMI changes, a new LT version is created.
Auto Scaling Group
The fleet policy
Defines how many instances should run, where (subnets), and how to replace them. Terraform manages the policy. The ASG autonomously creates, monitors, and terminates the actual instances.
EC2 Instances
Ephemeral compute
Created and terminated by the ASG using the Launch Template. Not tracked individually in Terraform state. Replaced wholesale during an AMI refresh. Cattle, not pets.
Launch Template

Building the PingFederate Launch Template

The Launch Template is the richest resource in this module. Every attribute in the template is stamped onto every EC2 instance that the ASG launches. Get the template right and every instance in the fleet is identical, predictable, and ready to run PingFederate on first boot.

HCLcompute.tf — Launch Template (complete)
# ── LAUNCH TEMPLATE ───────────────────────────────────────────────────
resource "aws_launch_template" "pf_engine" {
  name_prefix = "${local.name_prefix}engine-lt-"
  description = "PingFederate engine node launch template"
  # Terraform creates a new VERSION on every apply that changes the template
  # The ASG picks up the new version via instance_refresh

  # ── AMI — from the data source you learned in M02 ────────────────────
  image_id      = data.aws_ami.approved_pf.id
  instance_type = var.pf_instance_type   # e.g. "m5.xlarge"

  # ── IAM INSTANCE PROFILE — from M05 ──────────────────────────────────
  iam_instance_profile {
    arn = aws_iam_instance_profile.pf_instance.arn
    # NOTE: arn, not role arn — instance profiles, not roles
  }

  # ── NETWORK — attach the PF engine security group ─────────────────────
  network_interfaces {
    associate_public_ip_address = false   # private subnet — NO public IP
    security_groups             = [aws_security_group.pf_engine.id]
    delete_on_termination       = true
  }

  # ── EBS ROOT VOLUME ───────────────────────────────────────────────────
  block_device_mappings {
    device_name = "/dev/xvda"   # root device for AL2 / RHEL AMIs
    ebs {
      volume_size           = var.root_volume_size_gb   # e.g. 50
      volume_type           = "gp3"
      iops                  = 3000    # gp3 baseline; increase for high I/O
      throughput            = 125     # MiB/s; gp3 default
      encrypted             = true
      kms_key_id            = var.ebs_kms_key_arn
      delete_on_termination = true   # instance is ephemeral — disk too
    }
  }

  # ── USER DATA — the bootstrap script ─────────────────────────────────
  # base64encode() is required — EC2 expects base64-encoded user_data
  # templatefile() renders the script with Terraform variable values
  user_data = base64encode(templatefile("${path.module}/templates/userdata.sh.tpl", {
    config_bucket     = aws_s3_bucket.pf_config.bucket
    config_key_prefix = "config/"
    environment       = var.environment
    aws_region        = var.aws_region
    log_group         = "/pingfederate/${var.environment}"
  }))

  # ── METADATA OPTIONS — enforce IMDSv2 ─────────────────────────────────
  # IMDSv2 requires a session-oriented request with a PUT token
  # Prevents SSRF-based credential theft attacks
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"    # IMDSv2 REQUIRED
    http_put_response_hop_limit = 1             # prevent hop from containers
    instance_metadata_tags      = "enabled"    # tags accessible via IMDS
  }

  # ── MONITORING ────────────────────────────────────────────────────────
  monitoring {
    enabled = true   # detailed CloudWatch monitoring (1-minute resolution)
  }

  # ── TAGS — applied to the Launch Template resource ───────────────────
  tag_specifications {
    resource_type = "instance"   # tags applied to each launched EC2 instance
    tags = merge(local.common_tags, {
      Name        = "${local.name_prefix}pf-engine"
      Component   = "PingFederate"
      LaunchedBy  = "asg"
    })
  }
  tag_specifications {
    resource_type = "volume"     # tags applied to each EBS volume
    tags          = local.common_tags
  }

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}engine-lt"
  })

  # Ensure a new version is always created before the ASG is updated
  lifecycle {
    create_before_destroy = true
  }
}
user_data bootstrap script

The bootstrap bridge — how a blank instance becomes a PF node

The user_data script is the most important operational piece in this module. It is the bridge between the blank AMI and a fully configured PingFederate node. It runs exactly once — on first boot — as root. It is the mechanism that retrieves configuration from S3 (made possible by the IAM role from M05) and prepares the instance for Ansible to complete the configuration.

The script is rendered by Terraform's templatefile() function, which substitutes the S3 bucket name, environment, region, and other values at plan time. The result is base64-encoded and embedded in the Launch Template. Every instance launched from this template runs the same script with the same values.

Bashtemplates/userdata.sh.tpl — PF bootstrap script
#!/bin/bash
set -euo pipefail

# ── LOGGING SETUP ─────────────────────────────────────────────────────
exec > >(tee /var/log/userdata.log) 2>&1
echo "=== PingFederate bootstrap started: $(date) ==="

# ── WAIT FOR INSTANCE METADATA (IMDSv2 token) ─────────────────────────
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

INSTANCE_ID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id)

echo "Instance ID: $INSTANCE_ID"

# ── SET AWS REGION ────────────────────────────────────────────────────
export AWS_DEFAULT_REGION="${aws_region}"   # rendered by templatefile()

# ── RETRIEVE PF CONFIGURATION FROM S3 ────────────────────────────────
# Uses the IAM instance role credentials from IMDS automatically
# No credentials needed — the role grants S3 access

CONFIG_BUCKET="${config_bucket}"            # e.g. pf-config-prod-123456789012
CONFIG_PREFIX="${config_key_prefix}"        # e.g. config/
ENV="${environment}"                        # e.g. prod

echo "Downloading PF configuration from s3://$CONFIG_BUCKET/$CONFIG_PREFIX..."

# Create the PF config directory
mkdir -p /opt/pingfederate/config

# Download the configuration archive
aws s3 cp "s3://$CONFIG_BUCKET/${config_key_prefix}pingfederate-$ENV.zip" \
  /tmp/pf-config.zip \
  --region "$AWS_DEFAULT_REGION"

# Extract configuration to PF config directory
unzip -o /tmp/pf-config.zip -d /opt/pingfederate/config/
echo "Configuration extracted successfully"

# ── WRITE ENVIRONMENT FILE ────────────────────────────────────────────
# Ansible reads this file to know which environment it's configuring
cat > /etc/pingfederate-env << EOF
PF_ENVIRONMENT=${environment}
PF_INSTANCE_ID=$INSTANCE_ID
AWS_REGION=${aws_region}
CONFIG_BUCKET=${config_bucket}
LOG_GROUP=${log_group}
EOF

# ── SET HOSTNAME ─────────────────────────────────────────────────────
hostnamectl set-hostname "pf-engine-$INSTANCE_ID"

# ── SIGNAL READINESS ─────────────────────────────────────────────────
echo "=== Bootstrap complete: $(date) ==="
# Ansible will now run to complete PF installation and startup
# The lifecycle hook holds the instance in Pending:Wait state
# until Ansible signals completion via CompleteLifecycleAction
Why user_data is base64-encoded in Terraform
The AWS EC2 API requires user_data to be base64-encoded. Terraform's base64encode() function handles this automatically. The templatefile() function renders the script template by substituting variables before encoding. The combination ensures the final Launch Template contains a correctly encoded, variable-substituted script. Note: user_data is not re-executed on instance reboot — only on first boot. It is part of the instance's immutable launch configuration.

The four-module chain made concrete
Look at what the user_data script references: the S3 bucket name from M08's output, the IAM credentials from the M05 role (via IMDS), the environment variable from M02's variable system, the region from the provider. The user_data script is the physical point where all five prior modules converge into a single running PF node. This is why M06 is described as the heart of the system — it is the junction where all other infrastructure becomes operational.
Auto Scaling Group

The ASG — fleet policy, multi-AZ placement, and instance_refresh

The Auto Scaling Group is where the fleet policy is declared. It references the Launch Template, the subnet IDs from M04, the NLB target group (from M07 — referenced here via a data source or variable), and configures the health checks and replacement behaviour. The instance_refresh block is the mechanism that implements rolling AMI replacement.

HCLcompute.tf — Auto Scaling Group (complete)
resource "aws_autoscaling_group" "pf_engines" {
  name                = "${local.name_prefix}pf-engines"

  # ── CAPACITY ─────────────────────────────────────────────────────────
  desired_capacity    = var.pf_engine_desired   # e.g. 2 (start here)
  min_size            = var.pf_engine_min       # e.g. 2 (never go below)
  max_size            = var.pf_engine_max       # e.g. 6 (scale ceiling)

  # ── PLACEMENT — private subnets across AZs ───────────────────────────
  vpc_zone_identifier = local.private_subnet_ids

  # ── LAUNCH TEMPLATE reference ─────────────────────────────────────────
  launch_template {
    id      = aws_launch_template.pf_engine.id
    version = aws_launch_template.pf_engine.latest_version
    # latest_version ensures ASG always uses the current LT version
    # instance_refresh triggers replacement when this version changes
  }

  # ── HEALTH CHECK ─────────────────────────────────────────────────────
  health_check_type         = "ELB"      # use NLB health check, not EC2 status
  health_check_grace_period = 300        # 5 min: time for PF to start before HC
  # ELB type: instance must pass the NLB health check to be considered healthy
  # EC2 type: only checks that the instance is running (not that PF is ready)

  # ── NLB INTEGRATION ──────────────────────────────────────────────────
  target_group_arns = [var.nlb_target_group_arn]
  # ASG registers new instances with this target group on launch
  # and deregisters them on termination — automatically

  # ── INSTANCE REFRESH — rolling AMI replacement ────────────────────────
  instance_refresh {
    strategy = "Rolling"
    preferences {
      min_healthy_percentage       = 90   # keep 90% of fleet healthy during refresh
      instance_warmup              = 300  # 5 min warmup before counting as healthy
      checkpoint_delay             = 60   # pause 60s after each checkpoint
      checkpoint_percentages       = [25, 50, 75, 100]  # staged rollout checkpoints
      auto_rollback                = true  # roll back if health check fails
    }
    triggers = ["launch_template"]   # refresh when LT version changes
  }

  # ── TERMINATION POLICY ───────────────────────────────────────────────
  termination_policies = ["OldestLaunchTemplate", "Default"]
  # Ensures instances running old LT versions are terminated first
  # during scale-in — keeps the fleet on the latest AMI

  # ── LIFECYCLE HOOKS ──────────────────────────────────────────────────
  # Pause instance in Pending:Wait state before it goes InService
  # Gives Ansible time to configure PF before the instance accepts traffic
  initial_lifecycle_hook {
    name                 = "pf-launch-hook"
    default_result       = "ABANDON"    # fail safe: if no signal, terminate
    heartbeat_timeout    = 1800         # 30 min max for Ansible to complete
    lifecycle_transition = "autoscaling:EC2_INSTANCE_LAUNCHING"
  }

  # ── PROTECT FROM SCALE-IN ─────────────────────────────────────────────
  protect_from_scale_in = false   # set true per-instance for maintenance

  # ── WARM POOL (optional) ──────────────────────────────────────────────
  # Pre-initialised instances ready to join fleet quickly
  # Reduces AMI refresh time — instances are already running
  # warm_pool {
  #   pool_state                  = "Stopped"
  #   min_size                    = 1
  #   max_group_prepared_capacity = 2
  # }

  # ── TAGS propagated to instances ──────────────────────────────────────
  dynamic "tag" {
    for_each = merge(local.common_tags, {
      Name      = "${local.name_prefix}pf-engine"
      Component = "PingFederate"
    })
    content {
      key                 = tag.key
      value               = tag.value
      propagate_at_launch = true
    }
  }

  # CRITICAL: Tell Terraform not to manage desired_capacity in state
  # This allows auto-scaling to change the count without Terraform reverting it
  lifecycle {
    ignore_changes = [desired_capacity]
  }
}
Why ignore_changes = [desired_capacity] is essential
The ASG autonomously changes desired_capacity in response to scaling policies, scheduled actions, or manual adjustments. Without ignore_changes, the next terraform apply would reset the count to whatever is declared in the variable — potentially scaling down a fleet that was scaled up for legitimate reasons. With ignore_changes, Terraform only manages desired_capacity on the initial creation; subsequent changes by the ASG are preserved. Always include this lifecycle rule in production ASG resources.
The AMI refresh workflow

What actually happens during an AMI refresh — step by step

This is the moment the entire series has been building toward. You now have every piece: the data source that finds the new AMI, the Launch Template that references it, the ASG that manages the fleet, the health checks that gate traffic, and the user_data that bootstraps each node. Here is the exact sequence when you run terraform apply after a new approved AMI is released.

New AMI ID is resolved by the data source
At plan time, Terraform runs data "aws_ami" "approved_pf" and resolves the latest approved AMI. The plan output shows the Launch Template image_id changing from the old AMI ID to the new one.
Terraform
New Launch Template version is created
Terraform calls ec2:CreateLaunchTemplateVersion with the new AMI ID. The LT gets version N+1. The old version remains and can be used for rollback. Terraform updates state to record the new latest version.
Terraform
ASG is updated to reference the new LT version
The ASG's launch_template.version is updated to the new version. This triggers the instance_refresh because triggers = ["launch_template"]. The refresh strategy is Rolling with min_healthy_percentage = 90.
Terraform
terraform apply completes — instance refresh begins asynchronously
Terraform marks the apply complete. The instance_refresh is running in AWS asynchronously. GitHub Actions can poll the refresh status via aws autoscaling describe-instance-refreshes if the pipeline requires it.
ASG (AWS)
First batch of new instances launched (checkpoint: 25%)
ASG launches new instances using the new LT version. Each instance runs user_data: pulls config from S3, sets hostname, writes env file. Lifecycle hook holds the instance in Pending:Wait. Ansible runs, configures PF, calls CompleteLifecycleAction. Instance moves to InService.
ASG (AWS)
NLB health check validates new nodes before old ones are terminated
NLB checks port 8080 on the new instances every 10 seconds. Once the threshold of healthy checks is reached, the instance is registered as healthy in the target group. Only then does the ASG terminate an old instance. The 90% min_healthy_percentage ensures at least 90% of the fleet is always serving traffic.
NLB (AWS)
Staged rollout continues through checkpoints 50%, 75%, 100%
The refresh pauses 60 seconds at each checkpoint. If auto_rollback is true and health checks fail at any checkpoint, the ASG automatically triggers a rollback to the previous LT version. The old instances that haven't been terminated yet are preserved.
ASG (AWS)
All old instances terminated — refresh complete
All engine nodes now run the new AMI. The Terraform state file reflects the updated Launch Template version. Individual instance IDs are not tracked in state. The fleet is fully refreshed with zero downtime if health checks were configured correctly.
ASG (AWS)

What to monitor during a refresh: aws autoscaling describe-instance-refreshes --auto-scaling-group-name pf-prod-pf-engines — shows InstancesToUpdate, InstancesUpdated, Status, and any StatusReason. A Status of Failed with an auto_rollback policy means the old AMI is restored automatically. A Status of Cancelled requires manual investigation.

How long does a refresh take? For a 4-node fleet: approximately (instance warmup 5min + health check settle 2min + checkpoint pause 1min) × 4 stages = ~32 minutes end-to-end. Larger fleets take longer but the math is the same per batch.

Security — IMDSv2

Why http_tokens = "required" is non-negotiable

IMDSv2 (Instance Metadata Service version 2) is a session-oriented protocol that requires a PUT request to get a token before metadata can be retrieved. The old IMDSv1 allowed GET requests directly to 169.254.169.254 — which was vulnerable to SSRF (Server-Side Request Forgery) attacks where a web application vulnerability could be used to steal IAM credentials from the metadata service.

Setting http_tokens = "required" in the Launch Template metadata_options block disables IMDSv1 entirely. Only IMDSv2 token-based requests are accepted. This is a mandatory security control in any enterprise PCI, SOC2, or ISO 27001 environment — and it is the correct default for any new deployment regardless of compliance requirements.

IMDSv1 — vulnerable
http_tokens = "optional"
An attacker exploiting an SSRF vulnerability in a web application running on the PF instance can make a GET request to http://169.254.169.254/latest/meta-data/iam/security-credentials/ and retrieve valid AWS credentials — no authentication required.
IMDSv2 — required
http_tokens = "required"
To get credentials, the attacker must first make a PUT request to receive a token. PUT requests are blocked by most SSRF attack vectors. Even if SSRF exists, the attacker cannot complete the two-step protocol and cannot steal credentials. This single setting closes a critical attack vector.
Capacity planning

Sizing desired, min, and max for PingFederate

The desired/min/max values in the ASG are the operational heartbeat of the PF fleet. Setting them incorrectly means either over-spending on idle capacity or risking service degradation under load. Here is the reasoning framework for PingFederate specifically.

Capacity Configuration Reference
ParameterPurposePF RecommendationNever do this
min_size Floor — never go below this count regardless of scaling policy ≥ 2 for HA. Must be ≥ 2 to survive a single AZ failure without downtime min_size = 0 in production. One AZ failure means full outage.
desired_capacity Starting/target count — what the ASG aims for when not scaling = min_size for stable loads. Terraform uses ignore_changes so auto-scaling can override this Setting desired below min or above max. Terraform will error.
max_size Ceiling — the hard limit on instance count 2–3× desired. Provides burst capacity for authentication spikes max_size = min_size. Eliminates all scaling headroom.
health_check_grace_period Seconds after launch before health checks are enforced 300 seconds (5 min). PingFederate startup takes 2–4 min; allow margin Too short (< 120s). Healthy instances get terminated before PF starts.
min_healthy_percentage Minimum % of fleet healthy during instance_refresh 90%. For a 4-node fleet: 3 nodes always serving, 1 being replaced 100%. Means instances can only be replaced if fleet can exceed desired. Use only with warm pools.
Knowledge check

Test your compute understanding

QYou update the AMI ID in the Terraform data source and run terraform plan. The plan shows the Launch Template will be updated but the ASG will only show a version reference change. How many EC2 instances will be terminated during apply?▼
Zero instances are terminated during apply. Terraform's apply only creates a new Launch Template version and updates the ASG to reference it. The instance_refresh begins asynchronously after apply completes — it is an AWS-side operation, not a Terraform operation. Terraform does not wait for or monitor the refresh unless you use a wait_for_capacity_timeout setting or have GitHub Actions poll the refresh status. The actual instance replacement is performed by the ASG over the following 20–40 minutes, depending on fleet size and warmup settings. This is a critical insight: terraform apply returning success does not mean the new AMI is running on all instances yet.
QA new PF instance fails the NLB health check after an AMI refresh. The health check is on port 8080. The instance is running and you can ping it. What are the three most likely causes to check first?▼
Three most likely causes in order of frequency:

1. PingFederate hasn't started yet — health_check_grace_period expired too soon. If the grace period is too short, the ASG begins enforcing health checks before PF has fully started. Check /var/log/userdata.log and PF logs to see startup progress. Increase health_check_grace_period if PF routinely takes longer than the configured period.

2. PF is listening on port 9031 but not 8080 — wrong health check port. PF's runtime health check endpoint is configurable. If the NLB target group health check is pointing at port 8080 but PF's health endpoint is on a different port, every check will fail. Verify the health check port in the target group matches the PF health endpoint configuration.

3. Security group doesn't allow the NLB health check source. NLB health checks originate from the NLB nodes in the public subnets. If the PF engine security group only allows traffic from the NLB's security group on port 9031, but not on port 8080 (or not from the NLB's IP range), health checks are silently dropped. Add an ingress rule for the health check port from the NLB security group or the public subnet CIDR.
QWhat is the difference between health_check_type = "ELB" and health_check_type = "EC2"? Why does PingFederate require ELB type?▼
EC2 health checks only verify the instance is running (hypervisor-level). ELB health checks verify the application is responding on the specified port. With EC2 type: an instance could be running but have PF in a crashed state, and the ASG would consider it healthy, keep it in the target group, and route traffic to it — resulting in failed federation requests. With ELB type: the NLB health check on port 8080 (or 9031) verifies PF is actually responding before the ASG considers the instance healthy. If PF crashes, the health check fails, the ASG marks the instance unhealthy, deregisters it from the target group, and either replaces it (if below desired) or terminates it. ELB type is always the right choice for application-layer services like PF.
QA junior engineer removes the lifecycle { ignore_changes = [desired_capacity] } block from the ASG. The team scales up from 2 to 4 instances during a peak event. The next morning, someone runs terraform apply for an unrelated change. What happens?▼
Terraform resets desired_capacity to the value in the variable (2) and the ASG terminates 2 instances. Without ignore_changes, Terraform treats the desired_capacity drift (2 declared, 4 actual) as a configuration change and plans to reconcile it. The apply scales the ASG back to 2, terminating 2 healthy instances. If this happens during peak load, the authentication service is degraded or fails. The fix requires two actions: restore the ignore_changes lifecycle rule immediately, and run terraform apply -refresh-only (or terraform state rm + re-import the ASG) to reset state without changing infrastructure. This is one of the most common production incidents in teams new to Terraform managing auto-scaling workloads.
QWhat is the purpose of the initial_lifecycle_hook on the ASG, and what would happen to the PingFederate deployment if it was removed?▼
The lifecycle hook pauses the instance in a Pending:Wait state before it goes InService, giving Ansible time to complete the PF configuration. Without the hook: the instance launches, user_data runs and downloads config from S3, but the ASG immediately moves the instance to InService and the NLB begins routing traffic. If PF hasn't finished starting — which takes 2–4 minutes after Ansible completes — users receive connection errors or malformed SAML responses. With the hook: the instance stays in Pending:Wait (for up to 30 minutes as configured) while Ansible configures and starts PF, runs smoke tests, and then calls aws autoscaling complete-lifecycle-action --lifecycle-action-result CONTINUE. Only then does the ASG move the instance to InService. The default_result = "ABANDON" ensures that if Ansible fails or times out, the instance is terminated rather than being added to the fleet in a broken state.

The following is a terraform plan excerpt after a new AMI was published. For each change shown, identify: (1) which resource is changing, (2) what specifically is changing, (3) whether it is a create/update/replace, and (4) what consequence this has for running PF instances.

# aws_launch_template.pf_engine must be replaced
-/+ resource "aws_launch_template" "pf_engine" {
      ~ id             = "lt-0a1b2c3d4e5f" -> (known after apply)
      ~ latest_version = 3 -> (known after apply)

Is this plan safe to apply to a production PF environment? What should you verify before approving it?

✓Reveal Lab 06-A analysis▼

Launch Template: destroy and recreate (-/+) — The image_id changed. Because the Launch Template uses create_before_destroy = true, a new LT resource will be created first (with the new AMI), then the old one will be destroyed. This is not a risk — the ASG continues to use the old version during the transition. The latest_version attribute showing "(known after apply)" simply means it will be calculated after the new LT is created.

ASG: in-place update (~) — The launch_template.version reference is updating from "3" to "$Latest". This tells the ASG to always use the latest version, which will trigger instance_refresh because triggers = ["launch_template"] is set. No instances are terminated during this apply step.

Is it safe to apply? Before approving: (1) Verify the new AMI ID (ami-0NEW9z8y7x6w5v4u) is the correct approved image — confirm with the infrastructure team. (2) Verify it's an appropriate maintenance window — instance_refresh will replace all nodes over the next 30–40 minutes. (3) Confirm Ansible playbooks are updated for any changes in the new AMI's base configuration. (4) Ensure monitoring and alerting are active to detect health check failures during the refresh.

Lab 06-BAdd a scaling policy to the PF ASG

The operations team wants the PF fleet to scale out automatically when CPU utilisation exceeds 70% for 5 minutes. Write the Terraform resources for a target tracking scaling policy.

  1. Resource type: aws_autoscaling_policy, name: pf_cpu_scale_out
  2. Policy type: TargetTrackingScaling
  3. Target value: 70 (CPU utilization)
  4. Predefined metric: ASGAverageCPUUtilization
  5. Scale-in cooldown: 300 seconds. Scale-out cooldown: 60 seconds
  6. Reference the correct ASG name
✓Reveal Lab 06-B solution▼
HCLscaling_policies.tf
resource "aws_autoscaling_policy" "pf_cpu_scale_out" {
  name                   = "${local.name_prefix}pf-cpu-tracking"
  autoscaling_group_name = aws_autoscaling_group.pf_engines.name
  policy_type            = "TargetTrackingScaling"
  estimated_instance_warmup = 300   # match health_check_grace_period

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value            = 70.0
    scale_in_cooldown       = 300   # 5 min — be conservative scaling in
    scale_out_cooldown      = 60    # 1 min — scale out quickly under load
    disable_scale_in        = false # allow automatic scale-in
  }
}

Module 06 — Key Takeaways
  • The three-layer model: Launch Template (blueprint, Terraform-managed), ASG (fleet policy, Terraform-managed), EC2 Instances (ephemeral compute, ASG-managed, NOT in Terraform state).
  • The Launch Template references all prior modules: AMI from the data source (M02), security group IDs from M04, instance profile ARN from M05, S3 bucket name in user_data for M08.
  • user_data runs once on first boot, renders via templatefile(), is base64-encoded, and is the bridge between the blank AMI and a configured PF node. It pulls config from S3 using the IAM role's IMDS credentials.
  • The instance_refresh block with triggers = ["launch_template"] starts a rolling replacement whenever the LT version changes. It runs asynchronously after terraform apply completes.
  • ignore_changes = [desired_capacity] is mandatory — without it, Terraform resets the fleet count on every apply, overriding any auto-scaling that occurred since the last apply.
  • health_check_type = "ELB" is required for PF — it verifies PF is actually responding, not just that the instance is running. The health_check_grace_period must be longer than PF's startup time.
  • http_tokens = "required" enforces IMDSv2, blocking SSRF-based credential theft. This is a non-negotiable security control in enterprise environments.
  • The lifecycle hook (default_result = ABANDON) prevents a misconfigured or incomplete PF instance from joining the fleet. Without it, half-configured instances accept traffic and cause federation errors.
