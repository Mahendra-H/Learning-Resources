VPC fundamentals

What a VPC is and why PingFederate needs one

A Virtual Private Cloud (VPC) is a logically isolated network within AWS. It is the container for every other network resource — subnets, route tables, security groups, gateways. Everything in the PingFederate migration runs inside a VPC. Terraform creates and manages the VPC and all of its components as a dependency graph of resources.

In enterprise deployments, the VPC is typically provisioned by a dedicated networking team and shared across multiple workloads — or it is provisioned per-application in an isolated account. Either way, Terraform manages it. If your project already has a VPC, the PingFederate Terraform configuration reads it as a data source rather than creating a new one.

CIDR block — the address space of your VPC
A VPC is assigned a CIDR block — the range of private IP addresses available to all resources within it. A common enterprise choice is 10.0.0.0/16, which provides 65,536 addresses. The CIDR must be large enough to accommodate all subnets across all availability zones, plus room for future growth. In AWS, VPC CIDR ranges cannot be changed after creation — choose carefully.
HCLvpc.tf — complete VPC with all components
# ── VPC ───────────────────────────────────────────────────────────────
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr        # e.g. "10.0.0.0/16"
  enable_dns_support   = true               # required for Route53 private zones
  enable_dns_hostnames = true               # required for EFS, SSM, and others

  tags = merge(local.common_tags, { Name = "${local.name_prefix}vpc" })
}

# ── INTERNET GATEWAY — allows public subnets to reach the internet ────
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id   # implicit dependency on VPC
  tags   = merge(local.common_tags, { Name = "${local.name_prefix}igw" })
}

# ── PUBLIC SUBNETS — one per AZ ────────────────────────────────────────
resource "aws_subnet" "public" {
  for_each = var.public_subnets   # map of {name: {cidr, az}}

  vpc_id                  = aws_vpc.main.id
  cidr_block              = each.value.cidr
  availability_zone       = each.value.az
  map_public_ip_on_launch = true    # NLB/ALB nodes get public IPs
  tags = merge(local.common_tags, { Name = "${local.name_prefix}public-${each.key}", Tier = "public" })
}

# ── PRIVATE SUBNETS — where PF engine nodes live ──────────────────────
resource "aws_subnet" "private" {
  for_each = var.private_subnets

  vpc_id                  = aws_vpc.main.id
  cidr_block              = each.value.cidr
  availability_zone       = each.value.az
  map_public_ip_on_launch = false   # PF nodes NEVER get public IPs
  tags = merge(local.common_tags, { Name = "${local.name_prefix}private-${each.key}", Tier = "private" })
}

# ── ELASTIC IPs for NAT GATEWAYS ──────────────────────────────────────
# One NAT GW per AZ for high availability (or one shared for cost saving)
resource "aws_eip" "nat" {
  for_each = var.public_subnets
  domain   = "vpc"
  tags     = merge(local.common_tags, { Name = "${local.name_prefix}nat-eip-${each.key}" })
}

# ── NAT GATEWAY — allows private subnet instances to reach internet ────
# Lives in PUBLIC subnets; forwards traffic from PRIVATE subnets
resource "aws_nat_gateway" "main" {
  for_each      = var.public_subnets
  allocation_id = aws_eip.nat[each.key].id
  subnet_id     = aws_subnet.public[each.key].id
  tags          = merge(local.common_tags, { Name = "${local.name_prefix}nat-${each.key}" })
  depends_on    = [aws_internet_gateway.main]   # IGW must exist first
}

# ── ROUTE TABLES ──────────────────────────────────────────────────────
# Public route table: default route via Internet Gateway
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
  tags = merge(local.common_tags, { Name = "${local.name_prefix}public-rt" })
}

# Private route tables: one per AZ, default route via respective NAT GW
resource "aws_route_table" "private" {
  for_each = var.public_subnets
  vpc_id   = aws_vpc.main.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.main[each.key].id
  }
  tags = merge(local.common_tags, { Name = "${local.name_prefix}private-rt-${each.key}" })
}

# ── ROUTE TABLE ASSOCIATIONS ──────────────────────────────────────────
resource "aws_route_table_association" "public" {
  for_each       = var.public_subnets
  subnet_id      = aws_subnet.public[each.key].id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table_association" "private" {
  for_each       = var.private_subnets
  subnet_id      = aws_subnet.private[each.key].id
  route_table_id = aws_route_table.private[each.key].id
}
PingFederate network topology

Why PingFederate lives in private subnets

PingFederate engine nodes never have public IP addresses. They live in private subnets, isolated from direct internet access. All inbound federation traffic arrives via the Network Load Balancer, which sits in the public subnets. All outbound traffic from the engine nodes — to reach S3, LDAP, AWS APIs, package repositories — routes through the NAT Gateway in the public subnet.

This design is not just a security best practice — it is a compliance requirement in most enterprise environments. The NLB is the single controlled ingress point. The PingFederate nodes themselves are never directly reachable from outside the VPC.

PingFederate VPC Topology — Two Availability Zones
Why private subnets for PF engines
Defence in depth
PingFederate nodes process authentication requests with access to private keys, LDAP credentials, and configuration secrets. Placing them in private subnets means there is no route from the internet directly to these nodes — only through the NLB, which enforces health checks and port-level access control. A compromised internet-facing component cannot directly reach the PF nodes.
Why NAT Gateway for outbound
Private access to AWS services
PF engine nodes need to reach AWS services (S3 for config, SSM for parameter lookups, package repositories during AMI baking). Without a NAT Gateway, private subnet instances have no path to the internet or AWS service endpoints. The NAT GW provides a controlled, one-way outbound path — inbound connections are still blocked.
Security groups

Security groups — the instance-level firewall

Security groups are stateful, instance-level firewalls. Unlike NACLs (which are stateless and apply at the subnet level), security groups track connection state — an allowed inbound connection automatically allows the return traffic. This is why security groups are the primary network control mechanism in AWS, not NACLs.

In Terraform, security groups support two patterns for managing rules: inline rules (defined inside the aws_security_group block) and separate aws_security_group_rule resources. Enterprise deployments almost always use separate rule resources to avoid state conflicts when rules are added dynamically and to make the rules individually reviewable in plan output.

SG-to-SG references — the enterprise pattern
Instead of specifying CIDR blocks in security group rules, enterprise Terraform uses SG-to-SG references: "allow inbound traffic from instances that have security group X attached." This is more robust than CIDRs — it doesn't break when IP addresses change, it explicitly models trust relationships between components, and it provides clean audit evidence of which component can talk to which.
HCLsecurity_groups.tf — complete PingFederate SG set
# ── NLB SECURITY GROUP ────────────────────────────────────────────────

NACLs vs security groups

When to use each — and why most teams stick to security groups

Network ACLs (NACLs) and security groups both control traffic at the network level, but they operate very differently. Understanding the distinction is important for reading existing Terraform configurations and for participating in network architecture discussions.

NACL vs Security Group — Key Differences
AttributeNetwork ACL (NACL)Security Group
Applies atSubnet level — all traffic in/out of subnetInstance level — attached to ENI

Rule evaluationNumbered rules, lowest number wins, ends at DENYAll rules evaluated, most permissive wins

Enterprise usageUsed for broad subnet-level blocks (compliance)Used for all instance-level access control
Terraform resourceaws_network_aclaws_security_group
Why NACLs are a blunt instrument
Because NACLs are stateless, you must allow both the request and the response explicitly. For a TCP connection on an ephemeral port (which is how every HTTP/HTTPS/TLS response works), this means allowing a broad range of return ports (1024–65535). Security groups handle this automatically. As a result, most enterprise teams only use NACLs for broad compliance requirements — e.g. "deny all traffic from known-bad CIDR ranges at the subnet level" — and rely on security groups for all meaningful access control.
Networking outputs

Exposing network IDs for downstream modules

The VPC and subnet IDs produced by this networking configuration are consumed by every other module — IAM instance profiles need the VPC ID for certain policies, the ASG needs the private subnet IDs, the NLB needs the public subnet IDs, and the security group IDs are referenced by every compute resource. Outputs are how those values flow between configurations.

HCLoutputs.tf — networking module outputs
output "vpc_id" {
  description = "VPC ID — consumed by all downstream modules"
  value       = aws_vpc.main.id
}

output "private_subnet_ids" {
  description = "Private subnet IDs — for ASG placement"
  value       = [for s in aws_subnet.private : s.id]
}

output "public_subnet_ids" {
  description = "Public subnet IDs — for NLB/ALB placement"
  value       = [for s in aws_subnet.public : s.id]
}

output "pf_engine_sg_id" {
  description = "PF engine security group ID — attached to Launch Template"
  value       = aws_security_group.pf_engine.id
}

output "nlb_sg_id" {
  description = "NLB security group ID — for PF engine SG rule source"
  value       = aws_security_group.nlb.id
}

The dependency chain in practice
Notice how the networking module's outputs become the inputs to the compute module (M06). The ASG needs private_subnet_ids to know where to launch instances. The Launch Template needs pf_engine_sg_id to attach the right security group. The NLB needs public_subnet_ids to place its nodes correctly. This output → input chain is how enterprise Terraform configurations are composed from independent modules — each module has clear boundaries, and the state of each is accessible via remote state data sources.
Knowledge check

Test your networking understanding

QWhy does the NAT Gateway live in the public subnet rather than the private subnet? Isn't it there to serve private subnet instances?▼
The NAT Gateway itself needs a path to the internet — which means it needs to be in a subnet with a route to the Internet Gateway. Private subnets have no route to the IGW; that's what makes them private. The NAT Gateway sits in the public subnet, which has an IGW route, and serves as a "translator" for private subnet instances: outbound traffic from private instances goes to the NAT GW, which uses its Elastic IP to send it to the internet. Return traffic comes back to the Elastic IP and is forwarded back to the originating private instance. The private instance never has a public IP — the NAT GW provides address translation on its behalf.
QA security group rule uses source_security_group_id instead of cidr_blocks. What does this actually mean at the network level?▼
It means "allow traffic from any instance that has this security group attached to its network interface." AWS enforces this at the hypervisor level — when a packet arrives, AWS checks the source instance's attached security groups. If one of them matches the source_security_group_id, the traffic is allowed. This is more precise and more robust than CIDR-based rules because: (1) it doesn't break when IP addresses change, (2) it models the actual trust relationship ("the NLB can reach the PF engine"), and (3) it works across availability zones without knowing the IP ranges.
QThe PF engine security group has a rule allowing port 7600 inbound from itself (the same security group ID as source). Why? What does "self-reference" mean in a security group context?▼
A self-referencing security group rule allows traffic between instances that share the same security group. In the PingFederate engine cluster, every engine node has the same security group attached. A self-referencing rule on port 7600 means: any engine can communicate with any other engine on that port, but no other instance can. This is the JGroups cluster communication port that PingFederate uses for cluster state synchronisation, session replication, and node discovery. Without it, a new engine instance joining the cluster after an AMI refresh would be isolated — it would not be able to join the cluster or receive replicated session state from existing nodes.
QIn the Terraform configuration, both public and private subnets use for_each = var.public_subnets for the NAT Gateways and route tables. Why iterate over the public subnet map when creating private route tables?▼
Because there is one NAT Gateway per availability zone, and each AZ's NAT GW sits in that AZ's public subnet. The pattern ensures AZ-to-AZ correspondence: private-1a uses NAT-1a, private-1b uses NAT-1b. By iterating over the public subnet map (which is keyed by AZ name), we ensure the correct NAT Gateway is referenced for each AZ's private route table. If we used a single shared NAT Gateway, all private subnet traffic would route through one AZ — cross-AZ traffic incurs data transfer costs and introduces a single point of failure if that AZ's NAT GW becomes unavailable. The per-AZ pattern is both more resilient and more cost-effective in production.
QA colleague suggests removing the NAT Gateway to save costs — "PF just needs to talk to S3, and S3 has a VPC endpoint." Is this a reasonable trade-off?▼
Partially — but removing the NAT Gateway entirely requires careful analysis of everything PF needs to reach outbound. S3 can indeed be accessed via a VPC Gateway Endpoint (free) without a NAT GW. However, PF also needs to reach: LDAP/AD (on-premises, requires NAT or Direct Connect), OCSP responders and CRL distribution points (public internet), AWS SSM (can be replaced with VPC Interface Endpoints, at cost), and potentially OIDC discovery endpoints for upstream IdPs. If all of these can be served by VPC endpoints or private connectivity (Direct Connect, Transit Gateway), the NAT GW could be removed. In practice, most enterprise environments keep the NAT GW because the alternative — managing 6-8 VPC Interface Endpoints — costs more than the NAT GW and adds operational complexity. Always model the full outbound dependency list before removing NAT.
QYou run terraform plan and see that Terraform wants to destroy and recreate two private subnets. What is the most likely cause and why is this potentially catastrophic?▼
The most likely cause is a CIDR block change or an availability zone change — both of which are immutable attributes that force subnet recreation. AWS subnets cannot have their CIDR blocks changed after creation. If the variable value for a subnet's CIDR changed, Terraform must destroy and recreate it. This is catastrophic because: (1) the ASG instances running in those subnets will be terminated when the subnet is destroyed, (2) all ENIs in the subnet are terminated, (3) any EFS mount targets, RDS subnet group memberships, or VPC endpoint associations in those subnets are also destroyed. The correct approach when you must change subnet CIDRs is a blue/green VPC migration — provision a new VPC with the new CIDR, migrate workloads, decommission the old VPC. Never allow Terraform to destroy production subnets with running workloads.

Module 04 — Key Takeaways
  • The VPC is the first resource provisioned — everything else depends on it. Terraform's implicit dependency graph ensures this ordering automatically through resource references.
  • PingFederate engine nodes live in private subnets with no public IPs. All inbound federation traffic arrives via the NLB in public subnets. All outbound traffic routes through NAT Gateways in public subnets.
  • One NAT Gateway per AZ is the production pattern — per-AZ resilience and cost-efficient cross-AZ traffic avoidance. A single shared NAT GW is acceptable only in dev/test.
  • Security groups are stateful and instance-level. NACLs are stateless and subnet-level. Use security groups for all access control; NACLs only for broad compliance blocks.
  • SG-to-SG references are the enterprise standard — they model trust relationships, survive IP changes, and provide clean audit evidence. Avoid CIDR blocks where a SG reference can be used instead.
  • The PF engine self-references port 7600 (JGroups) so cluster nodes can communicate with each other without opening that port to any other instance in the VPC.
  • VPC and subnet outputs (IDs) flow to downstream modules as inputs. The networking module is the dependency of all compute, load balancer, and storage modules.
  • Subnet CIDR blocks are immutable — changing them forces destroy and recreate. In production, this means migrating workloads first, not letting Terraform destroy live subnets.
