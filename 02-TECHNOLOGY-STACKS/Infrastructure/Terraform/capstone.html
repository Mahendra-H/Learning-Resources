How to use this capstone

The rules of engagement

The capstone is a guided self-build challenge. Each section presents a requirement — what needs to exist in your Terraform configuration. You write the code. You decide the attribute values. You connect the pieces.

Three tools are available for each challenge: a Hint (a nudge in the right direction without giving the answer), a Key Concept reminder (which module covers this), and a Solution reveal (the reference implementation — consult only after a genuine attempt).

Work through the sections in order. Every section depends on the previous one — the VPC outputs feed the IAM module, the IAM output feeds the Launch Template, and so on. This is the same dependency chain your real project uses.

Start with an empty directory. When all eight sections are complete, the 25-point Enterprise Readiness Checklist at the bottom verifies you have implemented every critical control correctly.

Challenge 01 of 08

Build the network foundation

01
VPC, Subnets, NAT Gateways & Security Groups
Module reference: M04 · Network Foundation
~45 min ▼

Create a complete VPC configuration for a two-AZ PingFederate deployment. The network must support the immutable compute pattern: engine nodes in private subnets with no public IPs, NLB nodes in public subnets, NAT Gateways for outbound connectivity.

Starting point: An empty vpc.tf, security_groups.tf, and variables.tf. A locals.tf with name_prefix = "pf-${var.environment}-" and common_tags.

Requirements
  • VPC with DNS support and DNS hostnames enabled. CIDR from variable.
  • Two public subnets (one per AZ) — for NLB nodes and NAT Gateways. map_public_ip_on_launch = true.
  • Two private subnets (one per AZ) — for PF engine nodes. map_public_ip_on_launch = false.
  • Internet Gateway attached to the VPC.
  • One NAT Gateway per AZ (in public subnets), each with an Elastic IP.
  • Public route table with default route to IGW, associated with public subnets.
  • Two private route tables (one per AZ), each with default route to its AZ's NAT GW, associated with private subnets.
  • Security group for NLB — ingress on 9031 and 443 from 0.0.0.0/0, all egress.
  • Security group for PF engines — ingress 9031 from NLB SG only, ingress 9999 from bastion SG, ingress 7600 self-reference (JGroups), all egress.
  • Outputs: vpc_id, private_subnet_ids, public_subnet_ids, pf_engine_sg_id, nlb_sg_id.
HINT Struggling with the for_each subnet pattern? ▼
Use a map(object({cidr=string, az=string})) variable for both public and private subnets. The map key becomes the subnet name. Iterate both subnet maps with for_each. Each NAT Gateway's key should correspond to the public subnet key so you can reference aws_nat_gateway.main[each.key] in the private route tables. The private route table for_each can iterate over the same var.public_subnets map to maintain AZ correspondence.
HINT How do I write the JGroups self-referencing security group rule? ▼
Use aws_security_group_rule (not inline). Set source_security_group_id = aws_security_group.pf_engine.id — the same SG as the target. This means "allow traffic between instances that share this security group". Use port 7600, protocol = "tcp".
SOLUTION View the reference implementation for Challenge 01 ▼

Reference the complete annotated implementation in Module 04 — sections "VPC fundamentals" and "Security groups". The code there is production-ready with every attribute explained. Key points to verify your solution against:

  • NAT GW depends on IGW explicitly: depends_on = [aws_internet_gateway.main]
  • Private route tables iterate over public subnet keys (for AZ correspondence)
  • SG rules use aws_security_group_rule not inline blocks (prevents state conflicts)
  • All five outputs are declared in outputs.tf
02
IAM Role, Policy & Instance Profile
Module reference: M05 · IAM & Instance Profiles
~30 min ▼

Create the IAM role that PingFederate EC2 instances will assume. The role provides credential-free access to AWS services via the instance metadata service (IMDS). No static credentials should be needed anywhere in the configuration.

Requirements
  • IAM role with trust policy allowing ec2.amazonaws.com to assume it. Path: /pingfederate/.
  • Customer-managed IAM policy with least-privilege permissions: S3 GetObject/GetObjectVersion/ListBucket on the config bucket ARN (accept as variable), CloudWatch logs:Create*/PutLogEvents scoped to /pingfederate/*, SSM GetParameter* scoped to /pingfederate/*, KMS Decrypt/GenerateDataKey on the CMK ARN (accept as variable), EC2 DescribeInstances/DescribeTags on *.
  • Attach the customer-managed policy to the role via policy attachment resource.
  • Attach AWS-managed AmazonSSMManagedInstanceCore for Session Manager access.
  • Instance profile wrapping the role. Path: /pingfederate/.
  • Outputs: pf_instance_profile_arn, pf_instance_role_arn.
HINT What's the difference between the role ARN and the instance profile ARN output? ▼
The instance profile ARN is what you put in the Launch Template (aws_iam_instance_profile.pf_instance.arn). The role ARN is what other services (monitoring, cross-account access) use to reference the identity (aws_iam_role.pf_instance.arn). EC2 cannot use a role ARN directly — only a profile ARN. Output both, they serve different consumers.
SOLUTION View the reference implementation for Challenge 02 ▼
Reference Module 05 — "Complete Terraform implementation" section. Verify: four separate resource blocks (role, policy, attachment, profile), trust policy uses jsonencode(), permission policy ARNs are constructed using data sources not hardcoded strings, AmazonSSMManagedInstanceCore is a second separate attachment resource.
03
S3 Configuration Bucket with KMS Encryption
Module reference: M08 · S3 & Config Externalisation
~40 min ▼

Provision the S3 bucket that stores PingFederate configuration. This is the persistence layer that makes immutable compute possible — instances read their configuration from this bucket on first boot and again whenever they are replaced. The bucket must be secured, versioned, and encrypted.

Requirements
  • S3 bucket with a globally unique name including the account ID. force_destroy = false.
  • Versioning enabled — required for config rollback capability.
  • KMS key with auto-rotation enabled, 30-day deletion window. KMS key policy grants root account full access, PF instance role decrypt, CI/CD role encrypt.
  • SSE-KMS encryption using the KMS key. bucket_key_enabled = true.
  • Block all public access — all four settings true.
  • Bucket policy: Allow PF instance role S3 read, Allow CI/CD role S3 write, Deny all non-HTTPS requests.
  • Lifecycle rule: keep 10 non-current versions, expire non-current after 90 days, transition non-current to STANDARD_IA after 30 days.
  • Outputs: config_bucket_name, config_bucket_arn, config_kms_key_arn.
HINT The bucket policy needs the role ARN but the role is in a different file — how do I reference it? ▼
In the capstone, everything is in the same root configuration, so you can reference aws_iam_role.pf_instance.arn directly. In a module-based setup, the IAM role ARN would come from a module output passed as a variable to the S3 module. For the capstone, direct resource references across files in the same directory work fine — Terraform loads all .tf files in the directory as one configuration.
HINT How do I write the DenyNonHTTPS bucket policy statement? ▼
Use a Deny effect with Principal "*" and Action "s3:*", with a Condition: Bool: {"aws:SecureTransport": "false"}. When SecureTransport is false (plain HTTP), the request is denied for everyone. This is one of the few cases where using Principal "*" in a bucket policy is correct — the intent is to deny ALL principals who use HTTP.
SOLUTION View the reference implementation for Challenge 03 ▼
Reference Module 08 — "Complete S3 configuration" section. Six separate resource blocks. The depends_on on the bucket policy (depends on public_access_block) and lifecycle (depends on versioning) are easy to miss — verify both are present in your implementation.
04
Launch Template with IMDSv2 & user_data
Module reference: M06 · EC2, Launch Templates & ASG
~50 min ▼

Build the Launch Template that defines every PF engine instance. This is the blueprint the ASG uses to launch new instances. It must reference the AMI data source, the instance profile from Challenge 02, the security group from Challenge 01, and embed the bootstrap user_data script.

Requirements
  • Data source aws_ami — filter for the latest approved company AMI using owner account ID, name glob pattern, state=available, and ApprovalStatus=approved tag.
  • Launch Template with name_prefix. Image ID from the data source. Instance type from variable.
  • IAM instance profile block — reference the profile ARN from Challenge 02. Use arn, not the role name directly.
  • Network interface block — no public IP, security groups from Challenge 01's SG ID output.
  • EBS root volume — gp3, 50GB, encrypted=true, KMS key from Challenge 03, delete_on_termination=true.
  • user_data — write a bash template that: (1) configures IMDSv2 token for all curl calls, (2) downloads config from S3 using the bucket name, (3) writes an environment file at /etc/pingfederate-env. Use templatefile() + base64encode().
  • Metadata options: http_tokens = "required" (IMDSv2 mandatory), hop_limit=1.
  • Monitoring enabled. Tag specifications for instance and volume.
  • lifecycle { create_before_destroy = true }
HINT How do I use templatefile() and base64encode() together for user_data? ▼
Create a file templates/userdata.sh.tpl with your bash script. Use ${variable_name} syntax inside the template for Terraform to substitute values. In the Launch Template: user_data = base64encode(templatefile("${path.module}/templates/userdata.sh.tpl", { config_bucket = aws_s3_bucket.pf_config.bucket, environment = var.environment, aws_region = var.aws_region })). The path.module ensures the path resolves correctly regardless of which directory Terraform is run from.
HINT What's the AMI data source filter for company-approved images? ▼
Use three filters: filter { name = "name"; values = ["company-approved-pf-*"] }, filter { name = "state"; values = ["available"] }, filter { name = "tag:ApprovalStatus"; values = ["approved"] }. Set owners = [var.ami_owner_account_id] and most_recent = true. Without most_recent, the data source fails if multiple AMIs match.
SOLUTION View the reference implementation for Challenge 04 ▼
Reference Module 06 — "Launch Template" and "user_data bootstrap script" sections. Critical checks: profile uses arn not name, http_tokens = "required" not "optional", gp3 volume uses kms_key_id from the KMS key resource, user_data uses IMDSv2 token in the bash template (PUT request to get token before any metadata calls).
05
Auto Scaling Group with instance_refresh
Module reference: M06 · EC2, Launch Templates & ASG
~40 min ▼

Create the Auto Scaling Group that manages the fleet of PF engine nodes. This is the resource that implements rolling AMI replacement through instance_refresh. It references the Launch Template from Challenge 04, the private subnets from Challenge 01, and the NLB target group (from Challenge 07 — accept as variable for now).

Requirements
  • ASG referencing the Launch Template using latest_version.
  • Placed in private subnets from Challenge 01 outputs.
  • desired/min/max from variables. health_check_type = "ELB". health_check_grace_period = 300.
  • Target group ARN (from variable var.nlb_target_group_arn) — the ASG registers instances automatically.
  • instance_refresh block: strategy=Rolling, min_healthy_percentage=90, instance_warmup=300, checkpoint_percentages=[25,50,75,100], auto_rollback=true, triggers=["launch_template"].
  • Lifecycle hook on launch: heartbeat_timeout=1800, default_result=ABANDON. This holds new instances in Pending:Wait until Ansible completes.
  • termination_policies = ["OldestLaunchTemplate", "Default"].
  • Dynamic tags block propagating all common_tags to instances.
  • lifecycle { ignore_changes = [desired_capacity] } — mandatory.
HINT Why does the ASG reference latest_version instead of a specific version number? ▼
Using version = aws_launch_template.pf_engine.latest_version means the ASG always references the most recent LT version. When Terraform creates a new LT version (triggered by an AMI change), this reference updates — which triggers instance_refresh. Hardcoding a version number like version = "3" means you must manually update the ASG after every LT change. The dynamic reference makes the refresh automatic.
HINT How do I write the dynamic tag block for the ASG? ▼
ASG tags use a different syntax from resource tags — each tag is a block, not a map: dynamic "tag" { for_each = local.common_tags; content { key = tag.key; value = tag.value; propagate_at_launch = true } }. The propagate_at_launch = true means each launched instance will inherit these tags. Without this, ASG tags exist on the ASG itself but not on the EC2 instances.
SOLUTION View the reference implementation for Challenge 05 ▼
Reference Module 06 — "Auto Scaling Group" section. The most commonly missed requirements: ignore_changes = [desired_capacity] in lifecycle (without this, auto-scaling changes get reverted), default_result = "ABANDON" in the lifecycle hook (CONTINUE would allow broken instances into the fleet), and auto_rollback = true in instance_refresh preferences.
06
Network Load Balancer, Target Group & Listener
Module reference: M07 · Load Balancers & Route53
~35 min ▼

Build the traffic layer. The NLB sits in the public subnets and receives federation requests from the internet. It forwards to the PF engine target group using TCP passthrough — PF terminates TLS with its own federation certificate. The health check on port 8080 gates traffic during AMI refresh.

Requirements
  • Internet-facing NLB of type network, placed in public subnets from Challenge 01. enable_cross_zone_load_balancing = true. enable_deletion_protection conditional on environment being prod.
  • Target group: port 9031, protocol TCP, instance type. Health check: HTTP on port 8080, path /pingfederate/rest/v1/version, healthy_threshold=3, unhealthy_threshold=3, interval=10. deregistration_delay = 60. lifecycle { create_before_destroy = true }.
  • TCP listener on port 9031 forwarding to the target group.
  • Outputs: nlb_dns_name, nlb_zone_id, federation_target_group_arn.
HINT Why does the NLB use protocol=TCP but the health check uses protocol=HTTP? ▼
These are two different things. The listener protocol (TCP) controls how the NLB forwards traffic to the backend — pure passthrough, no HTTP inspection. The health check protocol (HTTP) controls how the NLB probes the backend to determine if it's healthy. NLB supports HTTP/HTTPS health checks even for TCP target groups. This lets you verify PF is actually responding (HTTP layer) while keeping the main traffic path as TLS passthrough (TCP layer).
SOLUTION View the reference implementation for Challenge 06 ▼
Reference Module 07 — "NLB in Terraform" section. Key checks: health check path is the PF runtime API endpoint (not just /), deregistration_delay = 60 (in seconds — allows in-flight SAML flows to drain), target_group uses target_type = "instance" (not IP), cross-zone is enabled.
07
Route53 Alias Record & Health Check
Module reference: M07 · Load Balancers & Route53
~25 min ▼

Give the PingFederate federation endpoint a stable DNS name. The Route53 alias record points to the NLB from Challenge 06. An alias record is preferred over CNAME — free, no extra DNS lookup, works at zone apex, supports health evaluation.

Requirements
  • Look up the existing hosted zone by name (data source, not resource — assume the zone already exists).
  • Alias A record: name = pf.${var.hosted_zone_name}, aliased to the NLB DNS name and zone_id from Challenge 06. evaluate_target_health = true.
  • Route53 health check: HTTPS_STR_MATCH on port 9031, path /pingfederate/rest/v1/version, search_string = "version", interval=30, failure_threshold=3, measure_latency=true. Check from at least two regions.
  • CloudWatch alarm on the health check — triggers when HealthCheckStatus < 1. Sends to var.alert_sns_topic_arn.
  • Output: federation_fqdn.
HINT What's the NLB zone_id and why is it different from the Route53 hosted zone_id? ▼
The NLB has its own zone_id — this is AWS's internal hosted zone for load balancer DNS names (not your hosted zone). You reference it as aws_lb.pf_nlb.zone_id. In the Route53 alias block, zone_id = aws_lb.pf_nlb.zone_id and name = aws_lb.pf_nlb.dns_name. The Route53 zone_id in the record resource is your hosted zone: zone_id = data.aws_route53_zone.main.zone_id. Two different zone_ids, two different purposes.
SOLUTION View the reference implementation for Challenge 07 ▼
Reference Module 07 — "Route53" and "Lab 07-B" sections. Verify: alias record uses type A (not CNAME), evaluate_target_health=true is set, the CloudWatch alarm uses Minimum statistic (not Average) and threshold=1 (1=healthy), the health check regions list has at least two regions.
08
Connect Everything: Variables, Outputs & Backend
Module references: M02, M03, M09 — connecting it all
~30 min ▼

Your resources are built. Now wire them together at the root level and ensure the configuration is production-ready: remote state, provider pinning, a complete variables.tf, and a single outputs.tf that exposes the key deployment artifacts.

Requirements
  • versions.tf: Terraform >= 1.5.0, AWS provider ~> 5.0, S3 backend with DynamoDB locking. Key: pingfederate/${var.environment}/terraform.tfstate.
  • variables.tf: All required variables declared with types and descriptions. Required variables (no defaults): environment, vpc_cidr, public_subnets, private_subnets, hosted_zone_name, ami_owner_account_id, cicd_role_arn, alert_sns_topic_arn. Optional with defaults: aws_region, pf_instance_type, pf_engine_desired/min/max.
  • provider.tf: AWS provider with region from variable, default_tags block with Environment, ManagedBy=terraform, Application=PingFederate.
  • Fix the circular dependency: the ASG needs nlb_target_group_arn but the NLB needs to be created first. Ensure the ASG references the target group ARN directly from the target group resource (not a variable).
  • outputs.tf: Export nlb_dns_name, federation_fqdn, asg_name, config_bucket_name, pf_instance_profile_arn.
  • Verify by running terraform validate — no errors.
HINT The ASG had nlb_target_group_arn as a variable — how do I fix the circular dependency? ▼
In the capstone (root configuration), there is no circular dependency — you can reference the target group directly: target_group_arns = [aws_lb_target_group.pf_federation.arn]. The "variable" approach was used in the modular version (M06/M07) because modules cannot call each other. In the root configuration, all resources are peers — direct references work fine and are preferred. Terraform resolves the dependency: target group is created first, then the ASG references it.
SOLUTION Review the complete connectivity checklist ▼

Key cross-resource connections that must be correct:

  • Launch Template image_id → data.aws_ami.approved_pf.id
  • Launch Template iam_instance_profile.arn → aws_iam_instance_profile.pf_instance.arn
  • Launch Template security_groups → [aws_security_group.pf_engine.id]
  • Launch Template kms_key_id (EBS) → aws_kms_key.pf_config.arn
  • Launch Template user_data → S3 bucket name from aws_s3_bucket.pf_config.bucket
  • IAM policy S3 resource → aws_s3_bucket.pf_config.arn
  • IAM policy KMS resource → aws_kms_key.pf_config.arn
  • S3 bucket policy principal → aws_iam_role.pf_instance.arn
  • KMS key policy → aws_iam_role.pf_instance.arn
  • ASG vpc_zone_identifier → private subnet IDs from aws_subnet.private
  • ASG target_group_arns → [aws_lb_target_group.pf_federation.arn]
  • NLB subnets → public subnet IDs from aws_subnet.public
  • Route53 record → NLB dns_name and zone_id
