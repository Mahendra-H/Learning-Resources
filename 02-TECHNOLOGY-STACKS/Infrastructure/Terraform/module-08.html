The core pattern

Config externalisation — why instances can be replaced safely

The immutable infrastructure model has a fundamental tension: instances are ephemeral and replaced regularly, but application configuration is precious and must survive replacement. In the traditional model, configuration is stored on the instance — in files, in local databases, in application memory. When the instance is replaced, configuration is lost.

Config externalisation resolves this tension by storing all configuration outside the instance lifecycle in a durable, versioned store. When a new instance launches, it retrieves the current configuration from the external store and initialises itself. The instance becomes stateless — its only unique attribute is the currently assigned private IP address, which is ephemeral by design.

For PingFederate, the external store is S3. The configuration includes the PF runtime configuration zip (server settings, connection templates, adapter configs), the signing and encryption keystores, the OAuth client registry exports, and any environment-specific property files. Everything that makes this PF installation this PF installation lives in S3, not on the instance.

Complete S3 configuration

Provisioning the PingFederate config bucket

The S3 configuration bucket requires more than just the aws_s3_bucket resource. Modern AWS S3 best practice uses separate resource blocks for each bucket configuration aspect — versioning, encryption, public access blocking, logging, and lifecycle rules. This separation allows each aspect to be managed independently and makes the plan output granular and readable.

HCLs3.tf — PingFederate config bucket (complete)
# ── THE BUCKET ────────────────────────────────────────────────────────
resource "aws_s3_bucket" "pf_config" {
  # Globally unique bucket name — include account ID to guarantee uniqueness
  bucket = "${local.name_prefix}config-${data.aws_caller_identity.current.account_id}"
  # e.g. "pf-prod-config-123456789012"

  # force_destroy: if true, terraform destroy deletes bucket even if non-empty
  # NEVER true in prod — set false to prevent accidental data loss
  force_destroy = false

  tags = merge(local.common_tags, {
    Name        = "${local.name_prefix}pf-config"
    DataClass   = "Confidential"   # contains keystores and credentials
    BackupPolicy = "versioned-s3"
  })
}

# ── VERSIONING ────────────────────────────────────────────────────────
# Critical: if a bad config is deployed, you can restore the previous version
resource "aws_s3_bucket_versioning" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id
  versioning_configuration {
    status = "Enabled"
  }
}

# ── SERVER-SIDE ENCRYPTION ────────────────────────────────────────────
# SSE-KMS: stronger than SSE-S3, key usage is auditable in CloudTrail
resource "aws_s3_bucket_server_side_encryption_configuration" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.pf_config.arn
    }
    # bucket_key_enabled: reduces KMS API calls by using a bucket-level key
    # Significant cost saving when many objects are accessed frequently
    bucket_key_enabled = true
  }
}

# ── BLOCK ALL PUBLIC ACCESS ───────────────────────────────────────────
# This bucket must NEVER be public. Enforce at the bucket level.
resource "aws_s3_bucket_public_access_block" "pf_config" {
  bucket                  = aws_s3_bucket.pf_config.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# ── ACCESS LOGGING ────────────────────────────────────────────────────
# Log every GetObject to a separate audit log bucket
# Required for security audits: who read config, when, from which IP
resource "aws_s3_bucket_logging" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id

  target_bucket = aws_s3_bucket.access_logs.id
  target_prefix = "pf-config-access/"
}

# ── LIFECYCLE RULES ───────────────────────────────────────────────────
# Keep last 10 non-current versions; expire older ones after 90 days
# Prevents unbounded version accumulation and cost growth
resource "aws_s3_bucket_lifecycle_configuration" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id

  # Only apply after versioning is enabled
  depends_on = [aws_s3_bucket_versioning.pf_config]

  rule {
    id     = "expire-old-versions"
    status = "Enabled"

    filter { prefix = "" }   # apply to all objects

    # Keep 10 most recent non-current (older) versions
    noncurrent_version_expiration {
      noncurrent_days           = 90    # expire after 90 days
      newer_noncurrent_versions = 10    # but always keep last 10
    }

    # Move non-current versions to cheaper storage after 30 days
    noncurrent_version_transition {
      noncurrent_days           = 30
      newer_noncurrent_versions = 10
      storage_class             = "STANDARD_IA"
    }
  }
}

# ── BUCKET POLICY ─────────────────────────────────────────────────────
# Restrict: only the PF instance role can read from this bucket
# Deny all other IAM principals (even account root — use SCPs for root)
resource "aws_s3_bucket_policy" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id

  # Depends on public access block being applied first
  depends_on = [aws_s3_bucket_public_access_block.pf_config]

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [

      # ALLOW: PF instance role can read config
      {
        Sid    = "AllowPFInstanceRead"
        Effect = "Allow"
        Principal = {
          AWS = aws_iam_role.pf_instance.arn
        }
        Action = [
          "s3:GetObject",
          "s3:GetObjectVersion",
          "s3:ListBucket"
        ]
        Resource = [
          aws_s3_bucket.pf_config.arn,
          "${aws_s3_bucket.pf_config.arn}/*"
        ]
      },

      # ALLOW: CI/CD pipeline role can write/update config
      {
        Sid    = "AllowCICDWrite"
        Effect = "Allow"
        Principal = {
          AWS = var.cicd_role_arn
        }
        Action = [
          "s3:PutObject",
          "s3:PutObjectAcl",
          "s3:DeleteObject",
          "s3:ListBucket"
        ]
        Resource = [
          aws_s3_bucket.pf_config.arn,
          "${aws_s3_bucket.pf_config.arn}/*"
        ]
      },

      # DENY: enforce HTTPS for all requests
      # Prevents accidental plain-HTTP access exposing config in transit
      {
        Sid    = "DenyNonHTTPS"
        Effect = "Deny"
        Principal = "*"
        Action    = "s3:*"
        Resource  = [
          aws_s3_bucket.pf_config.arn,
          "${aws_s3_bucket.pf_config.arn}/*"
        ]
        Condition = {
          Bool = { "aws:SecureTransport" = "false" }
        }
      }
    ]
  })
}

# ── KMS KEY for bucket encryption ─────────────────────────────────────
resource "aws_kms_key" "pf_config" {
  description             = "KMS key for PingFederate S3 config bucket"
  deletion_window_in_days = 30
  enable_key_rotation     = true   # auto-rotate every year

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      # Account root can manage the key
      {
        Sid       = "RootAccess"
        Effect    = "Allow"
        Principal = { AWS = "arn:aws:iam::${data.aws_caller_identity.current.account_id}:root" }
        Action    = "kms:*"
        Resource  = "*"
      },
      # PF instance role can decrypt (needed to read encrypted config)
      {
        Sid    = "AllowPFDecrypt"
        Effect = "Allow"
        Principal = { AWS = aws_iam_role.pf_instance.arn }
        Action    = ["kms:Decrypt", "kms:GenerateDataKey"]
        Resource  = "*"
      },
      # CI/CD role can encrypt when uploading new config
      {
        Sid    = "AllowCICDEncrypt"
        Effect = "Allow"
        Principal = { AWS = var.cicd_role_arn }
        Action    = ["kms:Encrypt", "kms:GenerateDataKey", "kms:DescribeKey"]
        Resource  = "*"
      }
    ]
  })

  tags = merge(local.common_tags, { Name = "pf-config-bucket-key" })
}

resource "aws_kms_alias" "pf_config" {
  name          = "alias/${local.name_prefix}pf-config"
  target_key_id = aws_kms_key.pf_config.key_id
}

# ── OUTPUTS ────────────────────────────────────────────────────────────
output "config_bucket_name" {
  description = "Config bucket name — referenced in Launch Template user_data"
  value       = aws_s3_bucket.pf_config.bucket
}

output "config_bucket_arn" {
  description = "Config bucket ARN — referenced in IAM policy"
  value       = aws_s3_bucket.pf_config.arn
}

output "config_kms_key_arn" {
  description = "KMS key ARN — referenced in IAM policy for kms:Decrypt"
  value       = aws_kms_key.pf_config.arn
}
Encryption strategy

SSE-S3 vs SSE-KMS — choosing the right encryption for PF config

S3 offers three server-side encryption options. The PF config bucket contains keystores, connection definitions, and potentially OAuth client secrets — it requires the strongest protection and the best audit capability. Here is the decision framework.

S3 Encryption Options Compared
OptionKey managementAuditabilityCostPF verdict
SSE-S3
aws:s3		AWS manages keys completely — no visibility or controlNo key usage in CloudTrail. You know data is encrypted but not who decrypted it.FreeInsufficient for config containing keystores. No audit trail.
SSE-KMS
aws:kms		You create and manage the CMK. IAM controls who can use it. Key rotation configurable.Every Decrypt call logged in CloudTrail with caller identity, timestamp, IP. Full audit trail.~$0.03/10k API calls + $1/month/keyRequired for PF config. Auditable key usage, access control, rotation.
SSE-KMS
bucket key		Same as SSE-KMS but a bucket-level data key reduces KMS API calls.Same as SSE-KMS but fewer CloudTrail events per object read (one per unique bucket key period).Significantly lower — fewer KMS API callsEnable for cost efficiency. bucket_key_enabled = true
DSSE-KMSDual-layer encryption — two independent KMS keysTwo audit trails, two key policies to manage2× KMS costsOverkill for standard enterprise. Use only under specific compliance requirements (FedRAMP High).
The two-door model for KMS access
KMS access requires BOTH the IAM identity policy AND the KMS key policy to allow the action. If either denies the action, the decryption fails. This is different from S3 bucket policies where either resource-based OR identity-based policy can grant access. In your PF configuration: the IAM role policy (M05) grants kms:Decrypt, AND the KMS key policy grants kms:Decrypt to that role ARN. Both must be present. This is the most common cause of "access denied on S3 GetObject" errors when KMS encryption is in use — one of the two doors is missing.
Bucket structure

What PingFederate configuration lives in S3

The bucket structure must be agreed upon between the Terraform team (who provisions the bucket), the Ansible team (who populates it), and the application team (who determines what configuration exists). Terraform does not manage the contents of the bucket — only the bucket and its properties. The configuration files are uploaded by the CI/CD pipeline and managed by the PF application team.

ShellS3 bucket key structure — PingFederate config
# Bucket: pf-prod-config-123456789012
# ─────────────────────────────────────────────────────────────────────

# Runtime configuration archive (downloaded by user_data)
config/pingfederate-prod.zip
  # Contains:
  # - pingfederate/server/default/conf/*.properties
  # - pingfederate/server/default/data/*.xml
  # - pingfederate/server/default/conf/META-INF/

# Signing and encryption keystores (highly sensitive)
keystores/signing.jks          # PF signing keystore
keystores/ssl.jks              # PF SSL/TLS keystore
keystores/encryption.jks       # PF encryption keystore

# Environment-specific property overrides
config/environment.properties  # env-specific overrides applied at boot

# Ansible inventory and variables (used during bootstrap)
ansible/inventory.ini
ansible/group_vars/pf_prod.yml

# NOT in this bucket:
# - The AMI itself (managed by infrastructure team, separate process)
# - The PingFederate binaries (baked into AMI)
# - AWS credentials (never stored — instance role provides these)
# - Database passwords (stored in SSM Parameter Store SecureString)
What NOT to store in the config bucket
The S3 bucket stores application-level configuration that must survive instance replacement. It should not store: AWS credentials (use IAM roles), database passwords or API keys (use SSM SecureString or Secrets Manager), the PF binary distribution (bake into AMI), or large binary files that change infrequently (consider EFS). The bucket is for configuration that PF needs to initialise itself — everything that makes this PF installation unique without being secret enough to warrant Secrets Manager.
Versioning and rollback

Using S3 versioning to roll back bad configurations

S3 versioning is not just a backup feature — for the immutable infrastructure model it is the configuration rollback mechanism. When a bad configuration is deployed (wrong keystore, corrupted connection definition, misconfigured OAuth client), the recovery procedure does not require rebuilding or re-configuring anything manually. It requires only restoring the S3 object to its previous version and triggering a new AMI refresh.

ShellConfig rollback using S3 versioning
# SCENARIO: Bad config deployed. PF instances failing on boot.
# RECOVERY: Restore the previous config version and re-deploy

# Step 1: List all versions of the config archive
aws s3api list-object-versions \
  --bucket pf-prod-config-123456789012 \
  --prefix config/pingfederate-prod.zip \
  --query 'Versions[*].[VersionId,LastModified,IsLatest]' \
  --output table

# Step 2: Identify the last-known-good version ID
# LAST_GOOD_VERSION_ID=abc123def456

# Step 3: Restore that version by copying it as a new current version
aws s3api copy-object \
  --copy-source pf-prod-config-123456789012/config/pingfederate-prod.zip?versionId=abc123def456 \
  --bucket pf-prod-config-123456789012 \
  --key config/pingfederate-prod.zip \
  --server-side-encryption aws:kms \
  --ssekms-key-id alias/pf-prod-pf-config

# Step 4: Trigger a new instance refresh to pick up the restored config
# Option A: Push a new Terraform apply (update a variable to force LT update)
# Option B: Trigger instance refresh directly via AWS CLI
aws autoscaling start-instance-refresh \
  --auto-scaling-group-name pf-prod-pf-engines \
  --preferences '{"MinHealthyPercentage":90,"InstanceWarmup":300}'

# Note: Terraform is not aware of direct instance_refresh calls
# The next terraform plan will not show this as a change
# because the ASG's Terraform-managed attributes haven't changed
Versioning benefit 1
Instant config rollback
Any configuration version can be restored in seconds. Copy the old version as the current version and trigger an instance refresh. New instances boot with the restored config. No rebuild, no re-configuration, no service desk tickets. MTTR drops from hours to minutes.
Versioning benefit 2
Config change audit trail
Every configuration upload creates a new version with a timestamp and the identity of who uploaded it (in the S3 access log and CloudTrail). You can reconstruct the complete history of configuration changes — what was deployed, when, and by whom. Essential for post-incident review.
When S3 isn't enough

EFS — the alternative for shared filesystem access patterns

S3 is the right choice for the PF configuration pattern because configuration is uploaded once and downloaded at instance launch. It is not a live, shared filesystem. However, some PingFederate configurations require shared filesystem access — for example, if PF is configured to write audit files to a path that multiple nodes must be able to read, or if the configuration is too large or too dynamic to manage as S3 objects.

In these cases, EFS (Elastic File System) is the alternative. EFS presents as a standard POSIX filesystem that can be mounted by multiple EC2 instances simultaneously. It survives instance replacement because it exists independently of the instance lifecycle — just like S3.

S3 vs EFS — Choosing for PingFederate
FactorS3EFS
Access patternObject-based, batch download at bootPOSIX filesystem, real-time read/write
PF config archiveIdeal — zip downloaded once at bootOverkill — adds mount complexity for static files
PF audit logsSuitable for batch upload via CloudWatch agentBetter if compliance requires real-time shared log access
PF dynamic configUnsuitable for high-frequency writesBetter for config updated frequently during runtime
CostVery low for config (MB-scale objects)Higher — priced per GB stored + throughput
EncryptionSSE-KMS, always-on, zero overheadKMS at rest + TLS in transit, slight latency overhead
Multi-AZNative — replicated across AZs automaticallyRequires multi-AZ mount targets, one per subnet
AMI refresh impactNone — new instance downloads from S3 at bootNone — EFS persists, new instance mounts the same filesystem
Decision rule for PingFederate
Use S3 for the configuration archive download pattern (startup-time config retrieval). Use EFS if and only if: (1) PF requires real-time write access to a shared filesystem path, (2) the configuration changes frequently enough that zip-and-upload is operationally impractical, or (3) compliance requires live, shared audit log files across all nodes. For the standard PF immutable deployment, S3 is sufficient and operationally simpler.

Knowledge check

Test your S3 and config externalisation understanding

QA PF instance starts but fails to download the config from S3. The error in user_data.log says "Access Denied" on a GetObject call. The S3 bucket exists and the object is there. What are the four things you would check, in order?▼
Four checks in order of likelihood:

1. Instance profile is not attached. Run aws ec2 describe-instances --query "Reservations[].Instances[].IamInstanceProfile". If null, the Launch Template is missing the IAM instance profile block or an old LT version is in use. Fix: update the LT and trigger a refresh.

2. Bucket policy denies the instance role. The bucket policy has an explicit Allow for the role ARN. If the role ARN in the bucket policy doesn't match the actual role ARN (e.g. different environment prefix), all requests are implicitly denied. Check with aws iam simulate-principal-policy against the role ARN.

3. KMS key policy doesn't grant the instance role Decrypt. The "two-door" model — both the IAM policy AND the KMS key policy must allow the action. If the KMS key policy was created before the IAM role existed, or the role ARN changed, the key policy may not include the current role ARN. Check the KMS key policy in the console or CLI.

4. The bucket is in a different region from the instance. S3 GetObject must use the correct regional endpoint. If user_data uses aws s3 cp without specifying --region, the SDK uses the instance's metadata region. If the bucket is in a different region, the request may fail or be silently redirected. Always specify --region in user_data S3 commands.
QThe lifecycle policy keeps the last 10 non-current versions. You have been deploying config updates weekly for 6 months (26 deployments). How many versions exist in S3? How much does this cost compared to no lifecycle policy?▼
With the lifecycle policy: 11 versions exist (1 current + 10 non-current). Without it: 26 versions.

Cost comparison for a 50MB config archive: Without lifecycle: 26 × 50MB = 1.3GB stored continuously. S3 Standard costs ~$0.023/GB/month = ~$0.03/month (negligible at this scale, but grows over years). With lifecycle: 11 × 50MB = 550MB = ~$0.013/month. The cost difference is minimal for a config bucket of this size. The real value of the lifecycle policy is not cost savings — it is operational clarity. An unbounded version list makes rollback archaeology difficult. Knowing you have exactly 10 rollback points simplifies operational runbooks and prevents the "which version was the last stable one?" question from becoming a hunt through dozens of entries.
QA colleague suggests removing the bucket policy and relying entirely on the IAM identity policy to control access. Why is this a bad idea for the PF config bucket?▼
Removing the bucket policy removes the explicit scope restriction and the HTTPS enforcement deny. Without the bucket policy: any IAM principal in the account with s3:GetObject permission on * can read the PF config (including keystores). The DenyNonHTTPS statement is gone — plain HTTP access is allowed. There is no resource-based audit trail of which roles are expected to access this bucket. Without an explicit Allow, S3 falls back to the IAM identity policy — which might grant broader access if misconfigured.

The bucket policy provides defence-in-depth: even if an IAM policy is misconfigured to grant broad S3 access, the bucket policy's explicit Allow list limits who can actually read this specific bucket. For a bucket containing PF keystores, defence-in-depth is not optional.
QThe team deploys a bad PF configuration on Monday morning. By 9:15 AM, all PF instances have been refreshed with the bad config and users are unable to authenticate. Walk through the complete recovery procedure using the tools you have built in Phase 2.▼
Recovery procedure (MTTR target: <15 minutes):

1. (0:00) Identify the incident: Route53 health check alarm fires. NLB target group shows all instances unhealthy. Check PF logs via CloudWatch log group /pingfederate/prod.

2. (0:02) Find the last-known-good S3 version: aws s3api list-object-versions --bucket pf-prod-config-123456789012 --prefix config/pingfederate-prod.zip. Identify the version ID before Monday's deployment (timestamp visible in version list).

3. (0:04) Restore the config: aws s3api copy-object --copy-source bucket/config/pingfederate-prod.zip?versionId=GOOD_VERSION_ID --bucket pf-prod-config-123456789012 --key config/pingfederate-prod.zip --server-side-encryption aws:kms --ssekms-key-id alias/pf-prod-pf-config

4. (0:05) Trigger immediate instance refresh: aws autoscaling start-instance-refresh --auto-scaling-group-name pf-prod-pf-engines --preferences '{"MinHealthyPercentage":50,"InstanceWarmup":300}'. Lower MinHealthyPercentage to 50% to allow faster replacement during incident.

5. (0:10–0:25) Monitor: Watch aws autoscaling describe-instance-refreshes and NLB target group health. First new instances appear healthy after ~10 minutes.

6. (0:25) Authentication restored. File incident report. Post-mortem scheduled.

Total MTTR: ~25 minutes, of which 20 are automated (instance refresh + boot sequence).

Lab 08-AAdd a cross-region replication rule

The disaster recovery team requires the PF config bucket to be replicated to a secondary region (us-west-2) for DR purposes. Add cross-region replication using the aws_s3_bucket_replication_configuration resource. Assume a destination bucket (pf-dr-config-123456789012) already exists in us-west-2.

  1. Create an IAM role (pf-s3-replication-role) with trust policy for s3.amazonaws.com
  2. Create an IAM policy that allows s3:GetObject, s3:GetObjectVersion, s3:ReplicateObject, s3:ReplicateDelete on both source and destination buckets
  3. Add the aws_s3_bucket_replication_configuration resource on the source bucket
  4. Set the rule to replicate all objects (no prefix filter), status Enabled
  5. Use StorageClass = "STANDARD_IA" in the destination — DR copies don't need hot access
✓Reveal Lab 08-A solution▼
HCLS3 cross-region replication
# IAM role for S3 replication service
resource "aws_iam_role" "s3_replication" {
  name = "pf-s3-replication-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "s3.amazonaws.com" }
      Action    = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy" "s3_replication" {
  name = "pf-s3-replication-policy"
  role = aws_iam_role.s3_replication.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = ["s3:GetObject", "s3:GetObjectVersion", "s3:GetReplicationConfiguration"]
        Resource = ["${aws_s3_bucket.pf_config.arn}/*", aws_s3_bucket.pf_config.arn]
      },
      {
        Effect   = "Allow"
        Action   = ["s3:ReplicateObject", "s3:ReplicateDelete", "s3:ReplicateTags"]
        Resource = ["arn:aws:s3:::pf-dr-config-123456789012/*"]
      }
    ]
  })
}

resource "aws_s3_bucket_replication_configuration" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id
  role   = aws_iam_role.s3_replication.arn
  depends_on = [aws_s3_bucket_versioning.pf_config]  # versioning required

  rule {
    id     = "replicate-all-to-dr"
    status = "Enabled"
    filter { prefix = "" }   # replicate all objects
    delete_marker_replication { status = "Enabled" }
    destination {
      bucket        = "arn:aws:s3:::pf-dr-config-123456789012"
      storage_class = "STANDARD_IA"   # DR — cheaper storage class

Module 08 — Key Takeaways
  • Config externalisation in S3 is the architectural decision that makes immutable compute possible. Instances are replaced; configuration is not. The bucket stores everything that makes a PF installation unique.
  • The S3 config bucket requires six separate resource blocks in Terraform: bucket, versioning, encryption, public access block, bucket policy, and lifecycle configuration. Each is independently manageable and independently plannable.
  • Use SSE-KMS, not SSE-S3, for the config bucket. KMS provides auditable key usage in CloudTrail — every Decrypt call shows who read the config, when, and from where. Enable bucket_key_enabled = true to reduce KMS API call costs.
  • The bucket policy restricts access to exactly two principals: the PF instance role (read) and the CI/CD role (write). The DenyNonHTTPS statement forces all access over HTTPS.
  • S3 versioning enables instant config rollback: restore the previous version object and trigger an instance refresh. No rebuild, no re-configuration, no manual intervention.
  • KMS access uses the "two-door" model: both the IAM identity policy AND the KMS key policy must allow the action. Access denied errors on S3 GetObject when using KMS almost always mean one of the two doors is missing.
  • Terraform provisions the bucket and its configuration — it does not manage the contents. The CI/CD pipeline uploads PF configuration files. These are separate concerns with separate owners.
  • Phase 2 is now complete. Five modules have built the complete AWS infrastructure stack: network (M04), identity (M05), compute (M06), traffic (M07), and persistence (M08). Phase 3 begins with module architecture and enterprise patterns.
