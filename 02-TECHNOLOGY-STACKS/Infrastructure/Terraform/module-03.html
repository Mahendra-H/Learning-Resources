Bridge from Module 02

You can write the infrastructure. Now learn how Terraform remembers it.

In Module 02 you learned to declare infrastructure in HCL — resources, data sources, variables, outputs, locals. You can now write an S3 bucket, an IAM role, a security group. You understand how resource references create implicit dependencies and how the AMI data source resolves to the latest approved image at plan time.

But here is the question that HCL alone cannot answer: how does Terraform know the bucket already exists the second time you run plan? How does it know which EC2 instance belongs to which resource block? How does it prevent two engineers from applying changes simultaneously? How does it know what to destroy when you decommission an environment?

All of this is answered by one file: the state file. It is the most critical piece of Terraform's architecture, the most common source of serious incidents, and the topic that most engineers underestimate until something goes wrong. Module 03 ensures you never underestimate it.

What is state

The state file — Terraform's source of truth

Every time you run terraform apply, Terraform creates or updates a JSON file called terraform.tfstate. This file records every resource that Terraform manages: its type, its ID in AWS, and the last-known values of all its attributes. This is the state file.

Without the state file, Terraform cannot function. It has no way to know whether the resources it declared already exist in AWS. It would attempt to create them again on every apply — or worse, fail silently. The state file is the bridge between your HCL declarations and the real world.

The three-way reconciliation
When you run terraform plan, Terraform performs a three-way comparison: (1) your .tf configuration — what you want to exist, (2) the state file — what Terraform last saw in AWS, and (3) the real AWS API — what currently exists. The plan output is the diff between what you want and what currently exists, informed by what Terraform last recorded. This is why plan makes live AWS API calls — it is not just comparing two text files.
The Three-Way Reconciliation at Plan Time

Here is a simplified but real excerpt from a Terraform state file for an S3 bucket. Notice what it records: the resource type, the Terraform address of the resource, the real AWS resource ID, and all the attribute values at the time of last apply.

// terraform.tfstate — simplified excerpt
{
  "version": 4,
  "terraform_version": "1.6.4",
  "resources": [
    {
      "type": "aws_s3_bucket",
      "name": "pf_config",                        // ← local name from your .tf
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "schema_version": 0,
          "attributes": {
            "bucket": "pf-config-prod-123456789012",  // ← real AWS bucket name
            "arn":    "arn:aws:s3:::pf-config-prod-123456789012",
            "region": "us-east-1",
            "versioning": [{ "enabled": true, "mfa_delete": false }],
            "tags": {
              "Environment": "prod",
              "ManagedBy":   "terraform"
            }
          }
        }
      ]
    }
  ]
}
⚠ The state file contains sensitive data
The state file stores every attribute value of every resource — including values marked sensitive = true in HCL. Database passwords, secret ARNs, private keys output from resources — all appear in the state file in plain text. This is why remote state on S3 with server-side encryption and strict bucket policies is mandatory in enterprise environments. Never commit a state file to version control.
Remote state

Moving state off your laptop and into production

By default, Terraform stores the state file locally in the directory where you run it. This works for a single developer on a single machine — and fails completely in every other scenario: teams, CI/CD pipelines, multiple environments, disaster recovery. Local state is never acceptable in production.

The solution is a remote backend. Your project uses the S3 backend — the industry standard for AWS-based Terraform deployments. The state file lives in a versioned, encrypted S3 bucket. Access is controlled by IAM policies. The file path uniquely identifies the environment and component being managed.

HCLversions.tf — S3 remote backend configuration
terraform {
  backend "s3" {
    # The bucket that stores all state files for this organisation
    # Created once, managed separately — not by this configuration
    bucket = "company-terraform-state-prod"

    # Unique key per environment + component
    # This is the "path" of the state file within the bucket
    key = "pingfederate/prod/terraform.tfstate"

    region  = "us-east-1"
    encrypt = true   # SSE-S3 encryption at rest

    # KMS key for SSE-KMS instead of SSE-S3 (stronger)
    # kms_key_id = "arn:aws:kms:us-east-1:123456789:key/abc-123"

    # DynamoDB table for state locking (covered in next section)
    dynamodb_table = "company-terraform-locks"
  }
}

# Accessing another configuration's state as a data source
# This is how the PF compute layer reads VPC outputs from the network layer
data "terraform_remote_state" "network" {
  backend = "s3"

  config = {
    bucket = "company-terraform-state-prod"
    key    = "networking/prod/terraform.tfstate"
    region = "us-east-1"
  }
}

# Reference an output from the network state
# This is how the PF configuration gets the VPC ID
resource "aws_security_group" "pf_engine" {
  vpc_id = data.terraform_remote_state.network.outputs.vpc_id
  # ...
}
Why S3 for state storage
Versioned, encrypted, auditable
S3 bucket versioning means every state file change is recorded with a timestamp. If a bad apply corrupts the state, you can restore a previous version. CloudTrail logs every access. SSE-KMS encrypts the file. IAM policies control who can read or write it. This is exactly what a sensitive JSON file containing infrastructure IDs and secrets requires.
State file key conventions
One state file per component per env
Enterprise teams use a consistent key structure: component/environment/terraform.tfstate. For example: pingfederate/prod/terraform.tfstate, networking/dev/terraform.tfstate. This avoids accidentally applying changes from one environment's state onto another — a catastrophic mistake that has happened in real incidents.
State locking

DynamoDB locking — preventing simultaneous applies

Imagine two engineers — or two CI pipeline runs — executing terraform apply at the same time against the same state file. Both read the current state. Both compute their plan. Both begin writing changes. The state file is now corrupted: it reflects the last write, which has overwritten changes from the first write. Resources exist in AWS that state doesn't know about. Resources that state thinks exist have been modified or deleted.

State locking prevents this. When any Terraform operation that modifies state begins, Terraform creates a lock record in a DynamoDB table. Any other operation that tries to acquire the lock immediately fails with an error — the caller must wait or force-unlock manually. When the operation completes, the lock is released.

DynamoDB Lock Table — what a lock record looks like
// DynamoDB lock record during an active terraform apply
{
  "LockID":   "company-terraform-state-prod/pingfederate/prod/terraform.tfstate",
  "Info": {
    "ID":        "a3f2c819-7b4e-4d2a-9f1c-3e8b204a6d7f",  // UUID of this lock
    "Operation": "OperationTypeApply",
    "Who":       "github-actions-runner@ip-10-0-1-45",     // who holds the lock
    "Version":   "1.6.4",
    "Created":   "2024-11-15T14:23:07.891Z",               // when acquired
    "Path":      "company-terraform-state-prod/pingfederate/prod/terraform.tfstate"
  }
}
ShellDealing with stuck locks
# If an apply fails mid-run, the lock may not be released automatically
# You will see this error on the next plan/apply attempt:
# Error: Error acquiring the state lock
# Lock Info: ID: a3f2c819-7b4e-4d2a-9f1c-3e8b204a6d7f
# Who: github-actions-runner@ip-10-0-1-45

# STEP 1: Verify the lock is genuinely stale (the operation has ended)
# Check GitHub Actions — is there an active run still in progress?
# Check DynamoDB directly to see the lock record

# STEP 2: Force-unlock ONLY when you are certain the operation is not running
# Use the lock ID from the error message
terraform force-unlock a3f2c819-7b4e-4d2a-9f1c-3e8b204a6d7f

# ⚠ Never force-unlock a lock held by an active operation
# Doing so while apply is running WILL corrupt the state file
The DynamoDB table setup — provisioned separately
The DynamoDB table used for locking must exist before the S3 backend can use it. It is provisioned once by the platform team using a bootstrap Terraform configuration (or manually) and is shared across all configurations that use the same backend bucket. The table requires a primary key named LockID of type String. Pay-per-request billing mode is standard — the table has very low traffic.
Drift detection

When reality diverges from state

Drift is the condition where the real infrastructure in AWS has diverged from what the Terraform state file records. It happens in four primary ways, and it is more common in enterprise environments than most teams admit.

Drift cause #1
Manual changes (ClickOps)
An engineer modifies a security group rule via the AWS console to fix an urgent production issue. The change is never committed to Terraform. The next plan detects the drift and shows the change will be reverted. The fix disappears silently on the next apply.
Drift cause #2
AWS auto-modifications
AWS modifies certain resource attributes automatically — rotating default certificates, updating AMI attributes, modifying instance metadata. Terraform detects these as drift on the next plan, even though no human made the change.
Drift cause #3
Resources deleted outside Terraform
A resource is deleted directly in AWS (via the console, CLI, or another tool) but not through terraform destroy. The state file still records it as existing. The next apply attempts to modify a resource that no longer exists, often resulting in a confusing error.
Drift cause #4 — benign
Provider version differences
A newer version of the AWS provider sometimes records additional resource attributes or normalises existing ones. An upgrade can cause a plan to show changes on resources that haven't actually changed in AWS — the provider is just representing them differently.
ShellDetecting and handling drift
# The standard plan command detects drift automatically
# by comparing state against the real AWS API
terraform plan

# If you only want to check for drift without comparing .tf changes:
terraform plan -refresh-only
# Shows only changes that AWS has made outside of Terraform
# Does NOT propose resource creation/deletion based on .tf changes

# Accept the drift — update state to match what AWS currently has
# Run this ONLY if the manual change was intentional and should persist
terraform apply -refresh-only

# Force a full state refresh on the next plan
# Terraform queries AWS for every resource before computing the diff
terraform refresh   # deprecated in favour of plan/apply -refresh-only

# If a resource was deleted outside Terraform and you want
# to remove it from state without recreating it:
terraform state rm aws_s3_bucket.pf_config
Real Incident Pattern The "emergency SG rule" problem

A common incident in enterprise environments: during a production outage, an engineer adds a security group rule directly in the AWS console to restore service. The incident is resolved. The post-mortem documents the change. But nobody updates the Terraform configuration.

Two weeks later, a routine infrastructure change is deployed. The GitHub Actions pipeline runs terraform apply. The plan shows the emergency security group rule as a change to revert — because it's not in the .tf files. Nobody notices. Apply runs. The rule is removed. Service degrades again.

The fix: any manual change made to resolve an incident must be mirrored in Terraform within 24 hours. Some teams enforce this with a policy that triggers a terraform plan -refresh-only on a schedule and pages if drift is detected.

Importing resources

Bringing existing AWS resources under Terraform management

When you join an organisation that has existing AWS infrastructure not yet managed by Terraform, or when a resource was accidentally created outside Terraform and needs to be adopted, you use terraform import. This command takes a real AWS resource and adds it to the state file — after which Terraform manages it normally.

Importing does not write HCL for you. You must write the resource block yourself first, then import the real resource into it. The state file will then contain the real attributes, and the next plan will show any differences between your HCL and what actually exists in AWS.

Shell + HCLImporting an existing S3 bucket
# SCENARIO: A config S3 bucket was created manually before Terraform existed.
# We want Terraform to manage it going forward.

# STEP 1: Write the resource block in HCL first
# (In s3.tf)
resource "aws_s3_bucket" "pf_config" {
  bucket = "pf-config-prod-123456789012"  # must match real bucket name
  tags   = local.common_tags
}

# STEP 2: Import the real bucket into the state
# Syntax: terraform import RESOURCE_ADDRESS REAL_AWS_ID
terraform import aws_s3_bucket.pf_config pf-config-prod-123456789012

# STEP 3: Run plan — it will show differences between your HCL
# and what the real bucket currently has (tags, versioning, etc.)
terraform plan

# STEP 4: Update your HCL to match the real resource, then apply
# OR: adjust the real resource to match your HCL, then apply

# --- Modern approach (Terraform 1.5+): import block in HCL ---
import {
  to = aws_s3_bucket.pf_config
  id = "pf-config-prod-123456789012"
}
# The import block is processed during plan/apply
# Terraform 1.5+ can also generate HCL from the import with:
# terraform plan -generate-config-out=generated.tf

State surgery

The state manipulation commands — with extreme care

There are scenarios where the state file must be directly manipulated: moving a resource to a different address, removing a resource from state without destroying it, renaming a resource during a refactor. These operations are collectively called state surgery. They are powerful, irreversible, and require careful execution.

The cardinal rule: always backup the state file before any state surgery. On the S3 backend, enable bucket versioning so you can restore a previous state version if something goes wrong.

ShellState surgery commands — the complete toolkit
# ── LIST — see everything Terraform currently manages ─────────────────
terraform state list
# aws_s3_bucket.pf_config
# aws_autoscaling_group.pf_engines
# module.vpc.aws_vpc.main
# ...

# ── SHOW — inspect a single resource's state attributes ───────────────
terraform state show aws_autoscaling_group.pf_engines
# Prints all recorded attributes — useful for understanding current state

# ── MV — rename or move a resource in state ──────────────────────────
# Use when you refactor HCL (rename a resource or move it into a module)
# WITHOUT moving, next plan would destroy and recreate — often catastrophic
terraform state mv aws_s3_bucket.config aws_s3_bucket.pf_config

# Moving a resource into a module
terraform state mv aws_security_group.pf_engine module.pf_compute.aws_security_group.engine

# ── RM — remove from state without destroying in AWS ─────────────────
# Use when you want Terraform to stop managing a resource
# but NOT delete it from AWS (e.g. passing ownership to another tool)
terraform state rm aws_s3_bucket.legacy_bucket

# ── PULL — download the current remote state ─────────────────────────
# Useful for inspection or manual backup
terraform state pull > backup_$(date +%Y%m%d_%H%M%S).tfstate

# ── PUSH — upload a local state file to the backend ──────────────────
# Use ONLY when restoring from backup after a known-bad apply
# ⚠ Overwrites the current remote state unconditionally
terraform state push backup_20241115_142307.tfstate

# ── TAINT (deprecated — use -replace instead) ─────────────────────────
# Mark a resource for forced recreation on next apply
terraform apply -replace=aws_instance.pf_engine_node
The moved block — the safe way to rename in HCL (Terraform 1.1+)
Instead of running terraform state mv manually, modern Terraform supports a moved block in HCL. When Terraform sees a moved block, it automatically updates the state during the next apply without requiring a separate command. This is safer, reviewable in a PR, and leaves an audit trail in version control.
HCLThe moved block — safer state renames
# When you rename a resource in HCL, add a moved block
# so Terraform updates state instead of destroy/recreate
moved {
  from = aws_s3_bucket.config
  to   = aws_s3_bucket.pf_config
}

# After the next apply, remove the moved block from HCL
# (it's a one-time migration instruction)
State & your project

What state records during an AMI refresh — and what it doesn't

This is the most project-specific insight in this entire module, and it is the one most engineers get wrong. Understanding it precisely changes how you think about the entire immutable infrastructure pattern.

Terraform tracks the ASG — not the instances
When Terraform creates an Auto Scaling Group, the state file records the ASG resource — its name, desired capacity, min/max, launch template reference, health check configuration. It does NOT record the individual EC2 instances that the ASG launches. Those instances exist in AWS, but they are not Terraform-managed resources. When an AMI refresh replaces every instance in the ASG, the Terraform state file doesn't change at all — because the ASG resource itself hasn't changed.
State Scope During an AMI Refresh

This distinction has a critical practical implication: if you run terraform state list during or after an AMI refresh, you will not see individual EC2 instances in the list — only the ASG resource. If you want to see the actual instances, you query the ASG directly via the AWS CLI: aws autoscaling describe-auto-scaling-instances. Terraform only cares about the policy and configuration it manages, not the ephemeral compute it spawned.

This is by design. The immutable infrastructure pattern works precisely because Terraform manages the durable infrastructure (the template, the policy, the load balancer, the storage) and the ASG manages the ephemeral compute. Neither tool needs to know about the internal workings of the other.

Workspaces

Terraform workspaces — what they are and when not to use them

Terraform workspaces allow you to maintain multiple state files from a single configuration directory. The default workspace is aptly named default. Creating a workspace named prod creates a separate state file at a env:/prod/ key prefix within the same backend bucket.

Workspaces sound like the obvious way to manage dev/test/prod environments. In practice, most enterprise teams avoid them for multi-environment deployments and use directory-per-environment instead. Module 09 covers this decision in depth. For now, understand what workspaces are and the primary limitation.

ShellWorkspace commands
terraform workspace list      # list all workspaces
terraform workspace new prod  # create + switch to "prod" workspace
terraform workspace select dev # switch to "dev" workspace
terraform workspace show      # print current workspace name

# In HCL, the current workspace name is available as:
terraform.workspace   # e.g. "prod", "dev", "default"

# Common pattern: use workspace name in resource names
resource "aws_s3_bucket" "pf_config" {
  bucket = "pf-config-${terraform.workspace}"
}
⚠ The workspace limitation
All workspaces share the same configuration
The fundamental problem with workspaces for environment management: all workspaces use the same .tf files. If prod needs a different instance type, different CIDR ranges, or a different module version from dev, you cannot express that cleanly in a single configuration. The code becomes cluttered with terraform.workspace == "prod" ? ... : ... conditionals. Directory-per-environment keeps configurations clean and independent. Use workspaces only for truly identical environments that differ only in variable values — for example, isolated test runs in CI.
Knowledge check

Test your state understanding

Q Two GitHub Actions pipeline runs start simultaneously — both run terraform apply against the same state backend. What happens? ▼
The second run fails immediately with a lock acquisition error. The first run to reach the DynamoDB table acquires the lock by writing a record keyed to the state file path. The second run attempts to write the same key, finds it already exists, and exits with an error message that includes the lock ID and the identity of who holds it. This is the correct behavior — no corruption occurs. The second run must either wait and retry, or be cancelled and re-triggered after the first completes. Some CI platforms support retry logic for this exact scenario.
Q An engineer runs terraform apply. It fails halfway through — some resources were created, some weren't. What is the state of the state file? ▼
The state file reflects the resources that were successfully created before the failure. Terraform updates state incrementally as each resource operation completes. If apply fails after creating the VPC and security group but before creating the ASG, state records the VPC and SG as managed resources but not the ASG. The next terraform apply picks up where it left off — it sees the VPC and SG in state (so it won't try to create them again), and attempts to create the ASG. This partial-state behavior is one of Terraform's most important reliability features. The lock is released when apply exits, regardless of success or failure.
Q An AMI refresh runs successfully. Twelve old EC2 instances were terminated and twelve new ones were launched. How many resources changed in the Terraform state file? ▼
Only one resource changed in state: the Launch Template (specifically, its latest version attribute pointing to the new AMI ID). The ASG resource's state may also show an updated launch_template version reference. But the twenty-four individual EC2 instances — twelve terminated, twelve created — do not appear in the Terraform state file at all. They are managed by the ASG, not by Terraform. This is the defining characteristic of the immutable infrastructure pattern: Terraform manages the durable infrastructure, the ASG manages the ephemeral compute, and the two concerns are cleanly separated.
Q You want to rename aws_s3_bucket.config to aws_s3_bucket.pf_config in your HCL. What happens if you just rename the block and run plan? ▼
Terraform will plan to destroy the old bucket and create a new one — which is catastrophic if this is the live config bucket. Terraform identifies resources by their address (type.name). If you rename the block, the old address disappears from the configuration and the new address appears. Terraform sees: the resource at aws_s3_bucket.config is no longer declared → plan to destroy. The resource at aws_s3_bucket.pf_config is new → plan to create. The solution is to add a moved block (Terraform 1.1+) before renaming, or to run terraform state mv aws_s3_bucket.config aws_s3_bucket.pf_config first. Always check the plan output carefully when renaming — a destroy on a production S3 bucket with versioning may be recoverable; a destroy on a production database is not.
Q What is the difference between terraform state rm and terraform destroy -target? ▼
terraform state rm removes the resource from Terraform's state file but leaves it completely intact in AWS. terraform destroy -target destroys the resource in AWS and removes it from state. Use state rm when you want Terraform to forget about a resource — perhaps you are migrating it to another configuration's management, or handing it off to another team. The resource continues to exist and serve traffic. Use destroy -target when you actually want the resource gone from AWS. In production, -target should be used with extreme caution — it bypasses the dependency graph and can leave other resources in an inconsistent state.
Q Your team notices that every Monday morning terraform plan shows unexpected changes to several security group rules — changes that match what was deployed on the previous Friday. No one is making manual changes. What is the most likely cause? ▼
The most likely cause is a scheduled CI pipeline that applies the Terraform configuration on a fixed schedule. Many teams run a weekly or daily "drift detection" pipeline that runs terraform apply -auto-approve to ensure the infrastructure matches the declared configuration. If manual changes were made on Friday evening (emergency fixes, load test tuning, etc.) that weren't committed to the Terraform codebase, the Monday morning apply reverts them. The correct fix is: all infrastructure changes must go through Terraform PRs. Emergency changes must be committed to the codebase within the same business day they are made. Some teams implement a pre-apply drift check that pages if unexpected changes are detected, requiring human approval before proceeding.

Lab 03-A Interpret a plan with drift

Review the following terraform plan output excerpt. For each change shown, identify: (1) what caused the change, (2) whether it is drift or a configuration change, and (3) whether it is safe to apply.

Plan Outputterraform plan — excerpt
# Terraform will perform the following actions:

  # aws_security_group.pf_engine will be updated in-place
  ~ resource "aws_security_group" "pf_engine" {
      # ingress block being removed
      - ingress {
          - from_port   = 8443
          - to_port     = 8443
          - protocol    = "tcp"
          - cidr_blocks = ["10.0.0.0/8"]
          - description = "temp: load test access"
        }
    }

  # aws_launch_template.pf_engine must be replaced
  -/+ resource "aws_launch_template" "pf_engine" {
      ~ image_id = "ami-0a1b2c3d4e5f" -> "ami-9z8y7x6w5v4u"
    }

  # aws_s3_bucket.pf_config will be updated in-place
  ~ resource "aws_s3_bucket" "pf_config" {
      ~ tags = {
          + "CostCenter" = "IAM-SSO-001"
        }
    }

For each of the three changes, answer: what caused it? Is it drift or a deliberate change? Is it safe to apply?

✓Reveal Lab 03-A analysis▼

Change 1 — SG ingress port 8443: This is drift. Someone added an inbound rule on port 8443 from 10.0.0.0/8 (the description says "temp: load test access") directly in the AWS console. It is not in the Terraform configuration. Terraform plans to remove it. Is it safe? Only if the load test is complete and the rule is no longer needed. If load testing is still in progress, applying this plan will break it. The team should either commit this rule to HCL (with a proper description and without the "temp" qualifier) or confirm the load test is done before applying.

Change 2 — Launch Template AMI ID: This is a deliberate configuration change. Someone updated the AMI data source or AMI ID variable to point to a new approved AMI. The -/+ symbol means the resource will be destroyed and recreated (a new Launch Template version is created; it is not updated in place). This will trigger an ASG instance refresh when applied. Is it safe? Yes — this is the intended AMI refresh workflow. Review the new AMI ID to confirm it is the correct approved image before applying.

Change 3 — S3 bucket tag addition: This is a deliberate configuration change — someone added a CostCenter tag to the bucket. The ~ symbol means an in-place update (the bucket itself is not replaced). Is it safe? Yes — adding a tag is a non-destructive change that doesn't affect bucket availability, permissions, or data.

Lab 03-B Design the state backend for a multi-environment PF deployment

You are setting up Terraform state management for a PingFederate deployment across three environments (dev, test, prod) and two components (networking, compute). Design:

  1. State file key structure — what should the S3 key be for each configuration? Write out all six keys.
  2. S3 bucket strategy — should you use one bucket for all environments or one bucket per environment? Justify your answer.
  3. DynamoDB table strategy — one table for all locking or one per environment? What is the primary key?
  4. IAM policy — what S3 and DynamoDB permissions does the GitHub Actions role need to operate the state backend?
✓Reveal Lab 03-B solution▼

1. State file keys:

# Six state file S3 keys — component/environment/terraform.tfstate
networking/dev/terraform.tfstate
networking/test/terraform.tfstate
networking/prod/terraform.tfstate
compute/dev/terraform.tfstate
compute/test/terraform.tfstate
compute/prod/terraform.tfstate

2. S3 bucket strategy: One bucket for all environments is the standard approach. Separating by bucket adds overhead (separate bucket policies, separate replication configs, etc.) with no meaningful security benefit if IAM policies are correctly scoped. Apply bucket policies that restrict: the dev IAM role can only read/write the */dev/* key prefix; the prod role can only read/write */prod/*.

3. DynamoDB strategy: One table is sufficient. The LockID includes the full state file path, so locks across environments don't conflict. Primary key: LockID, type String. Use on-demand billing mode.

4. IAM permissions for GitHub Actions: S3: GetObject, PutObject, DeleteObject, ListBucket — scoped to the state bucket ARN and relevant key prefix. DynamoDB: GetItem, PutItem, DeleteItem — scoped to the lock table ARN. For read-only operations (plan only): remove PutObject, DeleteObject, and PutItem, DeleteItem from the policy.

Module 03 — Key Takeaways
  • The state file is the bridge between HCL declarations and real AWS infrastructure. Without it, Terraform cannot function. It records resource IDs, attribute values, and metadata — including sensitive values in plain text.
  • Remote state on S3 with DynamoDB locking is mandatory for all production Terraform. Never use local state in team or CI environments.
  • Use the key pattern component/environment/terraform.tfstate to uniquely identify each state file. Mixing state files across environments causes catastrophic cross-contamination.
  • Drift is when real AWS infrastructure diverges from state. Caused by manual changes, AWS auto-modifications, or out-of-band tooling. Detected by terraform plan — which makes live API calls to compare against reality.
  • terraform import brings existing resources under Terraform management. Write the HCL block first, import second, reconcile the diff third.
  • State surgery commands (state mv, state rm, state pull) are powerful and irreversible. Always backup state before surgery. Use the moved block in HCL for resource renames in modern Terraform.
  • In the ASG model, Terraform tracks the Launch Template and ASG policy — not individual EC2 instances. An AMI refresh replaces all nodes without changing the Terraform state file (except the Launch Template's AMI reference).
  • Force-unlocking a state lock is safe only when the holding operation has definitively ended. Force-unlocking an active apply corrupts state. Verify before acting.
