Phase 3 — from building to organising

Across Phase 2 you built a complete PingFederate deployment in Terraform — VPC, IAM, compute, load balancers, DNS, and S3 persistence. You understand every resource, every attribute, and why every decision was made. You can read any part of the codebase and explain it.

Phase 3 asks a different question: how do enterprise teams organise this code so it can be safely maintained, extended, and deployed across multiple environments by multiple engineers simultaneously? The answer is the Terraform module system — the mechanism that turns one-off configurations into reusable, versionable, composable building blocks.

This module teaches you to navigate an enterprise Terraform codebase on day one, understand the module dependency tree, contribute changes safely, and reason about the Dev/Test/Prod environment strategy. It also settles the workspace vs directory debate — the most common source of confusion in enterprise Terraform adoption.

Mentor Note — this is where most engineers get stuck
Engineers who learn Terraform by writing resources quickly run into a wall when they enter a real enterprise codebase: unfamiliar directory structure, nested module calls, environment-specific variable files, and version-pinned module sources. Module fundamentals

What a Terraform module is and why it exists

Every Terraform configuration is technically a module — the root module. But in practice, "module" refers to a reusable configuration block that encapsulates a group of related resources, exposes inputs (variables) and outputs, and can be called from multiple places with different values.

The motivation is the same as in software engineering: write once, use many times, fix once. Without modules, the PF network configuration would be duplicated across Dev, Test, and Prod — three copies to maintain, three places for bugs to diverge, three sets of changes to apply when a security group rule needs updating. With a module, it's written once and called three times with different variable values.

The module contract — inputs, outputs, no side effects
A well-designed module exposes clearly named input variables, produces useful output values, and has no side effects outside its declared scope. It should be possible to call a module without knowing how it works internally — only what it requires as inputs and what it produces as outputs. This is the same principle as a well-designed function or API. The VPC module you built in M04 is a perfect candidate: it requires CIDR ranges, subnet configs, and tags as inputs; it produces VPC ID, subnet IDs, and security group IDs as outputs.
Without modules
Configuration duplication
The same VPC configuration exists in dev/, test/, and prod/ directories. A bug fix requires three PRs, three plans, three applies. Environments drift apart over time as each copy receives slightly different fixes. The prod VPC has a security group rule that dev and test don't — nobody remembers why.
With modules
One source of truth, three call sites
The VPC module is written once in modules/vpc/. Dev, test, and prod each call it with environment-specific variable values. A bug fix requires one PR to the module. All environments pick it up on next apply. The module version is pinned so prod doesn't accidentally get a breaking change.
Module anatomy

Standard module structure — the files every module must have

A Terraform module is a directory containing .tf files. The community convention (reinforced by the Terraform Registry) defines a standard set of files. Following this convention makes modules immediately navigable by any engineer who has worked with Terraform before.

modules/
└── vpc/                          # module directory — the unit of reuse
    ├── main.tf                    # primary resource definitions
    ├── variables.tf               # input variable declarations
    ├── outputs.tf                 # output value declarations
    ├── versions.tf                # required providers + version constraints
    ├── README.md                  # module documentation (required for registry)
    └── examples/                  # usage examples — runnable configurations
        └── complete/
            ├── main.tf
            └── outputs.tf

modules/
├── vpc/                          # M04 — networking
├── iam/                          # M05 — IAM roles + profiles
├── compute/                      # M06 — LT + ASG
├── loadbalancer/                 # M07 — NLB + target groups
└── s3-config/                    # M08 — config bucket
HCLmodules/vpc/variables.tf — module inputs
# Every module variable needs a description — this is the module's API documentation

variable "vpc_cidr" {
  description = "CIDR block for the VPC. Must not overlap with other VPCs in the org."
  type        = string
  # No default — caller must provide. Required inputs have no default.
}

variable "environment" {
  description = "Deployment environment. Used in resource naming and tagging."
  type        = string
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment must be dev, test, or prod."
  }
}

variable "public_subnets" {
  description = "Map of public subnets. Key = subnet name, value = {cidr, az}."
  type        = map(object({ cidr = string; az = string }))
}

variable "private_subnets" {
  description = "Map of private subnets. Key = subnet name, value = {cidr, az}."
  type        = map(object({ cidr = string; az = string }))
}

variable "common_tags" {
  description = "Tags applied to all resources in this module."
  type        = map(string)
  default     = {}   # optional — module works without tags
}

Calling modules

Module calls — source, version, and input passing

A module call is how a root configuration (or another module) uses a module. It specifies where to find the module (source), which version to use (version), and what inputs to pass. The output of a module call is accessed via module.<name>.<output_name>.

HCLenvironments/prod/main.tf — calling all modules
# ── NETWORKING ────────────────────────────────────────────────────────
module "vpc" {
  # source: where the module lives
  # Options: local path, git URL, Terraform Registry, S3 bucket
  source  = "git::https://github.com/company/terraform-modules.git//modules/vpc?ref=v2.1.0"
  # ref=v2.1.0 pins to a specific git tag — ALWAYS pin in production

  # Inputs — all required variables must be supplied
  vpc_cidr        = var.vpc_cidr          # "10.0.0.0/16" in prod.tfvars
  environment     = var.environment       # "prod"
  public_subnets  = var.public_subnets
  private_subnets = var.private_subnets
  common_tags     = local.common_tags
}

# ── IAM ───────────────────────────────────────────────────────────────
module "iam" {
  source      = "git::https://github.com/company/terraform-modules.git//modules/iam?ref=v2.1.0"
  environment = var.environment
  # Receives the config bucket ARN from the s3-config module output
  config_bucket_arn = module.s3_config.config_bucket_arn
  common_tags       = local.common_tags
}

# ── S3 CONFIG ─────────────────────────────────────────────────────────
module "s3_config" {
  source         = "git::https://github.com/company/terraform-modules.git//modules/s3-config?ref=v2.1.0"
  environment    = var.environment
  cicd_role_arn  = var.cicd_role_arn
  common_tags    = local.common_tags
}

# ── COMPUTE ───────────────────────────────────────────────────────────
module "compute" {
  source  = "git::https://github.com/company/terraform-modules.git//modules/compute?ref=v2.1.0"

  # Cross-module references — outputs from other module calls
  private_subnet_ids   = module.vpc.private_subnet_ids
  pf_engine_sg_id      = module.vpc.pf_engine_sg_id
  instance_profile_arn = module.iam.pf_instance_profile_arn
  config_bucket_name   = module.s3_config.config_bucket_name
  nlb_target_group_arn = module.loadbalancer.federation_target_group_arn

  pf_instance_type    = var.pf_instance_type
  pf_engine_desired   = var.pf_engine_desired
  pf_engine_min       = var.pf_engine_min
  pf_engine_max       = var.pf_engine_max
  environment         = var.environment
  aws_region          = var.aws_region
  common_tags         = local.common_tags
}

# ── LOAD BALANCER ─────────────────────────────────────────────────────
module "loadbalancer" {
  source             = "git::https://github.com/company/terraform-modules.git//modules/loadbalancer?ref=v2.1.0"
  vpc_id             = module.vpc.vpc_id
  public_subnet_ids  = module.vpc.public_subnet_ids
  nlb_sg_id          = module.vpc.nlb_sg_id
  hosted_zone_name   = var.hosted_zone_name
  environment        = var.environment
  common_tags        = local.common_tags
}
Always pin module versions in production
Using ref=v2.1.0 ensures that prod always gets exactly the module version that was tested. Using ref=main or omitting a version means the next terraform init might pull in breaking module changes. Enterprise teams maintain a module version upgrade process: update the ref in a dev branch, plan and apply to dev, promote to test, then prod. Never let prod see untested module versions.
Enterprise structure

Directory-per-environment — the production standard

The most important structural decision in enterprise Terraform is how to manage multiple environments. There are two main approaches: workspaces (covered in M03) and directory-per-environment. Most enterprise teams settle on directory-per-environment for production workloads. Here is why, and what the directory structure looks like.

terraform-pingfederate/
├── modules/                       # shared, versioned, reusable modules
│   ├── vpc/                       # main.tf, variables.tf, outputs.tf
│   ├── iam/
│   ├── compute/
│   ├── loadbalancer/
│   └── s3-config/
│
└── environments/                  # one directory per environment
    ├── dev/
    │   ├── main.tf                # module calls for dev
    │   ├── versions.tf            # backend: key=pingfederate/dev/terraform.tfstate
    │   ├── variables.tf           # variable declarations
    │   └── dev.tfvars             # dev-specific values
    ├── test/
    │   ├── main.tf
    │   ├── versions.tf            # backend: key=pingfederate/test/terraform.tfstate
    │   ├── variables.tf
    │   └── test.tfvars
    └── prod/
        ├── main.tf                # identical module calls to dev/test
        ├── versions.tf            # backend: key=pingfederate/prod/terraform.tfstate
        ├── variables.tf
        └── prod.tfvars            # larger instances, higher ASG counts, etc.

Environment-specific values

How Dev, Test, and Prod differ in practice

The module calls in all three environment directories look almost identical — they call the same modules with the same structure. What differs is the variable values passed to those modules. Here is a representative comparison of the tfvars files for the PingFederate deployment.

Day one in an enterprise codebase

How to navigate an unfamiliar Terraform codebase

When you open a real enterprise Terraform repository for the first time, it can look overwhelming — dozens of files, nested modules, cross-references, and environment-specific overrides. Here is the systematic approach that will orient you in any codebase within 30 minutes.

1
Find the backend configuration
Open versions.tf in the environment directory you are working in. Note the S3 bucket and state key. This tells you which environment's state this configuration manages — and prevents you from accidentally applying dev changes to prod.
2
Map the module dependency tree
Open main.tf and list every module block. Identify what outputs each module produces and what inputs each module consumes from other modules. Draw the dependency graph: VPC → IAM, VPC → Compute, S3Config → IAM, S3Config → Compute, Compute → LoadBalancer. This is the blast radius map.
3
Run terraform graph
terraform graph | dot -Tsvg > graph.svg generates a visual dependency graph of all resources. Even without Graphviz, the text output shows which resources depend on which. For a change to a specific resource, this tells you what will be affected downstream.
4
Identify the module versions in use
Note the ref= or version= values on each module source. Compare across environments. If prod uses v2.1.0 and dev uses v2.2.0, there is a version delta — anything that works in dev may not be available in prod. Never assume module parity without checking.
5
Run terraform state list
Lists every resource currently managed in this environment's state. Confirm the expected resources are present. Identify any resources in state that don't appear in the .tf files — these are candidates for state surgery or documentation issues.
6
Run terraform plan before any change
Always run plan in the target environment before making any changes. This establishes a baseline: what is the current diff between the declared configuration and the real state? If plan shows unexpected changes, investigate before proceeding. In enterprise environments, an unexpected change in plan output is a signal that someone made an out-of-band modification.
DRY patterns

Reducing duplication at the module call level

Even with the directory-per-environment approach, some duplication remains — each environment's main.tf has nearly identical module calls. Advanced teams use several patterns to reduce this duplication while keeping environment isolation intact.

Pattern 1
Shared local values
Extract repeated expressions into locals blocks. The common tags map, name prefix, and conditional expressions that appear in every module call become locals defined once. local.common_tags, local.name_prefix, local.is_prod — all defined in a locals.tf file shared across the environment directory.
Pattern 2
Terragrunt for DRY calls
Terragrunt is a thin wrapper around Terraform that generates backend configuration, manages module version inheritance, and allows DRY module call definitions. Large teams adopt Terragrunt to eliminate environment-level duplication. Awareness-level for your project — not used currently but valuable to recognise in the wild.
Pattern 3
Module composition
Create a "top-level" or "stack" module that calls all five sub-modules (vpc, iam, compute, loadbalancer, s3-config) together. Each environment calls this single stack module with different inputs. The internal sub-module calls are encapsulated inside the stack module.
HCLmodules/pf-stack/main.tf — composed stack module
# A "stack" module calls all sub-modules together
# Each environment calls this one module instead of five separate ones

module "vpc" {
  source  = "../vpc"
  vpc_cidr        = var.vpc_cidr
  environment     = var.environment
  public_subnets  = var.public_subnets
  private_subnets = var.private_subnets
  common_tags     = local.common_tags
}

module "s3_config" { source = "../s3-config"; /* ... */ }
module "iam"       { source = "../iam";       config_bucket_arn = module.s3_config.config_bucket_arn; /* ... */ }
module "compute"   { source = "../compute";   private_subnet_ids = module.vpc.private_subnet_ids; /* ... */ }
module "lb"       { source = "../loadbalancer"; vpc_id = module.vpc.vpc_id; /* ... */ }

Module versioning

Versioning strategy — semantic versioning for Terraform modules

Enterprise teams version their Terraform modules using git tags following semantic versioning (semver). This gives downstream environments stable, predictable module behaviour and a clear path for controlled upgrades.

Semver for Terraform Modules
Version typeSemverExample triggerSafe to auto-apply?
Patchv2.1.0 → v2.1.1Bug fix in health check config, tag correctionYes — no behaviour change
Minorv2.1.0 → v2.2.0New optional input variable added, new output addedYes for backward-compatible changes — run plan first
Majorv2.1.0 → v3.0.0Required variable renamed, resource type changed, output removedNo — requires explicit version upgrade with plan review
The production version update process
When a new module version is released: (1) Update the ref= in environments/dev/main.tf to the new version. (2) Run terraform init -upgrade to pull the new module. (3) Run terraform plan — review every change carefully. (4) Apply to dev. (5) Observe for 24 hours. (6) Repeat for test. (7) Repeat for prod with appropriate change window. Never skip environments. Never update module versions in prod directly.
Knowledge check

Test your enterprise patterns understanding

QA colleague updates the VPC module to rename the output private_subnet_ids to private_subnets_list and bumps the version to v3.0.0. Your compute module call references module.vpc.private_subnet_ids. What happens when you run plan after updating the VPC module version in dev?▼
The plan will fail with an error: "The object produced by this module does not have an attribute named 'private_subnet_ids'."

When a module output is renamed, all callers that reference the old output name must also be updated. This is the definition of a breaking change — hence the major version bump to v3.0.0. The correct process: (1) Update environments/dev/main.tf to use module.vpc.private_subnets_list everywhere module.vpc.private_subnet_ids appears. (2) Update the compute module call variable that passes this value through. (3) Run plan — it should now succeed. (4) Apply and verify. The major version serves as a signal to check all references before applying. This is why you never auto-apply major version upgrades.
QYou need to add a new optional input to the VPC module — an enable_nat_gateway bool with a default of true. What version bump is appropriate and why?▼
A minor version bump (v2.1.0 → v2.2.0) is appropriate. Adding an optional variable with a sensible default is backward-compatible — all existing callers that don't pass enable_nat_gateway will get the true default and behaviour is unchanged. Callers that want the new feature can opt in by passing enable_nat_gateway = false. This is the definition of a minor (non-breaking) change. A major bump would only be warranted if: the variable was required (no default), the change altered existing behaviour for callers who don't set the variable, or an existing variable was removed or renamed.
QYou are new to the project and just cloned the Terraform repository. How do you determine whether the current plan for prod will make any changes — without actually applying anything and without reading every .tf file first?▼
Navigate to environments/prod/ and run: terraform init && terraform plan -var-file=prod.tfvars.

The plan output will show exactly what Terraform intends to change — creates (+), updates (~), destroys (-), or no changes. If plan shows No changes. Your infrastructure matches the configuration., the environment is stable and no drift has occurred since the last apply. If plan shows changes, read the output carefully to understand why — is it a legitimate new configuration, or has someone made a manual change (drift)? Always run plan first when joining a team, before any other interaction with the infrastructure.
QYour compute module currently accepts nlb_target_group_arn as a direct input variable. The team wants to restructure so the compute module directly depends on the loadbalancer module output instead of receiving it as a variable. What is the problem with this approach?▼
This would create a circular dependency and violate module encapsulation principles. If the compute module calls the loadbalancer module internally, the loadbalancer module would then need the ASG's target group ARN — creating a circular reference (A depends on B depends on A). More fundamentally, modules should not call other modules from outside their scope — this violates encapsulation and makes modules harder to test in isolation. The correct pattern is: the root configuration (or stack module) calls both the compute and loadbalancer modules and passes the target group ARN output from loadbalancer as an input to compute. This maintains clean module boundaries and avoids coupling.
QThe team is debating whether to use Terraform workspaces or directory-per-environment for the PF deployment. Your architecture lead says "workspaces are simpler." How would you structure the counter-argument?▼
Workspaces are syntactically simpler but operationally riskier for production workloads.

The core problem: workspaces share the same .tf files. Any configuration change — a new variable, a modified resource, an updated module version — affects all workspaces simultaneously. If a module upgrade introduces a bug, you cannot test it in dev without it being immediately visible in prod's configuration on the next plan.

The specific PF risks: (1) A misconfigured NLB health check in the shared configuration would affect prod the moment it's committed, not just dev. (2) Different instance types (m5.large in dev, m5.2xlarge in prod) require terraform.workspace == "prod" ? ... : ... conditionals scattered through the code — this is fragile and hard to audit. (3) State isolation is partial — the same backend bucket is used, and a confused engineer running apply in the wrong workspace can modify prod.

The verdict: Workspaces are appropriate for identical, low-risk environments (e.g. parallel dev branches for feature testing). For Dev/Test/Prod with different configurations, capacities, and risk profiles, directory-per-environment is the safer choice.

Module design and navigation exercises

Lab 09-ADesign the interface for a reusable compute module

You are extracting the compute configuration (Launch Template + ASG) into a reusable module. Design the module's interface: what inputs must it declare in variables.tf and what values must it expose in outputs.tf? Do not write the internal implementation — only the interface.

  1. List all variables the compute module needs to receive as inputs. Include the type, whether it has a default, and a one-line description for each.
  2. List all outputs the compute module should expose. Think about what other modules or the CI/CD pipeline will need to consume.
  3. Identify which inputs should have defaults and what those defaults should be.
  4. Identify one input that should have a validation block and write the condition.

Module 09 — Key Takeaways
  • A module is a reusable group of resources with a defined input/output interface. The module contract: well-named inputs, useful outputs, no side effects outside the module's declared scope.
  • Standard module structure: main.tf (resources), variables.tf (inputs), outputs.tf (outputs), versions.tf (provider constraints), README.md (documentation).
  • Always pin module versions in production: ref=v2.1.0 on git sources, version = "2.1.0" on registry sources. Unpinned modules are a reliability risk.
  • Directory-per-environment is the production standard. Each environment has its own directory, its own state file (separate S3 key), and its own module version pins. This provides complete config and state isolation.
  • Workspaces are acceptable for identical low-risk environments. They are not suitable when environments differ in configuration, capacity, or module versions — which is always true for Dev/Test/Prod in enterprise.
  • The day-one navigation sequence: find backend config → map module dependencies → run terraform graph → identify module versions → run terraform state list → run terraform plan.
  • Module version upgrades follow semver: patch = safe auto-apply, minor = backward compatible, major = requires manual review of all callers. Never apply major upgrades to prod without a staged rollout through dev and test first.
  • Cross-module references (module.vpc.vpc_id) create implicit dependencies. Terraform resolves these automatically. Circular module dependencies are not allowed — design module interfaces to avoid them.
