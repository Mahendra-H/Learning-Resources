Mentor Note
HCL is intentionally simple. It has no loops that aren't built-in, no complex control flow, no classes. If you are used to TypeScript or Java, it will feel almost too straightforward. That's the point. The complexity in Terraform is not in the language — it's in the infrastructure patterns and the state model. Lean into the simplicity of HCL and spend your cognitive budget on understanding what the resources do and why.
How Terraform projects are structured

What files live in a Terraform directory

Before diving into individual block types, understand how a Terraform project is organized on disk. Terraform loads all .tf files in a directory as a single configuration — order of files doesn't matter. The separation into multiple files is purely for human readability.

Standard files
main.tf
The primary resource definitions. In practice, large projects split resources by concern — network.tf, compute.tf, iam.tf. There's no rule — just consistency.
Standard files
variables.tf
All variable declarations. The definitions of what inputs the configuration accepts — names, types, descriptions, defaults. Values come from terraform.tfvars or environment variables.
Standard files
outputs.tf
Output values the configuration exposes after apply — things like VPC IDs, ASG names, load balancer DNS names. Used by other modules or scripts to consume the results of a deployment.
Standard files
versions.tf
The terraform {} block that pins provider versions and the minimum Terraform version. Critical for reproducibility across teams and CI environments.
Standard files
terraform.tfvars
The actual variable values for a given environment. Often environment-specific: dev.tfvars, prod.tfvars. Never commit secrets here — use environment variables or a secrets manager instead.
Generated — never edit
.terraform/
Local directory created by terraform init. Contains downloaded provider plugins and module caches. Add to .gitignore — never commit this directory.
The six block types

Every HCL construct you need to know

HCL configurations are composed of blocks. There are exactly six block types you need to master. Everything else in a .tf file is an attribute inside one of these six.

provider
Provider Block
Configures the plugin that communicates with a cloud API. Specifies the region, credentials strategy, and any provider-level settings. You must have at least one provider for Terraform to do anything useful.
resource
Resource Block
Declares a single piece of managed infrastructure — a VPC, a security group, a Launch Template. The most common block type. Every resource has a type and a local name used to reference it elsewhere.
data
Data Source Block
Reads existing information from AWS without creating or managing it. The AMI lookup is a data source — it reads the latest approved AMI ID from AWS at plan time without Terraform owning that AMI.
variable
Variable Block
Declares an input parameter. Sets the type, description, default, and validation rules. Values are supplied at plan/apply time via tfvars files, environment variables, or the CLI. The interface of a configuration.
output
Output Block
Exposes a value after apply — the VPC ID, the NLB DNS name, the S3 bucket ARN. Used by other modules, CI pipelines, or scripts. Think of it as the return value of a module call.
locals
Locals Block
Computes intermediate values from variables and other expressions. Like a local variable in code — used to avoid repeating the same expression in multiple places. Not visible outside the configuration.
Provider block

Configuring the AWS provider

The provider block is always the starting point. In enterprise environments the AWS provider is almost never configured with static credentials — instead it inherits the IAM role of the execution environment: a GitHub Actions OIDC role, an EC2 instance profile, or a developer's local AWS profile.

HCLversions.tf
# Pin the minimum Terraform version and provider version
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"   # accept 5.x, reject 6.x
    }
  }

  # Remote state backend — where Terraform stores its state file
  # (covered in depth in Module 03)
  backend "s3" {
    bucket         = "company-terraform-state-prod"
    key            = "pingfederate/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "company-terraform-locks"
    encrypt        = true
  }
}

# Provider config — credentials come from the execution environment
provider "aws" {
  region = var.aws_region

  # In GitHub Actions: assumed via OIDC role, no keys in config
  # Locally: uses ~/.aws/credentials profile

  default_tags {
    tags = {
      ManagedBy   = "terraform"
      Project     = "pingfederate-migration"
      Environment = var.environment
    }
  }
}
Version Constraints — the ~> operator
~> 5.0 means "accept any version >= 5.0 and < 6.0". The tilde-arrow is the pessimistic constraint operator — it allows patch and minor updates but pins the major version. In enterprise environments, you will often see even tighter constraints like = 5.31.0 to guarantee reproducibility across all pipeline runs.
default_tags — enterprise tagging at scale
The default_tags block in the provider applies tags to every resource created by this provider configuration. This is the enterprise-standard way to ensure every AWS resource in an account has the mandatory tags (environment, owner, project, managed-by). You do not need to add them to every resource block individually.
Resource block

Resources — the core of every Terraform configuration

Every resource block follows the same pattern: resource "<type>" "<local_name>". The type is the AWS resource type. The local name is how you reference it inside the configuration. Together they form a unique address — aws_security_group.pf_engine — that other resources use to build dependency relationships.

HCLiam.tf — annotated resource example
# resource "<TYPE>" "<LOCAL_NAME>"
#   TYPE      = the AWS resource type (defined by the provider)
#   LOCAL_NAME = how you reference this resource in other blocks

resource "aws_iam_role" "pf_instance_role" {
  name = "pf-instance-role-${var.environment}"  # string interpolation

  # Trust policy — which AWS service can assume this role
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "ec2.amazonaws.com" }
      Action    = "sts:AssumeRole"
    }]
  })

  tags = local.common_tags  # reference a local value (defined below)
}

# Attach a managed policy to the role above
# Note: references pf_instance_role using the local name
resource "aws_iam_role_policy_attachment" "pf_ssm" {
  role       = aws_iam_role.pf_instance_role.name  # TYPE.LOCAL_NAME.ATTRIBUTE
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}

# Instance profile — wraps the role so EC2 can use it
resource "aws_iam_instance_profile" "pf_profile" {
  name = "pf-instance-profile-${var.environment}"
  role = aws_iam_role.pf_instance_role.name
}
🧑‍🏫
The reference pattern — critical to understand
Notice aws_iam_role.pf_instance_role.name — this is how Terraform resources reference each other. The pattern is always <resource_type>.<local_name>.<attribute>. When Terraform sees this reference, it automatically understands that the role must be created before the profile. You do not write depends_on for this — Terraform builds the dependency graph automatically from these references. This is one of its most powerful features.
Data source block

Reading from AWS without owning it

A data source is a read-only query against AWS — or any other provider — that happens at plan time. Terraform uses the result to build other resources, but does not manage the queried resource itself. It doesn't appear in state as a managed resource. If you destroy the configuration, the data source's target is unaffected.

Data sources are how your project solves the AMI ID problem. Instead of hardcoding an AMI ID — which breaks every time the infrastructure team releases a new approved image — the configuration dynamically queries for the latest approved AMI at every plan run.

HCLdata.tf — the AMI lookup pattern (critical for your project)
# data "<TYPE>" "<LOCAL_NAME>" — same naming convention as resource

data "aws_ami" "approved_pf" {
  # most_recent = true — if multiple AMIs match the filters,
  # use the one with the most recent creation date
  most_recent = true

  # owners — restrict to your company's own account
  # prevents pulling AMIs from public or unknown accounts
  owners = [var.ami_owner_account_id]

  # Filters narrow down which AMI is selected
  filter {
    name   = "name"
    values = ["company-approved-pf-*"]  # glob pattern on AMI name
  }

  filter {
    name   = "state"
    values = ["available"]  # only available (not deregistered) AMIs
  }

  filter {
    name   = "tag:ApprovalStatus"
    values = ["approved"]    # only AMIs tagged as approved by infra team
  }
}

# The selected AMI ID is then referenced in the Launch Template
resource "aws_launch_template" "pf_engine" {
  name_prefix = "pf-engine-"

  # data.TYPE.LOCAL_NAME.ATTRIBUTE — same reference pattern as resources
  image_id      = data.aws_ami.approved_pf.id
  instance_type = var.instance_type

  # ... rest of launch template config
}
Why this pattern matters for AMI refresh
When the infrastructure team publishes a new approved AMI with the tag ApprovalStatus=approved, the next time someone runs terraform plan, the data source will return the new AMI ID. The plan will show that the Launch Template will be updated with the new ID. No one needs to manually find or update an AMI ID in the code. The pattern is self-updating — the filter does the work.
Other common data sources
data "aws_vpc"
Look up an existing VPC by its ID or tags. Used when the VPC is managed in a separate Terraform configuration (e.g. a shared networking layer) and you need its ID to create subnets or security groups.
Other common data sources
data "aws_caller_identity"
Returns the AWS account ID and ARN of the IAM identity running Terraform. Used in IAM policies to construct ARNs dynamically — e.g. arn:aws:iam::${data.aws_caller_identity.current.account_id}:root.
Other common data sources
data "aws_subnets"
Looks up subnet IDs by VPC ID and tags. When you want the ASG to deploy across all private subnets in the VPC, use this data source to get the IDs — rather than hardcoding them.
Other common data sources
data "aws_ssm_parameter"
Reads a value from AWS Systems Manager Parameter Store at plan time. Used for sensitive configuration like the S3 bucket name or a shared ARN that's managed outside of this Terraform configuration.
Variable block

Variables — the inputs to your configuration

Variables are the interface of a Terraform configuration. They make it reusable across environments — the same configuration can deploy to dev, test, and prod by simply providing different variable values. Understanding how variables flow through the system is essential before you can read any real-world configuration.

HCLvariables.tf — comprehensive variable patterns
# Basic variable with type and default
variable "aws_region" {
  description = "AWS region to deploy into"
  type        = string
  default     = "us-east-1"
}

# Variable with validation — rejects invalid values before plan runs
variable "environment" {
  description = "Deployment environment"
  type        = string

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "Environment must be dev, test, or prod."
  }
}

# Sensitive variable — value redacted from plan output and logs
variable "db_password" {
  description = "PingFederate database password"
  type        = string
  sensitive   = true  # never printed in plan output
}

# Number variable
variable "pf_engine_min_capacity" {
  description = "Minimum number of PF engine nodes"
  type        = number
  default     = 2
}

# List variable — used for multi-AZ subnet IDs
variable "private_subnet_ids" {
  description = "Private subnet IDs for ASG placement"
  type        = list(string)
}

# Map variable — key-value pairs, e.g. for tags
variable "additional_tags" {
  description = "Extra tags to apply to all resources"
  type        = map(string)
  default     = {}
}

# Object variable — structured input with typed fields
variable "pf_config" {
  description = "PingFederate node configuration"
  type = object({
    instance_type = string
    disk_size_gb  = number
    enable_ssm   = bool
  })
  default = {
    instance_type = "m5.xlarge"
    disk_size_gb  = 50
    enable_ssm   = true
  }
}

Output block

Outputs — exposing values after apply

Outputs are the values a Terraform configuration makes available after a successful apply. They serve two purposes: passing values between modules (one module's output is another module's input), and surfacing information to CI/CD pipelines and operators — like the NLB DNS name or the S3 bucket ARN that Ansible needs.

HCLoutputs.tf — PingFederate deployment outputs
# Output the NLB DNS name — needed by Route53 and monitoring
output "nlb_dns_name" {
  description = "DNS name of the Network Load Balancer"
  value       = aws_lb.pf_nlb.dns_name
}

# Output the ASG name — needed by GitHub Actions to monitor refresh
output "asg_name" {
  description = "Name of the PingFederate Auto Scaling Group"
  value       = aws_autoscaling_group.pf_engines.name
}

# Output the config S3 bucket name — needed by Ansible
output "config_bucket_name" {
  description = "S3 bucket storing PingFederate configuration"
  value       = aws_s3_bucket.pf_config.bucket
}

# Sensitive output — value is hidden in plan, visible in state
output "pf_instance_role_arn" {
  description = "ARN of the PingFederate instance IAM role"
  value       = aws_iam_role.pf_instance_role.arn
  sensitive   = false   # ARNs are not secret, but flag is available
}

# --- Reading outputs from the CLI ---
# terraform output                      → show all outputs
# terraform output nlb_dns_name         → show specific output
# terraform output -json nlb_dns_name   → JSON format for scripts
Locals block

Locals — computed values inside your configuration

Local values are named expressions computed inside the configuration. They are not inputs (variables) and not outputs — they exist purely to reduce repetition and make complex expressions readable. Think of them as constants or helper values in your code.

In enterprise Terraform, locals are extensively used to build consistent tag maps, construct resource name prefixes, and compose complex string expressions that would be unreadable if repeated across dozens of resources.

HCLlocals.tf — practical local value patterns
locals {
  # Name prefix — used across every resource for consistency
  # Results in e.g. "pf-prod-" as a prefix
  name_prefix = "pf-${var.environment}-"

  # Common tags merged with any additional tags passed as a variable
  # merge() combines two maps; later keys override earlier ones
  common_tags = merge(
    {
      Environment = var.environment
      Application = "PingFederate"
      ManagedBy   = "terraform"
      Owner       = "iam-sso-team"
    },
    var.additional_tags   # overrides or adds to the base tags
  )

  # Derive the AZs from the subnet list to avoid hardcoding them
  availability_zones = distinct([
    for s in data.aws_subnets.private.ids : data.aws_subnet.details[s].availability_zone
  ])

  # Is this a production environment? Used in conditional expressions
  is_prod = var.environment == "prod"

  # AMI ID from the data source — centralise the reference
  approved_ami_id = data.aws_ami.approved_pf.id
}

# Usage: reference locals with local.NAME
resource "aws_s3_bucket" "pf_config" {
  bucket = "${local.name_prefix}config-${data.aws_caller_identity.current.account_id}"
  tags   = local.common_tags
}
Variable vs Local vs Data Source — when to use which
Use a variable when the value must come from outside the configuration — from a caller, a tfvars file, or CI.
Use a local when the value is derived inside the configuration from other values — a computed name, a merged tag map.
Use a data source when the value exists in AWS and you need to look it up — an AMI ID, a VPC ID, an account number.
Expressions & functions

The expressions you will see daily in enterprise code

HCL supports a set of built-in functions and expressions. You don't need to memorise all of them, but the following appear constantly in real-world Terraform and you will encounter them in your project on day one.

HCLCommon expressions and functions
# ── STRING INTERPOLATION ──────────────────────────────────────────────
name = "pf-${var.environment}-engine"
# → "pf-prod-engine"

# ── CONDITIONAL EXPRESSION ─────────────────────────────────────────────
# condition ? true_value : false_value
instance_type = var.environment == "prod" ? "m5.2xlarge" : "m5.xlarge"

# ── MERGE — combine two maps ────────────────────────────────────────────
tags = merge(local.common_tags, { Role = "engine" })

# ── TOSET — convert list to set (for for_each) ─────────────────────────
for_each = toset(var.availability_zones)

# ── FORMAT — printf-style string formatting ────────────────────────────
name = format("pf-%s-%03d", var.environment, count.index)
# → "pf-prod-001"

# ── JSONENCODE — serialize a value to JSON string ──────────────────────
policy = jsonencode({
  Version = "2012-10-17"
  Statement = [{ Effect = "Allow", Action = "s3:GetObject", Resource = "*" }]
})

# ── LOOKUP — safely read from a map with a default ─────────────────────
value = lookup(var.additional_tags, "CostCenter", "unknown")

# ── CONTAINS — check if a list contains a value ────────────────────────
contains(["dev", "test", "prod"], var.environment)   # → true or false

# ── LENGTH — count elements in a list ──────────────────────────────────
desired_capacity = length(var.private_subnet_ids)

# ── COALESCE — return first non-null value ─────────────────────────────
value = coalesce(var.override_ami_id, data.aws_ami.approved_pf.id)
HCLfor_each — creating multiple resources from a list
# for_each creates one resource instance per element in the set/map
# Essential for creating multiple subnets, security rules, etc.

variable "private_subnets" {
  type = map(object({
    cidr = string
    az   = string
  }))
  default = {
    "private-1a" = { cidr = "10.0.10.0/24", az = "us-east-1a" }
    "private-1b" = { cidr = "10.0.11.0/24", az = "us-east-1b" }
    "private-1c" = { cidr = "10.0.12.0/24", az = "us-east-1c" }
  }
}

resource "aws_subnet" "private" {
  for_each = var.private_subnets      # creates 3 subnet resources

  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value.cidr  # each.value = current map value
  availability_zone = each.value.az
  tags              = merge(local.common_tags, { Name = each.key })
  # each.key = "private-1a", "private-1b", "private-1c"
}

# Reference a specific subnet from the for_each:  
# aws_subnet.private["private-1a"].id
Reading strategy

How to read any .tf file you've never seen before

Senior engineers don't read Terraform files top-to-bottom. They follow a systematic approach that maps the dependency graph before understanding individual resources. Here is the exact process to use when you encounter an unfamiliar configuration.

1
Find versions.tf — understand the environment
What provider and version is used? What backend stores the state? What minimum Terraform version is required? This gives you the execution context before reading any resources.
2
Read variables.tf — understand the inputs
What does this configuration accept as inputs? What are the types and defaults? This tells you what the configuration can be parameterised with. Look for variables without defaults — those are required at runtime.
3
Read outputs.tf — understand what it produces
What values does the configuration expose after apply? This tells you what downstream systems, other modules, or operators depend on. The outputs define the contract.
4
Find the data sources — understand what it reads
What external state does this configuration depend on? Data sources are the configuration's dependencies on the external world — an AMI that must exist, a VPC that must already be provisioned, account IDs.
5
Read resource blocks — follow the references
Now read the resources. When you see module.vpc.vpc_id or aws_iam_role.pf_role.arn, follow the reference. Build a mental graph of what depends on what. The resource that has the most incoming references is usually the most critical one.
6
Check locals.tf — understand the computed values
Locals often contain the most important business logic in the configuration — the name prefix, the tag map, the conditional expressions. If something appears all over the resource files as local.something, look it up here to understand the pattern.
🧑‍🏫
The IAM parallel
This reading strategy mirrors how you would audit an unfamiliar IAM policy set. You don't start with the most complex policy statement — you start with the trust policies (who can assume what), then the permission boundaries, then the attached policies, then the individual statements. Always start with the structure before the detail. Terraform is no different.
Knowledge check

Test your HCL understanding

Q What is the difference between a resource block and a data block? If both declare an S3 bucket, what happens differently? ▼
A resource block creates and manages an S3 bucket — Terraform owns its lifecycle. A data block reads an existing S3 bucket without owning it. If you declare a resource "aws_s3_bucket" "config", Terraform creates it, tracks it in state, and will destroy it if you run terraform destroy. If you declare a data "aws_s3_bucket" "config", Terraform reads its attributes (ARN, region, etc.) at plan time but never creates, modifies, or deletes it. The bucket must already exist for the data source to succeed.
Q A variable is declared with default = "us-east-1" but the CI pipeline sets TF_VAR_aws_region=eu-west-1. What value does Terraform use? ▼
The environment variable wins: eu-west-1. The precedence order from highest to lowest is: CLI flag → auto-loaded tfvars / .auto.tfvars → named tfvars file → environment variable (TF_VAR_) → default in declaration. The default is only used if no other source provides the value. In CI/CD pipelines, TF_VAR_ environment variables are the standard way to inject environment-specific values without committing them to version control.
Q Why does the AMI data source use most_recent = true? What would happen without it if multiple AMIs matched the filters? ▼
Without most_recent = true, Terraform would throw an error if multiple AMIs match the filters. The AWS AMI data source expects to return exactly one result. If the filter matches multiple AMIs (e.g. all previous company-approved images), Terraform has no way to choose between them and fails the plan with "multiple values found". most_recent = true resolves this by selecting the AMI with the latest creation timestamp — which, by your team's convention, is the newest approved release. This is why the infrastructure team uses a consistent naming pattern with timestamps in the AMI name.
Q You see aws_iam_role_policy_attachment.pf_ssm.role = aws_iam_role.pf_instance_role.name in a Terraform file. What does this reference tell you about the dependency order? ▼
Terraform will automatically create the role before the policy attachment — you don't need to write depends_on. When Terraform sees a reference from one resource to another's attribute, it builds an implicit dependency. pf_ssm references pf_instance_role.name, so Terraform knows the role must exist before it tries to attach a policy to it. This implicit dependency graph is one of Terraform's most valuable features — it determines the correct creation order automatically from the references in your code.
Q When should you use a local value instead of repeating a variable reference? Give a real example from the PingFederate stack. ▼
Use a local when you are computing something from one or more variables that will be used in multiple places. A concrete example: your PingFederate configuration needs a consistent naming prefix — "pf-prod-" in production, "pf-dev-" in dev. Rather than writing "pf-${var.environment}-" in every resource's name attribute, define local.name_prefix = "pf-${var.environment}-" once and use local.name_prefix everywhere. If the naming convention changes, you fix it in one place. The same applies to the common tags map — define it once as a local, reference it everywhere.
Q What is the purpose of sensitive = true on a variable or output? Does it encrypt the value? ▼
sensitive = true prevents the value from appearing in plan and apply output — it does NOT encrypt it. When you mark a variable or output as sensitive, Terraform redacts its value in CLI output, showing (sensitive value) instead. This prevents accidental logging of secrets in CI pipelines. However, the value is still stored in plain text in the state file unless the state backend encrypts the file at rest (which S3 with SSE-KMS does). Sensitive flagging is about output hygiene, not encryption. For actual secret management, use AWS Secrets Manager or SSM Parameter Store with SecureString type.

locals {
  name_prefix = "pf-${var.environment}-"
  is_prod     = var.environment == "prod"
  engine_size = local.is_prod ? "m5.2xlarge" : "m5.xlarge"

resource "aws_autoscaling_group" "pf_engines" {

}

Questions: (1) What is local.name_prefix? (2) What is local.is_prod? (3) What is the full name of the ASG? (4) What would local.engine_size be if var.environment = "dev"?

✓Reveal Lab 02-A answers▼

Lab 02-B Write the S3 config bucket resource

Write a Terraform resource block for the PingFederate configuration S3 bucket. Requirements:

  1. Resource type: aws_s3_bucket, local name: pf_config
  2. Bucket name: "pf-config-${var.environment}-${data.aws_caller_identity.current.account_id}"
  3. Apply local.common_tags as the tags
  4. Add a second resource block: aws_s3_bucket_versioning named pf_config_versioning that enables versioning on the bucket above (reference the bucket ID from your first block)

Bonus: Add an aws_s3_bucket_server_side_encryption_configuration block using SSE-S3 (aws:s3) encryption. The full attribute tree for this resource can be found in the Terraform Registry docs for aws_s3_bucket_server_side_encryption_configuration.

HCLs3.tf — solution
resource "aws_s3_bucket" "pf_config" {
  bucket = "pf-config-${var.environment}-${data.aws_caller_identity.current.account_id}"
  tags   = local.common_tags
}

resource "aws_s3_bucket_versioning" "pf_config_versioning" {
  bucket = aws_s3_bucket.pf_config.id   # implicit dependency on pf_config

  versioning_configuration {
    status = "Enabled"
  }
}

# BONUS: Server-side encryption
resource "aws_s3_bucket_server_side_encryption_configuration" "pf_config_sse" {
  bucket = aws_s3_bucket.pf_config.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:s3"   # SSE-S3 (AWS-managed keys)
      # For SSE-KMS: use "aws:kms" + kms_master_key_id
    }
    bucket_key_enabled = true   # reduces KMS API calls and cost
  }
}

Module 02 — Key Takeaways
  • HCL has six block types: provider, resource, data, variable, output, locals. Master these and you can read any .tf file.
  • Resources declare infrastructure Terraform owns and manages. Data sources read existing infrastructure without owning it.
  • The dynamic AMI lookup using data "aws_ami" with filters is the pattern your project uses to always pick the latest approved AMI at plan time — no hardcoded IDs.
  • Resource references like aws_iam_role.pf_role.name create implicit dependencies. Terraform builds the execution order from these references automatically.
  • Variables are inputs (supplied externally), locals are intermediate computed values (internal), outputs are what the configuration exposes after apply.
  • Variable value precedence: CLI flag > auto tfvars > named tfvars > TF_VAR_ environment variables > default.
  • Read unknown .tf files in this order: versions → variables → outputs → data sources → resources → locals.
  • sensitive = true hides a value from plan output. It does not encrypt it. The state file still stores it in plain text unless the backend encrypts at rest.
