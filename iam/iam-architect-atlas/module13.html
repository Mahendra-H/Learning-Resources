AWS IAM, Microsoft Entra ID, and Google Cloud IAM look nothing alike on the surface — three different consoles, three different policy languages, three different mental models that vendor documentation presents as if they were invented independently. 13.1

☁️ Why Cloud Identity Is Architecturally Different

Cloud identity deserves its own treatment — not because AWS, Azure, and GCP invented fundamentally new authorization concepts, but because they operate at a scale and integration depth that on-premises IAM was never architected to match. In a traditional enterprise environment, an application makes authentication and authorization decisions perhaps thousands of times a day. In a cloud-native architecture, every single API call — to list an S3 bucket, to read a secret, to spin up a VM, to query a database — is independently mediated by an identity check, often at rates of millions of requests per hour across a moderately complex microservices deployment. Identity isn't a gate you pass through at login; it's the fabric that every resource interaction is woven through.

This has three architectural consequences that distinguish cloud IAM from what you've covered in Modules 01–12. First, identity is now infrastructure — the identity configuration that governs what a workload can access is as much a part of the system's architecture as the networking topology or the database schema, and it changes at infrastructure speed (managed via Terraform, deployed via CI/CD). Second, policy is code — every major cloud platform expresses authorization as structured JSON policy documents that are versionable, reviewable, and testable, continuing Module 08's policy-as-code thread directly into cloud-native primitives. Third, the security boundary shifted — in on-premises architecture, network segmentation (firewalls, VLANs) was often the primary control; in cloud architecture, identity and IAM policy is frequently the primary control, since cloud resources are API-addressable globally by default unless identity policy restricts access.

The Resource Hierarchy — Cloud IAM's Organizing Structure

Unlike Active Directory's relatively flat domain/OU structure (Module 02) or a single PingFederate instance fronting many SPs (Module 04), cloud platforms organize identity and authorization around a nested resource hierarchy. Policy can be set and inherited at any level in this hierarchy, cascading downward to all resources beneath it, with override and block mechanisms at each level. This is the cloud-era expression of AD's Group Policy inheritance — the vocabulary changed, the architectural pattern did not.

🔵 The Resource Hierarchy Is a Pattern You Already Know

The resource hierarchy with inherited policy is the cloud-era expression of a pattern from Module 02: AD's OU structure with Group Policy inheritance. Just as a GPO applied at a parent OU cascades down to child OUs unless explicitly blocked, an AWS Service Control Policy applied at an Organizational Unit cascades down to every account beneath it, and a GCP IAM policy applied at a Folder cascades down to every Project beneath it. The vocabulary changed. The architectural pattern — hierarchical inheritance with override and block mechanisms — did not. When you're evaluating an unfamiliar cloud policy configuration, trace it up the hierarchy first; the most consequential policies are often set levels above the resource you're looking at.

The Three Identity Populations Cloud IAM Serves Simultaneously

Unlike most on-premises IAM deployments — which were architected primarily around human employees authenticating to corporate systems — cloud IAM must simultaneously serve three distinct identity populations, each with different characteristics, different lifecycle requirements, and different security risks:

  • Workforce identity: Human employees accessing cloud consoles, management APIs, and cloud-hosted applications. These identities should federate from your existing enterprise IdP (AD, PingFederate, Entra ID) rather than existing as native cloud-platform users — covered fully in Section 13.5.
  • Workload identity: Applications, microservices, CI/CD pipelines, and Kubernetes pods that make programmatic API calls to cloud resources. These non-human identities (introduced in Module 11) need credentials without creating static secrets — covered fully in Section 13.6.
  • Cross-account and cross-organization: Partners, acquired companies, multi-cloud workloads, and third-party vendors that need scoped access across account, subscription, or organizational boundaries — extending Module 01's federated reference architecture into cloud-native trust primitives, covered in Section 13.7.

The Shared Responsibility Model — A Brief Framing

Cloud providers secure the identity platform's infrastructure — the global directory service, the token issuance infrastructure, the certificate rotation machinery underneath it. The enterprise is responsible for configuring identity correctly within it. Misconfigured IAM policies are consistently the leading cause of cloud security incidents; the platform wasn't compromised, the configuration of trust within it was. This distinction — platform security versus identity configuration security — is the architectural reason this entire module exists. Understanding the platform's model is prerequisite to configuring it safely.

🔗 Analogy — Cloud IAM Policies as Module 08 Authorization Logic

Cloud IAM policy documents are the same authorization logic as the Spring Security expressions and OPA Rego policies from Module 08 — just expressed as a cloud provider's specific JSON schema instead of a general-purpose policy language. An AWS IAM policy statement with a Condition block evaluating request tags is ABAC (Module 08, Section 8.3), written in AWS's dialect. An Entra ID Conditional Access policy evaluating device compliance is ABAC applied to authentication events. A GCP IAM Condition restricting access to business hours is time-based ABAC. Learning to read AWS, Azure, and GCP policy JSON isn't learning three new authorization concepts — it's learning three new syntaxes for concepts you already mastered in Module 08. Approach unfamiliar cloud policy syntax as a translation exercise, not a new subject.

Lab 13.1 — Trace Your Resource Hierarchy

Pick any resource your team manages in AWS, Azure, or GCP. Trace its full position in the resource hierarchy: what Organization or Tenant, what Account or Subscription or Project does it live in? Find one policy applied above the resource level (an SCP at the OU, a Management Group policy, an Org-level IAM binding) and one applied directly at the resource. Which one would "win" if they conflicted? This exercise reveals whether your team understands their own policy inheritance chain — most engineers configure resource-level policy without ever checking what's inherited from above. The most common cloud misconfigurations are caused not by incorrect resource-level policies but by misunderstanding what organizational-level guardrails are already in effect.

🟠 AWS IAM — Architecture & Policy Model

AWS Identity and Access Management is the authorization backbone for every AWS service. Every API call to every AWS resource — whether made by a human via the console, a developer via the CLI, or a microservice via an SDK — is evaluated against IAM policy before being executed. Understanding AWS IAM's architecture isn't optional for cloud architects; it's the vocabulary in which every AWS security conversation takes place.

Core IAM Entities

AWS IAM has four fundamental entity types, and understanding the architectural distinction between them is the starting point for everything else:

  • Users: Long-lived identities with persistent credentials (passwords for console access, access keys for API access). AWS's own best-practice guidance pushes strongly toward eliminating Users wherever possible — their long-lived credentials are the static secret risk Module 11 and Module 12 documented at length.
  • Groups: Collections of Users that share a permission boundary. Groups don't have credentials of their own — they're purely a permission assignment convenience, directly parallel to AD security groups from Module 02.
  • Roles: Assumable identities with no long-lived credentials. A Role is assumed by a principal (a User, a service, a federated identity) to receive temporary credentials scoped to that Role's permissions. This is the correct AWS primitive for almost everything — workloads, CI/CD pipelines, cross-account access, and federated human access all use Roles.
  • Policies: JSON documents that define what actions are allowed or denied on what resources under what conditions. Policies attach to Users, Groups, Roles, or directly to resources.

IAM Policy Anatomy — Reading Authorization as Structured JSON

Every AWS IAM policy is a collection of statements, and every statement answers the same four authorization questions from Module 08 Section 8.1: subject (implicit — who the policy is attached to), action (what can be done), resource (on what), and context (Condition block). Reading IAM policy fluently means reading it as a structured authorization declaration, not as raw configuration syntax.

Identity-Based vs Resource-Based Policies

AWS has two types of JSON policies with an important architectural distinction. Identity-based policies attach to a principal (a User, Group, or Role) and say "this principal can do X on Y." Resource-based policies attach to a resource (an S3 bucket, an SQS queue, a Lambda function) and say "these principals can do X to me." When a request is evaluated, AWS combines both: a principal must be allowed by the identity-based policy it carries AND must not be denied by the resource-based policy on the target. This dual-policy evaluation is the most common source of confusing "access denied" errors — the identity-based policy allows it, but a resource-based policy Deny on the target resource overrides it silently.

IAM Roles and the AssumeRole Pattern

The architectural heart of AWS IAM is the Role. Unlike a User, a Role has no standing credentials — it exists purely to be assumed by some other principal, which receives temporary, time-limited credentials via the AWS Security Token Service (STS). This directly expresses the Zero Standing Privilege principle from Module 10 at the infrastructure level: no workload or user ever holds long-lived credentials; credentials appear for a session and expire.

Every IAM Role has two separate policy documents, and conflating them is a critical mistake:

  • Trust policy: Defines WHO is allowed to assume this Role. This is the Role's federation configuration — it answers "what identities do I trust, and how do I verify them?" This is architecturally parallel to a SAML SP connection's trust configuration in PingFederate (Module 04) or a certificate chain trust root in Module 12.
  • Permissions policy: Defines WHAT the principal can do once the Role is assumed — the usual Allow/Deny policy statements.

Service Control Policies — Organizational Guardrails

Service Control Policies are applied at the Organization or Organizational Unit level and set the maximum possible permissions for every account beneath them in the hierarchy (Section 13.1). This is architecturally different from IAM policies: SCPs do not grant access, they cap what can be granted. An account administrator can never grant permissions that exceed the SCP ceiling, regardless of what they write in their IAM policies. SCPs are the cloud-native expression of an organizational security guardrail — the AWS equivalent of a top-level architectural constraint that no individual team can override.

Permission Boundaries — Preventing Privilege Escalation by Delegated Admins

A less commonly understood but architecturally important AWS feature: Permission Boundaries. A permission boundary is a policy attached to a User or Role that caps the maximum permissions that entity can ever be granted — even if someone with IAM admin rights tries to grant them more. This is specifically designed for delegated administration scenarios: you grant a team the ability to create and manage IAM Roles for their own workloads, but you attach a permission boundary to every Role they create, ensuring they can never create a Role that exceeds a defined scope, even accidentally. It's the IAM-level enforcement of least privilege for administrators themselves.

🟢 IAM Roles vs IAM Users — The Zero Standing Privilege Connection

The shift from IAM Users to IAM Roles is AWS's built-in enforcement of the Zero Standing Privilege principle from Module 10, applied natively to cloud API access. An IAM User has long-lived access keys that exist until someone manually rotates or deletes them — the exact static-credential risk profile Module 12 spent an entire module explaining how to eliminate. An IAM Role has no standing credentials at all; it only produces temporary, short-lived credentials at the moment something assumes it via STS. When you're reviewing an AWS architecture and see IAM Users with access keys being used instead of Roles, that's architecturally equivalent to finding a static, unrotated service account password (Module 11, Section 11.2) — the same governance gap, expressed in AWS's vocabulary. The finding is the same; only the remediation step (migrate to Role-based AssumeRole) differs.

🟣 Deep Dive — AWS IAM Policy Evaluation Logic in Full Detail

AWS evaluates IAM policy using a deterministic order that resolves conflicts predictably. Understanding the full order is essential for debugging complex "access denied" results that don't match what you'd expect from reading a single policy document:

  1. Explicit Deny check (any policy source): AWS first scans all applicable policies — SCPs, resource-based policies, identity-based policies, permission boundaries, and session policies — for any explicit Deny statement matching the request. If any Deny is found anywhere, the request is denied immediately. No Allow can override an explicit Deny. This is the most important rule in IAM evaluation.
  2. Organization SCP check: If the account is part of an AWS Organization, the SCP is evaluated. If the SCP doesn't include an Allow for the requested action (and the account is a member account, not the management account), the request is denied. SCPs work via whitelist — no explicit Allow in the SCP = denied.
  3. Resource-based policy check: If a resource-based policy exists on the target resource (S3 bucket policy, SQS resource policy, etc.) and it explicitly Allows the caller, access may be granted even without an identity-based policy Allow — this is the exception where a resource-based Allow alone can grant access for cross-account requests.
  4. IAM permission boundary check: If a permission boundary is attached to the principal, the requested action must be allowed by the boundary. Even if the identity-based policy grants it, the boundary can block it.
  5. Identity-based policy check: Finally, the principal's attached IAM policies are evaluated. If no explicit Allow is found here (and no resource-based policy grants cross-account access), the default is Deny.
  6. Default Deny: If no applicable policy explicitly Allows the request and no explicit Deny has been found, the result is implicit Deny.

The most common debugging mistake is reading only the identity-based policy attached to a Role and concluding "it should be allowed" — without checking for explicit Deny statements in an SCP above the account, a resource-based Deny on the target resource, or a permission boundary that caps the Role's effective permissions. Always evaluate all policy sources before concluding the configuration is wrong.

🏢 Use Case — Migrating 40 IAM Users to Roles

A security review finds 40 IAM Users with long-lived access keys, several over 2 years old, used by engineering teams for local development and CI/CD scripts. The migration architecture differs meaningfully between the two use cases:

Human developers (workforce identity): The correct replacement isn't a Role they manually assume — it's AWS IAM Identity Center (Section 13.5) fed by your existing Entra ID or PingFederate IdP. A developer authenticates once to their corporate IdP and receives short-lived, Role-scoped credentials for whichever AWS accounts they're permitted to access, with no AWS-native user identity ever created. Rollout sequence: enable Identity Center, configure the Entra ID SAML/OIDC connection, map existing AD groups to Permission Sets, validate access parity for a pilot group, then progressively disable the IAM Users.

CI/CD pipelines (workload identity): Replace with IAM Roles assumed via workload identity federation — IRSA if the pipeline runs in EKS (Module 11, Section 11.5), GitHub Actions OIDC federation if it's a GitHub Actions workflow (Section 13.6). The access key is deleted; the pipeline authenticates via short-lived tokens derived from the CI/CD platform's own OIDC issuer. Validate by running the pipeline end-to-end before disabling the user credential.

Lab 13.2 — IAM Role Architecture Audit

🔵 Microsoft Entra ID — Cloud-Native Identity Platform

Module 04 introduced Entra ID primarily in the context of coexistence: Entra ID as the cloud IdP that sits alongside PingFederate in a hybrid enterprise environment, taking over federation for Microsoft 365 and cloud-native apps while on-premises apps still relied on ADFS or PingFederate. This section gives Entra ID its full architectural treatment — as one of the three major cloud identity platforms this module covers, with its own complete model for tenant architecture, workforce authentication, workload identity, and authorization.

The Tenant Model — Identity Boundary vs Billing Boundary

Entra ID's fundamental organizational unit is the tenant — a dedicated, isolated instance of the Entra ID service for one organization, identified by a domain (company.onmicrosoft.com or a custom verified domain). The tenant is the identity boundary: users, groups, applications, and service principals all live within a specific tenant, and all authentication and authorization decisions for that organization happen within it.

One of the most common architectural misunderstandings, especially for engineers coming from an AWS background: an Entra ID tenant is not the same as an Azure Subscription. Subscriptions are billing and resource boundaries — they contain Azure resources (VMs, storage accounts, databases) and accumulate costs. Tenants are identity boundaries. One tenant can be associated with many subscriptions, and subscriptions can be transferred between tenants. A new engineer creating a "new Azure account" may think they're creating a new identity boundary; they're actually creating a new subscription, which is a billing boundary that still authenticates against an Entra ID tenant.

Entra ID Roles vs Azure RBAC — Two Separate Authorization Systems

Entra ID contains two authorization systems that share the same user directory but govern completely different things. Understanding this distinction prevents significant architectural confusion:

  • Entra ID Roles govern access to Entra ID and Microsoft 365 administrative functions — managing users, registering applications, configuring Conditional Access, reading audit logs. Examples: Global Administrator, User Administrator, Application Administrator, Security Reader. Scope: tenant-wide or administrative unit.
  • Azure RBAC governs access to Azure resources — VMs, storage accounts, databases, networking. Examples: Contributor, Reader, Virtual Machine Contributor, Storage Blob Data Reader. Scope: management group, subscription, resource group, or individual resource (the Section 13.1 hierarchy).

Managed Identities — Azure's Workload Identity Primitive

Azure Managed Identities are the Azure-native answer to the static credential problem for workloads. A Managed Identity is an identity automatically managed by Azure — the underlying credentials are rotated by the platform, and the application retrieves a token by calling a local Azure Instance Metadata Service endpoint rather than using any stored secret. There are two variants with meaningfully different lifecycle and governance characteristics:

User-Assigned trades that automatic cleanup for the flexibility of shared identity across multiple resources, and reintroduces the governance requirement: someone must own and review User-Assigned Managed Identities on the same cadence as the service account reviews from Module 11.

App Registrations vs Enterprise Applications

These two Entra ID constructs are frequently confused, but they have a precise architectural relationship. An App Registration is the application's identity definition — its client ID, the certificates or secrets it uses to authenticate, the API permissions it requests, and the redirect URIs it accepts. It lives in the tenant where the application is developed or owned.

An Enterprise Application (also called a Service Principal) is the tenant-specific instance that represents the application's access rights within a particular tenant. When an App Registration is consented to by a tenant administrator, an Enterprise Application is automatically created in that tenant. It's this Enterprise Application that receives role assignments, group memberships, and Conditional Access policy targeting. One App Registration can have multiple Enterprise Applications — one in each tenant that has consented to it.

🟢 Managed Identity — The Elimination of the Static Credential Problem in Azure

Managed Identity is Azure's direct answer to the static credential problem that Module 11 and Module 12 spent two full modules describing. A VM or App Service with a System-Assigned Managed Identity needs zero stored credentials to authenticate to other Azure resources — Azure itself manages the underlying credential rotation and exposes a local metadata endpoint the application calls to retrieve a token. This is conceptually identical to how an AWS IRSA-enabled pod retrieves temporary credentials (Module 11, Section 11.5) or how a Vault-authenticated application retrieves a dynamic secret (Module 12, Section 12.7). Three different vendors, three different mechanism names, the same underlying architectural principle: eliminate the static secret by federating trust to a platform-managed identity. When reviewing Azure code and seeing connection strings or API keys used to access Azure Key Vault, Azure Storage, or Azure SQL from within Azure infrastructure, the architectural finding is immediate — a Managed Identity should be used instead.

🟣 Deep Dive — Entra ID Conditional Access: End-to-End Evaluation Against Module 08's PDP/PEP Architecture

Conditional Access is Entra ID's PDP (Policy Decision Point, Module 08 Section 8.7) for authentication events. Where traditional IAM evaluated authorization at the resource level after login, Conditional Access evaluates a rich set of contextual signals during the authentication flow, making it a particularly powerful Zero Trust enforcement point:

  1. Signal collection: When a sign-in event occurs, Entra ID collects: user identity and group memberships, device state (Entra ID joined, compliant per Intune, managed), location (IP, named location, country), application being accessed, risk level (from Entra ID Identity Protection, using ML-based anomaly detection), and session characteristics.
  2. Policy matching: All Conditional Access policies with matching conditions (user/group target + application target) are evaluated. Each policy specifies Include and Exclude conditions — for example, "apply to all users, excluding the break-glass emergency accounts group."
  3. Grant control evaluation: For matched policies, the grant controls are checked — require MFA, require compliant device, require Entra ID hybrid-joined device, require approved client app, require password change. Multiple controls can be combined with AND or OR logic.
  4. Session control: Even after granting access, Conditional Access can impose session-level controls — sign-in frequency, persistent browser session restrictions, application-enforced restrictions (for apps that support the Conditional Access session control API).
  5. Decision: Block, Allow, or Allow-with-controls. The Allow-with-controls path requires the user or device to satisfy the specified controls (MFA challenge, device compliance enrollment) before access proceeds.

The PEP (Policy Enforcement Point) in this architecture is the Azure AD authentication endpoint itself — it enforces the Conditional Access decision during the OAuth 2.0/OIDC token issuance flow, before any token is issued to the application. This is earlier in the request lifecycle than most application-level authorization, making Conditional Access particularly effective as a lateral movement prevention control: a compromised credential attempting sign-in from an unexpected location or device is blocked before it can obtain a token at all.

🔴 Google Cloud IAM — Resource Hierarchy & Policy Model

GCP's IAM model shares the same resource hierarchy concept and policy-as-code philosophy as AWS and Azure, but expresses them with some structural differences that are worth understanding precisely — particularly around how Service Accounts function, why GCP's basic roles are architecturally problematic, and why GCP takes the strongest position of the three major providers against static credentials for workloads.

The GCP Resource Hierarchy — Organization to Resource

GCP's hierarchy runs: Organization → Folder → Project → Resource. The Project is GCP's primary unit of resource isolation and billing — roughly analogous to an AWS Account or Azure Subscription, but with some important identity-scoping differences. Service accounts, IAM bindings, and API enablement are all scoped to a project. An organization that deploys across 50 GCP projects has 50 separate IAM policy scopes to govern, each nested under Folders and the Organization above.

IAM policy inheritance flows downward: a binding applied at the Organization level grants that role to all resources in every Folder, Project, and resource beneath it. A binding applied at a Folder level covers all Projects in that Folder. Unlike AWS SCPs, which are separate from IAM policies and work by capping (deny by default anything not in the SCP), GCP's hierarchy works purely through additive inheritance — a binding at a higher level adds permissions, it does not restrict what can be granted below. Organization Policies (distinct from IAM policies) serve GCP's guardrail function, restricting what configurations are allowed regardless of IAM grants.

GCP's Folder is conceptually similar to an AWS Organizational Unit or an Azure Management Group — a grouping mechanism for applying consistent policy to related Projects. Unlike AWS SCPs (which deny by default), GCP's IAM inheritance is purely additive; Organization Policies handle the guardrail/restriction function separately.

GCP IAM Policy Binding Structure — Role + Member + Condition

GCP's IAM policy model organizes authorization as a set of bindings, each specifying a role, one or more members, and an optional condition. This is architecturally equivalent to AWS's policy statements and Azure's RBAC role assignments — same authorization logic (Module 08), different structural organization. Rather than attaching a JSON policy to a principal (AWS's approach), GCP attaches a binding to the resource, specifying both who (the member) and what access they get (the role) in the same record.

GCP Service Accounts — The Dual-Nature Identity

GCP Service Accounts are the platform's most architecturally distinctive primitive, because they play two roles simultaneously that AWS and Azure tend to keep more separated:

  • As a member (receiving access): A Service Account can appear in an IAM binding as a member, just like a user or group. You grant roles/storage.objectViewer to serviceAccount:payments-app@project.iam.gserviceaccount.com the same way you'd grant it to a human user.
  • As an identity (being authenticated as): A GCE VM, a GKE workload, a Cloud Run service, or a Cloud Function can be configured to run as a specific Service Account, meaning all API calls it makes are authenticated as that Service Account's identity.

Role Types — Predefined, Custom, and the Basic Role Anti-Pattern

GCP has three categories of roles, and architectural maturity in GCP IAM is largely about migrating away from the third:

  • Basic roles (Owner, Editor, Viewer): Legacy, project-wide, extremely broad grants. Owner grants nearly full control of all resources in a project. Editor grants broad modify rights across almost everything. These predate GCP's current IAM model and exist primarily for backward compatibility.
  • Predefined roles: GCP-maintained roles with fine-grained permissions scoped to specific services (e.g., roles/storage.objectViewer, roles/compute.instanceAdmin). These should be the default choice in most cases.
  • Custom roles: Organization or project-level roles with exactly the permissions you specify. Maximum least-privilege compliance, at the cost of maintenance overhead when the required permission set changes.
🔴 GCP Service Account Key Files — The Static Credential Problem, GCP Flavor

GCP Service Account key files are the platform's most direct analog to the static credential problem Modules 11 and 12 documented extensively. A downloadable JSON key file behaves exactly like a long-lived password: it doesn't expire automatically, it's reusable indefinitely until manually revoked, and a leaked file often goes undetected for a long time since it carries no built-in expiry. Google's own architectural guidance pushes strongly against Service Account key files for almost every use case in favor of Workload Identity Federation (Section 13.6). If you encounter a GCP environment with numerous downloaded Service Account key files stored as Kubernetes Secrets or CI/CD environment variables, that is architecturally equivalent to the AWS IAM User access key sprawl problem from Section 13.2 — same risk profile, same remediation pattern (replace with federated workload identity), same urgency.

🔗 Analogy — GCP Basic Roles as Cloud Domain Admin

GCP's basic roles (Owner, Editor, Viewer) are the cloud equivalent of the AD "Domain Admin for everything" anti-pattern you'd flag immediately in the on-premises context of Module 10's privileged account taxonomy. Owner grants nearly unrestricted control over an entire GCP project — the ability to delete resources, modify IAM bindings, access all data, and manage billing. Editor grants broad modify rights across almost every resource type. Just as you wouldn't accept "we made everyone a Domain Admin because it was easier to configure" as a design justification in Module 10's privileged account review, "we use basic roles because predefined roles take longer to configure" should trigger the same architectural objection in a GCP IAM review. The justification is identical; the finding is identical; only the remediation vocabulary differs.

👥 Workforce Identity Federation

Workforce identity federation in the cloud context means connecting your existing enterprise identity system — Active Directory, PingFederate, Entra ID — as the single source of truth for human employee access to cloud consoles and cloud APIs, rather than creating and managing separate user identities natively inside each cloud platform. It is the application of Module 03's SAML/OIDC federation architecture directly to the problem of cloud console access, and it's where Module 09's IGA lifecycle governance and this module's cloud IAM content converge.

Why Native Cloud User Creation Is an Anti-Pattern at Scale

When an engineer creates an AWS IAM User, a GCP project user, or a native Azure account for a colleague to access cloud resources, they recreate exactly the lifecycle governance problem that Module 09's IGA platform was built to solve for on-premises applications — just in a cloud platform that might not be connected to Saviynt at all:

  • The cloud identity has no connection to the HR-driven Joiner-Mover-Leaver lifecycle that governs the employee's AD account
  • It's invisible to Saviynt certification campaigns unless a connector has been explicitly configured and maintained
  • It requires manual deprovisioning when the employee leaves — a step that's easily forgotten when the employee's AD account is the focus of the offboarding process
  • It produces a separate credential the employee must manage, potentially resulting in credential reuse or weak passwords
  • It creates an orphaned account risk identical to Module 11's service account orphaning problem, but for human identities

AWS IAM Identity Center — Workforce Federation Architecture

AWS IAM Identity Center (formerly AWS SSO) is AWS's managed service for federating workforce identity into AWS accounts. It connects to an external IdP (Entra ID, PingFederate, Okta, or any SAML 2.0-compatible provider) and maps federated identities — specifically, the group claims in the SAML assertion — to Permission Sets that grant access to specific AWS accounts. A Permission Set is a template that defines the IAM policy attached to the temporary Role assumed when a federated user accesses an account.

For an organization with 100 AWS accounts under one AWS Organization, IAM Identity Center provides a single point of configuration: connect the IdP once, define Permission Sets once, and map AD group membership to account access across all 100 accounts from one place. Without IAM Identity Center, achieving this would require 100 separate SAML SP configurations or 100 sets of native IAM Users.

Group-Based Role Mapping — The Architecture Connecting Module 09 to Cloud Access

The mechanism that makes workforce federation work at scale is group-based role mapping: AD security groups (or Entra ID groups) are synchronized to the federation platform (PingFederate, Entra ID), their membership is carried as claims in SAML assertions or OIDC tokens (Module 03), and these group claims are mapped to Permission Sets or cloud roles at the target cloud platform. An engineer added to the "AWS-Production-ReadOnly" AD group in Saviynt's IGA provisioning workflow (Module 09) receives read access to all production AWS accounts within seconds — without any human touching an AWS console.

🟢 Where Module 09 IGA and Cloud IAM Converge — The Leaver SLA

If your organization's leaver process correctly disables an AD account within minutes (Module 09's SLA discussion) but employees also have native, separately managed AWS IAM Users, GCP users, or Azure native accounts, your actual offboarding completeness depends entirely on whether someone remembers the cloud-native account too — recreating the exact governance gap Module 09 was built to eliminate. ⚙️ Workload Identity Federation — The Full Cross-Cloud Picture

Module 11, Section 11.5 introduced workload identity federation through one detailed example — AWS IRSA for an EKS pod — and a GitHub Actions OIDC scenario. That was intentional: one well-understood reference pattern before expanding the picture. This section keeps that same diagram structure as the anchor and shows the identical architectural pattern expressed across all three major cloud platforms, plus the cross-cloud federation scenario that Module 11 didn't have room to cover. If you find this section moving quickly, that's the point — you already understand the architecture. You're learning new configuration surfaces, not new concepts.

The Universal Pattern — Restated Once, Clearly

Before looking at any vendor-specific implementation, state the pattern precisely, because recognizing it in any documentation is the skill:

  1. A workload has a short-lived token issued by its native platform's OIDC issuer — a Kubernetes cluster, GitHub Actions, another cloud provider's identity service.
  2. The workload presents that token to a cloud token exchange endpoint and requests credentials for a target role or identity.
  3. The cloud provider validates the token's cryptographic signature against the trusted issuer's published JWKS (JSON Web Key Set) — the same signature validation from Module 12's OIDC/JWKS content.
  4. The cloud provider evaluates trust conditions: does the token's subject, audience, or other claims match what has been configured as trusted for this identity or role?
  5. If valid: the cloud provider issues short-lived, scoped credentials — temporary, expiring, no static secret stored anywhere.

That five-step sequence is the universal workload identity federation pattern. It does not change across AWS, Azure, or GCP. What changes is the configuration surface: where you declare the trusted issuer, how you specify the trust conditions, and what the resulting credentials look like.

AWS: IAM Roles for Service Accounts (IRSA) — Reference Point

Covered in full in Module 11, presented briefly here as the baseline for comparison. An EKS pod is annotated with a Kubernetes Service Account that is itself annotated with an AWS IAM Role ARN. The EKS cluster's built-in OIDC issuer signs a service account token projected into the pod. When the pod calls AWS APIs, the AWS SDK automatically exchanges this token via AssumeRoleWithWebIdentity (STS) for temporary AWS credentials. The IAM Role's trust policy specifies the cluster's OIDC issuer URL and the specific service account subject as the trusted conditions — no other pod or service account in the cluster can assume this role.

Azure: Workload Identity Federation for AKS

Azure's implementation uses the same Kubernetes-projected service account token as AWS IRSA, but the trust is configured differently: rather than an IAM Role trust policy, you configure a Federated Credential on an Entra ID App Registration (Section 13.3). The Federated Credential specifies the AKS cluster's OIDC issuer URL, the Kubernetes namespace, and the service account name as trusted conditions. The Azure AD Workload Identity mutating webhook (deployed to the AKS cluster) injects the token into the pod and the Azure SDK exchanges it for an Entra ID access token. The App Registration must also have the appropriate Azure RBAC role or Entra ID API permissions for whatever resource the workload needs to access.

GCP: Workload Identity Federation — The Most General-Purpose Implementation

GCP's Workload Identity Federation is architecturally the most general of the three. Rather than being scoped to Kubernetes, GCP's implementation is designed to accept tokens from any OIDC-compliant external identity provider — Kubernetes clusters, GitHub Actions, GitLab CI, Bitbucket, and explicitly, other clouds' identity systems. Configuration is organized around two constructs:

  • Workload Identity Pool: A container for trusted external identity providers, scoped to a GCP project or organization.
  • Pool Provider: A configuration within the pool that specifies one trusted issuer (OIDC issuer URL or AWS account) and the attribute mapping from the external token's claims to GCP's own identity attributes.

A workload presents its external token to GCP's Security Token Service. GCP validates it against the configured Pool Provider and, if trust conditions are met, issues short-lived GCP credentials. Critically, GCP also supports binding these credentials to a GCP Service Account via Service Account Impersonation — the external workload effectively assumes a GCP Service Account's identity — or using the credentials directly with Workload Identity Pool-level IAM bindings.

What claims are validated for trust condition matching? How tightly is the condition scoped (per-repository, per-namespace, per-role, or broadly)? How short-lived are the resulting credentials, and is there a renewal mechanism? The same five questions apply to every implementation. When evaluating a new cloud platform or a new CI/CD integration, these questions structure the security review — not the vendor's specific terminology.

🟣 Deep Dive — How GCP Validates an AWS IAM Role Identity Without a Pre-Shared Secret

GCP's cross-cloud federation with AWS uses a different validation mechanism than the OIDC/JWKS approach used for Kubernetes and GitHub Actions, because AWS IAM Roles don't issue OIDC tokens in the same form as a Kubernetes OIDC issuer would. The mechanism is based on AWS's SigV4 request signing:

  1. The AWS workload signs a GetCallerIdentity request using its current AWS STS temporary credentials (SigV4 signing). This is a serialized HTTP request — not an actual HTTP call yet, just the signed request artifact.
  2. The workload presents this signed request artifact to GCP's Security Token Service as the "token" in the token exchange flow — specifically, it's base64-encoded and sent as the subject_token.
  3. GCP forwards the signed request to AWS's GetCallerIdentity endpoint. Because the request is SigV4-signed with the workload's actual AWS credentials, AWS validates the signature and returns the caller's identity (the IAM Role ARN and the session name).
  4. GCP receives the GetCallerIdentity response containing the verified AWS identity. It maps this against the Workload Identity Pool Provider's configured attribute conditions — for example, a CEL expression checking that the role ARN matches a specific expected ARN.
  5. If the condition matches, GCP issues OAuth 2.0 credentials scoped to whatever the Pool's IAM bindings allow for that external identity.

The elegance of this mechanism is that GCP never needs a credential shared with AWS — it outsources identity verification to AWS itself by having AWS validate its own SigV4-signed request. The trust chain flows: "I trust what AWS's GetCallerIdentity endpoint tells me about this caller" rather than "I trust a shared secret." No pre-established relationship between GCP and AWS is required beyond the GCP configuration trusting the AWS account ID. This is a different trust root than OIDC/JWKS validation, but achieves the same architectural outcome: cryptographic proof of identity from a trusted authority, with no static credential exchanged.

🏢 Use Case — Eliminating a GCP Service Account Key File from a Cross-Cloud Pipeline

Your platform team runs a data pipeline that processes data in AWS S3 and writes results to a BigQuery dataset in GCP. Currently it uses a downloaded GCP Service Account key file stored as a Kubernetes Secret in an EKS cluster — violating Module 11's container secrets guidance and this module's static-credential principle. The pipeline already uses IRSA for its AWS S3 access.

The pipeline now holds zero static credentials for either cloud, deriving both its AWS and GCP access from the same EKS IRSA role it already carries.

🔀 Cross-Account & Cross-Project Access Architecture

Almost every enterprise cloud deployment has multiple accounts, subscriptions, or projects — not one. The reasons mirror Module 01's reference architecture discussion exactly: blast radius isolation (a misconfiguration or security incident in one account doesn't automatically cascade to others), billing and cost separation, environment isolation (production, development, staging), team or business-unit autonomy, and compliance boundary enforcement (regulated workloads in dedicated accounts where controls can be independently verified). Managing identity and access across this multi-account estate is one of the most architecturally consequential decisions in cloud IAM.

AWS Cross-Account Access — AssumeRole Across Account Boundaries

The fundamental mechanism for cross-account access in AWS is the same AssumeRole pattern from Section 13.2, extended to trust principals from external accounts. An IAM Role in Account A (the target account) includes a trust policy that lists a specific principal from Account B (the source account) as trusted. When a principal from Account B calls sts:AssumeRole targeting the Role ARN in Account A, STS evaluates the trust policy — and if the source account's principal is listed, issues temporary credentials scoped to Account A's resources. The source account principal must also have permission to call sts:AssumeRole on the target Role ARN in its own identity-based policy.

This dual permission requirement — permission in the target account's trust policy AND permission in the source account's IAM policy — is intentional security design. Neither account alone can establish cross-account access; both must explicitly consent.

The External ID Pattern — Defending Against the Confused Deputy

When granting cross-account access to a third party (a SaaS vendor, a managed service provider, a monitoring tool), a specific vulnerability exists called the confused deputy problem: if the third party's AWS account hosts many customers, and they use the same Role ARN for all of them, an attacker who is also a customer of that third party could potentially provide your account's Role ARN as if it were their own, causing the third party's AWS role to assume your Role on their behalf.

The architectural defense is the External ID: a unique, unguessable string that you generate and provide to the third party. The trust policy on your IAM Role requires this exact External ID as a Condition. When the third party assumes your Role, they must supply the External ID — which only you and they know — preventing any other customer from causing the third party to access your account even if they know your Role ARN.

Azure Cross-Subscription and Cross-Tenant Access

Within a single Entra ID tenant, Azure RBAC role assignments are natively cross-subscription: a user or Managed Identity can be granted a role on Subscription A and Subscription B simultaneously, with both enforced via the same Entra ID tenant's authorization system. The Section 13.1 resource hierarchy handles this — role assignments inherit downward, and assignments at the Management Group level automatically cover all subscriptions beneath it.

Cross-tenant access — when a user in Tenant A needs to access Azure resources in Tenant B (a common M&A or MSP scenario) — uses either Entra ID B2B guest accounts (the user's Tenant A identity is invited as a guest in Tenant B, where Azure RBAC can then be assigned) or Azure Lighthouse, which enables a service provider's tenant to be delegated specific management roles over a customer's subscription without requiring the service provider to exist as guest accounts in the customer tenant. Lighthouse is the Azure-native equivalent of Module 01's federated reference architecture applied to managed services.

GCP Cross-Project Access

In GCP, granting a member (user, group, or Service Account) an IAM role on a resource in a different project is structurally simple — IAM bindings can specify any member regardless of project. A Service Account from Project A can be granted roles/bigquery.dataViewer on a dataset in Project B by adding the cross-project IAM binding. Organization Policies may restrict cross-project resource sharing (a guardrail that prevents accidental data exposure across project boundaries), so cross-project access may require Organization Policy exceptions in hardened environments.

🔴 The Confused Deputy — SAML Replay's Cousin

The confused deputy problem that AWS's External ID pattern defends against is architecturally the same class of risk as a SAML assertion replay attack from Module 03 — in both cases, a trust relationship that is correctly configured in isolation can be exploited if an identifier meant to be unique gets reused or misappropriated by an unexpected party. Just as Module 03 taught you to scrutinize SAML's InResponseTo tracking and assertion NotOnOrAfter conditions for replay protection, cross-account AWS trust policies deserve the same scrutiny: is the External ID actually unique and unguessable per customer relationship, or is it a predictable value like a company name or account number that undermines the protection it's meant to provide? A weak External ID provides the appearance of protection without the substance — the architectural equivalent of a SAML assertion with a 24-hour validity window.

📋 Multi-Cloud Identity Governance

Sections 13.2 through 13.7 have given you the architecture of identity within and across each cloud platform. This section asks the harder operational question: once you have AWS IAM, Entra ID, GCP IAM, cross-account trust relationships, workload identities, and Service Accounts all in motion simultaneously across a real enterprise estate, how do you govern that population of identities and entitlements as a single, coherent picture rather than three separate inventories owned by three separate teams using three separate review processes?

Why Multi-Cloud Governance Is Harder Than Single-Cloud Governance

The governance difficulty isn't that any one cloud's IAM is complicated in isolation — Sections 13.2–13.4 showed that each platform's model is understandable once you recognize the shared architectural patterns underneath it. The difficulty is that the combination produces a volume and variety of identity artifacts that outpaces manual governance processes almost immediately:

  • Three different policy languages (AWS JSON, Azure RBAC JSON, GCP binding structure) mean a single reviewer can't quickly read a policy from an unfamiliar platform
  • Three different resource hierarchies mean the effective permission of any given assignment requires tracing upward through different inheritance chains depending on the platform
  • Three different workload identity mechanisms (IRSA, Azure Workload Identity, GCP WIF) plus Service Accounts with downloaded key files means the non-human identity population is fragmented and poorly understood
  • And critically: different teams typically own each cloud, using different processes and different tooling, with no shared visibility into who has what access across all three

Extending Saviynt's IGA Model into Cloud IAM

Module 09 established Saviynt's architecture as the IGA platform for on-premises and SaaS application entitlements — the identity warehouse, certification campaigns, SoD detection, and role management. The architectural extension into cloud IAM uses exactly the same framework, adding three new connector targets. Modern IGA platforms including Saviynt connect to AWS, Azure, and GCP via native connectors that import cloud IAM role assignments, Permission Set memberships, Managed Identity ownership records, and Service Account bindings into the same entitlement catalog (Module 08, Section 8.8) used for on-premises application access.

The goal is a single access certification campaign that presents a reviewer with: "This engineer has access to Salesforce (via Okta provisioning, Module 09), three on-premises applications (via AD group membership), and these IAM Role assignments across four AWS accounts plus two GCP projects." All of it in one campaign, one interface, one certification outcome that feeds back to the authoritative source for each platform.

CIEM — Cloud Infrastructure Entitlement Management

Cloud Infrastructure Entitlement Management (CIEM) is a tooling category that specifically analyzes cloud IAM policies across AWS, Azure, and GCP to identify over-permissioning, unused permissions, and toxic combinations — effectively automating the SoD detection from Module 09, Section 9.7 and the least-privilege analysis from Module 01, applied continuously to the cloud IAM policy graph at a scale no manual review could match.

The core analytical capability: CIEM ingests both the granted permissions (what IAM policy allows) and the used permissions (what CloudTrail, Azure Activity Log, or GCP Cloud Audit Logs actually recorded being called). The gap between granted and used is the over-permission footprint — permissions that exist but are never exercised and therefore represent unnecessary risk. Leading CIEM tools include Ermetic (acquired by Tenable), Sonrai Security, Wiz CIEM, and native capabilities in AWS IAM Access Analyzer, Azure's Permissions Management (Microsoft Entra Permissions Management), and GCP's IAM Recommender.

Centralized Policy-as-Code for Multi-Cloud Governance

The most architecturally mature multi-cloud governance posture uses policy-as-code to enforce consistent identity guardrails across all three platforms from a single source, rather than configuring three separate sets of platform-specific guardrails that inevitably drift out of alignment. Terraform (extending Module 11's IaC-coupled lifecycle content) can provision IAM Roles, Permission Sets, and GCP IAM bindings as code — ensuring that the entitlement definition is version-controlled, reviewed in pull requests, and deployed consistently. Open Policy Agent (Module 08, Section 8.4) can enforce guardrail rules at the Terraform plan stage — blocking IAM configurations that violate least privilege, use basic roles, or create toxic combinations — before they're ever applied to the cloud environment.

⚠️ The Governance Fragmentation Anti-Pattern

Multi-cloud identity governance fails most often not because any single cloud's IAM is poorly understood, but because each cloud is governed by a different team using a different process with no shared visibility — the AWS team runs quarterly access reviews using AWS IAM Access Analyzer, the Azure team relies on ad-hoc RBAC audits in the portal, and the GCP footprint (often the newest and smallest) has no formal governance process at all. When a security team asks "who has access to what across our cloud estate," the answer comes back as three separate responses of different quality, produced on different timelines, with no way to correlate them. The architectural fix mirrors Module 09's IGA centralization principle exactly: route all three clouds' entitlement data into the same identity warehouse and the same certification cadence, so "who has access to what" is one answerable question across the entire estate — not three separate questions with three separate answers of varying quality and freshness.

Defense in Depth in Cloud Architecture

Module 01 introduced Defense in Depth as a foundational security principle: no single control should be the only thing standing between an attacker and sensitive resources. In cloud architecture, this principle applies across four distinct layers, each providing independent protection:

  • Layer 1 — Identity policy (innermost, most consistently enforced): IAM policies, Azure RBAC, GCP IAM bindings — checked on every API call, regardless of network path or source location. This is the primary boundary in cloud architecture, and the one that cannot be bypassed by network-layer attacks.
  • Layer 2 — Network segmentation: VPCs, subnets, Security Groups, Azure NSGs, GCP firewall rules — restricting which resources can communicate and from where. Network controls connect directly back to Module 06's segmentation principles, now expressed in cloud-native form. VPC Service Controls in GCP and AWS PrivateLink restrict even IAM-authorized traffic to specific network paths.
  • Layer 3 — Encryption: Data at rest (KMS-managed keys, HSM-backed where required — Module 12) and in transit (TLS, enforced via both application configuration and network policy). Encryption ensures that even if layers 1 and 2 are breached, data remains protected.
  • Layer 4 — Monitoring and detection: CloudTrail, Azure Activity Log, GCP Cloud Audit Logs feeding a SIEM — detecting anomalous identity behavior, unexpected API calls, and policy changes. This is the layer that catches what the first three layers miss, and it feeds directly into Module 14's identity threat detection content.

The Landing Zone — Cloud Architecture as Governed Infrastructure

A landing zone is a pre-architected, consistently provisioned baseline environment — account structure, identity federation, network topology, centralized logging, guardrail policies — that new workloads deploy into, rather than each team assembling their own cloud foundation independently per project. It is the cloud-native expression of Module 01's "IAM as infrastructure, not a product" framing, taken to its architectural conclusion: not just identity, but the entire cloud foundation is provisioned as governed infrastructure via IaC.

AWS calls this concept AWS Control Tower (which automates landing zone provisioning). Azure has the Microsoft Cloud Adoption Framework landing zone reference architectures. GCP has the Google Cloud Foundation Toolkit. The vendor names differ; the architectural intent is identical: provision the security foundation once, correctly, as code — then bring workloads into that governed structure rather than retrofitting governance onto ungoverned infrastructure after the fact.

When appropriate: small organizations or single-team products with low isolation requirements.
RA-2: Federated (Business-Unit Owned) Module 01 RA-2 revisited
Business units own and manage their own AWS Organizations, Azure subscriptions, or GCP projects with minimal central control. Maximum autonomy, strong blast-radius isolation. But: inconsistent security posture across units, duplicated infrastructure management effort, no unified visibility, governance fragmentation (Section 13.8's anti-pattern). When appropriate: highly autonomous business units with genuine regulatory separation requirements.
RA-3: Hybrid — Landing Zone (Most Common in Practice) Module 01 RA-3 revisited ✅ Recommended
A central platform team provisions and maintains the landing zone: account structure, identity federation, shared networking, logging, and guardrail policies. Individual teams own their own workload accounts/subscriptions/projects within that governed structure. Teams have meaningful autonomy within the bounds the guardrails define — they can deploy freely, but cannot misconfigure identity, logging, or network baselines. This is the landing zone pattern (Diagram 24). This matches Module 01's RA-3 hybrid model exactly, now expressed in cloud account architecture.
The three cloud account strategies are not new architectural choices — they are Module 01's three enterprise IAM reference architectures, revisited with cloud account/subscription/project structure as the variable instead of identity provider topology. The decision framework is the same: centralized maximizes consistency at the cost of autonomy; federated maximizes autonomy at the cost of consistency; hybrid (landing zone) balances both through governed shared infrastructure with team-level autonomy within defined guardrails.

Five architect-level questions. Attempt your own answer before revealing the guidance — the thinking matters more than the answer.

Q1 — An AWS Organization has an SCP at the OU level that blocks all EC2 actions except ec2:Describe*. A team requests an IAM policy granting ec2:TerminateInstances on a critical Role in a member account. Walk through why this grant might have no effect, and how you'd diagnose it.

Why it has no effect: SCPs set the maximum allowed permissions for all principals in a member account. Even if an account administrator grants ec2:TerminateInstances via an IAM policy, the SCP at the OU level permits only ec2:Describe* actions. The effective permission is the intersection of the SCP ceiling and the IAM grant — and since ec2:TerminateInstances is not in the SCP Allow list, it is implicitly denied by the SCP regardless of what the IAM policy says.

Diagnosis process: (1) In the IAM console's Policy Simulator or via CLI, simulate the action for the Role — note the denial reason. (2) Navigate to AWS Organizations and find the SCP attached to the OU containing this account. Read the SCP's Statement — confirm that EC2 actions are whitelisted only for Describe*. (3) Confirm the account is a member account (management account is exempt from SCPs). (4) The fix requires either modifying the SCP at the OU level (which requires Organization-level administrative access and affects all accounts in the OU) or moving the specific account to an OU with a less restrictive SCP — both of which require deliberate organizational-level governance decisions, not just account-level IAM changes.

Q2 — Compare how AWS IAM Roles, Azure Managed Identities, and GCP Service Accounts (with Workload Identity Federation) each solve the static workload credential problem. What's architecturally identical across all three, and what's genuinely different?

Architecturally identical across all three: The core principle is the same — eliminate the static credential by federating trust to a platform-managed identity. In all three cases: no credential is stored in application code or configuration; the workload authenticates to a local platform endpoint (IMDS for Azure, STS for AWS, metadata server for GCP) to receive a short-lived token; the token is used to access cloud resources; and the token expires automatically, requiring renewal. The underlying trust mechanism in all three is OIDC-based token exchange (Section 13.6's universal pattern), with cryptographic validation of the token source against published JWKS material.

Genuinely different: (1) Configuration surface: AWS trusts are configured in the IAM Role's trust policy; Azure trusts are configured as Federated Credentials on an Entra ID App Registration; GCP trusts are configured in a Workload Identity Pool Provider. (2) Lifecycle coupling: Azure System-Assigned Managed Identity ties directly to the resource lifecycle (deleted with the VM); AWS IAM Roles and GCP Service Accounts exist independently and must be explicitly cleaned up. (3) Cross-cloud generality: GCP Workload Identity Federation explicitly supports AWS IAM Roles and arbitrary OIDC issuers as trusted external identities — the broadest trust scope of the three. AWS IRSA and Azure Workload Identity are primarily K8s-and-OIDC-source focused.

Q3 — Your organization federates workforce identity into AWS via IAM Identity Center but still has 30 native IAM Users created years ago by individual teams. Explain the governance risk this creates, using Module 09's leaver SLA concept explicitly.

The governance risk: Module 09 defined the leaver SLA as the maximum time between an employee's departure and the complete revocation of all their access. When workforce identity is fully federated via IAM Identity Center, the leaver SLA is determined entirely by the Saviynt/AD offboarding process — disable the AD account, and federated AWS access is immediately revoked because there is no AWS-native credential to revoke separately.

The 30 native IAM Users break this guarantee silently. For any employee who has or had an IAM User in addition to federated access, the leaver process must include: (1) disabling their AD account (which revokes federated access) AND (2) separately disabling or deleting their IAM User and access keys in each of the 30+ accounts where they might exist. Step 2 is manual, account-by-account, and entirely outside Saviynt's automation.

The real risk: A leaver's AD account is disabled on Day 1 — their manager's manager is satisfied, the leaver SLA appears met. But if that person had an IAM User with long-lived access keys, those keys continue working indefinitely until someone discovers and deletes them. The leaver SLA is silently broken for AWS access specifically. The remediation is: inventory all IAM Users across all accounts (AWS IAM Access Analyzer or Config), map each to a person, migrate them to IAM Identity Center Permission Sets, and delete the IAM Users — eliminating the gap so the leaver SLA is actually true end-to-end.

Q4 — A GKE workload needs to access both GCP BigQuery and an AWS S3 bucket, with zero static credentials for either cloud. Design the workload identity federation architecture that achieves this.

GCP side (native, straightforward): GKE has native Workload Identity built in. Annotate the Kubernetes Service Account with a GCP Service Account. Configure the GCP Service Account to bind the required BigQuery role (roles/bigquery.dataViewer or similar). The GKE pod authenticates as the GCP Service Account via the GKE metadata server — no static credential, no key file.

AWS side (cross-cloud federation, the novel part): The GKE pod already has a GCP identity — a short-lived GCP access token for the bound Service Account. Configure an AWS IAM Role with a trust policy that trusts GCP's OIDC issuer (accounts.google.com), specifying the GCP Service Account's email as the subject condition. When the pod needs to access S3, it calls AWS STS AssumeRoleWithWebIdentity, presenting the GCP OIDC token. STS validates the token against GCP's JWKS, checks the subject matches the configured condition, and issues temporary AWS credentials scoped to S3 access. The pod now has: GCP credentials (from GKE Workload Identity, native) and AWS credentials (from GCP token → STS exchange, cross-cloud).

Architectural note: This is the cross-cloud chaining pattern from Diagram 16 in reverse (GKE→AWS instead of EKS→GCP). The universal five-step pattern (Diagram 14) is the same — the direction of the federation chain and the source identity differ, but the architecture is identical.

Q5 — Explain why GCP's basic roles (Owner/Editor/Viewer) and AWS's long-lived IAM User access keys represent the same architectural anti-pattern, despite being completely different mechanisms on completely different platforms.

The shared anti-pattern is a violation of the Principle of Least Privilege (Module 01), manifested through excessive standing access.

GCP basic roles grant sweeping, project-wide permissions (Owner = nearly everything, Editor = broad modify rights across almost all resource types) where a specific, scoped permission would suffice. The violation: the effective permission surface granted is vastly larger than what any specific workload or user actually requires. Any credential compromise, misconfiguration, or insider threat operates within that entire broad permission set.

AWS long-lived IAM User access keys grant persistent, standing access that never expires automatically. The violation: the credential persists indefinitely, giving an attacker who obtains it unlimited time to exploit it without credential rotation preventing reuse. The access continues to exist between legitimate uses — standing privilege, not just-in-time access.

The common architectural shape: both represent more access than necessary, for longer than necessary — the two-dimensional form of Least Privilege violation (scope and duration). GCP basic roles violate the scope dimension (too broad). IAM User access keys violate the duration dimension (too persistent). Both are anti-patterns for the same Module 01 principle, expressed through different mechanisms that happen to live on different platforms. The remediation pattern is also analogous in shape: replace broad basic roles with scoped predefined/custom roles (narrow the scope); replace long-lived access keys with Role-based temporary credentials (eliminate the duration).

Governance Model

A central Cloud Identity team (3–5 engineers) owns the landing zone, the Saviynt connector configuration, the CIEM tooling, and the SCP/Org Policy/Azure Policy guardrail definitions.
