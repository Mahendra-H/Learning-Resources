Authentication & Federation
Questions 1–5 · Modules M03, M04, M05, M06
Q1 ★ Critical
Is phishing-resistant MFA (FIDO2/WebAuthn/hardware security key) enforced for all administrative and privileged access — not just regular employee SSO?
→ Module 05: FIDO2 & WebAuthn Architecture
AiTM phishing proxies defeat TOTP and push MFA in real time — only FIDO2's origin-binding is structurally phishing-resistant, making unprotected administrative accounts the most critical entry point for identity-based attacks.
Q2
Are all federation trust relationships (SAML metadata, OIDC signing certificates, federation partner agreements) tracked in a central inventory with expiry alerts at 90, 60, and 30 days before expiry?
→ Module 04: PingFederate Architecture · Module 12: Certificate Lifecycle
An expired SAML metadata or signing certificate causes a total SSO outage for all applications behind that trust relationship — often with no warning until users report login failures.
Q3 ★ Critical
Is legacy authentication (NTLM, HTTP Basic Auth, IMAP/POP with password, OAuth ROPC grant) explicitly blocked by Conditional Access or equivalent policy — not just discouraged?
→ Module 03: Deprecated OAuth Grants · Module 14: Conditional Access Blind Spots
Legacy authentication protocols bypass Conditional Access policy enforcement entirely, allowing an attacker with stolen credentials to completely circumvent MFA requirements applied to modern authentication flows.
Q4
Does VPN authentication enforce the same MFA policy as web SSO — or is there a gap where a password alone grants VPN access?
→ Module 06: VPN Authentication Architecture
Enforcing FIDO2 or push MFA on web SSO while allowing password-only VPN authentication creates an architectural bypass — an attacker with credentials skips the MFA-protected SSO layer entirely and reaches internal resources directly.
Q5
Are Linux server SSH access controls governed through a centralized SSH Certificate Authority model — or do unmanaged authorized_keys files proliferate across servers?
→ Module 07: SSH Key Management & SSH CA
SSH key sprawl means former-employee keys persist on servers indefinitely, remain invisible to IGA certification, and provide persistent access that survives all other deprovisioning steps — an SSH CA with short-lived certificates solves this architecturally.
Authorization & Governance
Questions 6–10 · Modules M08, M09
Q6
Is there a current, complete entitlement catalog in the IGA platform covering all material applications — with business-readable entitlement names, not just technical IDs?
→ Module 09: Entitlement Catalog Architecture
Access certification campaigns are meaningless if reviewers see "APP_ROLE_12847" instead of "Finance Manager — Accounts Payable" — without a readable entitlement catalog, certifiers rubber-stamp approvals because they cannot evaluate what they are certifying.
Q7
Are access certifications completing on schedule with a revocation rate consistently above 2%? (A rate below 2% is a strong indicator of rubber-stamping.)
→ Module 09: Access Certification Architecture
A certification campaign with a 0.5% revocation rate is compliance theater — it produces audit evidence without meaningful access control, and the revocation rate is the most reliable signal of whether certifications represent genuine review.
Q8 ★ Critical
Is there a functioning, fully automated Mover workflow that actively REMOVES access that is no longer appropriate for a user's new role — not just ADDS new access at transfer time?
→ Module 09: Mover Workflow Architecture
Without active removal at Mover events, access accumulates permanently with each role change — a user through five role changes over ten years holds the union of every permission they ever needed, a severe over-permission state invisible to most routine reviews.
Q9
Are all material SoD rules defined AND checked at access REQUEST TIME (preventive control), not only discovered during periodic certification campaigns (detective control)?
→ Module 09: SoD Architecture — Preventive vs. Detective
SoD violations discovered in quarterly certification campaigns represent up to three months of unchecked exposure — preventive SoD checking at request time eliminates the violation before it exists, applying the same security principle as input validation at the API boundary.
Q10
Is the organization's authorization model documented — which systems use RBAC, which use ABAC, where a dedicated Policy Decision Point (PDP) exists — with PEPs confirmed to fail-closed when the PDP is unreachable?
→ Module 08: PDP/PEP Architecture · Authorization Model Selection
A PEP that fails-open when the PDP is unreachable creates a complete authorization bypass exploitable by causing a PDP outage — this failure mode is almost never tested until it occurs in production, and undocumented authorization models accumulate inconsistency silently.
Privileged & Machine Identity
Questions 11–15 · Modules M10, M11, M12
Q11 ★ Critical
Are all privileged accounts (Domain Admin, Cloud Admin, root, DBA) vaulted in PAM with JIT access enforced — no standing privileged sessions, and session recording enabled for all privileged connections?
→ Module 10: CyberArk Architecture · JIT Access
Standing privileged credentials are the highest-value target in any environment — JIT reduces the attack window from 8,760 hours per year to the actual task duration (typically 30–120 minutes), and a Domain Admin account that exists permanently is available for compromise permanently.
Q12
Is there a complete inventory of non-human identities (service accounts, API keys, Kubernetes service accounts, RPA bot accounts) with a documented human owner for every entry?
→ Module 11: Non-Human Identity Governance Framework
Unowned service accounts are the identity equivalent of orphaned user accounts — but with often-broader permissions, no behavioral monitoring, and no lifecycle trigger to decommission them when the application they serve is retired.
Q13 ★ Critical
Are service accounts using gMSA (Group Managed Service Accounts) or equivalent automated password rotation — and are there any static service account passwords older than 90 days currently in use?
→ Module 11: Service Account Governance · Module 10: CPM Credential Rotation
Kerberoasting extracts service ticket material encrypted with the service account's password and cracks it offline — a 1,000-day-old service account password is a cracking exercise, not a security control, and service accounts with stale passwords are the primary Kerberoasting target.
Q14
Are CI/CD pipelines, Kubernetes workloads, and cloud automation using workload identity federation (IRSA / Azure Workload Identity / GCP WIF) — with zero static long-lived cloud credentials stored in pipeline secrets or config files?
→ Module 11: Workload Identity Federation · Module 13: Cloud Identity
Static cloud access keys stored in CI/CD pipeline secrets or Kubernetes Secret objects are the machine-identity equivalent of hardcoded passwords in source code — a single repository with a leaked key can grant persistent cloud access to an attacker indefinitely.
Q15
Is the enterprise Root CA private key HSM-protected, and is there an active expiry alert calendar covering all internal certificates with alerts at 90, 60, and 30 days?
→ Module 12: PKI Architecture · HSM Concepts · Certificate Lifecycle
Root CA private key compromise invalidates every certificate ever issued, and software-protected Root CA keys are exposed to anyone with OS-level access to the CA server — separately, certificate expiry incidents are entirely preventable but remain among the most common self-inflicted outages in enterprise infrastructure.
Cloud Identity
Questions 16–17 · Module M13
Q16 ★ Critical
Is workforce identity fully federated into all cloud platforms (AWS, Azure, GCP) — with no active native cloud IAM Users holding long-lived static access keys used by human employees for console or API access?
→ Module 13: Workforce Identity Federation
Native cloud IAM Users with static access keys are invisible to the enterprise's IGA leaver workflow — a terminated employee's cloud access persists indefinitely if created natively in the cloud platform rather than federated from the central identity source, which is exactly the orphaned account risk at cloud scale.
Q17
Are cloud IAM entitlements (IAM roles, Azure RBAC assignments, GCP IAM bindings) included in IGA certification campaigns on the same cadence as on-premises application entitlements — or are cloud permissions outside the governance program entirely?
→ Module 13: Multi-Cloud Identity Governance · Module 09: IGA Integration
Cloud IAM entitlement sprawl grows faster than any other category of identity risk — without IGA coverage, cloud role assignments never get reviewed for continued appropriateness, and the "who has access to what" question becomes unanswerable for an increasingly large portion of the technology estate.
Identity Security Posture
Questions 18–20 · Module M14, M15
Q18 ★ Critical
Is ITDR (Identity Threat Detection and Response) deployed and actively reviewed by the SOC — with identity detection signals (AD Kerberos anomalies, privileged session behavior, OAuth consent grants) correlated with SIEM events for kill-chain visibility?
→ Module 14: ITDR Architecture
Identity attacks (Golden Ticket, DCSync, Kerberoasting) use 100% legitimate protocol messages with no malware signature to catch — without ITDR, an attacker using these techniques operates undetected until the breach surfaces externally, with average dwell time exceeding 100 days.
Q19
Is Continuous Access Evaluation (or equivalent near-real-time session revocation) enabled for all sensitive applications — ensuring that a terminated account's active sessions are revoked within minutes rather than waiting for token expiry?
→ Module 14: Continuous Access Evaluation · Module 09: Leaver SLA
Without CAE, already-issued tokens remain valid for their full lifetime even after the AD account is disabled — a terminated employee's open browser session to a sensitive application can remain active for hours after their account is technically deprovisioned.
Q20
Is IAM platform configuration (PingFederate SP connections, Saviynt SoD rules, CyberArk safe policies, Conditional Access policies) managed as version-controlled code with peer review — or changed through admin consoles with no history, no rollback, and no change review process?
→ Module 15: Configuration as Code · IAM Platform Engineering
A misconfigured SP connection, a silently changed SoD rule, or a production-only Conditional Access policy that was never tested can cause immediate, widespread access failures or undetected security regressions — console-managed IAM configuration with no version history is the infrastructure equivalent of deploying application code without source control.
