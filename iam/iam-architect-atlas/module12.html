Secrets Management & Cryptographic Identity: PKI, Certificates, HSMs & Dynamic Secrets

Every identity in this portal — human or machine — ultimately proves itself with something cryptographic. A JWT is signed with a private key (Module 03). A Kerberos ticket is encrypted with a key derived from a password (Module 02). An SSH certificate is signed by a CA (Module 07). A Kubernetes pod authenticates to AWS using a federated token validated against a JWKS endpoint (Module 11). Underneath every one of these mechanisms sits the same architectural substrate: public-key cryptography, certificate authorities, trust chains, and the infrastructure that protects the private keys those chains depend on. This module makes that substrate explicit. You've seen pieces of it throughout this portal — this is where the pieces become one coherent picture, and where you'll learn the platforms (HashiCorp Vault, CyberArk Conjur) that manage this cryptographic material at enterprise scale. 🌍

12.1

🗝️ Why Secrets Management Is Its Own Discipline

In the architectural sense, a secret is any piece of data whose confidentiality is the basis of a security guarantee. Passwords are secrets. API keys are secrets. Private keys are secrets. Certificates are technically public, but the private key bound to them is a secret. Database connection strings, symmetric encryption keys, and bearer tokens are all secrets. What unifies the category isn't the data format — it's the fact that if the value leaks, the security guarantee built on top of it collapses immediately and silently, often with no obvious signal that anything has gone wrong.

It's worth being precise about why secrets management is a distinct discipline from the two adjacent disciplines this portal has already covered in depth. PAM (Module 10) governs human and service account access to systems through workflow, approval, and session control — it answers "who is allowed to use this credential, and under what process." IGA (Module 09) governs entitlement lifecycle and periodic certification — it answers "should this identity still have this access." Secrets management answers a third, more fundamental question: where does the actual cryptographic material live, how is it delivered to the application or service that needs it, and how does it get rotated without anyone needing to touch it by hand. PAM and IGA both assume a credential already exists somewhere and govern its use; secrets management is the runtime infrastructure that makes sure that assumption holds safely.

This is also a useful moment to revisit the secrets sprawl problem from Module 11 with a sharper lens. Every non-human identity category covered there — service accounts, API keys, container workloads, RPA bots, devices — ultimately reduces to a secret somewhere: a password, a private key, or a certificate. Module 11 named the sprawl problem at the identity level ("too many machine identities, poorly governed"). This module names it at the cryptographic level: every one of those identities is backed by something that needs to be stored, delivered, and rotated safely, and the platforms in this module are how that actually happens at scale.

The hardcoded secret anti-pattern

Before covering the platforms that solve this properly, it's worth naming the failure mode they exist to eliminate. Secrets end up hardcoded in source code, baked into configuration files, stuffed into environment variables, stored as CI/CD pipeline variables, or embedded directly in container images — and each of these locations represents a governance and security failure waiting to surface. Source code commits a secret to permanent history, recoverable from git log long after anyone "removes" it. Configuration files get copied between environments and backed up indefinitely. Environment variables in a CI/CD pipeline are visible to anyone who can read the pipeline definition or, in many platforms, anyone who can trigger a build and dump the environment. Container images bake credentials into a layer that's trivially extractable by anyone who can pull the image. None of these locations support rotation, fine-grained access control, or a usable audit trail — they're convenient exactly because they skip the controls that make a credential safe to use at scale.

Three categories this module is organized around

To keep nine sections of material navigable, this module organizes the entire secrets management landscape into three categories, and the rest of the module is structured around them in order:

  1. Asymmetric key material and certificates (Sections 12.2–12.6) — the PKI substrate behind TLS, mTLS, code signing, device identity, and SSH certificates.
  2. Dynamic and ephemeral secrets (Sections 12.7–12.8) — database credentials, cloud credentials, and API tokens generated on demand and designed to be short-lived from the start.
  3. Static secrets that must still exist — encryption keys for data at rest, legacy system passwords that can't yet be eliminated — minimized wherever possible, and vaulted properly wherever they can't be.

12.2

🏛️ PKI Architecture — Certificate Authorities & Trust Chains

Public Key Infrastructure (PKI) is the complete system of policies, roles, hardware, and software needed to create, manage, distribute, use, store, and revoke digital certificates. It's a big definition because PKI is genuinely a full system — not a single product, but a set of coordinated processes and trust relationships that, together, let two parties who have never met establish cryptographic trust in each other.

The asymmetric cryptography foundation

This isn't a cryptography course, so this is an architectural refresher rather than a derivation: asymmetric cryptography uses a mathematically related key pair — a private key that's never shared, and a public key that can be distributed freely. Anything encrypted with the public key can only be decrypted with the matching private key, and anything signed with the private key can be verified by anyone holding the public key. This is the exact primitive Module 05 used to explain FIDO2 (a private key on a security key signs a challenge, the relying party verifies it with the registered public key) and Module 03 used to explain JWT RS256 signing (the IdP signs with a private key, resource servers verify with the public key published at the JWKS endpoint). PKI is what makes that public key trustworthy in the first place — it answers "whose public key is this, actually?"

What a digital certificate is

A digital certificate is a public key bound to an identity — a domain name, a device, a user, a service — by a trusted third party's digital signature. The certificate itself is not secret; it's the signed, distributable proof that "this public key belongs to this identity, according to an authority you've agreed to trust." The corresponding private key is what stays secret, held only by the entity the certificate identifies.

Certificate Authority architecture

A Certificate Authority (CA) is the trusted third party that issues certificates. In any production-grade PKI, the CA isn't a single flat entity — it's structured as a hierarchy, almost always at least two tiers:

  • Root CA — the trust anchor of the entire hierarchy. It's self-signed (there's no higher authority to sign it), and it's kept offline and heavily protected — often physically air-gapped, brought online only for the rare, ceremonial act of signing an Intermediate CA's certificate. The Root CA does not issue end-entity certificates directly.
  • Intermediate CA (Subordinate CA) — does the day-to-day work of issuing certificates. Its own certificate is signed by the Root CA, which is what makes it trusted in turn. Because it's online and issuing constantly, it carries more operational exposure than the Root — which is exactly why the hierarchy exists.

The reason for this two-tier (or sometimes three-tier) structure is blast radius containment. If the Root CA's private key is ever compromised, every certificate ever issued under that hierarchy — at any tier, for any purpose — becomes untrustworthy, because an attacker holding the Root key could forge a signature for anything. Keeping the Root offline and delegating actual issuance to an Intermediate means that if the Intermediate is compromised instead, the damage is limited to the certificates it issued, and the Root can revoke the Intermediate's certificate and stand up a new one without invalidating the entire trust hierarchy from scratch.

The certificate chain of trust

A relying party verifying a certificate doesn't just check the certificate in isolation — it walks the chain of trust from the leaf (end-entity) certificate up through any Intermediate CA certificates to a Root CA that it already trusts. This is structurally identical to the AD forest trust traversal from Module 02: just as a domain controller walks a chain of configured trust relationships from one domain up through tree and forest trusts to determine whether two domains trust each other, a certificate validator walks a chain of cryptographic signatures from a leaf certificate up through Intermediates to a Root, verifying a signature at each hop instead of checking a configured trust relationship. The shape of the problem — and the shape of the solution — is the same; only the mechanism (administrative configuration versus cryptographic proof) differs.

Public CAs vs private/enterprise CAs

Not every certificate needs to come from the same kind of CA. A public CA — DigiCert, Let's Encrypt, Sectigo, and similar — issues certificates that are trusted by default in every major OS and browser, which makes them the right choice for internet-facing TLS, like your organization's public website. A private or enterprise CA — Active Directory Certificate Services, or HashiCorp Vault's PKI engine (Section 12.7) — issues certificates trusted only within your own environment, because you control which trust stores carry its Root certificate. Enterprise CAs are the right choice for internal mTLS, device certificates (the 802.1X and Conditional Access certificates from Module 06 and Module 11), SSH certificates (Module 07), and code signing, where there's no need — and real downside — to paying a public CA or exposing internal naming to the public certificate transparency logs that public CAs publish to.

Certificate Signing Requests and X.509 structure

A certificate is requested, not just generated by the CA out of nowhere. The requesting entity generates its own key pair locally, then sends the public key along with identity information to the CA as a Certificate Signing Request (CSR). The CA validates the request — confirming the requester actually controls the identity being claimed — and signs it, producing the certificate. The private key never has to leave the requesting entity at any point in this process.

Conceptually, an X.509 certificate (the standard format virtually all TLS and enterprise certificates use) carries: the subject (who the certificate identifies), the issuer (which CA signed it), a validity period (not-before / not-after dates), the public key itself, and a set of extensions — most importantly Subject Alternative Name (SAN, the actual list of domains or identities the certificate covers), Key Usage (what cryptographic operations the key is permitted for), and Extended Key Usage (more specific purposes like server authentication or client authentication).

Certificate trust stores

For a chain to validate successfully, the Root CA at the top of it has to already be present in the relying party's trust store — the OS trust store, the browser's trust store, or, in Java environments, the JVM's cacerts truststore. Public CA roots ship pre-installed in all of these by the OS and browser vendors. An enterprise CA's Root certificate has no such head start — it has to be explicitly distributed, usually via Group Policy or MDM, to every device and trust store that needs to validate certificates issued under it. Skipping this distribution step is one of the most common causes of "certificate not trusted" errors for internal applications.

Recognizing the recurring trust-chain pattern is the single highest-value insight in this section. Module 02 taught you that AD forest trust verification walks a chain from a domain up through tree and forest trust relationships to establish whether two domains trust each other. Certificate chain validation does the exact same thing structurally: walk from a leaf certificate up through Intermediate CAs to a trusted Root, verifying a cryptographic signature at each hop instead of a configured trust relationship. Once you see PKI trust chains as "the same shape as AD trust chains, but cryptographically enforced instead of administratively configured," every certificate validation failure becomes much easier to reason about.

🟣 Deep dive: Certificate pinning — what it is and why rotation makes it dangerous

Certificate pinning is when an application hardcodes trust in a specific certificate or CA, rather than trusting anything that validates against the full system trust store. An application might pin a public key, a leaf certificate, or an Intermediate CA, and refuse to connect if the server presents anything else — even something that would otherwise validate as a fully trustworthy chain. The motivation is real: it defeats an attacker who has somehow gotten a fraudulently-issued certificate from a different, legitimately-trusted CA (a scenario that has happened in the wild with compromised public CAs), and it defeats interception by a malicious or compromised intermediary that has its own CA certificate installed in the system trust store.

The operational risk is the mirror image of the security benefit: pinning creates a hard dependency on a specific certificate or key that the application's own developers don't fully control the lifecycle of. When that certificate rotates — which Section 12.3 will show is happening on increasingly short cycles — every application that pinned the old certificate breaks unless its pin set was updated and redeployed in advance. Pinning trades a security improvement for an operational coupling between certificate rotation and application release cycles, which is exactly why many architectures use it sparingly, often only for the highest-risk client-to-server relationships, with a deliberate process to update pins ahead of every planned rotation.

12.3

♻️ Certificate Lifecycle Management

A certificate isn't a one-time artifact — it moves through a full lifecycle: request → issuance → deployment → monitoring → renewal → revocation or expiry. Each stage has its own failure modes, and most certificate-related production incidents trace back to a gap in this lifecycle rather than a cryptographic flaw.

Certificate enrollment methods

How a certificate gets requested and issued varies a great deal by context:

  • Manual CSR generation and submission — the legacy approach: an engineer generates a key pair and CSR by hand, submits it to the CA, and installs the resulting certificate manually. It works, but it's slow, error-prone, and doesn't scale past a small number of certificates.
  • SCEP (Simple Certificate Enrollment Protocol) — lets devices auto-enroll for certificates over the network, the protocol referenced but not explained in Module 06's 802.1X content. It's explained fully later in this section.
  • ACME (Automatic Certificate Management Environment) — the protocol behind Let's Encrypt's fully automated issuance, increasingly adopted for internal automation as well, not just public certificates.
  • AD CS auto-enrollment via Group Policy — domain-joined Windows devices and users automatically receive and renew certificates without any user action, the prerequisite that made Module 06's EAP-TLS deployment operationally feasible.
  • HashiCorp Vault PKI engine API-driven issuance — programmatic, on-demand certificate issuance designed for short-lived certificates, covered fully in Section 12.7.

The shrinking validity period

There's a clear architectural trend toward shorter certificate validity periods — 90 days is now common, and some modern patterns issue certificates valid for only hours. This is a sharp departure from the older norm of one-to-three-year certificates. Shorter validity is more secure for a straightforward reason: it bounds the compromise window. If a private key is stolen and nobody notices, a 90-day certificate limits how long that key remains useful to an attacker, where a 3-year certificate would leave the door open for years. But shorter validity has a real architectural requirement attached to it: you cannot manually renew thousands of 90-day certificates on any reasonable operational budget. Automation stops being a nice-to-have and becomes mandatory the moment validity periods drop below what a human team can track by hand.

The certificate expiry incident pattern

Module 04 already showed you a concrete example of this risk: PingFederate's signing certificate expiring and breaking federation. That wasn't a one-off — it's a universal PKI operational risk that recurs anywhere certificate lifecycle isn't actively managed. Expired certificates cause silent, cascading authentication failures across TLS, mTLS, code signing, and federation, and because the failure presents as a generic handshake or trust error, it often takes longer to diagnose than the actual fix takes to apply.

Inventory, monitoring, and renewal strategy

The foundational operational question in PKI — "what certificates exist, where are they deployed, and when do they expire" — is one that most enterprises answer poorly. Certificates get issued by individual engineers for individual projects with no central record, and nobody finds out a given certificate exists until it expires and something breaks. This is the case for centralized Certificate Lifecycle Management (CLM) tooling: a system of record for every certificate in the environment, with proactive expiry alerting, regardless of who issued it or for what.

On renewal mechanics specifically, there's a security trade-off between in-place renewal (same key pair, new validity period — operationally simpler, but doesn't help if the original key was ever exposed) and re-key on renewal (a new key pair generated alongside the new certificate — slightly more operational overhead, but closes any undetected key exposure on every renewal cycle). And on certificate scope, wildcard certificates (covering *.company.com) trade operational simplicity for concentrated risk — a single compromised wildcard certificate affects every subdomain — against SAN certificates (each covering a specific, enumerated list of names), which are more granular but multiply the number of certificates an organization has to track.

Certificate expiry incidents are among the most preventable yet recurring outages in enterprise IT — and Module 04 already showed you one example with PingFederate's signing certificate. 12.4

🔄 Key Rotation Architecture

Certificate renewal, covered in Section 12.3, extends a validity period. Key rotation is a related but distinct discipline: replacing the underlying cryptographic key material itself, not just extending how long a given key is trusted. The distinction matters because renewal alone doesn't help against an undetected compromise — if a private key was quietly stolen six months ago, renewing the certificate that points at the same key just extends the attacker's access right along with it. True rotation generates an entirely new key pair, which limits the impact of any compromise that hasn't yet been detected.

Rotation across different secret categories

Key rotation isn't a single mechanism — it looks different depending on what kind of key is being rotated:

  • TLS/mTLS certificate key rotation — extends directly from Section 12.3's renewal discussion, with the added step of generating a new key pair rather than reusing the old one.
  • JWT signing key rotation — a direct Module 03 callback. An OIDC provider like PingFederate rotates its signing key, publishes the new public key via JWKS before switching to signing with it, and only then begins using the new key — a careful sequencing covered in detail below.
  • Symmetric encryption key rotation (data at rest) — either re-encrypting the entire dataset with a new key, or using envelope encryption so only a small data-encryption-key needs rotation, not the entire underlying dataset.
  • API key / service account credential rotation — the explicit Module 10 callback to CyberArk's CPM (Central Policy Manager), which automates exactly this rotation for privileged accounts and service credentials.

The JWKS rollover pattern, in detail

This is worth walking through carefully, because it's the detail most homegrown JWT implementations get wrong. JWT validators should never cache and trust only a single signing key. Instead, they should fetch and cache all currently valid signing keys from the JWKS endpoint, distinguishing between them by the kid (key ID) claim that Module 03 introduced. During a rotation window, the IdP publishes both the outgoing key and the incoming key simultaneously in JWKS, continues signing new tokens with the outgoing key for a period, then switches to signing with the new key — all while validators keep trusting both keys until every token signed with the old one has naturally expired. This overlap window is what prevents rotation from causing an outage.

Choosing a rotation frequency

How often a key should rotate is a balance between operational overhead and security benefit, not a single universal answer. The sensitivity of what the key protects, the blast radius if it's compromised, and the maturity of the automation available to rotate it all factor in — a Root CA key might rotate on a multi-year cycle precisely because rotating it is a major ceremony, while a database credential generated by Vault might rotate every hour because the automation makes that essentially free. What matters architecturally isn't picking one "correct" frequency — it's making the decision deliberately rather than by default.

Automated rotation is not optional at scale

Manual rotation inevitably degrades over time. The "we'll rotate it next quarter" credential has a way of quietly becoming the credential that's three years old and nobody remembers the last time it changed — directly paralleling Module 11's orphaned service account problem, where an account nobody owns simply persists indefinitely because nothing forces a decision about it. Rotation has to be automated to be reliable; a manual process that depends on someone remembering to do it is, in practice, a process that doesn't happen consistently.

Graceful key rollover is the detail most homegrown JWT implementations get wrong, and it's worth being explicit about why this connects directly to Module 03. This looks identical to an outage. The fix is the overlap window shown above: always publish the previous key alongside the new one in JWKS until you're certain every token signed with the old key has naturally expired.

🔒 HSM Concepts — Protecting the Keys That Protect Everything

An HSM (Hardware Security Module) is a dedicated, tamper-resistant hardware device designed to generate, store, and use cryptographic keys without the private key material ever leaving the device in plaintext. It exists to solve a problem every section so far has implicitly raised: a software-based key — a key file sitting on a server's disk — is only as protected as that server's OS-level access controls. Anyone who gains administrative access to that server can, in principle, copy the key file and walk away with it. An HSM removes that possibility by physically and cryptographically isolating the key: cryptographic operations like signing or decrypting happen inside the device itself, rather than exposing the key to the calling application.

The "keys never leave the HSM" principle

The operating model is request/response, not key handoff. An application sends a request — "sign this data with key X" — to the HSM, and receives a result, the signature, in return. The private key itself is never extracted from the device, not by the calling application, and not even by the HSM's own administrators. This is exactly the pattern Module 10 described for CyberArk's Vault Server Key, the most protected key in the entire CyberArk key hierarchy, which encrypts the Safe Keys that in turn encrypt every Object Key and credential underneath it. An HSM is how that "most protected key" is often physically secured in serious enterprise deployments — Module 10 told you the key existed and was critical; this section tells you where it actually lives.

HSM use cases across this portal

Once you know to look for it, the HSM shows up underneath nearly every "most critical key" mentioned earlier in this portal: the Root CA private key from Section 12.2 (the single most catastrophic key to lose), the PingFederate/IdP signing key from Module 03/04, the CyberArk Vault server key from Module 10, database and application encryption keys protecting data at rest, and code signing keys used to assert the authenticity of released software.

Tamper resistance and tamper evidence

HSMs are engineered not just to resist extraction under normal operation, but to actively detect physical tampering attempts — drilling, probing, unusual temperature or voltage changes — and respond by zeroizing (destroying) the keys stored inside, rather than allowing extraction under duress. This is a meaningfully different security posture than a software keystore, which has no equivalent physical response to an attacker gaining hands-on access to the hardware it runs on.

HSM deployment models

Organizations don't have to choose between "no HSM" and "build your own HSM infrastructure" — there's a spectrum:

  • On-premises physical HSM appliances (Thales, Entrust nShield) — full control and the highest assurance, at the highest cost and operational complexity; you're responsible for your own HA/DR.
  • Cloud HSM services (AWS CloudHSM, Azure Dedicated HSM) — dedicated, single-tenant hardware physically located in the cloud provider's datacenter; you control the keys, the provider manages the physical infrastructure underneath.
  • Cloud KMS with HSM-backed keys (AWS KMS, Azure Key Vault, GCP Cloud KMS) — the simplest to adopt; keys are backed by HSMs, but the service itself is shared, multi-tenant infrastructure with less granular control than a dedicated HSM.

FIPS validation and the cost/complexity trade-off

FIPS 140-2/140-3 validation is a formal certification of an HSM's cryptographic module against a defined US government security standard, and regulated industries (financial services, government, healthcare) often require it explicitly when selecting HSM vendors or cloud KMS tiers. But HSMs — particularly dedicated, on-premises ones — are genuinely expensive and operationally complex, and the security benefit isn't free. The architectural judgment call is whether that benefit is worth it for a given key, versus a well-secured software key store or a multi-tenant cloud KMS being sufficient. In practice, this usually comes down to how catastrophic the consequences would be if that specific key were ever extracted — the Root CA key warrants an HSM in almost every serious deployment; a low-sensitivity internal service's TLS key often does not.

🟣 Deep dive: PKCS#11 and why it prevents HSM vendor lock-in

PKCS#11 is a standard, vendor-neutral API that applications use to talk to HSMs and other cryptographic tokens, regardless of which manufacturer built the underlying hardware. Without a standard like this, an application like PingFederate or a Certificate Authority would have to be written and tested against each individual HSM vendor's proprietary API — meaning a decision to switch HSM vendors, or to add a second vendor for redundancy, would require code changes in every dependent application.

Because PKCS#11 defines a common interface — a set of functions for operations like generating keys, signing data, and managing sessions — an application written against PKCS#11 can talk to a Thales HSM, an Entrust HSM, or a cloud HSM service that exposes a PKCS#11 interface, without needing vendor-specific integration code for each one. This is what allows organizations to treat HSM vendor selection as primarily a procurement and operational decision rather than an application architecture decision, and it's a meaningful part of why HSM-dependent systems like enterprise CAs and federation signing infrastructure can be migrated between HSM vendors without a full application rewrite.

🚫 OCSP & CRL — Certificate Revocation Architecture

A certificate's validity period makes a forward-looking promise: "trust this until this date." But that promise has an obvious gap — what happens if the private key is compromised today, long before that stated expiry? Revocation is how a CA retracts trust early, declaring "this certificate is no longer trustworthy, regardless of what its expiry date says."

CRL: the original mechanism

A Certificate Revocation List (CRL) is the original answer to this problem: the CA periodically publishes a signed list of every revoked certificate's serial number, and validators download that list and check the certificate they're validating against it. CRLs have real limitations, though. The list grows continuously over time and has to be downloaded in full (or via CRL Distribution Points and delta updates to soften that cost), and there's an inherent staleness window between when a certificate is actually revoked and when the next CRL publication reflects that — during which a revoked certificate might still pass validation.

OCSP: the real-time alternative

The Online Certificate Status Protocol (OCSP) takes a different approach: instead of downloading an entire list, a validator queries an OCSP responder with a specific certificate's serial number and gets back a direct answer — good, revoked, or unknown — in real time. This avoids the staleness and list-size problems of CRLs, but introduces its own trade-offs.

OCSP stapling

Querying an OCSP responder on every single TLS connection creates two problems: it adds a network round-trip's worth of latency to every handshake, and it creates a privacy concern, because the OCSP responder ends up seeing every site a given client connects to. OCSP stapling solves both: instead of the client querying the responder directly, the server itself periodically fetches a signed OCSP response for its own certificate and "staples" that response to the TLS handshake it presents to clients. The client validates the stapled response's signature and trusts it without ever contacting the OCSP responder directly — the query happens periodically from the server, not per-connection from every client.

Soft-fail vs hard-fail revocation checking

What should happen when a revocation check itself fails — the OCSP responder is unreachable, or the CRL can't be downloaded? Most browsers and clients soft-fail: proceed with the connection anyway, on the theory that hard-failing would make the CA's or responder's availability a single point of failure for enormous swaths of the internet. The practical consequence is that revocation checking is, in real-world deployments, often bypassable by an attacker capable of blocking the revocation check itself — a known, accepted gap rather than an oversight.

Short-lived certificates as a revocation alternative

This connects directly back to Section 12.3's discussion of shrinking validity periods. If a certificate is only valid for hours or days, the architectural need for revocation infrastructure to work correctly diminishes substantially, because compromise exposure is already bounded by how soon the certificate naturally expires anyway. This is a meaningful part of why the industry has been moving toward very short-lived certificates: it reduces how much weight the system has to place on revocation infrastructure functioning correctly in real time.

Revocation in contexts already covered in this portal

Revocation looks different depending on the certificate type. SSH certificates (Module 07) are typically revoked by simply being short-lived rather than through CRL/OCSP infrastructure at all. Device certificates (Module 06/11) are revoked when a device is decommissioned or fails compliance. TLS server certificates use the CRL/OCSP mechanisms described above, sitting alongside the validity-period trend from Section 12.3 as a second, complementary line of defense.

🔴 Security note

Soft-fail revocation checking is a known, accepted gap in most TLS implementations, and it's important to understand why it exists rather than treat it as obviously broken. If your browser hard-failed — refused to connect — every time it couldn't reach an OCSP responder or download a CRL, then a network outage, a CA's infrastructure issue, or an attacker simply blocking traffic to the OCSP endpoint would break HTTPS connectivity broadly — an availability risk considered worse, in practice, than the residual risk of occasionally trusting a revoked certificate. This is a real architectural trade-off, not an oversight — and it's part of why the industry trend toward very short-lived certificates (Section 12.3) is gaining traction: it reduces reliance on revocation infrastructure working correctly in the first place.

🟪 Analogy

Revocation checking is architecturally similar to the RADIUS Access-Challenge fail-open/fail-closed decision from Module 06. Just as a NAS must decide what happens when its RADIUS server is unreachable, a TLS client must decide what happens when its revocation check is unreachable. Both decisions trade security (fail-closed: safer, but an availability risk if the checking service is down) against availability (fail-open/soft-fail: more resilient, but a determined attacker can exploit the gap). The fact that the security industry has largely converged on soft-fail for revocation checking, while insisting on fail-closed for RADIUS network access, tells you something about how risk is weighed differently depending on what's actually being protected.

🔓 HashiCorp Vault — Dynamic Secrets Architecture

HashiCorp Vault is a developer-centric secrets management platform built around API-first access and, most distinctively, the concept of dynamic secrets — credentials generated on demand and designed to be ephemeral from the moment they're created, rather than static, long-lived values that simply get rotated periodically.

The dynamic secrets model

The architectural shift is significant. Instead of storing a static database password and rotating it on a schedule — the CyberArk CPM model from Module 10 — Vault generates a brand-new, unique database credential at the exact moment an application requests one, attaches a short TTL (time-to-live) to it, and automatically revokes that specific credential when the TTL expires. There is no long-lived password sitting in a vault waiting to be rotated; the credential's entire lifespan is the lease.

Why is this architecturally stronger than rotating a static secret? It's the same Zero Standing Privilege principle from Module 10, and the same workload identity federation logic from Module 11, applied to credentials instead of sessions or tokens. A credential that exists only for the duration of a single application's lease, used by exactly one consumer, eliminates entire categories of risk that rotation alone never fully closes: shared credentials that multiple services unknowingly depend on, stale credentials that quietly outlive the application that originally requested them, and lateral movement using a static credential an attacker happened to find lying around. Dynamic secrets don't make rotation faster — they remove the concept of a long-lived credential to rotate in the first place.

Vault's secrets engines

Vault's pluggable secrets engines are what generate different types of dynamic secrets:

  • Database secrets engine — generates per-request database credentials with automatic expiry.
  • AWS/Azure/GCP secrets engines — generate short-lived cloud IAM credentials on demand, a capability that complements, and in some architectures overlaps with, Module 11's workload identity federation.
  • PKI secrets engine — Vault can act as a Certificate Authority in its own right, issuing short-lived certificates on demand via API, directly extending Section 12.3's validity-period discussion into a fully automated implementation.
  • SSH secrets engine — Vault can sign SSH certificates on demand, a direct extension of Module 07's SSH Certificate Authority content into Vault's API-driven model.
  • Transit secrets engine — encryption-as-a-service: applications send data to Vault to encrypt or decrypt without ever handling the encryption key directly, the same "keys never leave" principle Section 12.5 described for HSMs, implemented in software (and, in HSM-backed Vault deployments, ultimately enforced by an actual HSM underneath).

How applications authenticate to Vault

Before an application can request a secret, it has to authenticate to Vault in the first place. Vault supports a range of authentication methods for this — AppRole (a role-and-secret-ID pattern designed for machine-to-machine use), the Kubernetes auth method, and the AWS IAM auth method among others — and the cloud-native identity methods connect directly back to Module 11's workload identity content: a workload presents its already-established platform identity (a Kubernetes service account token, an AWS instance role) to Vault, and Vault validates that identity before issuing any secret.

Vault architecture: storage, sealing, and policy

Vault separates the storage backend (where encrypted data physically lives) from the Vault server process itself, and introduces an operational concept unique among the platforms in this module: the unseal process. When Vault starts or restarts, it begins in a "sealed" state — its storage is encrypted and Vault cannot read it — until it's unsealed using Shamir's Secret Sharing, a cryptographic scheme that splits the master key into multiple shares, requiring a threshold number of them (commonly three of five) to reconstruct the key and unseal Vault. This is explained fully below; the operational point is that sealing is a real consideration any time Vault restarts, whether planned or not.

Finally, Vault policies govern which identities can access which secrets paths — an explicit application of the PBAC pattern from Module 08, expressed as policy rather than embedded in application logic, and applied here specifically to secrets access rather than general authorization decisions.

🟣 Deep dive: How Vault's Kubernetes auth method establishes trust without a shared secret

When a pod authenticates to Vault using the Kubernetes auth method, it presents its bound service account token — the same token type Module 11 introduced as the modern, audience-scoped replacement for the older, unbounded default service account token. Vault doesn't simply trust that token at face value; it validates it by calling back to the Kubernetes API server's TokenReview API, asking the cluster itself to confirm that the token is genuine, unexpired, and bound to the service account it claims to represent.

This callback validation is what lets Vault and the Kubernetes cluster establish trust without ever needing to share a pre-configured secret between them. Vault is configured with the Kubernetes API server's address and a way to verify its TLS certificate (often the cluster's own CA certificate, tying directly back to Section 12.2's PKI trust chain content), and from that point on, trust flows from the live validation call rather than from any static credential Vault and Kubernetes would otherwise need to keep in sync. If a pod's service account is deleted or its token is revoked, the very next validation call fails — there's no stale shared secret anywhere to clean up.

🤖 CyberArk Conjur — Secrets Management for DevOps

Module 10 closed Section 10.8 with a preview of CyberArk Conjur; this section gives it the full architectural treatment it was deferred from. CyberArk Conjur is CyberArk's secrets management platform purpose-built for DevOps, CI/CD, and cloud-native workloads — architecturally distinct from the EPV/Vault product covered throughout Module 10, which is workflow-driven and human-PSM-centric.

Why CyberArk built a separate product

This goes back to Module 10's closing insight: humans and machines consume credentials in fundamentally different ways, and a single product optimized for one consumption pattern tends to be a poor fit for the other. Humans need workflow, approval, and session recording — that's EPV's strength, built around the PVWA portal and PSM session proxying. Machines need fast, programmatic, API-native credential delivery with no human in the loop and no session to record — that's Conjur's strength. Same vendor, same underlying security philosophy, but two architecturally different products because the thing being optimized for is different in each case.

Conjur's core architecture

At its core, Conjur is a secrets store exposed through a REST API, governed by policy-as-code access control — Conjur policies define, in a declarative format, exactly who or what is permitted to retrieve which secrets. It ships with native integrations for Kubernetes, the major CI/CD platforms, and container orchestration generally, reflecting its purpose-built focus on the machine and pipeline consumers it was designed for.

Conjur and CyberArk EPV integration

Conjur and EPV aren't necessarily either/or — in many enterprise deployments, Conjur acts as a secrets proxy and cache sitting in front of EPV-managed credentials. Conjur handles the high-volume, low-latency requests that machine workloads generate, while EPV remains the system of record for human-facing privileged accounts, with rotation still governed centrally through EPV's existing CPM policies. This lets an organization extend its existing CyberArk investment to cover machine consumers without duplicating the rotation and governance logic it already has in place for human accounts.

Conjur policy-as-code

Conjur access policies are defined in YAML and version-controlled — a direct callback to Module 08's PBAC content, where policy is externalized from application code and governed independently, applied here specifically to secrets access. A Conjur policy declares which workload identity ("Host" in Conjur's terminology) can retrieve which specific secret, and because the policy lives in version control, every change to who can access what is auditable through normal Git history rather than buried in an application's configuration.

Conjur authentication methods for workloads

Just as Vault authenticates workloads through methods like AppRole and the Kubernetes auth method, Conjur has its own set of authenticators that let a Kubernetes pod, a Jenkins pipeline, or an AWS Lambda function authenticate to Conjur to retrieve a secret — paralleling Section 12.7's Vault auth methods and Module 11's workload identity federation patterns directly. The platforms differ in implementation detail, but the underlying architectural shape — a workload presents an already-established platform identity, the secrets platform validates it, a secret is returned — is identical.

Conjur for CI/CD pipelines

One of Conjur's most direct, practical use cases is eliminating the "secret stored as a CI/CD pipeline variable" anti-pattern called out explicitly in Module 11 Section 11.5's GitHub Actions OIDC example. Rather than a pipeline holding a static, long-lived secret as a stored variable, the pipeline authenticates to Conjur at runtime — using exactly the kind of short-lived, federated identity Module 11 described — and retrieves the secret it needs fresh, for that run only.

Conjur for Kubernetes

The Conjur Kubernetes Authenticator and the Secrets Provider for Kubernetes solve a specific, often-underestimated gap: native Kubernetes Secret objects are only base64-encoded by default, not encrypted, which makes them trivial to decode for anyone with read access to that namespace's secrets — including, per Module 11's default service account risk discussion, a compromised pod with broader-than-intended RBAC permissions. Conjur's Kubernetes integration injects the actual secret value directly into a running pod at startup, retrieved fresh from Conjur's encrypted store, rather than relying on a native Kubernetes Secret object as the storage mechanism at all.

🧭 Secrets Management Selection & Integration Framework

Sections 12.2 through 12.8 covered seven distinct technologies — PKI/CAs, certificate lifecycle tooling, HSMs, OCSP/CRL infrastructure, HashiCorp Vault, and CyberArk Conjur — and a working architect rarely gets to deploy all of them greenfield. The real job is choosing the right combination for a given environment, and integrating it cleanly with everything else this portal has already covered. This section is that decision framework.

Selection dimension 1: who or what is consuming the secret

This is the same human-vs-machine distinction Section 12.8 used to explain why CyberArk built two separate products. Human-consumed credentials — interactive admin sessions, break-glass access — favor PAM platforms with workflow and session recording (CyberArk EPV, Module 10). Machine-consumed credentials — application database connections, CI/CD pipeline secrets, container workloads — favor API-native, programmatic platforms (Vault, Conjur). Getting this dimension wrong early is the single most common cause of secrets management projects that stall: forcing a human-workflow-centric tool onto a high-volume machine use case (or vice versa) creates friction that eventually gets bypassed.

Selection dimension 2: what type of secret

Different secret types favor different platforms even within the "machine consumer" bucket. Database and cloud credentials are the strongest fit for dynamic secrets engines (Vault, Conjur with appropriate integrations). Certificates are the domain of PKI infrastructure (Sections 12.2–12.3, or Vault's PKI secrets engine for short-lived, API-issued certs specifically). Encryption keys protecting data at rest belong with HSMs or cloud KMS (Section 12.5), not in a general-purpose secrets store. Static legacy secrets that can't yet be eliminated — an old mainframe application's hardcoded service account, for example — still belong in a vault with strict access control, even if dynamic generation isn't achievable for that particular system yet.

Selection dimension 3: existing platform investment

An organization with substantial existing investment in CyberArk for human PAM has a meaningfully lower-friction path extending into Conjur for machine secrets than standing up Vault as an entirely separate platform with its own operational team, policy model, and integration surface — not because Vault is worse, but because the integration and operational overlap with the existing CyberArk deployment (shared rotation policies via CPM, a single vendor relationship, overlapping skill sets on the team) reduces total cost and risk. Conversely, an organization with no existing CyberArk footprint and a strongly Kubernetes/cloud-native engineering culture often finds Vault's open-source roots, Terraform-ecosystem integration, and broad community tooling a better starting point. Neither answer is universally correct — the existing investment is a real architectural input, not just a procurement consideration.

Selection dimension 4: regulatory and compliance requirements

Regulated industries often have explicit requirements that constrain the decision space directly — a FIPS 140-2/140-3 validation requirement (Section 12.5) for any HSM or KMS in scope, specific key-rotation-frequency mandates for certain secret types, or audit trail requirements that favor a platform with mature, exportable logging over one that's earlier in its compliance certification journey. These requirements should be gathered before the technology selection, not retrofitted afterward.

Bringing it together: the full-circle integration

Every platform and pattern in this module connects back to specific content from Modules 02 through 11, and seeing that full map is the point of placing this section last. PKI underlies the JWT signing in Module 03, the SSH Certificate Authority in Module 07, the mTLS and device certificates in Module 06 and Module 11. HSMs protect the most sensitive keys named throughout Modules 03, 04, and 10. Vault and Conjur both directly extend the Zero Standing Privilege and workload identity federation principles established in Module 10 and Module 11, applied specifically to the credential layer underneath those higher-level identity mechanisms. None of this module's content stands alone — it's the cryptographic foundation that every other module has been quietly resting on.

A maturity roadmap, not a single decision

Most organizations don't arrive at a mature secrets management architecture in one project. The realistic path runs through stages: first, eliminate hardcoded secrets from source code and config files (Section 12.1's anti-pattern) by moving everything into at least a basic vault, even a static one. Second, automate certificate lifecycle management to eliminate expiry-driven outages (Section 12.3). Third, introduce dynamic secrets for the highest-value, highest-risk credentials — typically production database access and cloud IAM credentials — before attempting a wholesale migration of every secret in the environment. Fourth, extend HSM protection to the most catastrophic keys (Root CA, signing keys) if not already in place. Treating this as a staged roadmap, prioritized by risk, is consistently more successful than treating it as a single "buy the platform" decision.

Knowledge Check

Five questions to test recall before moving on. Click each question to reveal the answer.

Q1
Why is secrets management considered a distinct discipline from PAM and IGA, rather than a subset of either?

PAM governs workflow and access to existing credentials (who can use it, under what process); IGA governs entitlement lifecycle and certification (should this identity still have this access). Secrets management answers a different question entirely: where does the actual cryptographic material live, how is it delivered, and how is it rotated. PAM and IGA both assume a credential already exists and govern its use — secrets management is the runtime infrastructure that creates and protects the credential itself.

Q2
Why is the Root CA kept offline while the Intermediate CA does the day-to-day certificate issuance?

Blast radius containment. If the Root CA's private key is compromised, every certificate ever issued under the entire hierarchy becomes untrustworthy. Keeping the Root offline and delegating issuance to an Intermediate means a compromise of the Intermediate only affects the certificates it issued — the Root can revoke and replace it without invalidating the whole hierarchy.

Q3
What problem does the JWKS overlap window solve during key rotation?

It prevents an outage. If an IdP rotated signing keys abruptly — publishing only the new key and immediately removing the old one — every token already signed with the old key would instantly fail validation. The overlap window keeps both the old and new keys published in JWKS until every token signed with the old key has naturally expired, so rotation never breaks in-flight tokens.

Q4
Why does HashiCorp Vault's dynamic secrets model represent a stronger security posture than rotating a static secret on a schedule?

A static secret, even when rotated regularly, exists continuously and may be shared across multiple consumers — creating a standing attack surface for up to the entire rotation interval. A dynamic secret is generated uniquely per request, used by exactly one consumer, and automatically revoked at lease expiry — eliminating shared credentials, stale credentials, and most of the window an attacker could exploit, rather than just shrinking it.

Q5
Why does CyberArk offer both EPV and Conjur instead of one unified product?

Humans and machines consume credentials in fundamentally different ways. Humans need workflow, approval, and session recording — EPV's strength, built around PVWA and PSM. Machines need fast, programmatic, API-native delivery with no human in the loop — Conjur's strength. Optimizing one product for both consumption patterns would compromise its fit for each.

Real-World Scenario — The Certificate Outage Post-Mortem

Situation

At 2:14am, every service calling the internal payments-authorization API begins failing with TLS handshake errors. On-call is paged. Customer-facing checkout starts failing within eleven minutes. The on-call engineer spends the first forty minutes ruling out network and load balancer issues before someone thinks to check the certificate — and finds it expired three hours earlier.

Root Cause

The certificate was issued two years prior by an engineer who has since left the company, manually requested from the enterprise CA, manually installed, and never entered into any central certificate inventory. No monitoring existed because no system knew the certificate existed in the first place. This is precisely Section 12.3's expiry incident pattern — not a cryptographic failure, a lifecycle management failure.

🟪 Analogy

An untracked certificate is architecturally identical to an orphaned service account from Module 11 — a credential with no clear owner, invisible to governance until the moment it causes a failure. The fix in both cases is the same shape: you cannot govern what you haven't inventoried, and inventory has to be the foundation any lifecycle or rotation program is built on top of, not an afterthought added once something breaks.

Immediate Remediation

The on-call team manually issues an emergency replacement certificate, restarts the affected service, and restores checkout within fifty-eight minutes of the initial page. A full incident review is scheduled for the next business day.

Use Case — Apply This to Your Own Environment

Before reading further, pause and ask: could this exact incident happen in your environment today? Do you have a complete, centrally-maintained inventory of every TLS certificate in production, regardless of who issued it? If you're not confident in the answer, that uncertainty is itself the finding — and it's the same gap this post-mortem is about to walk through closing.

90-Day Architecture

The team stands up a centralized Certificate Lifecycle Management (CLM) tool that discovers every certificate in the environment via network scanning and CA log review, alerts at 90/60/30/7 days before any expiry, and assigns an owning team to every discovered certificate — even ones with no clear original owner, defaulting to the platform team until reassigned. This closes the immediate visibility gap without yet changing how certificates are issued or renewed.

🟣 Deep dive: Why certificate discovery is harder than it sounds

"Just scan the network for certificates" sounds simple but runs into real architectural friction. Network-based scanning only finds certificates actively presented on a listening port — it misses certificates sitting unused on disk, certificates embedded in client applications rather than servers, and certificates protected behind network segmentation the scanner can't reach. CA-log-based discovery (reviewing every certificate a given CA has ever issued) is more complete for certificates from CAs you control, but says nothing about certificates obtained from a public CA outside your direct oversight, or certificates issued by a forgotten, unmanaged internal CA instance someone stood up years ago.

A mature discovery program typically combines both approaches — active network scanning for what's currently in use, plus CA log review for what's been issued — and accepts that even this combination won't reach 100% completeness on day one. The realistic goal isn't a perfect inventory immediately; it's a steadily improving one, with every newly discovered "unknown" certificate treated as a data point about where the next gap in the discovery process is, not just a one-off cleanup item.

12-Month Target State

The organization migrates its highest-churn internal services to short-lived certificates issued automatically via Vault's PKI engine (Section 12.7), eliminating manual renewal — and the entire category of "someone forgot to renew it" risk — for the services where automation is feasible. Lower-churn legacy systems that can't yet support automated issuance remain on the CLM tool's monitoring and alerting, with a long-term goal of migrating them as the underlying platforms allow.

Lessons

Certificate expiry incidents are entirely preventable, and they keep happening anyway because inventory and monitoring are treated as optional until an outage makes them mandatory. The architectural fix this post-mortem converged on — inventory first, automation second — is the same staged maturity roadmap Section 12.9 described in the abstract: don't attempt to automate what you haven't yet discovered and inventoried.

🟩 Analogy

This incident, and its resolution, is a small-scale rehearsal of the exact maturity roadmap from Section 12.9: you can't skip straight to Stage 3's dynamic secrets when you haven't yet completed Stage 1 and Stage 2's foundational visibility and lifecycle automation. Every organization that's been burned by a certificate outage has, in effect, been forced to learn this staging the hard way — the value of Section 12.9's framework is learning it in advance instead.
