Machine Identity & Non-Human Identities: Service Accounts, Workloads & RPA

Walk into any enterprise identity program and ask: how many human employees do you have? Someone will know the answer immediately — it's in the HR system, it's the headcount number the CFO reports quarterly. Now ask: how many service accounts, API keys, container identities, and automation bots exist in your environment? Almost no one knows. The honest answer, at most enterprises, is "more than the human count, and growing faster."

Non-human identities have exploded with cloud adoption, microservices, CI/CD automation, and RPA — and most IAM programs built their entire governance model (Modules 08–10) around humans. This module gives architectural shape to the identity population that's quietly become the larger attack surface: what these identities are, how they're created, how they should be governed, and why the lifecycle problem from Module 01 is far worse here than it ever was for humans. 🌍

11.1

💥 The Non-Human Identity Explosion

The Scale Problem

Across cloud-native enterprises, industry surveys consistently point in one direction: non-human identities now outnumber human identities by a wide margin — commonly cited in the range of 10x to 45x, depending on how aggressively an organization has adopted microservices, cloud infrastructure, and automation. The exact multiple matters less than the trend it represents. A decade ago, a service account was something an engineer requested for a specific batch job, and there were a few hundred of them in even a large enterprise. Today, every microservice, every cloud resource, every CI/CD pipeline run, and every automation bot can mint its own identity — and most of them do.

Why the Explosion Happened

No single trend caused this. It's the compounding effect of several architectural shifts your career has already taken you through:

  • Microservices architecture — where a monolith needed one application identity, a microservices decomposition of that same application might need fifty, one per service, each calling the others.
  • Cloud adoption — every cloud resource, from a Lambda function to an S3 bucket policy, typically needs an IAM role or service account of its own.
  • CI/CD automation — every deployment pipeline needs credentials to push code, pull secrets, and provision infrastructure, often on every single run.
  • Container orchestration — Kubernetes assigns every pod a service account by default, whether or not anyone asked for one (Section 11.4 covers this in depth).
  • RPA adoption — every bot automating a business process needs the same application access a human user would have had.
  • API-first architecture — every internal or external integration needs a client identity to authenticate against the API it's calling.

The Governance Gap

The IGA programs you studied in Modules 08–09 were built around a clean lifecycle trigger: an HR system records a hire, a transfer, a termination, and that event drives provisioning, recertification, and deprovisioning. Non-human identities have no equivalent system of record. There's no "HR feed" for a Kubernetes service account. There's no manager to ask "does this API key still need write access to the customer database?" The governance model that works well for humans simply doesn't extend naturally to machines — and most enterprises haven't built a parallel model that does.

Why Non-Human Identities Are Often More Privileged

It's tempting to assume machine identities carry less risk than human ones because no person is "behind" them in the moment of compromise. The opposite is usually true. A service account connecting an application to a database often has broader data access than any single human user would ever be granted — because it was provisioned once, for an application that needs to read and write broadly, and nobody has revisited the scope since. That same service account typically has no MFA (there's no human to prompt), no session timeout (it authenticates once and runs indefinitely), and no behavioral baseline against which anomalous use could be detected.

The Attacker's Perspective

From an attacker's point of view, non-human identities are an unusually attractive target: long-lived credentials that rarely rotate, broad permissions granted for convenience rather than necessity, minimal monitoring, and credentials that are frequently hardcoded into source code, configuration files, or CI/CD pipeline definitions where they're easy to find once an attacker has any foothold. A single leaked service account credential or API key can provide more durable, less-detectable access than compromising an individual human user's password ever would.

🟣 Security — The Governance Asymmetry

The governance asymmetry is the core security problem this module addresses. A human employee's access is reviewed quarterly (Module 09 certification), requires MFA (Module 05), is deprovisioned within 24 hours of termination (Module 09), and is monitored for anomalous behavior (Module 14 preview). A service account created three years ago by an engineer who has since left the company may have none of these controls — no owner, no review, no MFA-equivalent, and no deprovisioning trigger because there's no "termination event" for a service account. This governance asymmetry is why non-human identities are increasingly the entry point in enterprise breaches.

🟢 Analogy — API Sprawl, Revisited

The non-human identity explosion is the identity equivalent of the API sprawl problem you've watched unfold over your career. Ten years ago, an enterprise had a manageable number of APIs, each well-documented and owned. Today, microservices architectures produce hundreds or thousands of internal APIs, many undocumented, many with unclear ownership, many running with broader permissions than they need "because it was easier to get it working." Non-human identity sprawl is the same pattern: every new microservice, every new cloud resource, every new automation script creates a new identity, and without deliberate governance, that identity outlives its purpose, its owner moves on, and nobody remembers why it has the access it has.

🧪 Lab — Estimate Your Ratio

Estimate your organization's non-human-to-human identity ratio. Count (or estimate): AD service accounts, cloud IAM roles/service accounts across AWS/Azure/GCP, Kubernetes service accounts, API keys issued for internal/external integrations, and RPA bot accounts. Compare this total to your human employee count. If you don't know these numbers — that unknown is itself the finding. Most enterprises cannot answer this question quickly, and that inability is the starting point for every non-human identity governance program.

11.2

🏢 Service Account Governance

Module 10 introduced service accounts as privileged identities and showed how CyberArk AIM/Conjur can vault and rotate their credentials. This section widens the lens from credential protection to full governance: who creates a service account, who owns it, who reviews it, and — the question that breaks down most often — who decommissions it when the application it served is retired.

What a Service Account Is, and Its Common Types

A service account is an identity used by an application, script, or system process to authenticate — not tied to a single human user's session. In practice, you'll encounter a handful of recurring patterns:

  • AD/LDAP service accounts — used for application authentication against directory services, often the credential a Windows service or scheduled task runs as.
  • Database service accounts — used for application-to-database connections, frequently with far broader read/write scope than any individual feature requires.
  • Scheduled task / batch job accounts — used for unattended automation that runs on a timer rather than in response to a human action.
  • Cross-application integration accounts — used for system-to-system data exchange, where one platform pulls or pushes data into another on an ongoing basis.

The Ownership Problem

Service accounts frequently have no clear human owner. They're created by an engineer solving an immediate problem, that engineer changes teams or leaves the company within a year or two, and the account is documented nowhere except possibly a long-forgotten ticket. The systems that depend on it keep running — which is precisely why nobody notices the ownership gap until a security review or an incident forces the question.

Service Account Governance Architecture

A mature service account program rests on four architectural controls:

  • Mandatory ownership assignment at creation — a human owner is recorded even though the account itself isn't human.
  • Naming conventions that encode purpose and owner — svc-paymentapp-dbconn tells a reviewer something useful; svc1234 tells them nothing.
  • Regular certification — the Module 09 access-review pattern applied to non-human identities: does this service account still need this access?
  • Decommissioning triggers tied to application lifecycle, not human lifecycle — when the application retires, the account should retire with it.

Risk scoring gives this program a way to prioritize: permissions scope, password age, number of systems with access to the credential, and whether any MFA-equivalent control (such as certificate-based authentication) exists all push a given account toward higher or lower risk. Saviynt's service account governance capabilities treat service accounts as a distinct entitlement category with their own certification workflow, separate from — but parallel to — human access reviews. The hardest detection problem in this space is the orphaned service account: one whose creating engineer has left and whose purpose is undocumented, hiding in plain sight as a working credential nobody questions because it still functions.

🟢 Architect's Take

Mandatory ownership assignment is the single highest-leverage governance control for service accounts. A service account without a human owner cannot be meaningfully certified — there's no one to ask "is this still needed?" The architectural fix: make owner assignment a hard requirement at creation time, enforced by the IGA workflow (Saviynt should refuse to provision a service account without an owner field populated), and build a quarterly process to identify and remediate orphaned accounts — no owner, or an owner who has left the company per the HR feed. This single control transforms service accounts from ungoverned infrastructure into governed entitlements.

🟢 Analogy — CODEOWNERS for Identities

Mandatory service account ownership is the identity-governance equivalent of a CODEOWNERS file in a git repository. A CODEOWNERS file assigns a named human reviewer to a directory of code so that every change has someone accountable to approve it — without it, pull requests pile up with no obvious owner to ask. A service account's owner field plays exactly the same role for an identity that nobody else thinks to claim: it gives a certification campaign, an incident responder, or an auditor someone concrete to ask "does this still need this access?" instead of an empty field and a guess.

🟣 Deep dive: What is gMSA, and what are its limitations?

A Group Managed Service Account (gMSA) is an Active Directory object designed to eliminate manual service account password management. Instead of a human-set password that a domain admin must remember to rotate, the domain controller generates a 240-byte, cryptographically random password automatically, stores it in the msDS-ManagedPassword attribute, and rotates it on a configurable interval (30 days by default) without any human intervention. Authorized member computers — servers explicitly added to a security group permitted to retrieve the password — fetch the current value transparently through the Windows authentication stack, so a Windows service can run as a gMSA without anyone ever typing or storing its password.

The architectural limitations matter as much as the benefit. gMSA password retrieval relies on the KDS Root Key, generated within a single AD forest, which means gMSAs don't natively cross forest trust boundaries without additional configuration, and they offer no benefit at all to non-Windows workloads — a Linux container or a cloud-native service gains nothing from gMSA, since the entire mechanism is built into the Windows authentication stack. For those workloads, the equivalent architectural goal — eliminating static, manually-rotated credentials — is achieved through different mechanisms entirely: CyberArk-managed rotation for traditional service accounts, or workload identity federation (Section 11.5) for cloud-native ones. gMSA solves the Windows-domain slice of the service account credential problem extremely well; it isn't a universal answer.

Use Case

A quarterly service account audit finds 1,400 AD service accounts. 600 have no documented owner. 200 have passwords older than 1,000 days. 80 are members of Domain Admins. The application teams that created many of these accounts no longer exist — reorganized or outsourced. Design the 6-month remediation architecture: how do you identify which accounts are still in use, assign ownership, and safely decommission the rest without breaking production systems?

🧪 Lab — Service Account Spot-Check

Pull a list of service accounts in your AD environment (accounts with an "svc" prefix, accounts excluded from password expiry policy, or accounts in a designated Service-Accounts OU). For five of them: can you identify the owner? The purpose? The last password rotation date? The systems that use it? Each "I don't know" is a governance gap in your service account program.

11.3

🔑 Application & API Identities

Section 11.2 covered identities applications use to reach other systems. This section covers identities applications present when they are the thing being authenticated — the identity an application establishes when it acts as an OAuth client, or when it calls an API as itself rather than on behalf of a service account elsewhere in the stack.

OAuth Client Identities

Revisit Module 03's OAuth roles: the application identity established at client registration — a client_id paired with a client_secret or certificate — is the architectural foundation here. Every OAuth client registration is, in effect, an application identity record: who owns this client, what scopes can it request, what's its purpose.

API Keys: Simpler, and Architecturally Weaker

API keys differ from OAuth tokens in ways that matter architecturally. They're simpler to issue and simpler to use — a single static string passed in a header or query string — but they typically carry no expiry by default, no scope enforcement without custom application logic, and they're leak-prone precisely because of how casually they're handled. Where an OAuth access token is short-lived by protocol design (Module 03), an API key is often architected as a permanent credential unless the issuing platform deliberately builds in expiry.

API Key Sprawl and Lifecycle

API key sprawl mirrors the SSH key sprawl problem from Module 07: keys get issued to partners, internal teams, and third-party integrations, with no central inventory and no consistent rotation policy. Good governance treats an API key the same way Module 09 treats any other entitlement — issuance with a documented purpose and owner, scoping to the minimum required permissions, scheduled rotation, and a clean revocation path when the integration ends.

The API Gateway as Enforcement Point

API gateways (Kong, Apigee, AWS API Gateway, or PingFederate acting as an OAuth AS) are where application identity gets operationally enforced: validating the API key or OAuth bearer token presented, identifying which application is calling, enforcing rate limits per application identity, and applying the same PEP pattern from Module 08 to decide what that application identity is allowed to do.

mTLS: The Strongest Application Identity Mechanism

Mutual TLS authentication — where both client and server present certificates and verify each other cryptographically — is the strongest application identity mechanism available, because it removes the shared-secret problem entirely. There's no API key or client secret to leak; trust is established through certificate-based cryptographic proof. This connects directly to Module 12's PKI content, where certificate lifecycle management gets its full architectural treatment.

Governing Application Identities Like Privileged Identities

The same entitlement discipline from Section 11.2 applies here: an OAuth client with broad scopes, or an API key with unrestricted access, is a privileged identity and deserves the same governance rigor as any service account — an owner, a documented purpose, and a periodic review of whether its current scope is still justified.

🟣 Security — Static Keys Recreate the Password Problem

Static API keys without expiry are the credential equivalent of a password that's never rotated and never expires — a standing risk that grows every day it exists. Unlike OAuth access tokens, which are inherently short-lived by protocol design (Module 03), API keys are often architected as permanent credentials by default. If your API platform issues keys without an expiry mechanism, you've recreated the static password problem (Module 05) at the application identity layer — except often with broader scope and less monitoring than a human user account would ever have.

🟢 Analogy — Registration Discipline, Applied Everywhere

Application identity governance is exactly the OAuth client management discipline you already practice when you register a new client application with PingFederate. You assign a client_id, scope the permissions, set a redirect URI, and — critically — you know who owns that client registration. The gap most enterprises have is applying that same registration discipline to every API key and service identity, not just the ones that go through PingFederate's OAuth AS. Every application identity, regardless of which system issues its credential, deserves the same registration rigor: an owner, a documented purpose, a scope, and a rotation/expiry policy.

🟣 Deep dive: What is OAuth's mTLS-bound access token mechanism (RFC 8705)?

A standard OAuth bearer token is, as the name implies, usable by whoever bears it — if an attacker intercepts the token in transit or steals it from storage, they can replay it against the resource server with no further proof required. RFC 8705 closes this gap by cryptographically binding the access token to the client's TLS certificate at issuance time. The authorization server records a hash of the client certificate used during the token request and embeds that hash as a confirmation claim (cnf) inside the issued token.

When the token is later presented to a resource server, the resource server doesn't just validate the token's signature and expiry — it also re-establishes the mTLS connection and checks that the certificate presented on this connection matches the certificate hash bound into the token. If an attacker steals the bearer token but doesn't also possess the private key for the bound certificate, the token is useless to them: it will fail certificate-binding validation even though the token itself is perfectly valid and unexpired. This is what distinguishes mTLS-bound tokens from ordinary bearer tokens architecturally — the security property shifts from "anyone who has the token can use it" to "only the entity holding the matching private key can use it," which is exactly the proof-of-possession model that high-assurance financial and government APIs increasingly require.

🧪 Lab — Application Identity Registry Audit

Find your API gateway's client/application registry (Kong, Apigee, AWS API Gateway, or PingFederate OAuth clients). Count the registered applications. For five of them: do they have an expiry policy on their credentials? Are they scoped to only the permissions they need, or do they have broad/wildcard scopes? When was the credential last rotated? This is your application identity governance baseline.

11.4

📦 Container & Kubernetes Identity

Everything covered so far assumes an identity that lives for months or years. Containers break that assumption. A pod is created and destroyed constantly, runs at a scale traditional identity models never anticipated, and the old pattern — one long-lived credential per long-lived account — simply doesn't fit a workload that might exist for ninety seconds.

Kubernetes Service Accounts

A Kubernetes Service Account (KSA) is the built-in Kubernetes identity primitive for pods. It's conceptually similar to an AD or Linux service account — an identity a process runs as, rather than a human logs in as — but it's native to the cluster and scoped by namespace. The default behavior is the part that catches people off guard: every pod gets a service account whether anyone asks for one or not. If a pod spec doesn't specify serviceAccountName, Kubernetes silently assigns the namespace's default service account and mounts its token into the pod's filesystem.

Kubernetes RBAC

Kubernetes implements the RBAC model from Module 08 through four object types: Roles and ClusterRoles define permissions (namespace-scoped and cluster-scoped, respectively), while RoleBindings and ClusterRoleBindings attach those permissions to a service account. A service account with no RoleBinding has no permissions beyond authenticating to the API server; a service account bound to an overly broad ClusterRole can read or modify far more of the cluster than the workload running under it was ever meant to touch.

Token Architecture: Legacy vs. Bound

Early Kubernetes versions mounted long-lived JWT tokens — stored as a Kubernetes Secret, with no expiry by default and no audience restriction, meaning the token was valid against any service that trusted the cluster's signing key. The TokenRequest API and Bound Service Account Tokens replaced this with short-lived tokens (one hour by default), bound to a specific audience, and automatically rotated by the kubelet without any manual intervention — the same architectural shift Module 03 covered when OAuth moved from long-lived API keys toward short-lived, scoped access tokens.

Pod Identity for External Resources

A pod frequently needs to authenticate to something outside the cluster entirely — an S3 bucket, a managed database, an external API. Embedding a static AWS access key or database password in a container image or environment variable is a well-known anti-pattern: the image gets pushed to a registry, the credential gets baked into every layer that ever referenced it, and rotating it means rebuilding and redeploying. Section 11.5 covers the architectural fix in full: workload identity federation, which lets a Kubernetes service account assume a cloud IAM identity without any static credential ever existing.

Container Image Identity and Service Mesh Identity

Two related but distinct concepts round this out. Container image signing and provenance attestation establish a form of identity for the image itself — verifying what's running is what was built and approved, separate from the runtime identity of the pod executing it. And service mesh platforms like Istio and Linkerd go a step further than KSA tokens, assigning workloads cryptographic identity through SPIFFE/SPIRE (X.509-based SVIDs) so that every service-to-service call inside the mesh is mutually authenticated via mTLS, independent of the application code having to implement any of it.

🔵 Concept — Ephemeral Identity

Every identity model covered through Module 10 assumes the identity outlives the credential check that uses it — a human account, an AD service account, even a long-lived API key all persist independently of any single authentication event. Container identity inverts that assumption. A pod's identity is often created, used, and destroyed within the same lifetime as the workload itself, sometimes minutes apart. This is "ephemeral identity": the credential and the thing it identifies are born and retired together, which is exactly why bound, short-lived tokens (rather than long-lived Secrets) are the correct default for container-native identity — a long-lived credential attached to a short-lived workload is a mismatch that outlives its own justification.

🟣 Security — Default Auto-Mount Misconfiguration

The default service account auto-mount is one of the most common Kubernetes security misconfigurations. By default, every pod gets a token for the Kubernetes API mounted into its filesystem, whether or not the application running in that pod actually needs to call the Kubernetes API. An attacker who achieves remote code execution in any pod can read this token and use it to enumerate — or potentially escalate privileges within — the cluster, depending on what RBAC permissions the default service account has. Architectural remedy: set automountServiceAccountToken: false at the pod or service account level for any workload that doesn't need Kubernetes API access, which is most application workloads.

🟢 Analogy — The Container-Native Keytab

Kubernetes Service Accounts are the container-native equivalent of the AD service accounts and Linux keytabs you already understand from Modules 02 and 07. Just as a Linux host has a Kerberos keytab that proves its identity without a password, a pod has a KSA token that proves its identity to the Kubernetes API. Just as you'd never want every Linux host to have local admin rights by default, you don't want every pod to have broad Kubernetes API access by default. The governance discipline transfers directly: least privilege, scoped permissions, short-lived credentials, and explicit assignment rather than implicit defaults.

🟣 Deep dive: What is SPIFFE/SPIRE, and how does it relate to service mesh mTLS identity?

SPIFFE (Secure Production Identity Framework For Everyone) is an open specification for a universal workload identity format that works the same way whether a workload runs in Kubernetes, on a VM, or on bare metal — solving the problem that KSA tokens, cloud IAM roles, and on-prem certificates each have their own incompatible identity formats. Every workload gets a SPIFFE ID, a URI-formatted identifier like spiffe://example.org/payments/api, and that identity is expressed cryptographically as an SVID (SPIFFE Verifiable Identity Document) — typically an X.509 certificate, though JWT-based SVIDs also exist for non-mTLS contexts.

SPIRE is the reference implementation that issues and rotates these SVIDs. It runs a server plus a node agent on every host, and crucially, it doesn't rely on a static secret to bootstrap trust — it uses node and workload attestation, verifying properties of the runtime environment itself (which Kubernetes node a pod is running on, which AWS instance, which Unix process) to decide which SPIFFE ID a workload is entitled to receive. This is what service meshes like Istio build on: Istio's sidecar proxies fetch SVIDs from a SPIFFE-compatible identity provider and use them to establish mTLS between every service-to-service call automatically, so individual application code never has to implement certificate handling itself. The architectural payoff is portability — the same workload identity model holds whether you're running in EKS, GKE, on-prem VMware, or bare metal, which none of the platform-native mechanisms (KSA tokens, IRSA, Azure managed identities) achieve on their own.

🧪 Lab — Kubernetes Service Account Audit

If you have access to a Kubernetes cluster: run kubectl get serviceaccounts --all-namespaces to see all service accounts. Pick one namespace and check which pods use the default service account versus a custom one. Check whether automountServiceAccountToken is explicitly set. Now check the RBAC bindings for the default service account in that namespace — does it have any permissions? If yes, every pod using the default SA inherits them — that's your finding.

11.5

🔄 Workload Identity Federation

Section 11.4 ended on a problem: how does a pod, a CI/CD pipeline, or a server authenticate to a cloud provider's IAM without a static, long-lived credential embedded somewhere? Workload identity federation is the architectural answer, and it's arguably the single most consequential shift in non-human identity management of the last several years.

The Federation Pattern

The pattern is consistent across every cloud provider, even though the implementation details differ: a workload presents a token from a trusted identity provider — the Kubernetes API server's OIDC issuer, GitHub Actions' built-in OIDC issuer, or your enterprise IdP — to the cloud provider. The cloud provider validates that token against the trusted issuer's public keys, checks the claims against a pre-configured trust policy, and in exchange issues temporary, short-lived cloud credentials. No static cloud credential is ever stored anywhere in this flow.

Provider-Specific Implementations

AWS implements this as IAM Roles for Service Accounts (IRSA): an EKS cluster has a cluster-specific OIDC issuer URL, registered in AWS IAM as a trusted OIDC identity provider, and an IAM role's trust policy references a specific Kubernetes service account by name. GCP's Workload Identity does the equivalent for GKE, binding a Kubernetes service account to a GCP service account. Azure Workload Identity follows the same model for AKS using federated credentials registered against Entra ID. And GitHub Actions OIDC extends this exact pattern to CI/CD: instead of storing an AWS access key and secret as a GitHub secret, a workflow requests a short-lived OIDC token scoped to that specific repository, workflow, and branch, then exchanges it for temporary cloud credentials.

The Unifying Principle

What ties all of these together is the same Zero Standing Privilege principle from Module 10, applied to machine identity: short-lived, automatically rotated, cryptographically verified credentials issued just-in-time, replacing static long-lived secrets entirely. The trust relationship itself does the heavy lifting — the cloud provider is configured to trust a specific OIDC issuer and validates specific claims (subject, audience, and for CI/CD, often the repository and branch) before ever issuing a credential.

Diagram 11.5-A · Workload Identity Federation — Generic Flow
  1. Workload (pod / CI job) has a short-lived identity token from its native platform — a K8s service account token or a GitHub Actions OIDC token.
  2. Workload → Cloud Provider STS/Token endpoint: presents the token plus the requested role/identity.
  3. Cloud Provider: validates the token's signature against the trusted OIDC issuer's public keys.
  4. Cloud Provider: validates the claims — does the subject match the trust policy condition? Is the audience correct?
  5. Cloud Provider → Workload: issues temporary credentials (e.g. an AWS STS AssumeRoleWithWebIdentity response — short-lived access key, secret, and session token).
  6. Workload: uses the temporary credentials for cloud API calls. They expire in roughly an hour — no manual rotation needed.
No static long-lived credential exists anywhere in this flow.

🟢 Architect's Take

Workload identity federation is the single most important architectural shift in non-human identity management of the last several years, and it directly extends the JIT/Zero Standing Privilege principle from Module 10 to machine identity. The old pattern — generate a long-lived cloud access key, store it as a secret somewhere, hope it never leaks — is being systematically replaced by federation: trust an existing, already-governed identity provider (your Kubernetes cluster, your CI/CD platform) and exchange short-lived proof of that identity for short-lived cloud credentials, scoped to exactly what's needed, for exactly as long as needed. If your CI/CD pipelines still store static AWS/Azure/GCP credentials as secrets, migrating to OIDC-based workload identity federation should be a top priority on your non-human identity roadmap.

🟣 Deep dive: How does the cloud provider validate an OIDC token without a pre-shared secret?

This is the same JWKS-based validation flow from Module 03's JWT validation content, applied to an external trust relationship instead of your own IdP. When an OIDC issuer — whether that's a Kubernetes cluster's API server or GitHub's Actions platform — signs a token, it signs it using the private half of an asymmetric key pair. The issuer publishes the public half at a well-known endpoint, typically /.well-known/jwks.json, which any relying party can fetch independently. There's no shared secret to provision or rotate between the issuer and the cloud provider; the cloud provider simply needs to know which issuer URL to trust.

When AWS IAM is configured with an OIDC identity provider, it stores the issuer's URL and a thumbprint of the issuer's TLS certificate. At validation time, when a workload presents a JWT to AWS STS, AWS fetches (and caches) the issuer's JWKS, finds the public key matching the token's kid (key ID) header, and verifies the token's signature cryptographically. If the signature checks out and the token hasn't expired, AWS then evaluates the trust policy's conditions against the token's claims — the subject, audience, and any custom claims like repository or branch. Only if every condition matches does STS issue temporary credentials. The entire chain of trust rests on asymmetric cryptography and a one-time configuration step (registering the issuer and its certificate thumbprint) rather than any secret that could leak or need rotation.

Use Case

Your CI/CD platform (GitHub Actions or GitLab CI) currently stores AWS access keys as pipeline secrets for 40 different repositories, used to deploy to various AWS accounts. A security audit flags this as a critical risk: any of the 40 repos' secrets could leak and grant persistent AWS access. Design the migration to workload identity federation: what AWS IAM trust policies need to be created, how do you scope each repository's access to only its intended AWS account/resources, and what is the rollout sequence across 40 repositories without breaking deployments?

11.6

🤖 RPA Identities — Governance for Bots

Robotic Process Automation bots automate tasks the way a human would — logging into applications and operating them through the standard UI or API, but driven by automation software like UiPath, Automation Anywhere, or Blue Prism rather than a person at a keyboard. That single design choice creates a governance blind spot unlike anything else in this module.

Why RPA Identity Is Architecturally Distinct

RPA bots typically use credentials that look like human credentials — a named user account in the target application — precisely because the bot is automating what a human used to do. Either the bot reuses the same login a real employee used when the process was manual, or a dedicated "bot user" account gets created in the target application. Either way, IGA systems built around human JML often don't recognize this account as non-human at all. It has a name. It has a license seat. It logs in like a person.

RPA at Scale, and Credential Vaulting

Enterprises running hundreds of bots quickly accumulate hundreds of credential sets across multiple applications — the bot that processes invoices might need SAP access, email access, and shared drive access, all at once. The architectural fix mirrors Section 11.3's application identity governance: RPA orchestration platforms like UiPath Orchestrator and Automation Anywhere Control Room should integrate with CyberArk to retrieve bot credentials at runtime, rather than storing them inside the automation workflow itself where they'd be visible to anyone who can open the workflow definition.

Unattended vs. Attended Bots

This distinction drives most of the governance risk calculus. Unattended bots run on a schedule or trigger with no human supervision — the highest-risk category, because there's no human in the loop to notice anomalous behavior in the moment. Attended bots run alongside a human user, sharing accountability and visibility with that person, which meaningfully lowers the risk profile even though the underlying credential mechanics are similar.

RPA and Separation of Duties

This is the surprising one. If a bot has both "create payment" and "approve payment" access — the exact SoD conflict Module 08/09 taught you to flag for human users — the bot itself becomes an SoD violation. And because it's automated, that conflict isn't a theoretical risk waiting for a malicious human to exploit it; it can be triggered and exploited at machine speed, with no approval delay to catch it.

Bringing RPA into the IGA Framework

The fix is the same governance architecture Section 11.2 built for service accounts, applied to bot accounts: ownership, certification, SoD checking, and a lifecycle tied to the automation's business owner rather than to whatever human account the bot happened to inherit.

🟣 Security — Unattended Bots as an Insider-Threat Equivalent

Unattended RPA bots with broad application access and no behavioral monitoring are an underappreciated insider-threat-equivalent risk. A compromised unattended bot credential gives an attacker the same access the bot has — often broad, often privileged, often running on a schedule that makes anomalous activity hard to distinguish from normal automated behavior. Unlike a compromised human account, where unusual login times or locations can trigger Module 14's anomaly detection, a bot account's "normal" behavior pattern is already automated and scheduled — making malicious use that mimics the bot's normal pattern very hard to detect without dedicated RPA security monitoring.

🟡 Analogy — Batch Jobs, With One Critical Difference

RPA bots are architecturally similar to the batch job service accounts you've managed for years, but with one critical difference: batch jobs typically use application-specific service accounts — API or database credentials — while RPA bots frequently use named human-style user accounts because the automation literally drives the application's UI the way a person would. This means RPA bot accounts often sit in your HR-disconnected "named user" pool in target applications — invisible to JML-based governance because there's no HR record driving their lifecycle, yet visible (and exploitable) as a standard user account to anyone who obtains the credential.

Use Case

An enterprise has 230 active RPA bots automating finance, HR, and procurement processes. A security review finds: 40 bots use credentials of former employees whose accounts were never disabled because "the bot needs that login." 15 bots have both create and approve permissions in financial systems (an SoD violation). No bot credentials are in CyberArk — they're stored in the RPA platform's own credential store with weak encryption. Design the remediation architecture: how do you migrate bot credentials to proper governance, eliminate the dependency on former-employee accounts, and resolve the SoD violations without breaking the automated processes the business depends on?

11.7

📡 Device Identity Architecture

Everything so far in this module has covered identities for software — applications, workloads, bots. Device identity covers the hardware underneath: the identity assigned to a physical or virtual device itself, distinct from the identity of whoever happens to be operating it.

Device Identity Types

  • Managed endpoints — corporate laptops and desktops, issued device certificates via AD CS auto-enrollment or Intune, used for 802.1X (Module 06) and Conditional Access (Module 04) device-trust signals.
  • Mobile devices — identity established through MDM enrollment, with ongoing device compliance attestation rather than a single static credential.
  • IoT devices — sensors, badge readers, building systems — frequently shipped with weak or no cryptographic identity by design.
  • Network infrastructure devices — routers, switches, firewalls — managed through TACACS+ (Module 06).
  • OT/ICS devices — industrial control systems running legacy protocols, frequently unable to support modern identity mechanisms at all.

Device Certificates and Conditional Access

Enterprise PKI — previewed here, with full treatment in Module 12 — issues and manages the device certificates that make 802.1X, VPN authentication, and Conditional Access device-trust signals possible. Entra ID Conditional Access (Module 04) consumes the device compliance state Intune reports as one input into its access decisions, meaning device identity feeds directly into how human access policy gets evaluated: the same user credential produces a different access outcome depending on whether it's presented from a managed, compliant device or an unmanaged one.

The IoT/OT Identity Gap

Industrial and IoT devices frequently can't support certificate-based identity at all — limited compute, legacy protocols, vendor lock-in, and hardware lifecycles that can span decades all work against retrofitting modern cryptographic identity onto them. The architectural response isn't to force identity onto hardware that structurally can't support it; it's to compensate at the network layer, through segmentation and the NAC-based device profiling Module 06 introduced.

Device Lifecycle and the Two-Signal Model

Device identity follows its own three-stage lifecycle — provisioning at enrollment, ongoing attestation that re-verifies trust over time, and decommissioning (certificate revocation) when a device is retired or reported lost. None of this replaces user identity; it complements it. A compromised user credential presented from an unmanaged device is a meaningfully different risk than the same credential presented from a managed, compliant device, which is exactly why strong access architectures evaluate both signals together rather than either one alone.

🟢 Architect's Take

Treat device identity and user identity as two independent attributes feeding the same access decision, not as a single combined credential. Architecturally, this means your Conditional Access policy engine needs both signals available at evaluation time: the user's authentication result from your IdP, and the device's compliance state from Intune (or equivalent MDM/EMM tooling), evaluated together rather than the device check happening as an afterthought bolted onto a separate system. The payoff is graceful degradation — a stolen password alone isn't enough to gain full access if the device signal doesn't also check out, which is a materially stronger posture than user identity carrying the entire access decision by itself.

🟣 Security — The IoT/OT Structural Gap

IoT and OT devices represent a structural identity gap that pure software solutions cannot fully close. Many industrial control systems and IoT devices were designed with 10–20 year hardware lifecycles, predate modern identity standards, and run on constrained hardware that cannot support TLS/certificate operations at all. The architectural response is not "force identity onto these devices," which is often technically infeasible, but "compensate at the network layer" — strict network segmentation isolating OT networks from IT networks, NAC-based device fingerprinting (Module 06) to detect unauthorized devices joining the network, and monitoring for anomalous traffic patterns rather than relying on the device to prove its own identity cryptographically.

11.8

♻️ Machine Identity Lifecycle Management

Module 01's JML lifecycle works because there's a single authoritative trigger system behind it — the HR record. Machine identities have no equivalent. They're created by engineers, deployment pipelines, cloud provisioning tools, and RPA platforms, each operating independently, with no unified system that says "this identity's reason for existing has ended."

Lifecycle Stages and Their Real Triggers

  • Creation — triggered by code deployment, infrastructure provisioning (Terraform/CloudFormation), application onboarding, or RPA bot development.
  • Active use — ongoing authentication and authorization, ideally monitored for usage patterns rather than left silent.
  • Rotation — credential rotation per policy (CyberArk CPM, Module 10), certificate renewal on its own schedule.
  • Change — application architecture changes, scope changes, ownership transfer.
  • Decommission — triggered by application retirement, infrastructure teardown, or project end — and, in practice, the stage most often not triggered reliably.

The "Who Decommissions It" Problem

When an application is decommissioned, its service accounts, API keys, and cloud IAM roles routinely outlive it. No automated process ties identity decommissioning to infrastructure teardown unless someone deliberately built one — the application's servers get powered off, its database gets archived, and its identities just keep existing, valid, unmonitored, waiting for someone to either notice or exploit them.

Infrastructure as Code as the Architectural Fix

When identity is defined as part of the same Infrastructure as Code that provisions the resource it serves — an IAM role or Kubernetes service account declared in the same Terraform module as the application it supports — destroying that module destroys the identity with it. This doesn't solve the problem for identities created through manual console actions or ad-hoc scripts, which is exactly why discovery and inventory remain necessary as a compensating control: periodic discovery scans, including cloud IAM access analyzers, AD service account audits, and API gateway client inventories, catch what lifecycle automation missed.

Machine Identity Certification

Module 09's access certification model extends here too, with one structural change: certification needs an owner to certify against (Section 11.2's mandatory ownership requirement is what makes this possible at all), and the certification cadence should be tied to risk — a high-privilege, ungoverned service account warrants more frequent review than a tightly-scoped, IaC-managed one.

🟢 Architect's Take

The architectural principle that solves the machine identity lifecycle problem most effectively is coupling identity lifecycle to infrastructure lifecycle through Infrastructure as Code. When a cloud IAM role, a Kubernetes service account, or a database credential is defined in the same Terraform module as the resource it serves, destroying that module destroys the identity too — no separate manual decommissioning step exists to be forgotten. This doesn't solve the problem for identities created through manual console actions or ad-hoc scripts, which is why discovery and inventory remain necessary as a compensating control, but it dramatically reduces the orphaned-identity surface for any organization with mature IaC practices.

🟢 Analogy — Try-With-Resources, at Infrastructure Scale

IaC-coupled identity lifecycle is the infrastructure-scale equivalent of a Java try-with-resources block. Inside a try-with-resources statement, you don't have to remember to call close() on a file handle or a database connection — the language guarantees cleanup happens when the block's scope ends, regardless of how execution exits it. A Terraform module that declares an IAM role alongside the resource it serves gives you the same guarantee at infrastructure scale: the identity's "scope" is the module's lifecycle, and destroying the module destroys the identity automatically. Identities created outside that scope — through a console click, an ad-hoc script, a one-off CLI command — are the infrastructure equivalent of a raw file handle opened without a try-with-resources wrapper: it works fine until somebody forgets to close it, and now you're debugging a leak months later.

🟣 Deep dive: What is AWS IAM Access Analyzer's "unused access" feature?

IAM Access Analyzer's unused access findings address exactly the discovery/compensating-control gap this section describes. Rather than relying on someone to remember to review a role, Access Analyzer continuously evaluates IAM roles, users, and permissions across an AWS account or organization against CloudTrail activity data, and surfaces specific, actionable findings: an IAM role that hasn't been assumed in 90+ days, a permission granted to a role that has never actually been exercised by any API call the role has made, or an access key that exists but shows no recent usage.

What makes this more useful than a blunt "delete anything unused" rule is the granularity — it doesn't just flag an entire role as unused, it can flag individual unused permissions within an otherwise active role, which is the more common real-world case: a service account that's genuinely still needed, but was granted broader permissions than it has ever exercised. That distinction matters architecturally because it turns a binary "keep or delete" decision into a least-privilege tightening exercise, which is exactly the kind of finding a non-human identity governance program (Section 11.9) should be routing into a recurring remediation workflow rather than a one-time cleanup project.

Its API keys revoked? Its cloud IAM roles deleted? Its Kubernetes service accounts removed? 11.9

🏛️ Non-Human Identity Governance Framework

This closing section synthesizes everything the module has covered — service accounts, application identities, container/K8s identities, workload federation, RPA, and devices — into a single practical governance model.

The Five Pillars

  1. Inventory — you cannot govern what you cannot see. A continuously updated inventory across every non-human identity type is the foundation everything else depends on.
  2. Ownership — every non-human identity has an accountable human owner, enforced at creation, not retrofitted after the fact.
  3. Least Privilege — scoped permissions, not broad defaults, applying the Module 01/08 principles to machines as rigorously as to humans.
  4. Lifecycle — credential rotation, certificate renewal, and, critically, decommissioning tied to infrastructure or application lifecycle rather than left to memory.
  5. Monitoring — a behavioral baseline and anomaly detection for machine identities, parallel to what Module 14 covers for human identities.

Where IGA Platforms Are Heading

Platforms like Saviynt are evolving to treat non-human identities as first-class governed entities in their own right, not a human-centric workflow with a service-account checkbox bolted on. That shift matters because it changes the default: instead of non-human identity governance being an opt-in add-on a program might get to eventually, it becomes part of the same certification, ownership, and lifecycle machinery already built for humans.

Organizational Ownership

Who should own this program — security, the IAM team, or platform engineering? In practice, the strongest programs share ownership with clear accountability boundaries: platform engineering owns the IaC patterns and tooling that make identities easy to create correctly, the IAM/IGA team owns the certification and ownership workflow, and security owns monitoring and incident response. No single team can own all five pillars alone, because the pillars span disciplines that have historically reported to different parts of the organization.

🔵 Concept — Why the Boundaries Are Blurring

PAM, secrets management, and IGA grew up as separate disciplines because they solved separate problems for humans: PAM vaulted privileged credentials, secrets management handled application configuration, and IGA governed who-has-access-to-what. Non-human identities don't respect those boundaries. A single Kubernetes service account touches all three — it needs a vaulted, rotated credential (PAM), it's retrieved as a runtime secret by the workload (secrets management), and it needs an owner and a certification cycle (IGA). That overlap is precisely why this category has been historically under-governed: each discipline assumed the others were covering the gaps non-human identity actually falls into.

🟡 Cost — No Single Product Solves This

Non-human identity governance cannot be solved with a single product purchase — it requires a framework that spans PAM, secrets management, and IGA simultaneously, applied consistently across service accounts, application identities, container workloads, workload federation, RPA bots, and devices. Enterprises that treat this as "buy CyberArk and we're done" miss the IGA ownership/certification dimension. Enterprises that treat it as "buy a secrets manager and we're done" miss the lifecycle/decommissioning dimension. The architecture requires all five pillars working together, with clear organizational ownership of the cross-cutting program — not just the individual tools.

Use Case

Your CISO asks you to present a 12-month non-human identity governance roadmap to the board's risk committee. Using the five-pillar framework, prioritize the roadmap: what gets addressed in the first 90 days, what in months 4–9, what in months 10–12, and what is the measurable outcome for each phase?

🗂️ Real-World Scenario — The Non-Human Identity Discovery Project

Situation

A 15,000-employee enterprise completes its first comprehensive non-human identity discovery. The numbers, once finally assembled, tell their own story:

CategoryCount
AD service accounts (estimated — no prior central count existed)2,100
Cloud IAM roles/service accounts across AWS, Azure, and GCP890
Kubernetes service accounts across 15 clusters1,200+
API keys issued through various platforms (no single registry)450
RPA bots180
Human employee count (reference)15,000

Non-human-to-human ratio: approximately 3.2 : 1 — and that's almost certainly an undercount, since several categories were estimated rather than exhaustively enumerated.

Discovery Methodology

No category had a clean source of truth. AD service accounts were pulled via LDAP queries cross-referenced against accounts excluded from password-expiry policy and accounts sitting in a designated Service-Accounts OU — three overlapping but imperfect signals that had to be reconciled by hand. Cloud IAM identities were enumerated using each provider's native tooling (AWS IAM Access Analyzer across all member accounts via AWS Organizations, Azure Resource Graph, GCP Asset Inventory) and merged into a single spreadsheet, since no cross-cloud inventory tool was already in place. Kubernetes service accounts were visible per-cluster but had never been aggregated across all 15 clusters until this project forced the question. API keys were the hardest category: there was no central registry at all, and the count came from manually surveying each platform team about what they'd issued. RPA bot counts came directly from the Orchestrator and Control Room consoles. The entire discovery exercise took six to eight weeks — longer than the team expected — precisely because assembling a single inventory meant reconciling five categories that had never been asked to talk to each other.

Risk Prioritization

Plotted against the five-pillar risk matrix from Section 11.9, three clusters of risk stood out as Critical — high privilege, ungoverned: the roughly 600 unowned AD service accounts with no certification history, the 40 RPA bots running on former-employee credentials with two confirmed SoD violations in financial systems, and the default RBAC bindings across the Kubernetes footprint, which had never been individually reviewed across 200+ namespaces. Cloud IAM roles split more evenly between governed and ungoverned, since the more recently provisioned ones tended to follow IaC patterns, while older, console-created roles did not.

90-Day Quick Wins

The first ninety days focused on stopping further accumulation rather than fully remediating the backlog: mandatory ownership became a hard requirement for any newly created service account, API key, or RPA bot account; automountServiceAccountToken: false was rolled out across Kubernetes namespaces that didn't need API access; the highest-risk RPA bots were migrated off former-employee credentials and onto dedicated, CyberArk-vaulted bot accounts; and the five highest-traffic CI/CD pipelines began migrating from static cloud credentials to OIDC-based workload identity federation.

12-Month Target Architecture

By month twelve, the goal was a working five-pillar program rather than a one-time cleanup: a unified non-human identity inventory aggregating all five categories into a single Saviynt-fed system of record, ownership coverage above 90% across AD service accounts and API keys, IaC-coupled lifecycle as the default pattern for all newly created cloud IAM roles, full OIDC federation across CI/CD pipelines with no remaining static credentials in pipeline secrets, RPA bot governance folded into the standard IGA certification cycle, and device certificate coverage extended to the remaining gaps identified during discovery.

Ongoing Governance Model

The program settles into a recurring cadence rather than a project with an end date: quarterly certification campaigns spanning every non-human identity category, shared ownership split across platform engineering (IaC patterns and tooling), the IAM/IGA team (certification and ownership workflow), and security (monitoring and incident response), and a monthly risk-register review where newly discovered unused-access findings — the same kind Section 11.8's deep dive covered — get triaged and routed into remediation before they become next year's discovery surprise.
