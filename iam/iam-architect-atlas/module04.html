Architecture Lens

You've logged more hours in PingFederate's admin console than most people have in their entire IAM career. You know where the settings are. This module teaches you something different: how PingFederate works as an architectural system, why it's designed the way it is, how to position it in an enterprise identity ecosystem, and how to design with the Ping stack rather than just operate it. When a CISO asks "why PingFederate instead of Okta?" or "how does our Ping deployment scale to 50,000 users?" — this module is where those answers come from.

4.1

The Ping Identity Stack: Platform Architecture

Before you can architect with the Ping platform, you need a precise mental model of what each product does — and what it deliberately does not do. Many engineers who work with these products daily carry an implicit mental model that conflates their responsibilities. That conflation is harmless when you're configuring an existing deployment. It becomes costly when you're designing a new one.

The Three Products and Their Architectural Roles

PingFederate is the federation and protocol engine. It speaks SAML, OIDC, OAuth 2.0, and WS-Federation. It authenticates users (via adapters), applies authentication policy, builds identity assertions, and delivers them to applications. PingFederate does not store identity data persistently — it reads from external stores. It does not manage user lifecycle — that's IGA. It does not enforce access policy at the resource level — that's PingAccess or a separate authorization layer. PingFederate's job is the authentication handshake: accept a request for identity, verify the user, assert who they are.

PingDirectory is the identity data platform. It stores user entries, credentials, group memberships, consent records, and application-specific profile attributes. It exposes this data via LDAP (to PingFederate and legacy systems), REST/SCIM (to modern applications and IGA), and its own proprietary DS HTTP API. PingDirectory does not authenticate users to applications — PingFederate does that. PingDirectory's job is to be the authoritative identity data source and serve it reliably at high throughput.

PingID is the MFA and adaptive authentication engine. It provides the second factor — push notification, TOTP, biometric, security key — and the risk intelligence layer that decides when a second factor is needed at all. PingID integrates into PingFederate as an authentication adapter. PingID does not store user profiles — it relies on PingDirectory for that. PingID's job is to answer two questions: Can we trust this authentication attempt? and What additional verification is needed?

The relationship between the three products maps cleanly onto a layered concern model: PingDirectory owns who you are (identity data). PingFederate owns proving who you are (authentication orchestration). PingID owns how much we trust this proof (risk and MFA).

PingOne: The Cloud Umbrella

PingOne is Ping Identity's cloud platform — the SaaS delivery layer for Ping's capabilities. Understanding where PingOne fits is important because the naming creates confusion: PingOne is not a fourth product alongside PingFederate, PingDirectory, and PingID. It's the cloud infrastructure that hosts cloud-native versions of those capabilities and provides the coordination layer for PingID's cloud operations.

When PingFederate invokes PingID for an MFA challenge, it makes an API call to PingOne cloud. PingOne handles device enrollment records, push delivery, and risk signal aggregation. The on-premises PingFederate and PingDirectory you operate daily depend on PingOne for the MFA flow — which means you have a cloud dependency even in what feels like a fully on-premises deployment.

Ping also offers cloud-native counterparts: PingFederate as a service inside PingOne, and PingDirectory as a service (PingOne Advanced Identity Cloud, based on the ForgeRock acquisition). These are distinct from the self-hosted products. For enterprises doing net-new deployments in 2025, the cloud-native path is increasingly viable. For enterprises with existing on-premises Ping deployments, the hybrid model — on-premises PingFederate and PingDirectory, cloud PingID via PingOne — is the operational reality.

Diagram 2 — Ping vs. Okta vs. Entra ID: Market Positioning Map

Ping's Architectural Philosophy

The single most important framing for working with Ping architecturally is this: PingFederate is a platform you build an IAM architecture on, not a SaaS product you subscribe to. This distinction has cascading implications for how you design, operate, and evolve a Ping deployment.

Okta's philosophy is the opposite: opinionated defaults, managed infrastructure, fast time-to-value. An Okta deployment's complexity ceiling is lower than PingFederate's — but so is its floor. You can get Okta SSO working for 50 applications in days. You cannot necessarily implement the same complex multi-source attribute enrichment, custom authentication adapter, or protocol translation that PingFederate handles natively.

Entra ID is a third pattern: it is highly capable within the Microsoft ecosystem and increasingly capable outside it, but its architectural philosophy is Microsoft-first. Applications designed around Entra ID get excellent native integration for M365, Azure, and the Microsoft portfolio. Applications outside that ecosystem get federation that works but isn't optimized.

💡 Core Architectural Concept

Ping's architectural philosophy: PingFederate is designed for enterprises that need maximum control over their federation topology, protocol support, and policy configuration. It's a platform to build an IAM architecture on, not a SaaS product you subscribe to. This makes it the right choice for large enterprises with complex requirements and dedicated IAM engineering teams — and a mismatch for companies that want a simple, pre-configured identity service.

4.2

PingFederate: Federation Engine Architecture

PingFederate is a Java application. Architecturally, it is a stateful request-processing engine wrapped around a plugin framework. Understanding its internal structure lets you reason about why it behaves the way it does under load, during failures, and when you need to extend it.

The Connection Model

PingFederate organizes every integration as a connection. An IdP connection (Identity Provider connection) represents an upstream identity source — another IdP that PingFederate trusts as an authentication authority. An SP connection (Service Provider connection) represents a downstream application that PingFederate serves identity assertions to. Every SAML partner, every OIDC client, every OAuth resource server is a connection in PingFederate's configuration.

This connection model is the unit of configuration granularity. Per-connection, you configure: which adapters are invoked for authentication, what attributes are mapped into the assertion, which token format is used (SAML assertion, JWT, opaque reference token), and what signing certificate signs the assertion. The connection model means you can have 120 SP connections, each with different attribute contracts, different signing keys, and different authentication requirements — all managed independently without one affecting another.

The Adapter Framework

Adapters are how PingFederate authenticates users. An adapter is a plugin that handles a specific authentication mechanism. The platform ships with several built-in adapters:

The HTML Form Adapter presents a login form and validates credentials via an LDAP bind to PingDirectory (or any configured LDAP server). This is the primary first-factor adapter in most enterprise deployments. The Kerberos Adapter performs Windows Integrated Authentication — transparent SSO for domain-joined machines inside the corporate network. The PingID Adapter invokes PingOne cloud for MFA — this is how PingID enters the authentication flow. The RADIUS Adapter delegates authentication to a RADIUS server — important for network device authentication scenarios. The Certificate Adapter validates client certificates for PKI-based authentication.

Adapters are not mutually exclusive. PingFederate's authentication policy system allows you to chain adapters: first the HTML Form Adapter (primary auth), then the PingID Adapter (MFA), with conditional logic determining when the chain is invoked. The adapter framework is also extensible — you can write custom adapters in Java using the PingFederate SDK, which becomes important in Section 4.8.

The Attribute Contract

The attribute contract is one of PingFederate's most architecturally significant concepts. Every SP connection has an attribute contract: a configured mapping that defines (a) what attributes will be included in the assertion delivered to this SP, (b) where each attribute's value comes from, and (c) what name the attribute will have in the assertion.

The attribute contract is the decoupling layer between your internal identity data model and the external claim model that applications expect. Your LDAP schema in PingDirectory uses attributes named uid, mail, memberOf, departmentNumber. Your SP applications expect claims named username, email, groups, costCenter. The attribute contract performs this translation. It also allows you to pull attributes from multiple sources — PingDirectory for core identity attributes, a JDBC database for application-specific data, or even static values configured in the connection — and present them all in a single assertion.

Token Generators and the Authentication Policy Tree

After the authentication adapters have run and the attribute contract has been assembled, PingFederate's token generator takes over. The token generator is the component responsible for producing the output assertion — a SAML 2.0 Assertion, a JWT, or an opaque token — that will be delivered to the SP. Per SP connection, you configure which token generator is used and what format/signing parameters apply.

PingFederate's authentication policy system is more sophisticated than a simple adapter chain. The authentication policy tree allows you to configure branching logic: if the user belongs to a certain group, require PingID. If the request comes from an internal IP range, skip MFA. If the SP connection has a high-risk classification, always require hardware key. The policy tree is evaluated at request time against the authenticated session context, and it drives which adapters are invoked and in what order.

The distinction between a simple adapter sequence (adapter A then adapter B) and a policy tree (if condition X invoke adapter B, else invoke adapter C) matters architecturally when you have diverse application populations with different authentication requirements. A flat adapter sequence forces all applications into the same authentication experience. A policy tree lets you apply appropriate authentication based on the application, the user, the device, and the network context — simultaneously, with zero user-visible difference in the infrastructure.

🟢 Architect's Insight — The Attribute Contract as a Decoupling Layer

The attribute contract is where IAM engineering meets IAM architecture. Most engineers know how to configure an attribute mapping in PingFederate — but architects understand why the mapping exists as a layer: it decouples the internal identity data model (LDAP attributes in PingDirectory) from the external claim model (what SPs expect in assertions).

Changing your directory schema doesn't require reconfiguring every SP connection — only the attribute contract. This is the single-point-of-change pattern. If you ever need to rename the LDAP attribute that stores department from departmentNumber to ou, you update one attribute source mapping, not 120 SP connections. When designing new PingFederate integrations, think attribute contract first.

🟣 Deep Dive

Authentication policy tree vs. simple adapter configuration: A simple authentication chain is appropriate when all SP connections share the same authentication requirements — primary factor, then MFA, done. A policy tree becomes necessary the moment you have heterogeneous requirements: some SPs require MFA, some don't; some users require step-up for sensitive operations; some network origins are trusted. If your PingFederate deployment has 50+ SP connections with varying security requirements and you're using a single flat adapter chain for all of them, you're either over-authenticating low-risk flows or under-authenticating high-risk ones. The policy tree is the architectural tool for resolving that.

🔷 Use Case: Multi-Source Attribute Assertion
A new enterprise application needs to receive a SAML assertion containing the user's email, their manager's email (sourced from AD), their Workday cost center code (sourced from HR system via SCIM sync into PingDirectory), and their PingID risk score. The PingFederate architecture to deliver this: (1) HTML Form Adapter authenticates against PingDirectory. (2) PingID Adapter performs MFA and returns a risk score. (3) The attribute contract for this SP connection defines four attribute sources — PingDirectory LDAP for email, a second LDAP query for manager DN lookup, PingDirectory again for the Workday-synced cost center attribute, and the PingID adapter context for risk score. (4) The token generator assembles the multi-source assertion and signs it. Each source is independently queried at assertion-build time. The SP sees a clean, normalized assertion with no knowledge of where each value originated.

4.3

PingFederate Deployment Topologies

How you deploy PingFederate is as architecturally significant as how you configure it. A misconfigured PingFederate can be fixed with a configuration change. A misdeployed PingFederate creates operational risk that persists until the topology is redesigned. This section translates PingFederate's deployment options into their architectural trade-offs.

Single-Node Deployment

A single PingFederate node is appropriate for development and test environments. It is never appropriate for production. The failure domain of a single node is total: if the node goes down, all SSO fails. If the node needs a restart for a configuration change or software update, all in-flight SSO sessions are lost. There is no certificate of reasonable production intent for a single-node PingFederate deployment. The moment you have even one production application behind PingFederate, you need a cluster.

Clustered Deployment Architecture

PingFederate's clustering model separates two roles: engine nodes and the console node. Engine nodes process authentication requests — they are the nodes your users and applications actually talk to. The console node runs the admin UI and is used only by administrators. In production, these must be separated.

Why separate them? Because the admin console shares the JVM with the federation engine in a non-separated deployment. An administrator performing a configuration export, a bulk import, or a JVM-heavy operation on the console can degrade the request-processing performance of the engine. Separating the console node means admin operations cannot affect production request processing. The console node does not handle user authentication traffic and should not be reachable from the internet or user network segments.

Within the cluster, PingFederate engine nodes share configuration (SP connections, IdP connections, adapter configurations, authentication policies — everything you configure in the admin console is replicated to all engine nodes). What is not shared between nodes is the in-memory session state for in-flight authentication requests. This is why load balancer session affinity (sticky sessions) matters: a user who starts a SAML SSO flow on engine node 1 must be directed back to engine node 1 for the response leg. If the load balancer routes them to engine node 2, PingFederate can't find the in-flight session context and the authentication fails.

Diagram 5 — PingFederate HA Deployment Topology

Multi-Region Architecture

Multi-region PingFederate deployments introduce a fundamental question: should the identity platform follow users to each region, or should authentication traffic traverse to a central region? The answer depends on latency tolerance, data residency requirements, and organizational appetite for operational complexity.

The typical multi-region pattern deploys independent PingFederate engine node clusters per region, all running identical configuration. Configuration is replicated through the deployment pipeline (GitOps or manual sync from the console node) rather than through PingFederate's native clustering (which is not designed for WAN-latency replication). PingDirectory replication, by contrast, is designed for WAN distances and replicates user data bidirectionally across regions. PingID remains a cloud service and is inherently region-agnostic — both regional PingFederate clusters make HTTPS calls to the same PingOne endpoint.

Diagram 6 — Multi-Region PingFederate Architecture

Certificate Management — The Silent Outage Risk

PingFederate uses cryptographic certificates for three distinct purposes that each carry their own expiry risk: signing certificates (used to sign SAML assertions and OIDC tokens), SSL/TLS certificates (securing the HTTPS endpoint), and encryption certificates (for encrypting assertions to SPs that require it).

The signing certificate expiry scenario is categorically different from other outage types because the blast radius is total and the symptom is delayed. When a signing certificate expires, PingFederate continues to generate and sign assertions — with an expired certificate. The SP's signature validation rejects the expired certificate. Every application verifying signatures (which is all of them, if properly configured) immediately fails to accept assertions. The result is a complete SSO outage across all PingFederate-backed applications simultaneously, with no PingFederate errors visible in logs (PingFederate signed successfully — the SP rejected it).

🔴 Security & Availability Risk: Certificate Expiry

PingFederate signing certificate expiry is a category-5 incident waiting to happen. When the signing certificate expires, every SP that validates signatures rejects your assertions — resulting in total SSO outage for all PingFederate-backed applications simultaneously. Certificate rotation must be planned months in advance, tested in non-production, and coordinated with all SP administrators. Build a certificate expiry calendar and alert on 90-day, 60-day, and 30-day thresholds. If you do not have this calendar today, that is the most urgent operational gap from this module.

🟣 Deep Dive

Session management in a clustered deployment: PingFederate stores in-flight SSO session state in the JVM memory of the engine node handling the request. This is why sticky sessions on the load balancer are mandatory — not optional. Without stickiness, the response leg of an authentication flow (the POST back from the IdP after credential verification) arrives at a node with no knowledge of the initial request context, and the flow fails. For session resumption (existing authenticated sessions), PingFederate can use a distributed session cache (JDBC or similar) allowing any node to validate an existing session token. The in-flight vs. established-session distinction is architecturally important: you need sticky sessions for in-flight flows regardless of whether you have a distributed session cache for established sessions.

4.4

PingDirectory: Identity Platform Architecture

Module 02 introduced PingDirectory as an LDAP directory. This section treats it as what it actually is in a mature deployment: an identity platform that happens to speak LDAP as one of its protocols. Understanding PingDirectory architecturally means understanding what distinguishes it from commodity LDAP servers — and why those distinctions matter for how you design with it.

What Distinguishes PingDirectory from Standard LDAP

Every LDAP server supports the core LDAP protocol: search, add, modify, delete, bind. What PingDirectory adds is a set of capabilities that make it suitable as the central identity data platform for a modern enterprise, rather than just a credential store for legacy applications.

The REST API (DS HTTP API) exposes the directory's data via a standards-based HTTP interface, enabling modern applications to read and write identity data without implementing an LDAP client. This is how you integrate cloud-native applications with PingDirectory — they call the REST API, not raw LDAP. The SCIM 2.0 server capability allows IGA platforms like Saviynt to provision users directly to PingDirectory using the SCIM protocol, without building custom LDAP provisioning logic. The consent management capability stores GDPR consent records and enforces consent policy — when a user has not consented to data sharing with a particular application, PingDirectory can enforce that at the attribute retrieval layer. The PingDirectory Sync Server is a separate component that maintains bidirectional synchronization between PingDirectory and other directories (Active Directory, LDAP servers) — keeping identity data consistent across sources without manual reconciliation.

Replication Architecture

PingDirectory uses a multi-master replication model: every node in the replication topology is a writable master. There is no single-master bottleneck. Writes to any node are replicated to all other nodes. This matters for read-write latency in multi-region deployments — applications in Region B can write to their local PingDirectory node and have the change replicated to Region A asynchronously, rather than requiring a round-trip to a remote master for every write.

Replication conflict resolution handles the case where the same entry is modified on two different nodes before replication completes (a split-brain scenario). PingDirectory uses last-write-wins resolution based on the change sequence number — the modification with the higher change sequence number wins. For most identity attributes (email address changes, group membership updates), this is acceptable. For password changes, PingDirectory applies additional logic to prevent credential reset races. Understanding the conflict resolution model is important when designing high-frequency provisioning workflows that write to PingDirectory replicas concurrently.

Diagram 7 — PingDirectory Multi-Master Replication Topology

Access Control Instructions (ACIs)

PingDirectory's access control system uses Access Control Instructions (ACIs), stored as directory attributes on entries or subtrees. An ACI defines: who the subject is (a user DN, a group, an IP range, an anonymous bind), what operation they can perform (read, write, add, delete, compare), and on which attributes or entries. ACIs are inherited — an ACI on a parent entry applies to all child entries unless overridden.

The ACI model is powerful but requires careful design. The two common failure modes are: (1) overly broad ACIs that grant a service account read access to all attributes of all entries — a Least Privilege violation that exposes sensitive data unnecessarily, and (2) ACIs that are so granular they become unmaintainable, leading to administrators making them broader to stop debugging them. Architect your ACI model per consumer: the PingFederate service account gets read access to the attributes PingFederate actually needs for authentication and the attribute contract. The Saviynt SCIM service account gets write access to provisioned attributes only. The audit logging service gets read-only access to operational attributes.

Diagram 8 — PingDirectory Integration Architecture
🟢 Architect's Insight — ACIs as Directory-Layer Least Privilege

PingDirectory's ACIs are the directory-layer enforcement of the Least Privilege principle introduced in Module 01. An ACI defines who can read which attributes of which entries. If your PingFederate service account ACI grants read access to every attribute of every user entry — including password hashes, personal data, and sensitive HR attributes — that's a Least Privilege violation at the directory layer.

The correct model: each consumer gets an ACI scoped to exactly the attributes its function requires. PingFederate needs mail, uid, memberOf, department — and nothing else. Saviynt needs write access to provisioned attributes, not read access to passwords. This is an architectural constraint, not a configuration optimization — it belongs in your IAM design documentation, not as a post-hoc tightening exercise.

4.5

PingID: Adaptive MFA Architecture

PingID is not just a second-factor checkbox. Architecturally, it is a risk-aware authentication intelligence layer that plugs into PingFederate's policy engine. Understanding how it works — and where it fails — determines whether your MFA deployment actually increases security or merely increases friction.

PingID's Position in the Authentication Flow

PingID enters the PingFederate authentication flow as an adapter. When the authentication policy tree specifies that MFA is required for a given flow, PingFederate invokes the PingID adapter after primary authentication succeeds. The PingID adapter makes an API call to PingOne cloud, which coordinates the MFA challenge and collects the risk signals. The user's registered device receives a push notification (or the user provides TOTP, biometric, or security key input). PingOne returns the authentication result and a risk score to PingFederate, which uses both to make the final access decision.

The key architectural point: PingID is a cloud service. Even if your PingFederate and PingDirectory are entirely on-premises, PingID requires HTTPS connectivity to PingOne cloud. If that connectivity is broken — network outage, firewall change, PingOne availability event — PingID MFA becomes unavailable. Whether that causes a fail-open (users bypass MFA) or fail-closed (users are blocked) depends on your authentication policy configuration. This is a critical failure mode to test before it happens in production.

PingID Authentication Factors

Push notification is the default and highest-usability factor: the user taps Approve on the PingID mobile app. TOTP/HOTP provides a time-based or counter-based one-time password via the authenticator app — works offline, no push infrastructure required. Biometric (Face ID, fingerprint) uses the device's platform biometric to authorize the PingID approval — the biometric verification happens on-device, with the result reported to PingOne. Security key (FIDO2) provides phishing-resistant hardware authentication — highest security, requires FIDO2-compatible hardware. SMS and email OTP are available as fallback factors — lower security due to SIM swapping and email compromise risks, but important for users without smartphones.

Adaptive Authentication: The Risk Engine

PingID's adaptive authentication evaluates a set of risk signals on every authentication attempt and computes a risk score. The score drives authentication policy decisions: low-risk flows proceed with reduced friction; high-risk flows receive step-up challenges or are blocked.

🔴 Security Risk: MFA Bypass via RADIUS

A common architecture mistake is to enforce PingID MFA on web SSO flows through PingFederate, while leaving the VPN RADIUS endpoint using only password authentication. An attacker who obtains credentials can bypass web MFA entirely by authenticating to VPN instead of the web portal. The architecture requirement: MFA must be enforced at every authentication endpoint — web, VPN, SSH, and any other access pathway. PingID's RADIUS integration addresses this, but it must be explicitly configured and enforced. "We have MFA" and "MFA is enforced everywhere" are not the same statement — audit the gap.

💡 Analogy — Adaptive Authentication as Fraud Detection

PingID's adaptive authentication is the same pattern as a fraud detection system for financial transactions. Your bank doesn't ask for OTP on every $5 coffee purchase — it evaluates risk signals (merchant, location, amount, history) and only interrupts high-risk transactions. PingID does the same for authentication: low-risk sign-ins (same device, same office, same time of day) flow through silently; high-risk sign-ins (new device, foreign country, 2am) trigger a step-up challenge.

The user experience improves and security increases simultaneously — which is why adaptive authentication replaced blanket MFA-on-every-login approaches. Blanket MFA creates alert fatigue; adaptive MFA creates signal. Alert fatigue leads to users approving push notifications without verifying them (MFA fatigue attacks). Risk-based step-up means every MFA prompt is meaningful, which means users are more likely to scrutinize and deny unexpected prompts.

4.6

Ping Stack Integration Architecture

Understanding each Ping product in isolation is necessary but not sufficient. The operational reality is a platform where PingFederate, PingDirectory, and PingID have dependencies on each other — and where the failure of any component propagates in specific ways through the others. Designing with the Ping stack means designing for these dependencies explicitly.

The Integration Architecture in Detail

The integration points between Ping products follow distinct protocols and carry different operational dependencies. PingFederate → PingDirectory uses LDAP/LDAPS on port 636 for both credential validation (the LDAP bind in the HTML Form Adapter) and attribute retrieval (the data store queries in the attribute contract). This is synchronous and on the critical path of every authentication request — a PingDirectory outage directly causes PingFederate authentication failures. PingFederate → PingID/PingOne uses HTTPS REST calls to PingOne cloud endpoints. This is also on the critical path for flows requiring MFA. PingDirectory ← Active Directory runs through the PingDirectory Sync Server, which maintains a near-real-time bidirectional sync. PingDirectory ← Saviynt uses SCIM 2.0 for provisioning writes triggered by JML events. PingDirectory ↔ PingDirectory replicas uses PingDirectory's proprietary replication protocol over dedicated replication ports.

Failure Impact Analysis

Every integration point is a potential failure domain. The discipline of failure impact analysis — systematically asking "what happens if this connection fails?" for every integration arrow in your architecture diagram — is what separates a resilient Ping deployment from one that fails in unpredictable ways during incidents.

Diagram 12 — Ping Stack Failure Impact Analysis
⚠️ Architecture Practice — Fail-Open vs. Fail-Closed Decisions

For every Ping integration point, ask: what happens if this connection fails? Does it fail open (users get through without full authentication — security risk) or fail closed (users are blocked — availability risk)? PingFederate's behavior when PingDirectory is unreachable is a configuration choice — and the default behavior may not match your security policy. Similarly, when PingOne is unreachable, whether PingFederate bypasses MFA or blocks users depends on how the authentication policy handles adapter errors.

These decisions must be made deliberately during design — not discovered during an incident. Document the fail-open vs. fail-closed decision for every integration point and verify that your deployment configuration matches the documented intent.

Does PingFederate fail closed (error page) or fail open (partial access)? Restore the data store, then simulate PingID unavailability and repeat. The answers you get from testing are your actual failure modes — not what you assumed they were.
4.7

Ping in the Enterprise Ecosystem

No enterprise runs only Ping products. The real architectural challenge is designing an identity ecosystem where PingFederate, PingDirectory, and PingID coexist with Entra ID, Okta, Saviynt, CyberArk, AWS IAM Identity Center, and whatever else the organization has accumulated over the years. This section maps the most common coexistence patterns and their architectural implications.

PingFederate and Entra ID: The Most Common Coexistence

The dual-IdP architecture — PingFederate for on-premises and custom application federation, Entra ID for Microsoft cloud workloads — is the dominant pattern for large enterprises in 2025. It exists because enterprises adopted PingFederate years before Microsoft built Entra ID into a credible enterprise IdP, and because the migration cost of moving 80+ SAML connections from PingFederate to Entra ID outweighs the operational simplification benefit.

In this pattern, the authoritative source of identity remains on-premises — Active Directory or PingDirectory — and flows into both IdPs via different paths. Entra ID Connect (or Entra ID Connect Cloud Sync) synchronizes users from AD to Entra ID for Microsoft workload authentication. PingFederate reads from PingDirectory (which itself syncs from AD) for on-premises and custom application authentication. The two IdPs are not federated to each other in most deployments — each has its own set of application connections and serves its own application population.

The architectural risk in this pattern is identity data divergence. If a user's email address is updated in AD and the sync to Entra ID runs on a 30-minute schedule while the PingDirectory sync runs in near-real-time, there is a window where the user has different identity attributes in each IdP. Applications that make authorization decisions based on claims from either IdP will see different data. Designing for convergence — ensuring the sync pipelines, schedules, and conflict resolution policies produce consistent identity data across both IdPs — is the architect's responsibility.

Ping Coexistence with Okta: Post-M&A Pattern

When a company running PingFederate acquires a company running Okta (or vice versa), the typical 90-day integration requires a bridge architecture, not a migration. Full migration of all SP connections from one IdP to another in 90 days is operationally infeasible at any meaningful scale — each SP connection requires coordination with the SP administrator, testing, and a cutover window.

The bridge architecture options are: (1) Okta federated to PingFederate — Okta acts as the SP, PingFederate acts as the upstream IdP, users authenticate via PingFederate and receive Okta sessions. Acquired company's 200 Okta apps remain connected to Okta, but identity flows from PingFederate. (2) PingFederate federated to Okta — the reverse: PingFederate acts as the SP, Okta as the IdP. (3) Side-by-side coexistence — each IdP serves its own application population independently, with no federation between them. Users need credentials in both systems during the transition. The architectural choice depends on where the majority of applications live, which directory is the authoritative source of truth, and the long-term target state.

Ping and Saviynt: The IGA Integration

Saviynt provisions identities into PingDirectory via SCIM 2.0. When a new hire is processed through the Joiner workflow in Saviynt (Module 01's JML lifecycle), Saviynt calls PingDirectory's SCIM endpoint to create the user entry. When the employee transfers departments, Saviynt updates the department attribute in PingDirectory. When the employee is terminated, Saviynt disables or removes the PingDirectory entry — removing the user's ability to authenticate through PingFederate immediately.

The architectural coupling here is tight: Saviynt's provisioning accuracy directly determines PingFederate's authentication accuracy. A user whose PingDirectory account is not yet created cannot authenticate. A user whose PingDirectory account was not disabled on termination can still authenticate after their employment ends. The JML lifecycle in Saviynt and the identity data in PingDirectory are two sides of the same architectural contract.

Ping and CyberArk: Privileged Access MFA

CyberArk's Privileged Access Manager integrates with PingFederate for authentication of privileged sessions. When an administrator initiates a privileged session in CyberArk, CyberArk redirects to PingFederate for authentication using SAML. PingFederate's authentication policy for the CyberArk SP connection is configured to always require PingID MFA — regardless of risk score — because privileged access sessions warrant maximum authentication assurance. The MFA context claim returned in the assertion allows CyberArk to verify that the MFA requirement was satisfied before granting access to the privileged credential vault.

🟢 Architect's Insight — The Dual-IdP Source-of-Truth Problem

The dual-IdP enterprise architecture — PingFederate for on-premises and custom apps, Entra ID for Microsoft workloads — is the most common pattern for large enterprises today. The architectural decision is where the authoritative source of truth for identity lives (almost always AD/PingDirectory on-prem) and how it flows into both IdPs.

The mistake is letting each IdP become its own source of truth — creating divergent identity data that causes access inconsistencies, provisioning conflicts, and audit gaps. If a user's email changes in AD and Entra ID reflects the change in 30 minutes while PingDirectory reflects it in seconds, applications that use email as a key across both systems will see inconsistent state during that window. Design the sync pipelines to minimize divergence and make the sync schedule explicit in your architecture documentation.

4.8

Ping Platform Engineering Patterns

PingFederate is a Java application. If you've spent 18 years building Java systems, you already understand the runtime model: JVM, Tomcat, classloading, heap sizing, thread pool tuning. The platform engineering skills you've developed transfer directly — with the domain knowledge of federation layered on top. This section treats PingFederate as the platform engineering challenge it actually is.

PingFederate as a Java Platform

PingFederate runs on an embedded Tomcat instance. Its extension model is classpath-based: adapters, token generators, and attribute sources are JAR files dropped into PingFederate's deploy/ directory and picked up at startup or via hot deployment. The implication for platform engineers: everything you know about Java classloading, dependency isolation (shade/shadow your dependencies to avoid version conflicts), and JVM heap sizing applies directly to PingFederate extension development.

Performance tuning a PingFederate node follows the same methodology as any Java server: JVM heap sizing (the default is rarely optimal for production scale — 4–8GB heap for an active cluster node is common), garbage collection tuning (G1GC with appropriate pause targets), thread pool sizing (Tomcat's connector thread pool must be sized relative to concurrent authentication requests), and LDAP connection pool sizing (the number of concurrent LDAP connections to PingDirectory is a frequently-encountered bottleneck under authentication spikes).

Custom Adapters: When to Build vs. Configure

PingFederate's built-in adapters handle the vast majority of enterprise authentication requirements. You build a custom adapter when: (1) you need to authenticate against a system that no existing adapter supports (a proprietary user store, a custom REST-based authentication API, an internal authentication service), (2) you need to perform authentication logic that the policy tree cannot express with existing adapters (complex conditional flows, stateful multi-step challenges), or (3) you need to acquire claims from a source that is not accessible via LDAP, JDBC, or the standard REST attribute source.

Custom adapters implement PingFederate's IdpAuthenticationAdapter interface. The adapter receives the HTTP request context, performs authentication, and returns an AuthnAdapterResponse containing the authentication result and any attributes acquired during authentication. The adapter JAR, its dependencies, and a descriptor XML file are deployed to PingFederate's deploy/ directory. From PingFederate's perspective, a custom adapter is indistinguishable from a built-in one — it appears in the admin console and can be used in authentication policies and SP connections exactly as any built-in adapter would.

Configuration as Code: The Admin API and GitOps

PingFederate exposes its entire configuration — every SP connection, IdP connection, adapter configuration, authentication policy, certificate, and server setting — through its Admin API: a REST API available at /pf-admin-api/v1/. Every operation you perform in the admin console has an equivalent Admin API call. This is the technical foundation for configuration-as-code.

The Ping Identity Terraform provider wraps the Admin API, allowing PingFederate configuration to be declared in Terraform HCL and applied through standard terraform plan/apply workflows. A GitOps pipeline for PingFederate configuration looks like: engineer makes changes to Terraform HCL in a feature branch → pull request → peer review of the configuration diff → merge → pipeline applies to staging → validation tests run → pipeline applies to production with approval gate. This is the same lifecycle as any infrastructure-as-code deployment.

For organizations not yet using Terraform, the Admin API alone enables significant automation: scripted SP connection creation (onboarding a new SAML application via API rather than manual console configuration), configuration export/import for environment promotion, and automated certificate rotation triggered by expiry monitoring.

PingFederate as an OAuth Authorization Server

PingFederate's OAuth 2.0 Authorization Server capabilities are a frequently underused architectural asset. If your organization is building microservices that need token-based API authorization, PingFederate can serve as the OAuth AS — issuing access tokens to service clients, validating tokens presented to resource servers, and managing OAuth client registrations. This means you don't need a separate OAuth server (like Keycloak or Auth0) alongside PingFederate; the OAuth AS capability is built in.

From a platform engineering perspective, integrating your microservices with PingFederate's OAuth AS follows standard patterns: Client Credentials flow for service-to-service authentication, Authorization Code + PKCE for user-facing applications, token introspection endpoint for resource servers to validate opaque tokens, and JWKS endpoint for JWT validation without introspection. PingDirectory can serve as the user store for resource owner password credentials flows (though this flow is deprecated in OAuth 2.1). The attribute contract applies here too — the claims included in JWTs issued by PingFederate's OAuth AS are configured per client registration.

Automated Testing and CI/CD for IAM Configuration

An IAM platform with no automated testing is one where engineers are afraid to make changes — because they can't be confident a configuration change didn't break an existing SP connection. The discipline of automated testing for PingFederate configuration is underdeveloped in most organizations but achievable with available tooling.

A practical test suite for PingFederate includes: SP connection smoke tests (initiate a SAML flow for each critical SP connection and verify the assertion is delivered successfully — can be scripted with Selenium or Playwright), attribute assertion tests (verify that specific attributes appear correctly in assertions for test users), MFA flow tests (verify that PingID is invoked for connections requiring MFA, and that the MFA context claim appears in the assertion), and certificate validity tests (verify that signing certificates are valid and not within the expiry alert threshold). These tests run in CI/CD against the staging environment before any configuration change is promoted to production.

💡 Analogy — PingFederate as an Application Server

PingFederate is to IAM what Tomcat is to Java web applications. Tomcat gives you an HTTP runtime, connection pooling, and a deployment model — but you extend it with servlets, filters, and custom code deployed as WARs. PingFederate gives you a federation runtime, protocol support, and a connection model — but you extend it with adapters, token generators, and attribute sources deployed as JARs.

The same engineering instinct that makes you good at building on Tomcat makes you good at building on PingFederate. Heap sizing, thread pool tuning, classloader isolation, hot deployment, JMX monitoring — the mental model transfers directly. The only new dimension is the domain knowledge of federation protocols and identity semantics layered on top of the Java platform fundamentals you already have.

🟢 Architect's Insight — Configuration as Code is Non-Negotiable

Every IAM platform engineer should be deeply uncomfortable with PingFederate configurations that live only in the admin console and have never been committed to version control. The PingFederate Admin API exposes all configuration as REST resources. The Terraform provider wraps it. A GitOps pipeline that applies PingFederate configuration from a Git repository is not optional in a mature IAM platform — it's the difference between an IAM system you can operate confidently and one you're always afraid to change.

Without configuration-as-code: you can't peer-review IAM configuration changes before they go to production. You can't roll back a bad configuration change quickly. You can't audit what changed between two incidents. You can't reproduce your production configuration in a new environment. With it: all of those capabilities are table stakes. The Admin API is already there — the investment is building the pipeline around it.

🟣 Deep Dive

PingFederate Admin API + GitOps pipeline: A production-ready pipeline structure: (1) Git repo structure mirrors PingFederate resource types — /sp-connections/, /idp-connections/, /authentication-policies/, /certificates/. Each resource is a JSON or Terraform HCL file. (2) A PR to the repo triggers a terraform plan against the staging PingFederate environment, with the plan output posted as a PR comment for review. (3) After merge, terraform apply runs against staging. (4) Automated SP connection tests validate the change. (5) Manual approval gate triggers terraform apply against production. (6) Post-apply smoke tests validate production. Secrets (client credentials, signing key passphrases) are stored in Vault or AWS Secrets Manager, never in Git. The pipeline service account uses a dedicated Admin API credential with minimal required permissions.

✅ Knowledge Check

Five questions that test architectural reasoning, not configuration recall. Click each question to reveal the model answer.

Q1
A PingFederate SP connection is delivering the wrong email attribute — the application is receiving the LDAP uid value instead of mail. Walk through the attribute contract architecture to diagnose and fix this.
▼

Diagnosis path: The attribute contract for this SP connection maps a source attribute to a claim named email (or whatever the SP expects). The source is incorrectly configured to pull from uid rather than mail. Navigate to: SP Connections → [connection name] → Attribute Contract → expand the email attribute → examine the attribute source mapping.

Fix: In the attribute source configuration for the LDAP data store, the LDAP attribute name should be mail, not uid. Update the attribute source, save, and test with a SAML tracer to verify the assertion now contains the correct value.

Architectural note: This is the attribute contract decoupling layer in action — the internal LDAP attribute name (mail) is mapped to the external claim name (email). The misconfiguration is at the attribute source level, not the claim name level. The SP never sees LDAP attribute names — it only sees the mapped claim names in the assertion.

Q2
Your PingFederate deployment has a 4-node cluster. The load balancer is not session-sticky. What architectural problems does this create and what is the correct load balancer configuration?
▼

Problem: PingFederate stores in-flight SSO session state (the context from the initial authentication request) in the JVM memory of the node that received the request. In an SP-initiated SAML flow, the AuthnRequest arrives at Node 1, which stores context for that transaction. The user authenticates and the browser posts credentials back — but without sticky sessions, the load balancer may route this POST to Node 2, Node 3, or Node 4. Those nodes have no record of the in-flight session, and the authentication fails with an error.

What users see: Intermittent authentication failures approximately 75% of the time (3 out of 4 nodes have no context for any given request), with errors like "request not found" or "invalid session state."

Correct LB configuration: Enable session persistence (sticky sessions) using either source IP affinity or a session cookie. Cookie-based stickiness is preferred as it is more reliable behind NATs and shared IP environments. The stickiness window should exceed the maximum expected SSO flow completion time (typically 5–10 minutes is sufficient).

Clarification: Sticky sessions are required for in-flight authentication flows, not for already-established sessions. PingFederate can optionally use a distributed session store for existing session validation, allowing any node to accept requests from users with established sessions — but in-flight flows always require stickiness.

Q3
PingID's adaptive authentication is configured but the security team reports that MFA can be bypassed via VPN. What is the architectural gap and how do you close it?
▼

Gap: PingID MFA is enforced on web SSO flows through PingFederate but the VPN RADIUS authentication endpoint is configured for password-only authentication. An attacker with stolen credentials can authenticate directly to VPN, bypassing PingFederate and PingID entirely. Once on the VPN, they may have access to internal resources that assume VPN connectivity implies corporate authentication.

Closing it: PingID supports RADIUS integration — it can intercept RADIUS authentication requests and inject an MFA challenge before allowing VPN access. Deploy PingID's RADIUS server component between the VPN concentrator and the RADIUS authentication backend. Configure the VPN's RADIUS server settings to point to PingID RADIUS rather than directly to Active Directory or your NPS server. PingID RADIUS validates the password against the backend and then requires PingID MFA (push or OTP) before returning a RADIUS Access-Accept.

Broader principle: The security model must be: every authentication pathway that grants access to corporate resources requires MFA. Enumerate all authentication pathways — web SSO (PingFederate), VPN (RADIUS), SSH (PAM module), developer tools (API keys, SSH keys), and any legacy systems with direct LDAP authentication — and verify MFA coverage for each.

Q4
A developer wants to build a mobile app that uses PingFederate as its OAuth AS and PingDirectory as its user store. Walk through the full architecture of this integration using concepts from Modules 02, 03, and 04.
▼

Flow architecture: The mobile app (OAuth public client) initiates Authorization Code + PKCE flow to PingFederate's authorization endpoint. PingFederate applies the authentication policy for this OAuth client: HTML Form Adapter (LDAP bind to PingDirectory — Module 02's directory layer) → PingID Adapter (MFA step-up — Module 04). After successful authentication, PingFederate issues an authorization code. The app exchanges the code for tokens at the token endpoint. PingFederate's token generator issues a JWT access token (Module 03's token format) and optionally an OIDC ID token (Module 03's identity layer).

Attribute contract for tokens: The OAuth client registration in PingFederate has an attribute contract defining which claims appear in the access token and ID token. PingDirectory (Module 02) is the data source: sub from uid, email from mail, name from cn, custom app scopes mapped to PingDirectory group memberships.

Resource server validation: The app's backend API (resource server) validates the JWT access token using PingFederate's JWKS endpoint (Module 03's token validation pattern) or via token introspection. Authorization decisions at the API layer use the scope and groups claims from the token.

Module connections: Module 02 (PingDirectory as user store) + Module 03 (OAuth 2.0 + OIDC protocols, JWT structure) + Module 04 (PingFederate as OAuth AS, attribute contract, PingID MFA) combine into a complete mobile authentication architecture.

Q5
The CISO asks: "Can we replace PingFederate with Okta?" Walk them through the dependency inventory process and the architectural implications.
▼

Step 1 — Dependency inventory: Enumerate all systems connected to PingFederate: (a) SP connections — every SAML and OIDC client that receives assertions. Each one requires reconfiguration with the new IdP's metadata, and coordination with the SP administrator. At 100+ connections, this is months of work. (b) Custom adapters — any Java adapters built using the PingFederate SDK have no equivalent in Okta; equivalent functionality must be rebuilt as Okta workflows or custom OIDC integrations. (c) Attribute contract customizations — complex multi-source attribute enrichment (pulling from JDBC, REST, PingID context) maps to Okta's Attribute Mapping + Workflows capability, but requires redesign. (d) PingDirectory integration — Okta's user store is Okta Universal Directory; PingDirectory becomes either a Mastered source via AD Agent or must be migrated. (e) PingID — Okta has its own MFA (Okta Verify), so PingID must be replaced or maintained in parallel during transition.

Architectural implications: Migration complexity scales with SP connections (100 connections = 100 coordination events), custom code (adapters must be rebuilt), and directory architecture (PingDirectory → Okta UD migration or mastering relationship). A realistic timeline for a fully migrated, tested, and validated cutover at enterprise scale is 18–36 months, not weeks.

What you gain: Reduced operational complexity (Okta is managed SaaS), faster SP onboarding (Okta's catalog), native M365 integration, pre-built workflow automation.

What you lose: Maximum protocol flexibility, on-premises data control, custom adapter extensibility, the ability to run without cloud dependency.

Recommendation framing: The question isn't "can we?" (yes, with sufficient time and resources) but "should we, and what does it cost?" Present the dependency inventory as the first deliverable — then a cost/benefit analysis comparing Okta TCO vs. Ping TCO including migration cost.

Upgrade Architecture
The upgrade sequence: (1) Deploy new PingFederate 12.x infrastructure (cluster of 3 engine nodes + 1 console node) in parallel alongside the existing single node — do not upgrade in place. (2) Export configuration from PingFederate 9.x via Admin API. (3) Import and validate configuration on the new 12.x cluster in a staging environment. (5) Run SP connection smoke tests against the staging 12.x cluster. (6) Schedule a maintenance window for production cutover — update load balancer to point to the new cluster. Immediate Risk — Certificate Expiry in 47 Days
This is the P0 blocker that must be addressed before the upgrade. With 47 days to expiry, begin certificate rotation immediately: (1) Generate a new signing key pair in PingFederate. (4) Configure PingFederate to dual-sign with both old and new certificates during the transition window. (5) Once all SPs have updated their trusted certificates, set the new certificate as primary. (6) Confirm all SPs are validating with the new cert before the old cert expires. The 47-day window is workable but requires immediate action and dedicated coordination resources.
Automation Strategy
The modernization is the opportunity to establish configuration-as-code from day one on the new platform. Sequence: (1) Export all 135 SP/IdP connections from the staging 12.x environment as JSON via Admin API. (2) Convert to Terraform HCL using the Ping Identity Terraform provider. (5) Validate that Terraform state matches the actual PingFederate configuration. (6) From this point forward, all configuration changes go through the pipeline — the admin console becomes read-only for production.
