Modern Authentication: MFA, Passwordless, FIDO2 & WebAuthn

Passwords have been the IAM industry's worst-kept secret for decades: they're the leading cause of breaches, the biggest source of support tickets, and architecturally the weakest link in any authentication chain. The industry has known this since the 1980s and has been slowly, imperfectly replacing them ever since. This module covers where that replacement stands today — FIDO2, WebAuthn, passkeys, adaptive MFA — with architectural honesty: what these technologies actually do, what problems they solve and don't solve, and what enterprise deployment looks like when your user base is 40,000 people with laptops, desktops, mobile phones, shared terminals, call centers, and production server access. 🔑

5.1 · Foundations

The Password Problem — An Architectural View

Every authentication scheme has to answer one question: how does the server know the person on the other end of the connection is who they claim to be? The password's answer is the simplest possible one — both sides know a secret, and presenting the secret is proof of identity. That simplicity is exactly the architectural flaw. A shared secret model means the secret must exist in at least two places: in the user's memory (or password manager) and in some form on the server. Anywhere the secret exists is a place it can be stolen from, and because it is the same secret used to prove identity every time, stealing it once gives an attacker indefinite reuse — at least until it's rotated.

This is not a new observation. The shared-secret weakness has been understood since the earliest multi-user computer systems in the 1960s, and the industry has spent the intervening decades building an ever-growing pile of mitigations on top of a fundamentally weak primitive: complexity requirements, rotation policies, breach-database checks, rate limiting, MFA. Each mitigation closes one attack path while leaving the core problem — a static, reusable, human-rememberable secret — fully intact.

The attack surface of passwords

A useful way to reason about password risk architecturally is to enumerate where the attack actually happens, because each attack vector implies a different defensive layer:

  • Phishing — the user is tricked into typing their password into an attacker-controlled site that looks identical to the real one. This attacks the human, not the cryptography.
  • Credential stuffing — an attacker takes a breached username/password list from Site A and replays it against Site B, betting on password reuse. This attacks behavior across the user's entire digital footprint, not any single system's security.
  • Password spray — instead of brute-forcing one account with many passwords (which trips lockouts), the attacker tries one common password (e.g. Summer2026!) against thousands of accounts. This attacks population-scale weak password selection.
  • Brute force / hash cracking — if a password database is breached, an attacker cracks the hashes offline, unconstrained by rate limits. This attacks storage-side security.
  • Pass-the-hash — in Windows/NTLM environments, an attacker who obtains a password's hash (not the plaintext) can authenticate as the user without ever knowing the actual password. This attacks the protocol design of legacy Windows auth.
  • Keylogging — malware on the user's device captures keystrokes as the password is typed. This attacks the endpoint.

Notice that these six vectors target six different layers — the human, cross-site behavior, population statistics, server storage, protocol design, and the endpoint. No single mitigation closes all six. That's the architectural case for moving past passwords entirely rather than continuing to patch around them.

It's worth noting where the industry's own guidance has changed, because it undercuts a lot of legacy password policy still running in production directories today. NIST's current guidance no longer recommends mandatory periodic password rotation or strict complexity rules (forced special characters, mixed case, frequent expiry) — research showed these policies push users toward predictable patterns (incrementing a digit at the end of a reused base password) without meaningfully improving resistance to the attack vectors above, while measurably increasing helpdesk load and user frustration. Modern guidance favors length over complexity, screening new passwords against known-breached password lists at set time, and treating MFA as the real control rather than password policy theater. If your directory still enforces 90-day rotation and complex character rules as its primary password defense, that's a signal worth raising — not because it's actively harmful by itself, but because it represents security effort spent on a control with proven low marginal return, when that same effort could go toward closing the gaps a stronger MFA or FIDO2 rollout actually addresses.

Diagram 1 · Authentication Attack Surface Map
Nine attack vectors against password-centric authentication. Most collapse entirely once there's no password to steal, spray, or replay. Two — pass-the-hash and keylogging — live partly at a different layer (OS/network protocol, endpoint malware) and need mitigations of their own even after FIDO2 removes the password itself.

MFA was the industry's first major answer to this problem, and it genuinely helps — but it doesn't fully solve it, because most MFA implementations still keep the password as the first factor and add a second secret-or-signal on top. That second factor opens its own attack surface: SIM swapping defeats SMS OTP by porting the victim's phone number to an attacker-controlled SIM. MFA fatigue attacks (also called prompt bombing) exploit push-based MFA by sending repeated approval requests until the user taps "approve" out of annoyance or confusion. Real-time OTP phishing uses a proxy site that captures the password and OTP simultaneously and relays them to the real site within the OTP's validity window. And session hijacking simply waits until after a successful MFA challenge and steals the resulting session token instead of the credential.

The authentication assurance spectrum

It's useful to think of authentication strength as a spectrum rather than a binary "has MFA / doesn't have MFA" classification:

  • Level 1 — Password only. Phishable, stealable, spray-able. The weakest practical posture for anything internet-facing.
  • Level 2 — Password + OTP/push. Meaningfully better, but still vulnerable to MFA fatigue, SIM swap, and real-time relay phishing.
  • Level 3 — Password + phishing-resistant factor. A hardware FIDO2 key used as a second factor alongside a password. The password is still phishable, but an attacker who phishes it alone cannot complete authentication without the physical key.
  • Level 4 — Passwordless + phishing-resistant. No password exists at all; FIDO2 (hardware key or platform authenticator) is the only factor. There is no shared secret anywhere in the system to phish, spray, stuff, or crack.

NIST formalizes a closely related idea in its Authentication Assurance Level (AAL) framework, published in NIST SP 800-63B: AAL1 requires single-factor authentication of any kind, including a password alone. AAL2 requires two distinct authentication factors, which covers most OTP- and push-based MFA. AAL3 requires a hardware-based authenticator that provides verifier impersonation resistance — in practice, this means FIDO2/WebAuthn with a hardware-backed key, or a PIV/CAC certificate. AAL3 is the level the U.S. federal government requires for its most sensitive systems, and it is architecturally synonymous with "phishing-resistant."

Diagram 2 · Authentication Assurance Spectrum (L1–L4)
Assurance increases as the shared secret is progressively removed from the authentication path — first supplemented, then made non-decisive, then eliminated entirely.
🛡️ The MFA Fatigue Attack
An attacker with stolen credentials sends dozens of MFA push notifications to the victim's device, hoping the user approves one out of fatigue, confusion, or simply to stop the notifications. This attack has been used in real enterprise breaches. Architectural mitigations: number matching (the push notification shows a code the user must independently match in the app, removing the single-tap "approve"), additional context in push notifications (location, application name, IP), rate limiting on MFA requests, and ultimately FIDO2, which eliminates the push notification vector entirely because there's no "approve" button for an attacker to spam — only a physical possession check.
🔗 Connecting to what you know

The password problem is architecturally identical to the API shared-secret problem you've dealt with throughout your career: if both sides know the secret, either side can be compromised, and a leak anywhere is a leak everywhere. The solution you already trust for API-to-API auth is public-key cryptography — mTLS, or a JWT signed with RS256: only the private key holder can generate valid proof, and the verifier only ever needs the public key. FIDO2 applies exactly that solution to human authentication: the private key lives on the device and never leaves it. The server stores only the public key. There is no shared secret to steal, because there's no longer a secret that both sides hold.

5.2 · Factors & Flows

MFA Architecture — Factors, Flows & Trade-offs

Multi-factor authentication rests on combining factors from different categories: something you know (password, PIN), something you have (phone, hardware key, certificate), and something you are (fingerprint, face). The architectural principle is that compromising one factor type shouldn't compromise another — a phished password doesn't hand over a physical key, and a stolen phone doesn't reveal a password. The strength of an MFA implementation depends entirely on how well that independence actually holds in practice, which is where the factor taxonomy below becomes important — not all "second factors" provide the same independence.

The MFA factor taxonomy

  • TOTP (Time-based One-Time Password). An authenticator app and the server share a secret seeded at enrollment. Both sides combine that secret with the current Unix time (rounded to a 30-second window) through HMAC-SHA1 to independently derive the same 6-digit code. The 30-second window balances usability against replay risk. Because it's a shared secret, a breach of the server-side seed database compromises every enrolled user, and TOTP codes can be phished in real time.
  • HOTP (HMAC-based One-Time Password). The counter-based predecessor to TOTP — instead of time, an incrementing counter on both sides drives the code. Less common today because counter desynchronization (the device increments, the server doesn't see the attempt) causes more support friction than time-based windows.
  • Push notification. The IdP sends an approve/deny prompt to a registered mobile app (this is PingID's primary MFA mechanism). Architecturally simple and user-friendly, but creates the MFA fatigue attack surface covered in 5.1 unless number matching is enabled.
  • SMS OTP. A code sent via text message. NIST formally deprecated SMS as an acceptable out-of-band authenticator in early drafts of SP 800-63B due to SIM swap risk and SS7 network interception, though it remains widely used because of its near-universal device compatibility and low enrollment friction.
  • Email OTP. Similar risk profile to SMS — if the email account itself is the weak link (reused or phished password), email OTP doesn't add real independence.
  • Hardware security keys (FIDO2/U2F). The phishing-resistant factor — covered in architectural depth in Section 5.3.
  • Software/platform FIDO2 authenticators. TouchID, FaceID, Windows Hello — the same FIDO2 cryptography as a hardware key, but the private key is sealed in the device's secure enclave/TPM rather than a separate physical token.
  • Certificate-based authentication. A client certificate (often on a smart card or in a TPM) presented during TLS negotiation. When the private key is hardware-bound, this reaches AAL3 — it's architecturally a sibling of FIDO2, both being public-key based and phishing-resistant.

Step-up authentication and the enrollment lifecycle

Not every resource needs the same authentication strength, and re-challenging users for MFA on every single request would be both unusable and unnecessary. Step-up authentication is the architectural pattern that resolves this: a user can hold an existing session with a lower assurance level and be transparently challenged for a stronger factor only when they reach a resource that requires it. In PingFederate, this is implemented through authentication policies that branch based on the requested resource's risk classification, checking the session's existing AMR (Authentication Methods References) claim before deciding whether to invoke the PingID adapter again.

MFA's weakest architectural link is often not the factor itself but its recovery path. When a user loses their MFA device, some recovery mechanism has to exist — backup codes, a helpdesk-assisted reset, or a fallback factor. Every one of these recovery paths is, by necessity, weaker than the primary factor it's recovering from (otherwise it would just be the primary factor), which makes account recovery a favorite target for social-engineering attacks against helpdesks.

Recovery codes deserve specific architectural scrutiny because they're the most common fallback and the easiest to get wrong. A set of one-time backup codes generated at enrollment is, functionally, a static shared secret — exactly the thing MFA exists to move away from — except now it's a secret the user is expected to store somewhere durable (printed, in a password manager, in a desk drawer) for an event that might not happen for years. In practice, a meaningful fraction of users never store them at all, which pushes the real recovery burden onto the helpdesk. That, in turn, makes helpdesk identity verification the de facto authentication factor for account recovery, and it's typically the weakest one in the entire chain: a caller who knows an employee's name, manager, and a few personal details can often talk a time-pressured support agent into a reset. Architecturally sound recovery design treats the helpdesk reset flow with the same rigor as the primary authentication path — multi-person approval for privileged accounts, callback verification through a number on file rather than the number the caller provides, and an audit trail that flags reset volume anomalies, since a sudden spike in resets for accounts in the same department is a classic precursor to a targeted social-engineering campaign rather than coincidence.

Finally, the OIDC AMR (Authentication Methods References) claim is the mechanism by which an IdP tells a relying party which authentication methods were actually used in a given session — pwd, otp, hwk, fido — letting downstream applications make their own risk decisions based on real assurance evidence rather than trusting a binary "authenticated: true." An application handling sensitive financial transactions can inspect the AMR claim and require a fresh, FIDO2-backed re-authentication before allowing a high-value transfer, even if the user's broader SSO session was originally established with a weaker factor — the claim makes assurance level a first-class, portable piece of information rather than something locked inside the IdP that downstream applications have to trust blindly.

🛡️ The TOTP Shared Secret Problem
TOTP works by both the authenticator app and the server knowing the same base secret, seeded at enrollment. If that server-side secret database is breached, an attacker can generate valid TOTP codes for any enrolled user — indefinitely, without needing the user's device at all. TOTP provides strong protection against password replay and remote brute-force attacks, but it is not phishing-resistant: an attacker can phish both the password and the TOTP code in real time through a proxy site and relay them to the legitimate server within the 30-second validity window. FIDO2 is specifically designed to close this exact gap, as Section 5.3 covers in depth.

5.3 · Core Protocol

FIDO2 & WebAuthn — The Protocol Architecture

FIDO2 is the umbrella specification published jointly by the FIDO Alliance and the W3C, made up of two complementary pieces: WebAuthn, the W3C browser API that web applications call to register and verify credentials, and CTAP2 (Client to Authenticator Protocol), which governs how the browser talks to the actual authenticator — a hardware security key over USB/NFC/Bluetooth, or a platform authenticator like a TPM-backed secure enclave. Together they define every hop in a FIDO2 transaction, end to end.

Every FIDO2 transaction involves exactly three parties, and keeping their roles distinct is the key to understanding the rest of this section:

  • Relying Party (RP) — the web server / application that wants to verify identity. This is your PingFederate instance or the application directly.
  • Client — the browser, which mediates between the RP and the authenticator and enforces the origin-binding rule described below.
  • Authenticator — the hardware key or platform biometric that actually holds the private key and performs the cryptographic signing.

Why FIDO2 is phishing-resistant by cryptographic design

FIDO2 replaces the shared-secret model with public-key cryptography. At registration, the authenticator generates a fresh key pair for that specific website. The private key never leaves the authenticator — not during registration, not during authentication, not ever. The server only ever receives and stores the public key plus a credential identifier. Because authentication consists of signing a server-issued challenge with the private key, and verification consists of checking that signature against the stored public key, there is no secret in transit that a phishing site could capture and replay.

The phishing-resistance goes one step further than ordinary public-key auth, though: every credential is cryptographically bound to the origin it was registered against (the rpId, typically the domain). The browser — not the website, the browser — enforces that a credential registered for company.com can only be used to sign a challenge for company.com. A phishing site at login-company.com is a different origin. The browser will not even let that site request the credential, and even if it somehow did, the authenticator's signature would be computed over the wrong rpId and would fail verification on the real server. This is a hard cryptographic boundary, not a UI cue the user has to notice.

Authenticator types and credential storage models

FIDO2 authenticators come in two architecturally distinct flavors. Roaming authenticators are physical hardware keys (YubiKey, Google Titan Key) that connect via USB, NFC, or Bluetooth and can move between devices — plug the same key into a laptop, then a phone, and it works identically on both because the private key lives on the key itself. Platform authenticators are built into the device — Windows Hello, TouchID, FaceID — and are bound to that specific device's secure enclave or TPM; they can't be moved to another machine, by design.

A second, orthogonal distinction matters for enterprise deployments: resident keys (discoverable credentials) store the full credential — including which account it belongs to — on the authenticator itself, enabling true passwordless flows where the user doesn't even need to type a username. Server-side (non-resident) credentials store only a wrapped key reference on the authenticator and require the server to send back the credential ID at authentication time, meaning the user still types a username first. Resident keys are what make passwordless possible; non-resident credentials are what make a single hardware key scale to an unlimited number of accounts without running out of on-device storage.

FIDO2 and enterprise SSO

FIDO2 itself only answers the question "is this the right person at this browser, right now" — it has no concept of sessions, tokens, or federation across applications. That's exactly the gap Module 03's OAuth and OIDC coverage fills. In a typical enterprise deployment, PingFederate acts as the WebAuthn relying party directly: the user's FIDO2 ceremony happens against PingFederate, not against each individual downstream application, and the result of that ceremony becomes one input into the OIDC token PingFederate subsequently issues. Concretely, a successful FIDO2 assertion causes PingFederate to populate the token's AMR claim with a value like fido or hwk, alongside the existing OAuth scopes and OIDC claims already covered in Module 03. Every downstream application trusting that token inherits the phishing-resistance guarantee without needing to implement WebAuthn itself — they simply check the AMR claim if they care about assurance level, the same pattern used for step-up policy decisions in Section 5.2. This is precisely why centralizing FIDO2 at the federation layer, rather than scattering WebAuthn implementations across every individual application, is the architecturally sound approach: one relying party to harden, register attestation policy for, and monitor, instead of forty.

🛡️ Architectural Honesty on Phishing Resistance
FIDO2 eliminates phishing of the credential itself. A phishing site that captures a FIDO2 challenge and tries to relay it to the real site gets back an assertion signed for the wrong origin — which the real server rejects outright. Compare this to TOTP: a phishing proxy can capture both the password and the TOTP code in real time and replay them at the legitimate site before the 30-second window expires. FIDO2's phishing resistance is cryptographic, not behavioral — it doesn't depend on users recognizing a fake login page, which is precisely why it closes a gap that user security-awareness training never fully closes.
🔗 Connecting to what you know

FIDO2 is the mTLS model applied to human authentication. In mutual TLS, the client presents a certificate — a public key plus a CA signature — and the server verifies that signature; the private key never leaves the client. Phishing the TLS handshake is cryptographically impossible because the private key isn't transmitted at any point. FIDO2 uses exactly this model for human authentication: the private key stays on the authenticator, only a cryptographic signature is transmitted, and that signature is bound to the specific origin being authenticated against. Your Java API security experience with mTLS is the right mental model here — FIDO2 isn't a new idea, it's an old, proven idea finally applied to the human login step.

🟣 Deep dive: What is attestation in FIDO2, what does it actually prove, and when does an enterprise need to verify authenticator attestation versus when is it unnecessary overhead? Attestation is a signed statement from the authenticator's manufacturer asserting properties of the device itself — its model, certification level, and whether the private key is hardware-protected — separate from the per-credential key pair used for ongoing authentication. Verifying attestation lets an RP enforce "only FIDO2-certified hardware keys from this approved vendor list may register" — relevant for regulated environments with procurement requirements. For most enterprise workforce deployments, attestation verification is unnecessary overhead: it complicates the registration flow, requires maintaining a metadata service of trusted attestation certificates, and the marginal security benefit is small compared to simply requiring FIDO2 registration at all. Reserve attestation checking for privileged-access tiers where hardware provenance genuinely matters.

5.4 · Passwordless UX

Passkeys — Architecture & Enterprise Reality

A passkey is a FIDO2 credential — same cryptography, same registration and authentication flows you just walked through in Section 5.3 — with one architectural difference: it's synced across a user's devices through a platform credential store, rather than bound to a single piece of hardware. Apple syncs passkeys through iCloud Keychain, Google through Google Password Manager, and Microsoft through Windows Hello for Business in its managed-enterprise form. Register a passkey on your iPhone and it's available on your iPad and Mac within seconds, with no re-enrollment step.

This is genuinely the right consumer answer to FIDO2's biggest historical adoption blocker: hardware keys are excellent security but a real usability tax — they cost money, get lost, and don't travel with you automatically across every device you own. Passkeys remove that tax. But the syncing mechanism that makes passkeys convenient is exactly what makes them architecturally different from a hardware key for enterprise purposes: the private key, while still never transmitted in plaintext, now exists inside a cloud-synced keychain that the enterprise does not control.

Diagram 9 · Device-Bound FIDO2 vs. Synced Passkey
Both are FIDO2 — the cryptography is identical. What differs is custody of the private key and what that means for an enterprise's actual control over the credential.

The enterprise passkey deployment reality

The architectural tension is straightforward to state: synced passkeys are dramatically more user-friendly because they're available on every device a user owns without re-enrollment, but the private key's custody now sits, at least partly, in a personal cloud account rather than under enterprise control. That tension cascades into several concrete deployment questions:

  • Who controls the credential store? A passkey synced to a personal Apple ID is outside enterprise control entirely. A passkey synced via Windows Hello for Business on a domain-joined, MDM-managed device is a fundamentally different — and enterprise-controllable — proposition.
  • BYOD implications. On an employee-owned phone, the enterprise has no way to enforce that the passkey is going into a managed credential store rather than the employee's personal iCloud or Google account.
  • Offboarding risk. If an employee enrolls a passkey synced to their personal cloud account and then leaves the company, that passkey — and the access it grants until revoked server-side — leaves with them, resident in an account the enterprise never had visibility into.
  • MDM integration requirements. Enforcing managed passkey behavior generally requires the device to be enrolled in mobile device management, with policy controls that route credential sync into a managed keychain rather than a personal one.

Windows Hello for Business is the enterprise-grade implementation of this idea: it provisions a passkey-equivalent credential tied to the user's identity in Active Directory or Entra ID, backed by the device's TPM, and managed through enterprise policy rather than a consumer cloud account. It's architecturally closer to a managed hardware key than to a consumer passkey, even though the user experience — unlock with PIN or biometric — feels identical.

💰 The Enterprise Passkey Dilemma
Consumer passkeys stored in iCloud Keychain or Google Password Manager provide excellent user experience and genuine phishing resistance — but the private key sits in the user's personal cloud account, not the enterprise's control. If the user leaves and retains their personal Apple or Google account (which they almost always do — it's personal), they retain the passkey. If that personal cloud account is compromised, the passkey is compromised right along with it, outside the reach of enterprise incident response. Enterprises that want passkey-level convenience without losing credential control need managed passkey solutions: Windows Hello for Business on MDM-managed devices, or — where managed sync isn't available or trusted — hardware security keys.

5.5 · Risk-Based Decisions

Adaptive Authentication Architecture

Adaptive authentication replaces blanket policies ("always require MFA") with risk-based decisions made at the moment of authentication. Instead of treating every login attempt identically, the system collects signals about the context of the request and only escalates the authentication requirement when those signals suggest elevated risk. This is the architecture underneath PingID's adaptive MFA, Entra ID's Conditional Access, and every major vendor's "risk-based authentication" feature — same concept, different product names.

The signal taxonomy

  • Device signals. Is the device enrolled and managed? Does it pass a health/compliance check? Has it been seen before for this user?
  • Network signals. IP reputation, geolocation, the requesting ISP, known proxy/VPN usage, corporate network vs. unrecognized home/public network.
  • Behavioral signals. Time of access against the user's typical pattern, access velocity, and impossible-travel detection — a login from two geographies too far apart to have been physically traveled between in the elapsed time.
  • Identity signals. Account health (recent password reset, recent lockout), whether this is a high-privilege account, an existing "at-risk user" flag from a threat-intelligence feed.
  • Context signals. The sensitivity classification of the application being accessed, the data classification involved, and the session duration being requested.

These signals feed a risk engine that combines them into a single risk score — anywhere from simple rule-based scoring ("unrecognized device + impossible travel = high risk") to machine learning models trained on historical authentication patterns that can catch subtler anomalies a rule set would miss. The risk score then drives a policy decision: low risk passes through silently, medium risk triggers an MFA step-up, and high risk blocks the attempt outright or routes it to manual review.

Rule-based and ML-based risk engines aren't an either/or choice in practice — most mature implementations layer both. Rules are explicit, auditable, and fast to reason about: a compliance team can read "block if country is on the sanctions list" and know exactly what the system does, which matters when an auditor asks why a specific login was denied. The limitation is that rules only catch the patterns someone thought to write a rule for. ML-based scoring, typically a model trained on historical login telemetry (successful logins, confirmed-fraudulent logins, user-specific behavioral baselines), can surface combinations of weak signals that individually wouldn't trip any single rule — a device that's technically recognized but is being used at an unusual hour, from a slightly atypical network, immediately after a password reset. The architectural trade-off is explainability: a rule denies access for a reason you can quote back to the user or auditor; a model produces a score that's harder to explain in plain language, which is why most enterprise deployments keep hard, explainable rules for the highest-confidence decisions (sanctioned countries, known-compromised credential lists) and reserve ML scoring for the gray area in between, where a probabilistic judgment is genuinely more useful than a brittle rule could ever be.

Diagram 10 · Adaptive Authentication Architecture
Five signal categories feed a risk engine, whose score drives a three-tier policy decision — the result flows into the token as AMR evidence for downstream relying parties.

Point-in-time vs. continuous evaluation

Traditional authentication is point-in-time: the user proves identity once, gets a session, and that session remains valid for some fixed duration regardless of what happens afterward. If an employee's device or credentials are compromised five minutes after login, the session keeps working until it naturally expires — potentially hours later. Continuous Access Evaluation (Microsoft's CAE, standardized more broadly as the Continuous Access Evaluation Profile, CAEP) closes that gap by continuously re-evaluating risk signals against an active session and revoking it immediately when a high-risk event is detected, rather than waiting for natural expiration.

Diagram 11 · Continuous Access Evaluation vs. Point-in-Time Authentication
Same compromise event, two very different exposure windows — six hours of standing access versus roughly one minute.
🛡️ Impossible Travel: Real Signal, Real False Positives
If a user authenticates from London at 9am and an authentication request then arrives from Tokyo at 9:30am, that's physically impossible — a strong signal of credential compromise. Adaptive authentication should detect this and trigger immediate step-up or a block. But "impossible travel" carries a real false-positive risk: VPN endpoints, split tunnels, and corporate proxies routinely create geolocation artifacts that look like impossible travel but aren't. Tune thresholds against your actual user population's travel patterns and VPN topology before enabling hard blocks on impossible travel — otherwise you'll generate helpdesk tickets faster than you catch attackers.

If not, ask why not — and whether that's a configuration gap or an intentional risk acceptance.

5.6 · Provisioning

SCIM 2.0 — Provisioning Architecture

SCIM — System for Cross-domain Identity Management — is a REST API standard for identity provisioning. Before SCIM existed, every application had its own proprietary mechanism for getting users into it: a CSV import, an LDAP sync job, a SOAP API, a custom REST endpoint nobody else used. Each integration was bespoke, which meant every new application onboarded to an enterprise IAM program was its own multi-week integration project. SCIM standardizes the basic operations every provisioning workflow needs — create a user, update a user, deactivate a user, sync group membership — behind one predictable REST interface that any SCIM-compliant IGA platform can call against any SCIM-compliant target application.

Resources, operations, and where SCIM fits

SCIM 2.0 defines two core resource types: Users and Groups. Each carries a core schema (name, emails, phone numbers, active status) plus an enterprise extension schema for attributes that matter to corporate directories specifically — employee number, organization, division, department, manager — and most implementations layer a further custom extension on top for company-specific attributes that don't fit either standard schema. The protocol exposes these resources through standard REST semantics: GET to read, POST to create, PUT to fully replace, PATCH to partially update, and DELETE to remove — though in practice, most enterprise deployments soft-delete via a PATCH setting active: false rather than a hard DELETE, preserving the audit trail.

SCIM is the mechanism that connects the JML (Joiner-Mover-Leaver) lifecycle you covered conceptually in Module 01 to an actual provisioning action against a real system. When Saviynt processes a joiner event, it doesn't manipulate the target application directly through whatever interface that application happens to expose — it calls a standard SCIM POST /Users endpoint, and the target application (or an adapter in front of it) handles translating that into whatever its native user store requires. PingDirectory can itself act as a SCIM server, exposing its LDAP-backed identity store through a SCIM REST interface so that IGA platforms never need to speak raw LDAP.

Diagram 12 · SCIM Provisioning Architecture

Diagram 13 · SCIM User Resource Schema
Core schema covers the universal identity attributes; the enterprise and custom extensions carry the organization-specific data your IGA platform actually needs to reconcile.

Provisioning patterns and security

SCIM provisioning is implemented in three common patterns. Push-based provisioning has the IGA platform actively call SCIM endpoints whenever a change occurs — this is what Saviynt does in the JML flow above. Pull-based provisioning inverts that: the target system periodically polls the identity source for changes, useful when a target system can't accept inbound connections. Event-driven provisioning combines SCIM's resource model with a separate event notification channel (webhooks, message queues) so that changes propagate near-instantly rather than waiting for the next poll cycle. SCIM endpoints are secured with bearer token authentication over TLS in essentially all enterprise deployments — an exposed, unauthenticated SCIM endpoint is an unauthenticated user-creation API, which is exactly as dangerous as it sounds.

💡 SCIM Is Provisioning, Not Authentication
SCIM is a provisioning protocol, not an authentication protocol — and that distinction matters architecturally. SCIM creates and manages identity records (writes to directories and application user stores). OAuth/OIDC/SAML authenticates those identities — proves who is who at login time. A complete IAM architecture needs both: SCIM for lifecycle management, OAuth/OIDC/SAML for authentication. Confusing the two layers leads to architectures that can authenticate users who were never properly provisioned, or that provision users into a target system who then can't actually authenticate because the federation side was never configured. They're complementary halves of the same identity lifecycle, not substitutes for each other.
🔗 Connecting to what you know

SCIM is the REST API equivalent of the LDAP provisioning scripts you've probably written more than once. Instead of LDAP Add/Modify operations to create a user directly in PingDirectory, SCIM gives you a standardized HTTP POST /Users endpoint with a defined JSON schema. It's the same underlying operation — create a user, set attributes, assign group membership — but delivered through a standard protocol that any OIDC-aware IGA platform can call without a custom integration. Your Java API development background means SCIM should feel immediately comfortable: it's just a REST API with a well-defined resource model, applied to identity instead of business data.

🟣 Deep dive: What is SCIM filtering, and how do IGA systems use it to reconcile their identity records against a target system without doing a full export every time? SCIM defines a query language for the GET /Users endpoint — filter=userName eq "jdoe" or filter=meta.lastModified gt "2026-06-01T00:00:00Z" — that lets a calling system request only the records it actually needs rather than pulling the entire user population on every reconciliation cycle. An IGA platform doing nightly reconciliation against a SaaS application with 50,000 users doesn't want to download all 50,000 records to find the dozen that changed; it filters on a lastModified timestamp and pulls only the delta, which is both faster and dramatically less load on the target system's API.

5.7 · Program Architecture

Enterprise Passwordless Rollout Architecture

Everything in this module so far has covered individual technologies. This section covers the much harder problem: what does it actually take to roll FIDO2/passwordless authentication out across a 40,000-person enterprise, with 180 applications of wildly varying age, 3,000 shared call-center workstations, and a board that just heard the phrase "passwordless" in a vendor pitch and wants it done by end of year? The honest architectural answer is that "going passwordless" is a phased program, not a single project, and most enterprises stabilize somewhere in the middle of that phasing rather than completing it.

The three-phase reality

  • Phase 1 — Password + phishing-resistant MFA. The password still exists and is still the first factor presented to the user, but a FIDO2 hardware key or platform authenticator is layered on top as a required second factor. This is the easiest phase to reach and delivers most of the phishing-resistance benefit immediately.
  • Phase 2 — Password hidden from the user. The user's day-to-day experience is passwordless — FIDO2 is the only factor they interact with — but a password still exists in the directory as a fallback/recovery mechanism, invisible in normal use. This is where most mature enterprise programs land as a stable end state.
  • Phase 3 — Password eliminated. True passwordless: the password attribute itself is removed or permanently randomized in the directory, and FIDO2 or a hardware-backed certificate is the only authentication mechanism that can possibly work. Few enterprises reach this for their full population.
Diagram 14 · Passwordless Rollout Phases
Each phase removes risk without removing it entirely — the residual risk just moves to a different part of the architecture, most often the recovery path.

Why most enterprises stall at Phase 1–2

Three blockers show up in nearly every enterprise passwordless program, regardless of industry: legacy applications that only support password authentication and can't be modified without a code change or a fronting proxy; shared workstations in call centers and similar environments where device-bound FIDO2 doesn't map cleanly onto a "many users, one machine" usage pattern; and break-glass procedures for emergency access that, almost by necessity, fall back to some form of password or recovery code — meaning a true Phase 3 environment still has exactly one password-shaped attack surface left, just a much smaller one.

Diagram 15 · User Population Segmentation Matrix
The same technology — FIDO2 — gets a different deployment answer in every cell, because risk level and work context change what "good" looks like.

Where a legacy application genuinely cannot be modified to support FIDO2/OIDC directly, the credential broker / reverse proxy pattern provides a transitional bridge: the user authenticates passwordlessly against PingFederate, and a broker component exchanges that token for an application-specific password credential that gets injected into the legacy app's native login flow — invisibly, from the user's perspective. The user experience is passwordless even though the legacy application, unmodified, still thinks it's receiving a username and password.

Helpdesk impact and rollout sequencing

A passwordless rollout changes the helpdesk's job more than almost any other part of the organization, and that change is frequently under-planned. When the password was the authentication mechanism, "I forgot my password" was the dominant ticket type and the resolution was simple and low-risk: verify identity, reset, done. Once a hardware key or platform authenticator is the authentication mechanism, "I lost my key" or "I got a new phone and lost my passkey" becomes the dominant ticket type — and the resolution is no longer low-risk, because re-issuing access without a strong factor in hand is exactly the social-engineering target described in Section 5.2. Helpdesk staff need new tooling (the ability to view enrolled factors and revoke/re-enroll them, not just reset a password), new training (recognizing pretexting attempts aimed at exactly this flow), and a clear escalation path for privileged accounts that shouldn't be resettable by a first-tier agent at all. Budgeting for this operational shift is as much a part of the program's architecture as the FIDO2 deployment itself.

Sequencing matters as much as the technology choice. The instinct to start with the easiest population — knowledge workers on managed laptops — is usually right, but it should be sequenced specifically to build operational muscle before tackling harder populations: enrollment workflows, helpdesk procedures, and break-glass processes should all be proven against a forgiving population of a few thousand users before they're relied upon for a call center population of shared workstations or a privileged-access population where a process gap is a genuinely dangerous outcome rather than an inconvenience. Privileged and high-risk accounts are the exception to "start easy" — they carry enough risk that they often justify going first even though they're operationally harder, simply because the cost of leaving them on password-based MFA the longest is the highest. Success metrics should track more than enrollment percentage: phishing simulation click-through rates, MFA fatigue-style approval anomalies, and helpdesk reset volume are all better signals of real risk reduction than a simple "percentage of users enrolled" dashboard, which can look complete while leaving the riskiest populations and the weakest recovery paths essentially untouched.

💰 The "100% Passwordless in 6 Months" Promise
Be cautious of this promise — most enterprises that attempt rapid passwordless deployment hit the same three blockers: legacy applications that require password auth and need either code changes or proxy patterns, shared workstations where FIDO2 device-binding doesn't fit the use case, and break-glass procedures that inevitably fall back to a password. A realistic enterprise passwordless program takes 2–4 years to reach Phase 3 for the majority of its user population — and most enterprises realistically target Phase 2 as a stable, acceptable end state rather than chasing full elimination everywhere.

Architecture Cheat Sheet

1

FIDO2 = phishing-resistant by cryptographic design — origin binding prevents a credential from being used on a phishing site, full stop.

2

Passkeys = synced FIDO2 credentials. Hardware keys = device-bound FIDO2. Same cryptography, different security/custody profile.

3

TOTP is not phishing-resistant — real-time OTP relay attacks against it are practical, not theoretical.

4

Adaptive authentication = risk-score-gated step-up, not blanket MFA on every single login.

5

SCIM = REST standard for identity provisioning, not authentication — don't confuse the two layers.

6

The AMR claim is how the IdP tells the relying party which authentication methods were actually used.

7

Continuous Access Evaluation = real-time session risk revocation, versus point-in-time auth that only checks once.

8

Passwordless rollout is a realistic 2–4 year program, not a 6-month project — plan and communicate accordingly.

Real-World Scenario

"The Phishing-Resistant Enterprise"

Situation

A financial services firm with 22,000 employees suffered a targeted phishing campaign. 12 employee credentials were compromised after a convincing email led users to a look-alike login page. MFA was already in place — push notification via the firm's MFA platform — but 3 of the 12 compromised accounts were successfully accessed anyway.

Root Cause Analysis

Investigation showed two distinct attack paths against the 12 victims. Nine accounts were stopped at the MFA layer — the attacker had the password but couldn't complete the push challenge. The remaining three were compromised through MFA fatigue: the attacker, holding valid passwords for those accounts, sent repeated push notifications late at night until each user approved one out of confusion or annoyance. None of the three step-up notifications included number matching or contextual detail about the request.

Architectural Remediation
  • Enable number matching on all push-based MFA immediately — closes the specific gap that allowed the three account compromises, with no user re-enrollment required.
  • Add geographic and application context to every push notification so a 2am approval request from an unrecognized location is visibly suspicious to the user.
  • Begin a phased FIDO2 hardware key rollout for all privileged and finance-adjacent accounts — the population with the highest blast radius if compromised — to remove the push-notification attack surface for that population entirely.
  • Layer in adaptive authentication so that login attempts from unrecognized devices or anomalous locations require step-up regardless of whether the push is eventually approved, rather than relying on push approval as the sole gate.
Phased Implementation

Week 1: number matching and contextual push notifications enabled firm-wide — a configuration change, not a deployment project. Month 1–3: FIDO2 hardware key rollout to the 500-person privileged/finance population, with attestation verification required given the regulatory environment. Month 3–9: adaptive authentication risk engine tuned against the firm's actual travel and device patterns, then enabled in enforcing (not just alerting) mode. Month 9–18: FIDO2/passkey rollout extended to the general workforce, targeting a stable Phase 2 (password hidden) end state rather than full elimination.

Metrics for Success
  • MFA fatigue-style approvals: tracked via "approved without number match entry" events — target: zero after week 1.
  • Percentage of privileged accounts on hardware FIDO2 keys — target: 100% by month 3.
  • Adaptive authentication step-up trigger rate vs. false-positive helpdesk ticket rate — tuned iteratively rather than set once.
  • Phishing simulation click-through-to-compromise rate — the metric that actually matters, tracked quarterly against the pre-incident baseline.
