Protocols Deep Dive: OAuth 2.0, OIDC, SAML & JWT

You've used these protocols for years. You've configured OAuth clients in PingFederate, debugged SAML assertions in browser dev tools, decoded JWTs on jwt.io. But there's a difference between knowing how to configure a protocol and understanding why it was designed that way — why OAuth 2.0 uses redirect URIs instead of server-to-server callbacks, why SAML uses XML instead of JSON, why OIDC adds an ID token when OAuth already has an access token, why the Authorization Code flow exists when the Implicit flow is simpler. This module answers those questions. When you finish it, you won't just configure these protocols — you'll make architecture decisions with them.

3.1 Why Protocols Exist: The Problem Space

Before identity protocols existed, every application owned its own authentication. Each app had its own username/password store, its own login page, its own session model. There was no way to tell App B "this user already proved who they are at App A" — so users re-authenticated everywhere, password stores proliferated across every system in the enterprise, and credential management became unmanageable. SSO, in any real sense, was not possible.

The fundamental challenge identity protocols solve is this: how do you let Application B trust a user who authenticated at Application A, without Application B ever seeing the user's credentials? That single question is the seed of every protocol in this module — and every design decision inside OAuth, OIDC, and SAML traces back to answering it a little more rigorously than the last attempt did.

It's worth being precise about why LDAP doesn't solve this. LDAP is a directory protocol — it's how an application reads identity data and verifies a bind against a password. It has no concept of issuing a portable proof of authentication that one application can hand to another. Module 02 covered LDAP as the back-end identity store. This module covers the layer above it: the protocols that let identity travel between applications.

Before any standard existed for this, enterprises that wanted something resembling SSO built proprietary, point-to-point integrations: a custom cookie shared across a narrow domain, a shared session database two applications both happened to read, or — worse — literal credential replication, where App B stored a copy of the password App A validated. None of these approaches scaled past a handful of tightly coupled applications, none of them worked across organizational boundaries, and every one of them multiplied the attack surface every time a password was copied somewhere new. The protocols this module covers exist specifically to replace that pattern with something that scales, that crosses organizational trust boundaries safely, and that never requires a second application to see a password at all.

That problem was solved in stages, not all at once — and the order matters architecturally:

  • SAML 2.0 (2005) — the first widely adopted enterprise federation standard. XML-based, browser-redirect-driven, built for an era when SOAP and enterprise XML tooling were the default stack.
  • OAuth 2.0 (2012) — not built to replace SAML, but to solve a different problem: letting a third-party application access a resource on a user's behalf, without ever handling the user's password. This is authorization delegation, not authentication.
  • OIDC (2014) — added an authentication layer on top of OAuth 2.0, because the industry kept misusing OAuth access tokens as proof of identity. OIDC formalized "who is this user" as a first-class concept on the OAuth foundation.

The resulting layered model is one every IAM architect needs internalized: OAuth handles authorization delegation, OIDC adds authentication on top of OAuth, and SAML handles both — but is older, XML-based, and purpose-built for enterprise browser SSO. None of the three protocols replaced the others; each occupies a distinct architectural niche, which is why a mature enterprise runs all three simultaneously (Section 3.8 covers this in depth). Recognizing which niche a given integration falls into — before you've opened PingFederate's admin console — is most of what separates a smooth protocol integration from a multi-week back-and-forth with a vendor's support team.

One more vocabulary note before going further, since architects use these words precisely: a protocol defines the rules of interaction between parties (the message flow). A standard or specification (RFC, OASIS standard) is the formal document that defines a protocol so multiple vendors can implement it interoperably. PingFederate doesn't invent OAuth — it implements the OAuth 2.0 specification (RFC 6749).

This distinction has a practical payoff later in your career: when a vendor claims something is "OAuth-compliant," the honest follow-up question is which specific RFCs and extensions they implement, since OAuth 2.0 itself is a framework with multiple optional extensions (PKCE, token introspection, device authorization) layered on top of the core spec. Two vendors can both be technically "OAuth-compliant" while supporting meaningfully different sets of capabilities — which is exactly the kind of gap an architect needs to catch during vendor evaluation, not during a production integration six months later.

The protocol problem is exactly the microservices authentication problem you've solved as a Java engineer. How does Service B trust a JWT from Service A without Service A's private key? You solved it with a shared signing key or a public key infrastructure — and you standardized on JWT. Identity protocols solve the same problem at human scale: how does Application B trust that Application A really authenticated this user? The answer is the same shape: cryptographic tokens issued by a trusted authority, validated against published keys. The difference is which trusted authority, which token format, and which protocol governs the flow.

🔵 The three questions every identity protocol must answer

1. How does the user prove who they are? (Authentication)
2. How does that proof get communicated to the application? (Token / assertion transport)
3. How does the application verify the proof without contacting the IdP on every request? (Token validation)
OAuth, OIDC, and SAML answer these three questions differently. Understanding those differences is the foundation of protocol selection.

3.2 OAuth 2.0: The Authorization Framework

Here is the single most important distinction in modern IAM, and the one most engineers get wrong: OAuth 2.0 is an authorization framework, not an authentication protocol. It was designed to answer "is this client allowed to do this thing on the user's behalf?" — not "who is this user?" Every misuse of OAuth in production traces back to forgetting this distinction.

The four roles

OAuth defines four roles, and every enterprise deployment maps real systems onto them:

  • Resource Owner — the human user who owns the data or resource being accessed.
  • Client — the application requesting access (a web app, mobile app, or service).
  • Authorization Server — issues tokens after authenticating the resource owner and obtaining consent. PingFederate or Entra ID typically plays this role.
  • Resource Server — the API that holds the protected resource and validates the access token on each request.

Tokens, scopes, and clients

The authorization code is deliberately separated from the token itself. It's short-lived, single-use, and travels through the browser. The actual token exchange happens server-to-server at the /token endpoint, away from the browser entirely — this is a security design decision, not an accident, and Section 3.3 walks through exactly why.

Access tokens are what the client presents to the Resource Server. They have a lifetime, an audience, and — critically — they say nothing about identity by design. Refresh tokens exist so the client doesn't need to send the user through a full re-authentication every time an access token expires; they're long-lived, sensitive, and architects design rotation policies around them carefully.

Scopes give OAuth coarse-grained authorization — read:orders, write:profile — but scopes are not enough for fine-grained authorization (who can approve a $50K invoice vs. a $500 one). That's a policy-engine problem, covered in Module 08.

How a confidential client actually proves its identity to the token endpoint is its own design decision. The simplest method, client_secret_post, sends the secret as a form parameter in the token request body. client_secret_basic sends it via HTTP Basic Auth instead. Neither is wrong, but both depend entirely on the secret never leaking — which is why higher-assurance deployments move to private_key_jwt, where the client signs a short-lived JWT assertion with its own private key instead of transmitting a shared secret at all. PingFederate supports all three, and which one an integration uses is a real architecture decision, not just a dropdown setting.

The /introspect endpoint deserves its own mention here, separate from the validation depth covered in Section 3.6: it exists specifically for opaque access tokens — tokens that aren't JWTs and carry no inspectable claims of their own. A Resource Server holding an opaque token has no way to check its validity locally; it must call back to the Authorization Server on every request. This is the architectural trade-off that makes JWT-based access tokens so attractive in API-heavy environments — they let the Resource Server skip that round-trip entirely.

Consent is worth a closer look too, because it's easy to treat as a UI screen rather than an architectural control. The first time a client requests a given set of scopes for a given user, the Authorization Server typically presents a consent prompt — "App X wants to read your profile and write to your calendar" — and records that decision. On subsequent requests for the same scopes, PingFederate can skip the prompt entirely, which is the right behavior for a trusted internal application but a real privacy control for third-party or partner-facing integrations, where re-prompting on scope expansion (a client suddenly requesting a new, broader scope) is what keeps a user from silently granting more access than they intended. The /revoke endpoint is the corresponding architectural safety valve: a user (or an administrator) can invalidate a previously issued token or refresh token immediately, without waiting for natural expiry — the operational equivalent of disabling an account mid-session rather than waiting for the next password rotation cycle.

OAuth also distinguishes confidential clients (server-side apps that can securely store a client_secret) from public clients (SPAs, mobile apps, which cannot). This distinction drives which grant types and protections (like PKCE) are mandatory. The redirect_uri must be pre-registered with the Authorization Server precisely because an attacker who can redirect the authorization response to their own URI can steal the code — this is the open redirect attack class.

🔴 Why OAuth is not an authentication protocol

OAuth access tokens tell you that a client is authorized to access a resource on behalf of a user — they don't tell you who the user is. An application that uses an OAuth access token to identify a user is misusing the protocol. This is why OIDC exists: it adds the ID token (which IS about the user's identity) on top of OAuth's authorization flow. Architecturally, using OAuth for authentication is like using a car park ticket to prove you own the car — it's evidence of authorization, not identity.

OAuth 2.0 is the valet key pattern. When you give a valet your car key, you give them limited authorization to move the car — not the title, not access to your house, not your identity. An OAuth access token is a valet key: it grants limited, scoped access to a resource (your API) on behalf of a resource owner (the user) without exposing the owner's credentials. The application never needs to know or store your password — just that you authorized it to act on your behalf. This is why OAuth is the right pattern for "let this third-party app read my calendar" but the wrong pattern for "log in with Google" — for the latter, you need OIDC.

🟣 Deep dive: What is the PKCE extension, and when is it required?

PKCE (Proof Key for Code Exchange, RFC 7636) was invented because public clients — mobile apps and SPAs — can't keep a client_secret confidential, which means anyone who intercepts the authorization code could exchange it for a token. PKCE fixes this without a secret: the client generates a random code_verifier, sends its hashed form (code_challenge) with the initial /authorize request, then sends the original code_verifier at the /token exchange. The Authorization Server hashes it and confirms it matches — proving the entity exchanging the code is the same one that started the flow, even with no secret involved. PKCE is mandatory for all public clients and is now recommended for confidential clients too, since it closes the authorization-code-interception attack regardless of client type.

3.3 OAuth 2.0 Grant Types: Choosing the Right Flow

A "grant type" is simply a defined recipe for how a client obtains a token. Picking the right one is one of the most consequential decisions in an OAuth integration — get it wrong and you either break the user experience or open a security hole.

Grant type 1 — Authorization Code

Used for web apps, mobile apps, and any user-facing application with a back channel. The flow has two distinct steps: the browser receives a short-lived, single-use authorization code via redirect, and then — separately, server-to-server — that code is exchanged for tokens at the /token endpoint. The two-step design exists because the code, even if intercepted in the browser, is useless on its own without the client credentials (or PKCE verifier) needed to redeem it at the token endpoint, which never touches the browser. For public clients (SPAs, mobile apps), PKCE is mandatory alongside this flow.

Grant type 2 — Client Credentials

Used for machine-to-machine and service-to-service calls where no human user is involved. The client authenticates directly to the /token endpoint with its own credentials — no redirect, no browser. In IAM terms: a microservice calling an internal API, a batch job pulling from a data store, or a CyberArk credential rotator calling a management API. Because there's no user in the loop, the entire security posture rests on protecting the client_secret — which makes secret rotation an IAM architecture problem in its own right (this connects directly to PAM patterns in Module 12).

Grant type 3 — Device Authorization (Device Code)

Built for devices with limited input — smart TVs, IoT controllers, CLI tools. The device displays a short code and a URL; the user enters that code on a second device (phone, laptop) that has a proper browser and keyboard, while the original device polls the token endpoint until authorization completes. This pattern shows up again when Module 11 covers IoT and network device identity.

The polling behavior is worth understanding precisely, because it's easy to implement carelessly: the device calls the token endpoint repeatedly at a server-specified interval (commonly every 5 seconds) until the user completes the authorization step on their second device, at which point the next poll returns real tokens instead of a "pending" status. Authorization Servers enforce that interval deliberately — a device that polls faster than instructed risks being throttled or rejected entirely, since aggressive polling against an Authorization Server at scale starts to look like a denial-of-service pattern rather than a legitimate device waiting for a user. A CLI tool authenticating an engineer against PingFederate to pull credentials from an internal API is a realistic enterprise example of this flow in action — no browser on the workstation running the CLI tool is required at all.

Refresh tokens — not a standalone grant

A refresh token isn't requested on its own; it's issued alongside an access token (typically only to confidential clients) and later exchanged for a fresh access token without re-prompting the user. The architecture decisions that matter here are absolute timeout (how long can a session live, full stop) vs. idle timeout (how long can it live without activity) — and whether refresh tokens rotate on each use, which limits the blast radius if one is stolen.

Refresh token rotation is the practice of issuing a brand-new refresh token every time the old one is used, and invalidating the old one immediately. This turns a stolen refresh token into a much smaller problem: if an attacker uses a stolen refresh token before the legitimate client does, the legitimate client's next refresh attempt fails — which is a detectable signal that something is wrong, rather than a silent, indefinite compromise. Without rotation, a single leaked refresh token can mint new access tokens for as long as its (often very long) lifetime allows, with no way to tell legitimate use from attacker use. Designing the absolute and idle timeouts is ultimately a balance between session convenience and blast-radius containment — a banking application and an internal wiki should not share the same refresh token lifetime policy, even if both run through the same PingFederate environment.

Deprecated patterns — know them, and know why they died

  • Implicit Grant — designed for browser-only apps before PKCE existed, it returned the access token directly in the URL fragment. Deprecated because URL fragments leak into browser history, referrer headers, and proxy logs. Replaced by Authorization Code + PKCE.
  • Resource Owner Password Credentials (ROPC) — the client collects the user's username and password directly and trades them for a token. This defeats the entire purpose of OAuth (never expose credentials to the client) and should be eliminated wherever possible; it survives mainly as a stopgap during legacy migrations.

🔴 Why the Implicit grant was deprecated

In the Implicit flow, the access token is returned in the URL fragment (after the #). Browser history, referrer headers, and proxy logs can all capture URL fragments — meaning access tokens leaked into browser history and server logs routinely. Authorization Code + PKCE solves this by keeping tokens out of URLs entirely: only the short-lived, single-use authorization code appears in the URL.

3.4 OpenID Connect (OIDC): Authentication on OAuth

OIDC is best understood with one sentence: OIDC = OAuth 2.0 + an identity layer. It doesn't replace any part of OAuth's authorization machinery — it adds exactly what OAuth was missing: a standardized, verifiable answer to "who is this user?" Layering it on top of an already-deployed authorization framework, rather than inventing something new, was the right design decision because it let OIDC reuse OAuth's entire endpoint and flow infrastructure.

The ID token

The ID token is OIDC's core addition. It's a JWT, it's issued alongside the access token at the /token endpoint, and it is for the client — not for any API. This is the distinction that matters most: the ID token says who you are; the access token says what you're allowed to do with this specific API. Sending an ID token to a Resource Server, or using an access token as proof of identity, are both protocol misuses that show up constantly in real deployments.

Standard OIDC claims carry specific architectural meaning: sub (the stable, unique subject identifier — never reuse this for a different user), iss (which Authorization Server issued this), aud (which client this ID token is for), exp/iat (validity window), and nonce (binds the token to a specific authentication request — more on this below).

The UserInfo endpoint exists for claims that are too large or too sensitive to embed in every ID token — the client calls it with the access token to pull additional profile data on demand, rather than bloating every token. OIDC scopes control what's returned: openid is mandatory and triggers OIDC behavior at all; profile, email, address, and phone each unlock a defined claim set.

This split matters architecturally for a reason beyond token size: the ID token is signed once at issuance and the client typically caches it for the life of the session, while a UserInfo call happens fresh, on demand, against current directory state. If an attribute changes mid-session — a department transfer, a group membership update during an access review — the ID token won't reflect it until the next full authentication, but a UserInfo call will, because it reads PingDirectory live. Architects choosing what to embed in the ID token versus what to leave for UserInfo are really deciding how stale an attribute is allowed to get before it matters.

OIDC reuses OAuth's flows directly — Authorization Code is the standard choice, Implicit is deprecated for the same reasons covered in Section 3.3, and Hybrid combines elements of both for specific native-app scenarios. The discovery document at /.well-known/openid-configuration is how a client learns every endpoint, supported scope, and signing algorithm an Authorization Server offers without hardcoding any of it — PingFederate publishes this automatically for every OIDC provider role it serves.

Before logout, there's session renewal to consider — keeping a user signed in without forcing a full re-authentication every time an access token expires. The classic browser-based pattern is "silent renew": the client opens a hidden iframe back to the /authorize endpoint with prompt=none, and if the user still has a live session at the Authorization Server, fresh tokens come back without any visible UI. It's a convenient pattern, but it depends on the same third-party cookie and iframe behavior that's increasingly restricted by modern browsers — which is part of why long-lived refresh tokens (Section 3.3) have become the more reliable mechanism for keeping a session alive across an extended single-page application session, with silent renew treated as a nice-to-have rather than something the architecture depends on.

Session management is where OIDC gets architecturally interesting at enterprise scale: front-channel logout uses an iframe loaded in the user's browser to notify each relying party of logout, which fails silently if a browser blocks third-party iframes or cookies. Back-channel logout has the Authorization Server call each relying party's logout endpoint directly, server-to-server — more reliable, but it requires the relying party to expose a reachable endpoint. PingFederate's back-channel logout support matters precisely because front-channel logout has become unreliable as browsers lock down third-party iframe behavior.

🔴 The nonce parameter in OIDC

The nonce is a random value the client includes in the /authorize request and expects to see in the ID token. It binds the ID token to the specific authentication request, preventing replay attacks where an attacker captures an ID token and replays it in a different session. Failing to validate the nonce is a security vulnerability even if everything else in the OIDC flow is correct. Check your OIDC client libraries — many handle nonce validation automatically, but custom implementations often skip it.

ID token as a boarding pass, access token as a gate badge. When you board a flight, you show your boarding pass (ID token) to prove who you are and that you're authorized on this specific flight. Once through security, you use your gate badge (access token) to access the lounge, priority boarding, etc. The boarding pass is about you. The gate badge is about what you're allowed to do. Airlines don't let you use the gate badge as ID. OIDC-compliant applications shouldn't use the access token as proof of identity.

🟣 Deep dive: Front-channel vs. back-channel logout

Front-channel logout loads a hidden iframe per relying party in the user's browser pointing at each app's logout endpoint — it depends on the browser actually executing those iframe loads, which modern third-party cookie and iframe restrictions increasingly break. Back-channel logout has the Authorization Server call each relying party's registered logout endpoint directly, server-to-server, with a signed logout token — it doesn't depend on the user's browser at all, which is why it's more reliable for enterprise SSO at scale. PingFederate's back-channel logout support means a single logout event can reliably terminate sessions across dozens of SP connections even if the user's browser closes immediately after clicking "Sign out."

3.5 SAML 2.0: The Enterprise Federation Standard

SAML 2.0 was finalized in 2005, when XML, SOAP, and browser form-post redirects were the default enterprise integration stack. It still runs an enormous share of enterprise SSO today — not because it's outdated and waiting to be replaced, but because the applications it was built to federate (Salesforce, Workday, ServiceNow, SAP) standardized on it and still support it as a first-class option.

SAML defines three roles, which map exactly onto the trust triangle from Module 01: the IdP (Identity Provider, who authenticates the user), the SP (Service Provider, the application granting access), and the Principal (the user). The core artifact that flows between them is the SAML assertion — an XML document, signed (and optionally encrypted) by the IdP, that makes a statement: "this user authenticated, here's when, and here's what I know about them."

Bindings, flows, and identifiers

SAML defines several bindings — the mechanism by which the assertion or request travels between parties: HTTP Redirect (compact data in the URL, used for the AuthnRequest), HTTP POST (the assertion delivered via an auto-submitting HTML form — used for the larger assertion payload), and Artifact (a reference is passed through the browser, and the actual assertion is fetched back-channel — more secure, more complex, less commonly deployed).

The trade-off between these bindings is mostly about where the sensitive payload travels. Redirect binding keeps everything in the URL, which has a practical size limit and exposes the request to anything that logs URLs — fine for an AuthnRequest, which carries no sensitive user data, but never used for the assertion itself. POST binding moves the payload into the form body, off the URL entirely, which is why it's the standard choice for delivering the assertion. Artifact binding goes a step further: only an opaque reference ever touches the browser, and the SP retrieves the real assertion through a direct back-channel call to the IdP — eliminating browser-side exposure altogether, at the cost of an extra round-trip and a back-channel connection the SP must be able to make. Most enterprise deployments default to POST for the assertion and Redirect for the AuthnRequest, reserving Artifact for environments with stricter exposure requirements.

There are two initiation patterns. SP-initiated starts when the user hits a protected resource at the SP, which sends an AuthnRequest to the IdP — this request carries a unique ID that the SP can later correlate against the response. IdP-initiated starts at the IdP's portal — the user clicks an app tile and the IdP pushes an assertion to the SP with no prior request. This sounds convenient, but it has a real security implication: with no AuthnRequest, there's no request ID to correlate the response against, which removes a layer of replay protection.

NameID is how SAML identifies the user to the SP, and its format matters architecturally: persistent gives a stable, opaque identifier ideal for account linking; transient is a one-time-use identifier for privacy-sensitive scenarios; email and unspecified are simpler but tie identity to a potentially-changing attribute.

Choosing the wrong NameID format has a specific, recurring failure mode: if an SP correlates users by email and a user's email address changes (marriage, department transfer, a corporate rebrand), the SP sees what looks like a brand-new user with no history — orphaning their existing account, permissions, and data. A persistent NameID, by contrast, stays stable across that kind of change because it's never tied to a human-readable attribute in the first place. This is exactly the kind of detail that looks like a minor configuration choice during initial SP onboarding and becomes a painful, hard-to-diagnose production incident eighteen months later.

User attributes travel in the assertion's AttributeStatement — built by PingFederate from the directory data covered in Module 02 (group memberships, department, email, and so on pulled from PingDirectory or AD). SAML metadata is the XML document each party publishes describing its endpoints, certificates, and supported bindings; metadata exchange is literally how IdP↔SP trust gets established, and expired metadata (specifically expired signing certificates) is one of the most common real-world causes of a sudden SSO outage — directly connecting back to the trust-failure scenarios in Module 01.

SAML separates signing (proves the assertion wasn't tampered with and really came from the claimed IdP) from encryption (protects the assertion contents from being read by anyone other than the intended SP, even if intercepted in transit). A mature deployment uses both — signing is closer to universal, encryption is reserved for assertions carrying sensitive attributes.

🟡 When to use SAML vs OIDC

SAML is the right answer for enterprise application integration where the SP is an established enterprise application (Salesforce, Workday, ServiceNow, SAP) — these apps have excellent SAML support and often offer SAML as their primary federation option. OIDC is the right answer for modern web apps, mobile apps, APIs, and anything you're building yourself. The mistake architects make is trying to mandate one or the other universally — in a real enterprise, you'll maintain both for the foreseeable future.

🔴 The SAML assertion replay attack

A SAML assertion has validity conditions (NotBefore, NotOnOrAfter). If an attacker captures an assertion in transit, they can potentially replay it at the SP before it expires. Mitigations: short assertion lifetime (minutes, not hours), the SP tracks InResponseTo values and rejects duplicate assertion IDs, HTTPS-only ACS endpoints. Check your PingFederate SP connection configurations — what assertion lifetime are you issuing?

🟣 Deep dive: SAML holder-of-key subject confirmation

The standard SAML subject confirmation method is bearer — whoever presents the assertion is treated as the legitimate subject, with no additional proof required. Holder-of-key raises the bar: the assertion is bound to a specific cryptographic key the subject holds (typically a client certificate), so even if an assertion is intercepted, the attacker can't use it without also possessing the private key. Enterprises adopt holder-of-key for very high-assurance scenarios — government, defense, financial-services federations — where bearer's "possession equals authorization" model isn't an acceptable risk posture, and where every party in the federation can support the added certificate-management overhead.

3.6 JWT: Structure, Claims & Validation Architecture

It's worth saying plainly: JWT (JSON Web Token) is a format, not a protocol. It's used by OIDC, by OAuth 2.0 access tokens, and by plenty of systems that have nothing to do with identity federation at all. Understanding JWT as a self-contained format is what lets you reason about it independently of whichever protocol happens to be using it.

The three parts

A JWT is three base64url-encoded segments joined by dots: header.payload.signature.

  • Header — contains alg (the signing algorithm), typ (the token type, always "JWT"), and kid (a key identifier telling the validator which public key to use).
  • Payload — the claims. Registered claims (iss, sub, aud, exp, nbf, iat, jti) have standardized meaning across every JWT consumer. Public claims are registered in IANA's JWT registry for shared use. Private claims are whatever the issuer and consumer agree on between themselves — PingFederate's custom claims fall here.
  • Signature — computed over the header and payload, and this is what makes the token tamper-evident: changing any claim invalidates the signature.

Symmetric signing (HS256) uses one shared secret to both sign and verify — simple, but every party that can verify a token can also forge one, which limits it to closed, internal systems with one trusted secret holder on each side. Asymmetric signing (RS256, ES256) uses a private key to sign and a public key to verify — the private key stays exclusively with the Authorization Server, while any number of Resource Servers can safely hold the public key and verify tokens they could never forge. The JWKS endpoint (JSON Web Key Set) is how that public key gets published and discovered, and key rotation works by publishing a new key under a new kid while the old key remains available just long enough for in-flight tokens to expire.

A full JWT validator must perform a specific sequence of checks — skipping any one of them reopens an attack the check exists to close: decode the header and locate kid; fetch the matching public key from JWKS (or cache); verify the signature; validate iss (is this the expected issuer?); validate aud (is this token intended for this Resource Server?); validate exp (not expired); validate nbf (not used too early); and check jti against a revocation list if your architecture requires it.

There's also a fundamental trade-off between opaque tokens and JWTs: an opaque token carries no information itself and must be checked against the Authorization Server's /introspect endpoint on every use, while a JWT can be validated locally using only a cached public key — far better for performance and availability, at the cost of being unable to instantly revoke an individual token before its natural expiry.

Finally, claims function as the authorization data plane: groups, roles, and entitlements embedded directly in the token let a Resource Server make access decisions without an extra network call. But claims have real limits — they're fixed at token-issuance time and can't express dynamic, contextual, or fine-grained policy (e.g., "this user can approve invoices under $1,000 but not over"). That gap is exactly what Module 08's policy-engine content addresses.

One more distinction worth holding onto: everything above describes a JWS (JSON Web Signature) — a signed JWT, which is what nearly every OIDC ID token and OAuth access token actually is. A JWE (JSON Web Encryption) is a different, less commonly used variant: instead of (or in addition to) signing, the payload itself is encrypted, so that only a holder of the correct decryption key can read the claims at all, not just verify them. Signing proves a token wasn't tampered with; encryption hides its contents from anyone who isn't the intended recipient. Most enterprise JWT usage relies on signing alone, because the claims aren't secret — they just need to be trustworthy. Encryption is reserved for tokens carrying genuinely sensitive data that shouldn't be readable by intermediate parties, mirroring the signing-vs-encryption distinction already covered for SAML assertions in Section 3.5.

🔴 The alg:none attack

The JWT specification originally allowed an algorithm value of "none" — meaning the signature should not be validated. Some early JWT libraries honored this, allowing an attacker to forge tokens by simply setting alg to "none" and stripping the signature. Any JWT library that accepts alg:none in production is critically vulnerable. Verify that your token validation code (or your PingFederate configuration) explicitly rejects unsigned JWTs.

🔴 JWT clock skew

exp and nbf claims are epoch timestamps. If the issuer's clock and the validator's clock disagree by even a few minutes, valid tokens get rejected (clock skew forward) or expired tokens get accepted (clock skew backward). Enterprise deployments must enforce NTP synchronization across all systems that issue or validate JWTs — and must configure a small (60–300 second) clock skew tolerance in validators.

JWT validation is exactly like verifying a signed JAR file in Java. The JAR contains the payload (classes). The signature in the manifest proves the content hasn't been tampered with since it was signed by the publisher's private key. The validator uses the publisher's public key (from the certificate chain) to verify the signature without needing access to the private key. JWTs use the same cryptographic pattern: the Authorization Server's private key signs, the Resource Server's validator uses the published public key (via JWKS) to verify.

🟣 Deep dive: JWT introspection (RFC 7662) vs local validation

Introspection sends the token to the Authorization Server's /introspect endpoint on every single use and gets back a live answer: still valid, or already revoked. Local JWT validation checks the signature and claims entirely offline, using a cached public key, with no network round-trip. The trade-off is direct: introspection gives you instant revocation at the cost of a network call (and a hard dependency) on every request, while local validation scales effortlessly and survives Authorization Server outages, but can't revoke an individual token before its natural expiry — you can only shorten token lifetimes or maintain a separate revocation list checked via jti. High-throughput Resource Servers default to local validation with short-lived tokens; introspection is reserved for scenarios where instant revocation is a hard requirement.

3.7 Protocol Selection Framework

At some point every IAM architect gets asked, "which protocol should we use for this integration?" — and the answer should never be a personal preference. It's a decision driven by a specific set of variables: the application type (web, mobile, SPA, server-to-server), whether the integration is enterprise-facing, consumer-facing, or partner-facing, what the Service Provider already supports (SAML-only? OIDC? both?), whether the implementing team can correctly build an OIDC integration, the required security assurance level, and any legacy constraints (an app that's been running SAML for 15 years isn't getting re-platformed just to switch protocols).

That "can the team implement it correctly" variable deserves more weight than architects usually give it. OIDC's flexibility is also its risk: a team that skips nonce validation, mishandles PKCE, or trusts the ID token at the Resource Server has built something that looks correct in a demo and fails silently in production. SAML's rigidity — heavier libraries, more boilerplate, less room to improvise — is sometimes the safer choice precisely because there's less surface area for a team to get wrong on their first attempt. Protocol selection isn't only about the application; it's also an honest assessment of who's going to build and maintain the integration.

Security assurance level is the other variable that tends to get skipped in a rushed integration conversation. A low-assurance internal tool with no sensitive data has very different protocol requirements than a SOX-relevant finance application or a system handling protected health information. Higher assurance typically pushes toward asymmetric JWT signing over symmetric, mandatory PKCE even for confidential clients, shorter token lifetimes, and — in the highest-assurance cases — SAML's holder-of-key subject confirmation (Section 3.5) over bearer. The protocol itself rarely changes based on assurance level; the configuration choices within that protocol do.

Real enterprises don't standardize on one protocol — they run all three simultaneously, and PingFederate's hub role (Section 3.8) is exactly what makes that coexistence manageable rather than chaotic. The common integration patterns by application type are fairly stable across enterprises: SaaS enterprise apps (Salesforce, Workday, SAP) → SAML; modern web apps → OIDC Authorization Code + PKCE; mobile apps → OIDC Authorization Code + PKCE; machine-to-machine → OAuth Client Credentials; legacy apps with no OIDC or SAML support → an adapter or reverse-proxy pattern that translates on their behalf.

Watch for protocol anti-patterns: choosing ROPC "because it's simple," sticking with Implicit grant "because it works in the browser," or forcing SAML onto a mobile app because that's what the team already knows. Each of these trades a small amount of integration effort today for a security or maintainability cost later.

Protocol selection is like choosing a shipping method, not a religion. You wouldn't ship a single document across town by ocean freight just because your company "standardized on ocean freight" for its export business — you'd use the method that fits the cargo, the distance, and the urgency. SAML is ocean freight: heavier, slower to set up, but extremely well-proven for large, established enterprise relationships. OIDC is air freight: faster to integrate, lighter-weight, ideal for anything modern and fast-moving. An enterprise that insists on one shipping method for every package isn't being disciplined — it's ignoring what the cargo actually needs.

3.8 Federation Patterns & Topologies

Federation topology is about how multiple IdPs and SPs connect across an enterprise IAM ecosystem — and the shape of that topology has direct operational consequences.

Point-to-point federation connects each IdP directly to each SP. It's simple to reason about for a single connection, but it doesn't scale: 10 IdPs × 50 SPs means 500 individual trust relationships, each with its own certificate lifecycle and configuration to maintain.

Hub-and-spoke federation routes every connection through a central federation hub — PingFederate — so SPs connect to the hub and IdPs connect to the hub, turning an N×M problem into roughly N+M connections. PingFederate's value as a hub goes beyond simplifying the connection count: it translates between SAML and OIDC, and between multiple upstream IdPs and downstream SPs that would otherwise have no way to speak to each other.

Mesh federation connects multiple hubs to each other with their own trust relationships — this shows up in large multi-organization environments, government federations, and healthcare trust frameworks where no single hub can or should own every relationship. A mesh topology trades the simplicity of a single hub for political and operational reality: in a merger of two large companies, neither side's PingFederate instance is going to fully absorb the other on day one, so the two hubs federate with each other instead, each retaining authority over its own IdPs and SPs while exposing a controlled trust boundary to the other. M&A divestiture work — separating one company's identity infrastructure back out of a shared hub — is the mirror image of this same problem, and it's exactly the kind of topology decision that takes real architectural judgment rather than a checklist.

Brokered identity (identity proxy) is the architectural role PingFederate plays as a hub: it doesn't just route traffic, it translates protocols, enriches attributes, and enforces policy at the federation layer itself.

The attribute authority question — where do the attributes in a token or assertion actually come from? — traces a specific flow: the upstream IdP passes whatever claims it has, the hub enriches them from the directory (Module 02's PingDirectory/AD content), and the downstream SP receives the enriched result. This enrichment step is where a lot of real architectural value gets created and a lot of real bugs get introduced: an upstream partner IdP might only know a user's email address, while the downstream SP needs department, cost center, and group membership to make an authorization decision. The hub is what bridges that gap — but it also means the hub now owns a transformation rule that, if wrong, silently corrupts every assertion that passes through it. Treat attribute mapping and transformation rules with the same change-control rigor as any other production configuration, because a broken transformation doesn't throw an error — it just hands the SP the wrong department or an empty group list.

Protocol translation is the concrete version of this: PingFederate can receive a SAML assertion from an upstream corporate IdP and issue an OIDC token to a downstream SP, with neither party needing to know what protocol the other one speaks.

🟣 Deep dive: What does protocol translation actually cost architecturally?

Every translation point in a federation topology is a place where the hub must hold enough trust and enough information to re-issue a credential in a different format — which means it's also a place where a compromise or misconfiguration has outsized blast radius. When PingFederate translates an upstream SAML assertion into a downstream OIDC token, it isn't just reformatting data: it's making an independent assertion, under its own signing key, that "this user authenticated, and here is who they are" — separate from whatever the upstream IdP originally signed. That's a deliberate trust decision, not a mechanical one. The architectural cost shows up in three places: the hub's signing key becomes a single point of failure for every translated relationship behind it; the hub's attribute-mapping logic becomes the de facto source of truth for downstream authorization, even though it didn't originate the data; and the hub itself becomes the place auditors look first when something about a user's access doesn't trace back cleanly to its origin. None of this is a reason to avoid the hub-and-spoke pattern — point-to-point federation has worse problems at scale — but it is the reason hub configuration changes deserve the same scrutiny as a production code deployment.

Real-World Scenario: The Protocol Consolidation Project

A large enterprise runs PingFederate with 90 SP connections: 55 SAML, 25 OIDC, 10 custom/proprietary. The new CTO wants to "standardize on OIDC."

🔵 Situation

The CTO's directive arrives as a flat mandate with a deadline, no budget line, and no inventory of why each of the 90 SPs is on the protocol it's on. Some of the 55 SAML connections are recent; many are 8–10 years old, tied to vendor contracts the company doesn't control.

🔴 Constraints

A meaningful share of the SAML SPs are commercial SaaS platforms (Workday, SAP, legacy ServiceNow modules) whose OIDC support is either absent, partial, or requires a paid tier upgrade the company hasn't budgeted for. The 10 custom/proprietary connections were built by teams that no longer exist in their original form, with no current owner.

🟢 Decision Framework

Segment the 90 connections into three buckets: (1) SPs where OIDC is already supported and the migration is low-risk — prioritize these first for visible early wins; (2) SPs where SAML is the vendor's primary or only supported option — these are not migration candidates, full stop; (3) custom/proprietary connections with no clear owner — these need an ownership and risk assessment before any protocol conversation even starts.

🟡 Migration Architecture

For bucket (1), migrate incrementally behind the PingFederate hub, validating each cutover against a rollback plan before decommissioning the old SAML connection. For bucket (2), the architecture doesn't change — document explicitly why, so the decision survives the next leadership turnover. For bucket (3), establish ownership and current usage before deciding whether to migrate, retire, or leave as-is.

🔵 What You Never Migrate

Any SP where the vendor's primary, best-supported integration path is SAML. Forcing OIDC onto a SAML-native vendor integration trades a stable, well-tested connection for a worse-supported one, purely to satisfy a protocol-purity goal that has no real security or operational benefit.

🟢 Outcome

The realistic result of a project like this is never "100% OIDC." It's a smaller, better-understood SAML footprint, a documented rationale for every connection that stays on SAML, and an OIDC-first policy for all new integrations going forward — which is the actual win the CTO's directive was reaching for, even if the literal mandate wasn't achievable.
