Network Authentication: RADIUS, TACACS+, 802.1X & NAC

Before a user ever sees PingFederate's login page, their device has already been authenticated at least once — by the network. The Wi-Fi access point checked their 802.1X certificate. The VPN concentrator validated their credentials against a RADIUS server. The network switch decided whether to put them on the corporate VLAN or the guest VLAN based on a NAC policy. This entire identity layer operates below the web, uses completely different protocols, and is almost never part of an IAM engineer's formal education — which is exactly why it's also the layer that attackers exploit when they've already bypassed web authentication. This module teaches you the architecture of network identity: what it is, how it works, how it connects to the enterprise IAM ecosystem you already know, and how to design it. ⚡

6.1

🌐 The Network Identity Layer: Why It Exists

Every enterprise identity stack you've studied so far in this portal — directories, protocols, the Ping platform, modern authentication — operates at the web layer. A user opens a browser or an app, authenticates, and gets a token or assertion that grants access to a resource. But none of that happens in a vacuum. Before a laptop can even reach PingFederate's login page, it had to get onto the network in the first place. That's a separate identity decision, made by separate systems, using separate protocols, and it's the subject of this module.

A layered identity model

Think of enterprise identity as three distinct layers stacked on top of each other. At the top sits web identity — OAuth, SAML, OIDC — the layer you already know deeply. Beneath that sits network identity — RADIUS, 802.1X — which determines whether a device gets onto the network at all, and what it can reach once it's there. Beneath that sits physical infrastructure identity — TACACS+ — which governs who can administer the network devices themselves. These layers are architecturally distinct, but they're not isolated: network identity constantly delegates back up to the same directories (AD, LDAP) that your web identity stack already relies on.

Why network authentication is architecturally separate

It would be convenient if RADIUS and OAuth were the same protocol wearing different clothes. They're not, and the reasons are structural:

  • Different actors. Web identity authenticates users (and increasingly, services). Network identity authenticates devices as a first-class concern — a laptop, a phone, an IP phone, a printer, an IoT sensor — often before any human has logged into anything.
  • Different protocols. Web identity runs over HTTPS with JSON tokens. Network identity runs at or near Layer 2 — before a device even has an IP address — using protocols designed in the dial-up and early-Ethernet era.
  • Different threat model. Web identity defends against credential theft and phishing aimed at a person. Network identity defends against an attacker plugging an unauthorized device directly into a switch port or impersonating a trusted access point.
  • Different failure modes. When PingFederate has an outage, users can't log into apps — painful, but contained. When a RADIUS server has an outage and the network fails open, every device on every switch port and every Wi-Fi AP gets unauthenticated access to the corporate network simultaneously.

The network access decision

Before a device receives an IP address on the corporate network, something has to decide whether it should get one — and if so, which network segment it lands on. That decision is what Network Access Control (NAC) exists to make, and it's built on top of the authentication protocols this module covers.

The four network identity questions

Every enterprise, whether it has formalized this or not, has to answer four questions before granting network access. Most enterprises only consciously answer the first one — which is exactly the gap this module will help you close:

  1. Who is this user? Answered by querying the same user store your web stack already uses — LDAP or AD.
  2. What device is this? Answered by device certificates, MDM enrollment records, or device fingerprinting.
  3. Is this device healthy? Answered by posture assessment — patch level, disk encryption, antivirus status — typically sourced from NAC or MDM.
  4. What network access should they get? Answered by policy that maps the answers to the first three questions onto a VLAN, an ACL, or a deny decision.

Network identity doesn't operate in isolation from the rest of your IAM stack — it integrates constantly. RADIUS servers query AD or LDAP for credential validation and group membership, exactly the way PingFederate does. Device certificates used in 802.1X are issued by the same enterprise PKI that might issue certificates for other purposes. NAC policy engines read posture data from MDM platforms like Intune or JAMF. The network layer is a consumer of the identity infrastructure you already operate — it just speaks a different protocol to get there.

The attack surface when network identity is weak

When this layer is absent or poorly designed, the consequences are severe and often invisible until a penetration test or an incident surfaces them: rogue devices plugged into conference room ports landing directly on the corporate VLAN, Wi-Fi networks secured only by a shared PSK that every employee (and every departed employee) knows, and network device management planes reachable by anyone who can guess a local admin password. These aren't theoretical — Section 6.9 walks through exactly this scenario as a guided use case.

Analogy

Network authentication is the building lobby security system. Before you reach the elevator bank (the corporate network), the lobby runs three checks: your badge scan (user identity, via RADIUS), your access card's embedded chip (device identity, via 802.1X), and your visitor-versus-employee status (access policy, via NAC, which decides which floors the elevator will even let you select). The elevator only stops at floors you're authorized for — that's your VLAN assignment. PingFederate's login page is the reception desk on the 12th floor: you only get there if you cleared the lobby first. Most IAM programs obsess over hardening the 12th floor and never look at the lobby. That's exactly where the risk lives.

🔒 Security

The most common network identity gap: web SSO gets hardened with MFA and adaptive authentication, but the VPN endpoint accepts username and password without MFA because "it's a separate system." This means an attacker holding stolen credentials can authenticate to VPN — bypassing web SSO entirely — and reach internal resources that implicitly trust anything arriving from the corporate network. Network and web authentication must be governed by the same identity policy. Separate systems is fine. Unified policy is not optional.

6.2

📡 RADIUS — Architecture & Protocol Deep Dive

RADIUS — Remote Authentication Dial-In User Service — is the single most deployed network authentication protocol in enterprise IT, and its name is a fossil. "Dial-In" refers to its origin in the early 1990s, when it was built to authenticate users dialing into ISP modem banks. Telco-era heritage notwithstanding, RADIUS remains the dominant protocol for VPN, Wi-Fi, and switch-port authentication today — not because nothing better was invented, but because it's simple, fast, universally supported by network hardware, and good enough when deployed correctly. Understanding RADIUS deeply is the foundation for everything else in this module.

The RADIUS model: three roles

RADIUS architecture has three actors, and getting the terminology right matters because it's used constantly in vendor documentation and troubleshooting:

  • RADIUS Client — also called the NAS (Network Access Server). This is not the end-user device. It's the network equipment that mediates access: a VPN concentrator, a Wi-Fi controller, or a managed switch. The NAS is the thing standing between the user and the network, deciding whether to let them through based on what RADIUS tells it.
  • RADIUS Server — the authentication authority. This is Windows NPS (Network Policy Server), FreeRADIUS, a PingFederate RADIUS adapter, or Cisco ISE. It receives requests from the NAS, validates credentials (usually against AD or LDAP), applies policy, and returns a decision.
  • RADIUS Proxy — an optional intermediary that routes requests between NAS devices and the correct RADIUS server, typically based on realm (Section 6.3 covers this in depth).

The protocol itself

RADIUS runs over UDP — port 1812 for authentication, port 1813 for accounting (the legacy ports 1645/1646 still appear in older deployments). UDP was chosen for performance: it's lightweight and fast, which mattered enormously when RADIUS was authenticating thousands of simultaneous dial-up sessions on constrained hardware. The tradeoff is reliability — UDP doesn't guarantee delivery, so RADIUS implementations build their own retry logic on top, and packet loss can manifest as confusing authentication timeouts that have nothing to do with credentials being wrong.

Every RADIUS client and server pair share a shared secret — a pre-configured password known only to the two of them. This secret is used to obscure the password field in transit and to verify packet integrity. It is the single most important configuration value in a RADIUS deployment, and Section 6.2's first security callout explains exactly why.

RADIUS packet types

PacketDirectionMeaning
Access-RequestNAS → Server"Here are credentials — is this user allowed in?"
Access-AcceptServer → NAS"Yes — and here's the policy to apply (VLAN, ACL, timeout)."
Access-RejectServer → NAS"No — deny access."
Access-ChallengeServer → NAS"Not done yet — I need more information (e.g. an OTP)." Enables multi-step flows like MFA inside the RADIUS protocol.

RADIUS attributes

RADIUS messages carry their payload as a series of attributes — typed key-value pairs. Standard attributes include User-Name, User-Password, NAS-IP-Address, NAS-Port, and Called-Station-Id. Vendors extend the protocol with Vendor-Specific Attributes (VSAs) — for example, Cisco's Cisco-AVPair attribute carries Cisco-specific authorization data that a generic RADIUS attribute can't express. Attributes are how RADIUS carries both identity (in the request) and policy (in the response) — there's no separate "token" the way OAuth has a JWT; the Access-Accept packet's attribute set is the authorization decision.

Authentication, authorization, and accounting

The RADIUS authentication flow moves credentials from the user, through the NAS, to the RADIUS server, which in turn validates them against AD or LDAP — usually via an LDAP bind. Authorization happens in the same exchange: the Access-Accept packet carries attributes that tell the NAS what to do — which VLAN to assign, which ACL to apply, how long the session should last. RADIUS accounting is a separate, parallel stream of packets (Accounting-Request / Accounting-Response on port 1813) that record session start and stop events — the audit trail you'll rely on for "who was on the network at 2pm last Tuesday."

Password encoding — not encryption

A detail that surprises engineers coming from the OAuth/SAML world: the User-Password attribute in standard RADIUS is encoded using the shared secret and MD5 — it is not encrypted in the cryptographic sense the word usually implies. This is a meaningfully weaker guarantee than TLS-protected credentials, and it's the core motivation behind RadSec.

RADIUS over TLS (RadSec)

RadSec (RFC 6614) wraps RADIUS traffic inside a TLS tunnel, replacing UDP with TCP-over-TLS and replacing the shared-secret trust model with mutual TLS certificate authentication. It fixes the password-encoding weakness and the packet-forgery risk described below. Enterprise adoption is growing but still far from universal — most organizations still run plain RADIUS on trusted internal network segments and reserve RadSec for cases where RADIUS traffic must cross untrusted networks (for example, federated eduroam-style Wi-Fi or multi-site RADIUS proxying over the internet).

🔒 Security

The RADIUS shared secret is the weakest link in the entire RADIUS security model. It's a pre-configured password known to both the NAS and the RADIUS server, used to encode (not truly encrypt) the User-Password attribute and to verify packet integrity via MD5. If the shared secret is guessed or leaked, an attacker can decode passwords from captured RADIUS packets and forge RADIUS responses — sending a fake Access-Accept to a NAS that has no way to know it's lying. Every RADIUS shared secret should be long (32+ characters), genuinely random, unique per NAS device, and rotated on a schedule. RadSec eliminates this vulnerability entirely by replacing the shared-secret model with TLS mutual authentication.

🔒 Security

PAP vs CHAP vs EAP in RADIUS determines exactly how much protection the password gets in transit. PAP (Password Authentication Protocol) sends the password encoded with the shared secret — capture the packet, know the shared secret, and you recover the plaintext password. CHAP (Challenge Handshake) never sends the password at all, only a hash of the challenge plus the password. EAP (Extensible Authentication Protocol) tunnels an entire authentication method inside RADIUS, which is what makes certificate-based auth, TOTP, and FIDO2 possible at the network access layer. For enterprise deployments, EAP-TLS — certificate-based authentication — is the gold standard. Section 6.5 covers it in full depth.

Analogy

RADIUS is to network access what an API gateway is to API access. The API gateway (the NAS equivalent) sits in front of protected resources. When a request arrives, the gateway calls the authorization server (the RADIUS server equivalent) to validate credentials and retrieve policy. The authorization server returns a decision packed with attributes — scopes for OAuth, VLAN assignment for RADIUS. The gateway enforces the policy it's handed. Neither the NAS nor the API gateway makes the identity decision themselves — they delegate it entirely. The pattern is identical between the two worlds. Only the protocol differs.

🟣 Deep dive: Why MD5 in RADIUS is cryptographically weak, and what RadSec fixes

Standard RADIUS uses MD5 to compute the Response Authenticator and to obscure the User-Password attribute, combining the shared secret with a Request Authenticator value via repeated MD5 hashing. MD5 has been considered cryptographically broken for collision resistance since the mid-2000s, and even setting collisions aside, the scheme's security rests entirely on the secrecy of the shared secret — there's no forward secrecy, no protection against an attacker who has captured enough traffic and computing time to attempt offline attacks, and no protection at all if the shared secret leaks. RadSec (RFC 6614) replaces this entire trust model: RADIUS packets are carried inside a TLS tunnel established with mutual certificate authentication between the RADIUS client and server. This gets you modern cipher suites, forward secrecy, and certificate-based mutual trust instead of a static shared password — the same upgrade path web authentication took years earlier when it moved from basic auth over HTTP to certificate-anchored TLS everywhere.

Use Case

Your VPN system uses RADIUS for authentication against Active Directory. An attacker has captured network traffic between the VPN concentrator and the RADIUS server using a compromised network device. Walk through what the attacker can recover from the captured traffic given: (a) PAP authentication, (b) CHAP authentication, (c) EAP-TLS certificate authentication. What does each scenario mean architecturally? With PAP and a known or crackable shared secret, the attacker can recover plaintext credentials directly. With CHAP, they capture only a challenge-response hash — not directly reusable, though still vulnerable to offline attack if the password is weak. With EAP-TLS, there's no password in the exchange to capture at all — the attacker would need to compromise a private key, a fundamentally harder problem. The architectural takeaway: your RADIUS deployment's actual security posture is determined entirely by which authentication method sits inside it, not by the fact that "RADIUS is being used."

6.3

🏢 RADIUS in Enterprise Deployments

A single RADIUS server is a demo, not a production architecture. Every enterprise deployment needs to account for high availability, multi-domain routing, policy complexity, and the inevitable Monday-morning authentication surge. This section covers what RADIUS looks like once it leaves the lab.

Topology: from single server to clustered

A single RADIUS server is a single point of failure — if it goes down, every VPN connection, every Wi-Fi authentication, every 802.1X port fails along with it. The minimum viable production topology is primary plus failover, where the NAS is configured with a backup RADIUS server to try if the primary doesn't respond within a timeout window. The enterprise standard goes further: a clustered deployment behind a load balancer or RADIUS proxy, where multiple RADIUS servers share session state (particularly important for accounting continuity) and any one node can fail without authentication capacity dropping below demand.

RADIUS proxy and realm-based routing

A RADIUS proxy is an intermediary that sits between NAS devices and RADIUS servers, routing each Access-Request to the correct backend server. The most common routing mechanism is realm-based routing: the username carries a realm suffix (user@realm), and the proxy uses that realm to decide which RADIUS server — and by extension, which identity domain — should handle the request. This pattern shows up constantly in multi-tenant environments, partner access scenarios, and — directly relevant to your M&A and divestiture work — acquisition integration, where an acquired company's users need network access routed to their own RADIUS server and AD domain before (or instead of) a full directory migration.

RADIUS and Active Directory: Windows NPS

Windows NPS (Network Policy Server) is the most common enterprise RADIUS server because it ships with Windows Server and integrates natively with AD. NPS organizes policy into two layers: Connection Request Policies, which decide how to handle the incoming request (which NPS server processes it, whether to proxy it elsewhere), and Network Policies, which decide whether to grant access and what attributes to return — the VLAN, the session timeout, the ACL. This two-layer model is conceptually similar to how PingFederate separates authentication policy from authorization decisions.

High availability: fail-open vs fail-closed

When the RADIUS server becomes unreachable, the NAS faces a binary choice: fail-open (let everyone in without authentication) or fail-closed (deny all access until RADIUS recovers). This single configuration decision has outsized security consequences, covered in the callout below.

RADIUS and MFA: the Access-Challenge pattern

RADIUS wasn't designed with MFA in mind, but the protocol's Access-Challenge packet type makes it possible to bolt on without breaking anything. After validating a username and password successfully, the RADIUS server can respond with Access-Challenge instead of Access-Accept, prompting the NAS to collect one more piece of information — an OTP code — before issuing a final decision. This is exactly the mechanism PingID's RADIUS integration uses, covered in full in Section 6.8.

Capacity planning

RADIUS server sizing has to account for peak authentication load, not average load. The classic failure scenario is the Monday-morning VPN surge: thousands of remote employees connecting within the same fifteen-minute window as the workday begins across a time zone. Undersized RADIUS infrastructure drops requests under this burst, and because RADIUS runs over UDP with NAS-side retry logic, a struggling server can produce a confusing mix of successful authentications, outright rejections, and silent timeouts — all from the same root cause.

💰 Architecture Trade-off

RADIUS fail-open vs fail-closed: when the RADIUS server is unreachable, the NAS must decide whether to let everyone in without authentication (fail-open) or deny all access until RADIUS recovers (fail-closed). Fail-open sounds operationally appealing — users keep working through an outage. But it means your network perimeter has zero identity enforcement for the duration of the outage window. If the RADIUS outage is itself caused by an attacker rather than an accident, fail-open hands them exactly the access they were trying to achieve. For all enterprise deployments, RADIUS should fail-closed, and RADIUS HA should be robust enough that the server is effectively never actually unavailable. Fail-open is acceptable only for specific low-sensitivity network segments with compensating controls already in place.

Use Case

Monday morning, 8:47am. 4,000 users attempt VPN connection within fifteen minutes as the East Coast workday begins. Your RADIUS server starts dropping requests under load — some users get in, some get Access-Reject, some get silent timeouts. Walk through the architecture decisions that prevent this: RADIUS server sizing based on peak (not average) concurrent authentication rate, an HA topology with enough headroom to absorb burst load on one node failure, connection request queuing on the proxy layer, and sane NAS retry/backoff behavior so a momentary delay doesn't compound into a retry storm that makes the load problem worse.

6.4

🛡️ TACACS+ — Infrastructure Device Authentication

RADIUS answers "should this user/device get on the network?" TACACS+ answers a different and more privileged question: "should this engineer be allowed to run this specific command on this router?" TACACS+ is the protocol that governs administrative access to network infrastructure itself — switches, routers, firewalls — and it's architecturally distinct from RADIUS in ways that matter.

TACACS+ vs RADIUS: the structural differences

DimensionRADIUSTACACS+
TransportUDPTCP (reliable)

Typical clientVPN concentrator, Wi-Fi controllerCisco IOS, Juniper JunOS devices

The AAA model in TACACS+

TACACS+ separates the three classic AAA functions into independent transactions rather than folding them together the way RADIUS does:

  • Authentication: who are you? Validated against AD/LDAP or a local store.
  • Authorization: what commands are you allowed to run? Evaluated per-command, not just per-session.
  • Accounting: what commands did you actually run? Logged with full fidelity, command by command.

This separation is what makes TACACS+ suited to a fundamentally different problem than RADIUS solves. RADIUS makes one binary decision — let this session in or don't. TACACS+ continuously re-evaluates authorization throughout a session, because a network engineer's SSH session to a core router might run dozens of commands, and not every command should be permitted at every privilege level.

TACACS+ and Cisco IOS

The dominant real-world use case for TACACS+ is network engineers authenticating into Cisco (and other vendor) infrastructure via SSH. Cisco IOS uses a privilege level model ranging from 0 to 15: privilege level 1 is basic user mode with read-only visibility, and privilege level 15 is full enable mode with unrestricted configuration access. TACACS+ is what maps a user's AD group membership onto the correct privilege level — and, critically, what governs which specific commands are authorized once they're at that level.

Command authorization in detail

Every command a TACACS+-protected device receives — not just login, but each individual CLI command — can trigger a separate authorization check against the TACACS+ server. The server's policy decides whether enable, configure terminal, or a specific interface command is permitted for that user, that group, on that device. This is command-level granularity that RADIUS architecturally cannot provide, because RADIUS authorization happens once, at session start, not continuously throughout the session.

TACACS+ and PAM — a connection worth naming now

TACACS+ is, functionally, a network-layer privileged access control mechanism — it's what PAM (Privileged Access Management, covered in full in Module 10) is for general server infrastructure, applied specifically to network devices. If you're familiar with CyberArk's approach to privileged session management, TACACS+ command accounting is solving the same architectural problem one layer down the stack, for routers and switches instead of servers.

When to use TACACS+ vs RADIUS — the decision framework

The decision isn't usually either/or — most enterprises run both, for different purposes. Use RADIUS when the question is "should this user or device get network access" (VPN, Wi-Fi, 802.1X). Use TACACS+ when the question is "should this administrator be allowed to manage this network device, and what exactly are they allowed to do once they're in." Running RADIUS for device management instead of TACACS+ is a common and consequential architectural mistake — covered in the security callout below.

🔒 Security

TACACS+ command accounting is the network-layer equivalent of privileged session recording in CyberArk (Module 10). Every command a network engineer executes on a device is logged: who ran it, on which device, at what time, with what output. This is your audit trail for "who changed that firewall rule at 2am last Tuesday" — a question that is genuinely unanswerable without TACACS+ accounting in place. Enterprises that run RADIUS for device management instead of TACACS+ lose this command-level accountability entirely, because RADIUS authorization is session-level (you're allowed in) rather than command-level (you're allowed to run this specific command). This is one of the clearest examples in the whole module of "the protocol you chose determines what evidence you'll have during an incident response."

Analogy

TACACS+ is to network devices what CyberArk PSM is to servers. CyberArk PSM records every command executed in a privileged server session — who did what, when, on which server. TACACS+ records every command executed in a network device CLI session — who did what, when, on which router or switch. Both are privileged access control mechanisms. Both separate the "who are you" question (authentication) from the "what can you do" question (command authorization) from the "what did you do" question (accounting). The domain is different — servers versus network infrastructure. The architecture is the same.

6.5

🎫 802.1X & EAP: Network Access Control at the Port

RADIUS tells a NAS whether to grant access. 802.1X is the standard that defines how that decision gets enforced at the most granular point possible — the individual switch port or Wi-Fi association — and it does so before the device even receives an IP address. This is genuinely Layer 2 security, operating beneath where most network engineers (let alone IAM engineers) usually think about identity.

What 802.1X is

802.1X is the IEEE standard for port-based network access control. Until a device successfully authenticates, the physical or logical port it's connected to stays blocked — no DHCP, no IP address, no network reachability at all, except for the narrow EAP exchange needed to authenticate. This is meaningfully stronger than "authenticate, then get an IP and maybe get blocked by a firewall later" — the port itself simply doesn't pass traffic until identity is established.

The three 802.1X roles

  • Supplicant: the client device seeking access — the laptop, phone, or IoT device, running 802.1X client software.
  • Authenticator: the network device enforcing the port state — a managed switch port or a Wi-Fi access point.
  • Authentication Server: the RADIUS server making the actual identity decision.

Notice this maps cleanly onto the RADIUS three-role model from Section 6.2 — the Authenticator is the RADIUS client (NAS), just operating at Layer 2 rather than mediating an IP-layer service like VPN.

How it works: EAP over the wire

EAP (Extensible Authentication Protocol) messages flow between the supplicant and the authenticator over Layer 2 — specifically EAPOL, EAP over LAN — before the device has any IP connectivity at all. The authenticator relays these EAP messages to the RADIUS server wrapped inside standard RADIUS Access-Request/Access-Challenge packets, and the RADIUS server's responses flow back the same way. The authenticator itself never makes the authentication decision — exactly the delegation pattern from Section 6.2's API gateway analogy.

EAP methods — the architectural comparison that matters

"802.1X" tells you authentication happens at the port. It tells you nothing about how strong that authentication is — that's entirely determined by which EAP method is configured underneath:

  • EAP-TLS: certificate-based, mutual authentication, the most secure option, requires PKI on both client and server.
  • PEAP (EAP inside a TLS tunnel): an inner method, typically MSCHAPv2, runs inside a TLS tunnel. Only the server presents a certificate; the client still authenticates with a password — encrypted in transit, but still a password.
  • EAP-TTLS: architecturally similar to PEAP, with more flexibility in inner method choice.
  • EAP-FAST: Cisco-proprietary, no certificate required at all — uses a Protected Access Credential (PAC) instead.

Why EAP-TLS is the gold standard

EAP-TLS does for network access what FIDO2 does for web authentication, and the underlying reasoning is identical. A certificate represents both device identity and (when issued per-user) user identity. There's no password in the exchange to steal, phish, or dictionary-attack. Mutual authentication means the client verifies the server's certificate too — which is what prevents rogue access point attacks, where an attacker stands up a fake Wi-Fi AP hoping to harvest credentials. And because certificate-based authentication doesn't require a logged-in user, EAP-TLS supports machine authentication — a domain-joined laptop can authenticate to the network using its machine certificate before anyone logs in, which matters enormously for things like Group Policy delivery at boot.

VLAN assignment and the quarantine path

Just as with standard RADIUS, the Access-Accept packet returned to the 802.1X authenticator carries VLAN-assignment attributes, which the switch enforces by placing the port on the specified VLAN. Devices that fail 802.1X — wrong credentials, expired certificate, or simply no supplicant configured at all — typically land in a Guest VLAN or Auth-Fail VLAN, a quarantine segment with deliberately limited reachability rather than a hard network cutoff. Section 6.6 goes deeper on designing that quarantine policy correctly.

The MAB fallback and its risks

Not every device can run 802.1X — printers, older IP phones, and many IoT devices have no supplicant capability at all. MAC Authentication Bypass (MAB) exists as a fallback: the switch authenticates the device by its MAC address instead of running an EAP exchange. MAC addresses are trivially spoofable, which means MAB is a meaningfully weaker control than genuine 802.1X — the deep dive below covers exactly how much weaker, and why.

🔒 Security

EAP-TLS eliminates password-based attacks on network access entirely. A laptop presenting an EAP-TLS machine certificate offers cryptographic proof of device identity — no password, no credential to phish, no dictionary attack surface at all. Combined with user certificate authentication (both machine and user must present valid certificates), 802.1X becomes as phishing-resistant as FIDO2 is for web authentication, covered in Module 05. The architectural requirement underneath this: enterprise PKI has to issue certificates to every managed device, typically via SCEP/NDES/ADCS auto-enrollment, and to every user. This is real infrastructure work — but it's achievable, and it's the same Active Directory Certificate Services + Group Policy auto-enrollment pattern that's likely already partially in place for other purposes in a mature AD environment.

🟣 Deep dive: MAC Authentication Bypass — why it exists and what it risks

MAB exists because a meaningful population of enterprise network devices simply cannot run an 802.1X supplicant — older IP phones, network printers, badge readers, and a long tail of IoT and OT devices that were never designed with port-based authentication in mind. MAB lets the switch authenticate these devices by MAC address against a RADIUS-backed allowlist instead of running a real EAP exchange. The risk is structural: MAC addresses are visible on the wire to anyone who can see traffic on the segment, and they're trivially spoofable with standard tooling on virtually any operating system. An enterprise that relies heavily on MAB is effectively trusting a value that offers no cryptographic guarantee at all — an attacker who learns a permitted MAC address (often by observing a legitimate device's traffic) can clone it and gain the same network access. The architectural mitigation is to treat MAB strictly as a narrow exception for devices that genuinely cannot do better, place MAB-authenticated devices on tightly scoped VLANs with minimal lateral reachability, and pair MAB with device profiling (Section 6.6) so that a device claiming to be a printer that suddenly behaves like a laptop gets flagged rather than silently trusted.

What PKI infrastructure does that depend on, and is it already in place for any other purpose? That gap analysis is your 802.1X maturity assessment.

6.6

🩺 NAC Architecture: Who Gets What Network Access

RADIUS and 802.1X answer "is this identity valid." NAC asks the question underneath that — "even if this identity is valid, is this device healthy enough to deserve network access right now." This is the policy layer that turns raw authentication into a graduated, risk-aware access decision, and it's where network security architecture and identity architecture genuinely converge.

NAC policy components

A mature NAC policy evaluates several independent signals together, not just one:

  • Identity: who is the user — sourced from RADIUS/802.1X authentication.
  • Device type: laptop, phone, IoT sensor, printer — established through device fingerprinting.
  • Device health: is the device MDM-enrolled, patched, running current antivirus, disk-encrypted, OS-compliant?
  • Ownership: corporate-managed, BYOD, or guest?
  • Location: office, remote, or partner site?

Enforcement outcomes — graduated, not binary

NAC enforcement isn't a single allow/deny switch. Mature deployments support a spectrum: full access (corporate VLAN, all resources reachable), limited access (a restricted VLAN — internet-only, or scoped to specific SaaS apps), quarantine (a remediation VLAN with reachability to patch servers and nothing else), and deny (no access at all, with an alert generated for follow-up).

Two architecture models: inline vs out-of-band

Inline NAC places an appliance directly in the traffic path — an older architecture pattern that creates both a bottleneck and a single point of failure. Out-of-band NAC, the modern standard, is RADIUS-based: there's no inline appliance, and enforcement happens through the same VLAN assignment mechanism RADIUS and 802.1X already use. The NAC platform's value-add is the policy intelligence behind the RADIUS decision, not a separate piece of hardware sitting in the data path.

Posture assessment: agent-based vs agentless

Device health checks happen one of two ways. Agent-based posture assessment runs lightweight software on the endpoint that reports compliance status directly — accurate, but requires deployment and maintenance. Agentless assessment relies on network-observable signals — DHCP fingerprinting, traffic profiling, device behavior patterns — to infer device type and rough health without installing anything. Agentless methods are essential for devices that can't run an agent at all (IoT, OT, guest devices) but offer less granular, less trustworthy signal than a real agent report.

NAC and MDM integration

Platforms like Cisco ISE and Aruba ClearPass don't typically reinvent posture assessment from scratch — they query existing MDM platforms (Intune, JAMF, Workspace ONE) for compliance status that's already being tracked there. This is the same integration pattern you've seen throughout this module: the network identity layer delegates to systems of record it doesn't own, rather than duplicating that data.

NAC as the first Zero Trust enforcement point

Module 14 covers Zero Trust architecture in depth, but it's worth naming the connection now: NAC at the network layer is frequently the first enforcement point in a Zero Trust design — the moment a device's identity and posture get evaluated, before it ever reaches an application. Where traditional perimeter security trusted anything already inside the network, Zero Trust treats network admission itself as just one more continuously-evaluated decision, not a one-time gate.

Diagram 15 of 21 — The outcome matrix: authentication and posture combine to determine the access tier, not just pass/fail.
🟣 Deep dive: How agentless device profiling actually works

Agentless posture and device-type identification rely on passively observable network signals rather than software running on the endpoint. DHCP fingerprinting examines the specific sequence and content of DHCP options a device requests during IP assignment — different operating systems and device classes request options in characteristic patterns, which is often enough to distinguish a Windows laptop from an iPhone from a network printer without asking the device anything directly. HTTP user-agent inspection captures browser and OS strings the first time a device makes an unencrypted web request. MAC OUI lookup maps the first three octets of a MAC address to the manufacturer that was assigned that range, narrowing device type immediately on connection, before any traffic analysis is even possible. CDP and LLDP, where supported, have devices actively announce their own identity to the switch. None of these signals is individually conclusive — OUI ranges can be spoofed, DHCP fingerprints can be forged by a sufficiently motivated attacker — which is why mature NAC platforms combine multiple signals and treat profiling confidence as probabilistic rather than binary, weighting authorization decisions accordingly rather than trusting any single fingerprint outright.

🟢 Architect's Take

NAC policy design is where identity architecture meets network security architecture, and the common mistake is treating it as a binary allow/deny system. Modern NAC architecture uses graduated access: a non-compliant device doesn't get denied outright — it gets quarantined to a remediation VLAN where it can reach the patch server, the MDM enrollment portal, and nothing else. This lets the device self-remediate without a helpdesk ticket, and without leaving a security gap open in the meantime. The real architecture question is: what does your quarantine VLAN actually allow? Just patch servers? Also general internet access for updates? That single decision carries real security implications either way — design it deliberately, don't inherit it as a default from whatever the NAC vendor ships out of the box.

6.7

🔑 VPN Authentication Architecture

VPN deserves its own section because it sits at a unique architectural intersection: it's the primary remote access control point for an enterprise, and unlike Wi-Fi or wired 802.1X, its authentication design varies enormously between organizations — from username-and-password with no MFA at all to fully SAML-integrated SSO. How a VPN authenticates determines exactly what a remote user can reach, which makes it one of the highest-leverage places in the network identity layer to get right.

VPN authentication models, weakest to strongest

  • Username + password: the weakest model, and still surprisingly common — no MFA, no device verification, just a shared secret an attacker can phish or stuff.
  • Username + password + RADIUS OTP: the most common enterprise pattern — adds MFA via the RADIUS Access-Challenge mechanism from Section 6.3.
  • Certificate-based VPN: strong device identity verification, no password to steal, but typically says nothing about which specific user is connecting unless paired with user-level certs.
  • SAML-based VPN: modern VPN clients (Cisco AnyConnect, Palo Alto GlobalProtect) support SAML authentication through the system browser — bringing full web SSO to the VPN authentication layer.
  • Certificate + SAML: the strongest model — device identity via certificate, user identity via SAML, both verified independently.

SAML SSO for VPN — closing the policy gap

This is the architectural development worth understanding deeply. Modern VPN clients can launch the system browser and authenticate the user through it, exactly the way a web application would — meaning PingFederate becomes the identity provider for VPN authentication, not just web SSO. The user goes through PingFederate's actual authentication policy tree: the same MFA requirements, the same adaptive authentication signals, the same risk-based policies that protect every other application behind PingFederate. This is the single biggest lever an IAM architect has for closing the historically common gap between hardened web SSO and loosely-governed VPN access.

Split tunneling and Always-On VPN

Split tunneling routes only corporate-destined traffic through the VPN tunnel while everything else (general internet browsing) goes direct — it exists for performance and bandwidth reasons, but it has identity and security implications worth naming: traffic that doesn't traverse the tunnel isn't subject to corporate network controls at all. Always-On VPN is the architecture for remote workers where the device maintains a persistent VPN connection, typically anchored by certificate-based machine authentication so the tunnel can establish before any user has logged in — this is what makes things like remote Group Policy delivery and centralized patching reliable for an always-remote workforce.

ZTNA vs VPN — the teaser for Module 14

Traditional VPN grants network-level access: once connected, a user typically has IP reachability to a broad swath of the internal network, with further restriction left to firewall rules. Zero Trust Network Access (ZTNA) inverts this: access is evaluated and granted per-application, with identity verification happening continuously rather than once at tunnel establishment. Module 14 covers this transition in full architectural depth — for now, the important framing is that VPN and ZTNA aren't simply "old vs new" implementations of the same idea; they represent genuinely different trust models.

The MFA consistency problem, revisited

This connects directly back to Module 05's MFA bypass discussion and Section 6.1's security callout: when VPN runs RADIUS-based MFA on one policy and PingFederate runs adaptive MFA on a separate policy, an attacker with stolen credentials has two doors to try, and they'll try the weaker one. SAML-based VPN authentication through PingFederate eliminates this by construction — there's only one policy tree, applied consistently regardless of which door the user walks through.

🟢 Architect's Take

SAML-based VPN authentication is the architectural bridge that closes the MFA gap between web SSO and VPN access. When a VPN client authenticates via SAML through PingFederate, it goes through exactly the same authentication policy tree as a web SSO login — same MFA requirements, same adaptive auth signals, same risk-based policies. An attacker who steals credentials cannot bypass MFA by connecting to VPN instead of the web app, because both paths converge on the same policy engine. This is the architecture, not a configuration nicety. If your VPN team is still running username+password+RADIUS-OTP with a separate, weaker MFA policy than web SSO, pushing them toward SAML authentication is one of the highest-leverage security improvements available in the entire network identity layer.

Use Case

A remote employee on a personal MacBook needs VPN access to internal resources. Design the authentication architecture that provides device identity verification (is this a trusted device?), user identity verification with MFA, and access policy enforcement (which internal resources can they actually reach?). On a corporate-managed device, this is straightforward: machine certificate plus SAML through PingFederate, full Always-On VPN. On BYOD, device identity verification becomes much harder — you generally can't issue a trusted machine certificate to a device you don't manage, so the architecture has to lean more heavily on user identity (SAML + strong MFA) and compensate with tighter authorization policy: limited resource reachability, no Always-On posture requirement, and likely a ZTNA-style per-application model rather than broad network-level VPN access.

6.8

🔗 PingID + RADIUS Integration Architecture

Module 05 teased this integration when covering PingID's MFA architecture; here's the full picture. When SAML-based VPN (Section 6.7) isn't available — legacy VPN concentrators, network devices, OT/ICS environments — RADIUS is still the access path, and PingID can still deliver MFA into it. This section covers exactly how a cloud push-MFA service plugs into a protocol that predates it by two decades.

The integration pattern

PingID acts as the MFA provider for RADIUS-authenticated network access through a component generally called the PingID RADIUS Bridge (or, depending on deployment, a PingFederate RADIUS Server adapter). Architecturally, it sits exactly where a standard RADIUS server would sit, but with an extra step woven in:

  1. Receives the RADIUS Access-Request from the NAS, same as any RADIUS server.
  2. Validates primary credentials via an LDAP bind against AD/PingDirectory.
  3. If primary credentials succeed, triggers a PingID MFA challenge through PingOne.
  4. Returns Access-Accept or Access-Reject to the NAS based on the final MFA result.

How push-based MFA fits inside RADIUS

The mechanism that makes this work is the same Access-Challenge pattern from Section 6.3 — except instead of prompting the user to type an OTP, the RADIUS Bridge holds the session open while PingOne sends a push notification to the user's phone and waits for approval. The NAS never needs to know anything about PingID at all; from its perspective, it sent an Access-Request and is waiting on a response, exactly like talking to any other RADIUS server. The push notification experience is invisible to the protocol — it's purely something the Bridge orchestrates behind the scenes during the wait.

Deployment topology and dependencies

The PingID RADIUS Bridge typically deploys close to the existing RADIUS infrastructure — often directly alongside or replacing a Windows NPS instance — and depends on connectivity to both the internal directory (for primary credential validation) and PingOne Cloud (for the MFA challenge itself). For VPN deployments specifically, the configuration change is concentrated entirely on the VPN side: point the VPN concentrator's RADIUS client configuration at the Bridge instead of at NPS directly, and the rest of the VPN configuration is unchanged.

RADIUS-based MFA for SSH

The same Bridge pattern extends to protecting SSH access to servers — a preview of the Linux/Unix authentication territory Module 07 covers in depth. A PAM module on the Linux host can be configured to authenticate against RADIUS instead of (or in addition to) local credentials, which means the same PingID push-MFA experience that protects VPN can protect direct SSH access to a server, using the identical underlying mechanism.

The honest limitation

RADIUS-based MFA, even with PingID behind it, is still fundamentally OTP/push-based — not phishing-resistant in the way EAP-TLS certificate authentication or FIDO2 are. A sufficiently motivated, real-time phishing or push-fatigue attack can still defeat it, the same risk Module 05 covered for web-based push MFA. SAML+PingFederate, when it's architecturally available, is the stronger option precisely because it can layer in adaptive risk signals and isn't constrained by what RADIUS as a protocol can express. RADIUS+PingID earns its place specifically where SAML isn't available: legacy VPN that can't do SAML, network devices, and OT/ICS environments where modern web-auth flows simply aren't supported.

Diagram 18 of 21 — PingID push-MFA wraps inside RADIUS Access-Challenge; the NAS never sees PingID directly.
🔵 Concept

The RADIUS-to-PingID integration works because RADIUS Access-Challenge provides a stateful, multi-step authentication mechanism within a protocol that's otherwise stateless per-exchange. The NAS doesn't need to know about PingID at all — it just sees a RADIUS challenge-and-response cycle, identical in shape to the OTP challenge flow from Section 6.3. PingID's push notification happens entirely outside the RADIUS protocol's awareness; the Bridge holds the RADIUS session open while waiting for the push approval, then responds to the NAS once it has an answer. This is architecturally elegant precisely because nothing about the NAS configuration changes — the user experience gains a push notification, and MFA gets enforced at the network layer, without touching the decades-old protocol underneath.

6.9

🧭 Cisco ISE: Enterprise NAC Platform Architecture

Everything covered in Sections 6.2 through 6.6 — RADIUS, TACACS+, 802.1X, NAC policy — is frequently consolidated into a single platform in real enterprise deployments. Cisco ISE (Identity Services Engine) is the dominant example, and understanding its component architecture gives you a concrete reference implementation for every concept covered so far in this module.

What ISE actually is

ISE combines a RADIUS server, a TACACS+ server, device profiling, posture assessment, a guest access portal, and MDM integration into a single platform with a unified policy engine. Rather than standing up separate point solutions for each of these functions — a RADIUS server here, a TACACS+ server there, a separate NAC appliance — ISE centralizes network identity policy across the entire enterprise.

Architectural components

  • Policy Administration Node (PAN): the central configuration point — where policy sets, authorization rules, and global settings are defined.
  • Policy Service Node (PSN): the workhorse — handles actual RADIUS and TACACS+ requests from NAS devices. Enterprises typically deploy multiple PSNs for capacity and geographic distribution.
  • Monitoring Node (MNT): centralizes logging and reporting across all PSNs, the source for the Live Logs trace used in the lab below.
  • pxGrid: a publish-subscribe API that lets ISE share identity and posture context with other security platforms — covered in the deep dive below.

ISE and Active Directory

ISE connects to AD for user authentication and group membership lookup, the same delegation pattern every other system in this module relies on. ISE maintains some configuration and policy data in its own local store, but it deliberately does not duplicate the identity data itself — AD remains the system of record, exactly as it does for PingFederate.

Policy sets: how ISE organizes decisions

ISE structures its decision-making into policy sets, each containing an authentication policy (who is this, and how should their credentials be validated — EAP-TLS via certificate profile, or PEAP via AD profile) and an authorization policy (given who they are, what access do they get). Authorization policies are ordered rule sets, evaluated top to bottom, where the first matching rule determines the outcome — an authorization profile that specifies exactly which RADIUS attributes to return (VLAN, ACL, session timeout).

Device profiling

ISE fingerprints connecting devices using multiple passive signals — DHCP options, HTTP user-agent strings, MAC OUI (organizationally unique identifier) ranges, CDP/LLDP discovery protocol data — to classify device type without requiring an agent. This profiling data feeds directly into authorization policy: a device profiled as "Cisco IP Phone" can be routed to a voice VLAN automatically, while a device profiled as "Unknown" can be routed to a restricted segment pending manual review.

Posture assessment

ISE's posture service evaluates device compliance using either a lightweight posture agent or agentless methods, checking the same kind of signals covered in Section 6.6 — patch level, AV status, disk encryption — and feeding the result directly into the authorization policy evaluation.

Guest access

ISE's guest portal architecture supports self-registration, sponsor-based approval (an employee vouches for a visitor), or SMS-based verification, each landing the guest device on an appropriately restricted VLAN with time-bound access.

🔒 Security

ISE itself becomes one of the highest-value targets in the enterprise once deployed, because it holds the keys to network admission for every device on every segment. Treat the PAN and PSNs with the same rigor you'd apply to a domain controller: no default credentials, administrative access itself governed by TACACS+ or a comparable control, the management interface reachable only from a dedicated, restricted management network, and ISE software kept current against published CVEs. A compromised ISE deployment doesn't just expose one system — it potentially gives an attacker the ability to grant themselves full VLAN access from any port in the building.

Analogy

Cisco ISE policy evaluation is exactly like PingFederate's authentication policy tree from Module 04. Both systems evaluate a request against an ordered set of rules — each rule has conditions (user attributes, device type, posture state) and an outcome (an access profile, a VLAN, or a step-up requirement). Both support ordered evaluation where the first matching rule wins. Both delegate to external systems — AD for user groups, MDM for posture, PingID for MFA — rather than owning that data themselves. The mental model you already built around PingFederate's policy tree transfers directly to ISE's authorization policy sets. Different domain, same policy engine architecture.

🟣 Deep dive: ISE pxGrid and context-aware security

pxGrid is a publish-subscribe API that lets ISE share live identity and posture context with other security platforms — next-generation firewalls, SIEM tools, threat detection systems — without those systems needing their own integration into RADIUS or AD. When a user authenticates to the network via 802.1X, ISE knows their username, their device, and their posture state; pxGrid publishes that context to subscribers in near real time. A next-generation firewall subscribing to pxGrid can then enforce identity-aware policy — "block this specific user from reaching this segment" — without the user ever having authenticated directly to the firewall itself. A SIEM subscribing to the same feed can correlate network events with actual user identity rather than just IP addresses, which matters enormously during incident investigation, since IP-to-user mapping in DHCP environments changes constantly. The broader capability this enables is context-aware security: instead of every security tool independently trying to figure out "who is 10.4.12.88 right now," ISE becomes the authoritative source that answers that question for the entire security stack, the same way a directory is the authoritative source for "who is jsmith" across the IAM stack.

Use Case

A contractor plugs their personal laptop into a conference room ethernet port. With Cisco ISE + 802.1X + NAC deployed: the port is blocked by default (802.1X), the device fails authentication (no valid credential or certificate), ISE's device profiling identifies it as an unmanaged, non-domain-joined Windows laptop, and the authorization policy routes it to a Guest/Quarantine VLAN with no reachability to internal resources — or, if guest self-registration is configured, to a captive portal requiring sponsor approval. Without ISE deployed: in many real enterprises, the honest answer is that the port has no 802.1X configuration at all, DHCP hands out a corporate IP address immediately, and the contractor's laptop lands on the same broadcast domain as every other corporate device — full network reachability granted by the simple act of finding an open ethernet jack.

📋 Architecture Cheat Sheet

RADIUS = network AuthN/AuthZ for user access (VPN, Wi-Fi, 802.1X) — UDP, shared secret, attributes carry both identity and policy.
TACACS+ = infrastructure device management (routers, switches) — TCP, full encryption, command-level authorization.
802.1X = port-based access control before IP assignment. EAP-TLS (certificate) is the gold standard; PEAP is common but password-based.
NAC = identity + device health + access policy combined — graduated outcomes: full / limited / quarantine / deny.
SAML VPN = bring web SSO MFA policies to VPN access — closes the historically common MFA bypass gap.
PingID RADIUS Bridge = network-layer push MFA using the RADIUS Access-Challenge mechanism.
Cisco ISE = enterprise NAC platform: RADIUS + TACACS+ + device profiling + posture + pxGrid in one system.
Fail-closed for RADIUS is mandatory — HA must be strong enough that an outage never means open access.

🔥 Real-World Scenario: The Network Identity Audit

Situation

An enterprise has 8,000 remote users on VPN authenticating with username + AD password and no MFA; 50 offices running unmanaged Wi-Fi secured only by WPA2-PSK with no 802.1X; 200 network devices managed via local accounts with no TACACS+ anywhere; and no NAC, meaning any device receives a corporate IP address the moment it's plugged in. The CISO has just been shown a penetration test report demonstrating credential stuffing against VPN, a rogue device successfully reaching the corporate network, and an unauthorized configuration change made to a core switch.

Root Cause Analysis

Every gap traces back to the same underlying pattern: network authentication was never treated as part of the enterprise's identity architecture. Web SSO matured under IAM ownership with MFA, adaptive auth, and governance; the network layer was left to network operations, governed by availability and uptime concerns rather than identity policy. The penetration test findings are three independent symptoms of one root cause — an unmanaged trust boundary at the network layer.

30-Day Quick Wins

Enable RADIUS-based MFA on VPN via the PingID RADIUS Bridge (Section 6.8) — closes the credential-stuffing path without requiring a VPN platform change. Rotate every RADIUS and TACACS+ shared secret currently in use, and confirm fail-closed behavior on every RADIUS client. Begin TACACS+ deployment for the highest-criticality core network devices first.

90-Day Medium Term

Pilot 802.1X with PEAP (password-based, faster to deploy than EAP-TLS) on a subset of office Wi-Fi and wired ports, with a properly scoped quarantine VLAN. Begin migrating VPN authentication from RADIUS-only to SAML through PingFederate, unifying VPN and web SSO under one MFA policy. Complete TACACS+ rollout across all remaining network devices.

Full Architecture Target

Enterprise PKI issuing device and user certificates to support EAP-TLS as the default 802.1X method across all offices. Cisco ISE (or equivalent) deployed as the unified NAC platform, combining RADIUS, TACACS+, profiling, and posture under one policy engine. VPN authentication fully migrated to SAML via PingFederate, with certificate-based machine authentication for Always-On VPN on managed devices. WPA2-PSK retired entirely in favor of 802.1X-secured Wi-Fi.

Trade-offs

EAP-TLS and full PKI rollout is the strongest end state but carries real PKI operational overhead and a longer timeline — PEAP is a legitimate interim step, not a failure, as long as it's explicitly treated as interim. Fail-closed RADIUS is the correct security posture but raises availability stakes on RADIUS HA — underinvesting in RADIUS redundancy while moving to fail-closed trades one risk for another. NAC quarantine VLAN scope (Section 6.6) needs deliberate design, not vendor defaults, or the "remediation" segment becomes its own under-governed risk.
