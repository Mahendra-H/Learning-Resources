Linux & Unix Infrastructure Authentication:
PAM, SSSD, SSH & Kerberos

When a system administrator types ssh prod-server-42 and presses Enter, a chain of identity verification happens that most IAM engineers have never fully traced. The SSH daemon receives the connection, calls PAM to authenticate the user, PAM delegates to SSSD, SSSD queries Active Directory via LDAP or obtains a Kerberos service ticket, the result comes back, and the shell is granted — or not. This entire chain operates outside PingFederate, outside OAuth, outside SAML. It's the infrastructure identity layer: older than SSO, closer to the metal, and in many enterprises significantly less governed than the web authentication layer sitting above it. That governance gap is where attackers live after initial compromise. This module teaches you the architecture of Linux authentication so you can design, secure, and govern it as rigorously as the rest of the identity stack. ⚡

Section 7.1

1 Linux Authentication Architecture Overview

Every login attempt on a Linux system — whether via SSH, a local console, or the sudo command — travels through a layered authentication architecture that most engineers never inspect. The layers are not magic: they are a set of well-defined components, each with a specific responsibility, that collectively answer the question "who is this person and are they allowed here?" Understanding the architecture from first principles is the prerequisite for securing it.

At the top of the stack sits the service — the program that needs to know who you are. For server access this is sshd; for privilege escalation it is sudo; for console login it is the login program. None of these services implement authentication directly. Instead, they delegate to a standardized abstraction layer called PAM (Pluggable Authentication Modules), which in turn delegates to whatever authentication backends have been configured. Those backends range from the local password file (/etc/shadow) to Active Directory via SSSD, to a RADIUS server, to a hardware MFA token — all through the same PAM interface.

The Four Authentication Pathways

Linux systems support four fundamentally different authentication pathways. An enterprise Linux estate typically uses all four simultaneously on different hosts — or on the same host for different use cases. Each pathway has distinct security properties, governance implications, and operational trade-offs.

2 Four Linux Authentication Pathways
Path 1 · Local Authentication
Mechanism: /etc/passwd + /etc/shadow

Flow: PAM → pam_unix.so → /etc/shadow

✓ Pros: Fast, no network dependency, works during AD outages

✗ Cons: No central governance · Deprovisioning requires touching every host · No IGA coverage · Root account multiplies unchecked

Enterprise use: Emergency break-glass only. Never for regular user accounts.
Path 2 · LDAP via SSSD
Mechanism: PAM → SSSD → AD/LDAP bind

Flow: PAM → pam_sss.so → SSSD → LDAP bind as user

✓ Pros: Centralized identity · AD-integrated · Full lifecycle via AD · SSSD caching for resilience

✗ Cons: Network dependency · Password transmitted (encrypted) · No mutual authentication

Enterprise use: Standard for AD-integrated Linux hosts. Most common enterprise deployment.
Path 3 · Kerberos via SSSD
Mechanism: PAM → SSSD → Kerberos KDC ticket exchange

Flow: PAM → pam_sss.so → SSSD → AS-REQ/AS-REP → TGT → service ticket

✓ Pros: Mutual authentication · Password never on the wire · SSO after initial TGT · Strongest credential protection

✗ Cons: Requires KDC reachability · NTP dependency · Keytab management required

Enterprise use: Preferred for high-security environments, Hadoop clusters, internal Kerberos-aware services.
Path 4 · SSH Key Authentication
Mechanism: SSH daemon + public key challenge-response

Flow: SSH → check authorized_keys → challenge → client signs → verify

✓ Pros: No password transmitted · Private key never leaves client · Phishing-resistant

✗ Cons: Key sprawl at scale · No central revocation · authorized_keys per host · No lifecycle management by default

Enterprise use: Automated/service-to-service access. Migrating toward SSH Certificate Authority model.
All four pathways can coexist on a single host. PAM controls evaluation order. The security properties and governance model differ fundamentally across paths.

The Centralized Linux Identity Problem

The most significant architectural challenge in enterprise Linux identity is the shift from local accounts to centrally managed identities. Every Linux server starts its life with a set of local accounts defined in /etc/passwd — root, system service accounts, and any users the provisioning process added. Over time, in the absence of centralized identity, this list grows: engineers add themselves, scripts add service accounts, and old accounts are never removed. The result is what security teams call local account proliferation — hundreds of hosts, each with its own independently managed user list, with no central visibility, no lifecycle management, and no audit trail beyond local log files.

Centralizing Linux identity means replacing the local account model with a directory-backed model where user identities live in Active Directory (or FreeIPA), authentication happens via SSSD, and the lifecycle of server access is managed centrally — provisioning, deprovisioning, and access review all operate on the directory, and propagate automatically to every joined host.

🔴 The IAM Governance Gap: Linux Server Identity

In most enterprises, Linux server identity is managed by infrastructure or operations teams, not the IAM team. The consequence is a systematic governance gap: no IGA coverage for server accounts, no access reviews, no lifecycle management, and no connection between the HR system's offboarding events and the removal of server access. When an engineer leaves, their AD account is disabled — but their authorized_keys entries on 200 servers remain. Their local accounts on legacy hosts remain. Their sudo rules remain.

This is the Linux equivalent of the orphaned account problem from Module 01 — but operating in a blind spot below the visibility of most IAM programs. An attacker who discovers and exploits a legacy local account that was never deprovisioned has a persistent foothold that no SIEM alert fires for, because the account is technically valid from the system's perspective.

🟣 Analogy — PAM as a Servlet Filter Chain

Linux authentication architecture is a plugin system — a mental model you know well as a Java engineer. PAM (Pluggable Authentication Modules) is conceptually identical to a servlet filter chain. Each PAM module in the stack is a filter: it can allow the request to continue (success), reject it (failure), or add context to the request before passing it on.

The filter chain is configurable per-service — /etc/pam.d/sshd, /etc/pam.d/sudo, /etc/pam.d/su are separate chain configurations for separate services. If LDAP auth fails, does the chain fall through to local auth? That's a control flag configuration decision — exactly like specifying whether a servlet filter's failure is terminal or whether the chain should continue. You've designed filter chains in Java. PAM is the same architecture applied to Linux authentication.

Section 7.2

2 PAM — Pluggable Authentication Modules

PAM is the abstraction layer that decouples Linux services from authentication mechanisms. Before PAM existed (pre-1997), every program that needed to authenticate a user — login, su, ftp, rlogin — contained its own hard-coded authentication logic reading directly from /etc/passwd. Adding a new authentication mechanism (LDAP, Kerberos, smart card) required modifying and recompiling every program that authenticated users. PAM solved this by introducing a single, stable authentication API that all programs call, with the actual authentication mechanisms provided by dynamically loadable modules.

The result: when a system administrator wants to add TOTP MFA to SSH logins, they don't touch the SSH daemon. They add a PAM module (pam_google_authenticator.so or pam_radius.so) to the /etc/pam.d/sshd configuration. The SSH daemon doesn't know or care — it calls the PAM API, and PAM handles the rest.

PAM Management Groups

Every PAM configuration line belongs to one of four management groups, each covering a distinct phase of the authentication lifecycle. Understanding these groups is essential for reading and writing PAM configurations correctly.

  • auth — Verifies the identity of the user. This is the "who are you?" step. Modules in this group check passwords, SSH keys, Kerberos tickets, and OTP codes. This is where authentication happens.
  • account — Checks whether the authenticated account is permitted to access the system. Even if auth succeeds, account checks can block access — for example, if the account is locked, past its access time window, or not in the allowed group for this host. This is the "are you allowed here?" step.
  • password — Manages password change operations. Modules in this group are invoked when a user changes their password, allowing PAM to enforce complexity rules, update multiple backends, and sync passwords across systems.
  • session — Sets up and tears down the user's session environment. This includes creating home directories, applying resource limits, mounting filesystems, and logging session start/end events. Invoked at session open and close.

PAM Control Flags

Each PAM module line carries a control flag that specifies what happens to the stack evaluation when that module succeeds or fails. These flags are the mechanism by which PAM implements conditional authentication logic — the equivalent of boolean short-circuit evaluation in your filter chain.

4 PAM Control Flag Flow Logic
required
✓ Success: Continue evaluating remaining modules
✗ Failure: Mark result as "failed", but continue remaining modules

Effect: All required modules run regardless. Overall result fails if any required module failed. Prevents early-termination information leaks.

✓ Success: Continue evaluating remaining modules
✗ Failure: Immediately stop and return failure — no further modules run

Effect: Hard gate. Use when failure makes further evaluation meaningless or risky.

✓ Success: If no prior required module failed — immediately succeed

✓ Success: Continue (result noted but not decisive)

Control flags are evaluated in order through the module stack. The final result is the aggregate of all decisive modules. A common mistake: using sufficient for network auth with a local fallback — see Section 7.2 architect callout.

Key PAM Modules in Enterprise Environments

Understanding what each PAM module does architecturally — not just that it exists — is essential for designing and auditing PAM configurations.

  • pam_sss.so — The SSSD bridge module. Delegates authentication, account checks, password changes, and session management to the SSSD daemon, which in turn talks to AD, LDAP, Kerberos, or FreeIPA. This is the central module in any AD-integrated Linux host.
  • pam_unix.so — Local authentication against /etc/shadow. The oldest PAM module and the default fallback. Its presence as a fallback after pam_sss.so creates the security risk described in the architect callout below.
  • pam_radius.so — Delegates authentication to a RADIUS server. Enables SSH MFA via PingID, RSA SecurID, or any RADIUS-speaking MFA provider — the same RADIUS infrastructure from Module 06 used here for server-level MFA.
  • pam_google_authenticator.so — TOTP-based MFA. Validates one-time codes from Google Authenticator or any TOTP-compatible app. Used in environments where RADIUS infrastructure is not available.
  • pam_mkhomedir.so — Auto-creates the user's home directory on first login. Essential in AD-integrated environments where the home directory doesn't pre-exist on each host.
  • pam_limits.so — Applies resource limits defined in /etc/security/limits.conf. Controls maximum open files, processes, and other ulimit parameters per user or group.
  • pam_access.so — Access control based on rules in /etc/security/access.conf. Allows restricting which users can log in from which hosts or terminals without modifying SSSD configuration.
  • pam_deny.so — Always fails. Used as an explicit "deny all" catch-all at the end of a PAM stack to ensure that if no prior module succeeded, the result is failure rather than implicit success.
  • pam_permit.so — Always succeeds. Used in account and session stacks where the goal is to permit something unconditionally after prior checks have already validated the request.

A production-grade enterprise SSH PAM stack. The pam_sss.so as sufficient + pam_deny.so pattern is the fail-closed architecture. Compare to the insecure pattern of pam_sss.so sufficient followed by pam_unix.so required, which creates a local auth bypass when SSSD is unavailable.
🟢 Architect Note — The pam_sss + pam_deny Pattern

The most common PAM security mistake: configuring pam_sss.so as sufficient and pam_unix.so as a fallback at the bottom of the auth stack. The intent is graceful degradation — if SSSD can't reach AD, fall back to local accounts. The security consequence: if SSSD is down (AD unreachable), any local account with a valid password can authenticate. If root or service accounts have known passwords, an AD outage becomes a security degradation event that opens a local auth bypass.

The correct architecture: pam_sss.so as sufficient followed by pam_deny.so as required. If SSSD fails, the deny module fires and authentication fails. Accept that hosts are temporarily inaccessible during AD outages — or configure SSSD offline caching (Section 7.3) to handle short outages without opening a local bypass. Emergency access to physically accessible hosts should be via a documented break-glass procedure, not an always-open local auth backdoor.

🔵 PAM and sudo — Privilege Escalation as an Auth Event

The sudo command has its own PAM configuration at /etc/pam.d/sudo. When a user runs sudo, the sudo binary checks /etc/sudoers for authorization rules, then calls PAM for authentication. This means MFA can be enforced for sudo independently of SSH — a user might SSH in with a key (no password), but still be required to enter an OTP code when they sudo to root. SSSD also supports downloading sudo rules from LDAP/AD, enabling centralized sudo policy management without distributing /etc/sudoers files to every host.

🟣 Deep Dive — SSH MFA Without Touching sshd

SSH supports a keyboard-interactive authentication method that delegates multi-step authentication to PAM. When ChallengeResponseAuthentication yes (or KbdInteractiveAuthentication yes in newer OpenSSH versions) is set in sshd_config, the SSH daemon doesn't implement the challenge itself — it hands control to PAM's auth stack and forwards prompts/responses to the client.

This is how pam_radius.so adds OTP to SSH: the RADIUS PAM module sends an authentication request to the RADIUS server (PingID, RSA SecurID), the RADIUS server responds with an Access-Challenge containing a prompt (e.g., "Enter your OTP:"), PAM forwards this prompt via SSH to the client terminal, the user enters their OTP, PAM sends it to RADIUS, and RADIUS responds with Access-Accept or Access-Reject. The SSH daemon only sees PAM returning success or failure — it has no knowledge of RADIUS or OTP. This is the plugin architecture working exactly as designed.

Section 7.3

3 SSSD — System Security Services Daemon

SSSD (System Security Services Daemon) is the enterprise-grade daemon that connects Linux PAM and the Name Service Switch (NSS) to network identity sources — Active Directory, OpenLDAP, FreeIPA, and Kerberos. It was designed specifically to replace the older pam_ldap + nss_ldap approach, which had a critical architectural flaw: it opened a new LDAP connection on every authentication attempt, from every process, with no caching and no graceful handling of network unavailability.

SSSD solves this by running as a system daemon — a long-running service that maintains a persistent, connection-pooled relationship with AD, caches identity data locally, and serves authentication requests from its local cache when possible. PAM modules (pam_sss.so) and NSS modules (nss_sss.so) communicate with the SSSD daemon via a local socket — they don't touch the network directly.

What SSSD Replaced — and Why

The pre-SSSD approach used pam_ldap and nss_ldap, two separate libraries that each opened direct LDAP connections for every operation. This created three categories of problems:

  • Performance: Every id command, every file listing that needed to resolve a UID to a username, and every login attempt opened a new LDAP connection. On a busy server this meant hundreds of concurrent LDAP connections.
  • Availability: If the LDAP server was temporarily unreachable, every authentication attempt failed immediately. There was no caching, no retry logic, and no graceful degradation. An AD blip meant a complete authentication outage on every Linux host.
  • Functionality: pam_ldap could not obtain Kerberos tickets, could not enforce host-based access control, could not download sudo rules, and could not store SSH public keys. Each of these features required additional, independently configured tools.

SSSD addresses all three by architecting identity as a service rather than a library — with connection pooling, local caching, and a unified provider model that supports all features through a single configuration.

SSSD Providers

SSSD separates its functionality into three types of providers, each configurable independently per domain. This separation allows fine-grained control over where identity information comes from vs. where authentication decisions are made vs. who is permitted access.

  • Identity provider — Handles user and group lookups: resolving usernames to UIDs, looking up group memberships, returning user attributes. This is what the id command and getent passwd use. Configured via id_provider in sssd.conf.
  • Authentication provider — Handles credential validation: verifying passwords, obtaining Kerberos tickets, validating MFA responses. Configured via auth_provider.
  • Access provider — Determines whether an authenticated user is permitted to access this specific host. This is the authorization layer most administrators overlook. Configured via access_provider. Default is permit — meaning any valid AD user can log in to any joined host. See the security callout below.
🔴 Security: The access_provider = permit Default

SSSD's access provider default is permit — any valid AD user can log in to any Linux host joined to AD. This is the Least Privilege violation at the infrastructure layer: your finance analyst in AD can SSH to production application servers. Your HR specialist can log in to database hosts. In a large enterprise with thousands of AD users and hundreds of Linux servers, every user has implicit access to every host unless the access provider is explicitly configured to restrict it.

The fix: set access_provider = ad in sssd.conf and configure either ad_access_filter (an LDAP filter that only permits matching users) or simple_allow_groups (a list of AD groups whose members can log in to this host). This is host-based access control via SSSD — the minimum viable access governance for an AD-integrated Linux estate.

🟣 Analogy — SSSD as a Caching Reverse Proxy

SSSD is the caching proxy layer for Linux identity — the same architectural pattern as nginx or Varnish in front of an origin web server. Direct LDAP authentication (pam_ldap) hits the directory on every login — like serving every request directly from the origin with no cache. SSSD caches the identity data locally — like a reverse proxy serving cached content with TTL-based freshness.

The performance and availability benefits are identical: lower latency for the common case (cached user data served from local LDB files), graceful degradation when the origin is temporarily unavailable (offline auth from cache). The offline_credentials_expiration TTL is the cache TTL — the architectural trade-off between availability (serve from stale cache) and security (force re-validation against AD to detect account lockouts or deprovisioning).

🟣 Deep Dive — SSSD SSH Public Key Integration

SSSD supports storing SSH authorized keys in LDAP and fetching them at login time — eliminating per-host authorized_keys file management. The architecture: an sshPublicKey attribute is added to user objects in AD or LDAP. When a user attempts SSH key authentication, the SSH daemon is configured to call an SSSD helper (sss_ssh_authorizedkeys) instead of (or in addition to) reading ~/.ssh/authorized_keys. The helper queries SSSD, which returns the public keys fetched from LDAP.

In sshd_config: AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys and AuthorizedKeysCommandUser nobody. This means SSH public keys can be managed centrally in the directory — add a key to the user object in AD, and within SSSD cache TTL, SSH key authentication works on every joined Linux host without touching any authorized_keys file. Revocation is equally centralized: remove the key from the AD attribute, and it's removed from all hosts at next cache refresh. This is a significant improvement over per-host key management but still not the CA model (Section 7.7) — keys are long-lived, just centrally stored.

Section 7.4

4 LDAP Authentication on Linux

When SSSD authenticates a user via LDAP — the most common authentication path in AD-integrated Linux environments — it performs a specific sequence of LDAP operations that most engineers have never traced in detail. Understanding this sequence is essential for designing the service account permissions correctly, configuring TLS properly, and troubleshooting authentication failures.

The key architectural insight is the double-bind pattern: SSSD cannot bind directly as the user without first finding the user's full Distinguished Name (DN) in the directory. A username like jsmith or a UPN like jsmith@company.com is not sufficient to bind as the user — the LDAP bind operation requires the full DN (cn=John Smith,ou=Users,dc=company,dc=com). SSSD must first bind as a service account with read access to the user directory, search for the user's DN, and only then bind as the user to validate the password.

🔴 Security: ldap_tls_reqcert = demand is Non-Negotiable

The setting ldap_tls_reqcert controls whether SSSD validates the LDAP server's TLS certificate. Setting it to never or allow means SSSD accepts any certificate — including a self-signed certificate presented by an attacker performing a man-in-the-middle attack between the Linux host and the AD domain controller.

An attacker who can intercept LDAP traffic on the network segment between Linux hosts and AD domain controllers, and present a fake certificate, can capture every username and password that SSSD transmits in LDAP bind requests — effectively harvesting credentials from every login attempt. Set ldap_tls_reqcert = demand, and deploy the enterprise CA certificate that signed the domain controller's certificate to /etc/pki/tls/certs/ (or the appropriate location on your distribution) so SSSD can validate it. This is not a hardening recommendation — it is the baseline configuration for any production environment.

Also note: LDAP referrals (ldap_referrals = true) cause SSSD to follow referrals to other domain controllers, which can result in authentication attempts over unencrypted connections if the referred DC doesn't support TLS. Set ldap_referrals = false in most enterprise deployments where all DCs are reachable directly.

LDAP Authentication vs. Kerberos Authentication

SSSD's AD provider actually uses both LDAP and Kerberos — LDAP for identity lookups (finding users, resolving groups, fetching attributes) and Kerberos for authentication (validating credentials). When the auth_provider = ad, SSSD uses Kerberos for the actual password check rather than the LDAP user bind. This is architecturally superior: the password is never transmitted, even encrypted — Kerberos proves knowledge of the password through cryptographic exchange without sending it. Section 7.5 covers this in detail.

When auth_provider = ldap explicitly (less common, used for non-AD LDAP servers), the LDAP user bind approach is used — the password is transmitted, protected only by TLS. The LDAP bind approach has no mutual authentication: the client proves identity to the server, but the server doesn't prove its identity to the client beyond the TLS certificate. This is why ldap_tls_reqcert = demand is so critical for the LDAP auth path — without certificate validation, the mutual authentication guarantee disappears entirely.

5 Kerberos Authentication on Linux

Module 02 established the Kerberos architecture: AS-REQ/AS-REP to get a TGT, TGS-REQ/TGS-REP to get a service ticket, and AP-REQ to present that ticket to a service. That architecture applies here unchanged — what changes is the context. Instead of a Windows workstation authenticating a user to an application server, we have a Linux host authenticating an SSH user to the same Active Directory Kerberos realm. The KDC is identical. The ticket exchange is identical. The Linux-specific elements are the client tooling (sssd, kinit, krb5.conf), the host principal stored in /etc/krb5.keytab, and the credential cache where TGTs live on the filesystem.

Linux Kerberos authentication has a critical advantage over LDAP authentication: the user's password never crosses the network. In Kerberos, the KDC issues a TGT encrypted with a key derived from the user's password. The client decrypts the TGT using the password locally — proving knowledge of the password without transmitting it. An attacker capturing the entire Kerberos exchange cannot recover the password from the AS-REQ/AS-REP packets (though they can attempt offline dictionary attacks against the encrypted response — the Kerberoasting and AS-REP roasting attacks from offensive security).

Kerberos SSO on Linux

One of the most significant benefits of Kerberos authentication on Linux is single sign-on across the session. Once SSSD obtains a TGT during the SSH login, that TGT is cached in the user's credential cache and available for the entire session. Any Kerberos-aware application running under the user's session can request service tickets without prompting for credentials — NFS mounts, HDFS access, internal web services using Negotiate/SPNEGO authentication, and other SSH sessions (via GSSAPI) all benefit from the cached TGT.

This is the infrastructure equivalent of web SSO: just as a PingFederate session cookie allows a user to access multiple web applications without re-authenticating, a Kerberos TGT allows a user to access multiple Kerberos-enabled infrastructure services without re-entering credentials. The trust boundary is the Kerberos realm — everything within COMPANY.COM can be accessed with the same TGT until it expires.

🔴 Security: The Keytab is the Host's Private Key

The keytab file contains the host's long-term Kerberos cryptographic key. If it is copied off the host — by an attacker who has gained root access, by a misconfigured backup that includes /etc/, or by a configuration management system that stores secrets in version control — the attacker possesses a permanent credential for this host's Kerberos identity.

With the keytab, the attacker can impersonate the server in Kerberos authentication exchanges: they can decrypt service tickets presented to the host, potentially revealing user credentials embedded in the AP-REQ authenticator. They can perform pass-the-ticket attacks and man-in-the-middle attacks against Kerberos-authenticated connections to this host. Keytabs must be: permission-controlled (chmod 600, root-only), excluded from all backup systems, excluded from configuration management secret stores, rotated on a schedule, and treated with the same governance rigor as TLS private keys. A keytab exposed in a git repository is equivalent to a private key in a git repository — equally serious, equally common as a finding.

🟣 Analogy — Keytab : Kerberos = Private Key : TLS

The Linux keytab is exactly what a TLS private key is in your Java API deployments. The TLS private key proves the server's identity to TLS clients — stored in a keystore, root-protected, rotated annually, excluded from source control. The Kerberos keytab proves the server's identity to Kerberos clients — stored in /etc/krb5.keytab, root-protected (chmod 600), rotated before AD password expiry, excluded from backups. Same security model, same governance requirements, different protocol stack. If your TLS private key rotation and secret management processes are mature, apply them verbatim to keytab management.

6 SSH Authentication Architecture

SSH (Secure Shell) is the primary remote access protocol for Linux infrastructure. Unlike PAM — which is an authentication abstraction layer — SSH is a complete protocol that handles transport security, authentication, and session multiplexing. SSH authentication is layered on top of the encrypted SSH transport layer (preventing credential capture even without TLS), and supports multiple authentication methods negotiated during the connection handshake.

The SSH daemon (sshd) controls which authentication methods are permitted via /etc/ssh/sshd_config. Methods are attempted in a client-specified order, and the server can require multiple methods to succeed (multi-factor SSH). Understanding each method's architecture — not just that they exist — is the prerequisite for designing a secure and operable SSH authentication policy for an enterprise Linux estate.

SSH Authentication Methods

1. Password Authentication — The user enters a password at the SSH prompt. The password is transmitted over the encrypted SSH transport to the server, where sshd passes it to PAM for validation. PAM delegates to SSSD, SSSD validates against AD (Section 7.4). The password crosses the encrypted SSH channel but does leave the client machine — phishable if the user is directed to a fake SSH endpoint. Configured via PasswordAuthentication yes|no in sshd_config. Should be no for all production servers.

2. Public Key Authentication — The user holds a private key; the server stores the corresponding public key. Authentication is a challenge-response: the server proves the client has the private key without the private key ever leaving the client. This is the most common enterprise SSH authentication method and the subject of Section 7.7's key management discussion.

3. Certificate Authentication — An evolution of public key authentication where the public key is replaced by a CA-signed certificate. The server trusts the CA rather than individual keys. Solves the key management problem at enterprise scale — covered in depth in Section 7.7.

4. GSSAPI/Kerberos — SSH uses an existing Kerberos TGT transparently, without a password or SSH key. If the user already has a TGT from domain login, SSH to a Kerberos-integrated server requires zero additional credentials. The SSH client presents a Kerberos service ticket via GSSAPI. See the Deep Dive below.

5. Keyboard-Interactive — A multi-step authentication method where the server sends prompts and the client responds. Used as the PAM bridge for MFA: RADIUS OTPs, TOTP codes, and push notifications all use keyboard-interactive as the carrier.

SSH Host Key Verification

SSH host keys provide the server-side identity — they prove that the SSH server you connected to is the same server you connected to before. The client stores server host key fingerprints in ~/.ssh/known_hosts. On first connection to a new host, the SSH client displays the host key fingerprint and asks whether to trust it (the "TOFU" — Trust On First Use — model). On subsequent connections, if the host key has changed (server rebuilt, new keys generated, or MITM attack), the client refuses to connect and shows a warning.

Enterprise environments address the TOFU problem by pre-populating known_hosts via configuration management tools (Ansible, Puppet, Chef), or by using SSH Certificate Authority for host certificates as well as user certificates — when both the host and user present CA-signed certificates, the TOFU problem disappears entirely.

🔴 Security: SSH Agent Forwarding is a Lateral Movement Vector

SSH agent forwarding (ForwardAgent yes in ~/.ssh/config or ssh -A) allows an SSH agent running on the client to be accessible from an intermediate (jump) host. The user SSH-es to a jump host with agent forwarding, and from that jump host can SSH to other servers using their local private key — without the private key being copied to the jump host.

The security problem: the SSH agent socket on the jump host is accessible to any process running as root on that host. If an attacker has compromised the jump host with root privileges (an entirely common scenario — jump hosts are high-value targets), they can access the forwarded agent socket and use the private key to authenticate to any server the user has access to, for the duration of the forwarding session. The private key itself is never exposed, but the attacker has equivalent operational capability — they can open SSH connections authenticated with the victim's key.

The correct architecture: disable agent forwarding by default (AllowAgentForwarding no in sshd_config). Use SSH certificates with short lifetimes instead — they eliminate the need for agent forwarding entirely, because the certificate provides its own authentication assertion rather than requiring the private key to be used interactively on the jump host.

🟣 Deep Dive — GSSAPI/Kerberos SSH: Passwordless Auth from AD Session

GSSAPI (Generic Security Services API) is the abstraction layer over which SSH can use Kerberos tickets for authentication. When a user has a valid TGT (from kinit or from SSSD obtaining one at login), SSH can use that TGT to authenticate without any password or key — the TGT proves identity, and the SSH client requests a service ticket for the SSH server's Kerberos principal (host/server.company.com@COMPANY.COM).

To enable: GSSAPIAuthentication yes and GSSAPIDelegateCredentials yes on the client; GSSAPIAuthentication yes on the server (sshd_config). The server must have a valid keytab. The client must have a TGT. The result: ssh server.company.com succeeds without any prompt if the user has a TGT and GSSAPI is configured — true SSO from the AD domain to Linux servers. This is the Linux equivalent of Windows integrated authentication (NTLM/Kerberos passthrough) that Java developers typically access via Negotiate authentication schemes in HTTP. The protocol differs, but the Kerberos SSO principle is identical.

SSH Key Management Approaches

Four approaches to SSH key management exist in enterprise environments, ranging from the default (no management at all) to the architecturally correct solution:

  • Approach 1: Manual management (default) — Engineers add their public keys to authorized_keys files on servers they need access to. No governance, no inventory, no lifecycle. This is the current state in most enterprises that haven't explicitly addressed the problem. It is not a viable long-term architecture.
  • Approach 2: Centralized authorized_keys via SSSD/LDAP — SSH public keys stored in an LDAP attribute (sshPublicKey) on the user object in AD. SSSD fetches keys at login time via the sss_ssh_authorizedkeys helper. Centralizes key storage but keys remain long-lived and require explicit revocation. Better than per-host management, but not the correct long-term solution.
  • Approach 3: SSH Certificate Authority — The architecturally correct enterprise solution. A CA signs short-lived SSH certificates; servers trust the CA. No per-host key distribution, automatic expiry, and certificate issuance can be gated on an authenticated identity session. Covered in depth below.
  • Approach 4: PAM/privileged access tools — Commercial tools (Teleport, HashiCorp Boundary, CyberArk) provide session brokering that abstracts SSH key management entirely. The tool issues ephemeral credentials per session, records sessions, and integrates with the broader PAM governance model. These are covered in Module 10.

SSH Certificate Authority is the architectural solution to SSH key sprawl, and it follows the same principle as every other certificate-based authentication in the identity stack. The server trusts the CA, not individual keys — exactly like TLS (browser trusts the CA that signed the server cert, not the cert itself). More importantly: because certificate issuance is gated on an authenticated OIDC/SAML session from PingFederate, SSH access inherits the full identity assurance of your web SSO layer. MFA completion is captured in the ID token. Group membership is evaluated at issuance. Adaptive authentication risk signals can influence certificate issuance. The SSH CA becomes a policy enforcement point for the identity stack — not a separate, ungoverned credential system.

Practical open-source implementations: Netflix BLESS (Lambda-based SSH CA), HashiCorp Vault SSH Secrets Engine (signs certificates on demand), Teleport (full access platform with built-in SSH CA and session recording). — How many unique key fingerprints are present?
— How many comment fields match current employees?
— How many are unknown, blank, or match former employees?

That ratio is your SSH key sprawl exposure. If unknown keys exist in /root/.ssh/authorized_keys, that is a P1 security finding requiring immediate investigation.
Section 7.8

8 FreeIPA & Centralized Linux Identity

FreeIPA is the open-source centralized identity management solution for Linux and Unix environments. Where Active Directory provides a unified identity platform for Windows environments — Kerberos, LDAP, DNS, Group Policy, PKI — FreeIPA provides the equivalent stack for Linux: MIT Kerberos for authentication, 389 Directory Server (LDAP) for the identity store, integrated DNS, Dogtag PKI for certificate issuance, and HBAC (Host-Based Access Control) rules as the Linux equivalent of Group Policy access restrictions.

In environments that run both Windows (AD) and Linux (FreeIPA), a cross-realm Kerberos trust between the two platforms allows AD users to authenticate to FreeIPA-managed Linux hosts — a single identity in AD, authoritative for both Windows and Linux access. In Linux-only or Linux-heavy environments, FreeIPA serves as the standalone identity platform without any dependency on Windows AD.

🟣 Analogy — FreeIPA is Active Directory for Linux

Active Directory provides Windows environments with: a Kerberos KDC, an LDAP directory (AD DS), an integrated DNS server, a Certificate Authority (AD CS), and Group Policy for policy enforcement. FreeIPA provides Linux environments with: a Kerberos KDC (MIT Kerberos), an LDAP directory (389 Directory Server), integrated DNS (BIND), a Certificate Authority (Dogtag), and HBAC/sudo rules as the policy enforcement equivalent of Group Policy.

The cross-realm trust between FreeIPA and AD is the equivalent of a forest trust between two Active Directory forests — Kerberos referrals allow a principal in one realm to obtain service tickets for resources in the other. Two identity platforms, one trust relationship, unified access across both Windows (AD) and Linux (FreeIPA) environments.

🔵 When to Choose FreeIPA vs Plain SSSD+AD

Choose FreeIPA when: the environment is Linux-heavy with limited AD dependency; AD does not exist or is not available to Linux teams; you need integrated HBAC (host access control) without building it separately in SSSD; you need centralized sudo rule management; you want integrated PKI for host and user certificates; or when an AD trust is acceptable and you want the full FreeIPA feature set alongside AD for Windows systems.

Choose plain SSSD+AD when: AD is already the authoritative identity store and Linux hosts should use it directly; the Linux estate is relatively small; FreeIPA operational overhead is not justified; or when organizational structure keeps Linux and Windows identity management in the same team with AD as the single source of truth.

9 Active Directory Integration for Linux

Joining a Linux host to an Active Directory domain is the foundational operation that enables all the SSSD, PAM, and Kerberos functionality described in previous sections. "Domain join" for Linux means creating a computer object in AD (just like a Windows workstation join), extracting a Kerberos keytab for the host principal, and configuring SSSD to use the AD provider. Modern Linux distributions accomplish all of this with a single command via realmd.

The critical distinction: while Windows domain join configures LSASS (the Windows authentication subsystem) to use AD, Linux domain join configures SSSD + PAM + krb5.conf. Same AD, same Kerberos realm, same LDAP directory — completely different client-side implementation. Understanding this distinction matters when troubleshooting, because the failure modes and diagnostic tools are entirely Linux-specific even though the backend infrastructure is identical to Windows AD authentication.

🔵 The NTP Requirement — Non-Negotiable for Kerberos

Kerberos has a built-in replay attack protection that requires client and server clocks to agree within 5 minutes (clockskew in krb5.conf). If a Linux host's clock drifts more than 5 minutes from the AD domain controller's clock, every Kerberos operation on that host fails — AS-REQ, TGS-REQ, and AP-REQ all include a timestamp that the KDC validates against its own clock. A drift of 5 minutes and 1 second means no users can SSH to that host until the clock is corrected.

Every AD-joined Linux host must have NTP configured (chrony or ntpd) and monitored. The monitoring threshold should be 4 minutes of drift — alerting before the 5-minute Kerberos failure threshold is reached. In containerized environments, the container clock is derived from the host's clock — a misconfigured host NTP creates a Kerberos outage for all containers on that host simultaneously.

Linux Host Lifecycle and AD

Linux hosts should be managed in AD with the same lifecycle rigor as Windows workstations:

  • Provisioning: realm join creates the computer object in a designated OU. Use a standardized naming convention and place Linux hosts in a dedicated OU (ou=LinuxHosts,ou=Computers,dc=company,dc=com) separate from Windows workstations for policy management clarity.
  • Operations: Monitor the computer account password expiry (AD computer accounts change their password every 30 days by default — SSSD and Winbind handle this automatically). Monitor keytab kvno alignment. Verify SSSD health via monitoring integration.
  • Decommissioning: When a Linux host is decommissioned, the AD computer object must be deleted. An orphaned computer object with a valid keytab represents a phantom Kerberos principal — if the keytab was not destroyed with the host (e.g., it ended up in a VM snapshot or backup), it could be used to impersonate a host that no longer legitimately exists in the infrastructure.
⚡ Use Case — Linux Identity Modernization: 500-Server Acquisition

Your company acquires a 500-server Linux estate using local accounts, no AD integration, and no central identity management. Each server has 5–40 local user accounts. SSH keys exist in multiple authorized_keys files. Sudo policy is jsmith ALL=(ALL) ALL for all senior engineers.

12-Month Remediation Architecture:

Months 1–2 (Inventory): Automated scan of all 500 hosts — collect local accounts (/etc/passwd), SSH key fingerprints (authorized_keys), sudo rules (/etc/sudoers), and running services. Build a comprehensive access map: who has access to what, via which credential.

Months 7–9 (Local Account Elimination): For each host, identify which local accounts are necessary (root, service accounts) vs legacy user accounts. Disable legacy local accounts. Implement break-glass procedure for root access (emergency local account with monitored use).

Months 10–12 (Governance): Add Linux server access groups to IGA platform (Saviynt) for access certification reviews. Implement HBAC via FreeIPA or SSSD access filters. Establish quarterly SSH key sprawl scan as ongoing control. Connect SSSD audit logs to SIEM for authentication event visibility.

📋 Architecture Cheat Sheet

Eight architectural principles from Module 07 that belong in every Linux identity design review.

01 · PAM is the invariant abstraction layer
Every Linux service that authenticates users — sshd, sudo, login, su, cron — calls the PAM API. PAM calls the configured module stack. The service never touches the authentication backend directly. Adding MFA to SSH requires only a new PAM module entry, not a change to the SSH daemon.
02 · SSSD is the caching identity proxy
SSSD connects Linux PAM and NSS to AD, LDAP, Kerberos, and FreeIPA. It provides connection pooling, local caching for offline auth, group membership resolution, sudo rules from LDAP, and centralized SSH key storage. It replaced the stateless pam_ldap + nss_ldap approach across all modern enterprise Linux deployments.
03 · pam_sss + pam_deny = fail-closed
Never configure pam_sss.so sufficient followed by pam_unix.so required as a fallback. If SSSD is down, local accounts become the authentication path. Correct pattern: pam_sss.so sufficient followed by pam_deny.so required. Accept that hosts are unreachable during AD outages, or rely on SSSD offline caching.
04 · ldap_tls_reqcert = demand · always
ldap_tls_reqcert = never or allow allows MITM attacks on the LDAP authentication channel — an attacker can capture every password SSSD sends in LDAP bind requests. Deploy the enterprise CA certificate to Linux hosts and set ldap_tls_reqcert = demand. This is baseline configuration, not optional hardening.
05 · SSH Certificate Authority solves key sprawl
Static SSH keys in authorized_keys files do not scale — N engineers × M servers = N×M unmanaged credentials. SSH CA architecture: server trusts the CA, not individual keys. CA issues short-lived certificates (8 hours). Certificate issuance gated on authenticated OIDC session from PingFederate. No key sprawl. Auto-expiry. Full audit trail.
06 · SSH agent forwarding = lateral movement risk
With agent forwarding enabled on a jump host, root access to that jump host gives an attacker the ability to use the forwarded key to authenticate to any server the user has access to. Disable AllowAgentForwarding no by default. Use SSH certificates instead — short-lived certificates eliminate the operational need for agent forwarding entirely.
07 · Keytab = host private key · govern identically
/etc/krb5.keytab is the host's long-term Kerberos credential. If stolen, the attacker can impersonate the host in Kerberos exchanges. chmod 600 · root ownership · excluded from backups · excluded from config management secrets · rotated regularly · treated as a secret with the same governance as a TLS private key.
08 · NTP is mandatory for Kerberos
Kerberos timestamps require client and server clocks within 5 minutes. Clock drift > 5 minutes = complete authentication outage on that host for all AD users. Configure chrony/ntpd on every Linux host. Monitor clock offset. Alert at 4 minutes of drift — before the 5-minute Kerberos failure threshold is reached.

Q1
A security audit finds that /etc/pam.d/sshd has pam_sss.so configured as sufficient with pam_unix.so as a fallback. What is the security risk and what is the correct configuration?
▼

Risk: When SSSD is unavailable (AD unreachable, SSSD crashed, or network partition), the PAM stack falls through to pam_unix.so, which authenticates against /etc/shadow. Any local account with a valid password can authenticate — including service accounts, legacy admin accounts, and any account whose password is known or guessable. An AD outage becomes a security degradation event that opens a local authentication bypass.

Correct configuration:

auth  sufficient  pam_sss.so
auth  required    pam_deny.so

If pam_sss.so succeeds, the sufficient flag exits the chain with success. If pam_sss.so fails (SSSD down), the chain continues to pam_deny.so which always fails — the host is inaccessible. This is fail-closed authentication. SSSD offline caching (cache_credentials = true) handles short AD outages by serving authentication from the local cache without opening a local auth bypass.

Q2
Your Linux estate has 300 servers, each with local SSH key authorized_keys files. An employee leaves. Walk through the removal process and explain why this doesn't scale architecturally.
▼

The manual process: Identify every server the departing employee had access to. On each server, find their public key by fingerprint in every user's authorized_keys and in /root/.ssh/authorized_keys. Remove the matching line. Verify removal. Repeat for all 300 servers. This requires knowing which servers they had access to (which requires a complete inventory — which typically doesn't exist), and performing a manual edit operation on potentially all 300 servers.

Why it doesn't scale: The fundamental problem is that SSH keys in authorized_keys files are a distributed credential store with N×M relationships (N users × M servers). There is no central inventory, no lifecycle management system, and no API for revocation. Removing access is O(N×M) in the worst case. With 300 servers and 50 engineers, that's 15,000 potential key relationships. Even with automation, the process requires discovering access relationships that were never tracked.

The architectural solution: SSH Certificate Authority. The departing employee's certificate expires automatically (8-hour lifetime). If immediate revocation is needed, their identity in the IdP is deprovisioned — the SSH CA won't issue new certificates for deprovisioned identities, and existing certificates expire within hours. Zero per-host changes required.

Q3
SSH logins start failing on a Linux host at 3am. The /var/log/secure log shows Kerberos errors. What is the most likely cause and how do you diagnose it without rebooting?
▼

Most likely cause: Clock skew. Kerberos requires client and server clocks to agree within 5 minutes. A Linux host whose NTP daemon has stopped, drifted, or is pointing at an unreachable NTP server will eventually exceed the 5-minute threshold — after which all Kerberos authentication fails with a "Clock skew too great" error. 3am is a common time for this to appear because it's when daily maintenance windows, cron jobs, or system load changes can cause clock drift to compound.

Diagnosis (no reboot required):

# Check current clock offset
chronyc tracking
# or
ntpstat

# Verify against an AD domain controller directly
date; ssh -o StrictHostKeyChecking=no \
  ad-dc.company.com "date" 2>/dev/null

# Check if NTP daemon is running
systemctl status chronyd
systemctl status ntpd

Fix: chronyc makestep forces an immediate time correction (may be disruptive for running applications). Or restart the NTP daemon: systemctl restart chronyd. Once the clock is corrected, Kerberos authentication resumes immediately — no sshd restart or SSSD restart needed, as Kerberos ticket requests are real-time. Add monitoring: alert at 4 minutes of drift to prevent reaching the 5-minute failure threshold.

Q4
Compare the access control model of (a) SSSD with ad provider and ad_access_filter, versus (b) FreeIPA HBAC rules. When would you choose each?
▼

SSSD + ad_access_filter: Access control is defined per-host in the host's sssd.conf — an LDAP filter that matching users must satisfy to be permitted. For example: ad_access_filter = (memberOf=cn=linux-admins,...). This configuration lives on the Linux host itself, is managed in SSSD config (typically via configuration management like Ansible/Puppet), and references AD groups. It provides host-level access control without requiring FreeIPA infrastructure. The limitation: access policy is distributed across host configs — changing which group can access a host requires updating sssd.conf on that host.

FreeIPA HBAC: Access control rules are defined centrally in FreeIPA (in the LDAP directory), specifying which users/groups can access which hosts/host-groups via which services. Rules are downloaded to clients by SSSD and evaluated locally. Changing access policy requires a single change in FreeIPA — it propagates to all affected hosts within SSSD cache TTL. HBAC is more expressive (service-level control — permit SSH but not sudo), more scalable (one rule applies to a host group), and centrally auditable. Limitation: requires FreeIPA infrastructure.

Choose SSSD + ad_access_filter when: no FreeIPA infrastructure exists, the environment uses AD directly, and per-host config management is acceptable. Choose FreeIPA HBAC when: centralized access policy management is required, host-group-level rules are needed, or service-level access control (ssh vs sudo) is required.

Q5
Design the SSH authentication architecture for a 1,000-server Linux estate that eliminates password SSH, SSH key sprawl, and gives the security team a full audit trail of who SSHed to which server using which identity assertion.
▼

Target Architecture — SSH Certificate Authority with OIDC Identity Gate:

1. Identity Provider (PingFederate): Users authenticate via OIDC with MFA. On successful authentication, they receive an ID token signed by PingFederate. This is the identity gate — no ID token, no SSH certificate.

2. SSH CA Service (HashiCorp Vault SSH Secrets Engine or Teleport): Users present their PingFederate ID token to the SSH CA API along with their SSH public key. The CA validates the token, checks group membership (is the user in linux-admins?), and issues a signed SSH certificate with: principal = username, valid-for = 8 hours, extensions = permit-pty (no agent forwarding), signed-by = enterprise-ssh-ca.

3. Server configuration (all 1,000 servers via Ansible):

# sshd_config
PasswordAuthentication no
PubkeyAuthentication yes
TrustedUserCAKeys /etc/ssh/enterprise-ssh-ca.pub
AuthorizedKeysFile /dev/null   # no per-host keys
AllowAgentForwarding no
AllowGroups linux-admins ops-team   # SSSD AD groups

4. Audit trail: Each SSH certificate contains the user's identity (from the OIDC token), issue timestamp, and validity window. sshd logs certificate authentication events including the certificate serial number. The SSH CA logs every issuance with the full OIDC identity assertion. Optional: deploy Teleport or similar for session recording — full keystroke audit trail per session, searchable by user, server, time, and session content.

Result: No passwords. No per-host key files. Certificate expiry = automatic revocation within 8 hours. Deprovisioning a user in AD/PingFederate blocks new certificate issuance immediately; existing certs expire within the workday. Full audit trail from OIDC token → certificate issuance → SSH session → commands executed.

⚡ Real-World Scenario: The Linux Identity Audit

The 3,000-Server Linux Estate Audit

A realistic enterprise Linux identity remediation scenario
Situation

An internal audit of the 3,000-server Linux estate reveals a fragmented identity landscape: 40% of servers have partial AD integration via SSSD (misconfigured — most with access_provider = permit), 30% use local accounts only with no central identity, and 30% use Winbind (legacy Samba, scheduled for deprecation). An SSH key audit reveals 2,847 unique key fingerprints across authorized_keys files. Cross-referencing against HR records: 634 keys belong to users not in AD (former employees and expired contractors). More critically: /root/.ssh/authorized_keys exists on 890 servers with a total of 1,240 root-level SSH keys — the majority with no identifiable owner in the comment field.

Risk Analysis

Critical (P0): 1,240 unaudited root-level SSH keys represent an unknown number of permanent root-level backdoors. Any key belonging to a former employee, compromised contractor, or unknown origin is a persistent, non-expiring privileged credential that bypasses all AD lifecycle controls. An attacker who obtained one of these keys at any point in the past has current root access to those servers — indefinitely.

High (P1): 634 keys belonging to former employees across the estate represent orphaned credential access. These accounts were deprovisioned in AD (access to web applications and Windows systems revoked) but SSH access to Linux servers was never removed. These are the persistence foothold that a sophisticated attacker exploits after initial compromise — valid credentials that HR systems show as inactive but Linux hosts still honor.

High (P1): 40% of servers with access_provider = permit means any valid AD user — including 8,000+ corporate users — can SSH to those servers with valid AD credentials. No host-level access control exists. Production application servers are accessible to employees in finance, HR, and other non-technical departments.

Medium (P2): 30% of servers with local accounts only have no central deprovisioning. When engineers who set up those servers leave the company, their accounts remain. There is no inventory of which employees have local accounts on which servers.

Immediate Actions (Week 1–2)

Day 1: Freeze new SSH key additions via change management process. Extract all /root/.ssh/authorized_keys content from all 890 affected servers to a centralized analysis repository. Treat this as an incident — engage the security incident response team to assess whether any of the unidentified root keys represent active compromise vs. legacy engineering access.

Days 3–5: Cross-reference all 634 ex-employee keys against HR records and remove from all servers via Ansible playbook. Verify removal. This is the highest-priority remediation because these are known-unauthorized credentials with known former owners.

Week 2: For the 1,240 root-level keys — engage with server owners to confirm ownership of each key by fingerprint. Any key where ownership cannot be confirmed within 5 business days is removed. 90-Day Architecture

PAM standardization (all 3,000 servers): Deploy standard /etc/pam.d/sshd via Ansible with the fail-closed pattern: pam_sss.so sufficient + pam_deny.so required. No pam_unix.so fallback for regular user accounts. Emergency break-glass procedure documented separately.

SSSD access_provider remediation: Update all 1,200 SSSD-integrated servers from access_provider = permit to access_provider = ad with environment-appropriate AD group filters. Production servers: linux-prod-admins group only. Staging: linux-staging-admins. Dev: broader access, but still bounded.

Local account servers: Inventory all 900 local-account-only servers. Begin AD join process prioritized by server criticality. Target: all production servers AD-joined within 60 days; all servers within 90 days.

Winbind deprecation: Migrate 900 Winbind servers to SSSD. Winbind and SSSD can coexist briefly during migration. Target: all Winbind servers migrated within 90 days.
