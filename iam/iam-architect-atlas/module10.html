Privileged Access Management:
CyberArk Architecture & PAM Design

If you could compromise one account in an enterprise and cause maximum damage, which would you choose? Not a regular user's account — those are limited by RBAC and monitored by IGA. You'd choose a domain admin account. Or a root account on a production server. Or a service account with read access to the entire database. Or the account that manages the firewall configuration. These are privileged accounts: the accounts that break the authorization model because their access is, by definition, outside normal controls. Privileged Access Management is the security architecture specifically designed for these accounts. CyberArk is the market leader. This module teaches you the architecture — not how to configure the vaults, but how to design a PAM program, understand what CyberArk's components actually do, and reason about privileged access as the highest-stakes security layer in enterprise identity. 🔒

10.1

What PAM Is and Why It Exists

Every IAM discipline you have studied so far — authentication, federation, authorization, governance — assumes a fundamental property of the access model: that access is bounded. A user gets roles. Roles grant entitlements. Entitlements open specific doors in specific applications. The authorization model defines what each person can do, and IGA ensures those definitions are appropriate, reviewed, and enforced through the identity lifecycle.

Privileged Access Management exists because certain accounts break this assumption entirely. A Domain Administrator account does not have roles that open specific doors — it can change every door, every lock, and every key in the entire Active Directory environment. A Linux root account does not have an entitlement to read a specific directory — it can read, modify, and delete everything on the system. A DBA account does not have row-level access to specific tables — it can query, export, or drop any data in any schema. These accounts are privileged accounts, and their defining characteristic is that they operate outside or above the normal authorization model.

Why Normal IAM Controls Fail for Privileged Accounts

Standard IAM assumes that the authorization model is the ceiling. For privileged accounts, the authorization model is the floor — or irrelevant entirely. Consider each control layer you've studied and how it breaks down for privileged access:

  • RBAC fails: Role-Based Access Control works by granting access through group membership. A Domain Admin account is itself effectively above group membership — it can modify group membership for every group in the directory, including the groups that control access to security systems.
  • ABAC fails: Attribute-Based Access Control applies policies based on user attributes. But if a privileged account can modify user attributes in the directory, ABAC policy conditions can be circumvented by changing the attributes that drive the policy decisions.
  • IGA certification fails: Access certification campaigns review entitlements and revoke inappropriate access. But privileged accounts often control the infrastructure that IGA depends on — an unmanaged Domain Admin could modify the IGA connector's service account, alter directory data, or disable the synchronization that feeds the IGA system.
  • MFA can be bypassed: Multi-factor authentication secures login flows. But privileged accounts often have administrative access to the MFA infrastructure itself — an attacker with Domain Admin access can disable MFA requirements, modify MFA group membership, or reset MFA enrollment for any user.
  • Audit logging can be cleared: Security monitoring depends on audit logs. Root access on a Linux server, Domain Admin access to domain controllers, or DBA access to a database allows an attacker to clear, modify, or disable the very audit logs that would record their actions.

This is why privileged accounts require a dedicated security architecture — not just an extension of standard IAM. PAM assumes that privileged accounts, if compromised, can undermine every other security control. The PAM architecture must therefore protect privileged credentials before they can be used by an attacker.

The PAM Discipline Defined

Privileged Access Management is the security discipline and technology category that governs privileged accounts — accounts with elevated access that bypasses or supersedes normal authorization controls. PAM addresses three fundamental problems:

  • Credential protection: Privileged credentials must not be exposed in configuration files, known to multiple people, or recoverable from system memory. PAM vaults credentials in a dedicated encrypted store with no human knowledge required for routine use.
  • Access accountability: When a privileged action causes an incident, the question "who did this?" must be answerable. PAM provides individual accountability for shared privileged accounts through checkout records and session attribution.
  • Session visibility: Privileged sessions must be observable and reviewable. PAM records privileged sessions — every command, every action — providing the forensic record that post-incident investigation requires.

PAM Scope vs IGA Scope

A common confusion in enterprise IAM programs is where IGA ends and PAM begins. The boundary is not always clean, but the conceptual distinction is clear:

  • IGA (Saviynt) governs: Standard employees, contractors, and partners accessing business applications. Standard entitlements, business roles, SaaS application access, workflow approvals, access certification for normal-privilege identities.
  • PAM (CyberArk) governs: Privileged accounts on infrastructure and systems — domain admin accounts, root accounts, service accounts with administrative rights, shared admin accounts, database DBA accounts, network device administrative accounts, cloud IAM admin accounts, and emergency break-glass accounts.
  • Overlap zone: Privileged business users — a finance director with SAP Basis admin access, a security analyst with SIEM admin rights — sit in both domains. Their standard identity lifecycle is in IGA; their elevated access credentials are in PAM.

The Privileged Account Risk Model

Why do attackers prioritize privileged account compromise? Because a single privileged account provides leverage that no number of standard user accounts can match. The economics of a breach are clear: a domain admin account equals complete environment control. Every other account in Active Directory can be reset, modified, or impersonated. Every system in the domain can be accessed. Every log can be cleared. Every security control can be disabled. This is why the attack path from initial access to significant breach almost always runs through privilege escalation — gaining access to a higher-privileged account than the initial compromise provided.

Zero Standing Privilege: The Architectural North Star

The most important architectural principle in modern PAM is Zero Standing Privilege (ZSP): privileged access should exist only for the duration of the task that requires it — not permanently. A domain admin account that exists around the clock, every day of the year, is vulnerable around the clock, every day of the year. A domain admin account that exists only for the 45 minutes required to complete a specific change task is only vulnerable for those 45 minutes.

ZSP has an architectural implication that runs through every PAM design decision: credentials should be issued on-demand and revoked on completion. This shapes how accounts are structured, how credentials are stored, how sessions are managed, and how approvals are designed. Section 10.7 covers Just-in-Time access — the practical implementation of ZSP — in depth.

PAM Maturity Levels

PAM programs mature along a well-understood progression. Understanding where an organization sits on this scale is the first step in designing the right architecture:

  • Level 1 — Vault only: Privileged credentials are stored in CyberArk but access control is minimal. Users can retrieve passwords from the Vault. No rotation, no session recording. Better than a spreadsheet; not yet a security architecture.
  • Level 2 — Vaulted + Rotated: CPM automates credential rotation. Credentials are never static. Users who leave can't use credentials they once knew because those credentials no longer exist.
  • Level 3 — Vaulted + Rotated + PSM: Session proxying and recording enabled. Users connect through PSM and never see the password. Every privileged session is recorded and auditable.
  • Level 4 — JIT + ZSP: Privileged access is provisioned on-demand and revoked automatically. No standing privilege. Attack surface minimized to the duration of actual tasks. The mature PAM target state.
🔴 Security Architecture Note — Privilege Escalation in Every Breach

The Verizon Data Breach Investigations Report consistently finds that the path from initial access to significant breach almost always involves privilege escalation — gaining access to a higher-privileged account than the initial compromise provided. PAM addresses this at the architectural level: by vaulting privileged credentials (so they can't be found in config files), rotating them frequently (so captured credentials expire quickly), and recording sessions (so post-incident forensics are possible), PAM raises the cost and complexity of the privilege escalation step that every significant breach depends on.

🔬 Lab 10.1 — Find Your Unmanaged Privileged Credentials

Look in: application configuration files (any database connection strings with embedded passwords?), SSH authorized_keys files for service accounts, shared team password documents or wikis, Active Directory service accounts with Domain Admin group membership, and Windows scheduled task credentials. 10.2

Privileged Account Taxonomy

Before you can architect a PAM program, you need to know what you're protecting. Privileged accounts span multiple categories with fundamentally different risk profiles, different PAM treatment requirements, and different failure modes if left unmanaged. The taxonomy below is the foundation for your vaulting scope, rotation policy, and session management decisions.

Domain and Enterprise Admin Accounts

What they are: Active Directory accounts that are members of the Domain Admins or Enterprise Admins groups — the most powerful accounts in a Windows enterprise environment. A Domain Admin can reset any password, add any account to any group, modify any Group Policy, access any domain-joined system, and disable any security control that runs on the domain infrastructure.

Why they're dangerous: Complete AD control means complete enterprise control in Windows-heavy environments. Active Directory is the trust anchor for authentication across the entire organization. If the attacker controls AD, they can create new accounts, elevate existing accounts, forge Kerberos tickets (Golden Ticket attack), and persist indefinitely even after incident response efforts remove the initial foothold.

PAM treatment: Vaulted in CyberArk with individual accounts (not shared — every administrator should have their own admin account, not a shared CORP\administrator). MFA required for every checkout. Sessions always proxied through PSM. JIT is the target state — domain admin access provisioned only for the duration of the specific change task. Rotation every 24 hours for standing accounts; rotation after every session for JIT ephemeral accounts.

Local Administrator Accounts

What they are: The built-in local Administrator account on every Windows system and its equivalents on other platforms. Unlike domain admin accounts, local admin accounts only have control over their specific machine — but that's still complete control over that machine, including the ability to read any file, install any software, and dump credentials from memory.

The built-in Administrator problem: In environments without PAM, every Windows server has the same local Administrator account with potentially the same password (or a password set years ago and never changed). An attacker who compromises one server can use pass-the-hash or credential reuse to access every other server with the same local admin password. This is one of the most common lateral movement techniques in enterprise breaches.

PAM treatment: CyberArk's Local Privileged Account Manager (LAPS) randomizes the local Administrator password on every managed system. Each server has a unique, randomly generated local admin password stored in the Vault. If one server is compromised, the credential cannot be reused on any other server.

Service Accounts

What they are: Accounts used by applications, services, and automation to authenticate to other systems. Examples: a Java application authenticating to a database, a Windows service authenticating to a file share, a monitoring tool authenticating to SNMP endpoints. Service accounts are typically AD accounts or local accounts with specific permissions required by the application they serve.

Why they're dangerous: Service accounts accumulate permissions over time (a new integration requires a new permission, and permissions are rarely revoked when integrations change). Their passwords are often embedded in configuration files, environment variables, or Windows service configurations — effectively static and rarely if ever rotated. When a developer leaves or a server is decommissioned, service account credentials often outlive their legitimate use.

PAM treatment: Vaulted in CyberArk with CPM-managed rotation. Applications retrieve credentials via CyberArk AIM (Application Identity Manager) rather than storing them in config files. The rotation cascade challenge — covered in Section 10.5 — is the primary implementation complexity for service account PAM.

Shared Administrator Accounts

The shared administrator account — a single root or Administrator account known by multiple people — represents the worst convergence of PAM anti-patterns. It combines lack of individual accountability (which of the fifteen administrators who knew the password made that change?), inability to rotate (changing the password breaks every person and process that uses it), and credential permanence (former employees take the password with them when they leave, and it doesn't expire).

🔴 Security Architecture Note — The Shared Password Problem

The shared administrator password is the most dangerous credential type in any enterprise environment. When every system administrator knows the root password or the Domain Admin password, that credential effectively cannot be rotated (changing it breaks every person and process that uses it), cannot be attributed (which of the 15 people who knew the password was it?), and cannot be revoked when someone leaves (they took the password with them). CyberArk's answer: no human knows the privileged credential — they check it out from the Vault for the duration of their task, and CyberArk rotates it after the session ends. Individual accountability is maintained through the checkout record, not the credential itself.

Emergency and Break-Glass Accounts

What they are: Last-resort accounts for scenarios where normal authentication infrastructure fails — the PVWA is unavailable, the domain is unreachable, MFA is broken, or the organization is actively responding to an incident that has taken down normal access paths. Break-glass accounts are intentionally the highest-privilege accounts in the environment and must be usable even when everything else has failed.

Why they're dangerous: By design, break-glass accounts bypass normal controls. They're used in crisis conditions where normal audit and approval processes may be compressed or skipped entirely. They're frequently undocumented, rarely rotated, and often known by more people than should know them ("just in case").

PAM treatment: Sealed in CyberArk with dual-approval workflow for access (two separate approvers must authorize before the credential is released). Mandatory post-access review — every break-glass access triggers an incident ticket and post-mortem review. Rotation after every single use. The DSRM (Directory Services Restore Mode) password for Active Directory domain controllers is a specific example that should be vaulted and rotated regularly.

Cloud Privileged Accounts

What they are: The super-administrator accounts for cloud platforms — AWS root account, Azure Global Administrator, GCP Organization Administrator. These accounts have unrestricted access to every resource in their respective cloud environment, including the ability to delete all data, disable all security controls, modify billing, and revoke access for all other accounts.

PAM treatment: Vaulted in CyberArk with hardware MFA required (not software MFA — hardware tokens for root-equivalent accounts). Conditional Access policies that restrict access to specific IP ranges and locations. Usage should be rare — cloud platforms provide mechanisms (AWS Organizations SCPs, Azure management groups) to accomplish most administrative tasks without using the root account. Heavy monitoring via AWS CloudTrail, Azure Monitor, and GCP Audit Logs, with PTA integration to alert on any root account activity.

🟢 Architect's Lens — Privileged Account Discovery

In a mature PAM program, the number of accounts in CyberArk is always smaller than the actual number of privileged accounts in the environment. The gap between "accounts we know about" and "accounts that exist" is the unmanaged privileged access risk. CyberArk's Discovery & Audit (DNA) tool and CyberArk Endpoint Privilege Manager provide automated discovery of privileged accounts across the environment. Running a discovery scan before designing the vaulting scope is a mandatory architectural step — designing to the known accounts means designing to an incomplete picture.

10.3

CyberArk Architecture — Core Components

CyberArk's architecture is not a monolithic product — it is a platform of specialized components, each owning a distinct layer of the PAM security model. Understanding what each component does, why it exists as a separate architectural piece, and how the components interact is the foundation for making sound PAM design decisions. You cannot design a PAM program by configuring CyberArk; you design it by understanding what each component is protecting and why.

There are five core components in the CyberArk Privileged Access Security (PAS) platform, plus the cloud-hosted variant and the secrets management extension. Each component solves a specific problem that the others cannot.

Component 1 — Digital Vault (Enterprise Password Vault / EPV)

The Vault is the encrypted credential store at the center of the CyberArk architecture. All privileged credentials — passwords, SSH keys, certificates, API keys — are encrypted and stored in the Vault. The Vault is the most hardened component in the entire CyberArk deployment: designed to be the last system standing even in a full environment breach scenario. Every other CyberArk component connects to the Vault to retrieve or update credentials. No credential operation bypasses the Vault. Section 10.4 covers the Vault's architecture in depth.

What it solves: Credential exposure. Credentials are not in config files, not in spreadsheets, not known by multiple people. They exist in one place, encrypted, with a complete access audit trail.

Component 2 — Central Policy Manager (CPM)

The CPM is the automation engine that manages credential lifecycle. Where the Vault is passive storage, the CPM is active management. CPM connects to the Vault to retrieve credentials, then connects to target systems to rotate those credentials on a defined schedule. It generates new complex random credentials, changes them on the target system, verifies the new credentials work, and updates the Vault with the new value.

What it solves: Static credentials. Without CPM, vaulted credentials are just a secure password manager — better than a spreadsheet, but still static. CPM transforms vaulted credentials into actively managed ones: automatically rotated, verified, and never stale. A credential that rotates every 24 hours is only valid for the attacker for 24 hours after capture.

CPM runs as a Windows service on a dedicated server. It uses plug-ins to connect to different target system types: Windows, Linux, databases, network devices, and cloud platforms. The plug-in architecture means CPM can rotate credentials on almost any system type, provided a plug-in exists or can be developed for it.

Component 3 — Privileged Session Manager (PSM)

The PSM is the session proxy and recording layer. When a user needs to connect to a privileged target system, they do not connect directly — they connect to PSM, which connects to the target on their behalf. PSM retrieves the credential from the Vault, injects it into the connection to the target, and records every keystroke and screen action during the session. The user sees the target system but never sees the password.

What it solves: Three distinct problems simultaneously. First, credential knowledge: the user never learns the password, so they cannot exfiltrate it, share it, or retain it after their access is revoked. Second, session accountability: even for shared accounts like root, the PSM session is attributed to the specific user who checked it out. Third, forensic visibility: every privileged session is recorded — post-incident investigation has a complete video record of what was done.

PSM uses Connection Components to connect to different target types: RDP for Windows servers, SSH for Linux, database clients for DBA access, and web browsers for web-based admin consoles. PSM for SSH (PSMP) is the Linux-specific variant that handles SSH proxy connections. Section 10.6 covers PSM architecture in depth.

Component 4 — Privileged Threat Analytics (PTA)

PTA is the behavioral analytics component that monitors privileged activity for anomalous patterns. PTA ingests CyberArk activity events — who accessed which account, when, from where, what commands were run — and correlates them with SIEM and endpoint events to detect compromised privileged accounts. PTA detects patterns like: a domain admin account accessed at 3am from an unusual IP; a privileged account accessing more systems than usual in a short time; a session executing commands that match known attack tool signatures.

What it solves: Compromised-but-authorized access. An attacker who has legitimately checked out a privileged account from CyberArk (by compromising the human who owns it) will appear authorized to the Vault. PTA detects the behavioral anomaly even when the credential access itself was authorized.

Component 5 — PVWA (Password Vault Web Access)

The PVWA is the web portal through which human users interact with CyberArk. It provides the interface for requesting access, checking out credentials, initiating PSM sessions, viewing audit logs, and managing safe permissions. The PVWA is the face of CyberArk to end users — the platform's user experience is almost entirely determined by how well the PVWA is configured.

What it solves: Human-to-Vault interaction. The Vault itself has no user-facing interface — the PVWA provides the workflow layer that makes the Vault usable for humans: request flows, approval chains, session launch, and audit visibility.

CyberArk Privilege Cloud (SaaS Variant)

CyberArk Privilege Cloud is the SaaS-hosted version of the PAM platform. The Vault and PVWA are hosted and managed by CyberArk in their cloud infrastructure; CPM and PSM Connectors are deployed on-premises or in the customer's cloud environment to reach target systems. Privilege Cloud eliminates Vault infrastructure management overhead but introduces network path considerations: CPM and PSM Connectors must reach both the CyberArk cloud Vault and the on-premises target systems.

CyberArk Conjur (Secrets Management Extension)

Conjur is CyberArk's secrets management platform for non-human and DevOps workloads. While the EPV Vault is optimized for human privileged access workflows (checkout, approval, session recording), Conjur is optimized for machine-to-machine credential delivery: fast programmatic API access, dynamic short-lived secrets, Kubernetes integration, and CI/CD pipeline secrets management. The architectural distinction — human PAM vs machine secrets — is covered in Section 10.8. Module 12 covers Conjur in depth.

The Architectural Principle: Separation of Credential Knowledge from Credential Use

CyberArk's architecture embodies a single core principle: credential knowledge and credential use are separated. The CPM knows the password (to rotate it). The PSM uses the password (to connect to the target on behalf of the user). The human user neither knows nor uses the password directly — they connect to PSM, which handles the credential injection transparently.

This separation has a profound security implication: when an employee leaves, revoking their CyberArk PVWA access is sufficient. They never had the actual password to take with them. The credential exists only in the Vault. Former employees cannot use credentials they once had access to — because they never had the credential, only access to use it through a controlled channel.

🟢 Architect's Lens — Privileged Access Without Privileged Knowledge

CyberArk's architecture separates credential knowledge from credential use. The CPM knows the password (to rotate it). The PSM uses the password (to connect to the target on behalf of the user). The human user never knows the password — they connect to PSM, which injects the credential to the target. This architectural separation means: when an employee leaves, revoking their CyberArk access is sufficient — they never had the actual password to take with them. The credential exists only in the Vault. This is the core architectural value of PAM: privileged access without privileged knowledge.

🔬 Lab 10.3 — Audit Your Safe Permission Model

In CyberArk PVWA, navigate to the safe structure and examine permission grants. For each major safe category, identify: who has Retrieve permission (they can see the actual password)? For which safes is that appropriate vs. which should be PSM-only? The target architecture: only the PAM team and CPM have Retrieve; all other users have Use (PSM session launch only). Document the gap between current state and target state.

10.4

The Digital Vault — Architecture & Design

The Digital Vault is the crown jewel of the CyberArk architecture — and therefore the highest-value target for any attacker who has already gained privileged access to the environment. Understanding the Vault's design philosophy is essential: the Vault is built on the assumption that everything else may eventually be compromised. The perimeter can fail. The network can be breached. Other servers can be compromised. The Vault must survive all of it.

This assumption shapes every architectural decision the Vault makes: its encryption model, its network isolation, its OS hardening, its HA configuration, and its access control model. The Vault is not merely a secure database — it is a purpose-built security appliance designed to be the last line of defense for the most valuable credentials in the enterprise.

Vault Design Philosophy

The Vault's design is organized around three principles:

  • Assume breach of everything else: The Vault must remain secure even if every other system in the environment is compromised. This means the Vault must not depend on any other system for its security — not the domain, not the network, not the certificate infrastructure, not the SIEM.
  • Defense in depth at the storage layer: Even if an attacker gains OS-level access to the Vault server (a scenario the design tries to make impossible), the encrypted data files must be unreadable without the encryption keys that never leave the Vault server.
  • Complete audit accountability: Every credential access event must be logged, tamper-evident, and preserved. The Vault's audit trail is the definitive forensic record for privileged access — it must survive attempts to manipulate or destroy it.

Vault Encryption Architecture

The Vault uses a hierarchical encryption model with three tiers of keys. Understanding this hierarchy explains why data exfiltration from the Vault's storage files cannot by itself compromise the credentials:

  • Server Key: The root encryption key for the entire Vault. The Server Key is hardware-bound — stored in a Hardware Security Module (HSM) in production deployments, or in a protected key file in smaller environments. The Server Key never leaves the Vault server. It cannot be exported, transmitted, or backed up separately from the Vault infrastructure itself.
  • Safe Keys: One encryption key per Safe. Each Safe has its own unique key, encrypted by the Server Key. A compromise of one Safe's key does not expose credentials in other Safes.
  • Object Keys: One encryption key per credential object. Each individual password, SSH key, or certificate has its own key, encrypted by the Safe Key. Even within a single Safe, individual objects are individually encrypted.

The practical implication: if an attacker copies the Vault's data files (by gaining access to the underlying storage), they have encrypted blobs that cannot be decrypted without the Server Key — which never left the Vault server. The data files without the keys are computationally useless.

Vault Server Hardening

The Vault server is hardened to a degree unusual even by enterprise security standards:

  • Minimal Windows Server OS: The Vault runs on a stripped-down Windows Server installation with most services disabled. No IIS, no unnecessary Windows roles, no additional software beyond what CyberArk requires. Every additional service is an additional attack surface.
  • No domain membership: The Vault server should not be domain-joined. If it were, domain administrators would have OS-level access to the Vault server. A Domain Admin could log in to the Vault server's OS and attempt to access the encrypted data directly. Domain isolation means the Vault server's OS is independently managed, with local administrator credentials that are themselves vaulted in a separate emergency safe.
  • No internet access: The Vault server has no outbound internet connectivity. There is no browsing, no Windows Update through the public internet, no email. Updates are applied through an isolated management channel.
  • Network isolation: The Vault server sits in an isolated network segment. Only specific CyberArk components (CPM, PSM, PVWA) can reach the Vault network port (TCP 1858) from their specific IP addresses. Firewall rules block all other access.
  • Physical access controls: For on-premises deployments, the Vault server should have physical access controls beyond the standard datacenter baseline — separate rack locks, access logging, and ideally a dedicated physically isolated cage.

Vault HA Architecture

The Vault operates in a Primary-DR (Disaster Recovery) topology. The Primary Vault handles all active requests. The DR Vault receives continuous replication from the Primary and stands ready for failover. CyberArk's replication is file-based: the Vault's data files, including all encrypted credential objects and their associated metadata, are replicated to the DR Vault in near-real-time.

Vault Access Control and Master Policy

The Vault's access control model is built on Safes. Access to a Safe grants access to the credentials within it. Safe permissions are granular: View, Retrieve, Add, Update, Delete, Use (PSM), Manage, and Administer. The separation between Retrieve (see the password) and Use (launch a PSM session) is the most important permission distinction in the entire CyberArk model — most users should have Use but never Retrieve.

The Master Policy is the CyberArk policy engine that defines requirements for credential management across the platform: rotation frequency, session recording requirements, minimum password complexity, dual-control enforcement (requiring a second approver for access), and exclusive access (only one user can check out a credential at a time). Master Policy settings cascade to all accounts unless overridden at the safe or account level.

Vault Audit Trail

Every credential access event in the Vault is logged: who accessed what account, when, from which IP address, through which CyberArk component, what action was taken, and whether the access succeeded or failed. The audit trail is append-only and tamper-evident within the Vault architecture. This audit data is the forensic foundation for privileged access investigations and the evidence base for compliance reporting (SOX, PCI-DSS, HIPAA all require privileged access audit trails).

🔴 Security Architecture Note — Vault Server is the Attack Crown Jewel

The Vault is the highest-value target for an attacker who has already gained privileged access. CyberArk's Vault hardening includes running a minimal Windows Server OS with most services disabled, no internet access, no domain membership (domain admins should not have OS-level access to the Vault server), and HSM integration for Server Key protection. If the Vault server's OS is somehow compromised, the encryption architecture means the actual credentials are still protected — but the architectural goal is to make OS-level Vault compromise practically impossible by eliminating every attack vector: no domain join, no internet, no unnecessary services, network isolation to port 1858 only.

🔬 Lab 10.4 — Assess Your Vault Security Posture

Locate the CyberArk Vault server(s) in your environment and answer these questions: Is the Primary Vault server domain-joined? (It should not be — if it is, domain admins can access its OS.) What network segment is it in? Can it be pinged from a regular workstation or developer machine? (It should not be reachable.) What is the DR Vault configuration — is it in a separate datacenter or same rack? When was the last Vault failover test? Is a Hardware Security Module (HSM) in use for the Server Key? These answers define your Vault security posture and the gap against architectural best practice.

10.5

Credential Rotation Architecture

A vaulted credential that never rotates is simply a very secure password manager. The Central Policy Manager (CPM) is what transforms vaulted credentials into actively managed ones — automatically rotating passwords on schedule, eliminating static credentials, and ensuring that even if a credential is captured by an attacker, it has a defined expiry. Credential rotation architecture is where most PAM implementations encounter their first serious operational challenges.

What CPM Does

The CPM is a Windows service that runs on a dedicated server and manages the credential lifecycle for all accounts in the Vault. Its core loop is straightforward: retrieve the current credential from the Vault, connect to the target system, change the credential to a new randomly generated value, verify the new credential works, and update the Vault. This loop runs on a defined schedule — or is triggered immediately after a checkout, depending on the Master Policy configuration.

CPM uses platform-specific plug-ins to interact with different target system types. The Windows platform plug-in authenticates to Windows servers using LDAP or WMI. The LDAP plug-in manages AD service account passwords through directory APIs. The SSH plug-in connects to Linux systems via SSH. The database plug-ins use native database client connections. Each plug-in encapsulates the protocol-specific logic for changing a credential on that target type.

The Rotation Flow in Detail

The full rotation sequence for a single credential involves seven steps, and a failure at any step requires a specific recovery path:

Rotation SSH Key Architecture

SSH key rotation is more complex than password rotation because SSH public keys are stored on the target system in authorized_keys files, not in a directory like AD passwords. The CPM SSH key rotation flow: generate a new RSA/Ed25519 key pair locally, connect to the target using the current private key, add the new public key to authorized_keys, verify the new key pair works by connecting with the new private key, remove the old public key from authorized_keys, and update the Vault with the new private key. A failure at the removal step means both old and new keys are temporarily valid — CPM handles this through a retry and cleanup mechanism.

The Rotation Cascade Problem

The rotation cascade is the most common PAM implementation failure. A service account is vaulted, CPM rotation is enabled, and the first rotation fires at 2am. Three applications that use that service account start returning authentication errors at 6am when their cached credentials expire. The rotation succeeded from CPM's perspective — the Vault has the new password and the AD account reflects the new password — but the applications are still using the old password from their local configuration files or connection pools.

🟢 Architect's Lens — The Rotation Cascade Anti-Pattern

The rotation cascade is the most common PAM implementation failure. A team vaults a service account and enables rotation — and the next rotation at 2am causes an application outage because a scheduled task was using the account with a hardcoded password that CPM didn't know about. Before enabling rotation for any service account, the prerequisite is: complete discovery of every system, application, and scheduled task that uses the credential. CyberArk's Application Discovery feature helps automate this. The architectural discipline: never rotate a service account until you have a 100% complete dependency map and have tested the cascade update in non-production. One missed dependency equals a production incident.

10.6

Privileged Session Management

The Privileged Session Manager (PSM) is the component that fundamentally changes the relationship between privileged users and privileged credentials. Before PSM, an administrator who needed to connect to a privileged server had to know the password — they typed it in. After PSM, the administrator connects to PSM, which connects to the server, injecting the credential transparently. The user sees the server session; they never see the password. This single architectural change — session proxying with credential injection — closes more attack vectors than any other single PAM capability.

PSM Core Architecture

The PSM server runs as a Remote Desktop Services (RDS) host for Windows targets and an SSH proxy for Linux targets. When a user initiates a PSM session through PVWA:

  1. PVWA verifies the user's authorization for the requested safe and account
  2. PVWA initiates the PSM session, passing the account context
  3. PSM retrieves the credential from the Vault (the user never touches this step)
  4. The user's workstation opens an RDP connection to PSM (not to the target)
  5. PSM opens a second RDP/SSH connection to the actual target, injecting the credential
  6. PSM begins recording — video stream of the session and full keystroke log
  7. The user works in the session, seeing the target but connected through the PSM proxy
  8. When the session closes, PSM terminates the target connection and saves the recording
  9. CPM rotation triggers if the Master Policy specifies rotate-after-checkout

PSM Network Isolation Architecture

PSM's value as a session proxy depends on enforced network isolation. If a user can bypass PSM and connect directly to the target server using a credential they've memorized or captured, the PSM recording is bypassed entirely. The complete PSM architecture therefore includes firewall rules that make direct workstation-to-target connections impossible:

Session Recording Architecture

PSM records privileged sessions as both a video stream (screen capture) and a full keystroke log. The recording is stored in CyberArk's Vault or a designated storage repository. Recordings can be played back through the PVWA, searched by time range, username, target system, or specific commands executed within the session. The session recording is the definitive forensic artifact for any privileged access investigation.

Retention design considerations: Session recordings consume significant storage (RDP sessions at typical compression run 10–50 MB per hour; 100 concurrent sessions per day yields 1–5 GB daily). The retention period must satisfy the longest regulatory requirement applicable to the organization — PCI-DSS requires 12 months; SOX environments typically require 7 years for audit evidence (though recordings older than 12 months are rarely needed in practice).

Command Filtering and Real-Time Monitoring

PSM can be configured to block specific commands during a privileged session. On Linux systems, command filtering can prevent a PSM session from executing rm -rf /, passwd root, or other destructive operations. For Windows sessions, specific application launches can be blocked. Real-time session monitoring allows a security team member to watch an active privileged session in the PVWA and terminate it immediately if suspicious activity is observed.

🔴 Security Architecture Note — Session Recording Governance Gap

Session recording is only as valuable as your ability to retrieve and review recordings when needed. A common implementation gap: sessions are recorded but recordings are never reviewed until an incident — by which time the recording storage policy may have already purged relevant sessions. Design the session recording architecture with: a retention period that satisfies regulatory requirements (90 days minimum; 12 months for most regulated industries), storage capacity that accommodates peak session volume without automatic purging, indexed recordings searchable by user, target, and command, and a regular review process for high-risk session categories (domain admin sessions, production database sessions). Recordings that cannot be found or reviewed are not governance — they're false assurance.

By target system name? Now check the retention policy configuration — how long are recordings retained? 10.7

Just-in-Time Access Architecture

Zero Standing Privilege (ZSP) is the architectural principle that privileged access should not exist until it is needed and should cease to exist the moment it is no longer needed. Just-in-Time (JIT) access is the implementation pattern that makes ZSP operational. JIT is not simply a policy preference — it is a measurable reduction in the attack surface. A domain admin account that exists permanently is available to be compromised every second of every day. A domain admin account that exists only for the 45-minute duration of a specific approved task is only vulnerable for those 45 minutes. The arithmetic is unambiguous.

JIT Access Models

JIT is not a single mechanism — it is a spectrum of access provisioning patterns, each with different security properties and operational overhead:

  • Time-limited access: The simplest JIT model. Access is granted for a defined time window (e.g., 2 hours) and automatically revoked when the timer expires. The privileged account exists throughout this period — elevated continuously for the 2-hour window. Implementation: CyberArk adds the user to the privileged group for the time window and automatically removes them at expiry. Simple to implement, significant improvement over permanent standing privilege.
  • Task-based access: Access is provisioned for a specific approved task and revoked when the task is marked complete, regardless of elapsed time. A change management ticket defines the scope; access lives for the life of the ticket. Tighter than time-limited because access expires on task completion rather than a time boundary. Requires integration with change management (ServiceNow).
  • Ephemeral accounts: The most powerful JIT model. A temporary privileged account is created specifically for the task and deleted entirely afterward — not disabled, not expired, deleted. There is no standing account to compromise between tasks. The account literally does not exist outside the task window. CyberArk can create ephemeral AD accounts on demand, with unique credentials, used for a single session and then permanently removed.
  • Just-Enough-Access (JEA): Rather than granting the full Domain Admin role for a specific task, JEA grants only the specific permissions required. A Windows Server JEA endpoint defines a constrained PowerShell session where only specific cmdlets are available — an administrator who needs to restart a specific service gets only that capability, not full administrative rights.
🟢 Architect's Lens — JIT Is an Operational Change, Not Just a Technical One

JIT access is the architectural North Star for privileged access management. Permanent privileged accounts — even well-managed ones — are a standing invitation for compromise. JIT eliminates the attack surface between tasks. The implementation challenge: every privileged workflow that assumes "I always have this access" must be redesigned to "I request this access, do the work, and it's revoked." Teams must have time to submit JIT requests before they're needed, approval workflows must not introduce unacceptable delays for emergency tasks (a 2am incident cannot wait for a 9am approval), and the JIT process must be auditable to demonstrate compliance. Design the emergency path first — if JIT doesn't work for 3am incidents, adoption will fail.

🎯 Use Case — JIT Emergency Access at 2am

A production incident requires emergency access to a Kubernetes cluster at 2am. The on-call engineer needs cluster-admin privileges. Design the JIT emergency access architecture: the request is submitted through the on-call runbook's mobile-friendly self-service portal (not a full PVWA workflow — the engineer is half-awake). Auto-approval fires within 30 seconds for incident-coded requests that match an active PagerDuty alert, with a mandatory post-access review SLA of 24 hours. Access is provisioned: a cluster-admin ClusterRoleBinding scoped to the engineer's identity for 90 minutes. At T+90m, the binding is automatically removed. The PSM session recording captures every kubectl command. The post-incident review verifies the commands were consistent with the stated incident scope. This is JIT working at the operational pace that production incidents demand.

🔬 Lab 10.7 — Identify Your Standing Privilege Inventory

Identify the top five privileged accounts in your environment that currently have permanent standing privilege — always active, always elevated. For each account, pull the CyberArk access log: how many times was the account actually used in the last 30 days? 10.8

PAM for Non-Human Identities

Human privileged accounts — domain admins, DBAs, root users — are the traditional focus of PAM programs. But in every enterprise environment, non-human identities are both more numerous and more privileged than their human counterparts. Service accounts have administrative rights on dozens of servers. Application credentials have read access to entire databases. CI/CD pipeline secrets can deploy to production environments. API keys can modify cloud infrastructure. These are privileged identities, and most of them are managed worse than any human privileged account in the environment.

Why Non-Human Identities Are the Larger PAM Problem

Non-human privileged identities share a set of risk characteristics that make them distinctly more dangerous than human privileged accounts in most environments:

  • No MFA: Service accounts cannot do multi-factor authentication. If the credential is compromised, there is no second factor to stop the attacker.
  • Credential hardcoding: Service account passwords, database connection strings, API keys, and SSH keys are routinely stored in application configuration files, environment variables, Kubernetes secrets, source code, and CI/CD pipeline variables — exposed to every person and process that can read those files.
  • No behavioral monitoring: Standard UEBA and threat analytics tools are tuned for human behavioral patterns. A service account that makes 10,000 API calls per hour doesn't trigger anomaly alerts because that's its normal pattern.
  • Long-lived static credentials: Service account passwords set at application deployment time and never changed are more common than exception in enterprise environments. Credentials 3, 5, or 10 years old are not unusual.

CyberArk AIM — Eliminating Hardcoded Credentials

The CyberArk Application Identity Manager (AIM) and its Credential Provider component solve the hardcoded credential problem at the application layer. Instead of an application reading its database password from a configuration file, it requests the credential from CyberArk at runtime via the Credential Provider — a local agent or API endpoint that retrieves the current credential from the Vault on the application's behalf.

💡 Concept — EPV vs Conjur: Different Problems, Different Architectures

The distinction between CyberArk's EPV (for human privileged access — workflow, PSM, session recording) and CyberArk Conjur (for non-human privileged access — API-native, dynamic credentials, developer-friendly) reflects a fundamental architectural insight: humans need workflow, approval, and session recording. Machines need fast, programmatic, short-lived credential delivery. These are different usage patterns requiring different architectural solutions — even when they're both "privileged access management." Module 12 covers Conjur and the secrets management layer in depth.

🔬 Lab 10.8 — Count Your Non-Human PAM Gap

Check: database passwords, API keys, service account passwords, LDAP bind passwords. Each credential found in a config file is an unmanaged privileged identity that CyberArk AIM or Conjur should be managing. 10.9

PAM Integration Architecture

CyberArk does not operate in isolation. A PAM platform that is disconnected from the rest of the enterprise identity stack — from Active Directory, from IGA, from SSO, from SIEM — is a security island. Credentials are protected inside CyberArk but the governance model that determines who should have access to what, the lifecycle management that provisions and deprovisions access, and the monitoring that detects misuse all require integration with the surrounding identity ecosystem. PAM integration architecture is what transforms CyberArk from a credential vault into a governed privileged access platform.

CyberArk ↔ Active Directory

Active Directory is CyberArk's foundational integration partner. CyberArk authenticates PVWA users against AD using LDAP. The CPM uses AD APIs (LDAP write, ADSI) to rotate AD service account passwords. Ephemeral JIT accounts for domain admin access are created and deleted in AD by CyberArk. The PVWA safe permission model can be mapped to AD groups — members of the PAM-DomainAdmin-Requestors AD group automatically get Use permission on the Domain-Admin-Accounts safe.

CyberArk ↔ PingFederate + PingID

For enterprises using PingFederate as the SSO platform, CyberArk PVWA can be configured as a SAML Service Provider. Users authenticate to PingFederate (which handles AD authentication and MFA via PingID), and receive a SAML assertion that grants access to the PVWA. This centralizes authentication — there is no separate CyberArk username and password. The PingFederate integration also enables step-up authentication: accessing a high-sensitivity safe can trigger a PingFederate step-up authentication request, requiring the user to re-authenticate with a stronger second factor at the moment of privilege escalation — not just at login time.

CyberArk ↔ Saviynt — The IGA-PAM Integration

The integration between CyberArk and Saviynt is bidirectional and represents the most critical cross-platform governance integration in the enterprise identity stack:

The IGA-PAM Governance Gap

The most common governance failure at the intersection of IGA and PAM: CyberArk safe memberships are managed independently by the PAM team, never included in access certification campaigns, and never subject to Mover/Leaver lifecycle enforcement from Saviynt. The result: former employees' CyberArk safe access outlives their standard account deprovisioning because nobody connected the leaver workflow in Saviynt to the safe membership revocation in CyberArk.

A terminated employee's AD account is disabled within 5 minutes (Saviynt IGA leaver workflow). Their CyberArk safe membership is revoked 3 days later (manual PAM team action, after a ticket is raised). During those 3 days, the account is AD-disabled but their CyberArk safe membership is still active — and if an attacker had already compromised their CyberArk session before termination, that session context may still be active.

🟢 Architect's Lens — Close the IGA-PAM Governance Gap

PAM and IGA must share a privileged access governance model. The architecture fix: CyberArk safe memberships are managed as entitlements in Saviynt. The IGA leaver workflow triggers CyberArk safe membership revocation as part of the deprovisioning sequence — not as a separate manual PAM team action. The SLA for CyberArk deprovisioning should match or beat the SLA for AD account disablement. If AD is disabled in 5 minutes, CyberArk safe membership should be revoked in 5 minutes — not 3 days. This requires the CyberArk REST API to be called from the Saviynt leaver workflow, which is a straightforward integration but one that most organizations have not implemented.

CyberArk ↔ SIEM and Change Management

PTA forwards privileged activity events to the enterprise SIEM (Splunk, QRadar, Microsoft Sentinel) via Syslog or CEF format. This privileged activity stream — who accessed what, when, commands executed, anomalies detected — is the input that SIEM correlation rules use to detect privileged account misuse. The SIEM can correlate CyberArk events with endpoint telemetry (was the user on VPN when they accessed the domain admin account at 3am from a new IP?) and network flow data (did the domain admin account generate unusual lateral movement traffic after being checked out?).

Change management integration ensures that privileged access is only available during approved change windows. CyberArk integrates with ServiceNow to verify that an active change ticket exists before a privileged account checkout is approved. A domain admin trying to access a production server outside a change window receives an auto-rejection — the system enforces the change management policy at the credential access layer, not just the process layer.

🔬 Lab 10.9 — Audit the IGA-PAM Governance Integration

In Saviynt, check whether CyberArk safe memberships appear as entitlements in the identity warehouse. Navigate to the application catalog — is CyberArk listed as a managed application? If not, that is the IGA-PAM governance gap in its entirety. Now check the leaver workflow definition: does it include a CyberArk deprovisioning step? What is the SLA for CyberArk deprovisioning after termination? Compare it to the AD deprovisioning SLA — CyberArk should be equal or faster, never slower. Finally, verify the last access certification campaign: did it include CyberArk safe membership review items? If not, the last three years of certifications have been incomplete — certifiers were certifying standard access but leaving privileged access uncertified.

Architecture Cheat Sheet

01 PAM governs accounts that break the authorization model — Domain Admin, root, DBA, service accounts, network device admins, cloud IAM admins, break-glass accounts. These accounts operate above or outside normal RBAC/ABAC controls and require a dedicated security architecture. IGA governs standard access; PAM governs privileged access.
02 CyberArk has five core components with distinct roles: Vault (encrypted credential store, most hardened), CPM (automatic rotation engine), PSM (session proxy and recorder), PTA (behavioral anomaly detection), PVWA (human-facing web portal). Every credential operation flows through the Vault. No component is optional for a complete PAM architecture.
03 No human knows the privileged password — PSM injects it. This is the core PAM value proposition. Credential knowledge and credential use are architecturally separated. When an employee leaves, revoking their CyberArk access is sufficient — they never had the actual password to take with them. Grant Use (PSM session launch) not Retrieve (password visibility) wherever possible.
04 The Vault uses a three-tier key hierarchy: Server Key (hardware-bound, never leaves Vault server) → Safe Keys (one per Safe) → Object Keys (one per credential). Copying the Vault's data files without the Server Key yields computationally useless encrypted blobs. The Vault must not be domain-joined — Domain Admins must not have OS-level access to it.
05 Rotation cascade: map ALL dependencies before enabling CPM rotation. A service account used by four consumers will break all four when CPM rotates if dependency mappings are missing. Never enable rotation without a complete dependency map tested in non-production. One missed dependency equals a production incident at 2am.
06 JIT reduces the privileged attack window by 99%+. A permanent Domain Admin account is attackable 8,760 hours per year. An ephemeral JIT account exists only for the 45-minute task duration. The operational challenge: every privileged workflow that assumes "I always have this access" must be redesigned for JIT. Design the 2am emergency path first — if JIT doesn't work for incidents, adoption will fail.
07 Credentials in config files = unmanaged privileged access. CyberArk AIM (Application Identity Manager) eliminates hardcoded credentials by providing runtime credential retrieval — the application requests its database password from the local Credential Provider at startup, which retrieves the current rotated value from the Vault. No config file change needed when CPM rotates. Module 12 covers CyberArk Conjur for DevOps and cloud-native workloads.
08 IGA ↔ PAM governance gap is the most common enterprise failure. CyberArk safe memberships must be Saviynt entitlements, included in access certification campaigns, and subject to Joiner/Mover/Leaver lifecycle. The Saviynt leaver workflow must trigger CyberArk deprovisioning in the same automated sequence as AD account disablement — with equal or faster SLA. Manual PAM team deprovisioning processes create the governance gap that allows terminated employee access to persist.

Q1

An employee with CyberArk access to the Domain-Admin safe is terminated. The AD account is disabled by Saviynt within 5 minutes. But the CyberArk safe membership is not revoked for 3 days (manual PAM team process). What is the risk during those 3 days and what architectural change closes it?

▼

The risk: The AD account being disabled does not automatically terminate the CyberArk safe membership. If the attacker had already established a CyberArk session context (e.g., an active session cookie from a session the user initiated before termination), that session context may still grant access to the Vault's API. More critically, if the CyberArk safe membership persists for 3 days, any attacker who has compromised the employee's CyberArk authentication factor (not their AD credential, but their PVWA authentication — which may be MFA-backed separately from AD) during the notice period can still access the safe contents.

Architectural fix: CyberArk safe memberships must be managed as entitlements in Saviynt. The IGA leaver workflow must include a CyberArk deprovisioning step via the CyberArk REST API — called in the same automated sequence as AD account disablement, with the same or better SLA. The target: CyberArk safe membership revoked within 5 minutes of termination, not 3 days later. No manual PAM team action should be on the critical path for leaver deprovisioning.

Q2

CPM rotation of a service account's password fails at 2am. Three applications that use the account start returning authentication errors at 6am when their cached credentials expire. Walk through the CyberArk architecture that should have prevented this and the incident response process.

▼

What should have prevented this: Before enabling CPM rotation on any service account, CyberArk requires a complete dependency map — all systems, applications, scheduled tasks, and Windows services that authenticate with this account must be defined as dependent accounts in the CPM configuration. CPM's dependent account update mechanism propagates the new credential to all registered consumers simultaneously at rotation time. The absence of this dependency map is the architectural gap that caused the outage.

Root cause of the rotation failure: CPM rotation generates a new credential and attempts to change it on the target AD. If rotation failed, the likely causes are: target unreachable, reconciliation account permissions insufficient, or the account was locked. CPM should have triggered an alert to the PAM team at 2am on failure — the Vault retains the old credential when rotation fails, so if this alert had been acted on, the application errors would have been avoidable.

Incident response: Immediately restore the known-good credential in the Vault (the old one, which CPM retained on failure). Fix the rotation failure root cause. Map all dependencies before re-enabling rotation. Test the cascade update in non-production. Enable rotation with a complete dependency map.

Q3

A security team wants to implement JIT for all Domain Admin access. The Windows team says this will break their daily workflow because they "always need domain admin." Design the JIT implementation that addresses both the security requirement and the operational reality.

▼

Understanding the operational claim: "Always need domain admin" almost never means 24/7 continuous Domain Admin privilege. It means: when I need to make a change, I need it immediately, without a multi-step approval process that takes 30 minutes. The JIT design must address response time, not the need itself.

JIT design for Windows admin teams: Implement time-limited JIT with a self-service pre-approved tier for routine tasks (automated approval within 60 seconds for requests with valid change tickets), a standard tier for non-emergency changes (manager approval, 15-minute target SLA), and an emergency tier for incident response (auto-approval with mandatory 24-hour post-access review and automatic PagerDuty incident creation). Time windows: 4 hours for routine tasks, 2 hours for emergency. Individual named accounts (not shared) so accountability is preserved. PSM mandatory for all Domain Admin sessions regardless of JIT model.

Addressing "daily workflow": Audit the actual usage. Pull the CyberArk access logs for the Domain Admin accounts. In most environments, "daily domain admin need" translates to 15–30 minutes of actual elevated activity per day. The JIT request + self-approval flow should take under 2 minutes — a net improvement over the current no-JIT model where the credential is permanently exposed whether needed or not.

Q4

PTA detects that a Domain Admin account is accessing file servers at 3am from an unusual IP address. Walk through the CyberArk response architecture: what PTA does, what alert is generated, what automated response options exist, and what the human response should be.

▼

What PTA does: PTA correlates the CyberArk checkout event (who checked out the Domain Admin account, when, from which workstation) with the active session behavior (the IP address the session is originating from, the file server access pattern, the time of day). The unusual IP and unusual time both score as anomalies against the account's behavioral baseline. PTA generates a risk-scored alert.

Alert generated: PTA sends a high-severity alert to the SIEM (Splunk) via Syslog/CEF and raises an alert in the CyberArk interface. The SIEM correlation rule fires — it matches "Domain Admin session outside business hours from new IP" to a high-priority incident. The SOC on-call analyst receives a page.

Automated response options: CyberArk PTA can be configured to automatically suspend the active session (pause the PSM session) pending investigation. It can also trigger an automatic password rotation of the checked-out account, invalidating the credential even if the attacker has it. The account can be automatically locked in CyberArk, preventing further checkouts until manually re-enabled.

Human response: The SOC analyst reviews the PSM session recording in real-time or from the recent recording to determine what commands were executed on the file servers. They verify with the account owner (is this you? are you working at 3am from this IP?). If not authorized: terminate the session immediately, rotate the credential, initiate incident response for potential compromised privileged account. If authorized (on-call engineer working remotely): document and close the alert with the justification.

Q5

A developer asks why they can't just use a team password manager (like 1Password Teams) for their application's database credentials instead of CyberArk AIM. Walk through the architectural difference.

▼

The team password manager model: A human retrieves the database credential from the shared team vault, copies it into the application configuration file or environment variable, and deploys. The credential is now static — it will not change until a human manually retrieves a new value and re-deploys the application. The credential is stored as plaintext in the config file, accessible to anyone with file system access. It's in source control history. When the credential rotates (if it ever does), every application using it breaks until manually updated.

The CyberArk AIM model: The application code calls the local AIM Credential Provider at runtime — not at deploy time. The Credential Provider retrieves the current live credential from the Vault at the moment the application needs it. When CPM rotates the credential on schedule, the Vault is updated with the new value. The next time the application requests the credential, it gets the new rotated value automatically — no redeployment, no config file update, no human action required. The credential never appears in a config file, in source control, or in environment variables. The application's identity (OS user, path, certificate) proves its right to retrieve the credential — not another hardcoded secret.

Key architectural differences: Static vs. dynamic retrieval. Human-mediated vs. automated rotation. Plaintext storage vs. encrypted vault with key hierarchy. Manual rotation cascade vs. automated Vault update. Application identity authentication vs. shared team password. Team password managers are appropriate for human-to-application authentication; CyberArk AIM is the correct architecture for application-to-application authentication at enterprise scale.

The organization has CyberArk deployed but is operating at PAM Maturity Level 1 — credential storage only, with incomplete coverage, no active governance integration, and significant unmanaged privileged credential exposure. The 63% of privileged accounts outside CyberArk represent the primary attack surface. The 847-day average service account password age means the majority of service account credentials have never been rotated since initial deployment. The absence of CyberArk in access certification means three or more years of SOX certification campaigns have attested to "complete access review" while excluding the most privileged identities in the environment.

Risk Prioritization
  • Critical: 23 domain admin accounts with permanent standing privilege and no JIT — complete AD control available to any attacker who compromises any of these credentials.
  • Critical: 12 database passwords in configuration files — active, unrotated, accessible to anyone with file read access to those 5 application servers.
  • Critical: Break-glass accounts with unknown rotation history — highest-privilege accounts with no audit trail and potentially known to former employees.
  • High: 535 unmanaged privileged accounts — more than half the privileged account population is outside the PAM program entirely.
  • High: IGA-PAM governance gap — former employees may have active CyberArk safe memberships that survived their standard deprovisioning.
  • Medium: 60% of CyberArk accounts without session recording — incomplete forensic visibility for post-incident investigation.
30-Day Immediate Actions
  • Rotate all break-glass accounts immediately and vault the new credentials with dual-approval access control. Document the break-glass access procedure. Establish post-access review SLA.
  • Remove the 12 database passwords from configuration files. Deploy CyberArk AIM Credential Provider on the 5 affected application servers. Migrate to runtime credential retrieval before rotating the database accounts.
  • Audit CyberArk safe memberships against current employee roster. Revoke all safe memberships for terminated employees (manually, pending automation build). This closes the immediate leaver gap.
  • Enable session recording for all domain admin accounts in CyberArk. No domain admin PSM session should proceed without recording.
  • Begin Discovery scan using CyberArk DNA tool to enumerate all 535 unmanaged privileged accounts, categorize by type and risk, and create the onboarding backlog.
90-Day Architecture
  • Onboard top 100 highest-risk unmanaged accounts (all domain admins, all break-glass accounts, all accounts with AD replication rights or backup operator rights) into CyberArk with CPM rotation and PSM enforcement.
  • Complete Saviynt ↔ CyberArk integration: CyberArk REST API connector in Saviynt, safe memberships as entitlements in identity warehouse, leaver workflow updated to include CyberArk deprovisioning with 5-minute SLA.
  • Design and pilot JIT model for domain admin accounts with a small group of 5 administrators. Gather operational feedback. Refine approval workflow SLAs.
  • Map all service account dependencies for top 50 service accounts. Begin CPM rotation enablement for accounts with complete dependency maps tested in non-production.
12-Month Target State
  • All 847 privileged accounts in CyberArk (100% coverage). Discovery scans run weekly to detect new unmanaged accounts.
  • All domain admin access via JIT with time-limited or ephemeral accounts. Zero standing Domain Admin privilege.
  • Session recording at 100% for all vaulted accounts. Retention: 12 months (SOX requirement). Recordings indexed and searchable.
  • Saviynt access certification includes CyberArk safe memberships. Next SOX audit cycle includes privileged access certification evidence.
  • All service account credentials managed via CyberArk AIM or Conjur. Zero hardcoded credentials in configuration files (validated by automated scanning in CI/CD pipeline).
PAM Governance Model

The PAM program requires a governance model that spans three teams: the PAM Operations team (CyberArk administration, safe management, onboarding), the IGA team (Saviynt integration, certification campaign inclusion, leaver workflow), and the Security team (PTA monitoring, session recording review, incident response). The PAM steering committee meets quarterly to review coverage metrics, audit findings, and roadmap. Executive sponsor: CISO. Monthly PAM health metrics reported to the steering committee: coverage percentage, rotation compliance, session recording coverage, certification completion rate, open deprovisioning SLA violations.
