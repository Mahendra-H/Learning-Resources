Why this module matters

The most consequential IAM design decision

Authentication is binary — you either proved your identity or you didn't. Authorization is a design space. The model you choose determines everything downstream: how granular your access controls can be, how fast the system scales, how easily policy changes propagate, and how reliably you can answer the audit question "why did this user have access to this resource on this date?"

Most enterprise IAM programs default to RBAC because it's familiar. Many hit its limitations — role explosion, coarse-grained access, inability to express context-dependent rules — and attempt to bolt on attribute-based logic to an RBAC foundation. The result is a hybrid that's more complex than either model alone and less correct than a purpose-built ABAC or ReBAC system would be.

This module covers all four authorization models at architectural depth, with three enterprise design exercises that force you to choose and justify. By the end, you will be able to select the right model for any scenario and defend that choice at an architecture review board.

The foundational boundary

Where authentication ends and authorization begins

M02 defined this distinction conceptually. M06 makes it architectural. The most important design principle in authorization systems is keeping them separate from authentication systems — and understanding why violating this creates specific failure modes.

Authentication output
A verified identity + claims
After successful authentication, the system has a verified principal identity (e.g., alice@corp.com) and a set of claims about that principal (email, department, groups, auth method, assurance level). Authentication does not make access decisions. It produces the evidence that authorization will evaluate.
Authorization input
Principal + action + resource + context
Authorization evaluates: Subject (who — the verified principal), Action (what — read, write, delete, approve), Resource (on what — a specific file, API endpoint, database record), Context (under what conditions — time of day, device trust, risk score). All four must be considered for fine-grained authorization.
⚠️Classic design failure"If you can log in, you can see everything" — no authorization layer
The most common access control failure in legacy enterprise applications: authentication is the only gate. Once a user has a valid session, all resources are accessible. This is not authorization — it is the absence of authorization. An insider threat, a compromised account, or a privilege escalation attack immediately gains access to everything the application holds. Architects must ensure every system has an explicit authorization layer that evaluates each request independently of authentication state.
Authorization models

Four models — architectural depth

Each model is a different answer to the question "what determines whether access is granted?" Choose wrong and you'll be refactoring your authorization layer in 18 months. Understand them at depth and you'll make defensible, scalable choices the first time.

RBAC Role-Based Access Control
Core idea: Access is determined by roles assigned to users. Users don't have permissions directly — they have roles, and roles have permissions. alice → Finance-Analyst role → read:financial-reports.

Strengths: Simple to understand and audit. Maps naturally to organizational structure. Easy to explain to non-technical stakeholders ("all Finance Analysts can see financial reports"). Works well when job functions are well-defined and stable.

The role explosion problem: As organizations grow and access requirements diversify, the number of roles grows combinatorially. A company with 50 departments × 10 job levels × 5 access tiers = 2,500 potential roles. Many overlap. Roles are rarely retired. Users accumulate roles through Mover events (M02 privilege creep). The result: a role system that nobody fully understands, with access that nobody can audit confidently.

When RBAC breaks down: When you need to express "Finance Analysts can read financial reports for their department only" — this requires either 50 department-specific roles (explosion) or a hybrid model with attribute conditions.
Best for
Stable job functions, small-to-medium orgs, compliance-driven access control, applications where access tiers are few and well-defined
Breaks down when
Access depends on data attributes (ownership, classification), context (time, location), or relationships — all require adding attributes, which is ABAC/ReBAC territory
Enterprise examples
HR system access (HR-Manager, HR-Viewer, HR-Admin), network device access (Read-Only, Network-Operator, Network-Admin)
Governance tool
Saviynt / SailPoint role management, IGA certification campaigns, role mining to discover natural clusters
ABAC Attribute-Based Access Control
Core idea: Access is determined by evaluating a policy against attributes of the subject, resource, action, and environment. No predefined roles needed. Example policy: PERMIT IF subject.department == resource.ownerDepartment AND subject.clearanceLevel >= resource.classificationLevel AND environment.time WITHIN businessHours.

Strengths: Eliminates role explosion by expressing access rules as policies. Handles data-level access control naturally. Context-aware — access can vary by time, device, location, risk score. Fine-grained — different rules for different resources without creating separate roles for each.

The ABAC complexity challenge: Policies must be maintained and tested like code. A misconfigured ABAC policy can silently grant too much or too little access. Policy governance requires a PAP (Policy Administration Point) and testing infrastructure. Requires reliable attribute stores — if subject.department is wrong in the directory, access decisions are wrong.

XACML vs modern ABAC: Early ABAC used XACML (XML-based policy language) — verbose and complex. Modern ABAC uses JSON-based policy languages (OPA/Rego, Cedar) that are more readable and testable.
Best for
Healthcare (patient data access by treating clinician), financial services (data access by account ownership), multi-tenant SaaS, any scenario where resource attributes determine access
Breaks down when
Access depends on graph relationships (who is a member of what project, who manages whom) — which is ReBAC territory. Also hard when attribute data is unreliable or stale.
Enterprise examples
NHS clinical data access (only treating clinicians see patient records), GDPR-compliant data access (EU resident data only accessible from EU region)
Policy engine
OPA (Open Policy Agent) with Rego language, AWS Cedar, AXIOMATICS, PlainID
PBAC Policy-Based Access Control
Core idea: Authorization logic is expressed as externalized, machine-executable policies separate from application code. PBAC is often treated as ABAC implemented via a dedicated policy engine — the distinction is architectural: where the policy lives, how it's managed, and how it's evaluated.

Policy-as-code: Policies are authored, version-controlled, tested, and deployed like software. OPA (Open Policy Agent) is the most widely deployed PBAC engine in cloud-native environments. AWS Cedar is purpose-built for authorization with formal verification properties. Both enable policies to be tested in CI/CD pipelines before deployment.

Externalized authorization: Application code doesn't contain authorization logic — it calls an external policy evaluation service. POST /v1/data/authz/allow {"subject": "alice", "action": "delete", "resource": "invoice/123"} → {"result": false}. This separates the access control surface from the application surface, enabling policy changes without application redeployment.
Best for
Microservices architectures, Kubernetes admission control, API gateway authorization, multi-system consistent policy enforcement
Key advantage
Policy changes don't require application redeployment. A/B testing of authorization rules. Policy can be audited and reasoned about independently of application logic.
Tools
OPA (CNCF graduated), AWS Cedar (Amazon Verified Permissions), Casbin, Oso
Platform integration
API gateway sidecar (Envoy + OPA), Kubernetes admission webhook (OPA Gatekeeper), service mesh (Istio + OPA)
ReBAC Relationship-Based Access Control
Core idea: Access is determined by the relationships between entities in a graph. alice CAN delete document:123 because alice IS owner OF document:123. Relationships can be chained: alice CAN view file because alice IS member OF team and team HAS view ON project and file IS IN project.

Google Zanzibar — the seminal ReBAC system: Google's global authorization system powers Google Drive, YouTube, Google Maps, and Cloud IAM across billions of objects and users. Published in a 2019 paper, it introduced the tuple-based relationship model: (object, relation, subject). For example: (document:123, owner, user:alice) and (document:123, viewer, group:team-a). Access evaluation is a graph traversal — is there a path from the subject to the required permission on the object?

Why ReBAC matters for enterprise architects: Modern enterprise data (documents, projects, incidents, tickets, code repositories) has natural ownership and membership relationships. Google Drive's sharing model, GitHub's repository permissions, and Jira's project access are all ReBAC — users get access through organizational relationships, not role assignments.

Open-source implementations: OpenFGA (Auth0/Okta), SpiceDB (Authzed), Warrant. These implement Zanzibar-compatible tuple stores with consistent evaluation semantics.
Best for
Document/file sharing (Google Drive model), project-based access (GitHub, Jira), hierarchical resource access, any system where ownership and membership drive access
The key insight
RBAC asks "what role does this user have?" ReBAC asks "what is this user's relationship to this specific resource?" The answer is different for each resource — which is what makes it powerful.
Enterprise examples
Confluence (spaces → pages → comments), GitHub (org → team → repo → branch), ServiceNow (team → incident → change record)
Complexity cost
Relationship store must be kept in sync with application state. Graph traversal at scale requires careful caching (Zanzibar's "zookie" consistency tokens). Debugging access failures requires graph inspection tooling.
Policy architecture

PDP · PEP · PAP · PIP — the four components

Regardless of which authorization model you choose, every authorization system has the same four functional components. Understanding them precisely is what allows you to design, troubleshoot, and scale authorization systems correctly.

Diagram 1 — PDP/PEP/PAP/PIP architecture with OPA as the policy engine
PEP placement options
Where to enforce — the architectural choice
API Gateway — Centralized enforcement before any application code runs. Validates JWT, checks scopes, calls OPA. Works for HTTP APIs. Kong, AWS API Gateway, Apigee all support OPA integration.

Service mesh sidecar — Envoy proxy sidecar intercepts all service-to-service traffic. OPA plugin evaluates policy on every request. Consistent enforcement across all microservices without modifying application code.

Application middleware — Library in each application calls the PDP. More flexibility (can include business-layer context) but requires every team to implement it correctly.

Architectural choice: API gateway for coarse-grained (authentication + scope). Service mesh for service-to-service. Application layer for fine-grained (data-row level) where business context is needed.
PDP performance
Latency is the authorization architect's constraint
Every API call that requires an authorization decision adds latency. OPA evaluating a typical Rego policy: 1–5ms. At 10,000 RPS, that's acceptable. At 100,000 RPS with a 10ms policy evaluation latency, you've added 1 second of authorization overhead per second of traffic.

Optimization strategies:
(1) Bundle caching — OPA loads policies into memory; evaluation is in-process, not a network call.
(2) Attribute caching in PIP — cache user attributes from LDAP for 60–300 seconds. Most attributes don't change per-request.
(3) Partial evaluation — OPA's partial evaluation pre-computes what it can at policy load time, reducing per-request work.
(4) Compile policies to Wasm — OPA can compile Rego to WebAssembly for sub-millisecond in-process evaluation.
Google Zanzibar deep dive

Google Zanzibar — the architecture behind modern ReBAC

Google's 2019 paper "Zanzibar: Google's Consistent, Global Authorization System" described the authorization system that powers Google Drive, Google Calendar, YouTube, and dozens of other Google products. It handles trillions of authorization checks per second with single-digit millisecond latency. Understanding Zanzibar is essential for any architect designing fine-grained authorization for data-sharing products.

The tuple model — the fundamental data structure
Zanzibar stores authorization data as relationship tuples in the form: (object, relation, subject)

Examples:
(document:123, owner, user:alice) — Alice owns document 123
(document:123, viewer, group:team-a#member) — Members of team-a can view document 123
(folder:projects, parent, document:123) — Document 123 is in the projects folder
(folder:projects, viewer, user:bob) — Bob can view the projects folder

A check for "can bob view document:123?" traverses the graph: document:123 has no direct viewer for bob → check parent folder → folder:projects has viewer=bob → ALLOW.

This graph traversal is what makes ReBAC powerful — inherited access through relationships — and what makes it complex to implement correctly at scale.
The "new enemy" problem — why consistency is hard in ReBAC
The hardest consistency challenge in distributed ReBAC: Alice is removed as a viewer of document:123 at timestamp T. Bob checks at timestamp T+1ms from a different region. If Bob's check hits a replica that hasn't received the revocation, he gets ALLOW. The access was revoked, but the system said it wasn't.

Zanzibar's solution: zookies (consistency tokens). When a tuple is written, a zookie (a globally consistent timestamp) is returned. Subsequent reads include this zookie as a "read at least as fresh as this timestamp" constraint, guaranteeing the read sees the write. OpenFGA and SpiceDB implement this as the zed-token / snaptoken.

Architect's implication: ReBAC systems in distributed environments require careful consistency design. "Eventually consistent ReBAC" creates temporal access control windows that may be acceptable for document sharing (low stakes) but unacceptable for financial transactions (high stakes).

Design exercises

Three enterprise scenarios — choose and justify

Authorization model selection is a design decision, not a configuration choice. These three scenarios represent the most common enterprise authorization challenges. For each: identify the right model, justify it, and describe the implementation approach. Click to reveal the recommended design.

Exercise 1 · Healthcare Electronic Health Record access control
Scenario: A hospital system has 5,000 clinical staff accessing a shared EHR system. Access rules: nurses can read patient records for patients currently admitted to their ward. Attending physicians can read and write records for their assigned patients. Consultants can view records for patients they've been referred. No role-based assignment can practically capture all these rules — a patient's treating team changes daily. What authorization model do you recommend and why?
▶ Reveal recommended design ▼
Recommended: ReBAC (with ABAC elements for context)

The core access pattern is relationship-based: a nurse's access to a patient record is determined by the relationship "nurse IS assigned to ward W AND patient P IS currently in ward W." This is a graph relationship, not a role or an attribute policy.

Implementation: Use an OpenFGA-compatible tuple store. Tuples: (patient:123, admitted-to, ward:ICU-3), (user:nurse-alice, assigned-to, ward:ICU-3). Access check: "can nurse-alice view patient:123?" traverses: patient is in ICU-3, nurse-alice is assigned to ICU-3 → ALLOW.

ABAC elements: Add a time context check: after discharge, the relationship tuple (patient:123, admitted-to, ward:ICU-3) is deleted. Past-stay access requires a separate "treating-team" relationship retained for audit purposes, with read-only permission.

Why not RBAC: Creating roles like "ICU-3-nurse" for every ward × shift combination creates thousands of roles and requires hourly updates as patients move between wards. ReBAC relationships are updated automatically by the patient administration system — much lower maintenance burden.
Exercise 2 · Financial Services Trading platform API authorization
Scenario: A bank's trading platform exposes REST APIs consumed by internal systems and external clients. Rules: traders can execute orders up to their authorized risk limit. Risk managers can view all orders but not execute. Compliance officers can view all orders plus export audit reports. All access is blocked outside market hours. Large orders (>$1M) require additional authorization from a supervisor. External API clients can only access their own account data. What authorization model do you recommend?
▶ Reveal recommended design ▼
Recommended: PBAC (OPA/Cedar) with RBAC roles as input attributes

The access rules mix role-based elements (trader/risk-manager/compliance roles), attribute conditions (risk limit, order size, market hours), and resource ownership (external clients' own accounts). No single model handles all three cleanly — PBAC with OPA is the right architectural choice because it can evaluate all conditions in a single policy with access to all relevant context.

OPA policy sketch:
allow if { input.user.role == "trader"; input.action == "execute_order"; input.order.size <= data.limits[input.user.id]; market_hours_check }
allow if { input.user.role == "trader"; input.action == "execute_order"; input.order.size > 1000000; supervisor_approved }
allow if { input.user.role in {"risk-manager","compliance"}; input.action == "view_order" }

RBAC roles as attributes: Roles (trader, risk-manager, compliance) exist in the directory and are passed as claims in the JWT. OPA reads these claims — RBAC provides the coarse-grained categorization, OPA's policy engine adds the fine-grained conditions.

Why not pure RBAC: The risk limit check (order.size <= limits[user.id]) is per-user numeric data, not a role property. Market hours check is environmental context. Supervisor approval for large orders is a workflow condition. All of these require PBAC's expressive policy language.
Exercise 3 · DevOps Platform Internal developer platform access control
Scenario: Your enterprise is building an internal developer platform (IDP) that manages Kubernetes namespaces, GitHub repositories, AWS accounts, and deployment pipelines. Engineers belong to product teams. Teams own namespaces and repos. Platform admins manage the infrastructure. Security engineers need read-only access to everything for audit. Onboarding a new team must provision access to all their resources atomically. What authorization model do you design?
▶ Reveal recommended design ▼
Recommended: ReBAC for resource access + RBAC for platform-level roles

This is a hybrid design. The resource access pattern (engineer can deploy to namespace because engineer IS member of team that OWNS namespace) is naturally ReBAC. Platform-level roles (platform-admin, security-auditor) are few, stable, and naturally RBAC.

ReBAC tuples:
(team:payments, member, user:alice)
(namespace:payments-prod, owner, team:payments)
(repo:payments-api, owner, team:payments)
Access check: "can alice deploy to namespace:payments-prod?" → alice IS member of team:payments → team:payments OWNS namespace:payments-prod → ALLOW.

RBAC for platform roles: platform-admin role gets access to all namespaces via a wildcard tuple: (namespace:*, admin, role:platform-admin). security-auditor role gets read access everywhere.

Team onboarding atomicity: When a new team is created, the IDP creates the team entity and all resource tuples in a single transaction (OpenFGA supports batch writes). All access is established atomically — no partial state where some resources are accessible and others aren't.

Why not pure RBAC: Creating roles for every team × environment combination (payments-prod-deployer, payments-staging-deployer, etc.) creates O(teams × environments) roles. ReBAC's team→namespace relationship model scales O(teams + resources) — linearly, not combinatorially.
Knowledge check

Test your authorization architecture depth

Q1 Your enterprise's Saviynt IGA system manages RBAC roles for 300 enterprise applications. An audit finds 8,000 distinct roles across 300 apps, with the average user holding 47 roles. What is the architectural problem and what is the remediation strategy? ▼
This is classic role explosion — the primary RBAC failure mode at enterprise scale.

Root causes: (1) Roles were created reactively per-request rather than by design. (2) Mover events added new roles without removing old ones (privilege creep). (3) Application teams created app-specific roles independently with no governance. (4) No role re-use across applications — similar access in App A and App B created two separate roles rather than one business role mapped to both.

Remediation strategy — Role Mining + Role Engineering:
(1) Role mining analysis: Use Saviynt's role mining capability to analyze actual access usage patterns across the 8,000 roles. Identify: which roles are never used (candidates for retirement), which roles frequently co-occur (candidates for merging), which roles differ by only one permission (candidates for consolidation).
(2) Business role design: Design roles from the top down — start with business functions (Finance-Analyst, HR-Manager) and map them to application permissions, rather than starting with application permissions and grouping upward.
(3) Role lifecycle governance: No role created without a business owner. Every role reviewed in an annual certification campaign. Roles without any assigned users for 90 days are automatically deprecated.
(4) Target state: Reduce to fewer than 50 business roles covering 80% of access. Remaining access handled via access request workflows with time-limited grants, not permanent roles.
Q2 Describe the OPA evaluation model. A microservice receives a request and calls OPA with {"subject":"alice","action":"delete","resource":"invoice/123","context":{"time":"14:00","department":"Finance"}}. Walk through how OPA processes this query against a Rego policy. ▼
OPA evaluation model — step by step:

1. Input document: The JSON object sent by the microservice becomes OPA's input document, accessible in Rego as input.subject, input.action, etc.

2. Data documents: OPA has pre-loaded policy data (from the PAP bundle — e.g., role-permission mappings, resource metadata) available as data.*.

3. Policy evaluation: OPA finds the relevant Rego rule — typically allow in the authz package. Example rule:
package authz
allow { input.subject == data.resources[input.resource].owner }
allow { input.action == "delete"; data.roles[input.subject][_] == "Finance-Admin"; business_hours }
business_hours { hour := time.clock(time.now_ns())[0]; hour >= 9; hour < 17 }

4. Unification: OPA evaluates each rule body by attempting to unify variables with values from input and data. If any rule body evaluates to true, allow is true.

For alice/delete/invoice/123: Check rule 1: is alice the owner of invoice/123? → data lookup. If yes → ALLOW. Check rule 2: does alice have Finance-Admin role? → data lookup. Is current time in business hours? → time check. If both → ALLOW. If no rule matches → allow is undefined → OPA returns {"result": false} → microservice returns 403.
Q3 A developer proposes embedding authorization logic in the application code: "We check if the user has the 'admin' attribute in our middleware and allow/deny accordingly." As an IAM architect, what are the problems with this approach and what is the correct architecture? ▼
Five problems with embedded authorization logic:

(1) Policy drift: Each team embeds their own authorization logic. Two teams with the same business requirement implement it differently. Policy inconsistency accumulates invisibly across the codebase.
(2) Policy change requires redeployment: To change who can perform an action, the code must be modified, tested, and deployed. For security-critical changes (e.g., removing a terminated admin's access), you cannot afford a deployment cycle.
(3) No audit trail of policy state: At any point in time, "what was the authorization policy for this action?" requires examining the git history of every application — impossible for audit purposes.
(4) No policy testing: Embedded authorization logic is rarely unit-tested for authorization correctness. A logic error might grant too much access silently.
(5) Single attribute check is not authorization: Checking one attribute (is_admin) is not fine-grained authorization — it's binary access control. It doesn't consider the resource being accessed, the action being taken, or any context.

Correct architecture: Externalize authorization to an OPA service. Application middleware calls POST /v1/data/authz/allow with the full context. Policy is managed in a PAP (Git repo → CI/CD → OPA bundle). Policy changes are deployed independently of application code. Policy is version-controlled, testable, and auditable. Authorization decisions are logged centrally.
Q4 What is the difference between authorization and entitlements? How does Saviynt (IGA) relate to OPA (authorization engine) in an enterprise authorization architecture? ▼
Authorization vs entitlements — a critical architectural distinction:

Entitlement: The right to access a resource or perform an action, assigned to a principal through a governance process (IGA). An entitlement is a persistent assignment — "alice has the Finance-Analyst role in Salesforce." Entitlements are managed by IGA systems (Saviynt, SailPoint), provisioned via SCIM/connectors, governed through certifications and SoD policies.

Authorization decision: The real-time evaluation of whether a principal's current entitlements (plus context) permit a specific action on a specific resource. Authorization is ephemeral — evaluated on each request by a policy engine (OPA, Cedar). It doesn't persist; it computes.

How Saviynt and OPA relate:
Saviynt manages the lifecycle of entitlements — who should have what access, through what approval process, with what review cadence. It writes entitlement data (roles, group memberships) to target systems (AD groups, application roles).

OPA evaluates access requests at runtime — should this request be allowed, given the principal's current entitlements (read from AD/JWT claims) and the policy's rules about those entitlements?

The data flow: Saviynt provisions alice → Finance-Analyst role → written to AD group → synced to Entra ID → appears in alice's JWT claims → OPA policy reads input.claims.roles → evaluates against Rego policy → allow/deny.

Saviynt governs what alice has. OPA decides what alice can do with it on each request.

Key takeaways — M06 · Authorization Architecture
  • Authorization is the most consequential IAM design decision. The model you choose determines your security posture, operational burden, and scalability ceiling. Authentication proves identity; authorization decides what to do with it.
  • Four models, four different problems: RBAC for stable job functions (simple, auditable, role explosion risk). ABAC for attribute/context-dependent access (fine-grained, flexible, requires good attribute data). PBAC for externalized policy-as-code (testable, deployable, microservices-native). ReBAC for relationship-based access (Google Drive model, per-object permissions, graph traversal).
  • PDP/PEP/PAP/PIP are the four universal authorization components. PEP intercepts and enforces. PDP evaluates policy. PAP manages policies. PIP provides attributes. Every authorization system — regardless of model — has all four.
  • Externalized authorization (PBAC with OPA/Cedar) is the correct architecture for microservices. Policy-as-code, testable in CI/CD, deployed independently of application code, centrally auditable. Embedded authorization logic in applications is an anti-pattern.
  • Google Zanzibar's tuple model is the foundation of modern ReBAC. Relationship tuples (object, relation, subject) enable graph traversal for inherited access. Consistency tokens (zookies) solve the distributed authorization consistency problem.
  • Role explosion is RBAC's primary failure mode — not a sign that RBAC is wrong, but that the roles were never designed. Role mining identifies natural clusters. Business role design + IGA governance prevents accumulation.
  • Saviynt governs entitlement lifecycle; OPA evaluates access requests. These are complementary, not competing. IGA provisions the entitlements that the authorization engine evaluates at runtime.

⚠️ Anti-pattern
Embedded authorization code
Authorization logic in application middleware is untestable, ungovernable, and non-auditable. Externalize to OPA. Every service calls the PDP — no service decides access for itself.

Indigo-sapphire for the structural, architectural weight of authorization design. Copper for the operational complexity — the implementation cost and governance burden. Phase 2 begins here.
Saviynt connection
IGA + AuthZ = complete governance
