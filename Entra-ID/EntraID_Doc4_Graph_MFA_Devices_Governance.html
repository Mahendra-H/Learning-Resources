CH 01

Authentication
Methods API

The Authentication Methods API is your programmatic window into every user's MFA registration state across your entire tenant. It's the API that answers the questions that used to require portal screenshots or CSV exports: Who has MFA registered? Who's using FIDO2? Who hasn't registered anything? Who still has SMS?

API Architecture Overview

Push · Passwordless · TOTP

R: UserAuthenticationMethod.Read.All
W: UserAuthenticationMethod.ReadWrite.All
Returns each registered Authenticator device. Key fields: id, displayName (device name), deviceTag, phoneAppVersion, authenticationMethod (Notification vs. NotificationAndCode).

The Unified /methods Endpoint — Reading Everything in One Call

# Get ALL registered authentication methods for a user in one call GET /users/{userId}/authentication/methods # Sample response — note @odata.type distinguishes method type { "value": [ { "@odata.type": "#microsoft.graph.microsoftAuthenticatorAuthenticationMethod", "id": "3b0f7c3e-...", "displayName": "John's iPhone", "deviceTag": "softwareOneTimePasscode" }, { "@odata.type": "#microsoft.graph.passwordAuthenticationMethod", "id": "28c10230-...", "createdDateTime": null // password exists but no creation timestamp stored }, { "@odata.type": "#microsoft.graph.fido2AuthenticationMethod", "id": "d0f9a2b1-...", "displayName": "YubiKey 5 NFC", "aaGuid": "2fc0579f-8113-47ea-b116-bb5a8db9202a", "attestationLevel": "attested" } ] } # Presence of passwordAuthenticationMethod ≠ MFA registered # Every user has a password method — check for OTHER methods to determine MFA registration
The password method trap: Every user in Entra ID has a passwordAuthenticationMethod entry. When scanning for "users with no MFA registered," you must filter out the password method and check whether any OTHER method types exist. A user with only the password method has zero MFA registered. This is the most common mistake in tenant MFA audit scripts.

Creating a Temporary Access Pass via API

# Create a TAP for a new hire — for Authenticator bootstrapping POST /users/{userId}/authentication/temporaryAccessPassMethods Authorization: Bearer {token_with_UserAuthMethod.ReadWrite.All} Content-Type: application/json { "startDateTime": "2024-06-15T09:00:00Z", // when it becomes valid "lifetimeInMinutes": 480, // 8 hours — enough for Day 1 "isUsableOnce": false // false = can use until expiry } # CRITICAL: The TAP passcode is ONLY in the POST response — capture it immediately # Response: { "id": "a1b2c3d4-...", "temporaryAccessPass": "47829163", ← THIS IS THE PASSCODE — store securely, send to user "startDateTime": "2024-06-15T09:00:00Z", "lifetimeInMinutes": 480, "isUsable": true, "isUsableOnce": false }
CH 02

MFA Inventory
at Scale

Building a tenant-wide MFA registration report is one of the most common tasks an IAM engineer faces. Done naively it's slow and throttle-prone. Done right it's fast, complete, and the foundation of your security posture reporting.

The Right Architecture for Bulk MFA Queries

Querying MFA methods for 10,000 users one-by-one is like calling each employee in a 10,000-person company to ask if they have a badge. You'd be on the phone for days and the receptionist (API throttle) would cut you off. The smarter approach: use the credential user registration details report — a pre-computed report that Microsoft generates for your tenant, answering "who has what MFA methods" for all users in a single API call. It's eventually consistent (up to a few hours lag) but far more efficient for reporting than per-user method queries. Reserve per-user method queries for real-time lookups on individual users.

Option 1: Pre-Built Registration Report (Recommended for Bulk)

# The single most useful MFA reporting endpoint # Returns pre-computed auth method registration state for ALL users GET /reports/authenticationMethods/userRegistrationDetails Required permission: UserAuthenticationMethod.Read.All (Application) # Sample response entry: { "id": "87a3f21c-...", "userPrincipalName": "john@contoso.com", "userDisplayName": "John Smith", "isMfaRegistered": true, // Has ANY MFA method "isMfaCapable": true, // Can perform MFA right now "isPasswordlessCapable": false, // Has passwordless method "isSsprRegistered": true, // Can do self-service password reset "isSsprEnabled": true, // SSPR policy applies to this user "isSsprCapable": true, // Registered AND enabled "isSystemPreferredAuthenticationMethodEnabled": true, "methodsRegistered": [ "microsoftAuthenticatorPush", "softwareOneTimePasscode", "email" ], "defaultMfaMethod": "microsoftAuthenticatorPush" }

Option 2: Per-User Method Query + Batch (For Detailed Audits)

# For detailed method-level data (device names, FIDO2 key models, creation dates) # Step 1: Get all user IDs GET /users?$select=id,userPrincipalName,displayName,accountEnabled&$top=999 # Step 2: Batch method queries — 20 per batch request POST /$batch { "requests": [ { "id": "1", "method": "GET", "url": "/users/user1-id/authentication/methods" }, { "id": "2", "method": "GET", "url": "/users/user2-id/authentication/methods" } // ... up to 20 users per batch ] } # For 10,000 users: 10,000 / 20 = 500 batch requests # With retry-after handling: completes in minutes vs. hours for sequential calls

MFA Reporting Use Cases — Real Queries

Find All Users With No MFA Registered

GET /reports/authenticationMethods/userRegistrationDetails?$filter=isMfaRegistered eq false&$select=id,userPrincipalName,isMfaRegistered,methodsRegistered # Returns users with zero MFA methods — your highest-risk population

Find Users Still Using SMS as Only MFA

GET /reports/authenticationMethods/userRegistrationDetails?$filter=methodsRegistered/any(m:m eq 'mobilePhone') and not(methodsRegistered/any(m:m eq 'microsoftAuthenticatorPush'))&$select=id,userPrincipalName,methodsRegistered # Users who registered SMS but NOT Authenticator — migration candidates

Find Users With Passwordless Capability

GET /reports/authenticationMethods/userRegistrationDetails?$filter=isPasswordlessCapable eq true&$select=id,userPrincipalName,methodsRegistered,defaultMfaMethod # Track passwordless adoption progress over time

Count by Method Type (Summary Statistics)

GET /reports/authenticationMethods/usersRegisteredByMethod # Returns aggregate counts — how many users registered each method type # No per-user data — just counts. Great for executive dashboards. { "userRegistrationMethodCounts": [ { "authenticationMethod": "microsoftAuthenticatorPush", "userCount": 8423 }, { "authenticationMethod": "fido2", "userCount": 312 }, { "authenticationMethod": "mobilePhone", "userCount": 1205 } ] }
Governance Automation Scenario (Company A context): You need a monthly MFA compliance report for your CISO — percentage of users with MFA registered, breakdown by method, list of non-compliant users. Build a scheduled Graph API job (Azure Function, GitHub Actions, or a simple Node.js script with MSAL): (1) Query /reports/authenticationMethods/userRegistrationDetails for all users; (2) Filter non-registered users; (3) Cross-reference with active users only (exclude disabled accounts); (4) Output to CSV or push to a SharePoint list; (5) Email the summary to the security team. Runtime for 10,000 users: under 2 minutes with the pre-built report endpoint. This replaces a manual portal export that used to take an analyst 30 minutes.

Device Inventory Architecture

Device Inventory via Graph — Query Flow & Data Model

Device Queries — Production Cookbook

─────── INVENTORY QUERIES ─────── # All corporate Windows devices (Entra ID Joined or Hybrid) GET /devices?$filter=(trustType eq 'AzureAd' or trustType eq 'ServerAd') and operatingSystem eq 'Windows' &$select=id,deviceId,displayName,trustType,operatingSystem,operatingSystemVersion,isCompliant,approximateLastSignInDateTime &$top=999 # Find stale devices (no sign-in in 90 days) GET /devices?$filter=approximateLastSignInDateTime le 2024-03-01T00:00:00Z and accountEnabled eq true &$select=id,displayName,trustType,approximateLastSignInDateTime,registrationDateTime &$orderby=approximateLastSignInDateTime asc ConsistencyLevel: eventual # Find non-compliant devices (requires Intune) GET /devices?$filter=isCompliant eq false and accountEnabled eq true &$select=id,displayName,operatingSystem,isCompliant,isManaged,approximateLastSignInDateTime # Get devices owned by a specific user GET /users/{userId}/ownedDevices?$select=id,displayName,trustType,operatingSystem,isCompliant ─────── LIFECYCLE OPERATIONS ─────── # Disable a device (keeps it in directory but blocks token acquisition) PATCH /devices/{id} { "accountEnabled": false } # Delete a device (permanently removes from Entra ID) DELETE /devices/{id} # Note: Deletion is soft — device goes to deletedItems, recoverable for 30 days # Required permissions for write operations: Device.ReadWrite.All
Stale Device Cleanup Automation (Governance Pattern): Build a monthly cleanup job: (1) Query all devices with approximateLastSignInDateTime older than 90 days AND accountEnabled eq true; (2) Cross-reference with Intune enrollment state; (3) Disable (not delete) devices older than 90 days; (4) After 30-day grace period with no re-activation, delete them. The 30-day soft-delete recovery window gives you a safety net. Log all operations to Azure Monitor. Add an exception list for service VMs and shared kiosk devices that have legitimate reasons for infrequent sign-ins. This pattern reduces your device sprawl by 15–30% in the first run for most mature tenants.

Audit & Sign-in
Logs via Graph

Entra ID's audit and sign-in logs are your forensic record for every identity event in your tenant. Graph gives you programmatic access to pull, filter, and correlate these logs — essential for SIEM integration, incident response, and compliance reporting.

Sign-In Logs — The Most Valuable Dataset

# Full sign-in log query with IAM-relevant fields GET /auditLogs/signIns?$filter=createdDateTime ge 2024-06-01T00:00:00Z &$select=id,createdDateTime,userPrincipalName,userId,appDisplayName,appId, ipAddress,location,status,riskLevelAggregated,riskLevelDuringSignIn, conditionalAccessStatus,authenticationRequirement,mfaDetail, clientAppUsed,deviceDetail,appliedConditionalAccessPolicies &$top=999&$orderby=createdDateTime desc Required permission: AuditLog.Read.All
📊 Sign-In Log Entry — Key Fields for IAM Engineers
status.errorCode0 = success. Non-zero = failure. errorCode 50076 = MFA required.
conditionalAccessStatus"success" | "failure" | "notApplied" | "unknownFutureValue"
authenticationRequirement"singleFactorAuthentication" | "multiFactorAuthentication"
mfaDetail.authMethodWhich MFA method was used: PhoneAppNotification, FIDO2, etc.

Targeted Sign-In Queries for Incident Response

# All failed sign-ins for a specific user in last 24 hours GET /auditLogs/signIns?$filter=userPrincipalName eq 'john@contoso.com' and status/errorCode ne 0 and createdDateTime ge 2024-06-14T00:00:00Z &$select=createdDateTime,ipAddress,status,riskLevelAggregated,location,appDisplayName # High-risk sign-ins across entire tenant GET /auditLogs/signIns?$filter=riskLevelAggregated eq 'high' and createdDateTime ge 2024-06-01T00:00:00Z &$select=userPrincipalName,createdDateTime,ipAddress,location,riskEventTypesV2,appDisplayName # Sign-ins where CA policy FAILED (potential policy misconfiguration signal) GET /auditLogs/signIns?$filter=conditionalAccessStatus eq 'failure' and createdDateTime ge 2024-06-14T00:00:00Z # Legacy auth sign-ins (modern auth is blocked by CA — these indicate bypass risk) GET /auditLogs/signIns?$filter=clientAppUsed eq 'Exchange ActiveSync' or clientAppUsed eq 'Other clients' &$select=userPrincipalName,appDisplayName,clientAppUsed,createdDateTime,ipAddress

Directory Audit Logs — Change Tracking

# All user-related changes in last 7 days GET /auditLogs/directoryAudits?$filter=category eq 'User' and activityDateTime ge 2024-06-08T00:00:00Z &$select=activityDateTime,activityDisplayName,initiatedBy,targetResources,result &$orderby=activityDateTime desc # All admin role assignment changes (critical for privilege monitoring) GET /auditLogs/directoryAudits?$filter=category eq 'RoleManagement' &$select=activityDateTime,activityDisplayName,initiatedBy,targetResources,result # Changes to a specific user's authentication methods GET /auditLogs/directoryAudits?$filter=category eq 'UserManagement' and activityDisplayName eq 'User registered security info' and targetResources/any(t:t/id eq '{userId}') # App permission consent events (watch for suspicious OAuth grants) GET /auditLogs/directoryAudits?$filter=activityDisplayName eq 'Consent to application' and activityDateTime ge 2024-06-01T00:00:00Z &$select=activityDateTime,initiatedBy,targetResources,result
Log retention limits: Entra ID P1/P2 retains sign-in logs for 30 days and audit logs for 30 days. Free tenants get 7 days. If your compliance requirements need longer retention (SOC2, ISO27001 often require 90+ days), you MUST stream logs to an external store: Azure Monitor Log Analytics, Azure Event Hub → SIEM, or a third-party solution. Set this up before your 30-day window closes after any incident — log loss is the single most painful operational gap in post-incident investigations.

SIEM Integration Pattern — Continuous Log Streaming

# Efficient continuous pull pattern using delta queries on sign-in logs # Run every 5 minutes — only pulls new events since last run # First run: get initial batch + deltaLink GET /auditLogs/signIns/delta?$filter=createdDateTime ge {start_time}&$select={minimal_fields}&$top=999 # Store deltaLink. Every subsequent run: GET {stored_deltaLink} # Returns only new sign-in events since last poll # No duplicate events, no missed events, minimal API calls # Process events → push to SIEM (Sentinel, Splunk, QRadar, etc.) # Store new deltaLink for next run

Building an Executive Security Dashboard — The Data Model

Monthly CISO Dashboard Pattern: Combine these five endpoints into a single report that runs on the 1st of each month:

1. /reports/authenticationMethods/usersRegisteredByFeature → % users with MFA, SSPR, passwordless
2. /reports/authenticationMethods/userRegistrationDetails?$filter=isMfaRegistered eq false → count + list of unprotected users
3. /identityProtection/riskyUsers?$filter=riskLevel eq 'high' → currently high-risk users requiring remediation

Automate as an Azure Function, output to a SharePoint page or Power BI. The CISO gets a consistent, data-driven monthly security posture snapshot without manual portal work.
CH 06

Security & Least Privilege

The permissions model for Graph API integrations is where well-intentioned engineers create the most security debt. This chapter lays out the principles, anti-patterns, and concrete architectural decisions that define a production-grade Graph integration.

The Permission Hygiene Hierarchy

1
Use Managed Identity if running on Azure infrastructure
Azure VMs, App Service, Functions, AKS — all support Managed Identity. No credentials. No rotation. No leakage risk. The Azure platform handles token acquisition. Always preferred over any credential-based approach.
2
Use certificate-based auth if Managed Identity isn't available
Client certificate assertion means no secret to leak. Store private key in Azure Key Vault with auto-rotation. The app never handles the key directly — Key Vault signs the JWT assertion. Asymmetric cryptography: even if an attacker gets your App Registration details, they can't authenticate without the private key.
3
Use client secrets only as a last resort — with mandatory rotation
If you must use a client secret: max 1-year expiry (never 2-year), store in Key Vault (never in code or config files), alert on expiry 60 days before, rotate quarterly. Treat client secrets like database passwords — the same operational discipline applies.
4
Request minimum required permissions — scope to read-only when possible
User.Read.All for a reporting tool. User.ReadWrite.All only for provisioning tools. UserAuthenticationMethod.Read.All for audit scripts. UserAuthenticationMethod.ReadWrite.All only for tools that actually create TAPs or delete methods. Wrong permissions = blast radius multiplier if credentials are compromised.
5
One App Registration per logical service — never share
Sharing an App Registration across multiple tools means a compromised credential gives access to everything that service does. Separate App Registrations = separate blast radius, separate audit trail, independent rotation. Clean audit logs that show exactly which service called which API.

Never request Directory.Read.All or Directory.ReadWrite.All. These are broad permissions that grant access to nearly everything in the directory. They exist for legacy compatibility. Use specific permissions instead — User.Read.All + Group.Read.All + Device.Read.All is always better than Directory.Read.All. Specific permissions are clearer in admin consent, easier to audit, and narrower in blast radius. If a vendor's documentation says "we need Directory.Read.All" — push back and ask why they can't use specific permissions.
CH 07

Production Governance Patterns

This chapter ties together everything from across all four docs — the governance patterns, operational checklists, and integration architectures that define a mature Entra ID deployment. This is the "from learning to production" chapter.

The Production Entra ID Integration Checklist

  • Break-glass accounts created (2 minimum), credentials stored in physical safe, excluded from ALL CA policies, monitored with SIEM alerts on any sign-in
  • Baseline CA policies deployed: MFA for all users, phishing-resistant MFA for admin roles, block legacy auth, require compliant device for sensitive apps
  • Authentication Methods Policy configured — legacy per-user MFA disabled for all users (migrated to CA-driven MFA)
  • Password Hash Sync (or PTA) configured with Seamless SSO — ADFS retired or scheduled for retirement
  • UPN strategy validated — all users have routable UPN suffix matching a verified Entra ID domain (no .local or .internal)
  • All App Registrations audited — no client secrets expiring within 60 days, certificate-based auth preferred
  • Service principal permission audit complete — no overprivileged apps with Directory.ReadWrite.All or equivalent
  • Sign-in and audit logs streaming to SIEM with 90+ day retention (Azure Monitor or external)
  • Device cleanup job scheduled — stale devices (90+ days) identified and disabled monthly
  • Access Reviews scheduled — admin roles monthly, sensitive groups quarterly, all apps semi-annual
  • PIM configured for all Entra ID directory roles — no standing Global Admin except break-glass
  • Entitlement Management catalogs created for all major application bundles — no more email-based access requests
  • Lifecycle Workflows connected to HR system — automated joiner/mover/leaver
  • MFA registration campaign active — target 100% registration before enforcing MFA
  • Named Locations defined — corporate office IPs and VPN egress IPs as trusted locations
  • Conditional Access in Report-Only mode for 2 weeks before enabling — impact analysis complete

The Migration Path: PingFederate → Entra ID SSO

When to move an SP connection from PingFederate to Entra ID:

Move to Entra ID native SSO when: The app supports modern OIDC/SAML, is used by cloud users (not requiring on-prem data), and doesn't require complex attribute transformations that PingFederate's scripting handles. Standard SaaS apps (Salesforce, ServiceNow, Workday, Jira Cloud) all have pre-built Entra ID gallery connectors — migration is a configuration exercise, not an engineering project.

Keep on PingFederate when: The app requires complex claims transformations (JavaScript logic in PF adapters), depends on LDAP-sourced attributes not flowing through Entra ID, needs PingDirectory as the authoritative identity store, or is a legacy protocol app (Kerberos-constrained delegation, WS-Trust). PingFederate as a federation broker in front of Entra ID (federated IdP) is also a valid hybrid pattern for these cases.

The final chapter. Production readiness isn't just architecture — it's knowing what breaks, why it breaks, and how to fix it fast. These are the real-world failure patterns and diagnostic approaches for Entra ID and Graph API integrations.

Graph API Troubleshooting Flow

1
Reproduce in Graph Explorer first
Before debugging code, run the exact same query in Graph Explorer with the same user/app context. If it works in Graph Explorer but not your code — the issue is in token acquisition or request construction. If it fails in Graph Explorer — the issue is permissions, data, or the endpoint itself.
2
Decode the access token and verify claims
Paste your access token into jwt.ms. Check: aud is the correct resource, tid is your tenant, scp or roles contains the required permission. A token with wrong audience or missing permission will fail before Graph even processes the request.
3
Check if admin consent was actually granted
Navigate to the Enterprise Application (Service Principal) → Permissions blade. The "Admin consent" column shows whether each permission was consented. A common mistake: adding a permission to the App Registration but forgetting to grant admin consent. The permission appears requested but not granted.
4
Check sign-in logs for the service principal
Filter /auditLogs/signIns by appId or servicePrincipalId. See exact error codes, CA policy results, and authentication details for every token acquisition attempt your app made. This gives you the full picture including CA failures that your app-level error handling may obscure.
5
For throttling: respect Retry-After, don't retry immediately
HTTP 429 responses include a Retry-After header specifying how many seconds to wait. Ignoring this and retrying immediately makes the throttle worse and digs a deeper hole. Implement exponential backoff with Retry-After as the floor. Log all 429s to identify which operations are generating the most load.

Final architecture principle — the one thing to remember from this entire series: Entra ID is not a product you configure once and forget. It's a living platform. Microsoft releases new features every month. Deprecations happen. Your organization's security posture needs to evolve with it. Build your Graph API integrations to be observable (log every call and its result), maintainable (one service per App Registration, certificates not secrets, minimal permissions), and adaptable (use the v1.0 endpoint, subscribe to deprecation notices, test beta features before they ship). The IAM engineer who treats Entra ID as infrastructure to maintain — not a checkbox to tick — is the one whose systems don't fail at 2 AM.
