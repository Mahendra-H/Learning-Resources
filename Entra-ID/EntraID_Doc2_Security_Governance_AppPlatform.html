CH 01

Multi-Factor Authentication
Deep Dive

MFA in Entra ID is not a single feature — it's a policy surface, a registration journey, and an API-queryable data model rolled into one. Understanding all three layers is what separates someone who "configures MFA" from someone who architects identity security at enterprise scale.

The Two MFA Control Planes (And Why This Matters)

Most guides only teach one of the two MFA control planes. Entra ID has both a legacy per-user MFA model and a modern Authentication Methods Policy model. They can conflict. They're managed in different portals. And Microsoft is deprecating the legacy model — but millions of tenants still rely on it. You need to know both.
Criterion Legacy Per-User MFA Authentication Methods Policy (Modern)
Where managedAzure Portal → Users → Per-user MFA (legacy blade)Entra ID Portal → Protection → Authentication Methods
GranularityPer user: Enabled / Enforced / DisabledPer method, per group, with fine-grained config per method

Migration Scenario (Company A context): Your tenant was set up years ago and per-user MFA was enabled for all users. You're now rolling out Conditional Access. Problem: users with per-user MFA enforced will be prompted for MFA before CA runs — meaning CA cannot control the experience (can't skip MFA for trusted locations, can't require stronger auth for sensitive apps). The fix: migrate all users to CA-driven MFA using the "MFA Registration Policy" to ensure everyone registers, then disable per-user MFA for those users. Microsoft provides a conversion tool in the Security portal. This is a planned migration, not a flip-the-switch operation.

Authentication Methods — The Full Inventory

📱
Microsoft Authenticator
Push notifications, number matching, passwordless phone sign-in. The recommended method. Number matching is now mandatory (can't disable) to prevent MFA fatigue attacks.
🔑
FIDO2 Security Keys
Hardware keys (YubiKey, etc). Phishing-resistant. Highest assurance. Required for highly privileged accounts in Zero Trust architectures.
🔢
Temporary Access Pass (TAP)
Time-limited passcode for onboarding or recovery. The right way to bootstrap passwordless — use TAP to register Authenticator or FIDO2, then retire the TAP.
🪪
Certificate-Based Auth (CBA)
Smart cards and PKI certificates. Phishing-resistant. Common in government/defense. Satisfies MFA in a single factor (the cert = something you have).
📞
Phone (SMS / Voice)
Legacy. SMS is vulnerable to SIM-swap attacks. NIST 800-63B deprecated SMS as a second factor. Use only where no better option exists. Never for admin accounts.
📧
Email OTP
One-time passcode to email address. Used primarily for B2B guest users who don't have an Authenticator-capable device.
🔐
Windows Hello for Business
Biometric or PIN on Entra-joined Windows devices. Phishing-resistant, device-bound. Replaces password for Windows sign-in with cloud-backed credential.
🔒
Software OATH Tokens
TOTP apps (Google Authenticator, Authy, etc.) for tenants where Microsoft Authenticator isn't mandated. Weaker than push (no real-time approval) but better than SMS.

MFA Registration — The User Journey

MFA registration is like getting a security badge for a building. Just because the building requires badges doesn't mean every employee has one yet. The Registration Campaign is the HR department chasing everyone to come get badged before the deadline. The Combined Registration Portal (aka.ms/mysecurityinfo) is the badging office. The Authentication Methods Policy is the rulebook about which badge types are valid. And the MFA Registration Policy (in Identity Protection) is the automated reminder system that intercepts users at sign-in until they register.

Registration Campaign vs. MFA Registration Policy

These are two different mechanisms that both nudge users to register — and they confuse even seasoned admins:

  • Registration Campaign (under Authentication Methods Policy): Interrupts sign-in with a "Set up Microsoft Authenticator" nudge. Can be dismissed for a configured number of days. Targeted at migrating users to the Authenticator app specifically.
  • MFA Registration Policy (under Identity Protection): Requires users to register any MFA method before they can continue. Enforced via CA-like conditions. This is how you ensure 100% MFA registration before enforcing MFA on sign-ins.

Authentication Strengths — The Modern MFA Tiering Model

Entra ID now supports Authentication Strengths — a CA grant control that lets you require a specific tier of MFA, not just "any MFA." This is the phishing-resistant MFA story:

Strength LevelMethods IncludedPhishing Resistant?Use Case
Multifactor AuthenticationAny MFA combo❌ NoGeneral user populations
Passwordless MFAAuthenticator (passwordless), WHfB, FIDO2PartialPrivileged operations, sensitive apps
Phishing-Resistant MFAFIDO2 keys, WHfB, CBA only✅ YesGlobal Admins, privileged roles, government requirements
Architect's Pattern: Use Authentication Strengths in CA policies instead of just "require MFA." For your IAM team's admin accounts, require Phishing-Resistant MFA authentication strength. For regular users accessing sensitive data, require Passwordless MFA. For general access, require Multifactor Authentication. This creates a graduated assurance ladder enforced by policy — not by training users to pick the right method.
🔬 Deep Dive: Number Matching & MFA Fatigue Defense

The MFA Fatigue Attack

An attacker who has stolen a user's password repeatedly sends Authenticator push notifications hoping the user clicks "Approve" to make the noise stop. This is called MFA fatigue or MFA push bombing. Several high-profile breaches (Uber 2022, Cisco 2022) used exactly this technique.

Number Matching

Microsoft's primary defense: when the Authenticator push arrives, the app shows a number (e.g., "47") and the user must type that number into the app before approving. The number is displayed on the sign-in screen. An attacker can push notifications all day, but the user won't see the number on their screen — only a legitimate sign-in shows it. Microsoft enforced number matching for all tenants in May 2023. It cannot be disabled.

Additional Context

The Authenticator app can also show the application name and approximate geographic location of the sign-in attempt. Enabling this additional context configuration (under Authentication Methods → Microsoft Authenticator → configuration) gives users the context they need to spot suspicious pushes instantly.

CH 02

Conditional Access
Engine

Conditional Access is the most powerful and most complex feature in Entra ID. It's Entra ID's real-time policy engine — evaluating every sign-in against a set of conditions and applying access controls. Nothing in PingFederate has a direct equivalent to its depth and integration.

The Mental Model: If–Then Policy

Think of Conditional Access as a bouncer with a decision matrix. When you approach the door (sign-in attempt), the bouncer doesn't just check your ID. They check: Who are you? What app are you trying to enter? Where are you coming from (IP/location)? What device are you using — is it compliant? What time is it? What's your risk score? Based on all of these signals, the bouncer either lets you in, makes you prove you're really you (MFA), puts you on probation (session restrictions), or turns you away. And there are multiple bouncers in sequence — if ANY one says block, you're out.

Real CA Policy Patterns — What You'll Actually Build

Policy 1 — Baseline MFA for All Users:
Users: All users
Apps: All cloud apps
Exclude: Break-glass accounts (emergency access), service accounts
Grant: Require MFA
Rationale: The foundational policy every tenant must have. Without a baseline MFA policy, any user with a stolen password is fully compromised.
Policy 2 — Admin Role Protection (Phishing-Resistant):
Users: Directory role members (Global Admin, Security Admin, Privileged Role Admin, etc.)
Apps: All cloud apps
Grant: Require Authentication Strength → Phishing-Resistant MFA
Sign-in Frequency: Every time (no persistent sessions for admins)
Rationale: Admin accounts are the highest-value target. Requiring FIDO2 or WHfB eliminates the push-bombing attack vector entirely.
Policy 3 — Trusted Location Bypass:
Users: All users
Apps: All cloud apps
Locations: Include all, Exclude named corporate office IPs
Grant: Require MFA
Rationale: Users on corporate network skip the MFA prompt. Sign-ins from outside are challenged. This is the "smart MFA" pattern — reduce friction for known-good locations while protecting external access. Caveat: VPNs and split tunneling can make this unreliable. Always layer with device compliance too.
Policy 4 — High Risk Sign-In → Force Re-Auth:
Users: All users
Apps: All cloud apps
Conditions: Sign-in risk: High
Grant: Require MFA + Require password change
Rationale: When Identity Protection detects a high-risk sign-in (anonymous IP, impossible travel, malware-linked IP), immediately force step-up auth. If the user can't MFA, they can't get in — even with valid credentials.

CA Evaluation Order — Critical Details

CA policies don't have a priority order — ALL matching policies are evaluated. Unlike firewall rules where the first match wins, ALL applicable CA policies are evaluated and their results are combined. Grant controls use OR logic across policies by default (satisfying any policy's grant is sufficient). But Block overrides everything — if any single policy evaluates to Block for a sign-in, access is denied regardless of other policies granting access. This means a misconfigured block policy can silently lock out users even when other policies would grant access.

Continuous Access Evaluation (CAE)

Classic OAuth tokens are valid until they expire — typically 1 hour. If a user is compromised and their account is disabled, they could continue accessing resources for up to an hour before the token expires. CAE solves this.

Classic token validation is like a day-pass to an amusement park. Once you have it, the gates don't check you again — you just wave the pass. CAE is like a smart wristband that's connected to a central system. The moment park security marks your wristband as "revoked" (account disabled, risky user flagged, location policy changed), the next turnstile will reject it — even if the day isn't over. For Microsoft-native apps (Teams, Exchange, SharePoint, Graph), CAE reduces the effective token validity to near-real-time revocation. For third-party apps that don't support CAE, the classic 1-hour window still applies.

CAE triggers near-real-time revocation when:

  • Account is disabled or deleted in Entra ID
  • Password is changed or reset
  • MFA is newly required for the user by a CA policy change
  • User's IP changes significantly (leaving a trusted named location)
  • High user risk is detected by Identity Protection

Named Locations and the Trusted Network Strategy

Named Locations are IP ranges or countries that you label for use in CA policies. There are two types:

IP Range BasedCountry/Region Based
Define specific IPv4/IPv6 CIDR ranges. Can be marked as "trusted." Trusted locations get elevated trust in Identity Protection risk scoring.Select countries. Useful for geo-blocking (block all sign-ins from countries where you have no users or operations).

PingFederate's equivalent of Named Locations is the Authentication Policy Contract with IP range selectors or PingFederate's Adaptive Authentication Engine (risk scoring). The big difference: in PingFederate, you explicitly build these as adapter chain conditions in a policy tree. In Entra ID, Named Locations are a shared resource referenced across multiple CA policies — change the IP range in one place, all policies using it update automatically. Much more maintainable at enterprise scale.
🔬 Deep Dive: Break-Glass Accounts — The Safety Net

What Are Break-Glass Accounts?

Emergency access accounts that are excluded from ALL CA policies, including MFA requirements. These exist because if your CA policies have a bug, or your MFA provider has an outage, you need a way in to fix things — otherwise you're locked out of your own tenant. This has happened to real organizations.

Break-Glass Account Requirements

  • Cloud-only accounts — never synced from on-prem AD (AD outage can't affect them)
  • Global Administrator role assigned directly, not via PIM
  • Non-federated — authenticate directly to Entra ID (no ADFS, no external IdP)
  • FIDO2 key stored in a physical safe, or a very long complex password split between two people
  • Excluded from ALL CA policies (including MFA, device compliance, location policies)
  • Monitored with alerts on any sign-in activity — a break-glass sign-in should trigger immediate incident response
  • Credentials rotated quarterly and tested by a drill

How Many?

Microsoft recommends at least two break-glass accounts, with credentials stored separately — so a single person being unavailable (sick, travel) doesn't leave you without recovery options.

CH 03

The Application
Registration Model

The relationship between App Registrations, Enterprise Applications, and Service Principals is the single concept that confuses the most experienced IAM engineers coming to Entra ID. Get this right and everything else about Entra ID's app model clicks.

The Three-Object Model

Think of it like a movie franchise. The App Registration is the original screenplay — one master document owned by the creator. The Enterprise Application (Service Principal) in each tenant is like a specific screening license for that movie in a given country. The movie studio (app developer's tenant) has the screenplay. Every cinema chain (enterprise tenant) that wants to show the movie gets their own local license — their own service principal. The license references the original screenplay but adds local configuration (what ratings board approved it, what price to charge, who can watch it). This is exactly how multi-tenant apps work: one App Registration, one Service Principal per tenant.
App Registration → Enterprise App → Service Principal — Full Relationship Map

App Registration Deep Dive — What Lives Where

The most important mental model: The App Registration is the blueprint — it defines what the app is, what permissions it requests, and what it can do. The Service Principal is the instance in each tenant — it records what permissions were actually granted, who consented, and what the SSO configuration is. You can't configure SSO settings on an App Registration. You can't configure permission grants on an App Registration. These live on the Service Principal.

App Registration Key Configuration Areas

Authentication
Redirect URIs, platform configs (SPA, Web, Mobile), supported account types (single vs. multi-tenant), ID/access token settings.
Certificates & Secrets
Client secrets (expiring, rotate them!) or certificates (preferred). These are the credentials your app uses in client_credentials or auth code flows.
API Permissions
What Graph / other API scopes the app requests. Delegated vs. Application. Requesting doesn't grant — admin consent is still needed.
Expose an API
If your app IS an API — define your own scopes here. Other apps request these scopes to access your API. This is how microservice-to-microservice auth works.
App Roles
Custom roles defined by your app (e.g., "Approver", "ReadOnly"). Assigned to users/groups, appear in the token as the roles claim for the app to use for authZ.
Manifest
JSON representation of the full app object. Some settings only configurable here (e.g., accessTokenAcceptedVersion, groupMembershipClaims, optional claims).

Enterprise Application (Service Principal) Configuration Areas

Users and Groups
Assignment of users/groups to the app (access gate) and to app roles. If "Assignment required" is on, only assigned users can sign in.
Single Sign-On
SSO method: OIDC, SAML, or Password. SAML config (EntityID, ACS URL, attributes, claims) is all here.
Provisioning
SCIM provisioning config — push users/groups to the SaaS app automatically when they're assigned. Joiner/mover/leaver automation.
Permissions
The actual granted permissions — what was admin-consented. This is the source of truth for what the app can do in your tenant.
In PingFederate terms: the App Registration ≈ your SP Connection template / Partner metadata. The Enterprise Application (Service Principal) ≈ a deployed SP Connection instance with active policies and attribute contracts. The "Expose an API / request permissions" model ≈ PingFederate's resource server + scope management in the OAuth AS. The key structural difference: in PingFederate, you configure one connection per SP. In Entra ID, one App Registration can instantiate into thousands of tenant Service Principals — this is the gallery app and multi-tenant app architecture.
🔬 Deep Dive: Client Secrets vs. Certificates — Why Always Use Certs

Client Secrets — The Convenient Footgun

Client secrets are simple strings that expire (max 2 years). They're easy to create and easy to leak — committed to Git repos, stored in config files, logged in application logs. When they expire and aren't rotated, production auth breaks. Every IAM post-mortem involving service-to-service auth eventually mentions a leaked or expired client secret.

Certificates — The Right Answer

Client certificate authentication uses asymmetric cryptography. Your app signs a JWT assertion with its private key. Entra ID verifies the signature using the public key registered on the App Registration. The private key never leaves your key vault. If an attacker gets your public key (which is public by design), they can't authenticate. Rotation is managed separately from the app. Azure Key Vault can issue and auto-rotate certificates with zero code changes.

# Token request using certificate (client_assertion) POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token # Body parameters: grant_type = client_credentials client_id = {appId} client_assertion_type = urn:ietf:params:oauth:client-assertion-type:jwt-bearer client_assertion = {signed_JWT_with_private_key} scope = https://graph.microsoft.com/.default # vs. client secret (avoid this in production): client_secret = {the_secret_string} ← leaked = full compromise

Managed Identity — The Even Better Answer

For apps running on Azure infrastructure (App Service, Functions, VMs, AKS), use Managed Identity instead. No credentials at all. The Azure platform handles token acquisition transparently. Your app calls the Instance Metadata Service (IMDS) endpoint locally, gets a token, uses it. Zero rotation, zero secrets, zero certificates to manage.

You know the OAuth 2.0 spec. What you need here is how Entra ID implements it — the Microsoft-specific behaviors, the token formats, the claims that matter, and the nuances that bite engineers in production.

Token Anatomy — What's Inside an Entra ID Access Token

Do not validate Access Tokens by inspecting their claims in your application code — except for the aud and tid claims. Access Tokens are for the resource (the API), not for the client app. Their format is an implementation detail that Microsoft can change. Use the ID Token for user identity in your client app, and validate it using the OIDC discovery endpoint + JWKS keys. The only claims you must validate in an Access Token if you're the resource API: aud (must match your resource URI), tid (must match your tenant if you're single-tenant), iss (validate issuer), and signature.
🔍 Access Token Claims — The IAM Engineer's Reference
issIssuer — https://login.microsoftonline.com/{tenantId}/v2.0. Validate this.
audAudience — the resource/API this token is for. Must match your app's URI. Validate this.
tidTenant ID — which tenant issued this token. Validate for single-tenant apps.
oidObject ID of the user/service principal. Stable across token refreshes. Use as user identifier.
subSubject — pairwise identifier (unique per app+user combo). NOT the same as oid. Don't use as global user ID.
scpScopes granted (delegated tokens). Space-separated. "User.Read openid profile". Authorize at the API using this.
rolesApp roles granted (application tokens OR user app role assignments). Use for coarse authorization in your API.
amrAuthentication Methods Reference. ["pwd"], ["mfa","pwd"], ["hwk"]. How the user authenticated. Use for step-up auth decisions.
acrAuthentication Context Reference. Set by CA using Authentication Context. Custom values you define.
azpAuthorized party — the client app that requested the token (its appId).

upn / preferred_usernameUser Principal Name. Optional claim — request via optional claims in App Registration manifest.

The On-Behalf-Of Flow — Microservice Identity Chain

A user signs into your front-end app (App A). App A needs to call a back-end API (App B), which in turn calls Microsoft Graph. The user's identity needs to flow through the entire chain — App B needs to prove to Graph that it's acting on behalf of a specific user, not just as a service. OBO is the mechanism. App B takes the access token it received from App A, sends it to Entra ID's /token endpoint with grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer, and gets back a new access token for Graph — still representing the original user. The user's identity and permissions travel the whole chain.
# On-Behalf-Of flow — App B exchanging App A's token for a Graph token POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token grant_type = urn:ietf:params:oauth:grant-type:jwt-bearer client_id = {App-B-appId} client_secret = {App-B-secret-or-cert-assertion} assertion = {access_token_received_from_App_A} scope = https://graph.microsoft.com/User.Read requested_token_use= on_behalf_of # Entra ID validates: App B is allowed to use OBO, user has consented to the scope # Returns: new access token for Graph, still representing the original user (same oid/sub)

OIDC Discovery — Your Integration Starting Point

Every Entra ID tenant publishes an OIDC discovery document. This is where you get all the endpoints, signing keys, and supported algorithms — instead of hardcoding them:

# Fetch the discovery document for your tenant GET https://login.microsoftonline.com/{tenantId}/v2.0/.well-known/openid-configuration # Key fields in the response: { "issuer": "https://login.microsoftonline.com/{tenantId}/v2.0", "authorization_endpoint": "https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/authorize", "token_endpoint": "https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token", "jwks_uri": "https://login.microsoftonline.com/{tenantId}/discovery/v2.0/keys", "scopes_supported": ["openid","profile","email","offline_access","...], "response_types_supported": ["code","id_token","token id_token","code id_token"], "claims_supported": ["sub","iss","oid","email","name","preferred_username","...] }
Always fetch and cache the JWKS keys from jwks_uri. Microsoft rotates signing keys periodically. If you hardcode a signing key and Microsoft rotates it, your token validation breaks. Use a library that auto-fetches JWKS (MSAL, passport-azure-ad, etc.) or implement periodic refresh with a fallback to re-fetch on validation failure. This is the same pattern for any OIDC IdP — PingFederate, Okta, Entra ID all rotate keys.
CH 05

SAML 2.0
in Entra ID

SAML is alive and well in enterprise IAM — most legacy SaaS apps still use it. Entra ID's SAML implementation is solid, but its attribute mapping model and claims configuration are different enough from PingFederate to warrant a dedicated walkthrough.

How Entra ID SAML SSO Works — The Flow

1
SP-Initiated: User tries to access the SaaS app
User navigates to app.saasvendor.com. The app doesn't have a session. It constructs a SAML AuthnRequest, signs it (if required), and redirects the user to Entra ID's SAML endpoint: https://login.microsoftonline.com/{tenantId}/saml2
2
Entra ID authenticates the user
Entra ID presents the login page (or SSOs silently via PRT/Seamless SSO). MFA is triggered if required by Conditional Access. CA policy evaluation happens here.
3
Entra ID issues the SAML Response
Entra ID builds a signed SAML Response (Assertion) containing: the NameID, configured attribute statements, authentication context class, validity window. The assertion is signed with Entra ID's SAML signing certificate.
4
POST to the ACS URL
The browser POSTs the SAML Response to the app's Assertion Consumer Service URL (ACS URL). The app verifies the signature, validates the assertion, and establishes a session. The user is in.

Claims Mapping — The Critical Nuance

Entra ID SAML claims come from user object attributes by default. Unlike PingFederate where you have an Attribute Contract that you populate from adapters and data stores, Entra ID pulls claim values directly from the user object in the directory. If a required claim value (like employeeId) isn't an attribute on the Entra ID user object, you need to either: (a) sync it from AD/HR via the attribute flow, or (b) use extension attributes (there are 15 available: extensionAttribute1 through extensionAttribute15) or custom directory schema extensions. This is the LDAP-world equivalent of "attributes must be in the directory entry before they can be sent in a SAML assertion."

Claims Transformation — The Limited but Useful Set

Entra ID supports a limited set of claim transformations directly in the UI. For complex transformations, you need a Claims Mapping Policy (JSON-based, applied via PowerShell/Graph API):

  • ExtractMailPrefix() — extract the part before @ in an email
  • Join() — concatenate two attribute values
  • ToLower() / ToUpper() — case conversion
  • RegexReplace() — regex-based value transformation (Claims Mapping Policy only)
  • Constant value — hardcode a claim value (e.g., always send tenant=production)
PingFederate's Attribute Contract mapping is dramatically more powerful than Entra ID's claims UI. In PingFederate you can run JavaScript transformations, chain multiple data sources, do complex conditional mapping. Entra ID's built-in UI handles 80% of real-world cases, but the remaining 20% requires Claims Mapping Policies (JSON config via API) or pushing complex attributes through AD/HR provisioning first. If you're migrating a complex PingFederate SP connection to Entra ID, always inventory the claims transformations first — some will require architectural decisions.

Certificate Rollover — Avoiding Production Outages

Production Incident Pattern: Entra ID SAML signing certificates expire after 3 years by default. When the cert expires, Entra ID stops signing assertions with it, and every SAML SSO to that app breaks — users get cryptographic validation errors. The fix requires updating the public certificate on the SP side (the SaaS vendor). This requires a ticket to the vendor, which may have SLA timelines. Best practice: set a calendar alert 6 months before every SAML cert expiry. Roll the cert in your test environment first. Coordinate with the SaaS vendor for a maintenance window. This is operational discipline PingFederate engineers already have — the same principle applies in Entra ID.
CH 06

RBAC &
Administrative Roles

Entra ID has two separate RBAC systems that are frequently confused: Entra ID Directory Roles (for identity plane operations — managing users, groups, apps) and Azure RBAC (for resource plane operations — managing VMs, storage, networking). They don't inherit from each other. A Global Admin in Entra ID is NOT automatically an Owner of Azure subscriptions.

The Two RBAC Planes

Imagine a company with a corporate HR department and a facilities department. Entra ID Directory Roles are HR permissions — who can hire/fire employees, reset passwords, manage org structure. Azure RBAC is facilities permissions — who can unlock server rooms, provision new hardware, manage the network. The CEO (Global Admin) runs HR, but doesn't automatically get a master key to the server room — that's a separate access grant. This separation is intentional and important for least-privilege architecture.

Security AdministratorManage security-related features: CA policies, Identity Protection, Defender for Identity, Secure Score. Cannot manage users or apps.✅ Scoped
User AdministratorCreate/delete users and groups. Reset passwords (except for admins). Manage licenses. Cannot manage app registrations.✅ Scoped
Application AdministratorCreate/manage all App Registrations and Enterprise Applications. Grant consent. This role can create backdoors via app permissions — treat with care.⚠️ Sensitive
Cloud Application AdministratorSame as Application Admin, but CANNOT manage Application Proxy apps. Slightly reduced scope.⚠️ Sensitive
Authentication AdministratorReset MFA methods and passwords for non-admin users. Can re-register authentication methods. Useful for helpdesk — cannot manage admins.✅ Scoped
Privileged Authentication AdminSame as Auth Admin but CAN reset MFA for admin users. Use only for break-glass scenarios.❌ Sensitive

Privileged Identity Management (PIM) — Just-in-Time Elevation

Without PIM, assigning an admin role is like giving someone a master key and letting them keep it forever. With PIM, it's like checking out the master key from a key cabinet when needed — you have to justify why you need it, it's logged, it expires in a few hours, and a manager can approve or deny the request. If an account with a standing admin role is compromised, the attacker has admin forever. If the same account uses PIM, the attacker gets a regular user account — they'd have to separately compromise the PIM elevation process to get admin.

PIM Role Assignment Types

Active Assignment
User has the role right now, permanently. The old model — still exists in PIM but should be minimized. Break-glass accounts use this by design.
Eligible Assignment
User CAN activate the role but doesn't have it currently. They must activate (with MFA + justification + optional approval) to get the role for a time window.
Time-Bound Assignment
Both active and eligible assignments can have start/end dates. Ideal for contractors: "Security Admin for 3 months, then automatically expires."
Approval Workflow
High-sensitivity roles (Global Admin, Privileged Role Admin) require a designated approver to confirm each activation. Audit trail is automatic.
PIM + CyberArk Pattern (Company A context): Your team uses CyberArk for on-prem privileged access (server sessions, database credentials). The natural extension for cloud: use PIM for Entra ID admin roles and Azure RBAC elevation. The governance model is the same — just-in-time, justification required, time-limited. Consider adding PIM activation events to your SIEM alongside CyberArk session logs. A single pane for all privileged access events — on-prem and cloud — is the IGA dream. Some organizations integrate PIM and CyberArk through Saviynt (also in your stack) as the governance orchestrator.

Administrative Units — Delegated Administration

Administrative Units (AUs) let you scope admin roles to a subset of the directory — like OUs in Active Directory but for cloud roles. An AU groups users/groups and you assign roles scoped to that AU.

Real pattern: Company A divests a business unit but both share the same Entra ID tenant during transition. Create an Administrative Unit for the divested unit's users/groups. Assign a User Administrator scoped to that AU. The divesting team can manage their users without touching the parent company's directory. This is also the model for large multinational orgs: EMEA IT team gets User Admin scoped to the EMEA AU, APAC team scoped to APAC AU, etc. Much cleaner than a single global User Admin for everyone.

Governance

Identity Governance (IGA) is where the long-term compliance story lives. Entra ID's governance suite — Entitlement Management, Access Reviews, Lifecycle Workflows, and PIM — brings native IGA capabilities that used to require a separate product (SailPoint, Saviynt, OIM). This chapter covers all four, with production-grade depth.

The IGA Problem Statement

Identity sprawl is like a hotel that never takes back keycards when guests check out. After a few years, thousands of people have keycards to rooms they no longer need. Some keycards open the penthouse. Nobody knows who has what. An audit is terrifying. IGA is the system that tracks who was given which keycard (access provisioning), periodically asks managers to confirm their team still needs their keycards (access reviews), automatically revokes keycards when someone checks out (lifecycle/leaver), and requires justification for any keycard that opens sensitive areas (entitlement management + PIM). Entra ID Governance is that system for cloud identity.

Entitlement Management — The Access Package Model

Entitlement Management replaces the "email HR and wait" model of access requests. It allows admins to package related access (app assignments + group memberships + SharePoint sites) into an Access Package that users can self-request, with policy-controlled approval and automatic expiry.

Key Concepts

📦
Access Package
A bundle of resources (app assignments, group memberships, SharePoint sites). Users request the whole bundle. E.g., "Onboarding Engineering Package" = GitHub access + Azure DevOps + Jira + on-call group.
🏪
Catalog
Container for access packages. Catalogs can be delegated to resource owners — the network team manages their own catalog, the app team manages theirs. Central IT doesn't bottleneck everything.
📋
Assignment Policy
Who can request (any employee, specific groups, external guests), who must approve, how many approvals, maximum duration (30 days, 1 year, indefinite), expiry and renewal behavior.
⏰
Expiry & Renewal
Access automatically expires after the policy duration. Users get notified. They can request renewal (triggers approval again). No manual intervention — no forgotten permanent access.
M&A Onboarding Scenario: You've acquired 500 engineers from Company B. On Day 1 you create an "Acquired Engineering" Access Package containing: Azure DevOps read access, GitHub organization membership, Slack workspace, and the confluence space for the integration project. You target the package at all @companyB.com guests (auto-assignment policy). All 500 get access within minutes of the package being published. The policy sets 6-month expiry with manager approval for renewal. At the 6-month mark, managers actively confirm continued need — access sprawl prevented by design. When integration completes, you revoke the package and all access disappears atomically.

Access Reviews — Periodic Recertification

Access Reviews are periodic check-ins where resource owners, managers, or users themselves confirm that access is still needed. Entra ID automates the review scheduling, notification, and remediation.

Review TypeWhat's ReviewedWho ReviewsCommon Cadence
Group Membership ReviewUsers in a security or M365 groupGroup owners, managers of members, or the members themselvesQuarterly
Application Assignment ReviewUsers/groups assigned to an enterprise appApp owners or resource ownersQuarterly / Semi-annual

Auto-Remediation on No Response

The most powerful setting: if a reviewer doesn't respond, Entra ID can automatically remove access (deny) or approve access (approve). For sensitive resources and admin roles, always configure auto-deny on no response. This ensures that abandoned reviews result in access removal — not silent approval.

Architect's tip: Make reviewers' decisions defensible. When a manager approves access for a direct report, include the last sign-in date and access package details in the review email. A reviewer staring at "John Smith — IAM Admin Role — Last Sign-In: 147 days ago" is much more likely to remove access than one looking at just a name. Configure the review to include "justification required" for approvals on stale access.

Lifecycle Workflows — Joiner/Mover/Leaver Automation

Lifecycle Workflows automate identity tasks triggered by HR system events. This is the native Entra ID replacement for the custom scripts and runbooks that most organizations have built over the years.

J
Joiner Workflow — Pre-Hire to Day 1
Triggered by: employeeHireDate attribute on the user object (set by HR inbound provisioning). Tasks: Generate TAP (Temporary Access Pass) and email it to the manager. Assign starter access package. Add to onboarding groups. Send welcome email. All automated, triggered by a date field — no manual IT ticket.
M
Mover Workflow — Role Change
Triggered by: department or job title change in HR system (flows via SCIM/AD Connect). Tasks: Add to new department group, remove from old department group. Update access package assignments. Trigger a manager review for any access that doesn't match the new role. No manual revocation needed.
L
Leaver Workflow — Offboarding
Triggered by: employeeLeaveDateTime attribute (set by HR). Tasks: Disable account on last day. Revoke all active sessions (CAE). Remove all group memberships. Remove app assignments. Transfer OneDrive files to manager. Archive mailbox. Optionally delete account after 30-day retention window. All automated — no HR email to IT, no forgotten accounts.
Lifecycle Workflows require Entra ID P2 licensing (included in Microsoft Entra ID Governance license). They also require that your HR system is integrated as the source of truth via inbound provisioning (Workday, SAP SuccessFactors, or any SCIM 2.0 source). If user attributes like employeeHireDate and employeeLeaveDateTime aren't flowing from HR, the workflows can't trigger. This is an infrastructure dependency — not a last-minute configuration. Plan the HR integration first.

🔬 Deep Dive: Saviynt + Entra ID Governance — The Combined Model

Where Native Entra ID Governance Ends

Entra ID Governance is excellent for Microsoft cloud resources. But enterprises with diverse application portfolios (SAP, Oracle, legacy LOB apps, on-prem apps) need a governance layer that spans all systems — not just Azure/M365. This is where products like Saviynt, SailPoint, or OIM integrate.

Saviynt + Entra ID Architecture Pattern

  • Saviynt as the IGA Orchestrator: Saviynt connects to Entra ID via Graph API. It reads users, groups, app assignments, and role assignments. It writes provisioning actions back via Graph API (create users, add to groups, assign app roles).
  • Entra ID Governance as the Native Engine: For Microsoft-native resources (Teams, SharePoint, Azure RBAC), let Entra ID's native Access Reviews and Entitlement Management handle the heavy lifting — they have much deeper integration than any third-party tool.
  • Hybrid Reviews: Run Entra ID native reviews for M365/Azure resources. Run Saviynt reviews for SAP, Oracle, and legacy app access. Consolidate reporting in Saviynt or a SIEM.
  • PIM + Saviynt for Privileged Access: Use PIM for Entra ID/Azure role elevation. Use Saviynt's access request workflow for application-level privileged access (SAP BASIS, Oracle DBA). They operate in parallel — both governed, neither interfering.

The CyberArk Layer

In your stack, CyberArk handles the privileged session management and credential vaulting layer (on-prem servers, databases, network devices). PIM handles the cloud admin role elevation layer. Saviynt handles the application access governance layer. These are three separate concerns — infrastructure privilege, identity platform privilege, and application access governance — that together form a complete privileged access management architecture.
