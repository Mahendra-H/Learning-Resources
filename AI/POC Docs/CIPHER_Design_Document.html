01

Overview

CIPHER replaces the traditional form-and-ticket IAM portal with a conversational AI interface. A user types what they need in plain English — "onboard my app with OIDC", "create a CyberArk safe for my team", "create a Web SSO group in Saviynt" — and the system collects the required parameters, confirms the action, executes it, and returns a complete integration guide. No forms, no tickets, no handoff delays.

The system is built around a multi-agent pattern: a supervisor routes each request to the right specialist agent, which owns the full workflow for its domain. Phase 1 is TypeScript-only, runs entirely on a personal laptop using free local models, and is designed so any single component — LLM provider, mock API, database — can be swapped by changing one environment variable.

AI & Model Strategy

Model-Agnostic Design

No agent, tool, or prompt file ever references a model name or provider directly. All LLM calls route through a single getLLM(capability) gateway function. Swapping the entire AI backend is one environment variable: LLM_PROVIDER=groq. The rest of CIPHER is completely unaware. The same code runs on your laptop with Ollama today and on Claude API in production tomorrow.

Agent Design

Supervisor + Specialist Pattern

One supervisor function classifies user intent and routes to the correct specialist via a plain switch(intent). Each specialist is a plain async TypeScript function owning its full workflow — slot collection, tool calling, result handling. Supervisor is deliberately dumb: routing only. Specialist is smart: domain logic only.

Adding a new domain means adding one new agent function and one new switch case. No framework changes.

Slot Filling — 40 lines, no framework

Each operation has a Zod schema of required fields. The slot collector checks which fields are present in the conversation context and which are missing. For each missing field it asks one question. Once all fields are populated it moves to the confirmation step.

XState v5 state machines are added in Phase 2 when this simple approach shows its limits — not before.

Risk levelConfirmation UXExample operations
ReadNone — execute immediately and stream resultGet connection status, list safes, check group info, request status
Low writeInline chip: "Add John to infra-prod? [Yes] [No]"Add member to safe, add member to group, append redirect URI
High writeFull summary card — all parameters shown — [Confirm] [Edit] [Cancel]Create OIDC connection, create safe, create group, rotate client secret
DestructiveSummary card + user must type the resource name to proceedDelete OIDC client, delete safe, remove safe member
Hard rule: Risk level is declared as static metadata on each tool definition. The LLM never decides whether to confirm. The tool contract decides. This is non-negotiable.

Cross-Domain Requests

When a user requests operations across two domains — "onboard PaymentService with OIDC and create a Saviynt group for it" — the supervisor detects multiple intents and runs them sequentially. First confirmation card, user approves, execute, then second confirmation card. Simple, predictable, no combined card complexity. Parallel execution is a Phase 2 optimisation for read-only cross-domain queries.

Security Model

Hard rule — non-negotiable: No credentials, client secrets, signing certificates, or API keys ever appear in the chat stream. The SSE channel from LLM to browser is not a secure channel. Enforced in system prompt, agent output schemas, and tool definitions.
DataSensitivityIn chat?How it reaches the requester
Metadata URL, Issuer URL, Token Endpoint, Scopes, ACS URLPublic✅ Yes — integration guideFormatted guide card in chat. Downloadable as Markdown.
Client IDSemi-sensitive⚠️ Masked — pf-***-a3f9Partial value in guide. Full value never shown in chat.
Client Secret, Signing Cert, Private KeySecret❌ NeverStored in DB. IAM team notified (mocked in Phase 1) and delivers credentials via your company's secure channel.
IAM team notificationInternal✅ Status onlyChat confirms: "Request REQ-0042 processed. The IAM team has been notified and will share credentials." Email fires to IAM team with full request details.
Authentication (Phase 1)

Simple JWT. Users table in SQLite: id, email, name, passwordHash, role. Login form: email + password. Fastify JWT plugin validates on every request. Max 10–15 users seeded via script. No OIDC integration in Phase 1 — ironic but correct for a POC.

Email Flow (Phase 1 → Production)

Phase 1: email content written to server console — readable, no infrastructure. Phase 2: Mailpit (free Docker container) captures real HTML emails locally. Phase 4: one env var change to real SMTP. The Nodemailer client code never changes — only the transport config.

Deployment Strategy

What GitHub carries

All source code, package.json, pnpm-lock.yaml, docker-compose.yml, Prisma schema, .env.example, and Makefile travel via GitHub. Everything to recreate the environment is in the repo.

Does NOT travel: .env.local (recreate from example), node_modules (install from lockfile), Ollama model files (~12 GB — see USB steps below), SQLite database file.

Switching providers at office

If ollama.com is blocked by corporate firewall, switch to Groq — free, fast, no models needed:

# One command — nothing else changes
cp .env.demo-groq .env.local
pnpm dev

# Free API key at console.groq.com
# llama-3.1-70b runs at 500+ t/s on Groq
Offline model transfer: personal laptop → office laptop via USB
  1. Pull models at home on personal laptop: ollama pull llama3.1:8b && ollama pull phi3:mini
  2. Locate model folder — Windows: C:\Users\YourName\.ollama\models\ · Mac/Linux: ~/.ollama/models/
  3. Copy entire models\ folder to a USB 3.0 drive or external SSD (~12 GB — never use USB 2.0)
  4. Also copy to USB: OllamaSetup.exe, Node 20 installer, Python 3.11 installer, your .env.local
  5. On office laptop: install Ollama, paste the blobs\ and manifests\ folders into its models directory
  6. Verify: run ollama list — all models appear instantly with no internet download
Office laptop pre-flight checklist
  • node --version shows v20.x or higher
  • python --version shows 3.11 or higher
  • ollama list shows all required models (or Groq profile ready)
  • GitHub accessible via HTTPS — run curl https://github.com
  • npm registry accessible — run npm ping
  • .env.local created from .env.example with all required keys
  • Ports 3001, 5173, 9031, 1858, 8080, 11434 are free
  • Docker Desktop installed (or use Ollama native installer — Docker not required)
