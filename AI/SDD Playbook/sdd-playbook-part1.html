01Daily Workflow Ritual

How to start every session correctly.

Every productive SDD session follows the same startup rhythm. Miss it and you'll be re-explaining context, wasting tokens, and getting off-target output. Nail it and Copilot arrives to every session already loaded with everything it needs.

Your 5-Step Session Startup Do This Every Time

01
Select ONE task — and only one
Open your task tracker (GitHub Issues, Jira, your own file). Pick one task for this session. Rule: one task per Copilot session. Mixing tasks splits context and degrades output quality. If you finish early, close the session and open a new one for the next task.
02
Check if a spec exists for this task
Navigate to specs/your-task-name/ in VS Code. Does requirements.md exist and is it filled in? If yes → proceed to Step 3. If no → spec creation is Step 1 of this session before anything else. Never implement without a spec.
⚑ No spec = no implementation. This is not optional.
03
Spend 3 minutes reading your context
Open and skim: .ai/project-context.md (always), .ai/architecture.md (if architecture is involved), and specs/your-task/requirements.md + edge-cases.md. You don't need to memorise them — just refresh them in your own mind so you can catch when Copilot drifts off-target.
04
Identify your position in the prompt chain
Ask yourself: Where am I in the Plan → Spec → Test → Implement → Review → Document chain? Starting fresh? You're at Plan. Continuing from yesterday? Identify the exact step. Open the matching prompt file from .ai/prompts/. Section 3 of this document explains the full chain.
05
Open Copilot Chat with the 3-line Session Opener
Open Copilot Chat in VS Code (Ctrl+Shift+I). Use the Session Opener Format below — three lines only. copilot-instructions.md loads the rest of your project context automatically. You don't need to explain your tech stack, conventions, or architecture — they're already loaded.

The Session Opener Format Use Every Session

This is the most important habit in this entire document. Three lines. Every time. Nothing more.

SESSION OPENER — copy and fill in each time 
Task:     [Feature | Bug | Enhancement | Refactor | Maintenance]
Spec:     specs/[your-feature-folder]/
Scope:    [exact filename(s) in scope for this session]

Real example for adding JWT middleware:

REAL EXAMPLE 
Task:     Feature
Spec:     specs/jwt-middleware/
Scope:    src/middleware/jwt_validator.py (new file to create)
Why only 3 lines?
Your .github/copilot-instructions.md file auto-loads your full project context into every Copilot session. These 3 lines tell Copilot what to do with that context — not what the context is. You've already done that work once, in the setup. Don't repeat it.

Continuing Work from a Previous Session Don't Scroll Back

Starting a fresh session after yesterday's work? Never scroll back through old chat history to re-load context. Old sessions degrade the quality of new ones. Start completely fresh with this format:

CONTINUATION OPENER 
Continuing:  [feature name]
Spec:        specs/[folder]/
Last done:   [what was completed last session]
Current step:[which step of the Plan→Spec→Test→Implement→Review→Document chain]
This session:[exactly what you need from this session]

Token Hygiene — 5 Rules Saves Real Money

1
Reference files by path — never paste their contents
Write "Read .ai/project-context.md" — not the contents of that file. GitHub Copilot reads referenced files automatically. Pasting file contents doubles your token count for zero benefit.
2
One task per session — never mix topics
Mixing a feature request with a bug fix in one session degrades context quality. Each session should have a single clear purpose aligned to one prompt chain step.
3
Keep prompts under 5 sentences for implementation steps
If your implementation prompt is longer than 5 sentences, the task is too large. Break it down. Short prompts with good file references produce sharper output than long prompts with vague descriptions.
4
One prompt chain step per session
Plan in one session. Spec in the next. Test in the next. Never combine Plan and Implement in the same session. Each step's output is the next step's input — they need clean boundaries.
5
Before closing for the day — update your context files
If you added a library, changed a pattern, or made an architecture decision today — update .ai/project-context.md and/or .ai/architecture.md before closing VS Code. A stale context file is worse than no context file.
02Workspace Files Decoded

What each file is, when to open it, and what to put in the prompt.

Your workspace has two layers of intelligence: .ai/ context files (what your project is) and skill files (how to act on it). The prompt templates are the bridge between the two. Know all three and you'll never waste tokens re-explaining context again.

The Golden Rule
Always reference files by path — never paste their content. Write "Read .ai/project-context.md" and Copilot reads it. If you paste the whole file, you're paying double for what the tool already has.

03The Prompt Chaining System

Each prompt has one job. The output of each step feeds the next.

This is the most important structural concept in SDD. Chaining means running one focused prompt, reviewing its output, then using that output as the input for the next prompt. You never combine steps — ever. A combined prompt produces unreviewed, uncontrolled output. A chained sequence produces deterministic, reviewable work.

The 6-Link Chain

Every feature, every bug fix, every enhancement travels through some or all of these six steps in order. The chain is your workflow backbone.

STEP 01
PLAN
01-architect-plan.md
Output: Implementation plan. No code yet.
⚑ YOU REVIEW
→
STEP 02
SPEC
02-spec-writer.md
Output: Full specs/ folder with all spec files.
⚑ YOU REVIEW
→
STEP 03
TEST
03-test-writer.md
Output: Test files. No implementation yet.
⚑ YOU REVIEW
→
STEP 04
IMPLEMENT
04-implementer.md
Output: One scoped implementation unit.
⚑ TESTS PASS
→
STEP 05
REVIEW
06-code + 05-security
Output: Findings by severity. Fix all Critical+High.
⚑ YOU FIX ALL
→
STEP 06
DOCUMENT
08-doc-generator.md
Output: Module docs, ADR (if needed).
⚑ DONE ✓

The Gate Rule — What Keeps SDD Deterministic

Between every two steps is a gate. A gate is you reviewing the previous step's output and deciding it's good enough to proceed. You are the only one who can open a gate.

Non-Negotiable
You do not proceed to the next step until you have reviewed the current step's output. This single discipline is what separates SDD from vibe coding. It takes 2–10 minutes per gate. It saves hours of rework.

What to check at each gate:

After stepCheck this before proceeding
PLANDoes the plan cover all requirements? Does it match your architecture? Are the file boundaries correct? If not — correct the plan now, not later.
SPECIs requirements.md complete? Is edge-cases.md non-empty? Are acceptance criteria specific and testable? Are any security requirements captured?
TESTDo the tests cover all acceptance criteria? Do they cover all edge cases? Are they testing the right thing (not the implementation detail)?
IMPLEMENTDo all tests pass? Is the implementation within declared scope? No unintended side effects? No hardcoded values?
REVIEWAll Critical and High findings fixed? All Medium findings reviewed and accepted or fixed? Code matches coding-standards.md?

Chaining Across Multiple Sessions

A typical medium feature spans 3–5 sessions. Here is how to hand off cleanly between sessions without losing context or repeating work.

S1
Session 1 — Plan
Run 01-architect-plan.md. At the end: "Save this plan to specs/[feature]/implementation-plan.md". Review the plan. Close the session.
S2
Session 2 — Spec
Start with the Continuation Opener. Run 02-spec-writer.md. At the end: "Spec complete at specs/[feature]/. Do not generate implementation yet." Review all spec files. Close.
S3
Session 3 — Test
Start: "Read specs/[feature]/acceptance-tests.md and edge-cases.md. Write test file only. Do not generate implementation." Review tests. Close.
S4
Session 4 — Implement (may span 2–3 sessions for larger features)
Run 04-implementer.md once per scoped unit. Each session: one function, one endpoint, or one service — never more. Check tests pass after each implementation session.
S5
Session 5 — Review + Document
Run 06-code-reviewer.md then 05-security-reviewer.md. Fix findings. Then run 08-doc-generator.md. Write ADR if any architectural decisions were made.
04Breaking Any Task into Copilot-Ready Pieces

If you can't describe it in 3 sentences, it's a project — not a task.

The single biggest source of poor AI output is tasks that are too large. Copilot doesn't fail because it's not capable — it fails because you gave it an underdefined, oversized unit of work. This section teaches you how to size tasks correctly every time.

Step 1 — Identify Your Task Type

Every task you'll ever do maps to one of four workflow types. Identify which type before doing anything else — it determines which scenario in Part 2 to follow.

📋 What kind of work is this?
Something new
≤ 2 days
Small Feature
→ Part 2, Scenario 1
> 2 days
Large Feature
→ Part 2, Scenario 3
Something broken

→ Part 2, Scenario 2
Clean up / restructure

The 3 Decomposition Rules

1
One prompt = one unit of responsibility
One function, OR one API endpoint, OR one test file, OR one data model. Never combine two in one prompt. If you're implementing a service, implement the repository first, then the service layer, then the controller — three separate prompts, three separate reviews.
✓ "Implement the JWT token validation function in src/auth/validator.py"
✗ "Implement the authentication service"
2
Declare the boundary explicitly in every implementation prompt
Start every implementation prompt with two lines: the scope (what to create/change) and the exclusion (what must not be touched). Without these, Copilot will "helpfully" refactor adjacent code you didn't ask it to touch.
Scope: ONLY src/auth/token_validator.py
Do NOT modify: src/auth/__init__.py, src/middleware/*, any test files
3
The 3-sentence rule — if you can't, split it
Try describing the task in 3 sentences. If you can't — the task is too large and must be decomposed further. Each sentence should map to a single reviewable unit of work. If your description has conjunctions like "and then" or "also" — those are split points.
Can't say it in 3 sentences? Split at every "and then" and "also".

The Scope Declaration Format

Copy this format into every implementation prompt. Fill in all three lines. This prevents scope creep — the single biggest source of unreviewed AI output.

Scope: ONLY [exact filename or function name] Do NOT modify: [file1.py], [file2.ts], [any test files] Boundary: [any constraint — e.g. "must not change the public API signature"]

Real example:

Scope: ONLY src/auth/token_validator.py (create this file) Do NOT modify: src/auth/__init__.py, src/middleware/auth.py, tests/ Boundary: Function must accept a raw JWT string and return a validated claims dict or raise AuthenticationError

Too Big vs Just Right — Side by Side

❌ Too Big — Don't Do This
Build the authentication service with:
- JWT validation
- Refresh token rotation  
- Session management
- Audit logging
- Rate limiting
- Multi-factor support
6 responsibilities in one prompt. You'll get 400 lines you can't review. Security holes you won't spot. Tests that don't exist.
✅ Just Right — Do This
Scope: ONLY src/auth/token_validator.py

Read .ai/coding-standards.md
Spec: specs/jwt-middleware/requirements.md
Tests exist at: tests/auth/test_token_validator.py

Implement ONLY the validate_token() function.
Make existing tests pass.
Do NOT create any other files.
One responsibility. 20–40 lines. You can read and understand every line. Tests tell you if it's right.
05How to Think Like an SDD Engineer

Five questions before opening Copilot. Every time.

SDD is as much a thinking discipline as a workflow. The five questions below take 60 seconds to answer. They prevent the most expensive mistakes in AI-assisted development — not after the code is written, but before you write a single prompt.

The 5 Pre-Prompt Questions

1
Do I have a spec for this task?
No spec → Create specs/[feature]/ first. Use 02-spec-writer.md.
2
Do I have an architecture plan reviewed and approved?
No plan → Run 01-architect-plan.md first. Review before proceeding.
3
Do tests exist for what I'm about to implement?
No tests → Run 03-test-writer.md first. Tests define "done".
4
Is my scope defined and small enough to review?
Scope unclear → Write the 3-sentence description. If you can't, split further.
5
Do I know which review prompts to run after implementation?
Not sure → Plan now: code-reviewer.md + security-reviewer.md, minimum.
The 60-Second Habit
Answer these 5 questions before typing the first prompt of every session. If any answer is "no", fix it before proceeding. This single habit eliminates 80% of rework in AI-assisted development.

The Human Governance Model

AI accelerates execution. Humans govern direction. This table is the clearest possible statement of what you own, what AI helps with, and what AI must never be allowed to do.

WhatOwnerReason
Business requirementsHUMANAI doesn't understand business context, stakeholder intent, or regulatory constraints. Only you do.
Architecture decisionsHUMANArchitecture decisions have long-term consequences. AI generates plausible-sounding options — you choose and record the decision in an ADR.
Security rule definitionsHUMANYour organisation's security constraints come from policy and compliance requirements. AI implements them — it doesn't define them.
Production deployment approvalHUMANAlways. No exceptions. AI-generated code never goes to production without human review and explicit approval.
Implementation of defined plansAI ASSISTSOnce spec, plan, and tests exist — AI implementation is excellent and highly effective.
Test generation from specsAI ASSISTSAI converts acceptance criteria into test code efficiently. You review and correct the tests.
Code review suggestionsAI ASSISTSAI review prompts surface issues fast. You decide what to fix, what to accept, and what the severity actually is.
Documentation generationAI ASSISTSAI drafts documentation from code and specs. You review for accuracy.
Define security exceptionsAI NEVERNever ask AI whether it's OK to bypass a security rule. That decision is yours — and your organisation's.
Make deployment decisionsAI NEVERAI has no understanding of your production environment, your users, or the downstream impact of deploying broken code.
06The 7 AI Anti-Patterns

These are the exact ways SDD practitioners relapse. Know them.

Each of these patterns feels faster in the moment. Each one is slower when you count the rework, the debugging, and the security incidents they produce. Every example here is real — you will recognise your own past work in at least two of them.

💣 The Giant Prompt — Trying to implement everything in one shot ANTI-PATTERN #1 ▾
❌ BAD
Build a complete authentication system with JWT validation, refresh token rotation, session management, remember-me functionality, audit logging, and rate limiting. Use our FastAPI stack with PostgreSQL.
✅ GOOD
Task: Feature Spec: specs/jwt-middleware/ Scope: ONLY src/auth/token_validator.py Read .ai/coding-standards.md Implement ONLY the validate_token() function. Tests exist at tests/auth/test_token_validator.py Make those tests pass. Do not create other files.
Why it fails: A giant prompt produces 300–500 lines of output across multiple files. You cannot meaningfully review that output. Security holes hide in the parts you skim. The implementation will drift from your architecture. The tests won't exist. You'll spend more time fixing the output than you saved by combining the prompt.
📭 The Missing Spec — Implementing directly from a verbal description ANTI-PATTERN #2 ▾
❌ BAD
I need a rate limiter for the login endpoint. It should block users after too many failed attempts. Make sure it's secure.
✅ GOOD
Read specs/rate-limiter/requirements.md Read specs/rate-limiter/edge-cases.md Read .ai/security-rules.md Scope: ONLY src/middleware/rate_limiter.py Implement per the spec. Tests at tests/middleware/test_rate_limiter.py
Why it fails: "Too many failed attempts" is undefined. What's the threshold? Per IP? Per account? Per IP+account? What happens to locked accounts? What about distributed attacks? The spec answers all of these before a line is written. Without it, Copilot makes assumptions — and you inherit those assumptions as bugs.
👁️ The Blind Acceptance — Committing AI output without review ANTI-PATTERN #3 ▾
❌ BAD
# Looks good to me ✓ git add src/auth/ git commit -m "add jwt validation" git push origin main
✅ GOOD
# After implementation, BEFORE commit: # 1. Run code review [paste generated file into 06-code-reviewer.md prompt] # 2. Run security review [paste generated file into 05-security-reviewer.md prompt] # 3. Fix Critical + High findings # 4. Run tests: pytest tests/auth/ # 5. THEN commit
Why it fails: AI output is generated, not verified. It may expose stack traces in error responses, log sensitive data, fail open on auth errors, or miss input validation. These are not theoretical risks — they are the most common security bugs in AI-generated code. The review prompts catch them in minutes. Skipping them costs hours in incident response.
🌊 The Scope Creep Prompt — "While you're at it, also..." ANTI-PATTERN #4 ▾
❌ BAD
Implement the token validator. Also while you're at it, refactor the auth middleware to use the new validator, update the session manager to use it too, and add some logging throughout.
✅ GOOD
# Session 1: Scope: ONLY src/auth/token_validator.py Implement validate_token(). Do NOT modify any other file. # Session 2 (after review of Session 1): Scope: ONLY src/middleware/auth_middleware.py Update to use the new TokenValidator class. Do NOT modify token_validator.py or session_manager.py
Why it fails: "While you're at it" turns one reviewable task into three unreviewed ones. Each additional scope item adds multiplicative review complexity. What starts as 30 lines becomes 150 lines touching 4 files — and you've lost the ability to confidently say what changed and why.
🕸️ The Stale Context — Using outdated .ai/ files ANTI-PATTERN #5 ▾
❌ BAD
# project-context.md says: "uses requests library" # (you migrated to httpx 3 weeks ago — forgot to update) # Copilot generates: import requests response = requests.get(url, headers=headers) # ← wrong library, wrong async pattern
✅ GOOD
# After every significant change, update immediately: # .ai/project-context.md → update tech stack section # .ai/architecture.md → update module map if structure changed # .ai/coding-standards.md → update if new pattern adopted # Rule: context file updates are part of # your definition of "done" for any task # that changes tech stack or architecture.
Why it fails: A stale context file is worse than no context file. Copilot will confidently generate code using the wrong libraries, deprecated patterns, or outdated naming conventions — and it won't warn you because as far as it knows, the context is authoritative. Context files degrade silently. Review them monthly, and update them the same day you make any relevant change.
🏗️ The Implement-First Pattern — Skipping Plan and Spec ANTI-PATTERN #6 ▾
❌ BAD
# Direct to implementation with no plan: I need to add centralised error handling to the API. Write the error handler middleware and update all the endpoint files to use it.
✅ GOOD
# Session 1 — Plan ONLY: Task: Enhancement — centralised error handling Read .ai/architecture.md and .ai/project-context.md Produce an implementation plan for centralised error handling: - Which files to create vs modify - What the error response schema will look like - How existing handlers will migrate Do NOT generate any code. Plan only.
Why it fails: Jumping to implementation without a plan means discovering architectural problems in code instead of in a plan. Fixing an architecture mistake in code costs 10× more than fixing it in a plan. The planning prompt takes 5 minutes. Restructuring an incorrect implementation takes hours.
⚡ The Single-Session Monster — Running all 6 chain steps in one session ANTI-PATTERN #7 ▾
❌ BAD
# One massive session: Plan the JWT middleware → write the spec → write the tests → implement it → review it → document it. Do all of this now.
✅ GOOD
# Session 1: Plan only. Review. Close. # Session 2: Spec only. Review all spec files. Close. # Session 3: Tests only. Review tests. Close. # Session 4: Implement one unit. Run tests. Close. # Session 5: Review (code + security). Fix. Close. # Session 6: Document. ADR if needed. Close. # Each session: fresh context, clean output, full review.
Why it fails: As a session grows longer, model quality degrades. Early context gets deprioritised. Errors compound across steps because you never reviewed intermediate output. By the time you get to Review, the implementation has already drifted from the plan, the tests, and the spec — and you can't tell which one is correct.

Run after every implementation session, before git commit
✓
I ran the code review prompt (06-code-reviewer.md) on the generated output
Paste the generated file into the code reviewer. Review all findings.
✓
I ran the security review prompt (05-security-reviewer.md)
Mandatory if the code touches auth, input handling, logging, or data access.
✓
All Critical and High review findings have been fixed
Medium findings: reviewed and either fixed or explicitly accepted. Low: noted.
✓
All existing tests pass — no regressions introduced
Run your test suite. If tests fail → investigate before committing.
✓
.ai/project-context.md is still accurate — no stale info
If this session changed libraries, patterns, or architecture → update it now.
✓
The spec at specs/[task]/ reflects final implementation decisions
If requirements evolved during implementation → update the spec to match.
✓
If architecture was discussed → an ADR has been written in docs/adr/
One ADR per significant decision. Takes 10 minutes. Saves hours of future confusion.
