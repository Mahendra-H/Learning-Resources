MODULE 14 — OPENING BRIEFING

Everything so far learned its own lane. That ends here.

Modules 1 through 13 each went deep on one domain, or a closely related pair, at a time. IAM had its own module. Encryption had its own module. Detection, governance, incident response — each got a clean, isolated block of your attention. That was necessary. You cannot reason about a messy multi-domain incident until you deeply understand each of the pieces first.

But real incidents do not announce which domain they belong to, and neither does the real exam. A single SCS-C03 scenario question routinely touches three services from three different domains in one paragraph, and your job is to find the one fact that actually resolves the question — not the two that are just scenery. That skill has not been tested directly anywhere in this course yet. It is tested here.

Notice how often an exam question names three services but only one of them is actually the point. The other two are there to see if you will chase them. This module is where you build the instinct to tell the difference.

Ahead: six full Case Files, each a realistic multi-domain incident. You will investigate, find findings, uncover root cause, and identify the fix — the same motion, six times, across every combination of domains the exam favors. Then a thread convergence map, a rapid-fire triage drill, and a dense integration exam to close it out.

CASE FILE 01 OF 06

The Leaky Function

Incident CF-01
The Leaky Function
IAM · Domain 4 Data Protection · Domain 5 Detection · Domain 1

03:12 UTC. An automated alert fires from GuardDuty: an unusual volume of GetObject calls against a data-processing S3 bucket, originating from a Lambda execution role that has never touched that bucket before at this volume. On-call pulls the thread. The function is a nightly billing-reconciliation job, six months old, last touched by a departed contractor. Its execution role was scoped, at creation time, with s3:* on arn:aws:s3:::* — a wildcard grant nobody ever revisited, because the job worked and nobody had a reason to look at the role again. Somewhere between the last deploy and tonight, the function was compromised through a vulnerable dependency and used to enumerate and exfiltrate objects from a bucket the reconciliation job was never supposed to touch.

Role created wide, Module 2
→
Function compromised, Module 6
→
Bucket enumerated, read
→
GuardDuty fires, Module 10

At creation, the role was granted broad S3 permissions "to be safe" — a shortcut that skips the least-privilege modeling Module 2 covers. No resource-level scoping, no condition keys, no expectation that the role's blast radius would ever be tested.

A vulnerable third-party library in the function's deployment package (Module 6's workload-hardening territory) gave an attacker remote code execution inside the function's runtime, which meant the attacker inherited the role's live temporary credentials automatically.

With those credentials, the attacker had no need to escalate privilege — the role already had far more S3 reach than the job needed, so a simple ListBuckets plus GetObject loop was enough to find and pull sensitive records.

GuardDuty correctly flagged the anomalous access pattern — but only after objects were already gone. Detection did its job. It just was not the layer that should have carried the weight here.

What would you investigate first?

A. Pull CloudTrail data events for the affected bucket to see the exact API calls made
Efficient. Data events show you precisely what was read, when, and from where — the fastest path to scoping the actual damage before you do anything else.
B. Review the Lambda function's execution role policy in IAM
Valid, but slower as a first move. You will get here eventually to explain the "how," but it does not tell you what was actually taken — start with the data events, then come back to the role.
C. Check GuardDuty finding details for the source IP and geolocation of the calls
Useful supporting context, but attribution rarely changes your immediate containment or scoping decisions — treat this as a parallel thread, not the critical path.
D. Redeploy the Lambda function immediately from a clean artifact
Premature. Redeploying before you have scoped the blast radius risks destroying the evidence you need for the findings and root-cause phases — contain access first, redeploy after.
Findings

CloudTrail data events confirm roughly 40 minutes of sustained GetObject calls against a bucket containing customer billing records, none of which the reconciliation job had ever accessed in its six-month history. The source is the function's own execution role, invoked through a crafted event that triggered the vulnerable dependency's code path.

Root Cause

The execution role was never scoped to least privilege at creation time. A wildcard S3 grant meant that once the function itself was compromised, there was no permission boundary left to stop the attacker from reaching a completely unrelated bucket.

Fix & Prevention

Module 2's least-privilege modeling — resource-scoped policies naming the exact bucket ARN the job needs, nothing wider — would have contained this to a single, harmless bucket the attacker had no use for, regardless of whether the function itself was ever compromised. Prevention at role-creation time is dramatically cheaper than detection after the data is gone: GuardDuty did its job in Module 10, but it is the last line of defense, not the first.

CASE FILE 02 OF 06

The Public Bucket Nobody Noticed

Incident CF-02
The Public Bucket Nobody Noticed
Data Protection · Domain 5 Governance · Domain 6 Infrastructure · Domain 3

A marketing team, migrating assets ahead of a campaign launch, applies a bucket policy meant to make a handful of static images public. A copy-paste error in the policy scope leaves an entire bucket — including an export of customer survey responses someone left there "temporarily" four months earlier — readable by anyone with the URL. Nobody notices for eleven weeks, until a routine external security researcher scan reports it. There was no alert, no automatic block, nothing in the account that would have made this structurally impossible. It was simply possible, and eventually someone found it.

Bucket policy misconfigured
→
Sensitive export left in bucket
→
No org-wide guardrail existed
→
External researcher discovers exposure

The policy statement scoped its Principal: "*" grant to the bucket rather than a specific prefix, a mistake that a stricter review process would likely have caught, but nothing in the account enforced that review.

Macie (Module 8) was never enabled on this bucket specifically — it had been scoped only to the buckets the security team knew about, and this one was created outside that inventory.

No Resource Control Policy existed at the organization level to make public bucket access structurally impossible account-wide, regardless of what any individual bucket policy said (Module 3's RCP mechanism).

An external researcher, not an internal control, is what ultimately surfaced the exposure — the most expensive and reputationally risky way for a company to learn about its own misconfiguration.

What would you investigate first?

A. Immediately apply S3 Block Public Access at the account level
Efficient as an immediate containment step — it stops the bleeding in seconds while the rest of the investigation continues in parallel.
B. Run Macie now against the bucket to classify what was exposed
Valid and necessary, but slower as the very first move — you want access closed before you spend time classifying what was already open.
C. Check CloudTrail data events for GetObject calls from external IPs during the exposure window
Valid, and eventually necessary to scope actual damage, but it does not stop ongoing exposure — pair it with, not instead of, closing the bucket first.
D. Draft the customer notification before confirming what was actually exposed
Premature. Notification decisions should follow, not precede, a factual understanding of scope — acting on assumption here creates its own risk.
Findings

CloudTrail data events show a modest but real number of anonymous GetObject calls against the survey-response export over the eleven-week window, consistent with automated internet-wide scanning rather than a single targeted actor — still a genuine exposure requiring notification review.

Root Cause

Three independent layers all had a chance to prevent this and none of them were in place: Macie was not scoped to this bucket, so it never classified the sensitive content; no RCP existed at the org level to make public access structurally impossible regardless of bucket policy; and no continuous compliance check (Module 12) was watching for public buckets account-wide.

Fix & Prevention

An RCP applied at the organization root, per Module 3, would have made this specific exposure structurally impossible no matter what any individual bucket policy said — the guardrail sits above the mistake, not reliant on any one team getting it right. Module 12's governance guardrails, applied consistently, are the throughline here: prevention through structural constraint beats detection through scanning, every time cost and blast radius are compared.

CASE FILE 03 OF 06

The Instance That Went Quiet, Then Loud

Incident CF-03
The Instance That Went Quiet, Then Loud
Infrastructure · Domain 3 Governance · Domain 6 Incident Response · Domain 2

An EC2 instance running a legacy internal tool has IMDSv1 still enabled, no session-hop protection on its metadata service. An SSRF vulnerability in the tool lets an attacker request the instance's temporary credentials directly through the metadata endpoint — no exploit sophistication required, just a well-known path against a workload that was never hardened. The credentials work. The attacker uses them to enumerate the account, then attempts to assume a role in a second, more sensitive member account in the organization. That attempt fails outright. The attacker's next several attempts also fail. The instance stays compromised, but the damage stops expanding.

IMDSv1 exposed via SSRF
→
Instance credentials stolen
→
Cross-account pivot attempted
→
SCP blocks the pivot

Module 6's workload-hardening guidance calls for enforcing IMDSv2, which requires a session token obtained via a PUT request — something a simple SSRF vulnerability typically cannot replicate. That single setting was never enforced here.

With IMDSv1 reachable, the SSRF flaw let the attacker request the instance role's temporary credentials as plain GET requests, no additional token required.

The attacker's playbook assumed that stolen instance credentials would grant broader organizational reach, a common and often correct assumption — one this account's guardrails happened to defeat.

An SCP on the target account explicitly denied sts:AssumeRole from outside a defined allow-list of trusted principals, per Module 3 — the attacker's credentials were valid, but the destination account structurally refused the assumption.

What would you investigate first?

A. Isolate the compromised instance and revoke its current credentials
Efficient. Cutting off the compromised principal immediately, per Module 11's containment playbook, stops any further use of the stolen credentials while you investigate everything else.
B. Review CloudTrail for the failed AssumeRole attempts to confirm what the SCP actually blocked
Valid and genuinely useful for scoping, but slower as the very first move — isolate the live threat before you spend time confirming what a control already stopped.
C. Audit every SCP in the organization to see if similar gaps exist elsewhere
Important follow-up work, but far too broad for a first move during active containment — this belongs in the post-incident phase, not the opening minutes.
D. Patch the SSRF vulnerability in the application code
Necessary eventually, but the live credential compromise takes priority — a code fix does nothing about credentials already in an attacker's hands right now.
Findings

CloudTrail confirms the stolen instance credentials made several AssumeRole calls against a role ARN in a separate, more sensitive member account, all of which were denied. No successful pivot occurred; the compromise remained confined to the original instance and its immediate blast radius.

Root Cause

Workload hardening failed at the network and metadata-service layer — IMDSv1 being reachable is precisely the kind of defense-in-depth gap Module 6 and Module 5 warn about. That said, defense-in-depth means a failure at one layer should not become a failure of the whole environment, and here it did not.

Fix & Prevention

Enforcing IMDSv2 account-wide (Module 6) would have prevented the credential theft outright and should be the immediate remediation. Just as importantly, this case shows why defense-in-depth (Module 1, Module 5) is the whole point: a hardening failure at the workload layer was caught by a completely different, independent layer — the SCP-based governance guardrail (Module 3) — which is exactly what blast-radius minimization (Module 11's thread) is designed to achieve even when an earlier layer fails.

CASE FILE 04 OF 06

The Vendor Who Was Not Supposed to Have This Access

Incident CF-04
The Vendor Who Was Not Supposed to Have This Access
IAM/Federation · Domain 4 Detection · Domain 1 Incident Response · Domain 2

A third-party monitoring vendor is granted cross-account access through a standard assume-role trust relationship — a common, legitimate pattern from Module 4. The trust policy names the vendor's account as the trusted principal, but omits an external ID condition. Months later, GuardDuty flags an unusual role-assumption pattern: the vendor's role is being assumed from an API pattern that does not match its usual monitoring cadence. Investigation reveals the role ARN was obtained by an unrelated party — a different, unrelated customer of the same vendor — who used it to assume the role directly, impersonating the vendor's own service.

Cross-account trust set up without external ID
→
Role ARN obtained by unrelated party
→
Role assumed by attacker
→
GuardDuty flags the assumption pattern

The trust policy correctly named the vendor's AWS account ID as the trusted principal, per Module 4's cross-account federation pattern, but skipped the external ID condition that binds the trust to a specific customer relationship rather than the account as a whole.

Role ARNs are not secrets by design — they are frequently visible in vendor documentation, support tickets, or shared tooling across the vendor's entire customer base, which is exactly why the external ID exists as a second factor.

Because the trust policy trusted the account without requiring the external ID, any principal inside that account — including a completely different customer's automation — could successfully call sts:AssumeRole against it.

GuardDuty's anomaly detection on role-assumption patterns (Module 10) caught the mismatch between expected and actual usage — this is the classic confused-deputy problem, caught here by behavioral detection rather than by the missing structural control.

What would you investigate first?

A. Immediately update the trust policy to require an external ID and rotate it
Efficient, but slightly ahead of the evidence — you want to confirm the scope of what was accessed under the misassumed role before you change the trust relationship out from under an active investigation.
B. Pull CloudTrail for every action taken under the assumed role during the suspicious sessions
Efficient. This tells you exactly what the unauthorized party did with the access before you decide how aggressively to contain and remediate — the right first move under Module 11's playbook.
C. Contact the vendor to ask whether they recognize the access pattern
Valid as a parallel step, but the vendor cannot tell you what happened inside your own account — your own CloudTrail data is the authoritative source, not their statement.
D. Disable the vendor role entirely without further investigation
A valid containment option, but premature as a first move if it is done without checking what the legitimate vendor integration actually depends on — you risk breaking real monitoring coverage on the same incident you are trying to resolve.
Findings

CloudTrail confirms the unauthorized party's assumed-role sessions were limited to read-only monitoring-scope API calls consistent with the role's designed permission set — no destructive or exfiltration actions occurred, but the trust boundary itself was clearly violated.

Root Cause

This is the confused-deputy problem, textbook: a cross-account trust relationship that authenticated based on account identity alone, with no second factor tying the trust to a specific, unique customer relationship.

Fix & Prevention

An external ID, unique to this specific customer relationship and required as a condition in the trust policy (Module 4), would have made this exact attack path structurally impossible — the unrelated party would have needed a secret they never had, not just an ARN they could see. GuardDuty (Module 10) and the incident response playbook (Module 11) did their jobs well here, but this is a case where the Module 4 control, correctly applied at setup time, removes the need for detection to catch it at all.

CASE FILE 05 OF 06

The Key Policy That Was Too Permissive, Discovered Too Late

Incident CF-05
The Key Policy That Was Too Permissive, Discovered Too Late
Data Protection · Domain 5 Governance · Domain 6

A customer-managed KMS key protects a sensitive analytics dataset. Everyone on the team is confident in the setup — encryption at rest is enabled everywhere, the dashboards are green, and "encryption everywhere" has become the team's shorthand for "we are covered." Nobody has actually re-read the key policy since it was written eight months ago. It turns out the key policy grants kms:Decrypt to a role condition that is broader than intended, a leftover from an early testing phase that was never tightened once the dataset went to production. No breach has occurred. A routine Config conformance pack evaluation, run as part of Module 13's continuous compliance cadence, flags the key policy as non-compliant during a scheduled check — weeks before anyone else would have noticed.

Key policy written broad during testing
→
Encryption assumed to equal protection
→
Config conformance pack evaluates the key
→
Finding surfaces before any breach

Module 7's key-policy modeling calls for the same least-privilege discipline as IAM policies — decrypt permission scoped to exactly the roles that need it — but the testing-phase grant was never revisited once the workload matured.

"Encrypted" answers the question of whether data is unreadable in storage or transit; it says nothing about who is permitted to decrypt it. That second question lives entirely in the key policy and grants, not the encryption algorithm.

A Config conformance pack, evaluated on a recurring schedule per Module 13, checks key policies against an organizational rule set — in this case, a rule requiring decrypt permissions to be scoped to an explicit, reviewed role list.

The finding surfaces during routine compliance review, not during incident response — the best possible timing, since it means the gap is closed before anyone with malicious intent ever has a chance to exploit it.

What would you investigate first?

A. Pull the full key policy and identify exactly which principals currently have decrypt access
Efficient. This is the direct source of truth — you need the exact scope of the finding before deciding what to tighten or who to notify.
B. Check CloudTrail for any Decrypt calls made under the overly broad grant
Valid and important, but slightly secondary — you first want the policy scope itself, then you check whether the excess access was ever actually used.
C. Re-run the entire Config conformance pack against every key in the account
A reasonable follow-up action for broader assurance, but slower as the very first move on this specific finding — resolve the flagged key first, then widen the check.
D. Rotate the KMS key immediately
Not the efficient move here — key rotation changes the underlying key material, but the actual problem is the policy grant, not the key itself. Rotating does not fix an overly permissive policy.
Findings

The key policy's decrypt statement matches a role-name wildcard pattern left over from a testing convention, which resolves to several roles far beyond the analytics team's production access boundary — none of which had actually invoked Decrypt in practice, based on CloudTrail history.

Root Cause

Encryption everywhere, the thread introduced in Module 1 and built out in Module 7, gave the team a false sense of complete coverage. The cryptographic control was sound; the access-control layer governing who could actually decrypt was never tightened once the workload left its testing phase.

Fix & Prevention

Scoping the key policy's decrypt grant to an explicit, minimal role list (Module 7) closes the gap directly. More broadly, this case is the strongest possible illustration of why continuous compliance (Module 13) matters even when nothing has gone wrong yet — a scheduled conformance pack check found what eight months of manual confidence missed, and it found it before a breach, not after one.

CASE FILE 06 OF 06

The DDoS That Became a WAF Bypass Attempt

Incident CF-06
The DDoS That Became a WAF Bypass Attempt
Infrastructure · Domain 3 Incident Response · Domain 2 Detection · Domain 1

A public-facing application behind Shield Advanced and a Regional WAF absorbs a volumetric Layer 3/4 flood attempting to knock the service offline. Shield Advanced's automatic mitigations handle it cleanly — traffic is absorbed, the origin never feels the spike, and on-call barely notices. Twenty minutes after the flood subsides, request patterns shift: instead of raw volume, the traffic becomes a slow, methodical series of crafted requests probing specific WAF rule groups, clearly searching for a gap the ruleset does not cover. The volumetric attack was noise. This second phase is the actual objective — the attacker was testing which defenses would trigger DRT engagement and which rule gaps they could use once the obvious front door was closed to them.

Volumetric flood begins
→
Shield Advanced absorbs it automatically
→
Traffic pattern shifts to WAF probing
→
GuardDuty correlates the two phases as one campaign

Module 5's Shield content covers exactly this profile — a Layer 3/4 volumetric event designed to exhaust bandwidth or connection state rather than exploit application logic.

Shield Advanced's always-on detection and automatic mitigation absorbed the flood without manual intervention, which is precisely the service's design intent for this attack class.

Once the volumetric approach failed to achieve impact, the same source infrastructure pivoted to low-and-slow, application-layer requests deliberately structured to test individual WAF rule groups for coverage gaps.

GuardDuty's extended threat detection (Module 10) correlated the timing and source overlap between the two phases, surfacing them as a single multi-stage campaign rather than two unrelated events — exactly the kind of signal correlation the real exam rewards recognizing.

What would you investigate first?

A. Review WAF logs for the specific rule groups being probed during the second phase
Efficient. This tells you exactly which rule gaps the attacker is testing, letting you close them proactively before any request actually gets through.
B. Engage the Shield Response Team (DRT) even though the volumetric phase is already resolved
Valid and often correct as parallel escalation, but on its own it addresses the phase that already ended — the active probing needs the WAF log review as the immediate next step regardless.
C. Assume the incident is over once the volumetric traffic stops
This is the trap the case file is built around — the volumetric phase ending is not the same as the incident ending, and treating it as resolved is exactly how the second phase goes unnoticed.
D. Add broad rate-limiting rules across the entire WAF without reviewing what is actually being probed
A valid instinct but imprecise as a first move — untargeted rate limiting risks blocking legitimate traffic while still missing the specific rule gap the attacker found, since it does not come from reviewing the actual probe logs.
Findings

WAF logs show a concentrated series of crafted requests targeting a custom rule group that had not been updated since the application's last major release, consistent with a scripted rule-gap scan rather than manual exploration.

Root Cause

The volumetric flood and the WAF probing were not two separate incidents but one multi-stage campaign — the flood was a diversion or a first test of defenses, and the probing was the actual objective once the obvious path failed. Treating the volumetric event as the whole incident would have left the real threat unaddressed.

Fix & Prevention

Updating the stale custom rule group and engaging Shield Advanced's DRT for expert review (Module 5) closes this specific gap. The lasting lesson, per Module 11's incident response process, is treating attack phases as connected rather than resolving each in isolation — GuardDuty's cross-signal correlation (Module 10) is what made the connection visible here, and recognizing multi-stage attacks as a pattern is exactly the reasoning the real exam is testing when a scenario spans two seemingly unrelated events.

This is the encryption-everywhere thread's core lesson (Module 7): encryption protects data at rest and in transit, but the key policy is a completely separate access-control surface that must be scoped independently.
Question 12 of 13 — Detection + Incident Response

GuardDuty raises a finding for unusual cross-account role assumption. Which action sequence best reflects a mature incident response process?

A. Immediately delete the role and close the finding
B. Review CloudTrail for what the assumed role actually did, then contain and remediate the trust relationship
C. Ignore the finding if no data was moved
D. Escalate directly to law enforcement before internal review
Module 11's incident response playbook calls for scoping actual impact via CloudTrail before containment and remediation decisions are finalized — deleting the role first can destroy the evidence trail needed to understand and prevent recurrence.
Question 13 of 13 — All domains synthesis

A scenario mentions GuardDuty, an SCP, and a KMS key policy all in the same paragraph, and asks what the root cause of a data exposure was. What is the best approach to answering?

A. Assume all three services are equally the point of the question
B. Identify which single control's absence or misconfiguration actually enabled the exposure, treating the others as context
C. Pick the answer that mentions the most services
D. Assume the newest AWS service mentioned is always the answer
This is the entire skill this module trains: a dense scenario usually has one control whose absence or misconfiguration is the actual root cause, with the other named services serving as scenery or as controls that worked correctly. Finding that one fact, not listing every service mentioned, is what the real exam rewards.

Engineer · cohortIs it normal for a question to mention a service that turns out to be irrelevant?▸
AnswerYes, very. The exam frequently names a service that behaved correctly, specifically to see whether you will incorrectly blame it. In Case File 3, GuardDuty and the SCP both appear, but only the missing IMDSv2 enforcement is the actual root cause — the SCP was the thing that worked.
Engineer · cohortWhen two answer choices both sound technically correct, how do I pick?▸
AnswerAsk which one is efficient given the stated urgency versus merely valid. Several Case File choices above are both technically reasonable, but only one is the fastest correct path given what the scenario is actually asking for right now — sequencing matters as much as correctness.
Engineer · cohortDo I need to memorize every single AWS security service to pass questions like these?▸
AnswerNo — you need to know what each service's job is, well enough to recognize when a described symptom does not match the service being blamed. That is a much smaller, more durable skill than memorizing every API parameter.
Engineer · cohortWhy does prevention keep winning over detection in these Case Files?▸
AnswerBecause it usually does in real environments too — a structural control like least privilege or an RCP removes the possibility of an incident entirely, while detection only shortens how long it takes to notice one that already happened. Both matter, but the exam consistently rewards recognizing which layer actually prevented the worst outcome.
