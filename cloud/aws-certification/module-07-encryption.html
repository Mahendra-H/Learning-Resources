SCS-C03 · Module 07 · Encryption Foundations
Domain 5 — Data Protection
Domain shift · Infrastructure → Data Protection

The lock changes.

Modules 5 and 6 were about the perimeter and the workload — the network boundary, the edge, the compute layer, the hybrid connections tying it all together. The working assumption underneath all of it was simple: if access control holds and the network controls hold, the data behind them is safe.

This module asks the harder question. What protects the data if every other control somehow fails — if a policy is misconfigured, a network path opens that should not have, a credential leaks? That is what encryption is actually for. It is not a compliance checkbox sitting next to access control. It is the last line, the one that has to hold even when everything upstream of it did not.

We planted encryption everywhere as a bare concept back in Module 1. Here it gets its real mechanical depth: KMS key types, envelope encryption, key policies, grants, rotation, multi-region keys, and encryption in transit between resources. This is the deepest module in the Data Protection domain, and Domain 5 is 18% of the exam — so budget real focus time here.

One habit to build starting now: every time this module introduces a new KMS concept, ask yourself "what happens if this control is misconfigured, and does the rest of the system still catch it?" That question is exactly how the exam frames most of its scenario questions in this domain, and it is also, not coincidentally, how a good security review actually gets conducted in production.

Topic 1 · KMS Key Types

Three keys, one service, very different control.

Every encryption operation in AWS eventually traces back to a KMS key, but not all KMS keys give you the same level of control, and the exam leans on that distinction constantly.

AWS-managed keys are created and administered automatically by an AWS service on your behalf — think the default key behind S3 SSE-KMS if you never specify your own, or the key EBS uses by default. You cannot edit the key policy, you cannot control its rotation schedule, and you cannot share it cross-account. It exists in your account, but the service owns the operational levers.

Customer-managed keys are the ones you create yourself. You own the key policy, you control rotation (automatic or manual), you decide who else in another account can use it, and you control its deletion schedule. Whenever a scenario mentions fine-grained control — a custom key policy, controlled rotation cadence, or cross-account sharing — a customer-managed key is the answer the exam wants.

AWS-owned keys sit a level further away still: they are not even visible in your account. AWS uses them internally for certain service-side encryption where you have no key management responsibility at all — you get the benefit of encryption at rest with zero operational surface.

Separately, KMS keys are either symmetric or asymmetric. Symmetric is the default and the correct choice for the overwhelming majority of encryption use cases — a single key material both encrypts and decrypts, and it is what envelope encryption is built around. Asymmetric keys exist for two specific problems: digital signing and verification, or encrypting data with a public key held by a party who should never receive your private key material. If a scenario does not explicitly need signing or a genuinely external public-key exchange, asymmetric is the wrong answer, however secure it might sound.

There is a cost and operational dimension here too, and the exam expects you to weigh it. AWS-managed keys carry no monthly key fee — you only pay for API usage — which makes them attractive for services where you genuinely have no policy requirements beyond "just encrypt this by default." Customer-managed keys carry a small monthly fee per key in addition to usage charges, which is a real but usually trivial cost next to the control you get: the ability to disable a key immediately if you suspect compromise, schedule its deletion with a mandatory waiting period, and audit every policy change through CloudTrail.

One more distinction worth internalizing: choosing symmetric versus asymmetric is not really about "strength." A symmetric AES-256 key and an asymmetric RSA or ECC key pair are solving fundamentally different problems. Symmetric works because both the encryptor and decryptor can be the same trusted party (you, through KMS). Asymmetric exists specifically for situations where the encryptor and decryptor cannot safely share the same secret — a verifier who only ever needs the public half to check a signature, or an external partner who should be able to encrypt data for you without ever holding your private key. If a scenario does not describe one of those two shapes, symmetric is correct by default, full stop.

Production scenario

A partner integration team needs to encrypt files before dropping them into a shared S3 bucket, and your team needs to decrypt them on the way out — no external party ever holds a public key, and nothing needs to be cryptographically signed. A customer-managed symmetric key is correct. The instinct to reach for asymmetric "because it sounds stronger" is exactly the trap the exam is testing.

Common mistake

Treating "AWS-managed" and "AWS-owned" as interchangeable terms in conversation. They are not. AWS-managed keys are visible in your account under aliases like aws/s3 or aws/ebs — you can see them, view usage in CloudTrail, and reference their ARN. AWS-owned keys never appear in your account at all. Mixing these up on the exam is an easy way to lose an otherwise straightforward question.

Topic 2 · Envelope Encryption

KMS never touches your data.

This is the single most important mechanic in this module, and it explains almost every design decision downstream of it. KMS is deliberately built so that it never has to see, hold, or process your actual bulk data — only a small data key.

Here is the full cycle, step by step. Click each stage below to walk through it.

Two details the exam loves to test: GenerateDataKey returns both a plaintext data key and its KMS-encrypted counterpart in the same response — the plaintext copy is used immediately in memory and then discarded, never written to disk. And only the encrypted data key is ever stored alongside your ciphertext. Decryption simply reverses the process: KMS decrypts the stored encrypted data key using your KMS key, handing back the plaintext data key, which your application then uses locally to decrypt the actual data.

Why bother with this two-layer dance instead of just encrypting everything directly with the KMS key? Two reasons that matter operationally. First, KMS API calls have throughput limits — you cannot run your entire multi-terabyte dataset through KMS directly, but you absolutely can run a 256-bit data key through it. Second, when you rotate the KMS key, you only ever need to re-encrypt the small data keys, not the bulk data itself. That is the entire economic case for envelope encryption in one sentence.

Production scenario

An application team asks why their multi-GB file uploads to S3 with SSE-KMS do not appear to be hitting KMS request quotas the way they expected. The answer: S3 is doing envelope encryption under the hood — one GenerateDataKey call per object (or reused per a bounded window), not one KMS call per byte.

Common mistake

Assuming the plaintext data key is stored anywhere. It never is — it exists only in memory for the duration of the encrypt or decrypt operation. If you ever see plaintext data key material persisted to disk or logs in a design, that is a finding, not a feature.

There is a related API, GenerateDataKeyWithoutPlaintext, that is worth knowing precisely because of what it deliberately omits: it returns only the encrypted data key, never the plaintext copy. This exists for cases where the calling component's job is only to store the encrypted data key for later — a provisioning workflow, for instance — and should never have plaintext key material pass through it at all, even transiently. Recognizing when a design calls for this variant versus the standard GenerateDataKey is a subtle but real exam signal: if the described component never actually performs the encryption itself, it should not be requesting plaintext.

It is also worth being precise about what "envelope encryption" buys you architecturally, beyond throughput. Because the KMS key itself never directly touches your bulk data, you can change how that data is stored, move it between services, or scale storage independently of your KMS design. The KMS key's job stays constant and small: encrypt and decrypt small data keys, all day, regardless of how large or how distributed the underlying dataset becomes. That separation of concerns is what lets services like S3, EBS, and RDS offer KMS-backed encryption at massive scale without KMS becoming a bottleneck.

Topic 3 · Key Policies vs. Grants vs. IAM Policies

This inverts the usual IAM mental model.

Everywhere else in AWS, an IAM policy attached to a principal is sufficient on its own to grant an action. KMS is the exception. A KMS key's key policy is the root-level, resource-based control on that specific key — and even a maximally permissive IAM policy, "Action":"kms:*","Resource":"*","Effect":"Allow", grants nothing if the key policy does not also allow that principal.

In practice, most customer-managed keys ship with the classic "Enable IAM User Permissions" statement in their key policy, which delegates day-to-day authorization down to account-level IAM policies. Once that statement is present, an IAM policy genuinely can extend access — but only because the key policy explicitly opened that door first.

{ "Sid": "Enable IAM User Permissions", "Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::111122223333:root"}, "Action": "kms:*", "Resource": "*" }

With that statement present, an IAM policy attached to a specific role in the account can grant narrower actions like kms:Decrypt — and it will actually take effect, because authority was delegated down from the key policy. Remove that statement, and IAM policies in the account become powerless against the key no matter how permissive they are.

Grants are a third, separate mechanism — narrow, temporary, and created programmatically without ever touching the key policy document. AWS services use grants constantly: an EBS volume needing decrypt access for the lifetime of an attachment, or a Lambda execution needing a scoped, revocable permission. Grants can be issued and retired via API calls, which makes them the right tool when the need is short-lived and auditable at the API-call level rather than the document level.

Authority diagram — three layers, one gate

When you are staring down an access-denied error on a KMS action, evaluate in this exact order: key policy first — does it allow this principal at all, directly or via the IAM-delegation statement? Then IAM policy — is there an explicit allow, and no explicit deny? Then grants — is there a grant covering this specific action for this principal? Skipping straight to IAM policy is the single most common diagnostic mistake engineers make with KMS.

Production scenario

Team B in Account 222233334444 needs to decrypt objects encrypted under a customer-managed key that lives in Account 111122223333. Correct design: the key policy in the owning account must explicitly allow Account 222233334444's principal (or a specific role ARN), and separately, an IAM policy in Account 222233334444 must also allow that role to call kms:Decrypt. Both sides are required — missing either one breaks the flow.

It helps to think of the key policy as answering one question only: "which accounts or principals are even in scope to be considered for this key at all?" Everything an IAM policy does afterward is scoping down within that already-approved set — it can never expand access beyond what the key policy allowed in the first place. This is why security reviews of KMS access should always start at the key policy and work outward, rather than starting from an IAM policy and hoping it is sufficient.

Grants deserve one more distinction: unlike IAM policies, which are evaluated at request time by checking the full policy document, a grant is closer to a pre-authorized token — once created, it is valid until explicitly retired or until it expires, and the calling principal typically must present a grant token (or rely on the grant being visible to KMS) to use it. Because grants can be created without any key policy edit, they are the mechanism of choice for automated, high-frequency, short-lived authorization patterns — exactly the pattern AWS services themselves rely on internally, such as an EBS volume's temporary need to decrypt on attach and nothing more.

Common mistake

Trying to solve a permanent, auditable access requirement with a grant because it feels faster than editing a key policy. Grants are harder to inventory at a glance than a key policy document, and using one for a long-lived, business-critical access path makes that access path invisible to anyone reviewing the key policy alone. Permanent needs belong in the policy; temporary, programmatic needs belong in a grant.

Topic 4 · Key Rotation

Rotation is not re-encryption.

AWS-managed keys rotate automatically every year, no configuration required. Customer-managed symmetric keys can opt into the same automatic annual rotation. Here is what actually happens on rotation: new key material is generated, the key's ARN and key ID stay exactly the same, and the old key material is retained internally so anything encrypted under it remains decryptable indefinitely.

That last part is the piece the exam tests hardest. Rotation only changes which key material is used for new encryption operations going forward. It does not reach back and re-encrypt every object that was already encrypted under the previous key material — that data stays exactly as it was, and KMS silently tracks which version decrypts it.

Asymmetric keys do not support this kind of automatic rotation the same way, because a public/private key pair cannot be silently swapped without breaking any external party who has already been handed the public key. Rotating an asymmetric key is a manual, coordinated operation — you create a new key pair, redistribute the new public key to every consumer, and only then deprecate the old pair.

Common mistake

An application team assumes that after rotation, they need to re-encrypt every previously stored object under the new key material "to stay current." They do not — the retained old material keeps decrypting exactly what it always did. Re-encryption is only needed if you are deliberately migrating data to a different key entirely, which is an application-level operation, not something rotation does for you.

Production scenario

A team pins a specific KMS key version in application config rather than referencing the key by ARN, expecting rotation to leave that version untouched. This is unnecessary and fragile — the key ARN/ID is stable across rotation, and KMS internally tracks which key material decrypts which ciphertext. Reference the key by ARN and let rotation happen transparently.

There is a compliance angle here too that shows up frequently in scenario questions. Some regulatory frameworks require evidence that key material rotates on a schedule, but do not necessarily require the underlying data to be re-encrypted on that same schedule. Automatic annual rotation for a customer-managed symmetric key satisfies the rotation requirement on its own — you are not additionally on the hook to re-encrypt your entire dataset just to stay compliant, because the control being audited is "does key material rotate," not "is every byte of stored data re-wrapped every year."

If a genuine business requirement does call for re-encrypting existing data under entirely new key material — for example, moving data to a brand-new customer-managed key after a suspected compromise of the old one — that is a deliberate, application-level migration: decrypt with the old key, encrypt with the new one, and update what is stored. That is a fundamentally different operation from rotation, even though the two get confused constantly in casual conversation and in distractor answers on the exam.

Topic 5 · Multi-Region Keys

Related keys. Not one key, live-synced.

A multi-region key is a set of KMS keys in different regions that share the same key material and a common key ID prefix. That shared material is what lets you encrypt data in one region and decrypt it in another — the core use case for disaster recovery and global applications that need to move encrypted data across regions without a round trip to a single home region.

What it is not: a single key object replicated with live, automatic synchronization the way a database might replicate rows. Each regional key in the set is independently manageable — you can disable one region's replica, delete it, or manage its key policy separately from the others, and none of that automatically propagates. They started as clones of the same material; they are not wired together afterward.

Multi-region key relationship

The exam will describe a scenario where someone assumes updating the key policy in the primary region instantly applies everywhere. It does not. If you need consistent access control across every regional replica, you update each one — or you build automation to do it, because AWS will not do it for you.

Multi-region keys are the right answer when you genuinely need cross-region encrypt/decrypt continuity — DR failover, or a globally distributed application reading and writing the same encrypted data from multiple regions. Independent, per-region keys are more appropriate when the requirement is the opposite: tight regional isolation, such as data-residency rules that require a region's data to never be decryptable using material tied to any other region.

Production scenario

A financial services workload must guarantee that EU customer data can never be decrypted using key material that also exists outside the EU, even as a backup. Multi-region keys are the wrong fit here — independent regional keys, scoped and never replicated, satisfy the residency requirement.

A useful mental test for exam scenarios: ask whether the requirement is about continuity or about isolation. Disaster recovery, active-active global applications, and any workflow where "encrypt here, decrypt there" needs to just work without a cross-region KMS call are continuity requirements — multi-region keys fit. Data residency, regulatory data sovereignty, and "this data must never be decryptable outside this boundary" are isolation requirements — independent per-region keys fit, precisely because they guarantee no shared material exists to leak across the boundary in the first place.

Also worth knowing operationally: you designate one replica as the primary when you first create a multi-region key, and every other replica is created from it. You can later promote a replica to become the new primary if needed, but this is a deliberate administrative action, not something that happens automatically during a regional failure — DR runbooks that assume automatic primary failover for multi-region keys are describing something AWS does not do on its own.

Topic 6 · Encryption In Transit — Inter-Resource

The wire needs protecting too.

Everything so far protected data at rest. Data moving between an application and its data store — or between any two AWS resources — needs its own guarantee, and that guarantee is TLS enforcement, not KMS.

The exam-relevant mechanic ties directly back to Module 2's condition-key content: a resource policy can require aws:SecureTransport to be true, denying any request that arrives over plain HTTP rather than HTTPS. This is how you enforce, at the policy layer, that no client — internal or external — can talk to an S3 bucket, an API, or another resource without TLS in place, regardless of what the client itself is configured to do.

{ "Effect": "Deny", "Principal": "*", "Action": "s3:*", "Resource": "arn:aws:s3:::example-bucket/*", "Condition": {"Bool": {"aws:SecureTransport": "false"}} }

Notice this is enforced independently of encryption at rest. A bucket can have SSE-KMS at rest and still allow unencrypted transit unless this condition is explicitly in place — the two protections are separate controls that both need to be deliberately configured.

Production scenario

A security review finds that an internal service-to-service call between an application tier and its database is unencrypted in transit, even though the database's storage volume is encrypted at rest. The fix is a resource or connection-level TLS requirement — encryption at rest never covered the network hop, and it was never meant to.

This ties back directly to Module 2's condition-key material because the mechanism is identical — a policy condition evaluated against the request context, not a KMS concept at all. That is a distinction worth holding onto for the exam: encryption at rest is a KMS and service-configuration problem, while encryption in transit enforcement is an IAM/resource-policy condition problem. A question describing "data must always be encrypted end to end" is usually testing whether you reach for both controls together, rather than assuming one implies the other.

The same aws:SecureTransport condition pattern applies well beyond S3 — it shows up on SQS queue policies, SNS topic policies, and API Gateway resource policies wherever a service supports condition-based resource policies. Wherever you see a requirement that a resource must reject any non-TLS request outright, this is the condition key to reach for, regardless of which specific service is in front of you.

It is worth being precise about what this Deny statement actually blocks versus what it does not. It blocks the request outright at the resource-policy layer before the operation is ever evaluated further — the caller gets an access-denied response, full stop, regardless of what their IAM policy allows. It does nothing to inspect or validate the TLS version or cipher suite in use, only whether the underlying transport was HTTPS at all. If a scenario requires enforcing a minimum TLS version specifically, that is a separate control, typically configured at the load balancer or API Gateway layer, not something this condition key expresses on its own.

Choosing the right key type

Default to a customer-managed key whenever the scenario mentions any of: a custom key policy, cross-account access, controlled rotation timing, or the ability to disable/delete the key on your own schedule. Reach for AWS-managed only when the scenario explicitly says "default encryption, no special requirements." AWS-owned keys are almost never something you configure — they show up as background infrastructure inside certain AWS services.
