Scene 01 • Security Groups vs. NACLs

The Two Gatekeepers — and Why Both Exist

Every time a packet tries to reach an EC2 instance inside a VPC, it passes through exactly two network-layer filters: a Network Access Control List (NACL) at the subnet boundary, and a Security Group at the instance's Elastic Network Interface (ENI). They are not alternatives — they are complementary. Understanding the mechanical differences between them is the single most tested concept in this module, and arguably one of the most tested concepts across the entire SCS-C03 exam.

Security Group

Stateful · ENI-level · Allow only

  • Attached to an instance's ENI (or RDS, ELB, etc.)
  • Stateful: return traffic is automatically allowed — if inbound is permitted, the corresponding outbound response flows freely
  • Only allow rules exist — you cannot write a deny rule
  • All rules evaluated together as a union (most permissive wins across attached groups)
  • Default: deny all inbound, allow all outbound
NACL

Stateless · Subnet-level · Allow + Deny

  • Attached to a subnet — applies to all traffic crossing the subnet boundary
  • Stateless: return traffic is a separate, independent packet — must be explicitly allowed by an outbound rule
  • Supports both allow AND deny rules
  • Rules evaluated in numbered order — first match wins, processing stops
  • Default (AWS-created): allow all in both directions. Custom default: deny all

NACL — Subnet Boundary (Stateless)

The inbound packet hits the NACL first. AWS evaluates rules in ascending rule number order and stops at the first match. If rule 100 allows TCP 443 from 0.0.0.0/0, the packet passes. If rule 90 explicitly denies 203.0.113.0/24, traffic from that range is dropped before it ever reaches the security group. This is the only place in the VPC stack where you can write an explicit deny. The NACL has no memory of this transaction — when the response travels back outbound, it will be checked against outbound rules as if it's a brand-new packet.

Security Group — ENI Boundary (Stateful)

The packet next reaches the security group attached to the instance's ENI. AWS evaluates all attached security group rules together — there is no rule ordering, and the most permissive match wins. Crucially, there are only allow rules here. The SG tracks connection state: once it allows an inbound connection, it records that fact, and the corresponding return traffic is automatically allowed outbound without needing a separate outbound rule.

Return Trip — The Stateful vs. Stateless Difference

The response packet leaving the instance travels in reverse order: Security Group outbound → NACL outbound. The SG has already tracked the session state, so the outbound response flows automatically — no explicit outbound rule needed. The NACL, however, is completely stateless. It treats the response as a fresh packet and checks it against outbound rules. If your NACL allows inbound TCP 443 but has no outbound rule for the ephemeral port range (typically 1024–65535, the client's source port), the response will be silently dropped. This is the most common NACL misconfiguration on the exam.

Here is the question the exam loves to embed: "The security team wants to ensure that no traffic from IP range 192.0.2.0/24 can ever reach instances in the private subnet, even if a misconfigured security group accidentally allows it." The answer is always a NACL deny rule — because security groups structurally cannot deny anything. The inability to write deny rules in security groups is not a bug; it is a deliberate design. But it means NACLs are the correct tool when you need a hard, irrevocable subnet-level block.

Production Scenario — Blocking a Known-Bad IP Range

Your SIEM detects that a botnet operating from the CIDR block 185.220.0.0/16 is probing your public subnet on port 22. You need to stop this at the network layer immediately, without modifying every instance's security group. The correct action: add an inbound NACL DENY rule for 185.220.0.0/16 with a rule number lower than your existing allow rules (e.g., rule 50 DENY before rule 100 ALLOW). This blocks all traffic from that range at the subnet boundary, across every instance in the subnet, instantly — regardless of any security group configuration. No security group modification needed, and no security group could have achieved the same result anyway.

Scene 02 • AWS WAF

Application-Layer Defense — What Packets Cannot Tell You

NACL / Security Group sees
📦
Source IP · Destination port · Protocol (TCP/UDP)
Cannot read payload content
WAF sees
🔍
URI path · Query strings · Headers · Request body
Can detect SQL injection, XSS, SSRF patterns

AWS WAF (Web Application Firewall) operates at Layer 7 — the application layer. Unlike security groups and NACLs, which examine IP addresses and ports, WAF can read the actual content of HTTP requests: headers, URI paths, query strings, request bodies, and even decoded payloads after WAF unwraps things like base64 encoding. This visibility is what makes WAF the right tool for web-application threats, and it explains why the network layer controls cannot be extended to handle them — a NACL simply has no concept of "this URL contains a SQL injection string."

Core Architecture: Web ACLs and Rules

Web ACL

The top-level container. A Web ACL contains an ordered list of rules and rule groups. Requests are evaluated against each rule in order; the first rule that matches determines the action (Allow, Block, Count, or CAPTCHA). A Web ACL is scoped to a specific AWS resource: CloudFront, ALB, API Gateway, or AppSync.

Rules & Rule Groups

A rule is a single match statement + action. A rule group is a reusable collection of rules. AWS Managed Rule Groups (e.g., AWSManagedRulesCommonRuleSet, AWSManagedRulesSQLiRuleSet) are maintained by AWS and cover OWASP Top 10 patterns. Customer-defined groups let you write your own matching logic.

Rate-Based Rules

Block or flag IPs that send more than a defined number of requests in a 5-minute window. Essential for throttling brute-force login attempts, credential-stuffing attacks, and scrapers. Can be combined with geographic conditions: "block IPs from this country that also exceed 1,000 req/5 min."

Geographic Match Rules

Allow or block requests based on the country of origin of the requesting IP. Useful for services that are legally or commercially restricted to specific geographies. WAF uses IP geolocation data maintained by Amazon — you do not need to manage your own geolocation database.

The exam sometimes offers "add a WAF rule to block traffic from the malicious IP range" as an answer option. This is a plausible-looking trap. WAF is not the right tool for pure IP-range blocking — that is a NACL job, and it operates at Layer 3/4 before WAF even sees the traffic. WAF is the right tool when the threat is defined by application-layer content: a malicious query string, a particular user-agent string, or a request body that looks like a SQL injection. Use NACLs for CIDRs; use WAF for what packets say.

Production Scenario — WAF Rule Blocks Legitimate Traffic at Launch

Your team enabled the AWSManagedRulesCommonRuleSet on your ALB WAF Web ACL and deployed to production on launch day. Within minutes, your customer support team reported that the account registration form was returning 403 errors for legitimate users. The culprit: the managed rule group was blocking requests where the form body exceeded the default size limit, triggering the SizeRestrictions_BODY rule. The fix: switch the rule action from Block to Count mode first — this lets you observe the rate of matches in CloudWatch without enforcing — then adjust the size constraint override or move that specific rule to a custom exclusion before switching back to Block. Never enable a managed rule group directly in Block mode on a production endpoint without a Count-mode observation period first.

Key takeaway: WAF is the right tool when the threat lives in the HTTP payload — injection patterns, oversized bodies, suspicious query strings, rate abuse — not when the threat is a raw IP address or a volumetric flood, which belong to NACL and Shield respectively.
Scene 03 • AWS Shield & Shield Advanced

DDoS Protection — Layers, Cost, and When Standard Fails

Layer 3/4 only · Automatic · No DRT · No L7 protection
Shield Advanced
$3k/mo
L3 + L4 + L7 · DRT 24/7 · Cost protection · WAF integration

Distributed Denial of Service (DDoS) attacks attempt to overwhelm your infrastructure with traffic volume, making it unavailable to legitimate users. AWS provides two tiers of DDoS protection that operate at different layers and with fundamentally different capabilities. Knowing when to recommend Shield Advanced versus Standard is a predictable exam scenario.

Shield Standard

Automatic and Free

  • Automatically enabled for all AWS customers — zero configuration
  • Protects against Layer 3 (network) and Layer 4 (transport) attacks
  • Covers: UDP floods, SYN floods, reflection attacks
  • No DDoS Response Team access
  • No Layer 7 protection
  • No cost protection against scaling charges during an attack
Shield Advanced

Paid — $3,000/month org-wide

  • Enables at the AWS account level, covers all supported resources
  • Layer 3 + Layer 4 + Layer 7 application-layer protection
  • Integrates with WAF — during an active attack, the DRT can automatically deploy WAF rules
  • DDoS Response Team (DRT) available 24/7 for attack response
  • Cost protection — AWS credits usage spikes caused by an attack
  • Near-real-time visibility in the Shield console, attack metrics, forensics

When the Exam Expects Shield Advanced

Any scenario describing a business-critical, internet-facing application that must remain available during a DDoS attack and requires 24/7 expert response or Layer 7 protection is a Shield Advanced scenario. If the question mentions cost protection, the DRT, or WAF integration during an active attack, the answer is Shield Advanced. Standard is the correct answer only when the question describes basic Layer 3/4 protection needs on a non-critical workload, or when "no additional cost" is an explicit constraint.

Key takeaway: Shield Standard is always on and covers Layer 3/4 for free — but if your application is internet-facing, business-critical, and could face a Layer 7 HTTP flood, the $3,000/month cost of Shield Advanced is justified specifically because Standard is completely blind to application-layer attacks.

Scene 04 • CloudFront Security & Edge

Terminating TLS at the Edge — and What That Changes

Amazon CloudFront is a global Content Delivery Network (CDN), but for security engineers, it is first and foremost an edge proxy — a service that intercepts all incoming requests, terminates HTTPS connections at the nearest AWS edge location, and forwards them to your origin over a separate, private connection. This architecture has profound security implications: attackers never connect directly to your origin. CloudFront absorbs the initial TLS handshake cost, applies WAF rules, and only forwards legitimate requests. Your origin S3 bucket or ALB can be locked down to accept traffic from CloudFront only.

Origin Access Control (OAC)

OAC is the modern replacement for the older Origin Access Identity (OAI). It restricts an S3 bucket to only accept requests that come from your specific CloudFront distribution, signed by CloudFront using AWS SigV4. The S3 bucket policy grants access only to the CloudFront service principal with the distribution's ARN. Direct S3 URL access is denied — the bucket is not publicly accessible.

Security Headers at the Edge

CloudFront response headers policies let you attach HTTP security headers — HSTS (Strict-Transport-Security), Content-Security-Policy, X-Frame-Options, X-Content-Type-Options — to every response at the edge, without modifying your origin application. This is the lowest-effort path to a consistent security header posture across a multi-origin architecture.

TLS Termination and Threat Model

When TLS is terminated at the CloudFront edge, two distinct trust zones emerge: the public internet to the edge point (untrusted, TLS-encrypted), and the edge to your origin (private AWS backbone, separately encrypted). Your origin no longer needs to be exposed to the public internet. Your WAF rules see the decrypted application payload, which enables much richer inspection than at a point before TLS termination.

Geo-Restriction

CloudFront's built-in geo-restriction (an allowlist or blocklist of countries) blocks requests before they reach your origin. Unlike WAF geographic match rules, CloudFront geo-restriction applies to the entire distribution and cannot be combined with other match conditions within the same rule. For more granular geo-based logic, WAF geographic match rules are the better tool.

Production Scenario — Securing an S3 Static Site

Your team is building a static site served from S3 via CloudFront. Without OAC, a user who discovers the S3 bucket name can bypass CloudFront entirely — including your WAF rules and geo-restrictions — by accessing the S3 website URL directly. The correct architecture: make the S3 bucket private (no public ACLs, no website hosting endpoint), configure OAC on the CloudFront distribution, update the S3 bucket policy to allow only cloudfront.amazonaws.com with the distribution ARN condition. Now the only path to content is through CloudFront, and all your edge security controls apply to every request.

🎯 Exam Angle

CloudFront exam questions tend to come in two flavours: (1) "How do you prevent direct S3 access bypassing CloudFront?" — answer is OAC + private bucket, not bucket policy alone; and (2) "Which is correct for whole-distribution country blocking vs. path-specific geo rules?" — CloudFront geo-restriction for whole-distribution simplicity, WAF geographic match for any condition that combines geography with another attribute. OAI appearing as an answer option is a strong signal it is the wrong answer — OAC is current best practice.

Key takeaway: CloudFront + OAC is not just a CDN pattern — it is an access-control architecture: the origin becomes unreachable directly, all traffic flows through the edge where WAF, geo-restriction, and TLS policy apply, and attackers can never bypass your edge controls by probing the origin URL.
Scene 05 • AWS Network Firewall

Deep Packet Inspection Inside Your VPC

AWS Network Firewall is a managed, stateful, Layer 3–7 firewall service deployed inside your VPC. It provides capabilities that security groups and NACLs fundamentally cannot: domain-name filtering (block all traffic to *.malicious-domain.com), intrusion prevention signatures (detect known exploit patterns in traffic flows), and protocol anomaly detection. Network Firewall is the answer when the question describes traffic inspection needs that go beyond what IP/port-based rules can achieve.

Stateful Rule Groups

Inspect traffic as part of a connection — can match on multi-packet context. Supports Suricata-compatible IPS rules for signature-based detection. Domain list rules (block all HTTP/HTTPS to a list of domain names) are a common SCS-C03 pattern.

Stateless Rule Groups

Fast-path packet evaluation — IP, port, protocol matching (similar to NACLs but more flexible). Used to pass, drop, or forward to stateful engine. Evaluated first, in rule number order.

Deployment Architecture

Network Firewall is deployed in a dedicated firewall subnet within your VPC. Traffic is routed to it via VPC route tables — typically in a centralized inspection VPC in a hub-and-spoke architecture, using Transit Gateway to route traffic from spoke VPCs through the central inspection point.

When to Use vs. SG/NACL

Use SG and NACL for standard port/IP access control — they are lightweight and always on. Add Network Firewall when the requirement mentions domain filtering, IPS signatures, TLS inspection, or centralized network inspection across multiple VPCs or accounts.

Production Scenario — Blocking Exfiltration to C2 Domains

GuardDuty alerts you that an EC2 instance is communicating with a known command-and-control domain. You need to block all outbound DNS queries and HTTP/HTTPS connections to that domain class across your entire VPC fleet. NACLs cannot filter by domain name — they only understand IP addresses, and C2 operators rotate IPs rapidly. Network Firewall's domain list rule can block *.known-bad-c2.com regardless of the underlying IP, and the stateful engine can detect and block the HTTPS handshake to that domain even if the IP changes. Route 53 Resolver DNS Firewall would handle the DNS query layer; Network Firewall handles the connection layer — together they form a complete defense.

Key takeaway: Reach for Network Firewall when the requirement says "domain filtering," "IPS signatures," "centralized inspection," or "east-west traffic" — the moment a threat needs to be identified by what a connection says rather than just who it comes from, SG and NACL have reached their limits.
Scene 06 • Route 53 Resolver DNS Firewall

Stop the Query Before the Connection

❌ Without DNS Firewall
EC2 resolves c2-evil.net
→ Gets IP: 198.51.100.42
→ Opens TCP connection
→ Malware callbacks succeed
Network FW must know the IP
✅ With DNS Firewall
EC2 resolves c2-evil.net
→ DNS Firewall: BLOCK → NXDOMAIN
→ No IP returned
→ Connection never attempted
Stops threat before it starts

Route 53 Resolver DNS Firewall filters DNS queries made by resources inside your VPC — before any network connection is established. When an EC2 instance tries to resolve a known-malicious domain, DNS Firewall intercepts the query at the resolver layer, checks it against your domain block lists, and returns either NXDOMAIN (domain does not exist) or a custom response. The connection attempt never happens — there is no IP to block because no IP was ever returned.

Domain Lists

You maintain rule groups containing domain lists. AWS provides AWS-managed domain lists: AmazonRoute53ResolverDNSFirewall-MalwareDomainList and AmazonRoute53ResolverDNSFirewall-BotnetDomainList — updated automatically by Amazon threat intelligence. You can supplement with your own lists.

Rule Actions

BLOCK returns NXDOMAIN or a custom response. ALERT logs the query but allows resolution (good for detecting before enforcing). ALLOW can override a block list for trusted exceptions. Rules are evaluated in priority order.

Fail-Open vs. Fail-Closed

If DNS Firewall cannot evaluate a query (service disruption), the VPC-level setting controls behavior: fail-open allows the query through (availability priority), fail-closed blocks it (security priority). The exam will ask you to reason about this trade-off for critical security workloads.

VPC Association

A DNS Firewall rule group is associated with one or more VPCs. All DNS queries from resources in those VPCs pass through the firewall. This is centrally manageable through AWS Firewall Manager for multi-VPC and multi-account deployments.

A very common exam misconception: "If I already have AWS Network Firewall, do I also need DNS Firewall?" The answer is yes, and the distinction matters. Network Firewall sees traffic after DNS resolution — it can block a connection to a malicious IP or domain at the network layer. But if you have blocked the domain at the network layer and an attacker rotates to a new IP, your Network Firewall domain list may need updating. DNS Firewall blocks the query itself — no resolution means no IP means no connection attempt, regardless of what IP the domain points to. The two controls operate at different moments in the kill chain and are genuinely complementary, not redundant.

🎯 Exam Angle

DNS Firewall exam questions typically present a compromised EC2 instance making callbacks to a malicious domain and ask which control stops the communication. The answer will be DNS Firewall when the question emphasises stopping at the DNS resolution stage, or Network Firewall when it emphasises blocking the established connection. The "fail-open vs. fail-closed" trade-off is a direct exam target: the question will describe a security-critical workload and ask which setting prioritises security over availability — the answer is fail-closed. If availability is the stated priority, fail-open.

Key takeaway: DNS Firewall is the outermost possible interception point for domain-based threats — it stops the threat before a connection exists, before an IP is exchanged, before Network Firewall even has a packet to inspect. Use it for known-bad domains; pair it with Network Firewall for connection-layer enforcement of the same policy.

The SCS-C03 exam does not require memorising every OWASP category — but it does test which AWS service is the correct mitigation for each threat class. WAF handles application-payload categories; other categories belong to IAM, Config, ACM, or the application itself. Study which categories are not WAF scenarios just as carefully as the ones that are.

The exam uses "AWS WAF" as a distractor for threats it cannot actually fix. Broken access control (A01) is the world's most common web vulnerability — and it is entirely an application logic and IAM problem. WAF has zero visibility into whether a user is authorised to access a specific business object. A WAF rule cannot tell you "this authenticated user is trying to view someone else's account." If a question says "fix broken access control," the correct answers live in IAM least-privilege policies, resource-based policies, and application-layer authorisation — never WAF alone. Memorise that boundary: WAF stops malicious request content; it has no concept of request entitlement.

Key takeaway: WAF is the right answer for OWASP injection, SSRF, and authentication rate-abuse categories — and the wrong answer for broken access control, cryptographic failures, and security misconfiguration, which belong to IAM, ACM, and AWS Config respectively.
Scene 08 • Defense-in-Depth

The Layered Edge Stack — Every Control Has a Job

Defense-in-depth means that no single control is trusted to stop every threat. Each layer handles the attacks its position and capabilities are suited for, and passes the remainder to the next layer inward. A request from the internet to your EC2 instance can pass through up to five distinct inspection points before it reaches your application code. Key takeaway: Each layer defends only what it can see — DNS Firewall sees domains, Shield sees volumes, WAF sees HTTP content, Network Firewall sees network flows, and SG/NACL sees ports and IPs. The exam will present a threat and ask which control stops it; match the threat's observable characteristics to the layer that can observe them.

✅ Custom Rule — String Match or Regex Statement

Write a WAF rule with a ByteMatchStatement (exact string match in headers, URI, query string, or body) or a RegexMatchStatement (regex pattern). Combine multiple conditions with AND/OR/NOT logic. Use label matching to chain rules.

Exam tip: Custom rules are the right answer when the threat pattern is unique to your application (e.g., block any request where a header contains your internal API key format).

✅ Rate-Based Rule

Configure a Rate-Based Rule with a threshold (requests per 5-minute window) and an aggregation key (source IP is most common; you can also aggregate on a header value like X-Forwarded-For). Requests exceeding the threshold trigger the rule action (Block or CAPTCHA).

Combine with: A scope-down statement to apply the rate limit only to a specific path (e.g., /login) rather than all requests. This prevents legitimate high-volume API traffic from hitting the login rate limit.

✅ Geographic Match Rule

Use a GeoMatchStatement to allow or block requests based on country code. WAF uses Amazon IP geolocation data. For allowlists, combine with a NOT statement: block all requests where country is NOT in your approved list.

vs. CloudFront geo-restriction: CloudFront geo-restriction applies to the whole distribution with no other conditions. WAF geographic match can be combined with other conditions (e.g., block this country AND this URI path). WAF is more flexible; CloudFront geo-restriction is simpler and cheaper for whole-distribution blocks.

Do you have a specific IP list, or do you want AWS threat-intelligence-based reputation filtering?
↓
📋 I have a specific list of IPs
🔬 Use AWS threat intelligence
✅ IP Set + IPSetReferenceStatement

Create a WAF IP Set containing your CIDR ranges, then reference it in a rule. IP Sets support up to 10,000 addresses. For pure IP-range blocking at scale, a NACL deny rule is more efficient — but WAF IP Sets are correct when you need to combine IP matching with other WAF conditions.

✅ AWSManagedRulesAmazonIpReputationList

AWS maintains the AWSManagedRulesAmazonIpReputationList — a continuously updated blocklist of IPs associated with bots, scanners, and threat actors based on Amazon threat intelligence. Enable this rule group in your Web ACL for automatic coverage without managing your own IP lists.

Which Control Stops This?

An attacker is sending thousands of HTTP POST requests per minute to your login endpoint at /auth/login, attempting to brute-force user credentials. The requests come from rotating source IPs.
› Reveal answer
✅ WAF Rate-Based Rule (scoped to /auth/login path)

NACLs and security groups operate at Layer 3/4 — they see ports and IPs, not URL paths. Since IPs are rotating, a static IP block is ineffective. WAF rate-based rules can aggregate by IP across a 5-minute window and block once a threshold is crossed, with a scope-down statement limiting the rule to the login path only. Shield protects against volumetric floods but not application-layer credential stuffing.

Your security team has identified a specific CIDR block (203.0.113.0/24) as the source of malicious SSH scanning. They need to ensure no traffic from this range can reach any instance in the private subnet, even if a misconfigured security group were to allow it.
› Reveal answer
✅ NACL Deny Rule

Security groups structurally cannot deny — they have only allow rules. A NACL deny rule numbered below any existing allow rules enforces a hard block at the subnet boundary for ALL instances in the subnet, regardless of their security group configuration. This is the canonical "explicit deny" tool in the VPC network stack.

A web application is receiving HTTP requests with query strings like ?id=1' OR '1'='1 that are classic SQL injection probes. You need to detect and block these at the edge before they reach the ALB.
› Reveal answer
✅ WAF — AWSManagedRulesSQLiRuleSet attached to the ALB or CloudFront

NACLs and security groups see only the TCP packet — they have no visibility into the HTTP query string. WAF operates at Layer 7 and can decode URL encoding, inspect query string values, and match against known SQL injection patterns maintained by the AWS Managed Rules team.

A volumetric UDP flood is hitting your internet-facing Network Load Balancer with 10 Gbps of spoofed UDP traffic. The attack is overwhelmingthe NLB's connection capacity.
› Reveal answer
✅ AWS Shield (Standard for basic protection; Shield Advanced for full mitigation + DRT support)

This is a Layer 3/4 volumetric DDoS — exactly what Shield is built for. Shield Standard automatically mitigates common UDP floods. If the attack is sophisticated or business impact is critical, Shield Advanced provides the DRT, cost protection, and advanced detection. WAF operates at Layer 7 and has no visibility into UDP floods.

A compromised EC2 instance in your VPC is attempting to resolve update.malware-c2.net — a known command-and-control domain — every 30 seconds. You need to stop the callback without modifying the instance.
› Reveal answer
✅ Route 53 Resolver DNS Firewall — domain block list

DNS Firewall intercepts the DNS query at the Route 53 Resolver level and returns NXDOMAIN. The instance never receives an IP address for the C2 domain, so the connection cannot be established. Network Firewall would also work at the connection layer, but DNS Firewall stops the threat earlier in the kill chain and does so without requiring routing changes.

Your application serves users in the US and Canada only. Legal compliance requires that users from all other countries receive a 403 response. You want the simplest possible implementation with no custom rule logic.
› Reveal answer
✅ CloudFront Geo-Restriction (allowlist: US, CA)

CloudFront geo-restriction is the simplest solution when you need whole-distribution country filtering with no other conditions. WAF geographic match rules are the alternative if you need to combine geography with other match conditions, but they cost more and require a Web ACL. For a pure "allow only these countries" requirement, CloudFront geo-restriction is the right answer.

Your security team needs to inspect all east-west traffic between microservices in different subnets of the same VPC for known exploit signatures and suspicious protocol behavior, without making changes to the individual service security groups.
› Reveal answer
✅ AWS Network Firewall with Suricata-compatible IPS rules

Network Firewall is the correct tool for deep packet inspection of VPC-internal (east-west) traffic. It deploys in a dedicated subnet and traffic is routed through it via VPC route tables — no changes to security groups needed. It can apply IPS signatures to detect known exploit patterns and flag protocol anomalies. NACLs only do IP/port matching; security groups are per-resource; neither can do signature-based detection.

An EC2 instance needs to accept HTTPS traffic on port 443 from the public internet. The security group currently allows port 443 inbound from 0.0.0.0/0. Users are reporting that responses are being dropped intermittently after the connection is established.
› Reveal answer
✅ NACL — missing outbound rule for ephemeral port range (1024–65535)

The security group is stateful — its inbound allow on port 443 automatically permits return traffic outbound. But the NACL is stateless. If there is no outbound NACL rule allowing traffic on ephemeral ports (the client's source port, typically 1024–65535), the TCP response from the instance is silently dropped at the subnet boundary. The fix: add an outbound NACL rule allowing TCP 1024–65535 to 0.0.0.0/0.

A user accesses your S3-hosted website directly via the S3 website URL, bypassing your CloudFront distribution. This means your WAF rules and geo-restrictions are not applied to that traffic.
› Reveal answer
✅ CloudFront Origin Access Control (OAC) + private S3 bucket

OAC restricts the S3 bucket to only accept requests from the CloudFront distribution (signed by CloudFront with SigV4). The S3 bucket policy grants s3:GetObject only to the CloudFront service principal with the specific distribution ARN. Direct S3 URL access returns 403. Now all requests must flow through CloudFront, ensuring WAF rules and geo-restrictions apply to every request.

During a major product launch, your application experiences a large HTTP flood where each request appears individually legitimate (no obvious patterns, valid user agents, well-formed HTTP). Standard WAF rules are not blocking it. The attack is threatening availability.
› Reveal answer
✅ Shield Advanced + DRT engagement + WAF rate-based rules

A sophisticated Layer 7 HTTP flood where individual requests appear legitimate is precisely the scenario Shield Advanced exists for. The DDoS Response Team (DRT) can analyze traffic patterns and deploy targeted WAF rules during the attack — something Shield Standard cannot do. WAF rate-based rules are a first-line defense, but the DRT has access to broader traffic telemetry to craft attack-specific mitigations.

Scene 11 • Production Trap Gallery

Six Ways Engineers Get This Wrong

These are real failure modes — the kind of mistakes that appear in AWS post-incident reviews and in SCS-C03 exam distractors. Click each card to read the full vignette and the correct fix.

🚫
The "Deny with a Security Group" Trap
Security Group · Allow-only architecture
›

Scenario: An engineer is tasked with blocking all traffic from a competitor's IP range from accessing the company's API. They open the EC2 security group and look for "deny" — but the option does not exist. Confused, they add the competitor's IP range to the inbound rules with... allow? No, that would do the opposite. They cannot find a way to do it in the console.

What went wrong: Security groups are allow-only. There is no deny rule type. Every IP range not explicitly in an allow rule is implicitly denied — but you cannot write a rule that says "deny this specific CIDR while allowing others." The architecture cannot express this requirement.

Fix: Use a NACL deny rule. Add an inbound rule with a low rule number (e.g., rule 50) that explicitly denies the competitor CIDR, placed before any allow rules. NACLs are the correct tool when the requirement is an explicit block of a specific IP range, not a general "restrict to known sources" pattern.

🔄
The Silent NACL Return-Traffic Drop
NACL · Stateless ephemeral port misconfiguration
›

Scenario: A new VPC subnet is configured with a custom NACL. The engineer adds inbound rule 100: allow TCP 443 from 0.0.0.0/0. Users can reach the web server — the TLS handshake completes — but then the connection dies. Intermittent, impossible to reproduce consistently, no application errors logged.

What went wrong: NACLs are stateless. The inbound allow for port 443 does not automatically allow the return TCP responses. The return packets use the client's ephemeral source port (1024–65535) as the destination. Without an outbound NACL rule allowing traffic to port 1024–65535, the TCP ACK and data packets silently vanish at the subnet boundary. The security group is stateful and would have allowed it — but the NACL runs first on the outbound path.

Fix: Add outbound NACL rule 100: allow TCP ports 1024–65535 to 0.0.0.0/0. Every time you add an inbound NACL rule for a service, also add the matching outbound ephemeral port rule for return traffic.

🔢
The NACL Rule-Order Mistake
NACL · First-match evaluation pitfall
›

Scenario: A security engineer adds a NACL deny rule for a known-malicious CIDR: rule number 200, deny. But traffic from that range continues to reach the instances. The engineer is baffled — the rule is right there in the console.

What went wrong: There was already an inbound rule numbered 100: allow all traffic from 0.0.0.0/0 (often left from initial setup). Since NACL rules are evaluated in ascending numeric order and processing stops at the first match, rule 100 (allow all) is matched before rule 200 (deny this CIDR) is ever evaluated. The deny rule is functionally dead.

Fix: Give the deny rule a lower rule number than the allow rule it needs to override. Change the deny to rule 50 so it is evaluated first. This is why reviewing NACL rule numbers and ordering is critical — a deny placed after a broad allow is invisible.

🛡️
Shield Standard vs. Layer 7 Attack
Shield · Layer 7 blind spot
›

Scenario: A fintech company runs a business-critical payment API. Their security lead says "we use AWS, so we have DDoS protection." During a competitor-sponsored attack, the API goes down under a slow HTTP POST flood — thousands of clients sending oversized JSON payloads, each individually valid, holding connections open and draining ALB connection capacity. CloudWatch shows no volumetric anomaly because packet-per-second rates look normal.

What went wrong: Shield Standard protects against Layer 3/4 volumetric attacks. An HTTP application-layer flood at Layer 7 — especially a slow, connection-exhausting variant — is completely invisible to Shield Standard. Standard has no HTTP awareness.

Fix: Enable Shield Advanced. It provides Layer 7 attack detection, 24/7 DRT access, and integration with WAF to deploy targeted rules during an active attack. Also add WAF connection rate limits and body size restrictions to limit each connection's impact.

🚀
WAF Blocks Legitimate Traffic at Launch
WAF · Count mode vs. Block mode oversight
›

Scenario: An engineering team enables the AWS Managed Rules Common Rule Set on their ALB WAF Web ACL with all rules set to Block mode and deploys to production. Within 10 minutes of launch, the customer support queue floods with "account creation is broken" reports. 403 responses are coming from the WAF.

What went wrong: The managed rule group contained the SizeRestrictions_BODY rule, which was blocking registration form submissions with avatars or large profile data. The team had not observed the rule group in Count mode first to identify false positives before enforcing.

Fix: Always introduce a new WAF rule group or Web ACL in Count mode first. Monitor CloudWatch WAF metrics (BlockedRequests, CountedRequests, sampled requests in the console) for at least 24–72 hours of representative traffic before switching to Block mode. Identify and exclude rules that generate false positives using rule overrides.

🔓
S3 Origin Accessible Without CloudFront
CloudFront · OAC missing, WAF bypass
›

Scenario: A team sets up CloudFront in front of their S3-hosted single-page app and attaches WAF with geo-restrictions. Six months later, a pen tester discovers that the S3 website endpoint URL is still publicly accessible — bypassing CloudFront, WAF, and all geo-restrictions entirely. Worse, the S3 bucket had public read enabled for the website configuration.

What went wrong: Origin Access Control was never configured. The S3 bucket remained publicly accessible via its website URL. Any client that knew (or guessed) the S3 URL could bypass all CloudFront security controls. This is a critically common oversight — CloudFront in front of S3 without OAC provides zero security for the origin itself.

Fix: Enable OAC on the CloudFront distribution, update the S3 bucket policy to allow only the CloudFront service principal, disable public access on the bucket, and remove the S3 website endpoint. Also enable Block Public Access at the account and bucket level as a defense-in-depth control.

1. A security engineer needs to ensure that no traffic from CIDR 198.51.100.0/24 can ever reach any EC2 instance in a private subnet, even if a security group is misconfigured to allow it. Which control achieves this?
AAdd an inbound security group deny rule for the CIDR range on all instances in the subnet
BAdd an inbound NACL deny rule for the CIDR range with a rule number lower than any existing allow rules
CCreate a WAF IP Set rule to block the CIDR range and attach it to the VPC
DAdd a route table entry that routes the CIDR to a blackhole target
✓ Correct Answer: B

Security groups have no deny rules — only allow rules. A NACL deny rule explicitly blocks the CIDR at the subnet boundary, regardless of security group configuration. The deny must have a lower rule number than any existing allow rules (NACLs evaluate in ascending order, first match wins). WAF does not attach to VPCs and a route blackhole would break routing for all destinations, not just that source CIDR.

2. A company runs an internet-facing ALB. They have enabled an inbound NACL rule allowing TCP port 443 from 0.0.0.0/0, and the EC2 security group allows the same. Users report that HTTPS connections succeed initially but then hang and eventually time out. What is the most likely cause?
AThe security group is missing an outbound rule for TCP 443
BThe NACL inbound rule is configured with the wrong protocol
CThe NACL is missing an outbound rule for ephemeral ports 1024–65535
DThe ALB requires a separate security group rule for return traffic
✓ Correct Answer: C

NACLs are stateless — return traffic must be explicitly allowed. The TCP response from the server goes back to the client's ephemeral source port (1024–65535). Without an outbound NACL rule allowing this port range, the response is dropped at the subnet boundary. The security group is stateful and handles return traffic automatically, but it does not override the NACL outbound check.

3. A web application is experiencing SQL injection attacks against its search endpoint. The engineering team needs to block known SQLi patterns without modifying the application code. Which combination of services achieves this with the least operational overhead?
ADeploy a NACL deny rule matching known SQL syntax in packet payloads
BConfigure AWS Network Firewall with custom Suricata rules matching SQL injection patterns
CEnable GuardDuty anomaly detection and configure automated remediation via Lambda
DAttach AWS WAF with the AWSManagedRulesSQLiRuleSet to the ALB or CloudFront distribution
✓ Correct Answer: D

NACLs operate at Layer 3/4 and cannot inspect HTTP payload content — SQL syntax in a query string is invisible to a NACL. Network Firewall with Suricata rules could technically work but has far more operational overhead than a managed WAF rule group. GuardDuty detects threats but does not block HTTP requests. WAF with the AWS Managed SQLi rule group provides automatic detection and blocking with minimal configuration.

4. A company's business-critical e-commerce site was taken offline by a sophisticated HTTP flood during peak shopping season. The attack used rotating source IPs and well-formed HTTP requests that bypassed existing WAF rules. Which AWS service addition would best prevent this in the future?
AEnable AWS Shield Standard on the ALB
BEnable AWS Shield Advanced and engage the DDoS Response Team proactively
CAdd additional EC2 instances behind the ALB to absorb attack traffic
DDeploy a NACL to rate-limit inbound requests at the subnet level
✓ Correct Answer: B

A sophisticated Layer 7 HTTP flood with rotating IPs that bypasses WAF rules is the exact scenario Shield Advanced addresses. Shield Standard has no Layer 7 visibility. The DRT can analyze attack patterns and deploy custom WAF mitigations during an active attack. Scaling EC2 absorbs some capacity but does not stop the attack. NACLs cannot rate-limit or inspect HTTP content.

5. A security engineer wants to ensure that an S3 bucket used as a CloudFront origin is not directly accessible via the S3 URL, forcing all access through CloudFront (and its attached WAF). What is the correct approach using current AWS best practices?
AConfigure CloudFront Origin Access Control (OAC) and update the S3 bucket policy to allow only the CloudFront service principal for that distribution
BConfigure a CloudFront Origin Access Identity (OAI) and set the bucket ACL to private
CEnable S3 Block Public Access and add a NACL to deny direct S3 traffic
DSet a bucket policy that denies all requests where the referer header is not set to the CloudFront domain
✓ Correct Answer: A

OAC is the current AWS best practice, replacing the older OAI method. OAC uses SigV4 signing so CloudFront authenticates to S3 on your behalf. The bucket policy restricts access to only the CloudFront service principal (aws:SourceArn matching the distribution ARN). OAI still works but is legacy. A referer-header check is easily spoofed. NACLs cannot protect S3 endpoints the same way.

6. An EC2 instance in a private subnet is attempting to connect to a known command-and-control domain. Which control stops this callback at the earliest point in the kill chain?
AAWS Network Firewall domain list blocking the C2 domain
BA NACL outbound deny rule for the C2 server IP address
CRoute 53 Resolver DNS Firewall domain block rule
DA security group outbound rule removing access to port 443
✓ Correct Answer: C

DNS Firewall intercepts the DNS query before any IP address is returned — no connection can be established if the domain does not resolve. Network Firewall (A) blocks at the connection layer, which is still early but occurs after DNS resolution. A NACL IP deny (B) requires knowing the current IP — C2 operators rotate IPs. A security group removing port 443 (D) would break legitimate HTTPS traffic.

7. A WAF engineer has just enabled the AWSManagedRulesCommonRuleSet on a production ALB Web ACL in Block mode. Within minutes, legitimate customers report being unable to submit registration forms. What should the engineer do FIRST?
ARemove the WAF Web ACL from the ALB immediately
BDisable all rules in the managed rule group one by one until the issue resolves
CSwitch the entire Web ACL to Count mode and re-enable Block after reviewing all rules
DSet the specific offending rule(s) to Count mode using a rule group override, then investigate WAF sampled requests to identify the false positive rule
✓ Correct Answer: D

The correct immediate action is targeted: use a rule group override to set the specific blocking rule to Count (not the entire ACL). Check WAF sampled requests in the console or CloudWatch Logs to identify exactly which rule is matching legitimate requests. Removing the whole ACL (A) loses all protection. Switching the entire ACL to Count (C) is better than removing it but loses blocking for all other real threats. Disabling rules one-by-one (B) is slow and high-risk in production.

8. A company needs to inspect all traffic flowing between VPCs in a hub-and-spoke architecture for known exploit signatures, using centralized management. What is the recommended approach?
ADeploy NACLs on every subnet in every spoke VPC with rules matching known exploit signatures
BDeploy AWS Network Firewall in a centralized inspection VPC and route inter-VPC traffic through it via Transit Gateway
CAttach AWS WAF to each VPC and configure Layer 7 rules for exploit detection
DConfigure VPC Flow Logs for all VPCs and trigger Lambda functions to block traffic in real time
✓ Correct Answer: B

Network Firewall in a centralized inspection VPC, combined with Transit Gateway route tables that steer inter-VPC traffic through the inspection path, is the standard AWS architecture for centralized deep-packet inspection. NACLs cannot do signature matching. WAF does not attach to VPCs as a general traffic inspection point. VPC Flow Logs are metadata only — no payload inspection, no real-time blocking.

9. Which statement correctly describes the difference between Route 53 Resolver DNS Firewall and AWS Network Firewall in terms of where they intercept threats?
ADNS Firewall blocks domain resolution before a connection is attempted; Network Firewall inspects and blocks traffic after a connection is established
BDNS Firewall operates at Layer 7; Network Firewall operates at Layer 3/4 only
CDNS Firewall and Network Firewall are redundant — both block the same class of threats
DNetwork Firewall can block DNS queries; DNS Firewall can block established TCP connections
✓ Correct Answer: A

DNS Firewall operates at the resolver level — it intercepts the DNS query and prevents domain resolution, so no IP is returned and no connection can be initiated. Network Firewall inspects traffic that is already flowing (after DNS resolution has occurred and a connection is being established or maintained). They are complementary, not redundant — each stops threats at a different point in the kill chain.

10. A security team wants to add HTTP security headers (HSTS, X-Frame-Options, Content-Security-Policy) to all responses from a multi-origin CloudFront distribution without modifying any origin application code. What is the correct approach?
ACreate a WAF rule that injects security headers into HTTP responses
BConfigure an AWS Lambda@Edge function to add response headers on every request
CCreate a CloudFront Response Headers Policy and attach it to the distribution
DConfigure the ALB to add security response headers via listener rules
✓ Correct Answer: C

CloudFront Response Headers Policies are the purpose-built, lowest-overhead way to add security headers at the edge. You define the header names and values in the policy and associate it with a CloudFront distribution or cache behavior. Lambda@Edge (B) could work but is far more complex and costly. WAF does not modify response headers. ALB header rules would only apply to traffic behind the ALB, not other origins.

11. A company's application uses an Application Load Balancer and has AWS WAF attached. They notice that all requests from a specific corporate office IP range are being blocked, even though those requests are legitimate. The WAF logs show the AWSManagedRulesAmazonIpReputationList is matching and blocking those IPs. What is the best remediation?
ARemove the AWSManagedRulesAmazonIpReputationList rule group from the Web ACL
BSet the entire Web ACL to Count mode to stop blocking
CAdd a NACL rule to allow the corporate IP range, which overrides WAF
DAdd a WAF rule with higher priority (lower rule number) that explicitly allows the corporate IP set, placed before the managed rule group
✓ Correct Answer: D

WAF rules are evaluated in priority order. By adding an Allow rule with a lower rule number (higher priority) that matches the corporate IP Set, those requests are allowed before the reputation list rule is evaluated. WAF rule priority is controlled by the rule order in the Web ACL. Removing the rule group (A) loses all protection from that group. NACL allow rules do not override WAF — they operate at different layers and WAF still inspects allowed network traffic.

12. An organization must ensure that any DNS query resolution failure from Route 53 Resolver DNS Firewall does NOT allow queries to pass through to prevent malware callbacks during a service disruption. Which configuration achieves this?
AConfigure the DNS Firewall with fail-open mode at the VPC level
BConfigure the DNS Firewall with fail-closed mode at the VPC level

DNS Firewall's fail behavior is configurable per VPC. Fail-closed means that if the DNS Firewall service cannot evaluate a query, it blocks the query — prioritizing security over availability. For security-critical workloads where malware callback prevention outweighs availability risk, fail-closed is the correct setting. Query logging (C) is observability, not enforcement.

Scene 13 • Discussion FAQ

Questions You Will Actually Have

Click a question to see the answer. These are the questions that keep coming up — from students, from engineers, and on the exam.

🧑‍💻 You ask › If security groups are stateful and easier to manage, why would I ever need a NACL at all? Can I just use security groups for everything?
🛡️ Your Mentor You need NACLs the moment you need to explicitly deny traffic from a specific source — something security groups fundamentally cannot do. Security groups are allow-only by design. If you have a known-malicious IP range, a compromised supplier network, or a legal requirement to block specific CIDR ranges, security groups cannot express that requirement. Also, NACLs apply to the entire subnet — useful when you want a consistent deny across all resources without touching each resource's security group. Think of security groups as the primary tool and NACLs as the tool you reach for specifically when you need an explicit deny or a subnet-wide control. Both are almost always deployed together in production VPCs.
🧑‍💻 You ask › WAF is at Layer 7 and blocks web attacks. Network Firewall also does deep inspection. Are they basically the same thing? When do I use one vs. the other?
🛡️ Your Mentor They operate in very different positions and serve different traffic. WAF attaches to specific AWS services — CloudFront, ALB, API Gateway, AppSync — and inspects inbound HTTP/HTTPS requests to those services. It is purpose-built for web application protection: SQLi, XSS, rate limiting, geo-blocking. Network Firewall deploys inside your VPC and inspects arbitrary network traffic via route table steering — any protocol, any port, any direction including east-west (VPC-to-VPC). It uses IPS signatures (Suricata rules), domain lists, and protocol anomaly detection. Use WAF for your web-facing application attack surface; use Network Firewall for VPC-level traffic inspection, east-west security, and egress filtering. In a mature architecture, you would have both.
🧑‍💻 You ask › Does every application actually need Shield Advanced? The $3,000/month cost feels steep for most workloads.
🛡️ Your Mentor Shield Standard is genuinely enough for many workloads — it handles the common volumetric Layer 3/4 attacks automatically and for free. Advanced is the right answer when three conditions align: the application is business-critical, it is directly internet-facing, and a DDoS event would cause significant financial or reputational damage. Think: payment processing, streaming platforms, large e-commerce properties during peak seasons, regulated financial services. At $3,000/month per organization (not per resource), the cost protection clause alone can justify it for workloads that could face massive EC2 auto-scaling charges during a traffic flood. For internal tools, dev environments, or low-traffic services, Standard is fine. On the exam, "business-critical internet-facing application" is the signal phrase for Shield Advanced.
🧑‍💻 You ask › I have Network Firewall blocking outbound connections to known-bad domains. Why do I still need DNS Firewall? Is not that redundant?
🛡️ Your Mentor It is genuinely not redundant — they block at different points in the kill chain. Network Firewall sees a connection attempt and can block it. But by the time Network Firewall sees it, the DNS query has already resolved. If your DNS Firewall is not blocking, the EC2 instance has already received an IP address for the malicious domain. If the C2 operator rotates IPs and your Network Firewall domain list has not been updated, the new IP gets through. DNS Firewall blocks the query itself — no resolution means no IP means no connection attempt. Also consider DNS tunneling: malware that encodes C2 communication in DNS queries can bypass Network Firewall entirely because no TCP/UDP connection is made to the C2 server, only DNS packets to a resolver. DNS Firewall stops those queries before the tunnel is established. The two controls complement each other perfectly.
🧑‍💻 You ask › I enabled WAF with the Common Rule Set on my ALB and it blocked some legitimate user traffic. How do I find exactly which rule caused it?
🛡️ Your Mentor The WAF console has a "Sampled requests" view under each Web ACL — it shows recent requests, which rule matched, and what the matching field was. For deeper investigation, enable WAF full logging to a Kinesis Data Firehose, S3, or CloudWatch Logs group. The log record includes the terminatingRuleId (the rule that made the final Allow/Block decision), the httpRequest details, and matched rule labels. Once you have identified the offending rule, go to the Web ACL rule group, open the rule group, and set that specific rule to Count mode via a rule action override — this keeps all other rules enforcing while you observe the false-positive rate. Then either add an exception (a custom allow rule with higher priority), tune the managed rule override, or contact AWS if you believe it is a genuine false positive in their managed list.
🧑‍💻 You ask › For the exam, when a scenario mentions OWASP and asks which AWS service mitigates it, is the answer always WAF?
🛡️ Your Mentor WAF is the answer for OWASP categories that involve application-layer request content — injection (SQLi, XSS), SSRF patterns, and request-size or rate anomalies. But several OWASP categories are not WAF scenarios at all. Broken Access Control (A01, the top category) is an IAM and application authorization problem — WAF cannot determine if a user is authorized to access a specific business object. Cryptographic Failures (A02) are addressed by TLS enforcement, ACM, and KMS — not WAF. Security Misconfiguration (A05) is AWS Config and Security Hub territory. Software Integrity Failures (A08) are a supply-chain and pipeline problem. The exam will offer WAF as a distractor for these categories — knowing what WAF cannot see (authorization logic, encryption state, configuration state) is as important as knowing what it can.
🧑‍💻 You ask › What is the difference between CloudFront geo-restriction and WAF geographic match rules? Can they both do the same thing?
🛡️ Your Mentor Both restrict traffic by country, but with different flexibility. CloudFront geo-restriction applies to the entire distribution — all paths, all behaviors — with a simple allowlist or blocklist of countries. It is built into CloudFront, requires no WAF, and is cheaper. WAF geographic match is more powerful: you can combine it with other conditions (block this country AND this URI path, or block all countries except these AND only if the user agent is suspicious). WAF geo-match lets you write nuanced, multi-condition rules. For a straightforward "this service is only for users in the UK" requirement, CloudFront geo-restriction is the simpler answer. For "block users from these countries accessing the /admin path only," WAF is the right tool. The exam will usually hint at which you need through the specificity of the requirement.
🧑‍💻 You ask › A lot of these controls overlap. How do I think about which layer to put a control at when multiple controls could technically do the job?
🛡️ Your Mentor Apply the principle of blocking threats at the earliest point where the information to make the decision is available. DNS Firewall blocks before any connection — use it for known-bad domains. NACLs block before the security group — use them for hard CIDR denies. WAF blocks before the request reaches your origin — use it for application-layer threats. This ordering also determines cost and performance: stopping a threat at DNS is cheaper and faster than stopping it at the application layer. Defense-in-depth means you do not rely on any single layer — you apply appropriate controls at every layer, so a failure or bypass of one layer does not expose the whole stack. The exam loves scenarios where one layer fails (a misconfigured security group, a WAF false positive) and you must know which other layer would have caught it.
