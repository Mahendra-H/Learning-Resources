SCS-C03 Module 02 · IAM Core Domain 4 — Identity & Access Management
Scene 01 — Identities & Access

Who Gets To Touch What

Module 1 drew the line of the shared responsibility model — you now know, cleanly, what AWS secures and what is yours. IAM is where that line becomes operational. Shared responsibility told you what you own. IAM is the mechanism you use to control who is allowed to touch it: every S3 bucket, every EC2 instance, every KMS key you are accountable for is only as protected as the identities and policies standing in front of it. This module makes that control mechanism concrete, mechanical, and testable.

IAM users: long-term identity

An IAM user is a long-term identity: a named entity in your account with persistent credentials attached to it — a console password, and optionally one or two access keys for programmatic calls. A user represents something that exists indefinitely, the same way an employee badge exists until someone deactivates it. Under the hood, a user is really just an identity that IAM can attach policies to and that AWS can authenticate directly, with no handoff to another service required.

This is the core of why users are handled carefully on this exam: everything about a user's credentials is static until a human rotates or revokes it. If a user's access key leaks, that key stays valid — with whatever permissions the user carries — until someone notices and acts. There is no expiry working in your favor by default.

IAM groups: not an identity

A group is not an identity, and this trips up more candidates than almost anything else in this domain. A group is purely a container for attaching policies to several users at once — a management convenience, nothing more. You cannot log in as a group. You cannot place a group in the Principal element of a trust policy and have it mean "anyone in this group." AWS will not let you assume a group, because there is no identity there to assume — only a bundle of policy attachments that happen to apply to whichever users are members. When a scenario question describes a group, read carefully for whether it is really asking about the users inside it.

IAM roles: temporary by design

A role is the opposite of a user in exactly the way that matters most: it carries no permanent credentials at all. A role is an identity that something else — a person, an application, an AWS service — assumes temporarily. When a caller assumes a role, IAM does not hand over a static secret. The request goes to AWS STS, which checks the caller against the role's trust policy (the "who is allowed to become this role" half of the role) and, if that check passes, issues a temporary security credential: an access key ID, a secret access key, and a session token, bundled together and set to expire automatically — anywhere from 15 minutes up to 12 hours later, depending on how the role is configured.

Once that credential expires, it is simply gone. Nobody has to rotate it, revoke it, or remember it exists. This is the entire reason roles are the default answer on this exam for almost every access pattern — an EC2 instance calling S3, a Lambda function calling DynamoDB, one AWS account calling into another — because a credential that expires on its own is a credential that cannot quietly turn into a standing liability.

01 · CallerCould be a person in the console, an application calling the SDK, or another AWS service such as EC2 or Lambda acting on your behalf. Whatever it is, it does not already hold the permissions it is about to use.
02 · sts:AssumeRoleThe caller sends a request to AWS Security Token Service naming the role it wants to become. This is a single API call — no credentials change hands yet, only a request.
03 · Trust Policy CheckSTS checks the role's trust policy: the list of principals allowed to assume this specific role. If the caller is not named there, directly or through a condition it satisfies, the request fails here, before any permissions are even considered.
04 · Temp CredsSTS issues a temporary access key ID, secret access key, and session token, scoped to the role's permission policy and set to expire on a timer the role's configuration controls. When the clock runs out, the credential simply stops working — no revocation step required.

Production scenario

A platform team configured a CI/CD deployment role with the maximum 12-hour session duration, reasoning that long-running pipelines occasionally needed the extra room and they did not want jobs failing mid-deploy from an expired credential. Months later, a compromised build agent's temporary credentials stayed valid for most of a workday before anyone noticed the anomaly — the same auto-expiry that makes roles safer by default had been configured away. The fix was not abandoning roles; it was matching session duration to the actual job length, not to the maximum the API allows.

Common mistake

A surprising number of real-world IAM misconfigurations trace back to treating a group as if it were a principal. If a trust policy or resource policy ever references a group ARN as a Principal, that policy is broken — AWS will not evaluate it the way the author intended, because a group can neither be assumed nor authenticated as. On the exam this shows up as a scenario where access unexpectedly fails; the fix is almost always "reference the actual role or user, not the group."

Exam angle

Expect direct tests of the mechanism, not just the vocabulary: which service issues temporary credentials (STS, not IAM itself), what a trust policy actually governs versus a permission policy, and why a long-lived access key is treated as something to minimize rather than something to forbid outright. If a question's correct answer involves "avoid storing static credentials," it is almost always steering you toward a role.

Scene 02 — Policy Types

Four Ways To Grant The Same Permission

Every permission in AWS is granted by a policy, but "policy" is not one thing — it is four distinct mechanisms that differ in where they live, how they are reused, and what they are capable of. Picking the right one is a judgment the exam tests directly: not just "what is a resource-based policy" but "given this exact requirement, which of the four is the only correct tool."

An identity-based policy attaches to a user, group, or role and answers one question: what can this identity do? It is the default mental model most engineers start with — permissions travel with the identity, wherever that identity goes. Identity-based policies can be inline or managed, and both are evaluated the same way: as part of the full set of policies attached to the identity making the request.

A resource-based policy attaches directly to the resource itself — an S3 bucket policy, a KMS key policy, an SQS queue policy, a Lambda resource policy — and answers the opposite question: who is allowed to touch this? This distinction matters most in one specific, exam-favorite scenario: granting a principal in another AWS account access to a resource in yours, without that account ever assuming a role of yours. A resource-based policy can name an external account or principal directly and grant access — it is the only one of the four policy types that can do this unassisted. Module 3 goes deep on the cross-account mechanics; for now, know that resource-based policies are attached to what is being protected, not to who is asking.

An inline policy is embedded directly inside a single identity — it has no independent existence, no ARN of its own, and no way to be attached to a second identity. Its defining trait is lifecycle: delete the identity, and its inline policy disappears with it, guaranteed. That guarantee is genuinely useful for a permission so specific to one role that reuse was never the point. The cost is that inline policies do not scale as a management pattern — the same permission duplicated as inline policies across a dozen roles becomes a dozen separate places to remember to update.

A managed policy is a standalone object with its own ARN, attachable to many identities at once. AWS-managed policies are written and maintained by AWS — convenient, but you cannot edit them, and their scope tends to run broader than a genuinely least-privilege policy should. Customer-managed policies are the version you own: attach the same policy to twenty roles, and updating it once updates all twenty. AWS keeps up to five previous versions of a customer-managed policy, so a bad edit is a rollback, not an incident — exactly the auditability that inline policies trade away.

Production scenario

A team standardized on inline policies for speed — no separate object to create, just attach permissions directly to each role as it was built. It worked fine until a security review needed to answer one question: which roles can call kms:Decrypt on the production signing key? Because the same permission had been copy-pasted into inline policies on eleven different roles over eight months, three of those copies were already stale, granting decrypt on a key ARN that had since been rotated out. A single customer-managed policy attached to all eleven roles would have made that inconsistency impossible: one edit, eleven roles updated at once.

Common mistake

Do not assume a resource-based policy is always enough for cross-account access by itself. It is sufficient within the same account, and it is necessary for cross-account access — but depending on the service and the exact pattern in use, the calling account's own identity-based policy may still need to explicitly allow the action too. Treat this as a flag, not a full answer: Module 3 covers the cross-account evaluation rules in depth. For now, do not assume "a resource-based policy exists" automatically means "cross-account access works."

Exam angle

The exam loves a plain-English requirement dressed up as a policy-type question: "a security engineer needs Account B to read objects in an Account A bucket, without Account B assuming a role." The only policy type on this list that can do that unassisted is a resource-based policy — everything else either cannot reach across the account boundary or requires a role assumption you were explicitly told not to use. When a question rules out role assumption by name, that is your signal.

Scene 03 — Evaluation Logic
Scene 03 — Evaluation Logic

How AWS Actually Decides

Every concept so far — users, roles, policy types — feeds into one mechanical process: how AWS actually decides whether a specific request is allowed. This is the single most exam-critical skill in this module, and arguably in the whole IAM domain. Get the evaluation order internalized as a reflex, not a lookup — the exam will hand you a stack of policies and one request, and expect you to reason to the correct answer without guessing.

The order is fixed and it never changes. First, check for an explicit deny anywhere among every policy that applies to this request — identity-based, resource-based, and beyond. If any single statement explicitly denies the action, the request is denied, full stop, no matter how many other statements allow it. Second, if no explicit deny fired, check for an explicit allow anywhere among those same policies. If one exists, the request is allowed. Third, if neither an explicit deny nor an explicit allow matched anything, the request is denied anyway — this is the implicit deny, IAM's default-closed posture. Nothing has to actively block a request for it to fail; the absence of a matching Allow is enough on its own.

That third step is the one candidates most often get backwards. There is no "if unsure, allow" fallback anywhere in IAM. Silence is a denial. The exam frequently tests exactly this: a policy configuration where nothing explicitly denies the action in question, and the trap answer assumes that silence means it is allowed.

Step 1 · Explicit DenyScan every applicable policy for any statement with Effect: Deny that matches this action, resource, and any conditions. Find one? The request is denied immediately — nothing after this step matters.
Step 2 · Explicit AllowNo explicit deny fired. Now scan every applicable policy for any statement with Effect: Allow that matches. Find one? The request is allowed.
Step 3 · Implicit DenyNo explicit deny, and no explicit allow either. IAM defaults closed: this is an implicit deny. The request fails, even though nothing specifically said no.

  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::reporting-data-prod/*",
        "arn:aws:s3:::reporting-data-prod"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "true" }
      }
    }
  ]
}
VersionAlways "2012-10-17" in current practice — this is the policy language version, not a date you choose. An older version string exists but AWS documentation treats this one as the standard going forward.
StatementAn array — a policy can contain many statements, each evaluated independently. Every statement in every applicable policy is checked; there is no early exit after the first match.
EffectOnly two valid values: Allow or Deny. This single field decides whether the statement participates in step one (deny) or step two (allow) of the evaluation order above.
ActionThe specific API operations this statement matches, in service:action format. Supports wildcards, such as s3:Get* or s3:*, to match a family of actions at once.
ResourceThe ARN or ARN pattern this statement applies to. A statement with a matching Action but a non-matching Resource simply does not fire for this request.
ConditionOptional. If present, every condition in the block must be satisfied for the statement to apply. No Condition block means the statement applies unconditionally whenever Action and Resource match.

Same account: identity + resource policies combine

When both an identity-based policy and a resource-based policy could apply to the same request — the common case being an IAM user calling an S3 API against a bucket in the same account — AWS effectively takes the union of what each side grants, still subject to any explicit deny found anywhere in either. If the identity-based policy is silent on the action but the bucket policy grants it, the request is allowed: the resource-based policy alone was sufficient. If the identity-based policy grants it but the bucket policy explicitly denies it, the request is denied: the deny wins regardless of source. Neither policy has to carry the whole weight, but either one can be the thing that stops the request cold. Scene 04 walks through this pairing in detail.

Multiple policies on one identity: full aggregate, not "last one wins"

It is common for a single identity to have several policies applying at once: two or three attached managed policies, an inline policy, and whatever policies are attached to every group that identity belongs to. AWS does not evaluate these in any particular order, and there is no such thing as "the most recently attached policy wins." Every applicable statement, from every applicable policy, is collected into one evaluation set and run through the same three-step logic together. A narrower policy does not override a broader one just because it was attached more recently, and an older policy does not get ignored just because a newer one exists. If you want a permission actually revoked, you have to remove or explicitly deny it — attaching a more restrictive policy alongside an existing permissive one does not shrink what the permissive one still grants.

Every attached policy contributes. Only an explicit Deny subtracts.

Cross-account requests raise the bar: both the caller's own identity-based policy and the resource's resource-based policy generally need to independently allow the action, rather than either one being enough on its own. That is a meaningfully different rule from the same-account case above, and it is worth flagging now so it does not surprise you later — Module 3 is where you get the full mechanics, including how service control policies and permission boundaries factor into that cross-account picture.

Production scenario

A security engineer tightening access for a data-processing role removed a broad customer-managed policy that granted s3:* across every bucket, and attached a new, carefully scoped policy granting only the three actions the role actually used. The change looked complete in the console diff. Two weeks later, an audit found the role could still read objects from buckets far outside its scope — because a second, older customer-managed policy, attached back when the role was first created and never revisited, still granted broad S3 read access on its own. Attaching the new narrow policy did not remove what the forgotten one still granted; evaluation aggregates every attached policy, and no explicit deny existed to override it. The fix required detaching the stale policy directly, not just adding a better one beside it.

Common mistake

"No matching statement" is not a neutral outcome — it is a denial, and the exam tests whether you remember that. Expect scenario questions where a request touches an action or resource that no attached policy mentions at all, in either direction. The correct answer is Deny, by implicit default, even though nothing in the policy set was written with that specific request in mind. If you catch yourself reasoning "nothing denies it, so it must be fine," stop — that is the trap.

Exam angle

Multi-policy scenario questions are the signature format for this topic: you will be shown two or three policy snippets and one specific request, and asked to reason through all of them together. Work the three steps in strict order every time — scan everything for an explicit deny first, only then look for an explicit allow, and only conclude implicit deny if you genuinely found neither. Skipping straight to "does anything allow this" is how candidates miss a deny buried in the second or third policy.

Scene 04 — Identity + Resource, Same Account

Two Policies, One Decision

Scene 03 established the rule in the abstract: same-account identity and resource-based policies combine, either one can grant, and any explicit deny anywhere still wins. This scene makes that concrete with the pairing the exam asks about most — an IAM identity and an S3 bucket policy, evaluated together against one request.

Identity-based policy — attached to role Analytics-Reader (silent on S3)
{
  "Statement": [{
    "Effect": "Allow",
    "Action": "dynamodb:Query",
    "Resource": "*"

Resource-based policy — bucket "reporting-data-prod"

Identity-based policy — attached to role Break-Glass-Admin
{
  "Statement": [{
    "Effect": "Allow",
    "Action": "*",
    "Resource": "*"
  }]
}
Resource-based policy — bucket "reporting-data-prod"
{
  "Statement": [{
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": "arn:aws:s3:::reporting-data-prod/*",
    "Condition": { "Bool": { "aws:SecureTransport": "false" } }
  }]
}
Request: Break-Glass-Admin calls s3:GetObject over plain HTTP
Result: DENY — AdministratorAccess is not a rebuttal to an explicit deny

In Case A, the role has no S3 permissions in its identity-based policy at all — nothing attached or inline mentions S3. The bucket's own policy explicitly names that role's ARN as a Principal and grants s3:GetObject, so the request succeeds. The identity-based policy's silence is not a deny; it simply has nothing to say about this action, so it does not participate in the outcome one way or the other. The resource-based policy, on its own, was sufficient — exactly the special power Scene 02 flagged: a resource-based policy can grant access without any identity-based policy backing it up, as long as everything stays inside one account.

In Case B, flip it. An administrator role carries full access by design. The bucket policy carries an explicit Deny for any request that does not arrive over TLS, and the administrator's request happens to come in over plain HTTP — so it is denied. Broad permissions elsewhere do not create an exception to an explicit deny anywhere in the evaluation. This surprises engineers constantly: "but they have AdministratorAccess" is not a rebuttal, because step one of the evaluation order never checks who is asking or how broad their other permissions are — only whether any applicable statement says Deny. A bucket-level deny protects the bucket from every principal touching it, admins included, unless that principal is explicitly carved out of the condition.

Production scenario

A finance team locked down a reporting bucket with a policy granting read access only to a specific analytics role, and assumed that was the complete access boundary. During an incident review, they discovered a completely unrelated administrator role could still list and read every object in the bucket — not because of any bucket policy grant, but because that administrator role's own identity-based policy carried AdministratorAccess, and the bucket policy never carried an explicit deny for anyone else. The team had reasoned entirely in resource-policy terms and forgotten that a same-account identity-based Allow needs no help from the resource at all; a short principal list on a bucket policy restricts who gets in through that policy, but it does nothing to block identities that already have their own broad Allow. The real fix was a bucket-level explicit deny scoped by principal, not a narrower resource-based allow.

Common mistake

It is tempting to treat a bucket policy's principal list as a complete access boundary — "only these three roles are named here, so only these three can get in." That is false whenever any other identity's own identity-based policy already grants the action broadly. A resource-based policy narrows who can get in through itself; it does not, by existing, block access that a separate identity-based policy already grants elsewhere. The only way to make a resource-based policy an actual ceiling is to pair it with an explicit deny for everyone outside your intended list.

Exam angle

Expect a two-policy exhibit: one identity-based snippet, one resource-based snippet, one request. Check both for an explicit deny first, across both documents, not just one, before you even look for an allow. Then check both for an allow. Same-account questions usually hinge on whether you remember that either side alone can grant, and that a deny on either side alone can block, regardless of what the other side says.

Scene 05 — Condition Keys

Making Allow And Deny Situational

Every policy so far has matched a request unconditionally: right action, right resource, done. Condition keys add a third gate — a specific circumstance that must also be true. They are what turns "this role can read this bucket" into "this role can read this bucket, but only from the corporate network, only with MFA, only over TLS." Six of them show up constantly on this exam; know what each restricts and, just as importantly, how a condition behaves differently depending on whether it sits on an Allow or a Deny.

Click any card to expand the snippet and explanation.

The same condition means something different on Allow versus Deny

A condition behaves differently depending on which effect it is attached to, and this is one of the most frequently misread mechanics on the exam. On an Allow, a condition narrows the grant: the statement only allows the request if the condition evaluates true; if the condition is false, the Allow simply does not fire, and evaluation moves on to look elsewhere. On a Deny, a condition gates the block: the statement only denies the request if the condition evaluates true.

Here is the part that trips people up: if that condition evaluates false, the Deny does not fire either. It is not that the request becomes "safer" or "allowed instead" — the Deny statement is just inactive for this particular request, exactly the way an Allow with a false condition is inactive. Whether the request ultimately succeeds still depends on whether some other statement, somewhere else, explicitly allows it. A false condition on a Deny does not grant anything; it only means that specific Deny is not the one deciding this outcome.

Production scenario

A platform team added a Deny statement blocking any API call outside two approved Regions, aiming to keep a compliance-sensitive workload contained. The policy worked in every manual test. Weeks later, a global content-delivery integration silently stopped replicating data, and nobody connected it to the new policy at first — the replication job ran through a Lambda function whose IAM role picked up the same Region-restricting Deny, because the Deny had been attached at a level broad enough to cover every role in the account, not just the ones running the sensitive workload. The condition itself was correct; the blast radius of where it was attached was not.

Common mistake

The single biggest trap in this scene: reading a false condition on a Deny as if it means "access is granted." It does not. A false condition on a Deny only means that particular statement is not the one blocking this request — the request's actual fate still depends entirely on whether some Allow, anywhere, matches it. Never treat an inactive Deny as a substitute for an actual Allow.

Exam angle

Expect a policy with a conditioned Deny and a separate, unconditioned Allow, then a request that fails the condition. Trace it in order: the Deny does not fire (condition false), so step one passes clean; step two then finds the Allow, and the request succeeds. Candidates who stop reasoning the moment they see a Deny, without checking whether its condition actually matched, consistently pick the wrong answer here.

Scene 06 — The NotAction Trap

Everything Except...

NotAction and NotResource look like scoping tools, and used carefully, they can be. Used carelessly, they are the fastest way to accidentally grant almost an entire AWS account. Both flip the usual logic: instead of listing what a statement matches, you list what it does not match, and the statement applies to everything else. That inversion is exactly where the trap lives.

NotAction matches every action except the ones listed. Paired with Effect: Deny, this is often genuinely useful and fairly safe — "deny everything except these approved actions" reads naturally and behaves the way you would expect. Paired with Effect: Allow, it becomes dangerous fast: "allow everything except these listed actions" grants the entire rest of the AWS action namespace, across every service, unless something else stops it. NotResource works the same way for resources — it matches every resource except the ones listed, and combined with Allow, it is just as capable of over-granting if the excluded list is short and the rest of the statement is broad.

The exact trap policy, read two ways

A real pattern that shows up in production more often than it should
{
  "Effect": "Allow",
  "NotAction": ["iam:*", "organizations:*"],
  "Resource": "*"
}

Read it the way its author probably intended: "block IAM and Organizations actions, allow the rest — feels restrictive." Now read it the way AWS actually evaluates it: this statement grants every action, in every AWS service, except the ones under the iam: and organizations: prefixes. None of this makes NotAction inherently wrong. Paired with a tightly scoped Resource — not Resource: "*" — it can cleanly express "all S3 actions on this bucket except delete," which reads naturally and stays safely contained to one bucket regardless of which S3 actions AWS adds in the future. The trap is specifically the combination of NotAction, Effect: Allow, and a wildcard Resource together: that combination is what turns a seemingly narrow exclusion into an almost-unbounded grant. NotResource carries the identical risk in the other direction — Effect: Allow with a broad Action and a short NotResource list grants that action everywhere except the handful of resources named.

Production scenario

A platform team built an IAM role for a CI/CD pipeline and wrote what they believed was a safety-conscious policy: Allow, with NotAction excluding the IAM and Organizations namespaces, Resource set to *, reasoning that blocking identity and org management was the main risk to guard against. The pipeline ran for months without incident, which felt like validation. During a supply-chain security review, an engineer traced what the role could actually do and found it could read every secret in Secrets Manager, modify security group rules, decrypt data protected by every customer-managed KMS key the pipeline's principal was allowed to touch, and delete production S3 buckets outright — none of which the pipeline's actual job required. A compromised build step would have had nearly the same reach as a compromised administrator, just without IAM itself.

Common mistake

Treat NotAction plus Effect: Allow plus a wildcard Resource as a specific, nameable anti-pattern, not just "a policy that happens to be broad." The moment you see all three together, the correct instinct is to ask what the full action namespace looks like minus the excluded prefixes — not to trust that the exclusion implies safety. If a policy "only" excludes one or two service prefixes, assume it grants the rest of the account until you have actually reasoned through what remains.

Exam angle

Expect a question that shows a NotAction policy and asks whether a specific, unlisted action is permitted. Work it exactly like the checklist above: is this action under any excluded prefix? If not, and the Effect is Allow, it is granted — regardless of how dangerous that specific action is. The exam is testing whether you can mechanically evaluate NotAction rather than intuit "this looks restrictive so it must be fine."

Scene 08 — Production Trap Gallery

Six Ways This Actually Breaks

None of these are hypothetical shapes of failure — they are the recognizable pattern behind real incident reports, generalized. Each one traces back to a specific principle from this module. Read the setup, guess the fix before you get there, then check which rule from earlier would have caught it in review.

Roles vs. users

The key that outlived its repository's privacy

SetupA developer hardcoded an IAM user's access key into an application config file and pushed it to what they believed was a private repository.
AssumedThe repository's visibility setting was correct, and even if it briefly wasn't, no one would notice in time.
Actually happenedThe repo flipped public during a settings migration. A credential-scanning bot found the key in under ten minutes and began enumerating S3 buckets before internal monitoring caught it.
FixRotate and revoke immediately; migrate the app to assume a role instead of holding static credentials; add pre-commit secret scanning.
Principle: a long-lived key has no expiry working in your favor.
Policy types

"The bucket policy grants it" was not the whole story

SetupA team added a partner's account ID to a bucket policy as a Principal and considered the cross-account integration complete.
AssumedA resource-based grant is a resource-based grant — cross-account access should just work once the bucket policy says yes.
Actually happenedThe partner's calls failed with Access Denied. Their own identity-based policy also needed to explicitly allow the action; the bucket's generosity alone was not enough.
FixConfirmed with the partner's IAM team that their calling identity's policy also explicitly allowed the action before signing off on the integration.
Principle: resource-based access is necessary, not always sufficient, across accounts.
Evaluation logic

A Deny that forgot its own exception

SetupAn engineer wrote a Deny meant to block a risky action for everyone except one break-glass admin role, intending to add an exclusion for it.
AssumedThe intent was documented in a comment, so the exclusion would get added before the change shipped.
Actually happenedThe exclusion never made it into the policy itself. During an actual incident, the break-glass role hit the same Deny as everyone else — IAM evaluates what is written, not what was meant.
FixAdded an explicit principal exclusion to the Deny's condition and treated "intent in a comment" as incomplete work.
Principle: an explicit deny wins regardless of who is asking, unless the policy itself says otherwise.
Condition keys

An MFA requirement that automation can never satisfy

SetupA team added a bucket policy Deny requiring MFA for any delete action, following standard guidance for sensitive data.
AssumedThe policy would only ever affect human users clicking around in the console.
Actually happenedA nightly cleanup Lambda, running under a role that structurally never carries an MFA context, started failing every delete call it made.
FixScoped the Deny to exclude the specific automation role by principal, rather than applying it to every caller uniformly.
Principle: a condition-gated Deny applies to every principal touching the resource, human and machine alike.
NotResource

Excluding one bucket, exposing every other one

SetupA team wrote Effect: Allow, Action: s3:*, NotResource naming only their sensitive "legal-hold" bucket, intending to protect that one bucket.
AssumedExcluding the one sensitive bucket by name was enough to keep the role properly scoped.
Actually happenedThe role could act on every other bucket in the entire account, including an unrelated production backups bucket, because NotResource excluded only the named ARN, not "everything except the buckets this role should manage."
FixReplaced the exclusion with an explicit, positive Resource list naming only the buckets the role should actually touch.
Principle: NotResource, like NotAction, only restricts what it excludes — everything else in scope is still fully granted.
Groups

A trust policy that referenced an identity that cannot be assumed

SetupAn engineer wanted "anyone on the Platform team" to assume a new role, and added the Platform IAM group's ARN to the role's trust policy Principal field.
AssumedSince the group already listed the right people, referencing it directly would save maintaining a separate list.
Actually happenedEvery assumption attempt failed. IAM does not accept a group as a principal at all — the trust policy was invalid from the moment it was written.
FixListed individual user or role ARNs directly, and considered a dedicated team role that individuals assume instead.
Principle: a group is a policy-attachment container, not a principal — it cannot be assumed.

Scene 09 — Knowledge Check

Twelve Questions, Full Domain Range

Original, SCS-C03-style questions covering everything in this module. Answer each once — the explanation reveals immediately either way.

Score: 0 / 12
Question 01 of 12
When AWS evaluates multiple IAM policies that apply to a single request, which best describes the evaluation order?
This is the fixed, three-step order this entire module builds on: explicit deny beats everything, an explicit allow (if no deny fired) grants the request, and silence defaults to deny.
Question 02 of 12
Which AWS service issues the temporary security credentials returned when a role is assumed?
IAM defines the role and its trust policy, but AWS STS is the service that actually issues and expires the temporary access key, secret key, and session token.
Question 03 of 12
An application running on EC2 needs to write objects to S3. Per this module's guidance, what is the most appropriate way to grant that access?
An EC2 instance role issues temporary, auto-expiring credentials to the application with no static secret to leak or rotate — the default answer for compute-to-service access on this exam.
Question 04 of 12
A security engineer needs to grant a principal in Account B read access to an S3 bucket in Account A, without Account B assuming any role in Account A. Which policy type makes this possible on its own?
A resource-based policy is the only policy type here that can name an external account's principal directly and grant access, without that account needing to assume a role.
Question 05 of 12
A permission set is currently duplicated as inline policies across 14 roles. A security review needs to update that permission set consistently across all 14 going forward. What is the best long-term fix?
A customer-managed policy is a single reusable, versioned object — one edit updates every attached role at once, and AWS keeps prior versions for rollback. AWS managed policies cannot be edited to fit a custom scope, and this is not a resource-based access problem.
Question 06 of 12
A role has two managed policies attached: one grants ec2:*, the other has no mention of S3. A separate inline policy on the same role explicitly denies s3:DeleteBucket. The role calls s3:DeleteBucket. What happens?
All attached policies are evaluated together as one aggregate set. The explicit deny in the inline policy is found during step one and ends the evaluation immediately — precedence between policy types and "agreement" between policies are not how IAM works.
Question 07 of 12
A policy attaches a condition requiring aws:MultiFactorAuthPresent to be true on an Allow statement for a sensitive delete action. A request arrives from a session with no MFA present, and no Deny statement exists anywhere for this action. What is the result?
A failed condition on an Allow just means that Allow does not fire — it is not a deny. With no explicit deny and no matching explicit allow, the result is implicit deny, exactly like a request with no relevant policy at all.
Question 08 of 12
A policy statement reads: Effect: Allow, NotAction: ["iam:*"], Resource: "*". Which of the following best describes what this statement grants?
NotAction matches everything except the listed prefix. Combined with Allow and a wildcard Resource, that statement grants the entire AWS action namespace outside of IAM — a far larger grant than the single excluded prefix suggests.
Question 09 of 12
A policy grants Effect: Allow, Action: s3:*, NotResource: arn:aws:s3:::finance-reports/*. A request targets s3://finance-reports/q3.pdf specifically. Under this statement alone, what happens?
NotResource excludes the named ARN pattern from this statement's reach. The statement simply does not participate for that object — neither an allow nor a deny from this statement specifically; check the rest of the policy set for the real answer.
Question 10 of 12
A trust policy's Principal field is set to the ARN of an IAM group, intended to let every member of that group assume the role. What actually happens?
Groups are permission-attachment containers, not identities. They cannot appear in a Principal field and cannot be assumed — this configuration simply does not work as intended.
Question 11 of 12
A third-party, on-premises tool has no native support for assuming an AWS role and must use a long-lived IAM user access key. What is the most appropriate compensating control?
Access keys are not forbidden; the exam expects you to know the compensating control for the genuinely unavoidable case — scheduled rotation and active monitoring, not blanket prohibition or, worse, key sharing.
Question 12 of 12
An identity-based policy grants a role s3:GetObject with no conditions. A bucket policy on the target bucket contains a Deny for s3:GetObject that applies only when the request does not use TLS. The role's request arrives over HTTPS. What is the result?
The presence of a Deny statement does not automatically mean denial — its condition has to actually match. Here it does not, since the request is secure, so the Deny never fires, and the identity-based Allow is what decides the outcome.

Scene 11 — What's Next

Same Logic, One More Account

Every mechanic in this module was scoped to one account on purpose. You now know how a role gets its temporary credentials, which of the four policy types is the right tool for a given requirement, how to run the three-step evaluation order without guessing, how a condition changes meaning depending on which effect it rides on, and exactly how NotAction turns a short exclusion list into an enormous grant.

None of that changes in Module 3. What changes is the number of accounts involved. Cross-account trust policies, service control policies, resource control policies, and permission boundaries are not a new evaluation engine — they are additional layers that get folded into the same explicit-deny-then-explicit-allow-then-implicit-deny logic you just built into reflex. The two-policy exhibits get bigger. The stakes of an over-broad NotAction statement get bigger, because now it might reach across an account boundary instead of staying contained to one. But the underlying reasoning does not change: scan everything for a deny first, then for an allow, and never assume silence means yes.

If Scenes 03 through 07 felt solid by the end of this module, Module 3 is going to feel like more of the same skill applied at a larger radius — not a new one.
