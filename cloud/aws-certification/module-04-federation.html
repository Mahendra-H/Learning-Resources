    From policy mechanics to human identity

    Module 3 gave you the machinery: cross-account roles, service control policies, resource control policies, permission boundaries. All of it was mechanical — policy documents, trust relationships, guardrails wired between accounts. None of it, on its own, answered a much more human question: how does an actual person get in?

    That's what this module is about. This is where the policy-level controls you just spent three-plus hours mastering finally meet a real identity — an engineer badging into their laptop, authenticating once against a corporate directory, and walking away with scoped, temporary, expiring access across an entire AWS Organization, without a single long-lived access key ever touching their machine. Federation, IAM Identity Center, and AWS STS are the three pieces that make that possible, and Domain 4 (worth 20% of this exam — the single largest domain) leans on all three heavily.

    Core topics

    You've already spent five-plus years living inside OAuth 2.0, SAML, and Spring Security trust chains — so I'm not going to re-teach you what a signed assertion or a JWT is.     TOPIC 1 — FEDERATION FUNDAMENTALS

    Two standards, one AWS entry point: STS

    Think of it like a hotel that doesn't run its own passport office: it doesn't issue ID, but it absolutely knows how to check one at the front desk and hand over a room key. AWS plays the same role with identity — it never issues the assertion or token itself, but it knows exactly how to validate one at the door and hand back scoped, temporary access.

    AWS supports federated identity through exactly two standards, and — per the calibration in this module's intro — I'll keep the standards themselves brief, since you already know this territory:

    • SAML 2.0 — an identity provider (Okta, Azure AD, on-prem ADFS) authenticates the user and hands back a signed XML assertion asserting who they are and what attributes/groups they carry.
    • OIDC — a layer on top of OAuth 2.0. The identity provider (a public IdP like Google, or a workload identity provider like Cognito or EKS's OIDC endpoint) hands back a signed JWT, an ID token asserting identity claims.

    What's actually AWS-specific is where that assertion or token plugs into IAM. Neither SAML nor OIDC has any native concept of an "AWS role." AWS closes that gap with two purpose-built STS API calls:

    AWS-Specific Plumbing

    sts:AssumeRoleWithSAML takes the base64-encoded SAML assertion and a role ARN + SAML provider ARN, validates the assertion's signature against the IAM SAML identity provider resource you registered, and — if the trust policy's conditions match — issues temporary credentials. sts:AssumeRoleWithWebIdentity does the equivalent for an OIDC JWT: it validates the token's signature against the registered OIDC provider (or delegates that validation to Cognito Identity Pools) and issues temporary credentials the same way.

    Web identity federation vs. enterprise SAML federation

    The two paths solve different populations of caller:

    PathTypical IdPWho's authenticating
    Web/mobile identity federationCognito, Google, Facebook (OIDC)An end user of your product — often no corporate directory involved at all
    Enterprise SAML federationOkta, Azure AD, on-prem ADFSAn employee who already exists in a corporate directory
    Common Mistake

    Treating "federation" and "SAML" as synonyms out of habit. A huge share of modern federation — CI/CD pipelines, EKS pods, mobile apps — is OIDC, not SAML. If a scenario mentions a JWT, a workload identity token, or a provider like GitHub Actions or Cognito, the SAML-shaped answer is wrong regardless of how familiar it feels.

    Exam Angle

    The exam loves describing an identity-provider setup in a scenario and asking which STS call fits. The tell is always the provider type, not the use case wording: SAML IdP in the description → AssumeRoleWithSAML. OIDC/JWT-issuing provider (Cognito, Google, GitHub Actions OIDC, EKS service account) → AssumeRoleWithWebIdentity. We'll drill this explicitly in the exercise later in this module.

    Takeaway: the provider type — not the use case — decides the STS call; SAML always means AssumeRoleWithSAML, and any JWT-issuing OIDC provider always means AssumeRoleWithWebIdentity.

    Quick Check — Before You Continue

    A CI/CD pipeline authenticates using a token issued by GitHub Actions' built-in OIDC provider. Which STS call does it use?

    AssumeRoleWithWebIdentity — GitHub Actions issues a JWT, not a SAML assertion, so the OIDC-consuming call applies regardless of the "enterprise CI/CD" framing.

    IAM Identity Center
    TOPIC 2 — IAM IDENTITY CENTER

    AWS's own identity layer, sitting in front of Organizations

    This is where the real study time for this module goes, so let's be precise. IAM Identity Center (formerly AWS SSO) is AWS's own identity provider layer that sits in front of an AWS Organization, giving you one place to manage workforce access to every member account — and, optionally, to SAML-enabled cloud applications outside AWS entirely (Salesforce, Box, and similar). It can be backed by its own built-in directory, or connected to an external identity source: Azure AD / Entra ID, Okta, Google Workspace, or an on-prem Active Directory via AD Connector.

    Think of it as the piece that finally answers the question Module 3's cross-account roles couldn't: who is actually allowed to assume any of these roles, and how do they prove it once, centrally? Identity Center is that "once, centrally."

    Permission sets — the mechanism that actually provisions access

    A permission set is a named, reusable template of IAM policies (managed, customer-managed, or inline) that Identity Center provisions automatically as an actual IAM role into every member account you assign it to. You never hand-write the trust policy, never manually create the role in each account, and never manage a fleet of per-account SAML identity providers yourself — Identity Center's underlying service does all of that provisioning and keeps it in sync as accounts join or leave the assignment.

    Exam Angle

    This is exactly why the exam favors Identity Center as the AWS-recommended pattern over hand-rolling per-account SAML federation yourself: hand-rolled federation means manually registering a SAML IdP resource and writing a trust policy in every single account, one at a time, with no centralized lifecycle management. Permission sets collapse that into one definition, assigned centrally.

    Multi-account access from a single login

    Once a user authenticates to Identity Center — against its own directory or your external IdP behind the scenes — they land on the AWS access portal and see every account/permission-set combination they've been assigned. Selecting one triggers an AssumeRole under the hood into that account's provisioned role, handing them temporary credentials for exactly that scope. One authentication event, arbitrarily many downstream account/role combinations, zero long-lived per-account credentials anywhere in the chain.

    Production Scenario

    A 40-person platform team spans a landing zone with 30+ member accounts (dev, staging, prod × multiple business units). Before Identity Center: onboarding a new engineer meant manually federating them into every account they'd touch, or worse, minting IAM users with long-lived keys per account. With Identity Center: the engineer is added to two or three permission-set assignments — say, ReadOnlyAccess across all dev/staging accounts and PowerUserAccess scoped to their one owned service's prod account — and every downstream role, in every account, provisions itself automatically. Offboarding is a single deactivation, not a 30-account cleanup sweep.

    How this relates to Organizations and the landing zone

    Identity Center has a hard prerequisite: it requires an AWS Organization to exist, because permission-set assignments are made against Organizations' account structure — you're assigning "this permission set, to this user or group, in these accounts," and Identity Center needs Organizations' account inventory to resolve that. This ties it directly back to the multi-account architecture thread from Module 3 and the landing-zone concepts from Module 1: Identity Center is the identity plane sitting on top of the account structure those modules established.

    If you're picturing this as "just SSO," widen the frame a little. In an enterprise landing zone, Identity Center isn't a login convenience layer bolted on afterward — it's usually the very first thing provisioned alongside Organizations itself, because every downstream account's access model gets designed around permission sets from day one. It's less "add SSO later" and more "this is the access control plane."

    Federation flow: standard vs. Identity Center

    AspectHand-rolled SAML federationIAM Identity Center
    IdP registrationManual, per account (IAM SAML provider resource)Centralized, once
    Role provisioningManual, per accountAutomatic via permission sets

    Lifecycle managementManual cleanup per accountManaged centrally
    Requires OrganizationsNoYes

    Takeaway: a permission set is the reusable definition; Identity Center's job is provisioning it as a real IAM role, automatically, everywhere it's assigned.

    TOPIC 3 — STS TEMPORARY CREDENTIALS

    Three API calls, one shared mechanism

    Think of STS as a hotel key-card machine: it never checks who you are itself, but once someone else has (your IdP, or an already-trusted IAM principal), it hands over a key card that opens exactly the doors it was told to, and stops working the moment its clock runs out.

    Everything in this module funnels through AWS Security Token Service. There are three calls worth being precise about, because the exam distinguishes them by what identity each one trusts as input:

    CallTrusts as inputTypical caller
    AssumeRoleAn existing IAM principal (user or role) in the same or a trusted AWS accountCross-account access, Identity Center's internal role assumption
    AssumeRoleWithSAMLA signed SAML 2.0 assertion from a registered SAML IdPEnterprise workforce federation (Okta, Azure AD, ADFS)
    AssumeRoleWithWebIdentityA signed OIDC JWT from a registered OIDC providerMobile/web apps (Cognito, Google), CI/CD workload identity (GitHub Actions, EKS)

    What's actually inside a temporary credential

    A long-lived IAM user access key is two values: an access key ID and a secret access key. A temporary credential from STS is three values, and all three are required together: an access key ID, a secret access key, and a session token. Every signed request made with temporary credentials must include that session token — it's what lets AWS validate that the credential came from a legitimate, still-live STS session rather than a standalone long-lived key, and it's what AWS checks against the session's expiry and any session policies attached at assumption time.

    Session duration: the least-privilege lever

    Every IAM role has a maximum session duration configurable from 1 hour up to 12 hours (default 1 hour if unset). The caller can request any duration up to that configured maximum via the DurationSeconds parameter; STS will not honor a request for longer than the role's configured ceiling.

    Exam Angle

    A longer session duration is not automatically "safer" or even necessarily more convenient once you weigh the least-privilege cost: a 12-hour credential that leaks (logged accidentally, cached in a CI artifact, left in a shell history) gives an attacker a 12-hour window, versus a 1-hour credential's much narrower blast radius. The exam expects you to default toward the shortest duration that the workflow actually needs, not the longest one available.

    Production Scenario

    A federated engineer signs in through Identity Center and lands with a 4-hour session (the permission set's configured max). Mid-shift, a script they're running needs to call a Lambda that itself assumes a second role to reach into another account. That Lambda's assumed session — because it's chained on top of the engineer's already-temporary credentials — is capped at 1 hour, regardless of what either role's own configuration says. If that Lambda has a long-running job scheduled to take 90 minutes, it will fail mid-execution when the chained session expires — a very real production gotcha, not just an exam trivia point.

    Common Mistake

    Manually stripping or forgetting the session token when hand-constructing a signed request from temporary credentials (common when scripting outside the SDK, which normally handles this for you). Without it, the request fails outright — a temporary credential's access key ID and secret key alone are not valid for signing, unlike a long-lived IAM user key pair.

    Takeaway: a temporary credential is three values working together, not two — and a chained session's 1-hour cap is fixed regardless of any role's own configured maximum.

    TOPIC 4 — ASSUMEROLE CHAINS

    Assuming a role with a role you already assumed

    Role chaining is simple to state and easy to get wrong operationally: you assume Role A, and then — using Role A's own temporary credentials, not your original identity — you call AssumeRole again to assume Role B. That second hop is the "chain."

    You already saw the number that matters in the timeline above: a chained session is capped at 1 hour maximum, no matter what either role's own MaxSessionDuration is configured to. If Role A allows 12 hours and Role B allows 12 hours, the chained session assuming B from A's credentials still cannot exceed 1 hour. This is a deliberate, hard-coded ceiling in STS — not a configurable setting you can raise.

    Why the exam tests this limit specifically

    It's one of the most concrete, unambiguous facts in this whole domain — there's no interpretation required, just a number to know — which makes it a favorite for scenario questions that describe a multi-hop automation pipeline and ask "how long will this session actually last?" The trap is assuming the answer is whatever the more generous of the two roles' configured maximums is. It isn't. It's 1 hour, full stop, the moment a second hop is involved.

    Common Mistake

    Designing a cross-account automation pipeline (Account A → assume Role in Account B → assume Role in Account C) and configuring both roles for a generous 8-hour MaxSessionDuration, assuming the pipeline gets 8 hours to run. It gets 1 hour from the moment the second assumption happens, because that second hop is chained on top of the first.

    Production Scenario

    A data pipeline in a shared-services account assumes a role into a partner account to read from an S3 bucket, then — from that assumed session — assumes a third role into a downstream analytics account to write results. The whole job is expected to take 2 hours. It fails silently at the 1-hour mark on the second hop because nobody accounted for the chained-session cap; the fix is redesigning the flow so the long-running work happens under the first assumption (direct, up to 12h) rather than nesting a second hop inside it.

    Exam Angle

    If a question describes any scenario where credentials from one AssumeRole call are used to make a second AssumeRole call, treat "1 hour" as the answer to any session-duration question about that second hop — regardless of what duration values appear elsewhere in the question.

    Takeaway: chaining costs you a hard 1-hour ceiling — design long-running cross-account work to happen under the first assumption, not nested inside a second one.

    Quick Check — Before You Continue

    Role A allows a 10-hour session and Role B allows a 6-hour session. A caller assumes A, then uses A's credentials to assume B. What's the maximum duration of that second session?

    1 hour. Neither role's individually configured maximum matters once the assumption is chained — the 1-hour ceiling applies regardless of how generous either role's own setting is.

    TOPIC 5 — EXTERNAL ID FOR THIRD-PARTY ACCESS

    Closing the confused deputy gap

    Here's the concrete version of the confused deputy problem, stated the way it actually shows up in production: a third party — a SaaS monitoring vendor, an external auditor — needs read access into your account. You create a role and hand them its ARN so their system can call AssumeRole into it. So far, straightforward cross-account access.

    The problem: that vendor almost certainly serves other customers too, from the same multi-tenant system. If that system's trust policy on your role only restricts who the vendor's account is (the principal), it has no way to distinguish "assume this role on behalf of Customer A" from "assume this role on behalf of Customer B" — both requests originate from the same vendor AWS account. If another one of the vendor's customers can guess or obtain your role ARN (role ARNs aren't secret — they often appear in IAM console screenshots, support tickets, or logs), they could potentially trick the vendor's own system into assuming a role in your account instead of theirs, because the vendor's system is the "confused deputy" acting on a request it can't fully verify belongs to the right tenant.

    The fix: sts:ExternalId

    An external ID is a string — a shared secret unique to your specific engagement with that third party — added as a condition in your role's trust policy: "Condition": {"StringEquals": {"sts:ExternalId": "your-unique-value"}}. The third party's system must now present that exact value on every AssumeRole call. Since each of the vendor's customers gets a different external ID value tied to their own engagement, even if another customer somehow obtains your role ARN, their AssumeRole call won't carry your external ID — and the assumption fails.

    Exam Angle

    The exam frequently tests a subtle distinction: external ID is not authentication and is not a secret credential on its own — it's a confused-deputy mitigation layered on top of the trust policy's principal restriction, not a replacement for it. The principal condition still must correctly scope which AWS account can even attempt the assumption; external ID only prevents that already-correct principal's system from being tricked into acting on the wrong tenant's behalf.

    Before / after: click each card

    ⚠ Without External ID

    Vendor's multi-tenant system (shared across all their customers)
    Trust policy: Principal = Vendor's AWS account only
    Any customer who obtains your role ARN can trigger an assumption into your account

    The trust policy correctly restricts the principal to the vendor's AWS account — that part is fine. But it has no way to verify which of the vendor's customers is behind a given request. If Customer B's environment (accidentally or maliciously) references your role ARN instead of their own, the vendor's system — trusted by your account purely on the basis of its account ID — will happily assume into your account on Customer B's behalf.

    ✓ With External ID

    Vendor's multi-tenant system, same shared account
    Trust policy: Principal = Vendor's account AND sts:ExternalId = your unique value
    Only requests carrying your specific external ID succeed

    The vendor's system now must supply your unique external ID alongside the principal on every assumption attempt. Because each customer's engagement gets a distinct external ID, Customer B's request — even referencing your role ARN — carries Customer B's external ID, not yours, and the trust policy condition fails the assumption before it ever succeeds.

    Worked Example — Trust Policy

    A SaaS monitoring vendor (account 111122223333) requests read-only access to your account for dashboarding. Your role's trust policy:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "monitoring-vendor-acct-9f21c7"
      }
    }
  }]
}

    The vendor's monitoring system stores monitoring-vendor-acct-9f21c7 against your specific customer record and supplies it on every AssumeRole call targeting your account — a value no other customer of theirs possesses.

    Common Mistake

    Treating the external ID itself as sensitive the way a password is, and rotating it frequently or trying to keep it fully secret from the vendor. It's meant to be shared with (and stored by) the third party as part of onboarding — its job is uniqueness per engagement, not secrecy from the party you're sharing it with.

    Takeaway: external ID doesn't replace the principal restriction — it stops that already-correct principal's system from being tricked into acting on the wrong tenant's behalf.

    INTERACTIVE — FEDERATION FLOW

    The full path, step by step

    Click any step below to expand what's actually happening at that hop — this is the same flow whether the identity provider is a SAML IdP or an OIDC provider; only the assertion/token format and the STS call differ.

    1

    User authenticates against the identity provider

    Corporate directory (Okta, Azure AD, ADFS) or public/workload OIDC provider (Cognito, Google, GitHub Actions).

    This step is entirely outside AWS. The IdP validates credentials (password, MFA, device posture — whatever that IdP enforces) using its own mechanisms. AWS has no visibility into this step at all; it only ever sees the output.

    2

    IdP issues a signed assertion or token

    SAML: a signed XML assertion. OIDC: a signed JWT ID token.

    Both are cryptographically signed by the IdP's private key. AWS will later validate that signature against the public key/metadata registered when you created the IAM SAML or OIDC identity provider resource — this is what lets AWS trust the assertion without ever talking to the IdP directly at request time.

    3

    Client calls the matching STS API

    AssumeRoleWithSAML for a SAML assertion, or AssumeRoleWithWebIdentity for an OIDC JWT — plus the target role ARN.

    STS validates the signature, checks the role's trust policy conditions (audience, subject, any custom conditions like external ID), and — only if everything matches — proceeds to the next step.

    4

    STS issues temporary credentials

    Access key ID + secret access key + session token, valid up to the role's configured max session duration.

    No IAM user, no long-lived key pair was ever created or touched anywhere in this flow. The identity that "exists" in AWS for the duration of this session is entirely the assumed role, scoped by whatever permission policy is attached to it.

    5

    Client signs AWS API calls with the temporary credentials

    Every request includes the session token; access is scoped to exactly the assumed role's permissions until expiry.

    CloudTrail logs every one of these calls under the assumed role's session identity — visible as AssumedRole in the event, with the session name tying individual actions back to the specific federated session that made them.

    EXERCISE — WHICH ASSUMEROLE CALL?

    Eight identity setups. Pick the right STS call.

    Read each scenario, decide which STS API call and trust policy elements fit, then click to reveal the reasoning.

    Scenario 1

    A global enterprise uses Azure AD as its corporate directory. Employees need to access AWS resources under their existing corporate identity, with group-based role mapping.

    ✓ AssumeRoleWithSAML (or IAM Identity Center with Azure AD as the external identity source)

    Azure AD is a SAML 2.0 identity provider in this context. If Identity Center is in play, it handles the SAML exchange internally; if federating directly, the client calls AssumeRoleWithSAML with the assertion Azure AD issued.

    Scenario 2

    A consumer mobile app lets users sign in with their Google account, then needs to read/write to a DynamoDB table scoped per-user.

    ✓ AssumeRoleWithWebIdentity (typically via Cognito Identity Pools)

    Google is an OIDC provider issuing a JWT. Cognito Identity Pools wrap this exchange and call AssumeRoleWithWebIdentity on the mobile client's behalf, commonly with per-user scoping via policy variables like cognito-identity.amazonaws.com:sub.

    Scenario 3

    A CI/CD pipeline running in GitHub Actions needs to deploy to an AWS account without storing any long-lived AWS access keys as repo secrets.

    ✓ AssumeRoleWithWebIdentity

    GitHub Actions exposes an OIDC token per workflow run. Registering GitHub's OIDC provider in IAM and writing a trust policy conditioned on the repo/branch subject claim lets the pipeline call AssumeRoleWithWebIdentity with zero stored credentials.

    Scenario 4

    A Lambda function, already executing under its own IAM execution role, needs to reach into a partner account to read from an S3 bucket there.

    ✓ AssumeRole (this is role chaining if the Lambda's own execution role was itself assumed via another mechanism)

    The Lambda already holds an IAM principal (its execution role). Reaching cross-account from an existing IAM principal — not a SAML/OIDC assertion — is the plain AssumeRole call. Remember: if this Lambda's own role was itself the product of an earlier assumption, the resulting session inherits the 1-hour chained cap.

    Scenario 5

    An on-prem Active Directory environment, federated via ADFS, needs workforce access to 15 AWS accounts in an Organization, with centralized lifecycle management.

    ✓ IAM Identity Center, with ADFS/AD as the external identity source (SAML under the hood)

    ADFS speaks SAML, but the "15 accounts, centrally managed" requirement is the giveaway for Identity Center over hand-rolled per-account AssumeRoleWithSAML federation — permission sets solve the multi-account provisioning problem that raw SAML federation doesn't.

    Scenario 6

    A third-party SaaS security scanner needs read-only access into your account to run compliance checks, and you're worried about the confused deputy problem given they serve many customers.

    ✓ AssumeRole, with an sts:ExternalId condition in the trust policy

    This is a same-mechanism-as-cross-account (AssumeRole) case, but the multi-tenant confused-deputy risk means the trust policy must include a unique external ID condition alongside the principal restriction.

    Scenario 7

    An EKS pod needs to call S3 directly using a Kubernetes service account, without node-level IAM credentials being shared across all pods on that node.

    ✓ AssumeRoleWithWebIdentity (IAM Roles for Service Accounts / IRSA)

    EKS's built-in OIDC provider issues a token per service account. IRSA registers that OIDC provider in IAM and maps a service account to a role, resulting in AssumeRoleWithWebIdentity calls scoped per-pod rather than per-node.

    Scenario 8

    A batch job assumes Role A in a shared-services account, and — using Role A's resulting credentials — needs to assume Role B in a downstream analytics account for a job expected to run 3 hours.

    ✓ AssumeRole (chained) — but the 3-hour job will fail; redesign needed

    This is textbook role chaining, capped at 1 hour regardless of either role's configured maximum. A 3-hour job structured this way is a design flaw, not just an API choice — the long-running work needs to happen under a direct (non-chained) assumption instead.

    PRODUCTION TRAP GALLERY

    Six ways this goes wrong in real environments

    Not exam trivia — these are the shapes of real incidents and real outages.

    🔓

    The missing external ID

    A third-party monitoring vendor's trust policy was scoped only to their AWS account principal. Another one of the vendor's customers, testing their own integration, accidentally referenced the wrong role ARN — which happened to belong to a different customer entirely — and the vendor's system happily assumed into the wrong account. No external ID meant nothing stopped it.

    📛

    The over-broad permission set

    A permission set meant for "read-only dashboard access" was built from AWS's PowerUserAccess managed policy because it was faster than writing a scoped custom policy, then assigned across 20+ accounts. Every engineer with dashboard access could now also modify most resources in every one of those accounts.

    ⏱️

    The chained-session pipeline that hit its cap mid-run

    A data pipeline chained two role assumptions to reach a downstream account, expecting the job's full 4-hour runtime to be covered. It silently failed at the 1-hour chained-session cap, mid-transfer, with partial data written and no alert configured for STS expiry-related failures.

    🗝️

    Long-lived keys kept "just in case" alongside federation

    A team fully migrated to Identity Center for day-to-day access but left a handful of IAM users with long-lived access keys active "for emergencies." One of those keys, unused and unrotated for over a year, was the credential that ultimately leaked in a public repo — the exact long-lived-credential risk federation was supposed to eliminate.

    🌐

    Wrong STS call for the IdP type

    An engineer configured AssumeRoleWithSAML for a workload that was actually authenticating via an OIDC JWT from a CI system, because "SAML" and "federation" had become synonymous in the team's vocabulary. The trust policy's condition keys were mismatched to the wrong assertion format and every assumption failed until someone traced it back to the IdP type itself.

    🧩

    Orphaned permission set assignments after an org restructure

    When a business unit was carved out into its own sub-OU, several permission set assignments referencing the old account structure were never cleaned up. Contractors who should have lost access when their engagement ended retained a live, provisioned role in accounts nobody was actively reviewing anymore.

    Question 10 of 11
    From a least-privilege standpoint, what is the main risk of defaulting every role to a 12-hour MaxSessionDuration "for convenience"?
    Longer session durations widen the blast radius of any credential exposure — the same session token remains valid and usable for the full duration, regardless of how it was obtained by an attacker.
    Question 11 of 11
    A company's on-prem ADFS environment issues SAML assertions for workforce access to a single AWS account, with no plans for multi-account expansion. Which STS call directly consumes that assertion?
    ADFS issues a SAML 2.0 assertion; the client calls AssumeRoleWithSAML directly with that assertion and the target role ARN. Identity Center becomes the better choice once multi-account scale enters the picture, but isn't required here.
    DISCUSSION — FREQUENTLY ASKED

    Questions this module tends to raise

    🧑‍💻 You ask ›I already know SAML and OIDC cold from my Spring Security work. What's actually AWS-specific here that I don't already know?
    🛡️ Your MentorEverything past the assertion or token itself. The standards don't change — a SAML assertion is a SAML assertion whether it's headed for AWS or your own Spring Security resource server. What's new is: the IAM SAML/OIDC identity provider resource you register to hold the trust relationship, the two purpose-built STS calls (AssumeRoleWithSAML / AssumeRoleWithWebIdentity) that consume the assertion or token, the trust-policy condition syntax those calls check against, session duration mechanics including the chained-session cap, and Identity Center's permission-set abstraction on top of all of it. None of that exists in generic SAML/OIDC — it's the AWS-side plumbing, and it's what this module spent its depth on.
    🧑‍💻 You ask ›Is IAM Identity Center basically just "AWS SSO with a new name," or did something actually change?
    🛡️ Your MentorFunctionally, yes — it's the renamed, expanded successor to AWS SSO, and if you've used AWS SSO before, the mental model transfers directly. For exam purposes, always use "IAM Identity Center" — SCS-C03 questions will use the current name.
    🧑‍💻 You ask ›Can I just always use AssumeRole for everything and skip the SAML/WebIdentity variants?
    🛡️ Your MentorNo — AssumeRole only works when the caller already holds an IAM principal (a user or role) in an account trusted by the target role's trust policy. A SAML assertion or OIDC JWT isn't an IAM principal; STS needs the SAML- or WebIdentity-specific call to validate that external assertion's signature and translate it into a session. They're not interchangeable.
    🧑‍💻 You ask ›Does the 1-hour chained session cap apply to Identity Center logins too, since a user's console session technically involves an AssumeRole under the hood?
    🛡️ Your MentorNo — the Identity Center login itself is a direct assumption (the permission set's configured max applies, up to 12 hours), not a chain. The cap only bites once a session that was itself obtained via AssumeRole is used to call AssumeRole again for a second hop — that's specifically what "chained" means.
    🧑‍💻 You ask ›If external ID isn't secret, what actually stops someone malicious from just guessing it?
    🛡️ Your MentorIt should still be treated as not-easily-guessable — a long, random, unique string, not "customer-123." It's shared with the specific third party as part of onboarding rather than published publicly, and combined with the principal restriction, an attacker would need both the correct account principal and the correct external ID string. It's a defense-in-depth layer, not a public value, just not one relied on as the sole line of defense the way a password would be.
    🧑‍💻 You ask ›Why would anyone still hand-roll per-account SAML federation instead of using Identity Center?
    🛡️ Your MentorMostly single-account setups, or environments not using AWS Organizations at all (Identity Center requires it). Some legacy environments predate Identity Center's maturity and haven't migrated. But for any greenfield multi-account workforce access design today, the exam — and honestly, real architecture reviews — expect Identity Center as the default answer.
    🧑‍💻 You ask ›What's the practical difference between session duration and the role's trust policy conditions, for exam purposes?
    🛡️ Your MentorTrust policy conditions (principal, external ID, SAML/OIDC audience and subject claims) determine whether the assumption is allowed to happen at all. Session duration determines how long the resulting credential remains valid once it's already been issued. They're evaluated at completely different points — conditions at assumption time, duration as a property of the already-granted session — and exam questions sometimes blend them to see if you keep the two straight.
