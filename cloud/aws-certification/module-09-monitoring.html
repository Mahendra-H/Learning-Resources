SCS-C03 · Module 09 · Monitoring & Logging for Detection

Module Contents

Domain Shift · Data Protection → Detection

You've locked the doors. Now you have to watch them.

Modules 1 through 8 were about making sure your identity boundaries held, your network perimeter was sound, and your data stayed encrypted end to end. All of that assumed something worth stating plainly: eventually, you need to know whether those protections actually held up under real conditions — not just at design time, but every single day something touches your environment.

That's what this module is about. It's not glamorous. Nobody puts "configured CloudTrail organization trails" on a highlight reel. But it is foundational, because every detection service you'll meet in Module 10 — GuardDuty, Security Hub, Macie's findings pipeline — is only as good as the data feeding it. Detect nothing, and the smartest anomaly-detection engine in the world has nothing to reason about. This module builds the pipes. Module 10 is what watches what flows through them.

This is also where two threads from earlier in the course stop being abstract and become an actual build: shared responsibility — logging is unambiguously your job, not AWS's — and multi-account architecture, first introduced back in Module 3's SCP discussion, which finally gets a concrete, testable payoff here in the form of a centralized logging account.

Concept 1 of 6

AWS CloudTrail: the record of who did what

CloudTrail is AWS's API activity ledger. Nearly every action against an AWS API — from the console, CLI, SDK, or another AWS service acting on your behalf — gets recorded as an event: who called it, when, from where, what parameters were used, and whether it succeeded. If Config answers "what does this look like right now," CloudTrail answers "who made it look that way." Keep that distinction sharp; the exam leans on it constantly.

CloudTrail events come in three flavors, and knowing which is which is the actual tested skill:

Management Events

Control-plane operations — creating an IAM role, modifying a security group, launching an EC2 instance. Enabled by default on the trail you create, and this is where the vast majority of "who changed this" investigations start. Low volume relative to data events, so cost is rarely the concern here.

Data Events

Object- and resource-level operations — an S3 GetObject or PutObject call, a Lambda Invoke. These are opt-in for a reason: an active S3 bucket or high-throughput Lambda function can generate an enormous volume of data events, and that volume translates directly into cost. The exam consistently frames enabling data events as a deliberate scoping decision — you turn them on for the specific buckets or functions where object-level visibility genuinely matters (say, a bucket holding regulated data), not blanket-enabled across every resource in the account.

Insights Events

CloudTrail Insights analyzes your management event volume for unusual patterns — a spike in failed IAM calls, an abnormal burst of resource creation — and automatically generates findings when it detects something statistically off from your account's normal baseline. It's anomaly detection layered on top of the activity log itself, not a separate logging mechanism.

Production Scenario

Picture a security team investigating a mysteriously deleted S3 object in a compliance-archive bucket. If that bucket never had data events enabled, CloudTrail has no record of the DeleteObject call at all — no matter how carefully management events were configured. This is precisely why the scoping decision above isn't academic: it determines, in advance, whether an investigation like this is even answerable.

Organization trails: one trail, every account

In a single-account world, you create a trail, point it at an S3 bucket, and you're done. Real environments are never single-account — Module 3 already established that Organizations and multi-account design are the default, not the exception. An organization trail is created once, in the management account, and automatically applies to every existing and future account in the organization — no per-account setup, no risk of someone spinning up a new account and forgetting to enable logging in it.

Every member account's events get delivered into a single centralized S3 bucket (owned by whichever account you designate — typically the dedicated log-archive account this module builds toward). This is the AWS-recommended pattern for exactly the reason it sounds like: consistency. Per-account trails mean per-account configuration drift, and configuration drift in logging is the kind of gap that only gets discovered during an incident, which is the worst possible time to discover it.

Exam Angle

If a scenario describes a multi-account organization and asks for the most operationally sound way to ensure logging coverage across all accounts including future ones, the organization trail is almost always the intended answer over "configure a trail in each account."

Log file integrity validation: proving nothing was touched

A log an attacker can quietly edit isn't evidence — it's a suggestion. Log file integrity validation is CloudTrail's answer to that problem, and the course plan flags it explicitly as a point the exam returns to repeatedly, so we're going to walk through the actual mechanics rather than just naming the feature.

When enabled, CloudTrail periodically (roughly every hour) writes a digest file alongside your log files in S3. Each digest file contains a list of the log files delivered in that period, along with their SHA-256 hashes — plus, critically, the hash of the previous digest file. That last part is what makes this a hash chain: each digest cryptographically references the one before it, so the digests themselves form an unbroken, tamper-evident sequence stretching back to when validation was enabled.

Digest #1

The first digest file in the chain has no predecessor, so its "previous digest hash" field is null. It lists the log files delivered in its window along with each file's SHA-256 hash.

Digest #2

Contains the SHA-256 hash of Digest #1 in full. If a single byte of Digest #1 changes after the fact, recomputing its hash produces a different value than what's stored here — the mismatch is immediately detectable.

Digest #3

Same pattern, one link further down the chain. Validation walks this chain from the most recent digest backward, so tampering with any digest at any point in history breaks the chain from that point forward.

Log File(s)

Each individual log file's SHA-256 hash is recorded inside its corresponding digest file. To validate a specific log file, you recompute its hash and compare it against the value stored in the digest — if they don't match, that log file was altered after delivery.

Put concretely: to prove a specific log file wasn't altered, you use the CLI (aws cloudtrail validate-logs) to walk the digest chain from the current digest backward to the one covering your file, recomputing hashes at each link. If every hash matches what's recorded, both the log file and every digest in the chain are provably intact. If even one byte was changed anywhere — in a log file or a digest itself — the mismatch surfaces immediately, and you know precisely where the chain broke.

Here's the framing that makes this stick: integrity validation doesn't prevent tampering — it makes tampering detectable. Someone with sufficient permissions can still delete or edit a log file in S3. What they can't do is make that edit invisible, because they'd also have to recompute and rewrite every digest hash forward from that point in a way that still validates — and they'd need access to CloudTrail's own signing process to do that undetected. That's the actual security property: not prevention, but "if this was tampered with, we will know."

Exam Angle

Expect the exam to test whether you know what integrity validation actually proves (tamper-evidence via SHA-256 hash chaining across digest files) rather than a vague "it makes logs secure." Also expect the trap answer "encrypts your log files" — encryption and integrity validation are different properties; KMS encryption (Module 7) protects confidentiality, digest hash chaining protects integrity.

Concept 2 of 6

CloudWatch Logs: where activity becomes alertable

CloudTrail tells you what happened. CloudWatch Logs is where raw log data becomes something you can act on in near-real-time. Structurally, a log group is a named container (often mapped to an application, a Lambda function, or — relevant here — a CloudTrail trail configured to also deliver into CloudWatch Logs), and within it, log streams hold the actual sequences of log events from a given source. Retention is configured per log group, from one day up to indefinite — and it's worth noting explicitly that the default is "never expire," which quietly becomes a cost problem if nobody sets a policy.

The feature that matters most for detection is metric filters: you define a pattern to search for within incoming log events (say, "ConsoleLogin" "Failed authentication"), and every time that pattern matches, CloudWatch increments a custom metric. That metric can then trigger a CloudWatch Alarm — which is the practical bridge into Module 10's detection services. CloudTrail and CloudWatch Logs capture; metric filters translate a pattern in that raw text into a number; alarms and detection services act on the number.

Subscription Filters

Where metric filters turn patterns into metrics, subscription filters stream matching (or all) log events, in near-real-time, to another destination — typically Kinesis Data Streams or a Lambda function — for custom processing pipelines. This is meaningfully different from CloudTrail's own batch-style delivery to S3, which arrives in periodic chunks rather than a continuous stream. If a scenario calls for near-real-time reaction to log content rather than periodic batch analysis, subscription filters are the mechanism, not S3 delivery.

Log Event Arrives→ Metric Filter Matches Pattern→ CloudWatch Metric Increments→ Alarm Fires

Concept 3 of 6

VPC Flow Logs: metadata, never payload

Everything covered so far operates at the application or API layer. VPC Flow Logs is the network layer's contribution to this module — and the single most important fact about it is what it does not capture: packet contents. Flow Logs record traffic metadata only — source and destination IP, source and destination port, protocol, byte and packet counts, and whether the traffic was accepted or rejected — for traffic at an ENI, subnet, or entire VPC level.

That distinction matters because it defines what Flow Logs can and can't answer. It can tell you a specific instance rejected inbound traffic from an unfamiliar IP on port 22 at a specific timestamp — invaluable for reconstructing a network-layer picture of an incident. It cannot tell you what was inside that traffic, because it was never designed to. That's application-layer visibility, and it's what CloudTrail (API calls) and CloudWatch Logs (application logs) are for. Flow Logs complements those layers; it doesn't replace or substitute for either.

Destinations

Flow Logs can be delivered to S3 or CloudWatch Logs (a third option, Kinesis Data Firehose, exists for advanced streaming pipelines). S3 is the natural fit for long-term, lower-cost retention and later analysis with Athena — the pattern you'll want for compliance-driven investigations that may happen months later. CloudWatch Logs is the fit when you want metric filters and alarms directly on flow data — for example, alerting on a spike in rejected traffic to a specific security-critical subnet. The choice mirrors the same batch-vs-alertable trade-off already introduced with CloudTrail and CloudWatch Logs.

ENI / Subnet / VPC→ Flow Log Record (metadata only)→ S3or CloudWatch Logs
Exam Angle

Any answer choice implying Flow Logs reveal packet contents, payload data, or the actual content of a request is always wrong — that's the most consistently tested trap for this topic. Flow Logs are metadata about the fact that traffic occurred, never what the traffic contained.

Concept 4 of 6

AWS Config: what did this look like, at any point in time

This is the scene to hold CloudTrail right next to, because the exam loves to blur the two together. CloudTrail's question is who did what — it's an activity log. Config's question is entirely different: what did this resource's configuration look like, at any given point in time — it's a configuration state tracker.

When Config is enabled, it records a configuration item — a point-in-time snapshot of a resource's configuration attributes and relationships — every time that resource changes. String those configuration items together over time and you get configuration history: a timeline you can query to answer "what were this security group's inbound rules last Tuesday at 3pm," independent of which specific API call produced that state. Notice what that question does not require: you don't need to know who made the change or which API call did it — Config answers the "what" without needing the "who."

Production Scenario

A security group was found wide open to 0.0.0.0/0 on port 3389 during an audit. CloudTrail can tell you which principal made the API call that changed it and when. Config can independently confirm exactly what the rule set looked like before and after that change — useful both to verify CloudTrail's account of events and in the (rarer but tested) case where the relevant CloudTrail events have aged out of retention but Config history hasn't.

Config Rules build on this foundation: they're the mechanism for continuously evaluating whether a resource's current configuration matches a desired baseline — for example, "is this S3 bucket's public access block enabled" or "does this security group avoid unrestricted SSH." A rule evaluates on a schedule or in response to configuration changes and marks resources compliant or non-compliant. We're only previewing the concept at this level here — full compliance-automation depth, including remediation actions and organization-wide rule deployment, is Module 12–13 territory. For this module, just anchor the idea: Config Rules are what turns "we can see configuration history" into "we get told automatically when configuration drifts from policy."

Resource Changes→ Configuration Item Recorded→ Configuration History→ Config Rule Evaluates Compliance

One-sentence takeaway worth locking in: if the question is "who did it," reach for CloudTrail; if the question is "what did it look like," reach for Config. Almost every CloudTrail-vs-Config trap on this exam collapses once you translate the question into one of those two verbs first.

Concept 5 of 6 · Architectural Centerpiece

The centralized logging account: multi-account thinking, made concrete

Module 3 introduced Service Control Policies and the idea that a multi-account org isn't just an organizational nicety — it's a security control surface. This is where that idea earns its keep. The pattern: a dedicated, tightly access-controlled log-archive account, separate from every account that actually generates workload logs, receiving CloudTrail, Config, and VPC Flow Logs data from all of them.

The reasoning is a single sentence, but it's the one you need to be able to produce on demand: it limits blast radius. If a workload account is compromised, an attacker operating inside it should not be able to reach into that same account's own audit trail and delete the evidence of what they did. Centralizing logs into a separate account, with its own restrictive access policy, means compromising a workload account doesn't hand an attacker the ability to also erase the record of that compromise.

Workload Account A → Archive

CloudTrail (via the organization trail), AWS Config, and VPC Flow Logs are each configured to deliver into the log-archive account's S3 bucket rather than a bucket inside Account A itself. Account A's own IAM principals have no delete permission on that destination bucket.

Workload Account B → Archive

Same delivery pattern — the point of centralizing is that every workload account, regardless of what it runs, follows the identical delivery path into the same archive, so there's one place to secure rather than N places to audit for drift.

Workload Account C → Archive

Even an account fully compromised at the IAM level cannot reach into the archive account to tamper with or delete its own historical logs — that permission boundary lives entirely outside the compromised account.

Log-Archive Account mechanics

The destination S3 bucket carries a bucket policy that explicitly allows the CloudTrail/Config/Flow Logs service principals from each member account's organization to write (PutObject), while denying delete and overwrite from everyone else — including, notably, principals from the workload accounts themselves. If the bucket is encrypted with a customer-managed KMS key (tying back to Module 7), the key policy must separately grant those same service principals permission to use the key for encryption, since S3 bucket permissions and KMS key permissions are evaluated independently. Getting only one of the two right is a common misconfiguration — write access to the bucket without corresponding key access still fails.

The line I'd want you to walk out of this module able to say out loud: your logs shouldn't be deletable by the account that generated them. Say that sentence in an interview or on the exam and you've demonstrated you understand not just the feature, but why it exists. Everything else in this section — bucket policies, KMS key policies, organization trails — is just the implementation of that one sentence.

Exam Angle

A scenario describing logs stored in the same account that generates them, with a requirement for tamper-resistance or a compromised-account blast-radius concern, is signaling that the correct answer involves moving log delivery to a separate, centralized account — not just tightening IAM policy within the existing account.

Concept 6 of 6

Log data lakes: what happens once you're collecting everything

Once you're centrally collecting CloudTrail, Config, and Flow Logs data from every account in an organization, a new problem appears: volume. You now have terabytes of heterogeneous log data sitting in S3, and "grep through it during an incident" stops being viable. The natural next step is aggregating these sources into a log data lake — a normalized, centrally queryable store that lets you run a single query across CloudTrail, Config, VPC Flow Logs, and other sources together, instead of investigating each source in isolation.

We're only previewing the concept here, as the natural endpoint of everything this module built — Module 10 gives this full treatment under the name Amazon Security Lake, AWS's purpose-built implementation of this pattern using the OCSF open format. For now, the point to internalize is the progression: individual log sources → centralized delivery for blast-radius reasons → aggregation into a queryable data lake because the centralized volume demands it. That's the arc of this entire module in one sentence.
