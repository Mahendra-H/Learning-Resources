    EC2 Workload Security

    The Instance You Own Is the Instance You Harden

    IMDSv2 and the SSRF-to-Credential-Theft Attack Path

    Think of the EC2 metadata endpoint like a key cabinet bolted to the inside of a server room. It is only reachable from inside the room — but if your application opens a window that lets someone outside shout instructions through it, you have a problem. That window is an SSRF vulnerability, and that key cabinet is 169.254.169.254.

    Every EC2 instance can reach a special IP address — 169.254.169.254 — that serves instance metadata, including the temporary IAM credentials for the attached instance role. This is the Instance Metadata Service, or IMDS. Under IMDSv1, any process on the instance that can make an HTTP GET request to that address can retrieve those credentials. No authentication, no token, no session — just a raw HTTP request.

    This becomes a concrete attack when combined with a Server-Side Request Forgery (SSRF) vulnerability. SSRF flaws let an attacker manipulate a server-side request — typically a URL parameter, a webhook, or an image-fetch function — so it makes HTTP requests to attacker-chosen destinations. Redirect it to http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole and the application returns the instance role's access key, secret key, and session token. The attacker now has credentials they can use from anywhere on the internet.

    ⚠ Concrete Attack Path (IMDSv1)

    App receives a URL parameter → fetches it server-side → attacker redirects to metadata endpoint → app returns JSON with AccessKeyId, SecretAccessKey, Token → attacker exfiltrates credentials → uses them from their own machine. No access to the instance, no exploit of AWS infrastructure — only the application SSRF and an unprotected metadata endpoint.

    IMDSv2 closes this path by requiring a session-oriented flow. Before retrieving any metadata, the instance must first PUT to the metadata endpoint to get a session token (with a configurable TTL). All subsequent requests must include this token in the X-aws-ec2-metadata-token header. Most SSRF exploits cannot follow this two-step PUT-then-GET sequence. The session token requirement makes the metadata service effectively opaque to SSRF attacks.

    Enforce IMDSv2 with the --http-tokens required option on the instance metadata options, or enforce it at the AWS Organizations level using an SCP that denies ec2:RunInstances unless the condition ec2:MetadataHttpTokens: required is set. The exam expects IMDSv2 enforcement as the correct answer whenever IMDSv1 is presented as the current state — not "upgrade IMDSv1 is fine" but "enforce IMDSv2."

    Key takeaway: IMDSv2 is not a hardening option — it is the baseline. Any instance still running IMDSv1 is one SSRF vulnerability away from a credential theft incident.

    The IMDSv2 question usually arrives in the exam disguised as an application vulnerability question. The scenario describes an app making outbound HTTP requests, mentions a WAF or something else already in place, and asks what additional control prevents credential theft. IMDSv2 is the answer. The other answer choices (tightening the security group, adding a VPN) don't address the metadata endpoint at all — they let the attack succeed through a different vector.

    Least-Privilege Instance Profiles

    An instance profile is how an IAM role is attached to an EC2 instance — the profile is the container, the role is the permissions. Every EC2 instance that needs to call AWS services should have an instance profile with an IAM role scoped precisely to what that workload needs. A web tier that reads from S3 and puts messages on SQS needs those two permission sets, nothing more. It doesn't need iam:*, ec2:*, or access to other buckets. Granting overly broad permissions to an instance role means that when an instance is compromised (through SSRF, through a web application vulnerability, through a misconfigured app), the attacker inherits those permissions. The blast radius of a compromised instance is exactly the blast radius of its role.

    Security groups at the instance level should be scoped to the minimum set of ports and sources required. A backend API server that only receives traffic from a load balancer should have a security group that allows inbound traffic only from the load balancer's security group — not from 0.0.0.0/0, not from a broad CIDR that encompasses the whole VPC. This ties back to Module 5's security group discussion: the specificity of the source is the control.

    Guest OS Patch Ownership

    The shared responsibility model's most operationally concrete expression for EC2: AWS patches the hypervisor, the physical host, and the underlying infrastructure. You patch the operating system, the middleware (web servers, runtimes), and the application running inside the instance. This is not a theoretical division — an unpatched guest OS with a known CVE is a door that's open regardless of how locked down your VPC is. The exam doesn't just want you to know this as a concept (Module 1 covered it); it expects you to recognize the operational practices that fulfill this responsibility, which leads directly to Systems Manager Patch Manager.

    Production Scenario — SSRF via IMDSv1

    An e-commerce platform has a product image preview feature that fetches URLs provided by users. A researcher discovers the SSRF path and retrieves the EC2 instance role credentials via the metadata endpoint. The role has s3:GetObject on all buckets, which includes a bucket storing customer PII. The fix: enforce IMDSv2 on all instances via SCP, and scope the instance role to only the specific S3 prefix this workload needs to read.

    ⏸ Pause & Recall · Before You Continue
    An application on EC2 has an SSRF vulnerability. The instance runs IMDSv1. An attacker sends a crafted URL to the application's image-preview feature. Walk through exactly what happens next — step by step — and name the single AWS control that would have prevented the credential theft, even with the SSRF still present.

    Step 1: The app receives the attacker's URL and makes a server-side HTTP GET request to it. Step 2: The URL redirects (or resolves) to http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole. Step 3: The metadata service responds with the role's access key, secret key, and session token in JSON. Step 4: The application returns this JSON in its response — the attacker now has live credentials. Step 5: The attacker uses those credentials from anywhere on the internet. The single control that prevents step 2 from succeeding: IMDSv2 enforced with --http-tokens required. IMDSv2 requires a PUT request to get a session token first — SSRF attacks can't follow that two-step flow, so the GET to the metadata endpoint is rejected even if the SSRF vulnerability exists.

    Systems Manager

    Eliminate the Bastion Host. Audit the Session Instead.

    Session Manager: SSH Without SSH

    Think of a bastion host like giving every visitor to your building a physical key to the front door so they can let themselves in. Session Manager is the security desk version: visitors sign in at reception, show ID (IAM), are escorted to the right room, and every visit is logged. When they leave, there is nothing to hand back and nothing to steal.

    Traditional access to EC2 instances required a bastion host — a jump server sitting in a public subnet with port 22 open to the internet, carrying SSH keys that had to be rotated, accessed, and secured. The bastion host itself becomes a high-value target: compromise it and you have shell access to the fleet behind it. Session Manager eliminates this entire attack surface. It provides browser-based and CLI shell access to any instance running the SSM Agent — without opening any inbound port on the instance, without an SSH key to manage, and without a bastion host to maintain.

    The session is authenticated through IAM: the user needs ssm:StartSession permission for the target instance. The connection runs through the Systems Manager API over HTTPS — outbound from the instance to the SSM endpoint, not inbound from the internet to the instance. Sessions are logged automatically to CloudWatch Logs or S3, creating an audit trail. This is a concrete defense-in-depth win: you've removed an entire class of target (the bastion host and all the attack surface it carries) while adding auditability you didn't have with SSH.

    Key takeaway: Session Manager is not just a more convenient SSH — it is architecturally more secure because it eliminates inbound ports entirely and makes every session auditable by IAM identity.

    Session Manager is where the "eliminate SSH bastion hosts" principle becomes real. In the exam, when a scenario describes a bastion host with open port 22 and asks for a more secure alternative that maintains auditability, Session Manager is the answer. The key insight: it is not just equivalent to SSH from a security standpoint — it is meaningfully more secure because it eliminates inbound ports entirely and adds centralized, tamper-evident session logging tied to IAM identities.

    Patch Manager: OS Patching at Scale

    Patch Manager operationalizes your guest OS patching responsibility across an entire fleet. You define patch baselines — the set of patches to approve based on severity, classification, and product — and maintenance windows that specify when patching runs. Instances are assigned to patch groups via resource tags, and Patch Manager applies approved patches on schedule without requiring SSH or manual runbook execution. Compliance reporting in Systems Manager tells you which instances are compliant, which are missing patches, and by how many days.

    The shared responsibility principle is abstract until you're looking at a fleet of 400 EC2 instances with no patching schedule. Patch Manager is the operational mechanism that makes "you own the guest OS" a manageable reality rather than a spreadsheet nightmare.

    Run Command and IAM Scoping

    Run Command executes scripts or SSM documents across a fleet of instances in parallel, without SSH. This is useful for configuration management, security remediation, and compliance enforcement at scale. The critical security consideration: Systems Manager is a very powerful management-plane tool. The ssm:StartSession and ssm:SendCommand permissions give significant operational reach over your fleet. Scope these permissions with conditions — use aws:ResourceTag conditions to limit which instances a principal can target, and restrict by session document types. Don't treat SSM permissions as low-risk just because they don't look like "infrastructure access" at first glance.

    Production Scenario — Bastion Host Compromised via Leaked SSH Key

    A financial services company ran a fleet of 180 EC2 instances accessible through a bastion host in a public subnet with port 22 open to the internet. An engineer accidentally committed an SSH private key to a public GitHub repository. The key was discovered by an automated scanner within 11 minutes and used to log into the bastion, then pivot to production database servers from there. Post-incident, the team deployed the SSM Agent across the entire fleet, removed the bastion host, closed port 22 on all security groups, and configured Session Manager with CloudWatch Logs session logging. The follow-on audit also revealed that 43 instances were running OS builds more than 90 days behind on patches — which Patch Manager then remediated in a single scheduled maintenance window.

    Container Security — ECS & EKS

    Blast Radius Starts at the Task, Not the Node

    ECS Task Roles: The Correct Least-Privilege Pattern

    When you run ECS tasks on EC2-backed clusters, each EC2 host has an IAM instance role. The classic mistake is using that instance role to grant the permissions that tasks need — S3 read access, DynamoDB writes, SQS messages. The problem: every task running on that host inherits the instance role's permissions, regardless of what that specific task actually needs. One over-broad instance role means the entire host's workload runs with those permissions. If any container on that host is compromised, the attacker gets the full instance role.

    ECS Task IAM Roles solve this with per-task credential isolation. You define an IAM role in the ECS task definition. The ECS agent handles credential vending to each container through a task metadata endpoint — credentials for the task role are served to the container's environment and rotated automatically. The blast radius of a compromised container is now limited to exactly what that task's role permits. A task that processes image uploads and writes thumbnails to S3 gets s3:PutObject for the thumbnails prefix, and nothing else.

    EKS: IRSA — IAM Roles for Service Accounts

    EKS introduces the same problem with an additional Kubernetes layer. Worker nodes are EC2 instances and have an IAM role — the node role. If you grant pod-level permissions through the node role, every pod on that node inherits everything. IRSA (IAM Roles for Service Accounts) solves this at the Kubernetes level using OpenID Connect (OIDC) federation.

    Each EKS cluster has an OIDC identity provider endpoint. You create an IAM role with a trust policy that allows a specific Kubernetes service account in a specific namespace to assume it. You annotate the Kubernetes service account with the IAM role ARN. When a pod using that service account starts, the EKS control plane injects a projected token into the pod — a short-lived OIDC token that the AWS SDK exchanges for temporary IAM credentials for the bound role. The pod gets exactly the permissions of its assigned service account's role, scoped to that pod alone. The node role grants nothing to the pod's AWS calls.

    Key takeaway: IRSA is to EKS pods what task roles are to ECS tasks — pod-level IAM identity that limits blast radius to exactly what that workload needs, nothing more.

    Exam Trap — Node Role vs IRSA

    If a question describes an EKS deployment where pods need S3 access and the team has attached S3 permissions to the node IAM role, the correct answer is always to use IRSA instead. Node-role permissions are applied to every pod on the node, not just the ones that need them. IRSA achieves true pod-level least privilege. The exam tests this exact substitution.

    EKS Shared Responsibility Split

    For EKS specifically, the shared responsibility line runs through the control plane. AWS manages and operates the Kubernetes control plane — the API server, etcd, the scheduler, controller manager, and the underlying infrastructure they run on. AWS patches the control plane, scales it, backs up etcd, and maintains its availability. You are responsible for worker nodes (EC2 instances — you patch the OS, configure the node groups), the container images running in your pods, and the Kubernetes configurations you apply (RBAC, network policies, pod security standards).

    ECR Image Scanning and Supply Chain Risk

    A container image is the atomic unit of your workload's supply chain. The base image you start from — ubuntu:22.04, node:20-alpine, python:3.12-slim — carries whatever vulnerabilities existed in that image at build time. ECR image scanning (now powered by Amazon Inspector) checks images against known CVE databases both on push and on a scheduled basis. A container with a critical OpenSSL vulnerability in its base image is exploitable regardless of how clean your application code is.

    The shared responsibility principle applies directly: the container image is yours. AWS secures the underlying host and container runtime in Fargate; you own what's inside the container. Enable scanning on push for all ECR repositories, set up Inspector findings notifications, and enforce policies that prevent deployment of images with unresolved critical or high-severity findings. A finding in the image registry that stays unresolved is a known vulnerability you've chosen to accept — the exam treats that as a control failure.

    Production Scenario — Over-Broad EKS Node Role

    A microservices team runs 12 different services on an EKS cluster. Because configuring individual roles was deemed complex, all pods share the node role, which has full access to the production DynamoDB tables and S3 buckets. A vulnerability in one service's open-source dependency allows RCE inside the container. The attacker now has full access to every production data store — not just the one that service needed. The fix: IRSA for each service account, with each role scoped to only the specific tables and buckets that service needs.

    ⏸ Pause & Recall · Before You Continue
    A team is migrating from an ECS cluster using EC2 instance roles to one using ECS Task IAM Roles. The CISO asks: "If a container is compromised after this change, what exactly can the attacker do that they could not do before — and what can they no longer do?" Give a concrete answer.

    Before (instance role): A compromised container can use the EC2 instance role credentials — which are available to all containers on that host. The attacker has access to every permission in the instance role, regardless of what the compromised container actually needed. If the instance role had broad S3 or DynamoDB access added for other services, the attacker gets all of it. After (task roles): A compromised container can only use the permissions of its specific task IAM role — scoped to exactly what that task needs. The attacker cannot pivot to permissions belonging to other tasks on the same host. They also cannot use the EC2 instance role for application-level AWS access, because task roles replace that path entirely. The blast radius is now bounded by the task definition, not the host.

    Lambda Security

    One Function, One Role, One Purpose

    Execution Role Scoping: The Shared Role Anti-Pattern

    Think of a Lambda execution role like a staff badge. One shared badge for all 12 employees means losing any badge exposes every door in the building. Individual badges mean a lost badge only exposes the specific rooms that employee needed. Lambda functions are single-purpose by design — there is never a good reason not to give each one its own badge.

    Lambda's shared responsibility model differs from EC2 in a critical way: AWS manages the underlying execution environment entirely, including OS patching, runtime updates, and the security of the underlying host. Your responsibility narrows to the function code, the execution role permissions, the environment configuration, and the network placement. This narrower scope makes the permissions problem more avoidable — and more clearly your fault when it goes wrong.

    The most common over-permissioning pattern in Lambda is a single execution role shared across many functions. It's convenient — one role to rule them all, no per-function IAM management. It is also a significant blast-radius risk. Lambda functions are intentionally small and single-purpose. A function that processes SQS messages and writes to a DynamoDB table needs exactly those three permissions: sqs:ReceiveMessage, sqs:DeleteMessage, and dynamodb:PutItem on specific resources. A shared role that also has s3:GetObject, kms:Decrypt, and secretsmanager:GetSecretValue turns a compromised function into a much broader threat.

    Create a dedicated execution role per function. Scope it to the specific actions on specific resource ARNs. This is the Lambda embodiment of least privilege — it is achievable in Lambda because the function's purpose is narrow by design, and there is no excuse for not doing it.

    Environment Variable Encryption

    Lambda environment variables are a convenient place to store configuration — connection strings, feature flags, endpoint URLs. They should not store plaintext credentials or secrets. Environment variables at rest are encrypted by a default Lambda service key, but you should use a customer-managed KMS key for sensitive values to maintain control and auditability of the decryption. Better still: store secrets in AWS Secrets Manager or SSM Parameter Store, and have the function retrieve them at startup using the execution role's permission to call those services. Scope the role's Secrets Manager permission to the specific secret ARN the function needs — not secretsmanager:GetSecretValue on *.

    VPC-Attached Lambda: When and Why

    By default, Lambda functions run in an AWS-managed VPC outside your account's network. They can reach any public endpoint on the internet but cannot reach resources in your VPC that have no public endpoint — an RDS instance in a private subnet, an internal API behind an Application Load Balancer with no internet-facing listener, an ElastiCache cluster. Attaching a Lambda function to your VPC places its execution environment on an ENI inside your chosen subnets, giving it private network access to those resources.

    The security trade-off: a VPC-attached Lambda function loses its default internet access. If it also needs to call AWS service APIs (S3, DynamoDB, Secrets Manager), you need to provide a path — either a NAT Gateway in the subnet's route table (for internet access) or VPC endpoints for the specific AWS services the function needs to reach. This is where the VPC endpoint vs NAT Gateway decision, which we cover in the PrivateLink section, becomes practically important. The correct answer for a Lambda function that only needs to reach AWS services is VPC endpoints, not a NAT Gateway — smaller blast radius, no internet path, often lower cost.

    ⚠ Exam Trap — VPC Lambda Timeout on AWS Service Calls

    A Lambda function is placed inside a VPC to access an RDS instance. After deployment, calls to Secrets Manager, SSM Parameter Store, and KMS start timing out — not failing with an authorization error, but timing out. The team initially suspects IAM. The real cause: VPC-attached Lambda loses its default internet access. Those AWS service endpoints are public — unreachable without either a NAT Gateway (for internet) or interface VPC endpoints for each service. The exam distinguishes timeout errors (connectivity failure) from access-denied errors (IAM failure). When you see timeout on an AWS service call from VPC Lambda, the answer is a VPC endpoint — not an IAM fix.

    Production Scenario — Supply Chain Attack via Shared Lambda Role

    A startup's payment platform ran 14 Lambda functions all sharing one execution role created at project kickoff. The role carried s3:GetObject on all buckets, dynamodb:* on all tables, and secretsmanager:GetSecretValue on all secrets — accumulated over two years as features were added. A widely-used open-source XML parsing library used by one webhook-processing function was compromised in a supply chain attack. The malicious version exfiltrated AWS credentials using the shared role and exported 280,000 customer records from DynamoDB and archived payment data from S3 before detection. Post-incident: 14 dedicated scoped roles were created, Lambda code signing was enforced, and dependency scanning was added to CI/CD. The shared role had turned a single-function supply chain incident into a company-wide breach.

    Key takeaway: Lambda functions are single-purpose by design — that makes per-function scoped execution roles both achievable and mandatory. A shared role is a deferred blast-radius problem waiting for a supply chain incident to detonate it.

    Hybrid Connectivity

    VPN vs Direct Connect: Know the Difference Cold

    Site-to-Site VPN

    AWS Site-to-Site VPN creates an encrypted IPsec tunnel between a customer gateway (your on-premises router or firewall) and a virtual private gateway or Transit Gateway on the AWS side. The tunnel runs over the public internet. Encryption is not optional or configurable — it is inherent to IPsec. You cannot have an unencrypted Site-to-Site VPN tunnel. Provisioning takes minutes. Each tunnel supports up to 1.25 Gbps, and you can use ECMP (Equal-Cost Multi-Path routing) across multiple tunnels to increase aggregate throughput. Latency depends on the internet path — it will vary, and you cannot guarantee it.

    AWS Direct Connect

    Think of Direct Connect like a private rail line from your data center directly to an AWS station — no public roads, no other vehicles sharing the track. Consistent, fast, and dedicated. But here is the thing a private rail line and an armoured vehicle are two different things. You still need to lock the cargo. The rail line being private does not mean no one at the station can look inside the containers.

    Direct Connect is a dedicated, private fiber circuit between your data center (or colocation facility) and an AWS Direct Connect location. Once established, your traffic bypasses the public internet entirely — it travels on a private circuit that AWS operates between the Direct Connect location and the AWS region. This gives you consistent, predictable latency and high throughput — dedicated connections scale from 1 Gbps to 100 Gbps. Provisioning takes weeks to months, because a physical fiber circuit must be physically installed.

    ⚠ Critical Exam Gotcha — Direct Connect Is NOT Encrypted by Default

    Direct Connect is private — traffic does not traverse the public internet. But private and encrypted are two entirely different properties. A dedicated fiber circuit is still unencrypted unless you explicitly add an encryption layer. Another customer at the same colocation facility, a malicious insider at the carrier, or a splice on the physical fiber could theoretically read your traffic. The exam tests this distinction repeatedly and explicitly. "Private" does not mean "encrypted."

    This gotcha has ended careers in poorly architected compliance environments. A team assumes their Direct Connect connection satisfies data-in-transit encryption requirements because "it doesn't go over the internet." Their auditor disagrees. The fix requires either MACsec (Layer 2 encryption on the physical connection, supported on 10G and 100G dedicated connections) or a VPN-over-Direct-Connect setup — an IPsec tunnel that uses the Direct Connect circuit as its path rather than the internet. The VPN-over-DC approach gives you both the consistent latency of Direct Connect and the encryption of IPsec.

    Key takeaway: "Private" is a network topology property. "Encrypted" is a security property. Direct Connect gives you one. You have to add the other.

    Direct Connect Encryption Options

    MACsec operates at Layer 2 and encrypts frames on the physical connection itself. It is supported on dedicated 10G and 100G Direct Connect connections and requires compatible hardware at the customer end. It is the cleanest solution but has hardware requirements. VPN-over-Direct-Connect runs a standard IPsec VPN tunnel over the Direct Connect path instead of over the internet. This is compatible with any Direct Connect connection and any VPN-capable customer gateway. It adds IPsec overhead but provides encryption that satisfies compliance requirements. Both are legitimate exam answers — the question will tell you whether hardware compatibility is a constraint.

    When to Use VPN + Direct Connect Together

    The exam's favorite combined architecture: Direct Connect as the primary path, with a Site-to-Site VPN as a backup. Direct Connect provides the performance and consistency required for production traffic. The VPN provides an encrypted internet-routed path that activates via BGP failover when the Direct Connect circuit fails — carrier outages, physical link issues, or Direct Connect location maintenance. This pattern gives you production-grade performance under normal conditions and resilience under failure conditions. Configure BGP routing with appropriate local preferences so Direct Connect is preferred; the VPN path carries traffic only when Direct Connect routes are withdrawn.

    Production Scenario — Direct Connect Fails Compliance Audit

    A healthcare SaaS company ran all production traffic between its on-premises data center and AWS over a 10G Direct Connect connection for 18 months. A HIPAA technical safeguard audit required evidence of encryption in transit for all Protected Health Information (PHI). The security team submitted Direct Connect documentation — dedicated circuit, private path, no public internet traversal. The auditor rejected it. PHI was flowing unencrypted on a shared-carrier fiber path that, while dedicated, provided no cryptographic protection. The finding required remediation before the compliance attestation could proceed. The fix: VPN-over-Direct-Connect was implemented within 48 hours using the existing customer gateway hardware, providing IPsec encryption over the same physical path. MACsec was scoped for a future hardware refresh to provide Layer 2 encryption natively. The incident led to a company policy update explicitly distinguishing "private path" from "encrypted in transit" in all compliance documentation.

    PrivateLink & VPC Endpoints

    Remove the Internet From the Equation Entirely

    The Core Security Argument

    When an EC2 instance in a private subnet needs to call an AWS service — upload to S3, read from DynamoDB, retrieve a secret from Secrets Manager — the default path is through the internet. Traffic exits the VPC via an internet gateway or NAT Gateway, reaches the AWS service's public endpoint, and returns. This works, and HTTPS encrypts the data in transit. But the internet is still in the path. A misconfigured route, a BGP anomaly, or a network security group too loose could expose that traffic or redirect it. VPC endpoints remove the internet from the equation entirely: traffic stays on the AWS network backbone from your subnet to the AWS service.

    Gateway Endpoints — S3 and DynamoDB Only

    Gateway endpoints work only for S3 and DynamoDB. They function by injecting a route into your VPC route table: traffic destined for the service's managed prefix list is directed to the endpoint instead of through an internet gateway or NAT Gateway. No ENI is created in your subnet, no additional IP address is consumed, and there is no per-hour or per-GB charge beyond standard S3 or DynamoDB pricing. You can attach an endpoint policy to restrict which buckets or tables are accessible through this endpoint — a powerful tool for preventing data exfiltration to attacker-controlled S3 buckets from your instances.

    Interface Endpoints — PrivateLink-Backed, Everything Else

    Interface endpoints work for virtually every other AWS service — EC2 API, Secrets Manager, SSM, KMS, CloudWatch, STS — and many third-party services available through AWS PrivateLink on Marketplace. An interface endpoint creates an Elastic Network Interface (ENI) in your chosen subnet with a private IP address. When DNS is enabled (the default), the service's regional endpoint name resolves to this private IP inside your VPC. Your existing application code makes the same API calls as before; the DNS resolution transparently routes them through the endpoint. No code changes required. Interface endpoints have a per-hour charge per AZ and a per-GB data processing charge.

    An endpoint policy on an interface endpoint or gateway endpoint is an additional access control layer on top of IAM — not a replacement for it. The endpoint policy controls what can flow through the endpoint; IAM controls whether the calling principal is allowed to perform the action at all. Both must allow the request. This makes endpoint policies useful for blast-radius reduction: even if credentials are stolen, an endpoint policy restricting the S3 endpoint to a specific bucket list limits what an attacker can do with those credentials from inside your VPC.

    VPC Endpoint vs. NAT Gateway — The Decision

    The most common mistake: using a NAT Gateway for all outbound traffic from private subnets, including traffic that only needs to reach AWS services. A NAT Gateway routes traffic to the internet and back. It has a per-hour cost and a per-GB data processing charge. For traffic that only needs to reach S3 or DynamoDB, a gateway endpoint is free and removes the internet path entirely. For traffic that needs to reach other AWS services (SSM, Secrets Manager, ECR, etc.), an interface endpoint provides the private path without the internet. A NAT Gateway is only necessary when traffic genuinely needs the general internet — third-party APIs, package repositories, external webhooks.

    Key takeaway: If your private subnet only needs to reach AWS services, VPC endpoints are always the right answer — smaller attack surface, often lower cost, and no internet path at all.

    Production Scenario — S3 Access from Private Subnet

    A data processing fleet in private subnets uploads results to S3. The current architecture routes all traffic through a NAT Gateway. Adding an S3 gateway endpoint redirects that S3 traffic directly to S3 via the AWS backbone — no NAT Gateway costs for S3 data transfer, no internet path, and the endpoint policy restricts access to the specific production bucket. The NAT Gateway remains for any traffic that genuinely needs the internet, but S3 traffic is completely off that path.

    Guardrails for Generative AI Workloads

    📌 Study Note — New Exam Content

    Bedrock Guardrails appear on the SCS-C03 blueprint (December 2025 revision) but are absent from study materials written for earlier exam versions. This is a real but lighter-weight topic compared to IAM, encryption, and network security. Treat it as something you need to understand conceptually and be able to apply in a scenario — not a deep technical implementation area.

    What Bedrock Guardrails Are

    Amazon Bedrock is AWS's managed service for accessing and deploying foundation models — large language models and multimodal models from providers including Anthropic, Amazon, Meta, Mistral, and others. When you build a generative AI application on Bedrock, the application sends prompts to the model and processes responses. Guardrails are a configurable safety and policy layer that sits between the application and the model, inspecting both the incoming prompt and the outgoing response.

    A Guardrail is a standalone AWS resource — you create it, configure its policies, and apply it to a Bedrock API invocation by passing its ARN at call time. The same guardrail can be applied consistently across multiple model invocations, application entry points, or deployment environments.

    The Three Guardrail Controls

    Content filters apply configurable thresholds to harmful content categories — violence, hate speech, sexual content, self-harm, and prompt injection attacks. For each category, you set a sensitivity threshold from None to High. At the High setting, even mild references to that category are blocked. At Low, only extreme content is blocked. These filters apply bidirectionally: to the user's prompt and to the model's response.

    PII redaction detects personally identifiable information in prompts and responses. You can configure Guardrails to block inputs containing PII (preventing sensitive data from being sent to the model at all), redact PII in the model's response before it reaches the user (masking names, email addresses, phone numbers, credit card numbers), or both. This is particularly relevant for customer service or healthcare applications where inadvertent PII leakage in model outputs is a compliance risk.

    Topic restrictions (denied topics) let you define specific topics that the model should refuse to engage with for your application's use case. A financial services company deploying a customer service chatbot might deny topics related to investment advice (regulatory requirement) or competitor products (business policy). These are defined in natural language — Bedrock uses the foundation model itself to evaluate whether an incoming prompt attempts to steer the conversation toward a denied topic.

    Request Pipeline — Click to Explore Each Stage

    Stage 1

    Application sends prompt to Bedrock API

    Your application calls bedrock-runtime:InvokeModel with the model ID, the prompt, and the Guardrail ARN (plus guardrailVersion). IAM controls whether this principal can make this API call at all — Guardrails have no effect if the caller is blocked by IAM first.

    ↓
    Stage 2

    Content Filter — Harmful Category Check

    The prompt is evaluated against configured content category thresholds (violence, hate, sexual content, prompt injection). If the prompt exceeds any threshold, the request is blocked before the model ever sees it. The response returned to the application indicates which policy was violated.

    ↓
    Stage 3

    PII Detection and Redaction

    The prompt is scanned for configured PII entity types (names, emails, phone numbers, SSNs, credit card numbers, etc.). Depending on configuration: the request may be blocked if PII is present, or PII may be anonymized/masked before the prompt is forwarded to the model.

    ↓
    Stage 4

    Topic Restriction Evaluation

    Denied topics are evaluated using the model's own understanding. If the prompt is classified as attempting to discuss a denied topic, the request is blocked. Topic definitions are written in natural language and can be highly specific to your business context.

    ↓
    Stage 5

    Model Invocation (prompt passed to FM)

    The prompt has passed all configured guardrail checks. It is now sent to the foundation model. The model processes the prompt and generates a response. The response is then passed back through the guardrail pipeline before being returned to your application.

    ↓
    Stage 6

    Output Content Filter and PII Redaction

    The model response passes through the same content filters and PII checks on output. If the model generates harmful content or PII despite the input-side guardrails (which can happen), the output filter catches it here. PII in the response can be masked before the application receives it.

    Exam Trap — Guardrails Are Not IAM or Network Controls

    Bedrock Guardrails control what the model can say — not who can call it. You still need IAM permissions on bedrock:InvokeModel to control API access, VPC endpoints if your application requires private network access to Bedrock, and resource-based policies for cross-account access. Guardrails are an additional, workload-specific safety layer — they do not replace the foundational access controls.

    Secure This Workload

    Each scenario describes a real workload configuration with a security gap. Identify the specific problem and the correct fix before revealing the reasoning. These mirror the style of scenario questions on the exam.

    Scenario 01 — EC2 / IMDS

    An e-commerce application runs on EC2. A security researcher reports they retrieved IAM credentials by sending a crafted HTTP GET to 169.254.169.254 through a URL-fetching feature in the app.

    🔴 Gap: IMDSv1 is enabled — any HTTP GET to the metadata endpoint succeeds without a session token. The SSRF vulnerability in the application made it trivial to exploit.
    ✅ Fix: Enforce IMDSv2 using --http-tokens required on the instance metadata options (or via SCP for all new instances). IMDSv2 requires a PUT request to obtain a session token before any GET request succeeds. Most SSRF exploits cannot follow this two-step flow, which breaks the credential theft path. Additionally, scope the instance role to only the S3 prefix this workload needs — limiting what stolen credentials could access even if SSRF were exploited through some other vector.
    Scenario 02 — Systems Manager / SSH

    A team manages 200 EC2 instances by maintaining a bastion host in a public subnet with port 22 open to 0.0.0.0/0. SSH keys are distributed to 15 engineers. A recent audit flagged the bastion host as a high-value target with unclear session logging.

    🔴 Gap: Open port 22 to the internet is an unnecessary attack surface. Distributed SSH keys are difficult to rotate consistently. Session activity is not being centrally logged or audited.
    ✅ Fix: Replace the bastion host with AWS Systems Manager Session Manager. Install the SSM Agent on all instances. Grant engineers ssm:StartSession permissions via IAM (scoped to instance resource ARNs). Remove the bastion host, close port 22, and configure Session Manager to log sessions to CloudWatch Logs or S3. No SSH keys, no inbound ports, full audit trail tied to IAM identities.
    Scenario 03 — ECS / Task Role

    An ECS cluster on EC2 hosts 8 microservices. The EC2 instance role has s3:* on all buckets, dynamodb:* on all tables, and secretsmanager:GetSecretValue with a wildcard resource, because "it's easier to manage one role." A container vulnerability is discovered in one of the services.

    🔴 Gap: All containers on the host inherit the instance role. Compromise of any single container gives access to all S3 buckets, all DynamoDB tables, and all secrets — regardless of what that container actually needs.
    ✅ Fix: Create a separate ECS Task IAM Role for each service, scoped to only the specific resources that service needs. Attach the role to the ECS task definition, not the EC2 instance. Remove application-level permissions from the EC2 instance role entirely (it only needs permissions for ECS agent operation and CloudWatch). Compromise of any single container is now bounded by that task role alone.
    Scenario 04 — EKS / IRSA

    An EKS cluster runs a payment processing pod and a logging pod on the same node. The node IAM role has dynamodb:GetItem and dynamodb:PutItem on the payments table (for the payment pod) and s3:PutObject on the logs bucket (for the logging pod). The logging pod is built on an old base image with a known critical CVE.

    🔴 Gap: Both pods run with the node role permissions. An exploit against the logging pod gives the attacker access to the payments DynamoDB table — a resource the logging pod should never be able to reach.
    ✅ Fix: Implement IRSA. Create two separate IAM roles — one for the payment service account (dynamodb permissions only), one for the logging service account (s3:PutObject to the logs bucket only). Annotate each Kubernetes service account with the appropriate role ARN. Remove application permissions from the node role. Also: update the logging pod base image and enable ECR scanning to catch this class of issue earlier.
    Scenario 05 — Lambda / Shared Role

    A serverless application has 12 Lambda functions. All share one execution role that has s3:GetObject on all buckets, dynamodb:* on all tables, kms:Decrypt on all keys, and secretsmanager:GetSecretValue on all secrets. The role was created at project start and never revisited.

    🔴 Gap: A function that should only read from a single S3 prefix effectively has access to every data store and key in the account through the shared role. Any compromise, code injection, or supply-chain attack on any function gives the attacker the full role permissions.
    ✅ Fix: Create a dedicated execution role per Lambda function. For each function, determine exactly which AWS actions on which specific resource ARNs it needs. Define that as the role policy. A function processing SQS messages and writing to one DynamoDB table gets exactly those three permissions on those exact resource ARNs — nothing more. This is achievable in Lambda precisely because functions are single-purpose by design.
    Scenario 06 — Hybrid / Direct Connect Encryption

    An enterprise connects its data center to AWS via Direct Connect for its core banking application. The security team asserts that data in transit is protected because "traffic stays on the private circuit and never touches the public internet." A compliance auditor challenges this assertion.

    🔴 Gap: Direct Connect is private — it does not traverse the public internet. But private and encrypted are different properties. The Direct Connect circuit itself is unencrypted unless an additional encryption layer is added. The compliance assertion is incorrect.
    ✅ Fix: Add encryption to the Direct Connect path. Option 1: MACsec (IEEE 802.1AE) on the dedicated connection — Layer 2 encryption on the physical link. Requires supported hardware at the customer end; available on 10G and 100G dedicated connections. Option 2: VPN-over-Direct-Connect — run an IPsec tunnel over the Direct Connect circuit. This is the most common compliance solution and works with any connection speed and customer gateway hardware.
    Scenario 07 — VPC Endpoint vs NAT Gateway

    Private-subnet EC2 instances process data and upload results to S3. The current architecture routes all outbound traffic through a NAT Gateway. A cost review shows significant NAT Gateway data processing charges for the S3 traffic. Security wants to reduce internet exposure.

    🔴 Gap: S3 traffic does not need to traverse the internet or a NAT Gateway. Routing it through NAT adds cost, internet path exposure, and uses the NAT Gateway's bandwidth allocation unnecessarily.
    ✅ Fix: Create an S3 gateway endpoint in the VPC and add a route to the private subnet route tables. S3 traffic now travels directly to S3 via the AWS backbone — no NAT Gateway, no internet path, no data processing charges on NAT. The NAT Gateway remains for any traffic that genuinely needs the internet. Apply an endpoint policy to restrict access to only the specific S3 bucket(s) the instances should access — preventing accidental or malicious writes to other buckets.
    Scenario 08 — Lambda in VPC

    A Lambda function is attached to a VPC to access an RDS database in a private subnet. After deployment, the function can reach RDS successfully but cannot call Secrets Manager to retrieve the database password, timing out every time. The VPC has no internet gateway on the private subnet.

    🔴 Gap: VPC-attached Lambda loses its default internet access. Secrets Manager is a public AWS endpoint — the function has no route to reach it without either internet access (NAT Gateway) or a VPC endpoint for Secrets Manager.
    ✅ Fix: Create a VPC interface endpoint for Secrets Manager (com.amazonaws.region.secretsmanager) in the private subnet. This gives the Lambda function private network access to Secrets Manager without requiring internet access. No NAT Gateway needed for this use case. Also create interface endpoints for any other AWS services the Lambda calls (KMS for decryption, CloudWatch Logs for logging).
    Scenario 09 — Bedrock Guardrails Scope

    A team deploys a customer service chatbot on Amazon Bedrock with Guardrails configured for content filtering and PII redaction. They conclude that IAM controls on the Bedrock API are no longer necessary because "Guardrails handle the security." An internal user with misconfigured broad permissions begins probing the API directly.

    🔴 Gap: Guardrails control what the model can say — not who can call the API. A user with bedrock:InvokeModel permissions can bypass Guardrails by calling the API without specifying the Guardrail ARN, or calling with a different model ID.
    ✅ Fix: Maintain strict IAM controls on Bedrock API access — bedrock:InvokeModel should be granted only to the application's execution role, scoped to specific model ARNs. Use resource-based policies or IAM conditions to enforce Guardrail usage if needed. Guardrails are a workload-specific content safety layer that complements, not replaces, IAM and network-level access controls.

A: VPN tunnels max at 1.25 Gbps each — even with multiple tunnels and ECMP, 5 Gbps consistent throughput is not guaranteed and latency varies with internet path. C: Direct Connect without encryption fails the encryption-in-transit requirement. D: PrivateLink is for reaching AWS service endpoints from within a VPC — it is not a mechanism for connecting on-premises data centers to AWS.
    Question 6 of 12
    A security team wants to replace the company's SSH bastion hosts entirely. Engineers need interactive shell access to EC2 instances for troubleshooting, and all sessions must be audited and logged to a central location. Which AWS service best satisfies these requirements?
    ✅ B is correct. Session Manager provides browser and CLI shell access without SSH keys or open inbound ports. Sessions are logged (commands, output) to CloudWatch Logs or S3. Authentication is through IAM. This directly replaces SSH bastion functionality with improved security and auditability. A: CloudTrail logs AWS API calls — not interactive shell sessions. C: EC2 Instance Connect still uses SSH and requires open port 22; VPC flow logs capture IP traffic metadata, not shell command content. D: AWS Config tracks configuration changes to AWS resources, not shell session content.
    Question 7 of 12
    An ECS task needs to read objects from a specific S3 bucket. The ECS cluster runs on EC2 instances. Which IAM approach follows the principle of least privilege?
    ✅ B is correct. ECS Task IAM Roles assign an IAM role directly to the task definition. Only that task gets the role credentials — via the ECS task metadata endpoint. Other tasks on the same EC2 instance are not affected. Permissions are scoped to the specific bucket ARN. A: EC2 instance role credentials are available to all containers on that instance — all tasks inherit the permissions, violating least privilege. C: Static credentials in environment variables have no automatic rotation and risk exposure through environment inspection. D: Sharing one role across all tasks has the same blast-radius problem as the instance role approach.
    Question 8 of 12
    A Lambda function is configured to run inside a VPC and needs to call the AWS Secrets Manager API to retrieve database credentials. After deployment, the function times out when calling Secrets Manager. What is the MOST likely cause and solution?
    ✅ B is correct. By default, Lambda functions run in an AWS-managed environment with internet access. When placed in a VPC, the function runs on an ENI in your private subnet and loses internet access (unless a NAT Gateway is present). Secrets Manager is a public AWS service endpoint — unreachable from a VPC without internet or a VPC endpoint. Creating a Secrets Manager interface endpoint in the VPC resolves this. A: If the permission were missing, the error would be an authorization failure, not a timeout — timeouts indicate a connectivity failure, not an IAM failure. C: Increasing timeout does not fix a connectivity issue — it just makes the function wait longer before failing. D: Secrets Manager is a global service available in all AWS regions.
    Question 9 of 12
    An organization's security policy requires that all traffic between its private subnets and AWS services must not traverse the public internet. They currently use a NAT Gateway for all outbound traffic, which routes through an internet gateway. Which change satisfies the policy for AWS service traffic?
    ✅ B is correct. VPC endpoints (gateway for S3/DynamoDB, interface for other services) route AWS service traffic through the AWS backbone without touching the internet or requiring a NAT Gateway. The policy requirement is met because traffic never reaches the internet gateway or traverses the public internet. A: An internet gateway routes traffic to the public internet — worse, not better. C: Flow logs provide visibility but do not change the traffic path — the policy violation remains. D: KMS encrypts data at rest; it is not a mechanism for controlling network traffic paths. The NAT Gateway still routes through the internet regardless of KMS configuration.
    Question 10 of 12
    An Amazon ECR repository contains container images that are deployed to ECS production tasks. A new critical CVE is published affecting a library in the base image used by these containers. The images were scanned when they were pushed two months ago and showed no findings at that time. What should a security engineer configure to catch this going forward?
    ✅ B is correct. Amazon Inspector enhanced scanning for ECR provides continuous scanning — it re-evaluates existing images in the repository when new CVEs are published, without requiring images to be rebuilt or re-pushed. Findings are surfaced in the Inspector console and can trigger EventBridge events for automated notification or deployment blocking. A: Rebuilding and re-pushing works but is not scalable — it requires manual action whenever a CVE is disclosed and does not cover images that teams forget to rebuild. C: CloudTrail tracks API operations, not vulnerability data. D: ECR service health is about service availability, not image vulnerability findings.
    Question 11 of 12
    A company connects to AWS via Direct Connect for its primary path and also has a Site-to-Site VPN configured to the same VPC. Under what circumstances will traffic automatically fail over to the VPN?
    ✅ C is correct. Both Direct Connect and VPN advertise routes via BGP. When the Direct Connect connection fails, the BGP session on that path goes down, and the routes advertised by Direct Connect are withdrawn from the routing table. The VPN BGP session remains up and its routes are used automatically. This is standard BGP failover — it requires proper route preference configuration (e.g., local preference to prefer Direct Connect under normal conditions). A: BGP failover is binary — it triggers on session failure, not on throughput thresholds. B: Manual failover defeats the purpose of a resilient dual-path architecture. D: BGP failover is event-driven (session down), not time-based.
    Question 12 of 12
    A company deploys a customer service chatbot using Amazon Bedrock with Guardrails configured for PII redaction and content filtering. The security team states that because Guardrails are enabled, they do not need to configure IAM policies for the Bedrock API — the Guardrails handle all access control. Which statement accurately describes this assessment?
    ✅ B is correct. Bedrock Guardrails are a content safety and policy layer that controls what the foundation model can say — harmful content, PII in outputs, denied topics. They do not control who can call the Bedrock API. IAM policies (bedrock:InvokeModel) are still required to restrict which principals can make API calls. A principal with the IAM permission can call the Bedrock API and may be able to bypass Guardrails by calling without specifying the Guardrail ARN, or by calling a different model. Guardrails and IAM serve complementary, non-overlapping roles.
    Discussion-Style FAQ

    Questions You Will Actually Have

    Click any question to reveal the answer. These are the conversations that come up after studying this material for the first time — questions worth sitting with rather than glossing over.

    🧑‍💻 You ask ›Why is IMDSv1 such a big deal? My app runs on an EC2 instance, not on the internet — what is an attacker actually going to do with the metadata endpoint?
    🛡️ Your MentorThe key insight is that the threat is not an external attacker directly reaching the metadata endpoint — it is your own application being weaponized to make that request for them. If any part of your application accepts a URL and fetches it server-side (image previews, link shorteners, webhooks, curl-based integrations), that is potentially an SSRF vector. The attacker never touches your server directly. They craft a malicious URL that your app fetches for them. The metadata endpoint is on a link-local address that is reachable from inside the instance but not from outside — SSRF abuses the trust boundary between the instance and the metadata service. IMDSv1 makes this trivially exploitable because there is no authentication on the GET request at all.
    🧑‍💻 You ask ›If Direct Connect is private and never touches the public internet, why would I still need encryption on it? Who exactly is going to intercept traffic on a dedicated fiber circuit?
    🛡️ Your MentorThe threat model is narrower but real. Dedicated fiber goes through carrier networks and colocation facilities. Employees at those facilities, carrier insiders, or a party with physical access to the cable route could theoretically splice the fiber or tap the colocation cross-connects. More practically: compliance frameworks (PCI-DSS, HIPAA, FedRAMP) require encryption in transit for regulated data regardless of whether the path is private. The auditor does not care that it is a dedicated circuit — they want a cryptographic guarantee of confidentiality. "Private" is a topology property; "encrypted" is a security property. You need both for regulated workloads. MACsec or VPN-over-DC gives you both on the same physical path.
    🧑‍💻 You ask ›Why not just give the EKS node a broad IAM role and rely on Kubernetes RBAC to control what pods can do? Kubernetes RBAC is already controlling which pods can talk to which services within the cluster.
    🛡️ Your MentorKubernetes RBAC controls what Kubernetes objects a pod can interact with — API server resources like pods, services, configmaps. It has absolutely no influence on what that pod can do when it makes AWS API calls. When a pod runs code that calls s3.GetObject or dynamodb.PutItem, those calls go directly to the AWS API with the IAM credentials in scope — which on a node with a broad IAM role, are the node role's credentials. IRSA solves this by giving each pod its own IAM identity, completely independently of Kubernetes RBAC. The two systems address different access control planes: RBAC for the Kubernetes control plane, IRSA for the AWS IAM plane. You need both.
    🧑‍💻 You ask ›When exactly would I run both Direct Connect and a Site-to-Site VPN at the same time? Is that not redundant and expensive?
    🛡️ Your MentorThink of it as primary path plus automatic failover. Direct Connect gives you the consistent, high-throughput, low-latency path for production traffic. The VPN is your backup — it costs a few dollars a month and provisions in minutes, whereas getting a new Direct Connect circuit if the primary fails would take weeks. Under normal operation, all traffic flows over Direct Connect because your BGP route preferences favor it. If the Direct Connect circuit or your BGP session fails, the VPN path activates automatically — no manual intervention required. The additional cost of the VPN backup is nearly always worth it for any workload where Direct Connect downtime is a business problem. The exam often presents this pattern as the correct answer for "production Direct Connect with resilience requirements."
    🧑‍💻 You ask ›What is the real difference between a gateway endpoint and an interface endpoint? They both let me reach AWS services without the internet — why do I need to know which is which?
    🛡️ Your MentorThe implementation is fundamentally different, and it matters for both cost and architecture. A gateway endpoint is a route table entry — it is entirely software-defined, costs nothing, and works for S3 and DynamoDB only. An interface endpoint is an actual Elastic Network Interface in your subnet — it has an IP address, it uses Private DNS to resolve service endpoint names, it has an hourly cost per AZ, and it works for virtually everything else. The exam tests which type applies to which service. If a question mentions S3 or DynamoDB private access without internet, gateway endpoint is the answer. If it mentions SSM, Secrets Manager, KMS, ECR, or any other service, interface endpoint. Getting these swapped is a common exam mistake.
    🧑‍💻 You ask ›Should I always put Lambda functions inside a VPC? It seems like it would make them more secure by default.
    🛡️ Your MentorOnly put a Lambda in a VPC when it genuinely needs private network access — to an RDS instance, an ElastiCache cluster, an internal API that has no public endpoint. If you put a Lambda in a VPC without a good reason, you are adding latency (ENI setup time), complexity (VPC endpoints or NAT Gateway needed for AWS service calls), and operational overhead for no security benefit. A Lambda that only calls public AWS APIs (S3, DynamoDB, Secrets Manager) through VPC endpoints would need interface endpoints for each service — added cost and management. The security is provided by the execution role scope, not by VPC placement. VPC attachment is an architectural need, not a default security hardening step.
    🧑‍💻 You ask ›Are Bedrock Guardrails a replacement for IAM and network controls on the Bedrock API? If I have content filtering in place, does it matter who can call the model?
    🛡️ Your MentorCompletely different control planes. Guardrails control the content of model interactions — they decide what the model can say, what topics are off limits, what PII can flow through. IAM controls who can call the Bedrock API at all. An attacker who has the IAM permission bedrock:InvokeModel can call the model without specifying your Guardrail ARN — completely bypassing the content controls. Or they could call a different model ID. IAM is the gatekeeper for API access; Guardrails are the content safety layer for legitimate application traffic. You need both. Guardrails should be thought of the same way you think about WAF rules: they add a control layer, but they assume the underlying access controls (IAM, network) are already properly configured.
    🧑‍💻 You ask ›What actually happens if I use one shared Lambda execution role across all my functions? The exam keeps flagging this as wrong, but in practice it seems like it works fine.
    🛡️ Your MentorIt works fine right up until it does not. The blast radius problem is not visible in your monitoring dashboards — it shows up the moment one function is compromised through a dependency vulnerability, event injection, or code flaw. A shared role turns a single-function compromise into a full account-wide lateral movement opportunity. The attacker calls AWS APIs using the shared role and can access every resource that role touches: all the S3 buckets, all the DynamoDB tables, all the secrets. With per-function roles, a compromised function can only access what it specifically needs. Lambda functions are intentionally single-purpose — there is rarely a legitimate reason to share a role. The operational overhead of maintaining separate roles is small; the security benefit is real and measurable.
