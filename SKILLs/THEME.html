Why this module matters

Identity below the application layer

Most IAM architects think about identity in the context of web applications, APIs, and enterprise SSO. But in any large enterprise, a significant portion of access happens at the operating system level — server logins, sudo access, SSH sessions, cron jobs, and service account authentication.

This module fills the gap that most IAM curricula ignore: how identity reaches the OS layer, how it integrates with enterprise directories, and how you design centralized authentication architectures for Linux fleets.

PAM — Pluggable Authentication Modules
A framework in Linux/Unix that provides a flexible mechanism for authentication. Instead of hardcoding auth into every application, PAM provides a common API — applications delegate all auth decisions to the PAM stack, which is configured per-service via /etc/pam.d/.
SSSD — System Security Services Daemon
The bridge between Linux systems and enterprise identity stores (LDAP, Active Directory, Kerberos). SSSD caches identity data locally, enabling logins even when the identity store is temporarily unreachable. It integrates with PAM and NSS to provide centralized identity to the OS.
Authentication flow

Linux SSH → AD authentication

1
SSH client connects
User initiates SSH connection. Linux SSH daemon (sshd) receives the connection request and delegates authentication to PAM via pam_sshd.
2
PAM stack executes
PAM processes the stack in /etc/pam.d/sshd. The pam_sss module hands off to SSSD for identity resolution.
3
SSSD queries Active Directory
SSSD checks its local cache. On a cache miss, it queries the AD domain controller via LDAP/Kerberos, validates credentials, and returns user/group data.
4
Session established
PAM session modules (pam_limits, pam_env, pam_mkhomedir) run. The user's home directory is created if needed. SSH session starts.

Knowledge check

Test your understanding

Q A user can log in to a Linux server when the network is down. Which component enables this and how? ▼
SSSD's local cache. SSSD caches identity data (user attributes, group memberships, credentials) from the last successful authentication. When the identity store (AD/LDAP) is unreachable, SSSD serves the cached data, allowing authentication to succeed offline. The cache_credentials = true option in sssd.conf enables this. The cache TTL is configurable.
Q What is the architectural advantage of SSH certificate authorities over SSH public key pairs? ▼
Centralized lifecycle management. With per-host public key pairs, every server must maintain its own authorized_keys file, and revoking a user's access requires updating every server. An SSH CA issues short-lived signed certificates with embedded principal names and expiry times. Revocation is instant — let the certificate expire or use a CRL. Onboarding new servers requires only trusting the CA public key, not distributing individual public keys.

Key takeaways — M06
  • PAM is the universal authentication framework for Linux/Unix — all applications delegate auth to PAM, which delegates to pluggable modules
  • SSSD is the enterprise bridge: it connects Linux systems to AD/LDAP, caches identity data, and integrates with PAM and NSS
  • SSH certificate authorities provide lifecycle management, short-lived credentials, and centralized revocation — far superior to per-host authorized_keys
  • Kerberos on Linux uses the same AS/TGS infrastructure as Windows AD — realm join makes Linux a first-class Kerberos citizen
  • Infrastructure identity is often the path of least resistance for privilege escalation — it must be governed with the same rigor as application-layer identity

Common mistake
SSH key sprawl
Distributing individual SSH public keys at scale creates an unmanageable revocation problem. If any key is compromised, how many servers need updating? Design for certificate-based auth from day one.
