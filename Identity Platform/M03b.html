Why this module matters

SAML is not legacy — it is the dominant enterprise protocol

Every large enterprise has hundreds of SAML integrations. Salesforce, Workday, ServiceNow, GitHub Enterprise, AWS SSO, Azure applications — all support SAML as a first-class integration. When an enterprise buys a new SaaS application, the first question from IT is almost always: "Does it support SAML?" not "Does it support OIDC?"

SAML was standardized in 2005. OAuth was designed in 2010. By the time OAuth became enterprise-ready, every major SaaS application already had SAML support baked in. This is why SAML will outlive every "SAML is dead" prediction by another decade. Architects who dismiss SAML as legacy cannot design real enterprise identity ecosystems.

This module covers SAML 2.0 at depth — assertion anatomy, binding mechanics, federation patterns, and PingFederate's role as a federation hub. It closes with the definitive SAML vs OAuth decision framework — the most common architectural question you will face.

SAML fundamentals

What SAML 2.0 actually is

SAML 2.0 (Security Assertion Markup Language) is an XML-based open standard for exchanging authentication and authorization data between an Identity Provider and a Service Provider. It defines three things: the assertion format, the protocols for requesting and receiving assertions, and the bindings for transporting those protocols over HTTP.

The three SAML components — assertions, protocols, bindings
Assertions are the payload — XML documents containing statements about a subject. Three assertion types: AuthnStatement (the user authenticated at time T using method M), AttributeStatement (the user has attributes email=alice@corp.com, role=admin), AuthzDecisionStatement (the user is/isn't permitted to access resource R — rarely used in practice, authorization is handled at the application layer).

Protocols define the request/response message formats — the Authentication Request Protocol (AuthnRequest from SP to IdP), the Single Logout Protocol (SLO — coordinated session termination), and the Artifact Resolution Protocol.

Bindings define how protocols are transported over HTTP — HTTP-Redirect (parameters in URL), HTTP-POST (assertions in HTML form), HTTP-Artifact (a reference exchanged by back-channel). The binding choice has significant security and performance implications.
SAML Assertion anatomy — the XML payload an IdP sends to a Service Provider
The assertion validity window — why 5 minutes matters architecturally
The NotBefore / NotOnOrAfter window in SAML Conditions is typically 5 minutes. This is a replay attack defence — a stolen assertion can only be replayed within this window. The SP must also track the assertion's ID attribute in a replay cache and reject any assertion with a previously seen ID, even within the validity window. Architects designing high-security SAML deployments must ensure SPs implement this replay cache — many do not by default.
SAML bindings

How assertions travel — the three HTTP bindings

SAML bindings define how SAML protocol messages are transported over HTTP. The choice of binding affects security, performance, and the size of data you can transmit. Most enterprises use HTTP-POST for assertions and HTTP-Redirect for authentication requests.

HTTP-Redirect Binding
The SAML message is Base64-encoded, deflated (compressed), and sent as a URL query parameter. The user's browser performs a GET redirect. Typically used for the AuthnRequest (SP → IdP) because request payloads are small. The URL is signed by the SP's private key (separate from the XML signature).
Use for: AuthnRequest from SP to IdP. Small payloads only — URL length limits (~2KB). Fast; no form submission.
HTTP-POST Binding
The SAML message is Base64-encoded (not compressed) and embedded in a hidden HTML form field. The browser auto-submits the form via POST. Used for the SAML Response (IdP → SP) because assertions can be large (many attribute values). The XML assertion itself is digitally signed.
Use for: SAML Response (assertion) from IdP to SP. Large payloads. The standard binding for all assertion delivery. Content not visible in browser URL bar.
HTTP-Artifact Binding
Instead of the full assertion, the IdP sends a short "artifact" (opaque reference) to the SP via browser redirect. The SP then calls the IdP's Artifact Resolution Service directly (back-channel SOAP call) to exchange the artifact for the real assertion. The assertion never passes through the browser.
Use for: High-security scenarios where assertion must not touch browser. Financial services. Situations where very large assertions would break HTTP-POST. Requires SP to make direct network call to IdP.
⚠️GotchaHTTP-Redirect assertions — not a thing. Only requests use Redirect binding.
A common misconfiguration: configuring an SP to expect the assertion via HTTP-Redirect binding. SAML assertions cannot reliably be delivered via HTTP-Redirect — they are too large for URL parameters and XML signatures embedded in URL query strings are fragile. The correct combination: AuthnRequest via HTTP-Redirect, SAML Response (containing the assertion) via HTTP-POST. Any SP or IdP configuration that delivers assertions via redirect should be treated as a misconfiguration.
Authentication flows

SP-initiated vs IdP-initiated — the architectural difference

SAML supports two flow directions. The choice between them has significant security implications that most practitioners don't fully appreciate.

Diagram 1 — SP-initiated SAML SSO full sequence (the secure flow)
SP-initiated (recommended)
User → SP → IdP → SP
The user starts at the SP (the application). The SP generates and signs an AuthnRequest, preserves the original resource URL (RelayState), and redirects to the IdP. After authentication, the IdP sends the assertion back to the SP's Assertion Consumer Service (ACS). The SP can validate the InResponseTo attribute against the original request ID. This correlation check prevents assertion injection attacks. Always prefer SP-initiated flows.
IdP-initiated (use with caution)
User → IdP → SP
The user starts at the IdP (e.g., an enterprise portal). The IdP creates an unsolicited assertion and POSTs it to the SP's ACS — without a prior AuthnRequest. There is no InResponseTo attribute to validate. This means the SP cannot verify the assertion was generated in response to a legitimate request — a stolen assertion can be replayed at the SP. IdP-initiated SSO is a known SAML vulnerability. Use only when operationally required and implement replay cache + IP binding compensating controls.
Federation architecture

PingFederate as a federation hub

In large enterprises, the naive approach is to create a direct SAML trust relationship between the enterprise IdP and each Service Provider. With 500 SaaS applications, that means 500 bilateral trust relationships — each with separate metadata, certificates, and attribute mapping configurations. This is the N×N integration problem, and it is the primary reason federation hubs exist.

Diagram 2 — Federation Hub-and-Spoke architecture with PingFederate
The N×N problem — why the hub model matters
Without a federation hub, 10 identity sources × 50 SPs = 500 bilateral trust relationships. Adding a new SP requires 10 new integrations (one per identity source). Adding a new identity source requires 50 new integrations. With a hub: each new SP requires exactly 1 integration (SP ↔ hub). Each new identity source requires exactly 1 integration (source ↔ hub). PingFederate is valuable not because it does SAML — any IdP can do SAML. It is valuable because it decouples the identity source count from the SP count, eliminating N×N integration complexity.
PingFederate's protocol translation capability
PingFederate can receive identity assertions in one protocol and issue them in another. A user authenticated via Kerberos (Active Directory) can receive a SAML assertion for Salesforce, an OIDC ID token for a modern web app, and a WS-Federation token for a legacy .NET application — all from the same authentication event. This is the protocol brokering pattern, and it is the primary reason large enterprises choose PingFederate over simpler IdPs: it bridges the legacy-to-modern protocol gap without requiring application rewrites.
The definitive comparison

SAML vs OAuth 2.0/OIDC — when to choose which

This is the most common architectural question in enterprise IAM. The answer is not "OAuth is better" — it depends entirely on the use case. Both protocols solve different problems. Understanding the decision criteria is what separates architects from enthusiasts.

The architect's decision rule — simple and unambiguous
Choose SAML when: The SP requires SAML (legacy SaaS, partner org, no OIDC support). The flow is browser-based enterprise SSO. You're integrating with an existing SAML federation hub.

Choose OAuth/OIDC when: The use case involves APIs, mobile apps, or SPAs. The SP supports OIDC. You're building new integrations from scratch. You need delegation, M2M, or fine-grained API scopes.

Choose both via protocol brokering when: Your hub (PingFederate) can issue either protocol. The user authenticates once; the hub translates the assertion to whatever the SP requires. This is the enterprise answer — not SAML vs OAuth, but both via a translation layer.
Trust establishment

SAML metadata — how trust is established

SAML trust is established by exchanging metadata — XML documents that describe each party's identity, endpoints, supported bindings, and public certificates. This is the foundational configuration step before any SAML SSO can work.

X.509 encryption certificate (to encrypt assertions, if used)

⚠️GotchaCertificate expiry in SAML metadata — the most common production outage
SAML signing certificates embedded in metadata have expiry dates. When the IdP's signing certificate expires, every SP that has cached the old certificate will fail to validate new assertions — causing a complete SSO outage for all integrated applications simultaneously. This is one of the most common causes of enterprise-wide SSO outages. Architects must implement: (1) certificate rotation procedures that publish new certs in metadata before retiring old ones, (2) monitoring alerts for certificate expiry 90/60/30 days in advance, (3) automated SP metadata refresh where possible. PingFederate supports dual-certificate configuration to enable zero-downtime rotation.
Integration patterns

SAML proxy & protocol translation patterns

Not every enterprise scenario involves a simple IdP-to-SP SAML flow. These three patterns handle the complex integration scenarios architects encounter in real enterprise environments.

Pattern 1
SAML Proxy (Assertion Brokering)
PingFederate acts as both an SP (to the enterprise IdP) and an IdP (to the SaaS applications). The user authenticates to the enterprise IdP; PingFederate receives the assertion, applies attribute mapping and transformation, and re-issues a new assertion to the SP. This enables: attribute normalization, claim enrichment from additional sources (LDAP lookup), policy enforcement, and protocol adaptation — all transparent to the SP.
Pattern 2
SAML → OAuth/OIDC Bridge
The user authenticates via SAML (enterprise IdP). PingFederate validates the SAML assertion and issues an OAuth access token or OIDC ID token to modern applications that don't support SAML. This is the migration bridge pattern — it allows modern apps to receive OIDC tokens while the enterprise IdP continues issuing SAML assertions. No change required at the IdP or the modern app.
Pattern 3
B2B Partner Federation
Two enterprise organizations establish a SAML cross-domain trust. Users from Company A can access resources in Company B using their Company A credentials. PingFederate at each org's boundary establishes the trust via metadata exchange. Attribute mapping defines how Company A's roles/groups translate to Company B's access model. This extends the federation hub model across organizational boundaries.
Future direction

Decentralized identity — where the industry is heading

Both SAML and OAuth are built on a centralized trust model — the enterprise controls the IdP, and the IdP is the trust anchor. Decentralized identity challenges this assumption. Architects should understand the direction even if enterprise adoption is still early.

DID — Decentralized Identifiers
Self-sovereign identity anchors
A DID is a globally unique identifier (e.g., did:web:company.com:alice) that a principal controls without relying on a central registry. DIDs resolve to a DID Document (JSON-LD) that contains public keys, authentication methods, and service endpoints. The key innovation: the principal — not the enterprise — controls their identity anchor. Enterprise relevance: DID-based authentication for B2B partner access, eliminating the need for bilateral metadata exchange. Still maturing — Microsoft Entra Verified ID is the most production-ready enterprise implementation.
VC — Verifiable Credentials
Digitally-signed portable claims
A Verifiable Credential (W3C spec) is a cryptographically signed claim issued by one party (the Issuer — e.g., a university, employer, or government) that a holder presents to a verifier without the issuer being involved in the presentation. Like a digital diploma or passport. Enterprise relevance: Employee credentials that persist across employers. Healthcare practitioner licenses. Regulatory compliance certifications that travel with the individual. Reduces reliance on directory synchronization for B2B scenarios. The VC/DID stack is to future IAM what SAML was to 2005 — foundational but not yet ubiquitous.
Knowledge check

Test your federation depth

Q1 A SaaS vendor tells you they support "IdP-initiated SAML SSO only." You're the IAM architect. What is the security concern, what compensating controls exist, and what would you negotiate with the vendor? ▼
Security concern: IdP-initiated SSO sends an unsolicited assertion to the SP's ACS without a prior AuthnRequest. The SP has no InResponseTo attribute to validate, meaning it cannot verify the assertion was generated in response to a legitimate user action. This enables assertion injection attacks — a stolen valid assertion from one session can be replayed at the SP, potentially by a different user or from a different device, within the assertion's validity window (typically 5 minutes).

Compensating controls: (1) Require the SP to implement a JTI/assertion ID replay cache — reject any assertion with a previously seen ID. (2) Require the SP to validate the assertion's SubjectConfirmationData — specifically the Address attribute (client IP). (3) Reduce assertion validity window to 1–2 minutes. (4) Enable assertion encryption so stolen assertions cannot be read or replayed by intermediaries without the SP's private key.

Vendor negotiation: Push for SP-initiated SSO support. Most modern SaaS vendors support both — if they only support IdP-initiated, ask their product team why and when SP-initiated will be added. Document the risk formally in your security exception process. If the application handles sensitive data, the answer should be "we don't integrate until SP-initiated is supported."
Q2 Your enterprise uses PingFederate as the federation hub with 300 SAML SPs. The signing certificate expires in 30 days. Design the zero-downtime certificate rotation procedure. ▼
Zero-downtime SAML certificate rotation using dual-certificate publication:

Step 1 — Generate new certificate (Day 0): Generate a new RSA-2048 or EC-P256 signing certificate in PingFederate with a 2-year validity. Do NOT yet use it for signing.

Step 2 — Publish both certs in metadata (Day 0–7): Configure PingFederate to publish BOTH the old and new certificates in its IdP metadata (as separate <KeyDescriptor use="signing"> elements). Push the updated metadata to all 300 SPs — automated where possible, manual ticket queue where not. SPs can now validate assertions signed with either certificate.

Step 3 — Wait for metadata propagation (Day 7–14): Confirm all SPs have received the updated metadata. Monitor SP login success rates — any SP still using old cached metadata will still work (old cert still valid and still signing).

Step 4 — Switch signing to new cert (Day 14): Configure PingFederate to sign all new assertions with the new certificate. SPs with updated metadata will validate against the new cert. SPs still on old metadata will validate against the old cert — both are in metadata, both are trusted.

Step 5 — Remove old cert (Day 25, before expiry): Remove old certificate from PingFederate metadata. Any SP that did not pick up the updated metadata will now fail — these are identified and fixed during the propagation window.

Monitoring: Alert on assertion validation failures at any SP during steps 4 and 5. This indicates a SP has not yet received updated metadata.
Q3 A developer asks: "Can we just use the SAML assertion the user received for Salesforce to also authorize calls to our internal REST API?" What is your answer and why? ▼
No — and the reasons reveal fundamental SAML/OAuth architecture:

Problem 1 — Audience restriction: The SAML assertion's AudienceRestriction is set to Salesforce's EntityID. Your REST API's entity ID is different. Any correctly implemented REST API that validates the assertion audience will reject it. You cannot present a Salesforce assertion to a different service provider.

Problem 2 — Transport incompatibility: SAML assertions are XML documents designed to be delivered via browser POST. REST APIs expect HTTP Authorization headers — specifically Bearer tokens or JWTs. There is no standard mechanism for presenting a SAML assertion as an API authorization credential.

Problem 3 — Size and performance: SAML assertions can be 2–10KB of XML. Embedding one in every API request header is impractical and slow compared to a 300-byte JWT access token.

Correct architecture: Use the SAML SSO flow for browser authentication. At your application layer, after the SAML assertion is validated, issue an OAuth access token (from an internal AS) scoped for your REST API. The user is authenticated via SAML; the API call is authorized via OAuth. PingFederate can act as the bridge — accept the SAML assertion and issue an OAuth token — via the SAML → OAuth bridge pattern.
Q4 A partner organization wants to federate with your enterprise so their employees can access your internal applications. Design the B2B SAML federation architecture including trust establishment, attribute mapping, and deprovisioning. ▼
B2B SAML federation architecture:

Trust establishment: (1) Both organizations exchange IdP/SP metadata (PingFederate metadata XML). Your PingFederate becomes an SP to their IdP and an IdP to your internal applications. (2) Establish the trust via metadata import in PingFederate — define the partner connection, import their IdP metadata, configure your SP metadata. (3) Define the NameID format — transient (no linkage, highest privacy) vs persistent (enables user record correlation). For B2B, persistent NameID allows local account provisioning.

Attribute mapping: Their IdP will send attributes defined by their schema — which may not match your internal schema. Configure PingFederate's attribute mapping to: (a) map their email/UPN attribute to your user identifier, (b) map their group/role attributes to your local entitlements (e.g., their "PartnerAdmin" group maps to your "VendorPortal-ReadWrite" role), (c) add a fixed attribute identifying the partner organization for audit purposes.

Provisioning: On first successful assertion from the partner IdP, JIT (Just-In-Time) provisioning creates a local shell account in your directory with limited base access. Full access is provisioned via access request workflow. The local account's identity is correlated to the partner's NameID.

Deprovisioning: This is the hard part — partner IdPs don't typically notify you when an employee leaves. Solutions: (1) SCIM provisioning from the partner org to your IGA system, (2) Time-limited access tokens that expire after 90 days and require re-certification, (3) Regular reconciliation — if an employee's assertion stops being seen for 30 days, disable their local account.

Key takeaways — M03b · SAML 2.0 & Federation
  • SAML is not legacy — it is the operational standard for enterprise SaaS SSO. Every large enterprise has hundreds of SAML integrations. Architects who can't design SAML flows cannot design real enterprise identity ecosystems.
  • Three SAML components must be distinguished: Assertions (the payload — AuthnStatement, AttributeStatement), Protocols (the message formats — AuthnRequest, Response, SLO), Bindings (the transport — HTTP-Redirect for requests, HTTP-POST for assertions, HTTP-Artifact for high-security).
  • SP-initiated SSO is architecturally safer than IdP-initiated because the SP can validate InResponseTo, preventing assertion injection. IdP-initiated SSO is a security risk that requires compensating controls.
  • Federation hubs (PingFederate) solve the N×N integration problem. They decouple identity sources from service providers, perform protocol translation, and provide attribute mapping — reducing 500 bilateral integrations to a single hub with 1+1 per new participant.
  • SAML and OAuth solve different problems and are not substitutes. SAML for browser SSO to enterprise SaaS. OAuth/OIDC for APIs, mobile, delegation, and M2M. Protocol brokering via PingFederate enables both simultaneously.
  • SAML certificate expiry is the most common cause of enterprise SSO outages. Design certificate rotation procedures with dual-publication, automated metadata refresh, and 90-day advance alerting.
  • Decentralized identity (DID/VC) is the emerging paradigm — self-sovereign identity anchors and portable verifiable credentials that don't depend on a central IdP. Microsoft Entra Verified ID is the current enterprise entry point.

Protocols are complete.
Now: how do you prove who's there?

M03a and M03b gave you the two foundational federation protocols — OAuth/OIDC for modern API-first flows, SAML for enterprise SSO. Both protocols handle the mechanics of asserting identity across domains. Neither protocol specifies how strongly that identity must be proven before the assertion is issued.

Module M04a covers authentication factors and MFA architecture — the layer that sits inside the IdP, determining what evidence a user must present before the IdP will issue a SAML assertion or OAuth token. FIDO2, WebAuthn, passkeys, PingID, adaptive risk engines, and step-up authentication flows all live here. Understanding this module means you can design the complete authentication journey from "user opens browser" to "SAML assertion delivered to SP."

M04a was deliberately placed in Phase 1 alongside the protocol modules — not later — because every protocol design decision has an MFA implication. The OIDC acr_values parameter requests a specific authentication assurance level. SAML's AuthnContextClassRef carries the assurance level that was achieved. You need M04a before you can design complete end-to-end authentication architectures.
