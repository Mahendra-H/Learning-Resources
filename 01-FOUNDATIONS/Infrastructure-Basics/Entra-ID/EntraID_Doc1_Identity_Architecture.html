CH 01

The Identity Landscape Shift

Before touching a single Entra ID configuration, you need to understand why it exists the way it does. Microsoft didn't build a better Active Directory — they built something fundamentally different. Understanding that difference is the key that unlocks everything else.

The Problem with On-Premises Active Directory at Scale

Think of on-prem Active Directory like a massive filing cabinet system in a corporate building. Every employee, computer, and printer has a folder in the cabinet. The cabinet works perfectly — as long as everyone works in that building. But what happens when 40% of your workforce starts working from home, 60% of your apps move to the internet, and you acquire 3 companies with their own filing cabinets? You'd need couriers running between buildings 24/7. That courier system is what Microsoft built for 20 years — it's called Azure AD Connect. Entra ID is the moment they finally said "let's move the filing cabinet to a location everyone can reach."

Active Directory was designed in 1999 for a world where:

🏢
Everyone was on-prem
Users sat in offices, connected to a LAN. VPN was a niche concept, not a default.
🖥️
Applications were hosted internally
SharePoint, Exchange, and line-of-business apps ran on your hardware in your datacenter.
🔒
The network perimeter was the security boundary
Firewall = security. If you were inside the network, you were implicitly trusted.
🐢
Change was slow
IT provisioned accounts. Users rarely needed immediate access to new systems.

None of those assumptions hold today. Cloud-native identity needs to handle authentication from any network, for any device, to any app, at any time — with zero implicit trust based on network location.

The Evolution: AD → Azure AD → Microsoft Entra ID

1999–2010
Active Directory Dominates
Kerberos + NTLM authentication, LDAP directory, Group Policy for config management. The gold standard for enterprise identity — in a world of LANs and datacenters.
2010
Azure Active Directory Launches
Not AD in the cloud — a completely new, cloud-native identity service built for SaaS apps, Office 365, and REST APIs. Same name, completely different architecture. This naming decision confused everyone for a decade.
2014–2018
Hybrid Identity Becomes the Standard
Azure AD Connect lets organizations sync on-prem AD identities to the cloud. 90% of enterprise deployments became hybrid. The "courier system" era begins.
2020–2022
Zero Trust Adoption Accelerates
COVID-19 demolishes the network perimeter model overnight. Identity becomes the new security boundary. Conditional Access and MFA move from "nice to have" to "mandatory."
2023
Microsoft Entra ID
Azure AD is renamed to Microsoft Entra ID, positioned as the centerpiece of the broader Microsoft Entra product family (covering external identities, permissions management, and more).

What Entra ID Actually Is — and Isn't

The #1 misconception: "Entra ID is just Active Directory in the cloud." This is like saying a jet engine is just a bigger propeller. They both move planes, but the engineering is completely different. Entra ID has NO organizational units (OUs), NO Group Policy Objects (GPOs), NO Kerberos, NO LDAP protocol. It is a fundamentally different system that serves similar identity purposes through entirely different mechanisms.

Entra ID is an Identity-as-a-Service (IDaaS) platform. Unlike PingFederate (which is a federation broker you install and configure) or PingDirectory (which is an LDAP directory server), Entra ID is a fully managed cloud service that combines:

📁
Directory Service
Stores users, groups, devices, applications. The data plane — equivalent to PingDirectory/AD DS.
🔐
Authentication Engine
OAuth 2.0, OIDC, SAML, WS-Fed. The protocol plane — what PingFederate does, but built-in.
🛡️
Access Policy Engine
Conditional Access — evaluates risk signals and enforces access controls. No PingFederate equivalent.
🔄
Lifecycle Management
User provisioning, access reviews, entitlement management. Built-in IGA capabilities.
📱
Device Management
Device registration, join, and compliance integration with Intune.
🔍
Identity Protection
ML-driven risk detection for compromised credentials, impossible travel, anonymous IPs.
In your PingFederate world, you deploy PingFederate for federation, PingDirectory for the directory, PingAccess for policy enforcement, and PingDataGovernance for governance — separate products that you integrate. In Entra ID, all of this is ONE managed service. The upside: simpler architecture, always updated. The downside: less granular control, you're bound by Microsoft's feature roadmap and tenant configuration model.

CH 02

Tenant Architecture

The tenant is the atom of the Entra ID universe. Everything else — users, apps, groups, policies — exists within a tenant. Get this mental model right and everything downstream clicks into place.

What is a Tenant? (Really)

Imagine Microsoft Azure as a massive, multi-story office building. A tenant is your company's entire floor. You have your own locked entrance, your own filing cabinets (directory), your own security desk (authentication), and your own rulebook (policies). Microsoft maintains the building infrastructure — elevators, power, internet — but your floor is yours. No other tenant can see into your floor unless you explicitly invite them (B2B). Your floor also has a unique address: your Tenant ID (a GUID) and your primary domain (yourdomain.onmicrosoft.com, or your verified custom domain).

A tenant is a dedicated, isolated instance of Microsoft Entra ID. It's created when an organization signs up for any Microsoft cloud service. Key characteristics:

  • Every tenant has a globally unique Tenant ID (UUID format: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx)
  • Tenants have a default *.onmicrosoft.com domain and can have multiple verified custom domains
  • Tenant isolation is enforced at the infrastructure level — data never crosses tenant boundaries without explicit cross-tenant configuration
  • One organization typically has ONE production tenant (though large enterprises sometimes use multiple for division isolation)
M&A Integration Scenario (your wheelhouse): Company A acquires Company B. Both have Entra ID tenants. You have three options: (1) Tenant Merge — migrate all of B's users into A's tenant; (2) B2B Federation — keep both tenants, set up cross-tenant sync so B users can access A's apps as guest users; (3) Dual-tenant coexistence — long-term parallel operation with cross-tenant access policies. Option 2 is the most common initial approach during M&A because it avoids disruption and lets you migrate methodically. In a divestiture (your other specialty), you'd do the reverse — spin up a new tenant and migrate a subset of identities out.

Domains and Tenant Identity

Every tenant has one initial domain in the format companyname.onmicrosoft.com. This is permanent and cannot be changed or deleted. Organizations then add and verify their custom domains (e.g., contoso.com).

One domain is designated the Primary Domain — this determines the default UPN suffix for new users. In hybrid environments, this has significant impact on user UPN strategy (more on this in Chapter 7).

CH 03

The Directory Model

If Chapter 1 was about why Entra ID exists, this chapter is about how its data is structured. For someone who knows LDAP and PingDirectory, this is the most important unlearning + relearning in the entire series.

LDAP Hierarchical Model vs. Entra ID Graph Model

LDAP is like a family tree. Everything has a parent. You navigate by following branches: ou=Users,dc=contoso,dc=com. You always know exactly where something "lives" in the tree. Entra ID is like a social network. Everything exists at the same level (no hierarchy, no OUs), but objects are connected to each other by relationships: User is a member of Group. Device is owned by User. Application has a service principal in each tenant. You navigate by following relationship edges, not tree branches.
LDAP Hierarchical Model vs. Entra ID Flat Graph Model

The DirectoryObject Base Type

In Entra ID, everything is a DirectoryObject. Users, groups, devices, service principals, applications — they all inherit from the same base type. This is why the Microsoft Graph API uses /directoryObjects endpoints and why you can often query across object types using the same API patterns.

In PingDirectory, every entry has an objectClass hierarchy (e.g., inetOrgPerson → organizationalPerson → person → top). Entra ID's DirectoryObject base type is conceptually similar — a base schema that all objects extend. The key difference: in LDAP you can stack multiple objectClasses on one entry. In Entra ID, each object type is distinct (a User is not a Device is not a Group, even though they all have an objectId).

Key Object Types and Their Identifiers

Object Type Primary Identifier Human-Readable ID LDAP Equivalent
User objectId (GUID) userPrincipalName DN + uid/mail
Group objectId (GUID) displayName DN + cn
Application appId (GUID) = client_id displayName No direct equivalent
Service Principal objectId (GUID) servicePrincipalNames Service account entry
Device deviceId (GUID) displayName Computer entry
Never confuse appId and objectId for applications. Every Application Registration has an appId (the client_id used in OAuth flows — consistent across all tenants) AND an objectId (the directory object ID — unique to the tenant). When you're configuring OAuth, you use appId. When you're querying the Graph API for the object, you use objectId. This trips up nearly everyone coming from the LDAP world.

User Types: Member vs. Guest

The userType attribute is crucial and often overlooked:

Member Guest
Created by your tenant. Full directory member. Invited from another tenant (B2B) or external email.
Full access to directory listing by default (can enumerate users, groups). Restricted directory access by default — cannot enumerate other users/groups.
Synced from on-prem AD if hybrid. Authenticates in their home tenant, accesses your tenant as a guest.
Appears in Exchange GAL by default. Has a shadow user object in your tenant with #EXT# in the UPN.
Real Scenario — M&A Guest Access: During the early phase of a merger, you need partner engineers to access your Azure DevOps and SharePoint. Instead of creating full Member accounts, you invite them as B2B guests. Their UPN in your tenant looks like: johndoe_partnercompany.com#EXT#@contoso.onmicrosoft.com. They authenticate using their own tenant's credentials. You control access via Conditional Access. When the merger completes and accounts are migrated, you convert them to Member accounts or deprovision the guest objects.

Cloud-Only vs. Synced Users

This distinction is fundamental and affects what you can and cannot manage in Entra ID:

Attribute Cloud-Only User Synced User (Hybrid)
onPremisesSyncEnabled null true
Password management Managed in Entra ID (SSPR, admin reset) Must be changed in on-prem AD, syncs to cloud (or SSPR with writeback)
Attribute editing Edit directly in Entra ID / Graph API Most attributes are read-only in Entra ID — source of truth is on-prem AD
Deletion Delete in Entra ID Delete in on-prem AD — sync removes from Entra ID
UPN Set in Entra ID Sourced from on-prem AD, suffix must match a verified domain
Gotcha for automation scripts: If you write a Graph API script to update user attributes (like department, manager, or phone number) and the user is synced from on-prem AD, your write will either fail or be overwritten on the next sync cycle. Always check onPremisesSyncEnabled before attempting writes. Cloud-only users: write to Graph. Synced users: write to on-prem AD and let it sync.

CH 05

Group Management

Groups in Entra ID are more complex than LDAP groups — but also more powerful. The type of group you create determines how membership is managed, what the group can do, and which Microsoft 365 services it integrates with.

The Four Group Types You Must Know

Type Membership Primary Use LDAP Equivalent
Security Group Assigned or Dynamic Access control — assigning permissions to apps, resources, Azure RBAC roles groupOfNames / posixGroup
Microsoft 365 Group Assigned Collaboration — comes with a mailbox, SharePoint site, Teams channel, Planner No equivalent (it's a collaboration workspace)
Dynamic Group Rule-based (auto) Automated membership based on user/device attributes — zero manual management Virtual list view / computed groups
Role-Assignable Group Assigned Groups that can be assigned to Entra ID directory roles — for RBAC delegation No equivalent
Think of a Dynamic Group like a saved search query that automatically populates itself. You write a rule like (user.department -eq "Engineering") and (user.accountEnabled -eq true) and Entra ID continuously evaluates it. When a new engineer is hired and their department attribute is set, they automatically become a member. When someone transfers out of Engineering, they're automatically removed. For an IAM engineer, this is extremely powerful for birthright access automation — no provisioning workflows needed for group membership.
In PingDirectory, you might use computed groups or virtual attributes to achieve similar behavior. In LDAP-based systems, dynamic group computation is often expensive at query time (computing membership on the fly). Entra ID's dynamic groups are evaluated asynchronously (there's a processing delay of up to 24 hours for large membership changes), but the resulting membership is stored — so queries are fast.

Nested Groups and Their Critical Limitation

This is a major gotcha coming from the AD/LDAP world:

Entra ID does NOT support nested group membership for most scenarios. In Active Directory, you can nest groups inside groups (AGDLP strategy) to build sophisticated access hierarchies. In Entra ID, if Group A is a member of Group B, a user in Group A does NOT automatically get the permissions of Group B for most resources. There are some exceptions (Exchange/SharePoint may honor nesting for some operations), but for Entra ID app permissions, Azure RBAC, and Conditional Access — nested groups are not honored. This is a breaking design change if you're migrating group-based access strategies from on-prem.

Groups as the Authorization Vehicle

Real Scenario — SSO App Onboarding: You're onboarding a new SaaS application (say, a third-party ITSM tool) via Entra ID SSO. You need to control which users can access it. The pattern is: (1) Create a Security Group called APP-ITSM-Users; (2) Assign this group to the Enterprise Application (this gates authentication — only group members can sign in); (3) Optionally create app roles and assign different groups to different roles (e.g., APP-ITSM-Admins and APP-ITSM-Agents); (4) The group membership appears in the SAML assertion or JWT as a claim that the app uses for authorization. This is the direct equivalent of using PingFederate contract mapping with LDAP group membership attributes.
CH 06

Authentication Architecture

This is your home territory — OAuth 2.0, OIDC, SAML. But Entra ID implements these protocols with Microsoft-specific extensions and behavioral patterns that matter in production. Understanding where Entra ID diverges from the spec is what separates architects from configurators.

Protocol Support Matrix

Protocol Entra ID Support PingFederate Equivalent Notes
OAuth 2.0 Full OAuth AS capabilities Auth Code + PKCE, Client Credentials, OBO, Device Code, Implicit (legacy)
OpenID Connect 1.0 Full OIDC IdP adapter ID tokens, UserInfo endpoint, discovery document at /.well-known/openid-configuration
SAML 2.0 Full SAML IdP/SP SP-initiated and IdP-initiated SSO, artifact and post bindings
WS-Federation Legacy WS-Fed IdP Primarily for legacy Microsoft apps (SharePoint on-prem, ADFS)
Kerberos No N/A Cloud-only users have no Kerberos. Hybrid: Seamless SSO simulates Kerberos-like behavior via PRT.
NTLM No N/A Not supported. Legacy auth that Entra ID actively blocks via CA policies.

The Entra ID OAuth / OIDC Endpoints

Every tenant has its own set of well-known endpoints. This is different from PingFederate where you have one base URL. In Entra ID, the tenant ID (or domain) is part of the URL:

// Tenant-specific endpoints Authorization: https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/authorize Token: https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token OIDC Discovery: https://login.microsoftonline.com/{tenantId}/v2.0/.well-known/openid-configuration JWKS: https://login.microsoftonline.com/{tenantId}/discovery/v2.0/keys // Multi-tenant endpoints (accepts users from any tenant) Authorization: https://login.microsoftonline.com/common/oauth2/v2.0/authorize Token: https://login.microsoftonline.com/common/oauth2/v2.0/token // Consumer-only endpoint (Microsoft personal accounts) Authorization: https://login.microsoftonline.com/consumers/oauth2/v2.0/authorize
When to use /common vs. /{tenantId}: For internal line-of-business apps — always use your tenantId. This ensures only your tenant's users can authenticate. Using /common means any Microsoft account can attempt auth — you then must validate the tid claim in the token to ensure it matches your tenant. Forgetting to validate tid when using /common is a security vulnerability.

The Primary Refresh Token (PRT) — Windows SSO Magic

The PRT is something you won't find in PingFederate land. It's a Microsoft-specific long-lived credential issued to managed devices that enables seamless SSO across all Microsoft cloud services.

Think of the PRT like an airport lounge membership card. When you check in (device join + user sign-in), you receive a card that's tied to both you and your device. Every time you walk up to a Microsoft service's door, the bouncer (WAM — Web Account Manager) flashes the card on your behalf. You don't re-enter your password. The card is also checked against a real-time validity database — if your account is compromised and disabled, the card immediately becomes invalid, even if its physical expiry hasn't passed (this is Continuous Access Evaluation).

CH 07

Hybrid Identity Deep Dive

Hybrid identity is where 90% of enterprise Entra ID deployments live. It's also where the most complexity, the most confusion, and the most production incidents occur. This chapter goes deep — because your work at Company A almost certainly involves hybrid identity in every M&A and divestiture scenario you touch.

The Hybrid Identity Problem Statement

Your organization has run Active Directory for 15 years. Every user, computer, and group exists in AD. Tens of thousands of on-prem app integrations depend on Kerberos and LDAP. Now you're moving to Microsoft 365 and Azure. You can't rip-and-replace AD overnight. You need both systems to coexist — and you need users to have ONE identity that works in both worlds. That's the hybrid identity problem. Microsoft's answer is a synchronization bridge that makes on-prem identities available in the cloud while keeping AD as the source of truth.

The Three Synchronization Options

Hybrid Identity Architecture — Sync Methods Comparison

Password Hash Sync vs. Pass-Through Auth vs. Federation

This is the most consequential architectural decision in a hybrid deployment. It determines where authentication actually happens — in the cloud or on-premises.

Criterion Password Hash Sync (PHS) Pass-Through Auth (PTA) Federation (ADFS)
Auth location Entra ID (cloud) — hash validated in cloud On-premises — auth agent validates with DC On-premises ADFS server
Internet dependency None — works even if on-prem is down Needs on-prem agent reachable Needs ADFS reachable from internet
Password security concern Hash of hash synced — no plaintext. Acceptable for most. No password data in cloud. Preferred by security-sensitive orgs. No password in cloud. Full control.
Smart Lockout / Identity Protection ✅ Full support — Entra ID sees auth events ✅ Partial — cloud and on-prem lockout separate ❌ Limited — auth is opaque to Entra ID risk engine
SSPR (Password Reset) ✅ With writeback to AD ✅ With writeback to AD ❌ Must use ADFS password change
Microsoft recommendation ✅ Recommended for most ✅ Recommended for compliance-sensitive ⚠️ Legacy — migrate away when possible
Divestiture Scenario: Company A divests a business unit. The divested unit gets a new Entra ID tenant. Day 1, you need their 2,000 users to have working identities in the new tenant. Strategy: (1) Export user objects from the source AD using AD Connect health data; (2) Create new user accounts in the new tenant via Graph API bulk provisioning; (3) The divested unit's on-prem AD syncs to the new tenant via Cloud Sync; (4) Use Password Hash Sync initially (so users can authenticate immediately with their existing passwords via SSPR); (5) After 90 days, assess whether to keep PHS or move to PTA. The immutableId (sourced from AD's objectGUID) is the anchor attribute that prevents duplicate object creation during the sync. If you get the immutableId wrong, you'll get duplicate cloud accounts — a production incident waiting to happen.

Device Join Types in Hybrid Environments

The device join type determines which authentication mechanisms a device can use and what access it gets. This is critical for Conditional Access policies that require "compliant device" or "hybrid joined device."

Join Type trustType in Graph Auth Capability Typical Use Case
Hybrid AD Joined ServerAd Both Kerberos (on-prem) and PRT (cloud) Corporate Windows PCs managed by Group Policy + Intune. The most common enterprise scenario.
Entra ID Joined AzureAd PRT (cloud only). No Kerberos. New cloud-first devices, VDI, remote workers. No dependency on on-prem DC.

Seamless SSO — The Kerberos Bridge

When you enable Seamless SSO alongside PHS or PTA, users on domain-joined machines get automatic sign-in to cloud services — no password prompt — even though Entra ID doesn't speak Kerberos.

Seamless SSO works like a backdoor handshake. During setup, a computer account called AZUREADSSOACC$ is created in your on-prem AD. This account's Kerberos decryption key is shared with Entra ID. When a domain-joined PC tries to access a Microsoft cloud service, it silently requests a Kerberos ticket for AZUREADSSOACC$ from the on-prem DC. This Kerberos ticket is sent to Entra ID, which decrypts it (using the shared key) and knows "this request came from a domain-joined machine running as this AD user" — so it issues a cloud SSO token without a password challenge. PingFederate has no equivalent to this — it's uniquely enabled by Microsoft's control over both AD and Entra ID.

UPN Strategy in Hybrid — The Gotcha That Breaks Sign-In

The most common hybrid identity misconfiguration: In AD, users might have a UPN like jsmith@contoso.local (with a .local domain — not routable on the internet). When this syncs to Entra ID, the UPN comes along — but contoso.local is NOT a verified domain in your Entra ID tenant, so the sync agent substitutes it with the *.onmicrosoft.com fallback: jsmith@contoso.onmicrosoft.com. Now your user's cloud UPN doesn't match their email address — sign-in confusion, broken SAML assertions, wrong claims. The fix: add a routable domain suffix (e.g., contoso.com) to AD, verify it in Entra ID, update all user UPNs in AD to use the routable suffix before or during sync setup. This is a pre-migration planning task that gets skipped 40% of the time.

🔬 Deep Dive: Governance in Hybrid Environments

Lifecycle Workflows

Entra ID Lifecycle Workflows automate identity tasks triggered by HR events. In a hybrid environment, the challenge is that your source of truth may be on-prem AD, but governance workflows run in the cloud:

  • Joiner workflow: HR creates user in Workday → Entra ID provisioning creates cloud user → AD Connect creates AD account via provisioning agent → device, email, and app access provisioned automatically
  • Mover workflow: Department change in HR → attribute update flows to both Entra ID and AD → dynamic group membership updates → app access adjusts automatically
  • Leaver workflow: Termination in HR → Entra ID disables account → Conditional Access blocks any active sessions via CAE token revocation → AD account disabled via writeback within minutes

Access Reviews in Hybrid

Access Reviews let reviewers (managers, resource owners) periodically certify whether users still need their access. The catch in hybrid environments: reviews run against Entra ID group membership. If a group is synced from on-prem AD (and writable only in AD), review decisions must be written back to AD. This requires Group Writeback to be configured. Without it, reviews happen in the cloud but have no effect on the on-prem group that actually controls access.

PIM in Hybrid Contexts

Privileged Identity Management provides just-in-time elevation for Entra ID roles. For on-prem privileged access, you need a separate PAM solution (CyberArk in your case). These are separate systems — Entra ID PIM manages cloud roles, CyberArk manages on-prem privileged sessions. There's no native bridge between them. Governance teams often maintain dual PAM coverage: PIM for cloud admin roles, CyberArk for server and application privileged access.

🔬 Deep Dive: Multi-Forest and M&A Sync Architectures

Single Forest → Single Tenant (Standard)

Most common. One AD forest syncs to one Entra ID tenant. Simple, well-documented, low risk.

Multi-Forest → Single Tenant (M&A Scenario)

Post-acquisition: two separate AD forests (your company + acquired company) need to sync into one Entra ID tenant. This is where Entra Cloud Sync shines over Azure AD Connect — you can deploy Cloud Sync agents in each forest independently, and they all sync to the same tenant without a central sync server. Key challenge: UPN conflicts. If both forests have jsmith@contoso.com, you have a collision. Resolution strategy: use the sourceAnchor (immutableId) to ensure each user is unique, and resolve UPN conflicts through a naming convention change before sync.

Single Forest → Multiple Tenants (Divestiture)

One AD forest needs to feed two separate Entra ID tenants (parent company + divested entity). This requires running separate sync paths with scoping filters. Azure AD Connect supports this with multiple sync instances or organizational unit scoping. Cloud Sync handles it natively with per-tenant scope filters. The divested entity's users should have their AD accounts moved to a separate OU before sync configuration, to ensure clean separation.
