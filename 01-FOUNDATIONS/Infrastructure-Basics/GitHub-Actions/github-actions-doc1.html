// section 01

What is GitHub Actions, Really?

GitHub Actions is an event-driven automation platform built directly into GitHub. The critical word is event-driven. Unlike traditional CI systems where you schedule builds or manually press run, GitHub Actions reacts to things that happen in your repository — a push, a pull request, a tag, a release, a comment, a schedule, even an API call.

Your repository is constantly generating events. GitHub Actions lets you listen for those events and respond with automation. That automation is defined as code — YAML files living inside your repository at .github/workflows/, versioned and reviewed alongside the application code that triggered them.

🔐 Your Use Case — PingFederate AWS Migration

In your migration pipeline, GitHub Actions is the engine that detects a push to main, packages your PingFederate configuration artifacts, authenticates to AWS using OIDC federation (no long-lived credentials anywhere), and deploys to your target environment — all automatically, all auditable, all traceable to the exact commit that triggered it.

Every deployment is a GitHub Actions workflow run. Every approval gate is a workflow waiting for a reviewer. Every rollback is a re-run of a previous workflow. This is the power of treating your deployment process as code.

The Three Jobs GitHub Actions Does

⚡
Automate

Run any script, command, or tool automatically in response to repository events. Build, test, lint, package, deploy, notify.

🔗
Integrate

Connect to thousands of external services through a rich Marketplace — AWS, Slack, Docker Hub, npm, JIRA, and more.

🎛️
Orchestrate

Run jobs in parallel, sequence them with dependencies, fan out across matrix configurations, and pass data between stages cleanly.

Core Architecture — Five Layers

Every GitHub Actions setup is five nested concepts. Understand the hierarchy and everything else becomes intuitive. Get confused about the hierarchy and everything else is confusing. Start here.

// section 03

The Workflow Lifecycle

When you push a commit to a branch, here is exactly what GitHub Actions does — in order, every time:

// workflow execution — from event to done

1 — Event fires. You push a commit. GitHub generates a push event containing full context: branch name, commit SHA, author, files changed, and more.

2 — Trigger evaluation. GitHub scans all your .github/workflows/*.yml files. Does any workflow's on: block match this event? If yes, those workflows are queued. If no match, nothing happens — silently.

3 — Runner assignment. GitHub finds an available runner (or provisions a fresh VM for GitHub-hosted runners) and dispatches the workflow to it.

4 — Job execution. Jobs with no needs: start immediately and in parallel. Jobs with needs: wait for their dependencies. Each job runs its steps in sequence, one by one.

5 — Report and cleanup. Results are written to the GitHub UI. PR check statuses are updated. Notifications fire. For GitHub-hosted runners, the VM is completely destroyed — nothing persists.

⚠️ Critical Mental Model — Ephemeral Runners

GitHub-hosted runners are completely fresh virtual machines on every single run. Nothing persists. No files, no installed packages, no cached state from a previous run. If you install something in one job, the next job does not have it — they run on separate VMs. This is why caching (Doc 3) and artifacts (Doc 3) exist as explicit mechanisms.

This is very different from persistent build agents. Make no assumptions about state between runs.

// section 04

Runners — Where Your Code Actually Executes

A runner is a server that executes your job's steps. Every job must declare its runner using runs-on:. Omit it and the workflow fails immediately. There are two types:

GitHub-Hosted Runners

  • Fresh VM on every run — fully isolated
  • Pre-installed: Node.js, Python, Docker, git, AWS CLI, and 100s more tools
  • Ubuntu (ubuntu-latest), Windows, macOS available
  • 2-core CPU, 7GB RAM, 14GB SSD — standard tier
  • Free for public repos; billed by minutes for private repos
  • No infrastructure to manage — just use it

Self-Hosted Runners

  • Your own server, VM, container, or on-prem machine
  • State can persist between runs (be deliberate about cleanup)
  • Required for: private network access, compliance requirements, specific hardware
  • Labeled with custom tags you define
  • You manage patching, scaling, and lifecycle
  • Reference with: runs-on: [self-hosted, linux, your-label]
🔐 PingFederate Migration — Which Runner When

Self-hosted runner: Any step that needs to reach your on-prem PingFederate Admin API (not internet-accessible) during the migration. Run these steps on a self-hosted runner sitting inside your corporate network.

GitHub-hosted runner: Everything that runs after the config reaches AWS — build, test, AWS deployments via OIDC, Slack notifications. Use GitHub-hosted for these — they're faster, cheaper, and require zero infrastructure management from you.

.github/workflows/migration-pipeline.yml
yaml
jobs:
  fetch-config:
    runs-on: [self-hosted, linux, pingfed-network]  # needs internal network
    steps:
      - name: Export PingFederate config
        run: ./scripts/export-pf-config.sh

  deploy-aws:
    runs-on: ubuntu-latest   # GitHub-hosted — clean, fast, free of on-prem
    needs: fetch-config
    steps:
      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
      - name: Deploy to AWS
        run: aws ecs update-service --cluster pf-cluster --force-new-deployment

Events & Triggers — The Ignition System

The on: block at the top of every workflow is the ignition key. It defines exactly which events cause the workflow to fire. Get this wrong and your pipeline either never runs or runs at the wrong time — both are painful to debug.

The Six Triggers You'll Use Most

trigger-patterns.yml — all six
yaml
# ── 1. PUSH — fire on commits to specific branches ──
on:
  push:
    branches: [main, develop, 'release/**']
    paths:                          # only trigger when these files change
      - 'src/**'
      - 'package.json'
      - 'tsconfig.json'
    paths-ignore:                   # never trigger for these
      - 'docs/**'
      - '**.md'

# ── 2. PULL_REQUEST — CI checks on PRs ──
on:
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]  # default if omitted

# ── 3. WORKFLOW_DISPATCH — manual trigger with inputs ──
on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        type: choice
        options: [staging, production]
      force_deploy:
        description: 'Skip approval gate?'
        type: boolean
        default: false

# ── 4. SCHEDULE — cron-based, great for nightly jobs ──
on:
  schedule:
    - cron: '0 2 * * *'    # 2am UTC every day
    - cron: '0 8 * * 1'    # 8am UTC every Monday

# ── 5. RELEASE — fire when a GitHub release is published ──
on:
  release:
    types: [published]   # triggers on official release, not drafts

# ── 6. COMBINED — multiple triggers on one workflow ──
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:    # always keep this — allows manual emergency runs
💀 War Story — The Infinite Loop at 2am

A team set up a workflow that triggered on any push to main. That workflow auto-generated a CHANGELOG and committed it back to main. The commit triggered the workflow again. Which committed another CHANGELOG. Which triggered again. 47 runs later, GitHub rate-limited the entire organization's Actions quota at 2am before a critical release.

The fix: Use paths-ignore: ['CHANGELOG.md'] in the trigger. Or commit bot changes with a [skip ci] message. Or — better — don't commit auto-generated files back to the branch that CI watches. Structure matters.

// section 06

workflow_run — Chaining Workflows Together

The workflow_run trigger is one of the most powerful and underused features in GitHub Actions. It lets you trigger one workflow only after another workflow finishes — creating a clean, decoupled separation between your CI and CD pipelines.

Without workflow_run, many teams shove both CI and deployment logic into one massive workflow file. That becomes hard to read, hard to debug, and hard to grant appropriate permissions (CI needs read access, deployment needs write access to AWS — they should be separate).

.github/workflows/deploy.yml — triggered by CI completion
yaml
name: Deploy to Staging

on:
  workflow_run:
    workflows: ["CI Pipeline"]   # exact name from the other workflow's 'name:' key
    types: [completed]
    branches: [main]            # only chain deploys from main, not feature branches

jobs:
  deploy:
    runs-on: ubuntu-latest
    # Only proceed if the upstream workflow actually succeeded
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    steps:
      - name: Deploy to staging
        run: echo "CI passed — deploying..."
🔐 PingFederate Pattern — Decoupled CI and CD

ci.yml — Triggers on every push and PR. Runs lint → unit tests → integration tests → package artifacts. Has only read permissions. No deployment logic anywhere.

deploy.yml — Triggers via workflow_run after ci.yml completes on main. Checks conclusion == 'success' before proceeding. Has write permissions to AWS. Deploys to staging, then waits for approval before production.

This means a failed CI build cannot trigger a deployment — even if someone bypasses branch protection and force-pushes to main. The conclusion check is the gate.

⚠️ The Name Must Match Exactly

The workflows: list in workflow_run must match the exact value of the name: key in the upstream workflow file — not the filename. If your CI workflow file is named ci.yml but its name: key says CI Pipeline, you must use "CI Pipeline" in the downstream trigger. Case-sensitive. Typos here produce no error — the trigger just silently never fires.

Jobs, Steps & the Dependency Graph

Jobs are the unit of parallelism. By default, all jobs in a workflow run simultaneously, each on its own runner. To run jobs in sequence, you use needs: to declare which jobs must complete first. This creates a directed dependency graph that GitHub Actions visualizes in the UI.

pipeline.yml — parallel + sequential job graph
yaml
jobs:
  # These two run immediately, in parallel
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  # Waits for BOTH lint AND test — then builds
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    needs: [lint, test]
    steps:
      - uses: actions/checkout@v4
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

  # Only runs after build succeeds
  deploy:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    needs: build
    steps:
      - uses: actions/download-artifact@v4
        with: {name: dist}
      - run: echo "Deploying build artifacts..."

The execution order: lint and test start simultaneously → build waits for both to pass → deploy waits for build. Total time ≈ max(lint, test) + build + deploy. If lint takes 2 min and test takes 4 min, you pay only the 4-minute test cost — not 2+4=6. That parallelism compounds fast across larger pipelines.

💡 needs: also gives you upstream outputs

needs: isn't just about ordering — it also unlocks the ability to read output values from upstream jobs using ${{ needs.job-name.outputs.key }}. This is how a build job can expose a version tag that the deploy job uses to pull the right container image. You'll build this pattern in depth in Doc 2.

🐛 Spot the Bug #1 — Circular Job Dependency

This workflow should run test → build → deploy in sequence. It fails immediately on every run. What is wrong?

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  build:
    runs-on: ubuntu-latest
    needs: deploy     # ← look here
    steps:
      - run: npm run build

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - run: echo "deploying"

The bug: build has needs: deploy and deploy has needs: build. This is a circular dependency. Build is waiting for deploy, and deploy is waiting for build — neither can ever start. GitHub Actions detects this and fails instantly with "A cycle was detected in the workflow". The fix: build should have needs: test, and deploy should have needs: build.

YAML Deep Dive — The Syntax That Trips Everyone Up

GitHub Actions workflows are YAML. YAML looks friendly but has sharp edges. Here are the ones that will cost you time if you encounter them cold in a broken pipeline.

Indentation, Lists, Maps, Multiline

yaml-patterns.yml
yaml
# Scalar — single value
runs-on: ubuntu-latest

# List — block style (preferred for readability)
branches:
  - main
  - develop
# List — inline style (fine for short lists)
branches: [main, develop]

# Map — key-value pairs (used for env, with, etc.)
env:
  NODE_ENV: production
  API_VERSION: v2

# Multiline run — pipe | preserves newlines as separate commands
run: |
  npm ci
  npm run build
  npm test

# Folded > — newlines become spaces (one long string)
run: >
  echo "This long command
  continues on the next line as one string"

# Expressions — always wrap in quotes when used as a value
if: ${{ github.ref == 'refs/heads/main' }}

# Booleans — true/false (not 'true'/'false' strings)
continue-on-error: true
required: false

# Numbers — no quotes needed
timeout-minutes: 15
retention-days: 30
⚠️ The Colon Trap — URLs and Connection Strings

A colon followed by a space (: ) means "key-value separator" in YAML. If your value contains this pattern — URLs, connection strings, JWT headers — wrap the value in quotes, always:

❌ DB_URL: postgres://user:pass@host:5432/db — parse error

✅ DB_URL: "postgres://user:pass@host:5432/db" — correct

This appears constantly in IAM/SSO work where you're dealing with OAuth endpoints, LDAP connection strings, and SAML metadata URLs in environment variables.

🐛 Spot the Bug #2 — YAML Colon in Value

This step configures environment variables for a PingFederate API client. The workflow fails with a YAML parse error but the indentation looks correct. What is wrong?

steps:
  - name: Run API server
    env:
      PF_ADMIN_URL: https://pingfed.corp.internal:9999/pf-admin-api/v1
      PF_OAUTH_URL: https://pingfed.corp.internal:9031/as/token.oauth2
      NODE_ENV: staging
    run: node server.js

The bug: Both URL values contain :// and port numbers with colons — YAML tries to interpret parts of these as nested keys. Fix: Wrap all URL values in double quotes: PF_ADMIN_URL: "https://pingfed.corp.internal:9999/pf-admin-api/v1". Rule of thumb: always quote env var values that contain colons, slashes, or special characters.

Actions Marketplace — Using Pre-Built Actions Safely

The GitHub Actions Marketplace has 20,000+ pre-built actions. The good news: you don't need to write shell scripts for common tasks. The important news: you are running code from the internet in your pipeline — treat it with appropriate care.

The Actions You'll Use in Almost Every Pipeline

ActionDoesWhen
actions/checkout@v4Clones your repo onto the runner. Almost always Step 1 of any job that needs code.Every code job
actions/setup-node@v4Installs a specific Node.js version. Has built-in caching support for npm.All Node.js / TypeScript jobs
actions/upload-artifact@v4Saves files from the current job so later jobs or humans can download them.After build steps
actions/download-artifact@v4Retrieves artifacts uploaded by a previous job in the same workflow run.Deploy jobs
actions/cache@v4Caches dependencies between workflow runs. Dramatically speeds up install steps.Before install steps
aws-actions/configure-aws-credentialsOIDC-based AWS auth. No static access keys. The right way to authenticate to AWS.Any AWS deployment job

How to Trust a Third-Party Action

⚠️ Always Pin to a Commit SHA in Enterprise Pipelines

Using uses: some-action@v2 means the tag v2 can be silently moved to point to a different commit — including a compromised one. A maintainer account gets phished, an update gets pushed, and your pipeline now runs attacker code.

In enterprise CI/CD pipelines, pin actions to their full commit SHA. The SHA is immutable — it will always point to the exact code you reviewed.

secure-actions.yml — SHA pinning pattern
yaml
# ❌ Risky — tag can be moved to different commit
- uses: actions/checkout@v4

# ✅ Safe — SHA is immutable, always resolves to same code
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
  # v4.2.2 — document the tag so humans know what version this is

# ✅ For GitHub's own actions (lower supply chain risk), tags are acceptable
- uses: actions/setup-node@v4

# How to find the SHA: go to the action's releases on GitHub,
# click a release tag, and copy the full commit SHA from the URL.

Trust evaluation checklist for any third-party action: Look for the Verified Creator badge. Check recent commit activity (abandoned repos are a risk). Read the action.yml source — what permissions does it request, what external calls does it make? Prefer official actions from GitHub (actions/*), major cloud providers (aws-actions/*, azure/*, google-github-actions/*), and well-known tooling vendors.

Timeouts & Limits — Don't Let Pipelines Run Forever

GitHub Actions allows jobs to run for up to 6 hours by default. In enterprise environments, a hung job — a test that deadlocked, a deployment waiting for a resource that never comes — will silently burn runner minutes, block queue capacity, and potentially trigger billing alerts. Always set explicit timeouts.

timeouts.yml — job and step level
yaml
jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 15          # job-level: entire job must finish in 15 min
    steps:
      - name: Install dependencies
        timeout-minutes: 5        # step-level: npm ci should never take > 5 min
        run: npm ci

      - name: Build TypeScript
        timeout-minutes: 8
        run: npm run build

  deploy:
    runs-on: ubuntu-latest
    timeout-minutes: 30          # deployments take longer — be generous but bounded
    needs: build
    steps:
      - name: Deploy to AWS ECS
        timeout-minutes: 25
        run: aws ecs update-service --wait ...
💡 Good Defaults to Start With

lint / type-check: 5 min · unit tests: 10 min · build: 10 min · integration tests: 15 min · deployment: 30 min · full E2E suite: 45 min. Tune down as you observe actuals. A timeout that fires is a bug signal — a step that should take 3 minutes should not have a 30-minute timeout or you'll wait too long on real failures.

🐛 Spot the Bug #3 — Silent Trigger That Never Fires

An engineer set up a deploy workflow that should fire after the CI workflow completes on main. The CI workflow runs fine, but the deploy workflow never triggers. No error is shown. What is wrong?

# ci.yml
name: CI Pipeline
on:
  push:
    branches: [main]

# deploy.yml
name: Deploy
on:
  workflow_run:
    workflows: ["ci pipeline"]   # ← look here
    types: [completed]
    branches: [main]

The bug: The workflows: value is "ci pipeline" (all lowercase) but the upstream workflow's name: key is "CI Pipeline" (capitalized). The match is case-sensitive. GitHub finds no matching workflow name and silently does nothing — no error, no warning, no run. Fix: use the exact string "CI Pipeline" to match the upstream workflow's name key precisely.

🧪 Lab 1 — Your First Production-Ready Pipeline
Hands-On · ~45 min
Objective: Build a complete, working CI pipeline for a Node.js/TypeScript API project from a blank file. You'll have a real workflow running on GitHub by the end — not a toy example.
  1. Create the file. In your project repo (or a new one), create .github/workflows/ci.yml. The directory structure matters — GitHub only picks up workflows from exactly this path.
  2. Add the workflow name and triggers. Set name: CI Pipeline at the top (this is what appears in the GitHub Actions tab and what workflow_run references). Set on: to trigger on push to main and on pull_request to main. Add paths: filtering for src/** and package.json so markdown changes don't trigger unnecessary runs.
  3. Define the job. Create one job named ci. Set runs-on: ubuntu-latest. Set timeout-minutes: 15. Make this a habit from day one.
  4. Add the checkout step. uses: actions/checkout@v4. This must be Step 1 — without it, the runner has no code to work with. You will forget this exactly once, then never again.
  5. Add Node.js setup. uses: actions/setup-node@v4 with node-version: '20'. Pin the exact version — not latest — so you never get surprised by a Node.js major version bump in CI.
  6. Add install, build, and test. Three separate named steps: npm ci (not npm install — ci is faster, stricter, and reproducible), npm run build, and npm test.
  7. Commit and push the workflow file. Go to your repo's Actions tab on GitHub. Watch the workflow appear and execute in real time. Click into each step to see its log output.
  8. Intentionally break it. Add a failing test or a build error. Push. Observe exactly how the failure is reported in the Actions tab, in the PR check status, and in the step-level logs. This is how you learn to debug — see the failure modes before you encounter them under pressure.
.github/workflows/ci.yml — complete Lab 1 solution
yaml
name: CI Pipeline

on:
  push:
    branches: [main]
    paths:
      - 'src/**'
      - 'package.json'
      - 'tsconfig.json'
  pull_request:
    branches: [main]
  workflow_dispatch:    # always useful for manual reruns

jobs:
  ci:
    name: Build & Test
    runs-on: ubuntu-latest
    timeout-minutes: 15

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js 20
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: npm ci

      - name: Compile TypeScript
        run: npm run build

      - name: Run test suite
        run: npm test
🧪 Lab 2 — Multi-Job Pipeline with Parallel Execution
Hands-On · ~60 min
Objective: Extend your Lab 1 workflow into a multi-job pipeline with a real dependency graph. By the end you'll see the parallel execution visualization in GitHub's UI and measure the time savings vs sequential execution.
  1. Split Lab 1 into three independent jobs. Create lint, type-check, and test — each with their own runs-on: ubuntu-latest and checkout step. At this point all three will run simultaneously.
  2. Add a build job with needs: [lint, type-check, test]. This job only runs if all three pass. Add a step that runs npm run build and uploads the dist/ folder as an artifact using actions/upload-artifact@v4.
  3. Add a deploy-staging job with needs: build. Add a condition: if: github.ref == 'refs/heads/main' so this job only runs on pushes to main, not on PR branches. The deploy step can be a simple run: echo "Deploying to staging..." for now.
  4. Set timeouts on every job. lint: 5 min · type-check: 5 min · test: 10 min · build: 10 min · deploy-staging: 20 min. Every job. No exceptions.
  5. Push and observe the graph. In the Actions tab, click your workflow run. You should see the visual dependency graph — lint/type-check/test starting in parallel, build waiting for all three, deploy waiting for build. This is your pipeline's architecture made visible.
  6. Compare times. Note the total workflow duration vs the sum of all job durations. The gap is your parallelism savings. On a real project this difference is significant.
  7. Add workflow_dispatch: to the trigger block so you can fire the pipeline manually from the GitHub UI without making a code commit. Then test it — go to Actions → your workflow → Run workflow.
.github/workflows/ci.yml — complete Lab 2 solution
yaml
name: CI Pipeline

on:
  push:
    branches: [main]
    paths:
      - 'src/**'
      - 'package.json'
      - 'tsconfig.json'
  pull_request:
    branches: [main]
  workflow_dispatch:

jobs:
  # ── Parallel group — all three start simultaneously ──
  lint:
    name: Lint
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci --prefer-offline
      - run: npm run lint

  type-check:
    name: Type Check
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci --prefer-offline
      - run: npx tsc --noEmit

  test:
    name: Unit Tests
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci --prefer-offline
      - run: npm test

  # ── Sequential gate — waits for all three above ──
  build:
    name: Build & Package
    runs-on: ubuntu-latest
    timeout-minutes: 10
    needs: [lint, type-check, test]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci --prefer-offline
      - run: npm run build
      - name: Upload build artifact

💡 What to Observe in the GitHub UI

After pushing, go to your repo → Actions tab → click the latest run. You will see a visual job graph — three nodes (lint, type-check, test) starting in parallel, build waiting below them, deploy-staging waiting below build. The total pipeline time will be shorter than the sum of all jobs. That gap is your parallelism dividend. On real projects this saves minutes on every single CI run.
