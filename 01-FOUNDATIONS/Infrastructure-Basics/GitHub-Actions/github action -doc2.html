The Intelligence Layer

Variables, secrets, contexts, expressions, conditions, concurrency, and permissions — the layer where workflows stop being scripts and start making smart decisions.

⏱ 3–4 hours 🧪 3 Labs 🐛 3 Spot-the-Bug exercises 🎯 Intermediate Level

📍 Where You Are

You finished Doc 1 with a working multi-job pipeline that builds and tests a Node.js/TypeScript project. It runs, passes, and fails when things break. But it has no intelligence — it cannot make decisions, has no access to credentials, doesn't know which environment it's deploying to, and if two engineers push simultaneously it races itself.

This document fixes all of that. By the end your workflows will read context about who triggered them, access secrets at the right scope, make conditional decisions based on branch and job outcomes, pass data between jobs cleanly, and use concurrency groups to prevent deployment races. This is the layer that separates a toy pipeline from a production one.

// section 01

GitHub Contexts — The Data Universe of a Workflow Run

Every time a workflow runs, GitHub populates a set of context objects containing information about the run, the repository, the triggering event, the runner, and more. You access this data using ${{ context.property }}. Contexts are read-only — GitHub sets them, you read them.

github.*
Event & Repo Info

Who triggered the run, which branch, commit SHA, repo name, event type, and the full event payload.

secrets.*
Secret Values

Encrypted secrets from repo, org, or environment scope. Never logged — always masked in output.

vars.*
Config Variables

Non-sensitive config values set at repo/org/environment level in GitHub UI. Unlike secrets, visible in logs.

env.*
Environment Variables

Variables set via env: key at workflow, job, or step level. Scoped to where they're defined.

steps.*
Step Outputs

Output values and outcome status from previous steps in the same job via steps.step-id.outputs.key.

needs.*
Job Outputs

Outputs and status from upstream jobs declared in needs:. The bridge for data between jobs.

runner.*
Runner Info

The OS, architecture, and temp directory of the runner executing the current job.

job.*
Current Job Status

Status of the current job and container info. Useful in post-job cleanup and notification steps.

The github Context — Your Most-Used Context

github-context-examples.yml
yaml
steps:
  - name: Print useful context values
    run: |
      echo "Triggered by : ${{ github.actor }}"        # who pushed / opened PR
      echo "Event type   : ${{ github.event_name }}"    # push, pull_request, etc.
      echo "Branch       : ${{ github.ref_name }}"      # main, feature/auth
      echo "Full ref     : ${{ github.ref }}"           # refs/heads/main
      echo "Commit SHA   : ${{ github.sha }}"           # full 40-char SHA
      echo "Repo         : ${{ github.repository }}"    # org/repo-name
      echo "Run number   : ${{ github.run_number }}"    # sequential counter

  - name: Use SHA for Docker image tagging
    run: |
      SHORT_SHA="${{ github.sha }}"
      docker build -t myapp:${SHORT_SHA:0:8} .

  - name: Skip fork PRs — no secrets access
    if: ${{ github.event.pull_request.head.repo.full_name == github.repository }}
    run: echo "Not a fork — safe to access secrets"
⚠️ github.ref vs github.ref_name

github.ref returns the full ref: refs/heads/main. github.ref_name returns just the short name: main. In conditions, use the form that matches your comparison. Writing github.ref == 'main' is always false — the actual value is refs/heads/main. This is the most common context mistake.

Variables & Scoping — Where Values Live

GitHub Actions has four distinct ways to define variables, each with different scope, lifetime, and visibility. Using the wrong one is the most common source of "why isn't my variable available here?" bugs.

TypeDefined withScopeVisible in logs?Use for
Workflow envenv: at workflow levelAll jobs and stepsYesNon-sensitive config shared across all jobs
Job envenv: inside a jobAll steps in that job onlyYesJob-specific config — not visible in other jobs
Step envenv: inside a stepThat step onlyYesStep-level overrides of job or workflow vars
Repository/Org varsGitHub UI → Settings → VariablesAll workflows in repo/orgYesAPI URLs, feature flags, non-sensitive config
SecretsGitHub UI → Settings → SecretsRepo, org, or environmentNeverPasswords, tokens, private keys
variable-scoping.yml — all four levels in one file
yaml
name: Variable Scoping Demo

# Workflow-level env — available in ALL jobs and steps
env:
  NODE_VERSION: '20'
  APP_NAME: iam-api

jobs:
  build:
    runs-on: ubuntu-latest
    # Job-level env — only available in steps of THIS job
    env:
      BUILD_TARGET: production
      API_URL: ${{ vars.PF_API_URL }}   # from GitHub UI → Variables
    steps:
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}   # workflow-level var
      - name: Build with step-level override
        env:
          BUILD_TARGET: staging    # overrides job-level for THIS step only
        run: echo "Building $APP_NAME for $BUILD_TARGET on Node $NODE_VERSION"

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - run: |
          echo "APP_NAME=$APP_NAME"        # ✅ workflow-level — available
          echo "BUILD_TARGET=$BUILD_TARGET"  # ⚠️ empty — job-level from build job
⚠️ env: vs vars: — Easy to Confuse

env.* reads variables from the env: key in your YAML. vars.* reads configuration variables set in GitHub UI under Settings → Variables → Actions. They are completely different sources. ${{ env.MY_VAR }} reads your YAML definition. ${{ vars.MY_VAR }} reads from GitHub settings. Getting these wrong produces silent empty values with no error.

Environment Files — How Steps Share Data Within a Job

Steps in the same job run sequentially on the same runner, but a value set in one run: script doesn't carry to the next step automatically. GitHub Actions solves this with three special environment files written to disk between steps.

env-files.yml — GITHUB_ENV, GITHUB_OUTPUT, GITHUB_STEP_SUMMARY
yaml
steps:
  # ── GITHUB_ENV — set a variable for all subsequent steps in this job ──
  - name: Extract version
    run: |
      VERSION=$(node -p "require('./package.json').version")
      echo "APP_VERSION=$VERSION" >> $GITHUB_ENV

  - name: Use version in next step
    run: echo "Building version $APP_VERSION"   # ✅ available now

  # ── GITHUB_OUTPUT — expose named outputs for use in conditions and other steps ──
  - name: Generate build metadata
    id: meta
    run: |
      SHORT_SHA="${{ github.sha }}"
      echo "short_sha=${SHORT_SHA:0:8}" >> $GITHUB_OUTPUT
      echo "image_tag=myapp-${SHORT_SHA:0:8}" >> $GITHUB_OUTPUT

  - name: Use step output
    run: |
      echo "SHA:       ${{ steps.meta.outputs.short_sha }}"
      echo "Image tag: ${{ steps.meta.outputs.image_tag }}"

  # ── GITHUB_STEP_SUMMARY — write Markdown visible in the GitHub Actions UI ──
  - name: Write deployment summary
    if: always()
    run: |
      echo "## 🚀 Deployment Summary" >> $GITHUB_STEP_SUMMARY
      echo "| Field | Value |" >> $GITHUB_STEP_SUMMARY
      echo "| --- | --- |" >> $GITHUB_STEP_SUMMARY
      echo "| Version | $APP_VERSION |" >> $GITHUB_STEP_SUMMARY
      echo "| Commit  | ${{ github.sha }} |" >> $GITHUB_STEP_SUMMARY
      echo "| Actor   | ${{ github.actor }} |" >> $GITHUB_STEP_SUMMARY
💡 GITHUB_STEP_SUMMARY is Underused

The step summary renders Markdown directly in the GitHub Actions UI on the run page — no external dashboard needed. For your PingFederate pipeline, write a summary after each deploy showing config version, target environment, who triggered it, and the result. Engineers and managers see it instantly without digging into raw log lines.

💀 War Story — The :: Syntax That Silently Stopped Working

You may encounter older workflows using echo "::set-output name=key::value" or echo "::set-env name=KEY::value". This was the original GitHub Actions syntax before 2022. It was deprecated and then disabled entirely on all GitHub-hosted runners because it allowed script injection attacks. If you inherit a workflow where step outputs are empty for no obvious reason, this is the likely cause. Replace immediately with $GITHUB_OUTPUT and $GITHUB_ENV.

🐛 Spot the Bug #1 — Variable Not Available in Deploy Job

This workflow tries to use a version string set in the build job inside the deploy job. The deploy step always prints an empty value. What is wrong?

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      APP_VERSION: 1.4.2
    steps:
      - run: npm run build

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - run: echo "Deploying version $APP_VERSION"  # always empty

The bug: APP_VERSION is a job-level env variable in the build job. Job-level env variables are scoped to that job only — they never cross job boundaries. The deploy job runs on a separate VM with no knowledge of the build job's environment. Fix: Either move to workflow-level env:, or write it with echo "APP_VERSION=1.4.2" >> $GITHUB_ENV inside a step and expose it as a job output using $GITHUB_OUTPUT, then access via needs.build.outputs.app_version.

Secrets — Three Levels, One Precedence Rule

GitHub Actions secrets are encrypted key-value pairs that are never exposed in logs — GitHub masks any value that matches a stored secret. They exist at three scopes. Understanding the hierarchy is critical for enterprise IAM environments where different teams own different credentials.

Org Level
Organization Secrets
Defined at the GitHub organization level. Available to all repos in the org (or a policy-restricted subset). Ideal for shared credentials: corporate npm registry token, shared Slack webhook, cross-repo bot PAT.
Repo Level
Repository Secrets
Defined per repository. Available to all workflows in that repo regardless of environment. Ideal for repo-specific credentials like a Docker Hub token or a staging API key that does not need environment gating.
Env Level
Environment Secrets
Defined per deployment environment (staging, production). Only available to jobs that specify environment:. Can be protected with approval gates — a job cannot access production secrets until a reviewer approves. Ideal for production AWS credentials and PingFederate admin tokens.
⚠️ Precedence — Most Specific Level Wins

If the same secret name exists at all three levels, the environment secret wins over repo, which wins over org. Use this intentionally: define a default AWS_ROLE_ARN at org level pointing to a read-only staging role, and override it at the production environment level with the production role ARN that has write access.

secrets-usage.yml — accessing secrets at all three levels
yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Authenticate to private registry
        run: npm config set //registry.npmjs.org/:_authToken ${{ secrets.NPM_TOKEN }}
        # NPM_TOKEN is a repo-level secret

  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging            # unlocks environment-scoped secrets
    needs: build
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}   # staging env secret
          aws-region: us-east-1

  deploy-prod:
    runs-on: ubuntu-latest
    environment: production          # different env — different secrets + approval gate
    needs: deploy-staging
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}   # same name, different value
          aws-region: us-east-1
🔐 PingFederate Migration — Secret Architecture

Structure your secrets for enterprise scale:

  • Org secrets: Shared Slack webhook URL, npm registry token, GitHub bot PAT for cross-repo automation
  • Repo secrets: PingFederate admin API credentials for the specific PF instance, Docker registry credentials
  • Staging environment secrets: AWS role ARN for staging, staging RDS password, staging PF OAuth client secret
  • Production environment secrets: AWS role ARN for prod (with required reviewer approval gate), prod RDS password, prod PF OAuth client secret — nobody accesses these without explicit approval

Passing Secrets to Reusable Workflows

When calling a reusable workflow (covered in Doc 3), secrets are not automatically passed. Use secrets: inherit for simplicity or pass them explicitly for least-privilege access.

secrets-inherit.yml
yaml
jobs:
  call-deploy-all:
    uses: org/shared/.github/workflows/deploy.yml@main
    secrets: inherit         # passes ALL secrets — convenient but broad

  call-deploy-explicit:
    uses: org/shared/.github/workflows/deploy.yml@main
    secrets:                  # explicit — only what the workflow needs
      AWS_ROLE_ARN: ${{ secrets.AWS_ROLE_ARN }}
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

Permissions Scoping — Least Privilege for GITHUB_TOKEN

Every workflow run receives a GITHUB_TOKEN — an automatically generated token that lasts for the duration of the run. By default this token has broad repository write permissions. In enterprise workflows, always scope it to the minimum your jobs actually need.

permissions.yml — workflow and job level scoping
yaml
name: Secure Pipeline

# Start locked down at workflow level
permissions: read-all

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read          # read repo code only
      checks: write           # write test result checks to PRs
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write         # REQUIRED for OIDC — requesting JWT from GitHub
      deployments: write      # update deployment status in GitHub UI
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1

  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write         # create releases, push tags
      pull-requests: write    # update PR with release notes
💀 War Story — id-token: write Missing from OIDC Job

A team had AWS OIDC authentication working perfectly on one repo but failing on a newer one with: "Error: Credentials could not be loaded". After an hour of debugging AWS trust policies, the fix was one line — the newer repo had an org-level policy setting default permissions to read-all, and the OIDC action needs id-token: write to request a JWT from GitHub's token endpoint. Without it, the token request is silently blocked. Rule: any job using OIDC must have id-token: write at the job permissions level.

Expressions — The ${{ }} Syntax

Expressions are evaluated at runtime to produce values. They appear inside ${{ }} and can access contexts, call functions, and perform comparisons. They work in if: conditions, env: values, step with: inputs, and run: commands.

Essential Built-in Functions

expressions.yml — the functions you'll use constantly
yaml
steps:
  # contains() — string or array membership check
  - name: Notify only on main or release
    if: ${{ contains(fromJson('["main","release"]'), github.ref_name) }}
    run: echo "Sending release notification"

  # startsWith() / endsWith()
  - name: Deploy on version tags only
    if: ${{ startsWith(github.ref, 'refs/tags/v') }}
    run: echo "Deploying tagged release"

  # format() — safe string interpolation
  - name: Build image tag
    run: |
      echo "IMAGE=${{ format('{0}/{1}:{2}', vars.REGISTRY, github.repository, github.sha) }}"

  # toJson() — serialize context to JSON for debugging
  - name: Debug full event payload
    run: echo '${{ toJson(github.event) }}'

  # fromJson() — parse JSON strings
  - name: Get first service from JSON array input
    run: echo "Service: ${{ fromJson(inputs.services)[0] }}"

  # join() — array to string
  - name: List PR labels
    run: echo "${{ join(github.event.pull_request.labels.*.name, ', ') }}"

  # hashFiles() — generate stable cache key from file contents
  - name: Cache node_modules
    uses: actions/cache@v4
    with:
      path: node_modules
      key: node-${{ runner.os }}-${{ hashFiles('package-lock.json') }}

Conditions & if: — Making Jobs and Steps Conditional

The if: key can be placed on both jobs and steps. When it evaluates to false, the job or step is skipped — not failed. A skipped job shows a grey checkmark in the UI, not a red X. This is an important distinction for pipeline status reporting.

conditions.yml — real-world patterns
yaml
jobs:
  # Job condition — entire job skipped if false
  deploy-prod:
    runs-on: ubuntu-latest
    needs: deploy-staging
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    steps:
      - run: echo "Deploying to production"

  ci:
    runs-on: ubuntu-latest
    steps:
      # Step condition — only post PR comment on pull_request events
      - name: Comment on PR
        if: ${{ github.event_name == 'pull_request' }}
        run: echo "Posting results to PR..."

      # Run only if a previous step wrote a specific output
      - name: Check for migrations
        id: db-check
        run: |
          if git diff --name-only HEAD~1 | grep -q "migrations/"; then
            echo "needed=true" >> $GITHUB_OUTPUT
          fi

      - name: Run DB migration
        if: ${{ steps.db-check.outputs.needed == 'true' }}
        run: npm run db:migrate

      # Skip bot-triggered workflows entirely at job level
      - name: Skip renovate bumps
        if: ${{ github.actor != 'renovate[bot]' && github.actor != 'dependabot[bot]' }}
        run: echo "Human-triggered run"

Status Check Functions — The Four You Must Know

FunctionReturns true whenCommon use
success()All previous steps/jobs succeeded. Default behaviour — omitting if: is the same as if: success()Normal happy-path steps
failure()Any previous step/job failed or was cancelledRollback steps, error notifications, on-call paging
cancelled()The workflow was manually cancelledCleanup of partially-created cloud resources
always()Always — regardless of any previous outcomeUpload logs, post final Slack status, release distributed locks
status-functions.yml — failure handling and always-run cleanup
yaml
steps:
  - name: Deploy to AWS
    id: deploy
    run: ./deploy.sh

  # Runs only if the deploy step specifically failed
  - name: Rollback on failure
    if: ${{ failure() && steps.deploy.outcome == 'failure' }}
    run: ./rollback.sh

  # Always sends notification — success or failure
  - name: Notify Slack — always
    if: always()
    run: |
      curl -X POST ${{ secrets.SLACK_WEBHOOK }} \
        -d "{\"text\": \"Deploy ${{ job.status }} — ${{ github.repository }}\"}"

  # Upload test results even when tests fail — needed to diagnose failures
  - name: Upload test results
    if: always()
    uses: actions/upload-artifact@v4
    with: {name: test-results, path: coverage/}

continue-on-error vs failure() — A Critical Distinction

These two mechanisms both involve failures but behave very differently. Confusing them leads to pipelines that either block when they shouldn't, or silently pass when they should have failed.

continue-on-error: trueif: failure()
What it doesLets the workflow continue even if this step fails. The step is marked failed but subsequent steps still run.Runs a step ONLY IF a previous step has already failed. Used for cleanup, rollback, and error alerts.
Job outcomeJob still reports as failed — it just doesn't stop executingNo effect on job outcome — it is a trigger condition
Step outcomeoutcome = failure, conclusion = successThe conditional step runs normally and has its own outcome
Use forOptional best-effort steps: coverage checks, lint warnings that should not block a hotfix deployMandatory recovery steps: cleanup, notification, rollback that must run precisely because something broke
continue-vs-failure.yml
yaml
steps:
  # continue-on-error: optional gate — failing won't block the pipeline
  - name: Check code coverage
    continue-on-error: true
    run: npm run coverage:check

  - name: Build Docker image
    id: docker-build
    run: docker build -t myapp .

  # if: failure() — must run precisely BECAUSE the build failed
  - name: Page on-call for build failure
    if: ${{ failure() && steps.docker-build.outcome == 'failure' }}
    run: echo "Docker build failed — alerting on-call"

  # Using both: always upload scan results, don't block on them
  - name: Upload security scan
    if: always()
    continue-on-error: true
    uses: actions/upload-artifact@v4
    with: {name: scan-results, path: scan-output/}
🐛 Spot the Bug #2 — Slack Notification Only Fires on Success

This pipeline should notify Slack whether the deployment succeeds or fails. Engineers report they only get notified on success — failures go completely unannounced at 2am. What is wrong?

steps:
  - name: Deploy to production
    id: deploy
    run: ./deploy.sh

  - name: Run smoke tests
    run: ./smoke-test.sh

  - name: Notify Slack
    run: curl -X POST ${{ secrets.SLACK_WEBHOOK }} -d '{"text":"Deploy done"}'

The bug: The Notify Slack step has no if: condition, so it implicitly uses if: success(). When deploy or smoke tests fail, the job enters a failure state and subsequent steps with no if: are skipped. Fix: Add if: always() to the Notify Slack step. This is one of the most common enterprise pipeline gaps — monitoring that only works when everything is already fine. The steps that most need to always run are notifications and cleanup, yet they're the ones most often written without if: always().

Concurrency Control — Preventing Deployment Race Conditions

Without concurrency control, two engineers pushing to main within seconds of each other start two deployment workflows simultaneously. Both pull the same artifact and deploy to the same environment — racing each other, potentially leaving the environment in an inconsistent state mid-deploy.

The concurrency: key defines a named group. GitHub ensures only one workflow run in that group is active at a time. Others either queue or get cancelled depending on your configuration.

concurrency.yml — the four patterns that matter
yaml
# Pattern 1 — Cancel old runs. Latest push wins.
# Safe for CI — no point checking stale commits when new ones arrive.
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

---
# Pattern 2 — Queue. One at a time. Never cancel.
# CRITICAL for deployments — never cancel a deploy mid-flight.
concurrency:
  group: deploy-production
  cancel-in-progress: false

---
# Pattern 3 — Per-environment. Staging and prod can run simultaneously
# but two staging deploys cannot overlap.
concurrency:
  group: deploy-${{ inputs.environment || 'staging' }}
  cancel-in-progress: false

---
# Pattern 4 — Per-PR. Cancel old checks when new commits arrive.
concurrency:
  group: pr-checks-${{ github.event.pull_request.number }}
  cancel-in-progress: true
🔐 PingFederate Deployment — Two Concurrency Groups

Use separate groups for CI and CD:

  • CI: group: ci-${{ github.ref }} with cancel-in-progress: true. Old commit checks are wasted work when new pushes arrive.
  • Deploy: group: deploy-pf-${{ github.ref_name }} with cancel-in-progress: false. Never cancel a PingFederate config push mid-flight. A partial config can leave authentication broken for all users. Queue and wait.
💀 War Story — cancel-in-progress on a Live Production Deploy

A team used a single concurrency group with cancel-in-progress: true covering both CI and deployments. An engineer pushed a hotfix seconds after a release. The hotfix CI run cancelled the in-progress production deployment at the exact moment it was updating the ECS task definition. The service came up with half the containers on the old task, half on the new — a split-brain state. It took two hours to diagnose and restore service. The fix was adding separate concurrency groups for CI and CD.

Step & Job Outputs — Passing Data Through Your Pipeline

Data flows through a pipeline in two hops: step → job (via $GITHUB_OUTPUT + steps.id.outputs), and job → job (via job-level outputs: + needs.job.outputs). You must explicitly wire both hops — nothing crosses a boundary automatically.

outputs-full-chain.yml — complete step → job → job data flow
yaml
jobs:
  build:
    runs-on: ubuntu-latest
    # Declare which step outputs to expose to downstream jobs
    outputs:
      version:         ${{ steps.meta.outputs.version }}
      image_tag:       ${{ steps.meta.outputs.image_tag }}
      has_migrations:  ${{ steps.db-check.outputs.has_migrations }}
    steps:
      - uses: actions/checkout@v4
        with: {fetch-depth: 2}

      - name: Generate metadata
        id: meta
        run: |
          VERSION=$(node -p "require('./package.json').version")
          SHORT="${{ github.sha }}"
          echo "version=$VERSION" >> $GITHUB_OUTPUT
          echo "image_tag=$VERSION-${SHORT:0:8}" >> $GITHUB_OUTPUT

      - name: Check for DB migrations
        id: db-check
        run: |
          if git diff --name-only HEAD~1 HEAD | grep -q "^migrations/"; then
            echo "has_migrations=true" >> $GITHUB_OUTPUT
          else
            echo "has_migrations=false" >> $GITHUB_OUTPUT
          fi

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Deploy with version from build job
        run: |
          echo "Version:   ${{ needs.build.outputs.version }}"
          echo "Image tag: ${{ needs.build.outputs.image_tag }}"
          aws ecs update-service \
            --service iam-api \
            --task-definition iam-api:${{ needs.build.outputs.image_tag }}

      - name: Run migrations if needed
        if: ${{ needs.build.outputs.has_migrations == 'true' }}
        run: npm run db:migrate:prod
⚠️ Outputs Are Always Strings — Quote Your Comparisons

All step and job outputs are strings. Even echo "count=42" produces the string "42", not the number 42. When comparing in if: conditions always use single quotes: needs.build.outputs.has_migrations == 'true' not == true. The unquoted true is a YAML boolean. This is the single most common output-related bug in GitHub Actions — it trips up experienced engineers regularly because YAML booleans look identical to the string you're comparing against.

🐛 Spot the Bug #3 — Output Comparison Always False

The migration step should run when the build job detects schema changes. The build job correctly writes has_migrations=true to $GITHUB_OUTPUT. The migration step is always skipped. What is wrong?

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      has_migrations: ${{ steps.check.outputs.has_migrations }}
    steps:
      - id: check
        run: echo "has_migrations=true" >> $GITHUB_OUTPUT

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Run migrations
        if: ${{ needs.build.outputs.has_migrations == true }}
        run: npm run db:migrate

The bug: The condition compares against true (YAML boolean). But $GITHUB_OUTPUT always produces strings — the actual value is the string "true". The comparison "true" == true evaluates to false in GitHub's expression engine. Fix: Quote the comparison: ${{ needs.build.outputs.has_migrations == 'true' }}. This affects every boolean-like output you'll ever write — always quote the right-hand side in output comparisons.

🧪 Lab 1 — Smart Context-Aware CI Pipeline
Hands-On · ~45 min
Objective: Upgrade your Doc 1 pipeline to be context-aware — behaving differently based on who triggered it, which branch it's on, and whether it's a PR or direct push. Add a rich deployment summary visible in the GitHub Actions UI.
  1. Add a workflow-level env block with NODE_VERSION: '20', APP_NAME set to your project name, and reference these throughout instead of hardcoding values.
  2. Add a "print context" step at the start of your CI job printing github.actor, github.event_name, github.ref_name, and github.sha. Trigger it as both a push and a PR and observe what each value looks like differently.
  3. Make the deploy-staging job conditional using github.ref == 'refs/heads/main' && github.event_name == 'push'. This prevents accidental staging deploys from PR checks.

.github/workflows/ci.yml — Lab 1 solution
yaml
name: CI Pipeline
on:
  push:
    branches: [main]
    paths: ['src/**', 'package.json', 'tsconfig.json']
  pull_request:
    branches: [main]
  workflow_dispatch:

env:
  NODE_VERSION: '20'
  APP_NAME: iam-api

jobs:
  ci:
    name: Build & Test
    runs-on: ubuntu-latest
    timeout-minutes: 15
    if: github.actor != 'dependabot[bot]' && github.actor != 'renovate[bot]'
    concurrency:
      group: ci-${{ github.ref }}
      cancel-in-progress: true
    steps:
      - name: Print run context
        run: |
          echo "Actor:  ${{ github.actor }}"
          echo "Event:  ${{ github.event_name }}"
          echo "Branch: ${{ github.ref_name }}"
          echo "SHA:    ${{ github.sha }}"
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: ${{ env.NODE_VERSION }}}
      - run: npm ci && npm run build && npm test
      - name: Write workflow summary
        if: always()
        run: |
          VERSION=$(node -p "require('./package.json').version" 2>/dev/null || echo "unknown")
          echo "## ${{ env.APP_NAME }} CI Summary" >> $GITHUB_STEP_SUMMARY
          echo "| | |" >> $GITHUB_STEP_SUMMARY
          echo "| --- | --- |" >> $GITHUB_STEP_SUMMARY
          echo "| **Version** | $VERSION |" >> $GITHUB_STEP_SUMMARY
          echo "| **Branch** | ${{ github.ref_name }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Triggered by** | ${{ github.actor }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Status** | ${{ job.status }} |" >> $GITHUB_STEP_SUMMARY

  deploy-staging:
    name: Deploy to Staging
    runs-on: ubuntu-latest
    timeout-minutes: 20
    needs: ci
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    concurrency:
      group: deploy-staging
      cancel-in-progress: false
    steps:
      - name: Deploy
        run: echo "Deploying ${{ env.APP_NAME }} to staging..."
      - name: Notify outcome
        if: always()
        run: echo "Staging deploy status: ${{ job.status }}"

🧪 Lab 3 — Full Output Chaining Across Three Jobs
Hands-On · ~50 min
Objective: Build a three-job pipeline where each job passes typed data to the next. Build computes metadata. Deploy uses it. Notify reports the final outcome — always.
  1. In your build job, add a step with id: meta writing two outputs to $GITHUB_OUTPUT: version (from package.json) and short_sha (first 8 chars of github.sha).
  2. Declare job-level outputs: in the build job mapping to the step outputs. Without this explicit declaration the values will not cross the job boundary — this step is required and easy to forget.
  3. In the deploy job, access via needs.build.outputs.version and construct an image tag like myapp:${{ needs.build.outputs.version }}-${{ needs.build.outputs.short_sha }}. Print it and verify the value flows correctly end to end.
  4. Add a migration detection step that writes has_migrations=true or false based on whether a migrations/ directory was touched. In deploy, use needs.build.outputs.has_migrations == 'true' (single quotes — remember the string comparison) to gate a migration step.
  5. Add a notify job with needs: [build, deploy] and if: always(). Print version, short SHA, build result from needs.build.result, and deploy result from needs.deploy.result.
  6. Force a failure in the deploy job with exit 1. Run the pipeline and verify: deploy fails, notify job still runs (because of always()), and correctly shows deploy: failure in its summary.
.github/workflows/ci.yml — Lab 3 complete output chaining solution
yaml
name: CI Pipeline
on:
  push: {branches: [main]}
  workflow_dispatch:

permissions: read-all

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      contents: read
    outputs:
      version:        ${{ steps.meta.outputs.version }}
      short_sha:      ${{ steps.meta.outputs.short_sha }}
      has_migrations: ${{ steps.migration.outputs.has_migrations }}
    steps:
      - uses: actions/checkout@v4
        with: {fetch-depth: 2}
      - name: Generate metadata
        id: meta
        run: |
          VERSION=$(node -p "require('./package.json').version" 2>/dev/null || echo "0.0.0")
          SHORT="${{ github.sha }}"
          echo "version=$VERSION" >> $GITHUB_OUTPUT
          echo "short_sha=${SHORT:0:8}" >> $GITHUB_OUTPUT
      - name: Check for DB migrations
        id: migration
        run: |
          if git diff --name-only HEAD~1 HEAD | grep -q "^migrations/"; then
            echo "has_migrations=true" >> $GITHUB_OUTPUT
          else
            echo "has_migrations=false" >> $GITHUB_OUTPUT
          fi
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci && npm run build && npm test

  deploy:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    needs: build
    permissions:
      contents: read
      id-token: write
    concurrency:
      group: deploy-staging
      cancel-in-progress: false
    steps:
      - name: Deploy image
        run: |
          IMAGE="myapp:${{ needs.build.outputs.version }}-${{ needs.build.outputs.short_sha }}"
          echo "Deploying $IMAGE to staging"
      - name: Run DB migrations if needed
        if: ${{ needs.build.outputs.has_migrations == 'true' }}
        run: echo "Running migrations for v${{ needs.build.outputs.version }}"

  notify:
    runs-on: ubuntu-latest
    needs: [build, deploy]
    if: always()
    steps:
      - name: Deployment summary
        run: |
          echo "Version:    ${{ needs.build.outputs.version }}"
          echo "SHA:        ${{ needs.build.outputs.short_sha }}"
          echo "Migrations: ${{ needs.build.outputs.has_migrations }}"
          echo "Build:      ${{ needs.build.result }}"
          echo "Deploy:     ${{ needs.deploy.result }}"
