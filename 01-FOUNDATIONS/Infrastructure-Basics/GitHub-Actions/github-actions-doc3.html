Scale & Reusability

Artifacts, caching, reusable workflows, composite actions, matrix strategies, service containers, and release automation — where individual pipelines become an enterprise CI/CD platform.

📍 Where You Are

You finished Doc 2 with smart, secure, context-aware pipelines. You can read contexts, scope secrets, write conditional logic, chain outputs between jobs, and prevent deployment races with concurrency groups. Your pipelines make decisions.

The problem now is scale. When you have ten repositories, you don't want to copy-paste the same 300-line workflow YAML into each one. Artifacts — Persisting Build Output Across Jobs

Jobs in a workflow run on separate, isolated VMs. Nothing is shared between them automatically. Artifacts are how you pass files from one job to another — or make them available for download after the run. Think compiled binaries, test reports, coverage data, packaged configs.

Artifacts are uploaded by one job using actions/upload-artifact and downloaded by subsequent jobs using actions/download-artifact. They are stored by GitHub for a configurable retention period (default 90 days).

artifacts.yml — upload, download, cross-job passing
yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci && npm run build

      - name: Upload build output
        uses: actions/upload-artifact@v4
        with:
          name: dist-${{ github.sha }}     # unique name per commit
          path: dist/
          retention-days: 7              # keep for 7 days, not the 90-day default
          if-no-files-found: error        # fail loudly if dist/ is empty

      - name: Upload test coverage report
        if: always()                       # upload even when tests fail
        uses: actions/upload-artifact@v4
        with:
          name: coverage-${{ github.run_number }}
          path: coverage/
          if-no-files-found: warn          # warn but don't fail if coverage not generated

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Download build output
        uses: actions/download-artifact@v4
        with:
          name: dist-${{ github.sha }}     # must match exactly
          path: dist/                       # where to place it on this runner

      - name: Deploy the artifact
        run: aws s3 sync dist/ s3://my-bucket/

  # Download ALL artifacts from the run at once
  collect-reports:
    runs-on: ubuntu-latest
    needs: build
    if: always()
    steps:
      - name: Download all artifacts
        uses: actions/download-artifact@v4
        with:
          path: all-artifacts/            # no name: downloads everything
      - run: ls -la all-artifacts/
⚠️ if-no-files-found: error is Your Friend

The default value of if-no-files-found is warn — which means if your build step silently fails to produce output, the artifact upload succeeds with a warning, the deploy job downloads an empty artifact, and your deployment proceeds with nothing. Set it to error for all critical artifacts so a missing build output fails loudly at the upload step, not mysteriously at deploy time.

Caching Strategy — Making Pipelines Fast

Every GitHub-hosted runner starts fresh. Without caching, npm ci downloads every dependency from the internet on every single run. For a project with 500 packages, that's 30–90 seconds per job — multiplied across every branch, every PR, every push. Caching eliminates that cost by storing and restoring node_modules between runs.

The Two Ways to Cache Node.js Dependencies

Method 1 — Recommended
Built-in cache in setup-node
  • One line to enable: cache: 'npm'
  • Automatically uses package-lock.json as cache key
  • Handles cache restore and save automatically
  • Best choice for standard npm/yarn/pnpm projects
Method 2 — Full Control
Manual actions/cache
  • Explicit control over key, restore-keys, and paths
  • Works for any tool — Docker layers, pip, Go modules, Gradle
  • Supports fallback restore keys for partial cache hits
  • Best when you need custom cache key logic
caching.yml — both methods with real key strategies
yaml
jobs:
  build-method-1:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'              # ← that's it. Done.
      - run: npm ci               # uses cache automatically

  build-method-2:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Cache node_modules
        uses: actions/cache@v4
        with:
          path: ~/.npm
          # Primary key: exact match on OS + lock file hash
          key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
          # Restore keys: fallback to any npm cache for this OS
          restore-keys: |
            npm-${{ runner.os }}-
            npm-
      - uses: actions/setup-node@v4
        with: {node-version: '20'}
      - run: npm ci

Cache Key Strategy — The Pattern That Matters

A good cache key has three properties: it changes when dependencies change, it stays the same when only source code changes, and it has a useful fallback for partial hits. Here is the canonical pattern for Node.js:

cache-key-strategy.yml
yaml
# Primary key: exact match — cache hit if lock file hasn't changed
key: node-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}

# Restore keys: used when primary key misses — partial match
# Finds most recent cache with this OS prefix
restore-keys: |
  node-${{ runner.os }}-

# For monorepos — scope cache to specific package
key: node-${{ runner.os }}-packages/auth-${{ hashFiles('packages/auth/package-lock.json') }}

# For Docker layer caching
key: docker-${{ runner.os }}-${{ hashFiles('Dockerfile', '.dockerignore') }}
💡 How Much Time Does Caching Save?

A typical Node.js project with 400 packages: npm ci without cache takes 45–90 seconds. With cache hit, it takes 3–8 seconds. Across 50 workflow runs per day across a team of 10 engineers, that's roughly 40–60 minutes of saved pipeline time per day for one project. At scale across dozens of repos, caching is one of the highest-ROI pipeline optimizations you can make.

💀 War Story — Stale Cache Breaking Production Build

A team added a new npm package on a Friday. They pushed directly to main without updating package-lock.json properly. Their cache key was based on the lock file — so the cache hit, node_modules was restored from the old cache, the new package wasn't there, and the build succeeded because the import was in a code path that tests didn't exercise. The production deployment ran fine. The feature broke for users on Monday morning. The fix: always run npm ci (not npm install) — ci validates the lockfile is consistent and fails fast if it's not.

Reusable Workflows — DRY CI/CD at the Repository Level

A reusable workflow is a complete workflow file that other workflows can call like a function — passing inputs, receiving outputs, inheriting or explicitly passing secrets. One workflow file lives in a central repo; dozens of service repos call it. When you update the central workflow, all callers get the update automatically.

This is the pattern that turns a collection of per-repo pipelines into an enterprise CI/CD platform. One team owns the shared deployment workflow. Service teams consume it. Standards are enforced by default.

shared-workflows/.github/workflows/deploy-node.yml — the CALLED workflow
yaml
name: Deploy Node Service

# workflow_call makes this a reusable workflow
on:
  workflow_call:
    inputs:
      environment:
        description: 'Target environment'
        type: string
        required: true
      node-version:
        description: 'Node.js version'
        type: string
        default: '20'
      service-name:
        description: 'ECS service name to update'
        type: string
        required: true
      run-migrations:
        description: 'Run DB migrations before deploy?'
        type: boolean
        default: false
    secrets:
      AWS_ROLE_ARN:
        description: 'IAM role ARN for OIDC auth'
        required: true
      DEPLOY_TOKEN:
        required: false
    outputs:
      deployed-version:
        description: 'The version that was deployed'
        value: ${{ jobs.deploy.outputs.version }}

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    permissions:
      id-token: write
      contents: read
    outputs:
      version: ${{ steps.deploy-step.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1

      - name: Run migrations
        if: ${{ inputs.run-migrations }}
        run: npm run db:migrate

      - name: Deploy service
        id: deploy-step
        run: |
          VERSION=$(node -p "require('./package.json').version")
          echo "version=$VERSION" >> $GITHUB_OUTPUT
          aws ecs update-service \
            --cluster ${{ inputs.environment }} \
            --service ${{ inputs.service-name }} \
            --force-new-deployment
iam-api/.github/workflows/deploy.yml — the CALLER workflow
yaml
name: Deploy IAM API
on:
  push:
    branches: [main]

jobs:
  deploy-staging:
    uses: org/shared-workflows/.github/workflows/deploy-node.yml@main
    with:
      environment: staging
      service-name: iam-api-staging
      node-version: '20'
      run-migrations: true
    secrets:
      AWS_ROLE_ARN: ${{ secrets.STAGING_AWS_ROLE_ARN }}

  deploy-prod:
    uses: org/shared-workflows/.github/workflows/deploy-node.yml@main
    needs: deploy-staging
    with:
      environment: production
      service-name: iam-api-prod
      run-migrations: true
    secrets:
      AWS_ROLE_ARN: ${{ secrets.PROD_AWS_ROLE_ARN }}

  notify:
    runs-on: ubuntu-latest
    needs: [deploy-staging, deploy-prod]
    if: always()
    steps:
      - run: echo "Deployed version ${{ needs.deploy-prod.outputs.deployed-version }}"
🔐 PingFederate Pattern — Central Workflow Library

Create an org/platform-workflows repository with shared workflows for your common deployment patterns. Service teams call these instead of writing their own. The platform team controls security standards — OIDC auth, mandatory approval gates, required notifications — and service teams configure only what's specific to their service: environment name, service identifier, whether migrations are needed.

When a security requirement changes (for example, adding a mandatory SBOM scan before every deploy), you update it in one place and all callers get it immediately on their next run.

⚠️ Reusable Workflow Constraints

Reusable workflows have important limitations to know before designing around them:

  • A caller workflow can call at most 20 reusable workflows — they can be nested up to 4 levels deep
  • Reusable workflows run as a complete job in the caller — you cannot use them as a step inside an existing job
  • The called workflow must be in a repository the caller has access to — either public, the same org with appropriate access, or the same repo
  • Matrix strategies cannot be applied to a uses: job directly — use a composite action inside a matrix job instead
🐛 Spot the Bug #1 — Reusable Workflow Secret Not Passed

A team calls a shared deploy workflow. The called workflow fails with "AWS credentials could not be loaded." The secret is defined in the caller repo. What is wrong?

# Caller workflow
jobs:
  deploy:
    uses: org/shared/.github/workflows/deploy.yml@main
    with:
      environment: production
      service-name: auth-api

# Called workflow expects:
on:
  workflow_call:
    secrets:
      AWS_ROLE_ARN:
        required: true

The bug: The caller workflow does not pass the AWS_ROLE_ARN secret to the called workflow. Secrets are not automatically inherited unless you add secrets: inherit or explicitly pass them with a secrets: block. The called workflow declares it as required — so the run starts but the secret value is empty, causing the AWS credentials step to fail. Fix: Add secrets: AWS_ROLE_ARN: ${{ secrets.AWS_ROLE_ARN }} under the deploy job, or use secrets: inherit if you want to pass all secrets.

Composite Actions — Reusable Step Sequences

A composite action packages multiple steps into a single reusable unit that can be called as a uses: step inside any job. Unlike reusable workflows (which run as a complete job), composite actions run inline within an existing job — they have access to the job's environment, working directory, and previously set variables.

The key file is action.yml at the root of the action's directory. It defines inputs, outputs, and the steps to execute.

.github/actions/setup-node-app/action.yml — a composite action
yaml
name: 'Setup Node App'
description: 'Checkout, setup Node, install deps with cache — one step'

inputs:
  node-version:
    description: 'Node.js version to use'
    required: false
    default: '20'
  install-args:
    description: 'Additional args for npm ci'
    required: false
    default: ''

outputs:
  node-version:
    description: 'The actual Node version installed'
    value: ${{ steps.setup.outputs.node-version }}

runs:
  using: 'composite'       # ← this is what makes it composite
  steps:
    - uses: actions/checkout@v4

    - name: Setup Node.js
      id: setup
      uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: 'npm'

    - name: Install dependencies
      shell: bash             # ← required in composite actions for run: steps
      run: npm ci ${{ inputs.install-args }}
workflow using the composite action
yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      # One step replaces checkout + setup-node + npm ci
      - name: Setup app
        uses: ./.github/actions/setup-node-app    # local action
        with:
          node-version: '20'

      - run: npm run build
      - run: npm test

  lint:
    runs-on: ubuntu-latest
    steps:
      - name: Setup app
        uses: ./.github/actions/setup-node-app    # same action, different job
      - run: npm run lint
⚠️ shell: bash is Required in Composite run: Steps

In a composite action, every run: step must explicitly declare shell: bash (or shell: sh, shell: pwsh, etc.). Unlike regular workflow steps where the shell is inferred from the runner OS, composite action steps have no default shell — omitting it is a validation error that surfaces only when the action is actually called.

Reusable Workflow vs Composite Action — Choosing the Right Tool

Both mechanisms enable reuse. The choice comes down to what you're reusing and where it needs to run.

Reusable WorkflowComposite Action
Runs asA complete job (or multiple jobs) in the caller workflowInline steps within an existing job
Called withuses: at the job leveluses: at the step level
Has access to caller's env vars?No — runs in its own job environmentYes — shares the job's environment
Can use matrix strategy?No — cannot be combined with matrix on the same jobYes — works inside a matrix job
SecretsMust be explicitly passed or inheritedInherits from the calling job automatically
Best forFull deployment pipelines, multi-job sequences, cross-repo standardizationCommon setup sequences (checkout + install), linting steps, packaging steps shared across jobs
ExampleA shared deploy-to-aws.yml used by 20 service reposA setup-node-app action used at the top of every build job
✅ Quick Decision Rule

If you're reusing something that should run as its own isolated job — use a reusable workflow. If you're reusing a sequence of steps that need to run inside an existing job — use a composite action. If you need matrix compatibility — use a composite action.

Matrix Strategy — Running Jobs Across Multiple Configurations

A matrix strategy lets you run the same job multiple times with different variable values — simultaneously, in parallel. Test against Node 18, 20, and 22 at the same time. Deploy to us-east-1, eu-west-1, and ap-southeast-1 in parallel. The matrix expands automatically into as many parallel job instances as there are combinations.

matrix.yml — multi-version, multi-env, include/exclude
yaml
jobs:
  # Basic matrix — test against 3 Node versions simultaneously
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: ['18', '20', '22']
      fail-fast: false          # don't cancel other matrix jobs if one fails
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci && npm test

  # Multi-dimensional matrix — OS x Node version = 9 combinations
  test-cross-platform:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: ['18', '20', '22']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: ${{ matrix.node }}}
      - run: npm ci && npm test

  # include — add extra variables to specific combinations
  deploy-multi-region:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        region: [us-east-1, eu-west-1, ap-southeast-1]
        include:
          # Add cluster name per region
          - region: us-east-1
            cluster: prod-us
          - region: eu-west-1
            cluster: prod-eu
          - region: ap-southeast-1
            cluster: prod-ap
    steps:
      - run: |
          echo "Deploying to ${{ matrix.region }} cluster ${{ matrix.cluster }}"
          aws ecs update-service \
            --region ${{ matrix.region }} \
            --cluster ${{ matrix.cluster }} \
            --service iam-api

  # exclude — remove specific combinations from the matrix
  test-with-exclusion:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: ['18', '20', '22']
        env: [staging, production]
        exclude:
          # Don't test Node 18 against production
          - node: '18'
            env: production
⚠️ fail-fast: true is the Default — Know What It Does

By default, fail-fast is true — if any single matrix job fails, GitHub immediately cancels all other running matrix jobs. For CI tests this is often fine (you saw a failure, no need to run the rest). For multi-region deployments, this is dangerous — a failure in ap-southeast-1 would cancel the in-progress us-east-1 and eu-west-1 deployments, potentially leaving those regions half-deployed. Always set fail-fast: false for deployment matrices.

🔐 PingFederate Multi-Region Pattern

Use a matrix to deploy PingFederate config across multiple AWS regions simultaneously. Define your regions in the matrix, use include: to attach region-specific cluster names and role ARNs, and set fail-fast: false so a single region failure doesn't abort the others. Each matrix job picks up its region-specific OIDC role from the include: data and deploys independently.

🐛 Spot the Bug #2 — Matrix Deploy Aborts Mid-Flight

A team uses a matrix to deploy their IAM service to three AWS regions simultaneously. When the ap-southeast-1 deployment fails due to a transient AWS API error, the us-east-1 and eu-west-1 deployments — which were already 80% complete — are immediately cancelled. Production in those two regions ends up in a broken state. What is the root cause?

jobs:
  deploy:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        region: [us-east-1, eu-west-1, ap-southeast-1]
    steps:
      - run: aws ecs update-service --region ${{ matrix.region }} ...

The bug: fail-fast is not set, so it defaults to true. When ap-southeast-1 fails, GitHub immediately cancels all other running matrix jobs — including the in-progress us-east-1 and eu-west-1 deployments. For any deployment matrix, always set fail-fast: false. Let each region succeed or fail independently. A failure in one region should never cancel a deployment that's already running in another.

Service Containers — Running Dependencies Alongside Your Job

Integration tests for a Node.js/TypeScript API typically need a real database, a cache, or a message queue running while the tests execute. Service containers let you spin up Docker containers alongside your job — they start before your steps run and are available at a known hostname inside the job.

This eliminates the need for mocking database calls in integration tests — your tests hit a real PostgreSQL instance, just one that lives for the duration of the job.

service-containers.yml — Postgres + Redis for integration tests
yaml
jobs:
  integration-tests:
    runs-on: ubuntu-latest
    timeout-minutes: 20

    # Service containers run alongside the job
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: testuser
          POSTGRES_PASSWORD: testpass
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: >
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379
        options: --health-cmd "redis-cli ping" --health-interval 10s --health-retries 5

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: '20', cache: 'npm'}
      - run: npm ci

      - name: Run DB migrations against test DB
        env:
          DATABASE_URL: "postgresql://testuser:testpass@localhost:5432/testdb"
        run: npm run db:migrate

      - name: Run integration tests
        env:
          DATABASE_URL: "postgresql://testuser:testpass@localhost:5432/testdb"
          REDIS_URL: "redis://localhost:6379"
        run: npm run test:integration
💡 Health Checks Are Essential

The options: --health-cmd block tells Docker to wait until the service is actually ready to accept connections before starting your steps. Without it, your first step that tries to connect to Postgres might run before Postgres has finished initializing — resulting in a flaky connection error that disappears on retry. Always add health checks to database and cache service containers.

Release Workflows — Automating Versioning and Publishing

A release workflow automates the steps that happen when you're ready to ship: bumping the version, creating a Git tag, generating a changelog, creating a GitHub Release, and publishing to npm or a container registry. Done manually, this is error-prone and slow. Automated, it happens the same way every time.

.github/workflows/release.yml — tag-triggered release pipeline
yaml
name: Release

on:
  push:
    tags:
      - 'v*.*.*'              # triggers on tags like v1.2.3

permissions:
  contents: write            # create releases, push tags
  packages: write            # push to GitHub Container Registry
  id-token: write            # OIDC for npm publish provenance

jobs:
  release:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0         # need full history for changelog generation

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          registry-url: 'https://registry.npmjs.org'

      - run: npm ci && npm run build && npm test

      - name: Extract version from tag
        id: version
        run: |
          VERSION="${{ github.ref_name }}"      # e.g. v1.2.3
          echo "version=$VERSION" >> $GITHUB_OUTPUT
          echo "semver=${VERSION#v}" >> $GITHUB_OUTPUT   # strip the v → 1.2.3

      - name: Build and push Docker image
        run: |
          echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
          docker build -t ghcr.io/${{ github.repository }}:${{ steps.version.outputs.version }} .
          docker build -t ghcr.io/${{ github.repository }}:latest .
          docker push ghcr.io/${{ github.repository }} --all-tags

      - name: Publish to npm
        run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

      - name: Create GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          tag_name: ${{ steps.version.outputs.version }}
          name: Release ${{ steps.version.outputs.version }}
          generate_release_notes: true    # auto-generates from merged PRs
          files: |
            dist/*.js
            dist/*.d.ts
💡 generate_release_notes: true

GitHub automatically generates release notes from the merged PRs between the previous tag and this one — including PR titles, authors, and links. No manual changelog writing needed. For more control, add a .github/release.yml file to categorize PRs by label (Features, Bug Fixes, Chores) in the generated notes.

🐛 Spot the Bug #3 — Composite Action Step Missing Shell

An engineer creates a composite action that packages three common setup steps. When any workflow calls it, the action fails with: "Required property is missing: shell". The YAML looks correct. What is wrong?

# .github/actions/setup-env/action.yml
name: 'Setup Environment'
runs:
  using: 'composite'
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with: {node-version: '20'}
    - name: Install deps
      run: npm ci        # ← missing something here

The bug: The run: step inside a composite action is missing the required shell: property. In regular workflow steps, the shell is inferred from the runner OS. In composite actions, every run: step must explicitly declare its shell — there is no default. Fix: Add shell: bash to the Install deps step. This catches a lot of engineers off guard because the error only appears at call time, not when the action file is written.

🧪 Lab 1 — Artifact + Caching Pipeline
Hands-On · ~45 min
Objective: Add proper artifact handling and dependency caching to your pipeline. Measure the before-and-after time difference and verify artifact passing between jobs works end to end.
  1. Add cache: 'npm' to your actions/setup-node@v4 step. Run the pipeline twice — the first run is a cache miss (populates the cache), the second is a cache hit. Compare the install step duration between runs.
  2. In your build job, add actions/upload-artifact@v4 after the build step. Name the artifact dist-${{ github.sha }}, point it at your dist/ directory, set retention-days: 7, and critically set if-no-files-found: error.
  3. In your deploy job, add actions/download-artifact@v4 as the first step — before any deploy commands. Use the same name dist-${{ github.sha }} and download to dist/. Add a step that runs ls -la dist/ to verify the files arrived correctly.
  4. Test the if-no-files-found: error behaviour — temporarily change your build script to not produce output (or rename the dist directory). Run the workflow and observe it fails at the upload step with a clear error, rather than silently passing an empty artifact through to deployment.
  5. Upload test coverage with if: always() and if-no-files-found: warn. Run the tests, then check the Actions UI → your run → Artifacts section to see the uploaded coverage report available for download.
  6. Compare pipeline times — record the total workflow duration before adding caching, after first run (cache miss), and after second run (cache hit). Document the actual numbers in a comment in your workflow file.
.github/workflows/ci.yml — Lab 1 solution with caching and artifacts
yaml
name: CI Pipeline
on:
  push: {branches: [main]}
  pull_request: {branches: [main]}
  workflow_dispatch:

permissions: read-all

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read}
    outputs:
      short_sha: ${{ steps.meta.outputs.short_sha }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'                    # ← caching enabled

🧪 Lab 3 — Matrix Testing + Automated Release
Hands-On · ~60 min
Objective: Add matrix-based multi-version testing and an automated tag-triggered release workflow to your project. By the end you will have a pipeline that tests across Node 18/20/22 and publishes a GitHub Release automatically when you push a version tag.
  1. Create a matrix test job that runs your test suite against Node versions 18, 20, and 22 simultaneously. Set fail-fast: false. Run it and observe three parallel job instances in the GitHub Actions UI — note the time saving vs running them sequentially.

  3. Create a release workflow at .github/workflows/release.yml triggered by on: push: tags: ['v*.*.*']. It should: checkout with fetch-depth: 0, install and build, create a GitHub Release with generate_release_notes: true, and upload the dist/ files as release assets.

  5. Create and push a test tag: git tag v0.1.0 && git push origin v0.1.0. Watch the release workflow trigger. Verify the GitHub Release is created with auto-generated notes and your dist files attached.
  6. Add a composite action at .github/actions/setup-node-cached/action.yml that wraps checkout + setup-node + npm ci into one reusable step. Replace the three setup steps in all your jobs with a single call to this action. Verify all jobs still pass.

  push: {branches: [main]}
  pull_request: {branches: [main]}
