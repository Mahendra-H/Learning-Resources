Adding JWT Validation Middleware

FEATURE JWT Validation Middleware
A stakeholder requests that all protected API endpoints validate JWT tokens via a centralised middleware — rather than each handler doing it ad hoc. The token must be validated against a JWKS endpoint, support key rotation, fail closed, and produce an audit log entry on every validation attempt.

🔗 Chain steps: All 6
📁 Files created: 4 new

Example findings and how to handle them:

CRITICAL — FIX BEFORE COMMIT
Algorithm not validated against allowlist. The validator accepts any algorithm declared in the token header. An attacker can set alg:none to bypass signature validation. Fix: add ALLOWED_ALGORITHMS = ["RS256"] config and reject all others.
HIGH — FIX BEFORE COMMIT
Token string appears in error log. Line 47: logger.error(f"Invalid token: {token}"). Fix: log only token length and first 8 chars hash, never the raw token.
MEDIUM — REVIEW AND FIX
JWKS cache has no maximum size. Under adversarial key IDs, cache could grow unbounded. Fix: cap cache at 20 entries with LRU eviction.

SCENARIO 02Defect Fix

Refresh Token Failing Intermittently

BUG FIX Intermittent 401 on Valid Refresh Token
The refresh token endpoint occasionally returns HTTP 401 with "token invalid" even when the submitted token is valid and not yet expired. The issue appears under concurrent load (multiple simultaneous refresh requests). It does not reproduce reliably in development.
⚠️ Type: Intermittent / Race condition
🔗 Chain steps: Diagnose → Fix → Regress → Review
⚑ Risk: Auth-related — security review mandatory
Bug Fix Rule #1
Never ask AI to fix a bug before diagnosing its root cause. AI will generate a plausible-looking fix for a guess. You'll ship it, the bug will recur, and you'll have no idea why. Diagnosis first. Always.

Step 1 — Capture the Symptom Precisely

Before opening Copilot, write the symptom description. Not the cause — the symptom. What was observed? When? Under what conditions? This becomes the micro-spec.

Create: specs/bugfix-refresh-token/requirements.md

MICRO-SPEC CONTENT — write this yourself before any prompt 
Bug ID:    BUG-042
Severity:  High — impacts user authentication flow
Symptom:   POST /auth/refresh returns HTTP 401 "token_invalid"
           for tokens that are valid and not expired.
Frequency: ~5-8% of requests under concurrent load (≥50 simultaneous)
Reproducible: Only under load — not in single-request dev testing
Last known good: v1.3.2 (before connection pool changes in v1.3.3)
Affected file (suspected): src/auth/token_refresh.py
Logs show: "Token not found in store" error — but token exists when checked immediately after

Fix constraints:
  - Do NOT change the public API signature of /auth/refresh
  - Do NOT change the token format
  - Do NOT refactor unrelated code
  - Fix must be backward compatible with existing valid tokens

Step 2 — Root Cause Analysis Diagnose First

Now open Copilot. Ask for diagnosis only — not a fix.

RCA DIAGNOSIS PROMPT — Session 1 of Bug Fix 
Task:  Bug
Spec:  specs/bugfix-refresh-token/requirements.md
Read:  .ai/project-context.md
Read:  .ai/architecture.md

Bug symptom: Refresh token returns 401 intermittently under concurrent load.
Logs show "Token not found in store" — but token exists when checked afterward.
Only occurs since v1.3.3 (connection pool changes).

Analyse likely root causes in src/auth/token_refresh.py.

For each hypothesis, provide:
1. The suspected mechanism (what specifically could cause this)
2. Which function or line range to inspect
3. What evidence in the code would confirm this hypothesis
4. Severity of this cause if confirmed

Hypotheses to evaluate:
- Race condition between token validation read and token invalidation write
- Database connection pool exhaustion causing read failures that are misreported
- Clock skew in expiry check (exp - issued_at boundary condition)
- Concurrent refresh requests consuming and invalidating same token simultaneously
- Cache inconsistency if token store has a caching layer

Do NOT write any fix. Diagnosis and hypotheses only.
⚑ Gate — Review the RCA Before Fixing
  • Does the most likely hypothesis match the symptom exactly (intermittent, concurrent, version-correlated)?
  • Go inspect the actual source file at the suspected line range — do you see the suspected pattern?
  • If you see it: confirm the hypothesis and proceed to fix. If you don't: ask Copilot for a second hypothesis.
  • Never skip this inspection step. The AI's diagnosis is a starting point, not a verdict.

The Most Important Bug Fix Rule
The fix must be smaller than the diagnosis. If the fix is larger than the root cause description — it's a refactor, not a fix. Stop and split it into two tasks: (1) the minimal fix, (2) a separate refactor spec.

SCENARIO 03Large Architecture Change

Introducing a Centralized Authentication Gateway

ARCHITECTURE Centralized Authentication Gateway
Currently, JWT validation is scattered across three services — each with slightly different validation logic, different error formats, and separate audit logs. The goal is a single auth-gateway service that all requests pass through, producing consistent validation, a unified audit trail, and a single point for security policy updates.
⏱ Effort: 2–4 weeks
🔗 Phases: 5
📋 ADRs required: 1 main + sub-decisions
⚑ Risk: Breaking change — migration plan required
Large Architecture Rule
Architecture changes live in phases — not sessions. Each phase has its own spec folder, its own ADR (if applicable), its own prompt chain. You never mix phases. When Phase 1 is complete and reviewed, Phase 2 begins. This is how you avoid context overflow and maintain traceability.

Step 1 — Architecture Decision Record First Before Any Code

For any change that affects system boundaries, you write the ADR before anything else. The ADR forces you to articulate the problem, the decision, and the alternatives. It is your governance checkpoint.

ARCHITECTURE ANALYSIS PROMPT — Session 1 
Task:  Architecture analysis
Read:  .ai/project-context.md
Read:  .ai/architecture.md

Current state:
JWT validation exists in three services: user-api, admin-api, reporting-api.
Each has its own validation logic with minor inconsistencies.
Audit logs are per-service with different schemas.

Target state:
A single auth-gateway service handles all token validation.
Services delegate authentication to the gateway via a header or sidecar pattern.

Produce:
1. Current architecture pain points (specific, not generic)
2. Target architecture design (how the gateway integrates with existing services)
3. Three alternative approaches with trade-offs:
   - Centralised gateway service (the proposed approach)
   - Shared validation library
   - API gateway plugin (e.g. Kong, AWS API Gateway)
4. Migration risks and mitigation strategies
5. Phase breakdown — what gets built and in what order
6. Breaking changes to existing service APIs

Architecture analysis only. No code, no implementation, no specs yet.
ADR WRITER PROMPT — after reviewing analysis 
Read: .ai/architecture.md

Write Architecture Decision Record:

Title:   Introduce Centralized Authentication Gateway
Number:  ADR-002
Status:  Accepted

Context:
JWT validation is distributed across three services with inconsistent rules.
Security patches require changes in three codebases. Audit logs have different schemas.
This creates compliance risk and operational overhead.

Decision:
Introduce a dedicated auth-gateway service. All inbound requests are validated
at the gateway. Services receive pre-validated claims in a trusted header.

Positive consequences:
Single source of truth for auth rules · One security patch location ·
Unified audit log · Easier compliance reporting

Negative consequences:
New service to deploy and operate · Single point of failure (mitigated by HA)

Alternatives rejected:
Shared library — still requires each service to update per release.
API gateway plugin — creates vendor lock-in and limits custom audit logic.

Save to: docs/adr/ADR-002-centralized-auth-gateway.md

Each phase gets its own spec folder: specs/auth-gateway-phase-1/, specs/auth-gateway-phase-2/, etc. Each has its own requirements.md and acceptance-tests.md. Each phase runs its own complete prompt chain. You never mix phases in a single spec or a single session.

Step 5 — Preventing Context Overflow Critical for Long Work

Multi-week architecture work is where context overflow destroys quality. As the project grows, sessions become polluted with stale assumptions. Here is how to prevent it systematically.

Problems That Occur Without This
Copilot generates code using Phase 1 architecture in a Phase 3 session — because project-context.md was never updated after Phase 2
A security rule added in Phase 2 is not followed in Phase 3 because it was never added to security-rules.md
Session grows to 40 messages — model quality degrades, early context deprioritised, output becomes inconsistent
Two sessions contradict each other — no source of truth to arbitrate
How to Prevent It
After every phase completion: update .ai/architecture.md to reflect new service boundaries
After every ADR: update .ai/project-context.md with the new architectural fact
Maximum 15 messages per session — then close and start fresh with Continuation Opener
Each session's spec path is the single source of truth — not the chat history
PHASE HANDOFF PROMPT — use at start of each new phase 
Continuing:  Auth Gateway project — Phase [N]
Read:        .ai/project-context.md (updated after Phase N-1)
Read:        .ai/architecture.md    (updated after Phase N-1)
Read:        docs/adr/ADR-002-centralized-auth-gateway.md
Spec:        specs/auth-gateway-phase-[N]/

Phase [N-1] completed: [describe what was built and verified]
Phase [N] goal:      [describe this phase's output]
This session:       [which step of the chain: Plan/Spec/Test/Impl/Review]

Step 6 — Migration Planning (Phases 3–4) No Big Bang

The most dangerous moment in any architecture change is cutover. Here is how to use Copilot to plan a safe, incremental migration with rollback at every step.

MIGRATION PLAN PROMPT 
Task:  Migration planning — Phase 3
Read:  docs/adr/ADR-002-centralized-auth-gateway.md
Read:  specs/auth-gateway-phase-1/integration-contract.md
Read:  .ai/architecture.md

Produce a migration plan for moving user-api to use the auth-gateway.

The plan must include:
1. Feature flag strategy — how to dual-run old and new validation paths
2. Canary approach — what % of traffic starts on gateway, how to increase
3. Validation parity checks — how to confirm gateway produces same result as old validation
4. Rollback trigger — what metric or error rate triggers an immediate rollback
5. Rollback steps — exact sequence to revert to old path with zero downtime
6. Success criteria — what must be true before removing the old path

Migration plan only. No implementation code.
The Migration Non-Negotiables
Every migration must have: (1) a feature flag to enable rollback without redeployment, (2) a defined rollback trigger — a specific metric that, if crossed, triggers immediate rollback, (3) a dual-run period where both paths produce auditable output you can compare. Without these three, you have a big-bang deployment dressed up as a migration.
  • Never migrate all services in one deployment. Migrate one service, validate for 48 hours, then migrate the next. The rollback blast radius stays small.
  • Validate audit log parity before cutting over. Run both paths in parallel for a period and compare their audit output line by line. Discrepancies mean a spec gap, not a code bug — fix the spec first.
  • Update .ai/architecture.md after each service migration. The architecture diagram must always reflect current reality, not target state.
  • Phase 5 cleanup is not optional. Old JWT validation code left in services after migration becomes "mystery code" — it will confuse future AI sessions and may be accidentally re-activated.

The Non-Negotiables — Print This

  • No implementation without a spec. A spec means requirements.md AND edge-cases.md AND acceptance-tests.md — all three, filled in.
  • No commit without code review. Run 06-code-reviewer.md on every generated file before git add.
  • Security review is mandatory for any code touching authentication, input handling, logging, or data access.
  • One prompt = one unit of responsibility. One function, one endpoint, one test file — never two.
  • Declare scope explicitly in every implementation prompt: Scope: ONLY [file] and Do NOT modify: [list].
  • Update .ai/ files the same day you make any change to tech stack, architecture, or security rules. A stale context file is worse than no context file.
  • Large architecture changes live in phases. Each phase has its own spec, its own prompt chain, its own review. Never mix phases in one session.
