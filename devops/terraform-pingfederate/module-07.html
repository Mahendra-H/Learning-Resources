Bridge from Module 06

The fleet is running. Now let it serve traffic.

In Module 06 you built the compute layer — Launch Templates that define each PF instance, Auto Scaling Groups that manage the fleet, lifecycle hooks that gate instances until Ansible completes configuration, and instance_refresh that rolls out new AMIs safely. The ASG places engine nodes in private subnets across multiple availability zones.

But right now, those nodes are unreachable. They live in private subnets with no public IPs. Nothing knows they exist. Module 07 builds the traffic layer that connects the internet to the PF fleet: an NLB in the public subnets, a target group that the ASG registers instances into, health checks that verify PF is responding, and Route53 records that expose a stable DNS name to federation partners and internal consumers.

This module also explains one of the most important architectural decisions in the PF deployment: why NLB, not ALB? The answer lives in how SAML, OIDC, and OAuth work at the TLS layer — and it is the kind of decision that separates infrastructure engineers who understand the application from those who don't.

Mentor Note — the back-reference to M06
Notice that the ASG in M06 references target_group_arns. That variable is produced by this module. In real project codebases, this creates a circular dependency challenge — the ASG needs the target group ARN before it's created, and the target group needs the ASG's instances to be healthy. Terraform resolves this because the ASG registers instances automatically once it's running; the ASG resource only needs the target group ARN to exist at apply time, not to be populated with healthy instances. This is a common source of confusion in initial deployments.
The architectural decision

NLB vs ALB — why PingFederate uses NLB for federation traffic

AWS offers two types of application-facing load balancers: the Application Load Balancer (ALB) and the Network Load Balancer (NLB). Both are commonly used in enterprise environments, and you will encounter both in your project. Understanding the technical reasons for choosing one over the other is the kind of knowledge that makes you valuable in architecture discussions.

NLB vs ALB — Decision Framework for PingFederate

Why TLS passthrough is critical for PingFederate
Many SAML Service Providers validate the signing certificate in the SAML assertion against the TLS certificate used for the federation endpoint. If an ALB terminates TLS and re-encrypts with a different certificate, this validation fails. With NLB TLS passthrough, the TLS session is established directly with the PingFederate instance, which presents its own federation certificate. The SP sees the correct certificate, validation succeeds, and the assertion is accepted. This is why nearly every enterprise PingFederate deployment uses NLB or hardware load balancers with TLS passthrough for the primary federation endpoint.
Primary federation traffic
NLB → Port 9031
TLS passthrough to PF engines. PF terminates TLS and presents its own federation certificate. Real client IPs preserved in audit logs. No HTTP parsing overhead. Handles SAML, OIDC, OAuth 2.0, WS-Fed over the same port.
Admin console (optional)
ALB → Port 9999
ALB with WAF rules for admin console access. TLS terminated at ALB with a corporate certificate. Path-based routing allows restricting which source IPs or user agents can reach the admin endpoint. WAF blocks common admin-targeting attacks.
NLB in Terraform

Building the Network Load Balancer stack

An NLB in Terraform requires three resource types in a specific dependency order: the load balancer itself, the target group (which defines health checks and the backend port), and the listener (which defines the frontend port and forwards to the target group). The ASG then registers instances into the target group automatically.

HCLloadbalancer.tf — complete NLB stack
# ── NETWORK LOAD BALANCER ─────────────────────────────────────────────
resource "aws_lb" "pf_nlb" {
  name               = "${local.name_prefix}pf-nlb"
  internal           = false      # internet-facing: federation partners are external
  load_balancer_type = "network"  # NLB, not ALB

  # Place NLB nodes in public subnets (one per AZ for HA)
  subnets            = local.public_subnet_ids

  # Enable cross-zone load balancing
  # Allows NLB nodes to route to healthy targets in OTHER AZs
  # Critical if one AZ has fewer PF instances during AMI refresh
  enable_cross_zone_load_balancing = true

  # Preserve source IP — PF audit logs show real client IPs, not NLB IPs
  enable_deletion_protection = local.is_prod  # prevent accidental destroy in prod

  tags = merge(local.common_tags, {
    Name    = "${local.name_prefix}pf-nlb"
    Purpose = "PingFederate federation endpoint"
  })
}

# ── TARGET GROUP — federation traffic ─────────────────────────────────
resource "aws_lb_target_group" "pf_federation" {
  name        = "${local.name_prefix}pf-fed-tg"
  port        = 9031
  protocol    = "TCP"      # NLB uses TCP/TLS, not HTTP
  vpc_id      = local.vpc_id
  target_type = "instance"  # instances (not IPs or Lambda)

  # ── HEALTH CHECK ─────────────────────────────────────────────────────
  # NLB health checks for TCP target groups can be TCP or HTTP/HTTPS
  # Use HTTP on PF's health endpoint for meaningful application-layer check
  health_check {
    enabled             = true
    protocol            = "HTTP"        # check PF's HTTP health endpoint
    port                = "8080"        # PF runtime health check port
    path                = "/pingfederate/rest/v1/version"  # PF health path
    healthy_threshold   = 3             # 3 consecutive successes → healthy
    unhealthy_threshold = 3             # 3 consecutive failures  → unhealthy
    interval            = 10            # check every 10 seconds
  }

  # Stickiness — not applicable for stateless federation (OIDC/SAML)
  # PF cluster replication ensures any node can handle any request

  # Deregistration delay — how long NLB drains connections before removing
  deregistration_delay = 60   # 60s: allow in-flight SAML flows to complete

  tags = merge(local.common_tags, {
    Name     = "${local.name_prefix}pf-federation-tg"
    Protocol = "federation"
  })

  # IMPORTANT: Use create_before_destroy so ASG can stay registered
  # during target group replacement (e.g. when port changes)
  lifecycle {
    create_before_destroy = true
  }
}

# ── LISTENER — port 9031 TCP passthrough ──────────────────────────────
resource "aws_lb_listener" "pf_federation" {
  load_balancer_arn = aws_lb.pf_nlb.arn
  port              = 9031
  protocol          = "TCP"   # pure passthrough — TLS handled by PF itself

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.pf_federation.arn
  }

  tags = merge(local.common_tags, { Name = "pf-federation-listener" })
}

Route53

DNS configuration — hosted zones, records, and alias records

Route53 provides the DNS name that federation partners use to reach PingFederate. The critical pattern is the alias record — a Route53-specific record type that maps a DNS name to an AWS resource (like an NLB) rather than an IP address. Alias records are preferred over CNAME records for AWS resources because they are free of charge, resolve at the DNS level (no extra lookup), and update automatically when the NLB's IP changes.

HCLdns.tf — Route53 hosted zone and records
# ── DATA SOURCE: existing hosted zone ─────────────────────────────────
# In most enterprise setups, the hosted zone already exists
# and is managed by the networking team. We look it up as a data source.
data "aws_route53_zone" "main" {
  name         = var.hosted_zone_name    # e.g. "example.com"
  private_zone = false                  # public hosted zone
}

# If you need to CREATE the hosted zone (greenfield):
# resource "aws_route53_zone" "main" {
#   name    = var.hosted_zone_name
#   comment = "PingFederate federation domain"
#   tags    = local.common_tags
# }

# ── ALIAS RECORD: pf.example.com → NLB ───────────────────────────────
# Alias records are free and resolve directly to NLB without CNAME lookup
resource "aws_route53_record" "pf_federation" {
  zone_id = data.aws_route53_zone.main.zone_id
  name    = "pf.${var.hosted_zone_name}"   # pf.example.com
  type    = "A"   # A record with alias = no TTL, resolves to NLB IPs

  alias {
    name                   = aws_lb.pf_nlb.dns_name
    zone_id                = aws_lb.pf_nlb.zone_id
    evaluate_target_health = true
    # evaluate_target_health = true means:
    # Route53 considers the NLB's health before returning the record.
    # If ALL NLB nodes are unhealthy, Route53 does NOT return the DNS record.
    # This prevents DNS from pointing to a known-unhealthy endpoint.
  }
}

# ── ADMIN CONSOLE RECORD ───────────────────────────────────────────────
resource "aws_route53_record" "pf_admin" {
  zone_id = data.aws_route53_zone.main.zone_id
  name    = "pf-admin.${var.hosted_zone_name}"
  type    = "A"

  alias {
    name                   = aws_lb.pf_alb_admin.dns_name
    zone_id                = aws_lb.pf_alb_admin.zone_id
    evaluate_target_health = true
  }
}

# ── PRIVATE HOSTED ZONE: internal service discovery ───────────────────
# Allows internal services (Ansible, monitoring) to reach PF
# by a stable name without going through the internet
resource "aws_route53_zone" "internal" {
  name    = "internal.${var.hosted_zone_name}"
  comment = "Private zone for internal PF service discovery"

  vpc {
    vpc_id = local.vpc_id   # associate with the PF VPC
  }

  tags = merge(local.common_tags, { Name = "pf-internal-zone" })
}

resource "aws_route53_record" "pf_internal" {
  zone_id = aws_route53_zone.internal.zone_id
  name    = "pf.internal.${var.hosted_zone_name}"
  type    = "A"

  alias {
    name                   = aws_lb.pf_nlb.dns_name
    zone_id                = aws_lb.pf_nlb.zone_id
    evaluate_target_health = true
  }
}

# ── OUTPUT ─────────────────────────────────────────────────────────────
output "federation_fqdn" {
  description = "Fully-qualified DNS name for the PF federation endpoint"
  value       = aws_route53_record.pf_federation.fqdn
  # e.g. pf.example.com
}
Alias record vs CNAME — always prefer alias for AWS resources
A CNAME record is a hostname-to-hostname mapping. It adds a DNS lookup hop and cannot be used at the zone apex (you cannot CNAME example.com → something). An alias record is a Route53 extension that maps a hostname directly to an AWS resource's IP addresses, with no extra lookup. It is free (CNAMEs within Route53 cost per query), works at the zone apex, and supports evaluate_target_health which prevents Route53 from returning records for unhealthy endpoints. Always use alias records for NLBs, ALBs, CloudFront, and S3 website endpoints.
Health checks during AMI refresh

How the NLB maintains zero-downtime during instance replacement

The interaction between the NLB health check and the ASG instance_refresh is what enables zero-downtime AMI replacement. Each component plays a distinct role, and understanding the sequence prevents the most common operational mistakes.

NLB health check role
Gates traffic at the load balancer
The NLB health check probes port 8080 every 10 seconds. It only marks an instance as healthy after 3 consecutive successes. It never routes federation traffic to a new instance until that instance passes health checks. During instance_refresh, new instances are held in Pending until they pass health checks before old instances are terminated.
Deregistration delay role
Drains in-flight connections safely
When an instance is deregistered from the target group (during refresh), the NLB keeps existing TCP connections open for up to 60 seconds (the deregistration_delay). This allows in-flight SAML flows and OIDC token exchanges to complete. New connections to the deregistering instance are blocked immediately. After 60 seconds, all connections are forcibly closed.

Why evaluate_target_health = true matters during refresh
When evaluate_target_health = true is set on the Route53 alias record, Route53 will not return DNS results for the NLB if all of its targets are unhealthy. This is an additional safety net: if the AMI refresh goes wrong and all instances fail health checks, Route53 stops resolving pf.example.com — clients immediately see DNS failures rather than connection timeouts to unhealthy servers. In practice this should trigger alerts and the auto_rollback policy should have already kicked in, but it's a valuable last-resort protection.
ALB for admin console

Optional: ALB with WAF for the PingFederate admin console

The PF admin console (port 9999) has very different security requirements from the federation endpoint. It should never be exposed to the public internet directly. The ALB with WAF provides HTTP-layer protection, IP allowlisting, and audit logging for administrative access.

HCLalb-admin.tf — ALB for PF admin console
# ── APPLICATION LOAD BALANCER (admin only) ─────────────────────────────
resource "aws_lb" "pf_alb_admin" {
  name               = "${local.name_prefix}pf-admin-alb"
  internal           = true     # internal-only: only reachable from within VPC/VPN
  load_balancer_type = "application"
  security_groups    = [aws_security_group.admin_alb.id]
  subnets            = local.private_subnet_ids   # internal ALB in private subnets

  # Enable access logs to S3 for compliance audit trail
  access_logs {
    bucket  = aws_s3_bucket.alb_logs.bucket
    prefix  = "pf-admin-alb"
    enabled = true
  }

  tags = merge(local.common_tags, { Name = "${local.name_prefix}pf-admin-alb" })
}

Knowledge check

Test your load balancer and DNS understanding

QA federation partner reports intermittent SAML signature validation failures after an AMI refresh. The failures occur on approximately 30% of SSO attempts and resolve after about 5 minutes. What is the most likely cause?▼
The most likely cause is a JGroups cluster synchronisation lag. When new PF engine instances join the cluster after an AMI refresh, they need time to receive the cluster state — including any in-memory session data and configuration that was distributed across the existing nodes. If the deregistration delay is too short or the instance warmup period is too aggressive, new instances that haven't fully synchronised with the cluster are receiving traffic before their cluster state is complete. The 30% failure rate matches a partially synchronised cluster (some nodes have the state, some don't). The resolution after 5 minutes matches the JGroups synchronisation window.

Fix: Increase the lifecycle hook heartbeat timeout to ensure Ansible's PF configuration step explicitly waits for cluster membership (PF has a REST API endpoint to check cluster status). The CompleteLifecycleAction should not be called until the instance reports as a full cluster member.
QWhat is the difference between a Route53 CNAME record and a Route53 alias record? When would you be forced to use a CNAME instead of an alias?▼
A CNAME maps a hostname to another hostname (extra DNS lookup, chargeable per query, cannot be at zone apex). An alias record maps a hostname directly to an AWS resource's IP addresses (free, no extra lookup, works at zone apex, supports health evaluation). You would be forced to use a CNAME instead of an alias when: the target resource is not an AWS-native resource (e.g. an on-premises server, a third-party CDN, or an external DNS name that isn't an AWS resource type that Route53 supports for aliases). For any AWS load balancer, CloudFront distribution, API Gateway, or S3 website endpoint, always use alias records. The NLB alias record also benefits from evaluate_target_health = true — which is only available on alias records, not CNAMEs.
QThe deregistration_delay on the target group is set to 60 seconds. A long-running SAML artifact resolution takes up to 90 seconds. What happens to that request when the instance is deregistered?▼
The request will be forcibly terminated after 60 seconds, resulting in a failed SAML artifact resolution. The deregistration delay sets the maximum time the NLB keeps existing connections alive on a deregistering instance. After 60 seconds, the NLB closes all TCP connections to that instance, regardless of whether in-flight requests have completed. For the 90-second artifact resolution, the TCP connection would be closed mid-flow, the client would receive a connection reset, and the SAML flow would fail.

Fix: Increase deregistration_delay to at least 120 seconds (2× the longest expected request duration). Also review whether the SAML artifact resolution can be optimised — 90-second flows are unusually long and may indicate a configuration issue in the back-channel resolution pathway.
QYou need to give a new federation partner the PF endpoint URL. They ask for the IP address rather than the DNS name so they can configure their firewall whitelist. What do you tell them, and what NLB feature helps with this requirement?▼
Direct the partner to the DNS name (pf.example.com) and explain that NLB Elastic IP addresses can provide stable IPs if static IP-based whitelisting is required.

NLBs support Elastic IP assignment (one per subnet/AZ). When you create the NLB with Elastic IPs in the subnet mapping, the NLB's IP addresses are stable and predictable — the partner can whitelist those specific IPs. Unlike ALBs (which use DNS with dynamic IPs), NLBs with Elastic IPs provide deterministic addressing:

In Terraform, modify the NLB configuration to use subnet_mapping blocks instead of subnets:
subnet_mapping { subnet_id = "..." allocation_id = aws_eip.nlb_az_a.id }

Important caveat: once Elastic IPs are associated with an NLB, they cannot be changed without recreating the NLB. Plan this before initial deployment, not after.
QThe NLB health check is currently on TCP (just checking the port is open). The team wants to change it to an HTTP check on port 8080. What Terraform resources will change and will there be any downtime?▼
Only the aws_lb_target_group resource will change — specifically the health_check block. The NLB and listener are unaffected. There will be a brief period of uncertainty during the health check transition, but no downtime if managed correctly.

The target group health check configuration is updated in-place — the target group is not recreated. However, changing from TCP to HTTP health checks means existing healthy instances (healthy under TCP) will be re-evaluated under the new HTTP check. If PF's health endpoint is not responding correctly on port 8080, instances will transition to unhealthy and be removed from the target group, causing downtime.

Safe procedure: Before applying the Terraform change, manually verify that port 8080 is responding on all current PF instances (via SSM Session Manager: curl http://localhost:8080/pingfederate/rest/v1/version). Confirm the response is 200 OK. Then apply the Terraform change. Monitor the NLB target group health in the AWS console for 5 minutes after apply to confirm all instances transition to healthy under the new check.

resource "aws_route53_health_check" "pf_federation_hc" {

Module 07 — Key Takeaways
  • NLB is the correct load balancer for PingFederate federation traffic because it supports TCP/TLS passthrough — allowing PF to terminate TLS with its own federation certificate, which is required for SAML SP certificate validation.
  • ALB is used optionally for the admin console (port 9999) where WAF integration, HTTP-layer inspection, and IP allowlisting are required. ALB terminates TLS and is not suitable for the primary federation endpoint.
  • The three NLB Terraform resources in order: aws_lb (the load balancer itself), aws_lb_target_group (health checks + backend port), aws_lb_listener (frontend port → target group).
  • The health check on the target group (HTTP :8080 /pingfederate/rest/v1/version) verifies PF is running and responding — not just that the TCP port is open. This is what gates traffic during AMI refresh.
  • deregistration_delay = 60 gives in-flight SAML/OIDC flows 60 seconds to complete before the NLB forcibly closes connections to a deregistering instance. Set this higher if your SP back-channel flows are long.
  • Route53 alias records are preferred over CNAMEs for AWS resources — free, no extra DNS lookup hop, work at zone apex, and support evaluate_target_health.
  • evaluate_target_health = true on the alias record tells Route53 to consider NLB target health before returning DNS responses — a last-resort safety net if all instances fail health checks simultaneously.
  • Cross-zone load balancing on the NLB ensures that during AMI refresh, when one AZ may temporarily have fewer healthy instances, traffic is routed to healthy instances in other AZs.
