IAM fundamentals in AWS context

The IAM model — how EC2 instances get credentials

In the traditional model, applications authenticate to AWS using access key IDs and secret access keys — static credentials stored in configuration files, environment variables, or secrets managers. These credentials can be leaked, rotated incorrectly, or left behind on decommissioned instances. In the immutable infrastructure model, this approach is not viable at all — instances are replaced regularly and should not hold long-lived secrets.

The solution is the IAM instance role. An EC2 instance assumes an IAM role at launch time. The AWS metadata service (IMDS at 169.254.169.254) provides temporary, automatically rotated credentials to any process running on the instance. The credentials are scoped to the permissions of the role. When the instance is terminated, the credentials expire and are worthless.

EC2 Credential Flow — Instance Profile in Action
Key insight
No credentials on the instance
The PingFederate process never sees a static access key or secret. The AWS SDK automatically calls the IMDS endpoint to get temporary credentials before every API call. Credentials are short-lived (1–12 hours), automatically rotated, and tied to the instance's attached role. When the instance is terminated in an AMI refresh, the credentials become worthless immediately.
The immutable infra connection
Why this pattern enables instance replacement
In the traditional long-lived server model, credentials might be baked into config files or loaded once and cached. In the immutable model, every new instance gets fresh temporary credentials from IMDS on every API call. No credential rotation ceremony needed. No risk of stale secrets on decommissioned instances. The role policy controls what the instance can do — not what is stored on it.
The four Terraform resources

The IAM building blocks — four resources, one pattern

Creating an IAM instance profile in Terraform requires exactly four resource types, always in this order of dependency: the role, the policy, the policy attachment, and the instance profile. Understanding why each one exists as a separate resource — rather than one monolithic block — reflects AWS's own design philosophy of composable identity primitives.

1
aws_iam_role — the identity primitive
Defines the IAM role itself — its name, description, and critically its trust policy. The trust policy answers: who is allowed to assume this role? For an EC2 instance, the trust principal is ec2.amazonaws.com. Without the correct trust policy, no EC2 instance can assume the role, regardless of what permissions it has.
2
aws_iam_policy — the permission document
Defines what the role is allowed to do — the permission policy. Separate from the role so the same policy can be attached to multiple roles, and the same role can have multiple policies attached. This matches the IAM best practice of modular, reusable permission documents.
3
aws_iam_role_policy_attachment — the binding
Attaches a policy (either customer-managed or AWS-managed) to a role. The role and policy exist independently; the attachment is the relationship. Multiple attachments can exist per role — the permissions are unioned (all attached policies apply). This is the resource that most commonly causes confusion in plan output: if you remove an attachment, the policy is detached from the role but neither the policy nor the role is deleted.
4
aws_iam_instance_profile — the EC2 wrapper
Wraps the IAM role in a container that EC2 understands. EC2 does not directly attach IAM roles to instances — it attaches instance profiles. An instance profile holds exactly one role. The instance profile is what you reference in the Launch Template — not the role directly. This is a common source of confusion: you configure the profile, not the role, in the EC2 Launch Template.
Why EC2 uses instance profiles instead of roles directly
This is an AWS legacy design decision. Instance profiles were introduced before IAM roles existed, and the indirection layer remains for backward compatibility. In practice, a 1:1 relationship always exists between a role and its instance profile in a well-designed system. The separation allows the instance profile to be created, deleted, or updated independently of the role — useful in some migration scenarios. Terraform handles this transparently; you create both resources and reference the profile in the launch template.
Complete Terraform implementation

Building the PingFederate instance role from scratch

The following is the complete, production-ready Terraform code for the PingFederate instance role. Every decision is annotated — not just what it does but why each permission exists and what minimum access was chosen.

HCLiam.tf — PingFederate instance role (complete)
# ── 1. THE IAM ROLE ───────────────────────────────────────────────────
resource "aws_iam_role" "pf_instance" {
  name        = "${local.name_prefix}instance-role"
  description = "IAM role for PingFederate EC2 engine nodes"
  path        = "/pingfederate/"   # IAM path for organisational grouping

  # Trust policy — ONLY EC2 service can assume this role
  # This is the answer to: "who can assume this role?"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid       = "AllowEC2AssumeRole"
        Effect    = "Allow"
        Principal = { Service = "ec2.amazonaws.com" }
        Action    = "sts:AssumeRole"
      }
    ]
  })

  # Maximum session duration — default is 1 hour (3600 seconds)
  # Increase only if long-running operations need it
  max_session_duration = 3600

  tags = merge(local.common_tags, {
    Name    = "${local.name_prefix}instance-role"
    Purpose = "PingFederate EC2 instance identity"
  })
}

# ── 2. THE PERMISSION POLICY ──────────────────────────────────────────
# Customer-managed policy for PF-specific permissions
resource "aws_iam_policy" "pf_instance" {
  name        = "${local.name_prefix}instance-policy"
  description = "Permissions for PingFederate EC2 engine nodes"
  path        = "/pingfederate/"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [

      # S3 — read configuration from the PF config bucket
      # Scoped to the specific bucket and key prefix, not all S3
      {
        Sid    = "ReadPFConfig"
        Effect = "Allow"
        Action = [
          "s3:GetObject",
          "s3:GetObjectVersion",
          "s3:ListBucket"
        ]
        Resource = [
          aws_s3_bucket.pf_config.arn,
          "${aws_s3_bucket.pf_config.arn}/*"
        ]
      },

      # S3 — write audit logs to a separate audit bucket
      {
        Sid    = "WriteAuditLogs"
        Effect = "Allow"
        Action = ["s3:PutObject"]
        Resource = ["${aws_s3_bucket.pf_audit.arn}/audit/*"]
      },

      # CloudWatch Logs — write PF runtime and error logs
      {
        Sid    = "WriteCloudWatchLogs"
        Effect = "Allow"
        Action = [
          "logs:CreateLogGroup",
          "logs:CreateLogStream",
          "logs:PutLogEvents",
          "logs:DescribeLogStreams"
        ]
        Resource = [
          "arn:aws:logs:${var.aws_region}:${data.aws_caller_identity.current.account_id}:log-group:/pingfederate/*"
        ]
      },

      # SSM — allow Systems Manager agent, parameter reads
      # Required for Session Manager (no SSH key needed)
      {
        Sid    = "SSMParameterRead"
        Effect = "Allow"
        Action = [
          "ssm:GetParameter",
          "ssm:GetParameters",
          "ssm:GetParametersByPath"
        ]
        Resource = [
          "arn:aws:ssm:${var.aws_region}:${data.aws_caller_identity.current.account_id}:parameter/pingfederate/*"
        ]
      },

      # KMS — decrypt S3 objects and SSM parameters encrypted with CMK
      {
        Sid    = "KMSDecrypt"
        Effect = "Allow"
        Action = [
          "kms:Decrypt",
          "kms:GenerateDataKey"
        ]
        Resource = [var.config_kms_key_arn]
      },

      # EC2 — read instance metadata for cluster auto-discovery
      {
        Sid    = "EC2DescribeForCluster"
        Effect = "Allow"
        Action = [
          "ec2:DescribeInstances",
          "ec2:DescribeTags"
        ]
        Resource = ["*"]   # EC2 Describe actions don't support resource-level perms
      }
    ]
  })

  tags = local.common_tags
}

# ── 3. POLICY ATTACHMENTS ─────────────────────────────────────────────

# Attach the custom PF policy
resource "aws_iam_role_policy_attachment" "pf_custom" {
  role       = aws_iam_role.pf_instance.name
  policy_arn = aws_iam_policy.pf_instance.arn
}

# Attach AWS-managed SSM policy for Session Manager
# Provides ssmmessages, ec2messages, s3 access for session data
resource "aws_iam_role_policy_attachment" "pf_ssm_core" {
  role       = aws_iam_role.pf_instance.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}

# ── 4. INSTANCE PROFILE — the EC2 wrapper ────────────────────────────
resource "aws_iam_instance_profile" "pf_instance" {
  name = "${local.name_prefix}instance-profile"
  role = aws_iam_role.pf_instance.name
  path = "/pingfederate/"
  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}instance-profile"
  })
}

# ── OUTPUT — consumed by Launch Template in M06 ───────────────────────
output "pf_instance_profile_arn" {
  description = "Instance profile ARN — referenced in Launch Template"
  value       = aws_iam_instance_profile.pf_instance.arn
}

output "pf_instance_role_arn" {
  description = "Role ARN — used for cross-account or monitoring purposes"
  value       = aws_iam_role.pf_instance.arn
}
Trust policy vs permission policy

The two-policy model — trust and permissions are separate

This is fundamental IAM architecture that you already know deeply — but it maps onto Terraform in a specific way that's worth making explicit. Every IAM role has two distinct policy layers, each answering a different question.

IAM Role — Two-Policy Model
Policy TypeQuestion it answersWhere it lives in TerraformPF example
Trust Policy "Who can assume this role?" Inside the aws_iam_role resource, in the assume_role_policy argument ec2.amazonaws.com — only EC2 service can assume the PF instance role
Permission Policy "What can the role do once assumed?" Separate aws_iam_policy resource, attached via aws_iam_role_policy_attachment S3 GetObject on config bucket, SSM GetParameter, CloudWatch PutLogEvents
EC2 Service ─ AssumeRole → pf-instance-role ─ grants → S3 GetObject
ec2.amazonaws.com Trust policy: ✓ SSM GetParameter
Common mistake: inline policy vs attached policy
You will encounter two patterns in the wild. The aws_iam_role_policy resource creates an inline policy — embedded directly in the role, not reusable, deleted when the role is deleted. The aws_iam_policy + aws_iam_role_policy_attachment pattern creates a customer-managed policy that exists independently and can be attached to multiple roles. The enterprise standard is always the managed policy pattern — it's versionable, reusable, and auditable via IAM console without needing to inspect the role directly.
Least privilege in practice

What the PF instance role should and should not have

The most common IAM mistake in infrastructure automation is granting overly broad permissions because it is easier. The PF instance role is attached to long-running nodes that process authentication traffic — the blast radius of a compromised node depends entirely on what that role is permitted to do. Least privilege is not just a compliance requirement here; it is a direct security control.

✓ Should have
Minimum required permissions
  • ◆S3 GetObject / ListBucket on the specific config bucket only
  • ◆CloudWatch PutLogEvents scoped to /pingfederate/* log group prefix
  • ◆SSM GetParameter scoped to /pingfederate/* parameter path
  • ◆KMS Decrypt scoped to the specific CMK ARN used for config encryption
  • ◆EC2 DescribeInstances / DescribeTags for JGroups cluster discovery (resource: *)
  • ◆AWS managed policy AmazonSSMManagedInstanceCore for Session Manager
✗ Should NOT have
Over-privileged patterns to avoid
  • ✗s3:* — never allow full S3 access; scope to specific bucket and actions
  • ✗iam:* — instance roles should never be able to modify IAM
  • ✗ec2:* — DescribeInstances is needed; CreateInstance, TerminateInstance are not
  • ✗AdministratorAccess managed policy — never on an instance role
  • ✗S3 DeleteObject on the config bucket — PF reads config, never deletes it
  • ✗Cross-account permissions without explicit justification and review
🧑‍🏫
The wildcard resource asterisk — when it's unavoidable
Some AWS actions simply cannot be resource-scoped — ec2:DescribeInstances is one of them. AWS does not support resource-level permissions for Describe actions in EC2. The only option is "Resource": ["*"]. This is documented and expected — it does not violate least privilege in intent, only in expression. In any security review, the important distinction is: is the * in the Resource because it's required by the API, or because someone was lazy? The PF role has one justified * (EC2 Describe) and all other permissions are resource-scoped.
IAM paths and naming

Organising IAM resources at enterprise scale

IAM paths are a namespacing mechanism that most teams ignore until their IAM namespace becomes unmanageable. In an enterprise with hundreds of roles, clear path conventions make it possible to scope permission boundaries, write service control policies, and audit IAM resources by application or team.

HCLIAM naming and path conventions
# IAM path organises resources in the IAM namespace
# Path: /application/environment/ or /team/application/

resource "aws_iam_role" "pf_instance" {
  name = "pf-prod-instance-role"   # globally unique in the account
  path = "/pingfederate/"          # logical grouping in IAM console
  # ...
}

# With a path, the full ARN becomes:
# arn:aws:iam::123456789012:role/pingfederate/pf-prod-instance-role
#                                   ↑ path ↑

# Permission boundaries — restrict the maximum permissions a role can have
# Even if the policy grants AdministratorAccess, the boundary limits it
resource "aws_iam_role" "pf_instance" {
  name                 = "pf-prod-instance-role"
  path                 = "/pingfederate/"
  permissions_boundary = var.permissions_boundary_arn
  # var.permissions_boundary_arn is an ARN of a managed policy
  # that caps the maximum effective permissions of this role
  assume_role_policy   = jsonencode({ /* ... */ })
}

# Permissions boundary pattern in enterprise:
# - Platform team defines a boundary policy per application class
# - Application teams must apply boundary when creating roles
# - SCPs in AWS Organizations enforce that boundary usage is mandatory
# - Boundary prevents privilege escalation even if policy is misconfigured
Naming convention
{app}-{env}-{purpose}
Example: pf-prod-instance-role. Consistent naming enables CloudTrail filtering, cost allocation, and IAM console navigation without documentation lookup. Apply the same convention to policies and profiles.
IAM path
/application/
IAM paths scope resource-based policies and permission boundaries. Use /pingfederate/ for all PF IAM resources. Makes SCPs and permission boundaries easier to target precisely without affecting other application roles.
Permissions boundary
Maximum effective permissions
A boundary policy caps the maximum permissions, regardless of attached policies. Even if someone mistakenly attaches AdministratorAccess, the boundary limits what the role can actually do. Enterprise best practice for all application-facing roles.

iam:simulate-principal-policy — your most valuable IAM debugging tool
The IAM policy simulator is the authoritative way to verify what a role can do without having to actually attempt the action. You can test any combination of actions, resources, and conditions. In Terraform context, run the simulation after every IAM apply to confirm the effective permissions match your intention — especially when permission boundaries or SCPs are in play. Add it to your deployment runbook for the PF role.
Knowledge check

Test your IAM-to-Terraform mapping

QWhat is the difference between aws_iam_role_policy and aws_iam_policy + aws_iam_role_policy_attachment? When would you use each?▼
aws_iam_role_policy creates an inline policy embedded directly in the role. The combined pattern creates a customer-managed policy that exists independently. Use inline policies (aws_iam_role_policy) when: the policy is specific to exactly one role and will never be reused, you want the policy to be automatically deleted when the role is deleted, and you want the permissions to be clearly visible in the role definition without navigating to a separate policy. Use the managed policy pattern (aws_iam_policy + attachment) when: the policy might be reused across multiple roles, you want to version the policy independently, you want the policy to appear in IAM's list of managed policies for auditing, or your organisation requires all permissions to be customer-managed policies for compliance. In enterprise environments, the managed policy pattern is almost always preferred — it is more auditable, more modular, and compatible with permission boundary enforcement.
QA PingFederate instance starts but fails to read the configuration from S3. The S3 bucket exists and the file is there. What are the three most likely IAM-related causes?▼
Three most likely IAM causes, in order of frequency:

1. Instance profile not attached to the Launch Template. The role exists in IAM but the instance was launched without the profile — either because the Launch Template was missing the iam_instance_profile block or because the Launch Template version in use predates the profile addition. Check: aws ec2 describe-instances --instance-ids i-xxx --query "Reservations[].Instances[].IamInstanceProfile"

2. S3 bucket resource in the policy doesn't match the actual bucket ARN. A common mistake is specifying arn:aws:s3:::pf-config-bucket/* in the policy but the actual bucket name is different, or missing the bucket-level ARN alongside the object-level ARN (both are needed for ListBucket + GetObject). Check with iam:simulate-principal-policy.

3. KMS key policy denies the role. If the S3 objects are encrypted with SSE-KMS, the KMS key policy must explicitly allow the instance role to perform kms:Decrypt. An IAM policy that grants KMS permissions is necessary but not sufficient — the KMS key policy itself must also allow the principal. Both policies must allow the action (resource-based AND identity-based). This is the "two-door" model of KMS access control.
QWhy is the Launch Template configured with iam_instance_profile.arn rather than the IAM role ARN directly? What would happen if you put the role ARN in instead?▼
EC2 does not accept IAM role ARNs — it only accepts instance profile ARNs or names. The iam_instance_profile argument in a Launch Template must reference an instance profile, not the role itself. If you attempt to use a role ARN, the API call to create or update the Launch Template will fail with a validation error. The instance profile is the EC2-specific wrapper around the role. In Terraform, you reference the profile's ARN via aws_iam_instance_profile.pf_instance.arn — not the role's ARN. This is one of the most common sources of confusion when engineers first set up EC2 IAM in Terraform, because in the IAM console the role and profile look almost identical and the distinction seems arbitrary at first.
QYou add a new S3 bucket for PF audit logs and want the instance role to be able to write to it. What Terraform changes are required? Will any resources need to be recreated?▼
One resource is modified: the aws_iam_policy resource gets an updated policy document. No resources need to be recreated. IAM policies support in-place updates — Terraform will call iam:CreatePolicyVersion to create a new version of the customer-managed policy and set it as the default. The role, profile, attachment, and Launch Template are completely unaffected. The change takes effect immediately — the next time an instance's AWS SDK calls STS to refresh its temporary credentials, the new permissions will be included. Running instances do not need to be restarted to pick up IAM policy changes. This is one of the key advantages of the role-based model over static credentials — access policy changes propagate to all running instances automatically without any instance-level intervention.
QYour security team wants to prevent the PF instance role from being able to call IAM or STS APIs at all — not even to verify its own identity. Is this safe and how would you implement it?▼
Blocking STS is not safe — the instance role mechanism requires STS. Blocking IAM management actions is both safe and recommended. The IMDS credential mechanism works by having the AWS hypervisor call STS on behalf of the instance to generate temporary credentials. The PF process itself does not directly call STS — the SDK calls it automatically. However, you should NOT add sts:AssumeRole to the permission policy unless the PF process needs to assume a different role. To prevent IAM manipulation, add an explicit deny in a permission boundary or SCP: deny iam:CreateRole, iam:AttachRolePolicy, iam:PutRolePolicy, and similar IAM write actions. These denies should live in the permission boundary policy, not in the role policy itself — a permission boundary applies even if the role policy mistakenly grants IAM permissions.

Module 05 — Key Takeaways
  • IAM instance roles give EC2 instances temporary, automatically rotated credentials via the IMDS. No static credentials are stored on the instance — this is what enables safe immutable compute.
  • Four Terraform resources create the complete IAM stack: aws_iam_role (trust), aws_iam_policy (permissions), aws_iam_role_policy_attachment (binding), aws_iam_instance_profile (EC2 wrapper).
  • The trust policy answers "who can assume this role?" — for PF engines, that's ec2.amazonaws.com. The permission policy answers "what can the role do once assumed?" — S3 read, CloudWatch write, SSM read, KMS decrypt.
  • The Launch Template references the instance profile ARN, not the role ARN. EC2 cannot directly use roles — only profiles. This is the most common misconfiguration in IAM + EC2 Terraform code.
  • Customer-managed policy (aws_iam_policy) is preferred over inline policy (aws_iam_role_policy) in enterprise environments — it's reusable, independently versioned, and auditable.
  • Least privilege: scope S3 and SSM permissions to specific bucket ARNs and parameter path prefixes. The only justified Resource: ["*"] is for EC2 Describe actions, which don't support resource-level permissions.
  • IAM permission boundary provides a maximum permissions cap — even if the policy is misconfigured to grant too much, the boundary limits the effective permissions. Required in most enterprise environments.
  • IAM policy changes propagate to running instances automatically — the next credential refresh from IMDS picks up new permissions. No instance restart required.
