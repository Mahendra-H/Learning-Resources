The final module — from builder to operator

Across nine modules you have built the complete PingFederate AWS infrastructure stack and learned to structure it for enterprise operation. You understand every resource, every design decision, and how the pieces connect. You can navigate an enterprise codebase on day one and contribute changes safely.

Module 10 covers the last dimension: what happens when things go wrong. In production Terraform, things go wrong regularly — a plan shows unexpected changes, an apply fails mid-way, a state file gets corrupted, an AMI refresh stalls. The engineers who are trusted to own production deployments are not the ones who have never made mistakes — they are the ones who know exactly what to do when something goes sideways, and who can do it without making it worse.

This module is your operational handbook. Read it carefully. You will use this knowledge on your first week contributing to the real project.

🧑‍🏫
Mentor Note — the discipline that matters most
The most important operational discipline in Terraform is: all changes go through Terraform, always, even in an incident. The moment you make a manual change outside Terraform to resolve a production issue, the state file diverges from reality, and the next apply is unpredictable. Build the habit now — before you're under pressure — and it will serve you for the rest of your infrastructure career.
Reading plan output

How a senior engineer reads a terraform plan

Plan output is the most important document in a Terraform deployment. Reading it correctly — not just skimming it — is a core production skill. Here is a systematic approach to reviewing any plan, followed by a real-world PF plan annotated line by line.

Step 1 — Check the summary line
How many changes?
Scroll to the bottom first: Plan: 3 to add, 1 to change, 0 to destroy. The destroy count is the most important number. Any unexpected destroy warrants careful investigation before applying.
Step 2 — Find the destroys
Every - and -/+ must be justified
Search the plan output for lines starting with - (destroy) and -/+ (destroy and recreate). For each one: is this expected? Is there a change window? Will this cause downtime? Never apply unexplained destroys to production.
Step 3 — Verify the creates
Confirm + additions are intentional
For each new resource being created, confirm it is expected. A create with no corresponding PR change is a sign of drift or a missing ignore_changes. Unexpected creates usually indicate a resource that Terraform believes doesn't exist but actually does.

Debugging failed applies

What to do when terraform apply fails

A failed apply is not a disaster — Terraform's incremental state management means the partial apply is recoverable. The key is understanding what state was written before the failure, what was not, and how to safely resume.

ShellDiagnosing a failed apply — systematic approach
# ── STEP 1: Read the error message carefully ──────────────────────────
# The last few lines of the apply output contain the specific error
# Common error patterns:
# Error: error creating Security Group: InvalidGroup.Duplicate
# → The SG already exists in AWS but not in state. Use terraform import.

# Error: Error modifying DB instance: InvalidParameterCombination
# → Invalid attribute combination. Fix the HCL and re-apply.

# Error: timeout while waiting for resource to be created
# → AWS API timeout. Check AWS service health. Re-apply — Terraform will retry.

# Error: Error acquiring the state lock
# → Another operation holds the lock. Wait or force-unlock if stale.

# ── STEP 2: Check what was created before failure ─────────────────────
terraform state list
# Compare this list against what the plan said would be created
# Resources in state = successfully created. Not in state = failed or not reached.

# ── STEP 3: Verify resources exist in AWS ────────────────────────────
# Spot-check a few resources from state
terraform state show aws_security_group.pf_engine
# If it's in state, it should exist in AWS. If the resource was deleted out-of-band,
# state show will show stale data until next plan refreshes it.

# ── STEP 4: Fix the root cause ────────────────────────────────────────
# Address whatever caused the failure (fix HCL, wait for AWS, import existing resource)

# ── STEP 5: Re-apply ─────────────────────────────────────────────────
terraform plan    # verify the remaining changes look correct
terraform apply   # Terraform picks up where it left off — only applies what's missing

# ── ENABLING DEBUG LOGGING ────────────────────────────────────────────
# For hard-to-diagnose errors, enable detailed logging
export TF_LOG=DEBUG
terraform apply 2>&1 | tee terraform-debug.log
# TF_LOG levels: TRACE > DEBUG > INFO > WARN > ERROR
# DEBUG shows every AWS API call and response — powerful but verbose
export TF_LOG=   # clear after debugging
Most dangerous mistake
Making manual fixes after a partial apply
When an apply fails, the instinct is to log into the AWS console and fix the broken resource manually. Resist this. Manual changes after a partial apply cause state drift. The next plan will show unexpected changes. Fix the root cause in HCL, then re-apply. Terraform handles partial apply recovery correctly — human intervention usually makes it worse.
Safe recovery pattern
Fix-in-code → plan → apply
For any failed apply: identify the error, fix the root cause in the .tf files (or variables), run plan to verify the remaining changes are correct, then apply again. Terraform will not recreate successfully-created resources — it picks up from where the failure occurred. This is one of Terraform's most valuable reliability features.

State incidents

Recovering from state problems — the most stressful scenarios

State incidents are the most stressful scenarios in Terraform operations because the consequences of getting recovery wrong can cascade into production outages. The following are the most common state incidents in enterprise environments and the safe recovery procedure for each.

Incident 1 Plan shows unexpected resource destruction after a routine change

Symptom: You commit a small variable change and run plan. The output shows 15 resources being destroyed — far more than expected.

Most likely cause: A resource rename or module restructure caused Terraform to lose track of existing resources. When a resource address changes (e.g. aws_subnet.private becomes module.vpc.aws_subnet.private), Terraform sees the old address as "to destroy" and the new address as "to create" — even though it's the same resource.

Safe recovery: Do not apply. Add a moved block (Terraform 1.1+) mapping old addresses to new addresses, or run terraform state mv for each affected resource. Run plan again — the unexpected destroys should disappear. Only apply when the plan shows zero unexpected destroys.

Incident 2 State file corrupted after a crash mid-apply

Symptom: terraform plan fails with a JSON parse error or reports resources in impossible states (e.g. a VPC that "exists" with no ID).

Root cause: The apply process was killed mid-write to the state file, leaving a partial or malformed JSON document in S3.

Safe recovery: S3 versioning saves you here. (1) List state file versions: aws s3api list-object-versions --bucket company-tf-state --prefix pingfederate/prod/terraform.tfstate. (2) Identify the last valid version (before the crash). (3) Restore: aws s3api copy-object --copy-source bucket/key?versionId=VALID_VERSION_ID --bucket bucket --key key. (4) Run plan to see the difference between restored state and current AWS reality. (5) Apply carefully to reconcile.

Incident 3 Wrong environment applied — dev tfvars applied to prod state

Symptom: After a confused terraform apply -var-file=dev.tfvars run against the prod backend, the plan shows dozens of changes — smaller instances, different CIDR ranges, missing prod-specific resources.

Immediate action: If apply has not started: exit immediately, do not apply. If apply is in progress: do not interrupt it (partial apply is safer than crash). If apply completed: (1) Restore the state file from S3 backup (before the bad apply). (2) Run plan with the correct prod.tfvars — it will show what needs to be re-applied. (3) Apply to restore prod configuration. (4) Audit the AWS console for any resources that were partially modified.

ShellState recovery toolkit
# ── BACKUP STATE BEFORE ANY SURGERY ──────────────────────────────────
terraform state pull > backup_$(date +%Y%m%d_%H%M%S).tfstate
# Keep this backup until you are certain the environment is stable

# ── FIND DIVERGENT RESOURCES ──────────────────────────────────────────
# Resources in state but plan says will be created (→ state thinks they don't exist)
terraform plan 2>&1 | grep "^  + resource" | grep -v "known after apply"

# ── REMOVE GHOST RESOURCES FROM STATE ────────────────────────────────
# Resource is in state but was deleted in AWS — remove from state
terraform state rm aws_security_group.pf_engine

# ── MOVE RESOURCE TO NEW ADDRESS ─────────────────────────────────────
# After module refactor: old address → new address
terraform state mv \
  aws_security_group.pf_engine \
  module.vpc.aws_security_group.pf_engine

# ── IMPORT UNTRACKED RESOURCE ─────────────────────────────────────────
# Resource exists in AWS but not in state
terraform import aws_s3_bucket.pf_config pf-prod-config-123456789012

# ── VERIFY AFTER SURGERY ─────────────────────────────────────────────
# Always run plan after state surgery before doing anything else
terraform plan
# Expected: No changes. Your infrastructure matches the configuration.
# Or: expected changes from intentional modifications only

Dependency problems

Resource ordering and dependency cycle issues

Terraform builds an implicit dependency graph from resource references. Most of the time this works perfectly. The cases where it breaks — dependency cycles, incorrect ordering, missing explicit dependencies — are well-defined and solvable.

HCL + ShellDependency problems and solutions
# ── PROBLEM 1: Missing dependency — resources created in wrong order ──
# Symptom: apply fails because resource B can't find resource A
# but A hasn't been created yet in this run

# Wrong: S3 bucket policy applied before bucket exists
# (actually handled by implicit reference, but explicit is safer)
resource "aws_s3_bucket_policy" "pf_config" {
  bucket = aws_s3_bucket.pf_config.id   ← implicit dep: bucket created first
  # but public_access_block MUST be applied before bucket policy
  depends_on = [aws_s3_bucket_public_access_block.pf_config]  ← explicit dep
}

# ── PROBLEM 2: Dependency cycle ───────────────────────────────────────
# Symptom: Error: Cycle: aws_security_group.a → aws_security_group.b → aws_security_group.a
# Common cause: SGs referencing each other

# Wrong: circular SG reference
resource "aws_security_group" "nlb" {
  ingress { source_security_group_id = aws_security_group.pf_engine.id }  ← CYCLE
}
resource "aws_security_group" "pf_engine" {
  ingress { source_security_group_id = aws_security_group.nlb.id }        ← CYCLE
}

# Fix: use separate aws_security_group_rule resources
resource "aws_security_group" "nlb"       { /* no inline ingress rules */ }
resource "aws_security_group" "pf_engine" { /* no inline ingress rules */ }
# Separate rule resources allow one-directional references
resource "aws_security_group_rule" "pf_from_nlb" {
  source_security_group_id = aws_security_group.nlb.id   ← no cycle
}

# ── PROBLEM 3: Provider unavailable during plan ───────────────────────
# Symptom: Error: Failed to query available provider packages
# Fix: check network connectivity to registry.terraform.io
# In air-gapped environments: configure a private mirror
# provider.hostname in .terraformrc

# ── DIAGNOSING DEPENDENCY ORDER ───────────────────────────────────────
# Generate dependency graph to visualise resource order
terraform graph | dot -Tsvg > dependency-graph.svg
# Opens in browser — shows directed graph of resource dependencies
# Useful for understanding why a resource is being created before another
Zero-downtime patterns

Making dangerous Terraform changes safely

Some Terraform changes are inherently risky — they involve resource recreation that could cause downtime if executed naively. Here are the proven patterns for making these changes safely in a production PF environment.

High-Risk Change Patterns — Safe Execution Approaches
Change typeRiskSafe pattern
AMI ID updateAll instances replacedinstance_refresh with min_healthy_percentage=90, auto_rollback=true. Health checks gate traffic. Already covered in M06.
Security group rule changeBrief traffic interruption if wrong rule removedUse aws_security_group_rule separate resources. Terraform updates rules in-place for ~ changes. Add new rule first, verify traffic, then remove old rule in a separate apply.
NLB target group port changeAll existing connections droppedCreate new target group with new port (create_before_destroy). Update listener to point to new TG. ASG registers to new TG. Old TG has deregistration delay for connection drain. Delete old TG after drain completes.
VPC CIDR changeAll subnets and compute must be recreatedBlue/green VPC migration: provision new VPC, migrate workloads, update DNS, decommission old VPC. Never in-place in production.
IAM role name changeNew role created, old role referenced by existing instancesUse moved block to rename without recreating. Or: add new role, update instances to use new role via LT update and refresh, then remove old role after all instances are using new role.
KMS key rotationExisting encrypted objects inaccessible if key is deletedNever delete old KMS key — just schedule deletion with 30-day window. Rotate key (new key version, same key ID). All new S3 objects use new key version. Existing objects remain accessible via old key version until re-encrypted.
Instance type changeAll instances in ASG replacedSame as AMI refresh: update LT, instance_refresh handles rolling replacement. No additional steps needed.
Knowledge check

Final module — operational scenario questions

QYou run terraform plan on a Monday morning and it shows 47 resources to destroy and 47 to create. No code changes were made over the weekend. What is the most likely cause and what do you do first?▼
The most likely cause is a module refactor where resource addresses changed — old addresses are shown as destroys, new addresses as creates.

This pattern is almost always caused by: (1) someone moved resources into a module without adding moved blocks, (2) a for_each key changed, causing all resources in the for_each to be recreated, or (3) the resource type changed (e.g. aws_security_group with inline rules being replaced by aws_security_group + separate aws_security_group_rule resources).

First step: Do not apply. Run terraform state list | sort and compare to what terraform plan shows as destroys. If the destroy addresses match the create addresses but with different module prefixes, it's an address change. Use moved blocks or terraform state mv to map old addresses to new ones. Run plan again — the 47 destroys should disappear. Only apply when the plan shows the expected small set of changes.
QDuring a PF AMI refresh, the instance_refresh status shows "Failed" with the reason "Launch template version not found". The auto_rollback triggered and restored old instances. What happened and how do you prevent it next time?▼
The ASG was configured to use a specific LT version number (e.g. version = "4") instead of $Latest. When the new LT version (v5) was created and the old version was deleted during cleanup, the ASG could no longer find version 4.

Prevention: Always configure the ASG to use version = aws_launch_template.pf_engine.latest_version (which resolves to $Latest) rather than a hardcoded version number. When $Latest is used, the ASG always uses the newest version regardless of version number. Additionally, never manually delete Launch Template versions that are still referenced by an ASG. Use the AWS console or CLI to check which versions are in use before deleting old versions during cleanup.
QA terraform plan shows a security group rule being added that you didn't write. You check the .tf files and the rule isn't there. The rule also doesn't appear to be in the state file. What's happening?▼
This is most likely a provider-managed default rule being added by Terraform during a refresh. Some AWS resources, when created, automatically receive default rules or attributes that aren't specified in the original HCL. When Terraform refreshes state at plan time, it reads the real AWS configuration and compares it to what the HCL declares. If the HCL is more restrictive than what's in AWS, Terraform plans to remove the auto-added rule.

But if the rule appears as a create (not a destroy), and it's not in your HCL, the most likely explanation is: the rule was removed from AWS manually, and Terraform is planning to restore it to match what the HCL declares. This means there is a rule declared somewhere in your HCL that doesn't currently exist in AWS — perhaps in a for_each that's being iterated from a variable. Check the HCL carefully, including for_each iterations, to find where this rule is declared.
QAn apply is running in CI. The GitHub Actions runner crashes mid-apply (out of memory). The DynamoDB lock is still held. What are your steps?▼
Five steps, in order:

1. Verify the runner is truly dead. Check GitHub Actions — confirm the job is in a failed/cancelled state, not still running. Do not force-unlock a lock held by an active operation.

2. Check what was applied. Look at the GitHub Actions log before the crash. Note which resources were successfully created/modified before the OOM kill. Run terraform state list to see current state.

3. Spot-check critical resources in AWS. Confirm that key resources (ASG, NLB target group) are in the expected state. A partially applied LT change with no instance_refresh started is generally safe.

4. Force-unlock the stale lock. Get the lock ID from the DynamoDB table or from the error message on the next plan attempt. Run terraform force-unlock <lock-id>.

5. Re-run the apply. Run terraform plan to see remaining changes. Run terraform apply to complete the deployment. Terraform picks up where it left off — it will not re-apply changes that already succeeded.
QYou need to rename the aws_autoscaling_group resource from pf_engines to pf_engine_nodes to align with a new naming convention. What is the complete procedure to do this without destroying and recreating the running ASG?▼
Use a moved block to rename the resource address without destroying the ASG.

Step 1: Add a moved block to the configuration:
moved { from = aws_autoscaling_group.pf_engines; to = aws_autoscaling_group.pf_engine_nodes }

Step 2: Rename the resource block in your HCL from "pf_engines" to "pf_engine_nodes".

Step 3: Update all references to this resource throughout the configuration (any place that references aws_autoscaling_group.pf_engines must be updated to aws_autoscaling_group.pf_engine_nodes).

Step 4: Run terraform plan. The output should show: aws_autoscaling_group.pf_engines has moved to aws_autoscaling_group.pf_engine_nodes — with zero destroys and zero creates. The ASG is not recreated; only the Terraform state address changes.

Step 5: Apply. Remove the moved block after the apply (it's a one-time migration instruction).

Note: The name attribute of the ASG in AWS does not change — only the Terraform address changes. If you also want to rename the actual ASG name in AWS, that requires a separate change that will recreate the ASG (ASG names are immutable). Always separate address renames from name attribute changes.

Lab 10-ADiagnose a broken plan — five anomalies

Review the following terraform plan excerpt. Identify: (1) what is wrong with each change, (2) whether it is safe to apply, and (3) what remediation is needed before applying.

Plan OutputFive anomalies — identify each
Plan: 3 to add, 2 to change, 2 to destroy.

- resource "aws_s3_bucket" "pf_config" {}
+ resource "aws_s3_bucket" "pf_configuration" {}

~ resource "aws_autoscaling_group" "pf_engines" {
    ~ desired_capacity = 4 -> 1
  }

~ resource "aws_security_group" "pf_engine" {
    ~ ingress {
        + cidr_blocks = ["0.0.0.0/0"]
          from_port = 9999
      }
  }

- resource "aws_kms_key" "pf_config" {}

+ resource "aws_launch_template" "pf_engine" {
    + image_id = "ami-0NEW9z8y7x6w5v4u"
  }
✓Reveal Lab 10-A analysis▼

Anomaly 1 — S3 bucket destroy + recreate: The bucket was renamed from pf_config to pf_configuration. Terraform plans to destroy the existing bucket and create a new one. CRITICAL — do not apply. This would delete the production PF config bucket including all versioned config objects. Fix: add a moved block mapping the old address to the new one, or revert the rename.

Anomaly 2 — ASG desired_capacity drop from 4 to 1: The ignore_changes = [desired_capacity] lifecycle rule is missing from the ASG. The auto-scaler raised desired_capacity to 4; Terraform is now planning to reduce it back to the variable default of 1. Do not apply. Fix: restore the lifecycle rule. Run terraform refresh-only to update state to reflect the current 4, then plan again — the change should disappear.

Anomaly 3 — Admin port 9999 open to 0.0.0.0/0: Someone is about to expose the PF admin console to the entire internet. Do not apply. This is a critical security misconfiguration. The cidr_blocks should be the bastion security group ID (SG-to-SG reference), not a public CIDR. Reject the PR, fix the security group rule.

Anomaly 4 — KMS key destroy: The KMS key used to encrypt the config bucket is being destroyed. CRITICAL — do not apply. This would make the encrypted config objects unreadable. The 30-day deletion window protects you if caught in time, but this should be investigated immediately. Root cause: someone likely removed the KMS key resource block. Restore it.

Anomaly 5 — Launch Template create with new AMI: This appears to be a legitimate AMI refresh — a new LT is being created with a new AMI ID. Safe to apply IF the other four anomalies are resolved first, the AMI ID is confirmed with the infrastructure team, and it's an appropriate maintenance window. The LT create alone doesn't trigger instance refresh — the ASG must also reference the new LT version.

Module 10 — Key Takeaways
  • Read plan output summary line first (bottom): check destroy count. Every unexpected destroy must be explained before applying. A plan with unexplained destroys should never be applied to production.
  • Failed applies are recoverable. Terraform writes state incrementally. After fixing the root cause, re-apply — Terraform picks up where it left off without recreating already-successful resources.
  • All changes must go through Terraform, even in an incident. Manual changes after a partial apply cause state drift that makes subsequent plans unpredictable — and usually more dangerous than the original problem.
  • S3 versioning is your state recovery mechanism. Keep bucket versioning enabled on all state backends. A corrupted state file can be restored from the previous S3 version.
  • Dependency cycles (resource A references B references A) are resolved by using separate aws_security_group_rule resources instead of inline rules. Never mix inline and external rules on the same security group.
  • Resource address renames require moved blocks (Terraform 1.1+). Without them, Terraform destroys the old resource and creates a new one — which is catastrophic for S3 buckets, KMS keys, ASGs, and any stateful resource.
  • The AMI refresh runbook is the capstone of this series: it integrates every module — network (M04), IAM (M05), compute (M06), load balancers (M07), S3 (M08), module structure (M09), and operational discipline (M10).
  • The operational disciplines that matter most: run plan before every apply, check the summary line, justify every destroy, keep monitoring active during deployments, and always have a tested rollback plan before starting.
