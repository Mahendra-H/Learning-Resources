Why this module exists

Start with the map, not the syntax

Most Terraform courses start with terraform init. This one doesn't. Before you type a single command, you need a clear mental model of what problem Terraform solves, where it sits in the toolchain you are already working with, and what it is specifically responsible for in your PingFederate migration project.

Here is the key insight: Terraform is not a deployment tool, a configuration management tool, or an orchestration engine. It is an infrastructure provisioning tool. Its job is to describe what AWS resources should exist and to make that description real. Everything beyond provisioning — software installation, application configuration, deployment coordination — belongs to different tools.

By the end of this module, every concept in every module that follows will have a home in a mental model you already own.

🧑‍🏫
Mentor Note
Your 18+ years in IAM and SSO is a bigger advantage than you might think here. The concepts of declarative policy, state reconciliation, and least-privilege resource access that you already reason about daily map almost directly onto how Terraform thinks. You are not learning a new discipline — you are extending your existing one into infrastructure.
Infrastructure as Code

From ClickOps to declared state

Before IaC, infrastructure was managed manually — engineers logging into the AWS console, clicking through wizards, configuring resources by hand. This approach has a name: ClickOps. It works for one engineer building one environment once. It fails at scale, under team collaboration, across environments, and when you need to reproduce what you built six months ago.

Infrastructure as Code solves this by expressing infrastructure as text files checked into version control. The infrastructure becomes reviewable, repeatable, auditable, and automatable — the same properties you already demand from application code.

Before IaC — ClickOps
Manual & Undocumented
Resources created by hand in the AWS console. No record of why a security group rule exists. No way to reproduce the environment identically. Drift accumulates silently. One engineer holds all context in their head.
After IaC — Terraform
Declared & Version-Controlled
Every resource is a code file in Git. Changes go through pull requests. The diff shows exactly what will change before it changes. Any engineer can reproduce the environment from scratch. Drift is detected automatically.
Declarative vs Imperative Infrastructure
Terraform is declarative: you describe the desired end state — "I want a VPC with these subnets, these security groups, this ASG" — and Terraform figures out how to get there. You do not write step-by-step instructions. This is the same mental model as an IAM policy: you declare what should be true, not how to make it true.
Terraform in context

How Terraform compares to the alternatives

You will encounter several IaC tools in enterprise environments. Here is where Terraform sits in that landscape — at the level of awareness that matters for your project, not as a detailed evaluation exercise.

Tool Made by Approach Relevance to you

🧑‍🏫
Why your project chose Terraform
Terraform's multi-cloud provider ecosystem, strong state management, and mature module ecosystem make it the dominant choice for enterprise AWS infrastructure. The fact that it is cloud-agnostic also matters in M&A scenarios — if Company A ever absorbs or divests infrastructure across cloud boundaries, Terraform handles it without a tool change.
The four-component pipeline

GitHub Actions → Terraform → Ansible → PingFederate

Your project uses four technologies that work together. Each one owns a specific slice of the deployment. Understanding where each one's responsibility starts and ends is the foundation for everything else in this series.

The confusion most engineers experience comes from not having a clean mental boundary between these tools. Let's fix that now.

Responsibility Boundaries — PingFederate AMI Refresh
🎯
The boundary rule — memorise this
  • GitHub Actions — orchestrates and sequences. It calls the other tools. It does not know about subnets or PingFederate configuration.
  • Terraform — provisions and manages AWS infrastructure resources. It knows about VPCs, ASGs, and NLBs. It does not know about software running on the instances.
  • Ansible — installs and configures software on the instances that Terraform created. It knows about PingFederate, Java, and systemd. It does not provision AWS resources.
  • S3 — the persistence bridge. Terraform creates the bucket. Ansible reads from it. This separation is what makes instance replacement safe.
Terraform architecture

How Terraform works — the core model

Terraform operates through a small number of core concepts. Before looking at any code, you need these five firmly in place.

Provider
A plugin that translates your HCL declarations into API calls against a cloud platform. The AWS provider translates aws_instance, aws_vpc, and every other AWS resource into calls to the AWS API. Without a configured provider, Terraform cannot talk to anything.
Resource
A single piece of infrastructure managed by Terraform — an EC2 instance, a security group, a Route53 record. Every resource has a type (what kind of thing it is) and a name (how you reference it in other resources). Resources are the primary building block of every Terraform configuration.
State File
A JSON file that records what Terraform believes currently exists in your infrastructure. When you run terraform plan, Terraform compares your configuration against the state file and the real world to calculate what needs to change. Without state, Terraform cannot determine what already exists. This is the most important concept in the entire series — Module 03 is dedicated to it.
Plan
A dry-run that shows exactly what Terraform will create, modify, or destroy — before it does anything. Every change in your project goes through a plan step. Reading plans correctly is a senior engineering skill covered in Module 10.
Apply
The execution of an approved plan. Terraform calls the provider APIs to make the declared changes real. In your project, GitHub Actions runs apply automatically after a plan is approved in the pipeline.

HCL — first contact

Reading your first Terraform file

You do not need to write HCL yet — that is Module 02. Right now, you just need to be able to read it and understand what the different blocks mean. Here is a minimal but realistic Terraform configuration that provisions a security group for PingFederate engine nodes.

HCL · Terraform security_group.tf 
# ── PROVIDER — tells Terraform which cloud to talk to ──────────────────
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"          # use any 5.x release
    }
  }
}

provider "aws" {
  region = var.aws_region        # region comes from a variable
}

# ── VARIABLE — an input to this configuration ──────────────────────────
variable "aws_region" {
  description = "AWS region to deploy into"
  type        = string
  default     = "us-east-1"
}

# ── RESOURCE — the actual AWS resource being created ───────────────────
resource "aws_security_group" "pf_engine" {
  name        = "pf-engine-sg"
  description = "PingFederate engine node security group"
  vpc_id      = module.vpc.vpc_id   # reference another resource's output

  # Allow federation traffic from NLB only
  ingress {
    from_port       = 9031
    to_port         = 9031
    protocol        = "tcp"
    security_groups = [aws_security_group.nlb.id]
  }

  # Allow admin console from bastion only
  ingress {
    from_port       = 9999
    to_port         = 9999
    protocol        = "tcp"
    security_groups = [aws_security_group.bastion.id]
  }

  # Allow all outbound (to reach S3, LDAP, CAs)
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name        = "pf-engine-sg"
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

Notice what you can already read without knowing HCL in depth. The terraform block declares the AWS provider. The variable block defines an input — similar to a function parameter. The resource block is the AWS security group itself. The references like module.vpc.vpc_id show how resources connect to each other without hardcoded IDs.

This declarative style is the same mental model as writing a SAML SP metadata definition: you declare what should exist and let the framework handle the mechanics.

Your project model

Immutable infrastructure — validating your understanding

You came into this series with a working hypothesis about how the project operates. Let's formally validate it, sharpen the parts that are right, and correct the one common misconception.

✓ Correct
Immutable compute model
EC2 instances are treated as disposable compute resources. When a new AMI is released, instances are not patched in place — they are replaced. Terraform manages the template and policy; the ASG manages the replacement.
✓ Correct
Configuration in S3
PingFederate configuration lives in S3, not on the instance. New instances retrieve it at launch. This is what makes replacement safe — the instance is cattle, but the config is precious and persisted externally.
✓ Correct
Terraform owns the AWS layer
VPC, subnets, security groups, IAM roles, Launch Templates, ASGs, NLB, ALB, Route53, S3 — all provisioned and managed by Terraform. Correct and complete.
⚠ Clarification needed
Terraform doesn't manage EC2 instances directly
In an ASG model, Terraform manages the Launch Template and the Auto Scaling Group — not the individual EC2 instances. The ASG launches and terminates instances autonomously. Terraform's state tracks the ASG, not each node. This distinction matters deeply in Module 03.
AMI Refresh Flow — Terraform's exact role
1
Infrastructure team releases new AMI
A new company-approved AMI is baked with the latest OS patches and base software. The AMI ID is published to a shared parameter store or communicated to the application team. Terraform is not involved here yet.
2
Application team updates the Terraform data source
The Terraform configuration contains a data "aws_ami" block that looks up the latest approved AMI by filter at plan time. The team updates the filter or the AMI ID variable to point to the new release. A PR is raised.
3
GitHub Actions runs terraform plan
The pipeline runs terraform plan. The output shows that the Launch Template will be updated with the new AMI ID, and that an instance_refresh will be triggered on the ASG. The plan is reviewed and approved.
4
Terraform apply updates the Launch Template & triggers refresh
This is exactly what Terraform does. It updates the Launch Template with the new AMI ID and kicks off the ASG instance refresh. Terraform's job is now done. The ASG takes over.
5
ASG launches new instances, NLB shifts traffic
The ASG launches new instances using the updated Launch Template. Each new instance runs user_data on boot, pulls PingFederate config from S3 using the attached IAM role, and waits for Ansible to complete configuration. The NLB health check gates traffic until the node is healthy.
6
Old instances are terminated
Once new instances are healthy and serving traffic, the ASG terminates the old instances. The refresh is complete. Zero downtime (if health checks are configured correctly). Terraform's state file now reflects the updated Launch Template. Individual instance IDs are not in state.
First commands

Your first init, plan, and apply

These three commands are the Terraform workflow. You will run them hundreds of times. Understanding what each one does internally is more important than memorising the syntax.

Shell Terminal 
# Step 1 — initialise the working directory
# Downloads the AWS provider plugin, sets up the backend
terraform init

# Step 2 — preview exactly what will change
# Compares your .tf files against state file + real AWS
# Nothing is created or destroyed yet
terraform plan

# Step 3 — execute the plan
# Actually calls AWS APIs to make changes
# Always review the plan output before confirming
terraform apply

# Optional — preview what destroy would do before committing
terraform plan -destroy

# In CI/CD (GitHub Actions), apply is non-interactive:
terraform apply -auto-approve
What happens during terraform init
Terraform reads your terraform { required_providers {} } block, downloads the specified provider plugins from the Terraform Registry (or a private mirror in enterprise environments), and configures the backend. In your project this backend is an S3 bucket — the remote state location. init is safe to run repeatedly and should always be run before plan in CI.
What happens during terraform plan
Terraform reads your .tf files, loads the state file from the backend, refreshes its view of the real world by querying AWS, then computes the difference. The output shows every resource that will be created (+), updated in place (~), or destroyed and recreated (-/+). In your project, a plan that shows -/+ on a Launch Template means an instance refresh is coming.
Knowledge check

Test your mental model

Click each question to reveal the answer. Aim to answer it in your head first.

Q PingFederate is running on an EC2 instance. The infra team releases a new AMI. Who is responsible for replacing the EC2 instance — Terraform, the ASG, or GitHub Actions? ▼
The ASG — with Terraform initiating the process. Terraform updates the Launch Template with the new AMI ID and sets the instance refresh policy. After that, the Auto Scaling Group autonomously replaces instances one at a time (or in batches). GitHub Actions orchestrates the sequence by calling terraform apply, but it doesn't manage instances either. The ASG is the entity that actually terminates old nodes and launches new ones.
Q A new engineer asks: "Doesn't Ansible also provision infrastructure? I've seen Ansible create EC2 instances." How would you explain the boundary? ▼
Ansible can provision infrastructure, but that's not its primary role — and it's not how your project uses it. Ansible is optimised for idempotent configuration management — installing software, managing files, starting services. While Ansible has modules that can call AWS APIs, it lacks Terraform's state management, dependency graph, and plan/apply workflow. In your project, the architectural decision is clear: Terraform owns the AWS layer, Ansible owns the software layer. Mixing them creates fragile, hard-to-reason-about pipelines.
Q What is the difference between Terraform's state file and the real AWS infrastructure? Why do they sometimes diverge? ▼
The state file is Terraform's belief about what exists. The real infrastructure is what actually exists. They diverge — called drift — when someone makes a manual change outside of Terraform (ClickOps), when AWS modifies a resource automatically (e.g. rotating a certificate, updating a default), or when a resource is deleted directly without going through Terraform. terraform plan detects drift by comparing state against the real world. Module 03 covers this in depth.
Q Why does Terraform need a "provider"? Why can't it just talk to AWS directly? ▼
Terraform is cloud-agnostic at its core. The provider is the adapter layer. The Terraform engine understands HCL and state management. It doesn't know anything about AWS, Azure, or GCP APIs. The provider is a plugin that translates between the generic Terraform model and the specific API of a cloud or service. This is why the same Terraform patterns can be used across clouds — only the provider and resource types change, not the workflow.
Q Your colleague says: "We should use Ansible for everything — provisioning and configuration. Why split it across two tools?" What's your response? ▼
The separation exists because the two tools solve fundamentally different problems. Terraform's value is its state model — it tracks what exists, calculates diffs, and safely applies changes through a plan/apply workflow with locking. Ansible's value is idempotent task execution on running systems. Using Ansible to provision AWS infrastructure means giving up Terraform's dependency graph, drift detection, state locking, and module system. Using Terraform to configure software means giving up Ansible's rich module library for file management, service control, and package management. Each tool is best in class for its domain.

Lab 01-A Responsibility mapping exercise

For each of the following tasks, identify which tool owns it: Terraform, Ansible, GitHub Actions, or None of the three (the application or AWS itself). Write your answer before revealing it in the knowledge check below.

  1. Creating a VPC with public and private subnets in us-east-1
  2. Installing the PingFederate runtime on a new EC2 instance
  3. Deciding when to trigger a deployment based on a Git merge event
  4. Creating an S3 bucket to store PingFederate configuration files
  5. Reading the PingFederate configuration from S3 on instance startup
  6. Attaching an IAM role to an EC2 instance so it can read from S3
  7. Registering a new EC2 instance with the NLB target group
  8. Terminating an old EC2 instance after its replacement is healthy
  9. Starting the PingFederate systemd service after installation
  10. Storing the Terraform state file with locking
✓ Reveal Lab 01-A answers ▼
  1. Terraform — VPC and subnets are AWS infrastructure resources.
  2. Ansible — Installing software on a running instance.
  3. GitHub Actions — Event-driven pipeline orchestration.
  4. Terraform — S3 bucket is an AWS infrastructure resource.
  5. None of the three (user_data / Ansible) — The bootstrap script or Ansible playbook reads from S3. This is application initialisation, not infrastructure provisioning.
  6. Terraform — The IAM instance profile is defined in the Launch Template, which Terraform manages.
  7. ASG (AWS) — The Auto Scaling Group handles registration/deregistration with the target group automatically. Terraform configures the ASG policy that enables this, but the act of registering is handled by the ASG and NLB internally.
  8. ASG (AWS) — Instance termination during a refresh is handled by the Auto Scaling Group, not Terraform directly.
  9. Ansible — Starting a systemd service is configuration management.
  10. Terraform (S3 + DynamoDB) — Remote state backend with DynamoDB locking. Module 03 covers this in depth.
Lab 01-B Read your first real .tf file

If you have access to the project repository, navigate to the Terraform directory and find the following without running any commands. The goal is pure reading comprehension:

  1. Find the provider block — what version of the AWS provider does the project use?
  2. Find the backend configuration — what S3 bucket stores the remote state? What DynamoDB table is used for locking?
  3. Find a resource block — pick any aws_security_group resource. What ingress rules does it define?
  4. Find a data source — is there an aws_ami data source? What filter does it use to look up the approved AMI?
  5. Find a module call — does the configuration call any reusable modules? What inputs does it pass?

You will not understand all of it yet — that's the point. The goal is to see that the file is readable, structured, and follows patterns. Every pattern you notice here will be explained in the modules that follow.

Module 01 — Key Takeaways
  • Terraform is a declarative infrastructure provisioning tool. It owns the AWS layer. It does not install software or orchestrate deployments.
  • The four-component pipeline is: GitHub Actions orchestrates → Terraform provisions → Ansible configures → PingFederate runs. Each has a clean boundary.
  • In an ASG model, Terraform manages the Launch Template and ASG policy — not individual EC2 instances. The ASG manages instances.
  • S3 persistence of PingFederate configuration is what makes immutable compute possible. The instance is disposable; the configuration is not.
  • The core Terraform workflow is: Write → Init → Plan → Apply. Plan is always reviewed before Apply in enterprise environments.
  • Drift occurs when real infrastructure diverges from the state file. terraform plan detects it. Terraform does not prevent humans from making changes outside of it — governance and process do.
  • Your IAM depth is a structural advantage. The concepts of declarative policy, trust evaluation, and least-privilege resource access map directly onto Terraform's model.
