The 14-Question Checklist

Click any card to mark it reviewed. Work through all four groups before signing off on any AI system.

🔵 Group 1 — Concept  · Q1–Q3
01
Q1 · Concept
What problem is being solved — and is AI the right tool?
AI adds latency, cost, and non-determinism. A regex, a database query, or a rules engine often solves the same problem in 1/10th the time at 1/100th the cost. Never assume AI is the answer before you've named the question.
✅ Good The team can articulate why rule-based, search-based, or deterministic approaches are insufficient. The AI component handles genuine ambiguity, natural language, or synthesis that structured logic cannot.
🚩 Red Flag "We're using AI because it's the modern approach." No explicit comparison to simpler alternatives. The actual requirement is a lookup, filter, or template fill.
→ Atlas Dawn P1 · Foundation
02
Q2 · Concept
Which model is being used, and why this model over alternatives?
Model choice is an architecture decision, not a default. GPT-4o, Claude Sonnet, Gemini Flash, and Llama 3 each have meaningfully different cost, latency, context windows, and capability profiles. Picking the wrong tier is like over-provisioning an EC2 instance — except the bill never stops.
✅ Good Specific model named with version pinned. Benchmarked against at least one alternative on the actual task. Upgrade/downgrade path documented. Reasoning covers cost, latency, and capability tradeoffs.
🚩 Red Flag "We're using the latest GPT." No version pinned. No comparison. No awareness of whether a smaller, faster, cheaper model (Flash, Haiku, Llama) would meet requirements.
→ Atlas Ember P2 · Model Economics
03
Q3 · Concept
Which layer(s) of the AI Stack does this system touch?
The AI Stack has eight layers from Infrastructure to Applications. A system that touches three layers has three failure surfaces, three cost centers, and three teams to coordinate. Understanding the stack footprint is prerequisite to everything else in this checklist.
✅ Good Each layer is named explicitly: which LLM, which embedding model, which vector DB, which orchestration layer, which application surface. Ownership per layer is assigned. Interfaces between layers are documented.
🚩 Red Flag "It's just an API call to OpenAI." No awareness that embeddings, retrieval, orchestration, and tooling are each separate architectural concerns with separate operational responsibilities.

🟠 Group 2 — Economics  · Q4–Q6
04
Q4 · Economics
What is the realistic token budget per request — p50 AND p95?
Token cost is not average-case, it's worst-case. A p95 request with a bloated system prompt, a long RAG context window, and a verbose output can cost 10–20x the median. Budgeting on p50 alone is like capacity planning on average CPU — the spike is what breaks you.
✅ Good System prompt tokens counted and fixed. RAG chunk size and max chunk count defined. Output max_tokens capped. p50 and p95 estimated separately. Token budget reviewed and approved as a line item.
🚩 Red Flag Token budget estimated from a single happy-path test. No max_tokens cap set. System prompt grows organically without review. No distinction between input and output token costs.
→ Atlas Ember P2 · Token Economics
05
Q5 · Economics
What does this cost at 100 / 1,000 / 10,000 daily active users?
AI costs scale with usage in ways that traditional software does not. A feature that costs $50/day at 100 users can cost $5,000/day at 10,000 users. You need to know this number before launch, not after your first invoice shock.
✅ Good Cost model built: (tokens per request × requests per user per day × users × $/1M tokens). Modeled at 3 scale points. Caching strategy identified to reduce repeated token spend. Cost per user per month calculated and compared against revenue or budget allocation.
🚩 Red Flag "We'll figure out cost at scale later." No cost model exists. No caching considered. No awareness of the difference between input and output token pricing. No executive visibility into the cost trajectory.
→ Atlas Ember P2 · Cost Modeling
06
Q6 · Economics
What are the cost failure modes — what makes the bill 10x?
Every AI system has a cost cliff: the scenario where something goes wrong and the token spend explodes. Runaway agent loops, unbounded RAG retrieval, context window overflow retries, and prompt injection attacks that inflate outputs are all real production failure modes that have produced five-figure surprise bills.
✅ Good Hard limits set: max tokens per request, max requests per user per day, max agent loop iterations. Spend alerts configured in cloud billing. Circuit breakers exist to halt runaway processes. Anomaly detection on daily token spend.
🚩 Red Flag No rate limiting on AI endpoints. No spend alerts. Agent loops have no iteration cap. No circuit breaker. The first sign of a runaway cost event will be a monthly invoice, not a real-time alert.
→ Atlas Ember P2 · Cost Controls
🟢 Group 3 — Architecture  · Q7–Q11
07
Q7 · Architecture
Is RAG required? What is the chunking and retrieval strategy?
RAG is not free. Every retrieval adds latency, cost, and a new failure surface. But without it, models hallucinate facts they don't have. The decision to use RAG — and exactly how — is one of the most consequential architecture choices in any knowledge-intensive AI system.
✅ Good Chunking strategy explicit: size (e.g. 512 tokens), overlap (e.g. 50 tokens), and boundary logic (sentence vs. paragraph). Embedding model pinned. Retrieval method chosen (cosine similarity, MMR, hybrid BM25+vector). Top-K defined. Relevance threshold set to discard low-confidence chunks.
🚩 Red Flag "We just embed the whole document." No chunking strategy. Default top-K with no relevance threshold. Embedding model not pinned. No evaluation of retrieval quality against a test query set.
→ Atlas Circuit P3 · RAG Architecture
08
Q8 · Architecture
Are agents or tools required? What is the blast radius of failure?
Agents that can take actions in external systems are fundamentally different from agents that only read. A tool call that writes to Jira, triggers a ServiceNow workflow, or modifies IAM policies can cause real-world harm if the model hallucinates, misinterprets context, or is manipulated by a prompt injection attack.
✅ Good Every tool is classified as read-only or write/mutating. Blast radius documented per tool (what is the worst action this tool can take?). Mutating tools require human confirmation or approval workflow. Tools scoped to minimum necessary permissions — just like service accounts in IAM.
🚩 Red Flag Agents have broad write access with no approval step. No blast radius analysis done. Tools granted admin-level permissions "for simplicity." No distinction made between read and write tool calls.
→ Atlas Circuit P3 · Agent Design
09
Q9 · Architecture
What is the memory and state strategy for long or repeated sessions?
LLMs are stateless by design. Every session starts from zero unless you engineer memory explicitly. Without a memory strategy, users repeat themselves, context is lost between sessions, and long conversations hit context window limits and silently degrade. This is the closest thing in AI to session management in web apps — and it's just as easy to get wrong.
✅ Good Memory strategy explicitly chosen: none (stateless), session-scoped (in-context), summarization (compressed long-term), or external store (user profile DB). Context window budget allocated between system prompt, memory, retrieved context, and response. Overflow behavior defined.
🚩 Red Flag Full conversation history appended without limit. No awareness of context window ceiling. No summarization or compression strategy. Memory not considered at all because "it's just a prototype."
→ Atlas Circuit P3 · Memory Patterns
10
Q10 · Architecture
What is the fallback behavior when the model fails or returns garbage?
Models fail. They time out, return malformed JSON, hallucinate structured outputs, hit rate limits, and occasionally produce responses that bear no relation to the prompt. Unlike a database query that throws a typed exception, model failure is often silent and structurally valid but semantically wrong. You need a circuit breaker, not just a try/catch.
✅ Good Structured output validation in place (JSON schema, Pydantic, or equivalent). Retry logic with exponential backoff and jitter. Fallback model configured (e.g. downgrade to smaller model on timeout). Graceful degradation path exists: the product remains usable if AI is unavailable. User-facing error messages are clear, not raw model errors.
🚩 Red Flag Raw model output passed directly to downstream systems without validation. No retry logic. No fallback model. AI failure = feature unavailable with no graceful degradation. User sees stack traces or raw API errors.
→ Atlas Dawn P1 · Resilience Patterns
11
Q11 · Architecture
What latency requirements exist — and are they measured at p95?
LLM latency is non-deterministic and right-skewed. A request that takes 800ms at p50 can take 4–6 seconds at p95 — especially with tool calls, RAG retrieval, and long outputs stacked in sequence. Building to average latency is building to fail under load. P95 is the user experience that matters.
✅ Good Latency SLA defined per user-facing interaction (e.g. ≤2s p95 TTFB for streaming, ≤5s p95 for full completion). Latency budget allocated across each stage: retrieval, model inference, tool calls, postprocessing. Streaming enabled where possible to improve perceived latency. p95 measured in load test, not just smoke test.
🚩 Red Flag "It feels fast enough in dev." No latency SLA. No p95 measurement. Latency tested with a single user, not under concurrent load. Streaming not considered. Tool calls not measured separately from model latency.
→ Atlas Dawn P1 · Performance
🟣 Group 4 — Security  · Q12–Q14
12
Q12 · Security
What controls exist against prompt injection and context poisoning?
Prompt injection is SQL injection for the LLM era. An attacker who can influence content that enters the context window — through a document, a web page, a database field, or a user message — can attempt to hijack agent behavior, exfiltrate data, or override safety instructions. Every RAG pipeline and every agent with tool access is a potential injection surface.
✅ Good User-controlled content is clearly delimited from system instructions in the prompt structure. Retrieved documents are sandboxed and labeled as untrusted content. Input validation strips or escapes known injection patterns. Output is validated before acting on any model-generated instructions. Penetration testing includes prompt injection scenarios.
🚩 Red Flag User input concatenated directly into system prompts with no delimiting. Retrieved document content treated as trusted. No awareness that a malicious document in the vector DB could hijack agent behavior. Prompt injection not included in threat model.
→ Atlas Vault P4 · Security Architecture
13
Q13 · Security
What approval workflows and audit logging govern AI-driven actions?
When an AI agent takes an action in a business system — provisioning access in Okta, creating a ticket in ServiceNow, modifying a CyberArk vault entry — that action must be attributable, reviewable, and revocable. The audit trail for AI-driven actions must be at least as rigorous as for human-driven actions. "The model did it" is not a valid incident response answer.
✅ Good Every consequential action logged with: timestamp, actor (user + model), inputs provided, action taken, system affected, outcome. High-risk actions route through human approval before execution. Approval audit trail is immutable. Logs feed into SIEM. AI actions are distinguishable from human actions in audit logs. Retention policy matches compliance requirements.
🚩 Red Flag AI actions logged only at the application layer with no system-of-record audit trail. No human approval gate for consequential actions. Logs do not identify which model was used or what prompt produced the action. No review process for AI-generated access grants or policy changes.
→ Atlas Vault P4 · Governance
14
Q14 · Security
What monitoring exists for quality drift, cost anomalies, and security incidents?
AI systems degrade in ways that traditional software does not. Model behavior can shift when the provider updates a model without notice. Embedding drift makes retrieval silently worse over months. Cost anomalies signal abuse, runaway loops, or injection attacks. None of these show up in standard APM dashboards — you need AI-specific observability.
✅ Good Quality: automated eval suite runs on a golden test set after every model/prompt change. Cost: daily spend alerts with anomaly detection, per-user and per-endpoint cost attribution. Security: alerts on unusual token volumes, unexpected tool call patterns, and retrieval of flagged content. Model version changes trigger review. Dashboards owned by a named team.
🚩 Red Flag No automated quality evaluation — quality assessed by "does it seem fine?" in manual testing. No cost anomaly detection. No security monitoring specific to AI behavior. Model provider silently updates model version; team notices degradation weeks later via user complaints.
