00start

The Migration Mental Model

Beginner

TL;DR — Terraform builds infrastructure. Ansible configures software on top of it. They hand off at the exact moment an EC2 instance becomes reachable over SSH. Confusion about this boundary is the single most common source of architectural debates on PF migration projects.

Before writing or reading a single line of Ansible, you need one mental model locked in: Terraform and Ansible have a precise, non-overlapping division of responsibility. When a migration engineer says "Terraform deploys PingFederate" — they are wrong. Terraform creates the server. Ansible installs PingFederate on it.

The Responsibility Boundary

Terraform vs Ansible — Full Responsibility Map for a PF Migration
PF ComponentTerraform OwnsAnsible Owns
EC2 InstanceCreates it, assigns SG, attaches IAM role, tags it PFRole=engineInstalls Java, extracts PF ZIP, sets OS limits, deploys config
Security GroupsCreates rules for ports 9031, 9999, 7600, 636Optionally validates firewalld alignment (on-prem migrations)
PF ConfigurationNothing — outside its concernRenders run.properties and tcp.xml from Jinja2 templates
TLS CertificatesMay provision ACM cert for the ALB endpointDeploys JKS keystores to the PF server filesystem
SecretsCreates Secrets Manager entries as empty shellsReads secrets at runtime, injects them into config and API calls
Load BalancerCreates ALB, target group, health check rulesValidates engine heartbeat before considering deployment done
Cluster FormationNetwork connectivity only — SGs allow 7600 between nodesConfigures JGroups tcp.xml, starts admin first then engines serially

The Handoff Point

  1. Terraform applies — EC2 instance created, tagged PFRole=engine, security group attached, IAM role bound, instance running.
  2. Terraform outputs the instance private IP, DNS, and instance ID to pipeline artifact or remote state.
  3. Ansible inventory discovers it — the aws_ec2 dynamic inventory plugin reads the PFRole=engine tag and creates the pf_engines group automatically.
  4. Ansible executes — the playbook runs against the discovered hosts, first verifying SSH connectivity, then running the role sequence.
🔐
PF Context — Diagnosing the Right Layer When something breaks in a PF migration, the first diagnostic question is always: which layer failed? If the EC2 instance is in the wrong subnet or port 9031 is blocked — that is Terraform. If run.properties has the wrong operational mode or the JVM heap is too small — that is Ansible. If the PF Admin API is returning 403 — that might be Ansible (wrong password) or application config. Knowing the boundary saves hours of debugging time.

Why Ansible Specifically?

Agentless

PingFederate servers need no pre-installed agent. Ansible uses SSH — the same protocol your team already uses. Nothing to install, maintain, or update separately on managed nodes.

Idempotent

Run the same playbook 10 times — the result is identical. If run.properties hasn't changed, Ansible skips it. If PF is already running, it stays running. Safe to re-run after partial failures.

Config as Code

Every PF configuration decision — JVM heap, cluster mode, cert paths, LDAP bind DN — lives in YAML files in Git. You can see exactly what changed between deployments with a simple git diff.

Environment Separation

The same PF install role runs in dev, staging, and prod. Only the variable values differ. No copy-paste, no environment-specific scripts — just one role, three inventory directories.

01arch

Ansible Architecture & Execution Model

Beginner

TL;DR — Ansible runs on your laptop or CI runner (control node) and SSHes into remote servers (managed nodes) to execute Python modules. No agents, no daemons, no persistent processes left on the server.

The Agentless Architecture

Ansible Execution Flow — From Control Node to PF Managed Nodes

The 7-Step Execution Sequence

  1. Inventory loading — Ansible reads the inventory, builds its internal map of hosts and groups, resolves all group/host variables. No SSH yet.
  2. Fact gathering — By default, Ansible SSHes into every target host and runs the setup module to collect facts (OS type, IP addresses, memory). Runs before any of your tasks.
  3. Play execution begins — For each play in the playbook (in order), Ansible identifies target hosts, checks serial strategy, then starts tasks.
  4. Task-by-task across all hosts — Each task runs on ALL matched hosts (up to forks count in parallel) before the next task starts. Not "all tasks on host 1, then all tasks on host 2."
  5. Module dispatch — For each task, Ansible serializes the module + arguments, SSHes to target, runs Python, receives JSON result with changed/ok/failed status.
  6. Handler queuing — If a task reports changed and has notify, the named handler is queued. It does NOT run immediately — it runs at end of play.
  7. Play exit and handler flush — After all tasks complete, queued handlers fire. If any host failed and any_errors_fatal: true, the entire play stops after the failing task.

The CLI Commands Every Migration Lead Uses

bashEssential Ansible CLI — Pre-Deployment Safety Commands
# ── Before every production deployment — run these 4 in order ────────────

# 1. Confirm which hosts would be targeted (no SSH, no changes)
ansible-playbook site.yml -i inventory/prod/hosts.yml --list-hosts

# 2. Confirm which tasks would run (no SSH, no changes)
ansible-playbook site.yml -i inventory/prod/hosts.yml --list-tasks

# 3. Dry run against staging — simulate changes, show diffs
ansible-playbook site.yml -i inventory/staging/hosts.yml --check --diff

# 4. Single host dry run on prod (safer first step)
ansible-playbook site.yml -i inventory/prod/hosts.yml \
  --check --diff --limit pf-engine01.corp.example.com

# ── Recovery after a partial failure ─────────────────────────────────────

# Re-run only on the host that failed
ansible-playbook site.yml --limit pf-engine02.corp.example.com

# Run only specific tagged tasks (e.g., only config files, skip Java install)
ansible-playbook site.yml --tags configure,verify --skip-tags java

# ── Connectivity and debugging ────────────────────────────────────────────

# Test SSH connectivity to all PF hosts before running a playbook
ansible -i inventory/prod/hosts.yml all -m ping

# Check PF service status on all engine nodes (ad-hoc command)
ansible pf_engines -i inventory/prod/hosts.yml \
  -m command -a "systemctl status pingfederate"

# Verbose: -v task output, -vv connection info, -vvv module calls
ansible-playbook site.yml -v   # start here when something fails
ansible-playbook site.yml -vvv # use for SSH/module issues
👷
Engineer's Corner — The Pre-Production Gate Question Ask your team: "What is the mandatory validation step before any production Ansible run?" A well-run project has --check --diff executed against staging as a required pipeline gate — a human must review and approve the diff output before the actual apply runs against production. If your team skips this, raise it as a risk. Every PF configuration change should produce a visible, reviewable diff before it touches a live cluster.
🎯Knowledge Check — Section 01
A task in your PF playbook deploys the run.properties template and reports CHANGED. The next task deploys tcp.xml and also reports CHANGED. When does the PingFederate service restart?
After ALL tasks in the play complete — not immediately after either template task. Both tasks notify the "restart pingfederate" handler, but Ansible deduplicates: even though two tasks notify the same handler, it fires exactly once, at the end of the play. If there are 8 more tasks after the template tasks, all 8 run against the OLD config before PF restarts with the new config.
You need to test a change to the PF tcp.xml template before production. Write the exact command sequence you would run.
Step 1: ansible-playbook site.yml --list-hosts — confirm you're targeting the right hosts.
Step 2: ansible-playbook site.yml --list-tasks --tags cluster — confirm which tasks will run.
Step 3: ansible-playbook site.yml -i inventory/staging --check --diff --tags cluster — dry run on staging, review the diff of tcp.xml.
Step 4 (optional): ansible -i inventory/staging pf-engine01 -m template -a "src=templates/tcp.xml.j2 dest=/tmp/tcp.xml.preview" — render to a temp file for detailed review.
Only after reviewing the diff do you run without --check on production.

YAML for IAM Engineers

Beginner

TL;DR — YAML is JSON with indentation instead of braces. Every PF config value, every task, every variable is YAML. Wrong indentation creates bugs that are silent and hard to spot.

As an IAM engineer, you know JSON from OAuth token responses and OIDC discovery documents. YAML is the same data model — maps, sequences, and scalars — but whitespace-delimited. The mental shift is small but the pitfalls are specific.

jsonJSON you know (OIDC token)
// OIDC token response
{
  "iss": "https://pf.example.com",
  "sub": "jsmith",
  "groups": [
    "Admins",
    "AppUsers"
  ],
  "active": true,
  "exp": 1735747200
}
yamlSame data as Ansible variables
# Equivalent in YAML — indentation = nesting
iss: "https://pf.example.com"
sub: "jsmith"
groups:        # array: dash prefix
  - Admins
  - AppUsers
active: true   # boolean — no quotes
exp: 1735747200
yamlAll YAML Constructs You Will See in PF Ansible Code
---   # document start marker — every Ansible YAML file begins with this

# ── SCALARS ──────────────────────────────────────────────────────────────
pf_version: "12.1.0"           # quoted string — safe default for values with special chars
pf_https_port: 9031             # integer — no quotes
pf_manage_firewall: true        # boolean — always true/false, not "true"/"false"
pf_admin_host: ""               # empty string — intentionally blank

# Multi-line string — pipe | preserves newlines (use for embedded scripts)
pf_startup_hook: |
  #!/bin/bash
  export JAVA_HOME=/usr/lib/jvm/java-17-openjdk
  cd /opt/pingfederate && ./bin/run.sh

# Folded string — > joins lines with spaces (use for long JVM arg strings)
pf_jvm_extra: >
  -Dfile.encoding=UTF-8
  -Djava.awt.headless=true
  -Dpf.operational.mode=CLUSTERED_ENGINE

# ── MAPS (nested key-value) ──────────────────────────────────────────────
pf_ldap_connection:
  host: pd-01.internal.example.com
  port: 636
  ssl: true
  credentials:
    bind_dn: cn=svc-pingfed,ou=SA,dc=example,dc=com
    password: "{{ vault_ldap_bind_password }}"   # Jinja2 variable reference

# ── SEQUENCES (lists) ────────────────────────────────────────────────────
pf_plugins:                      # list of strings
  - pf-pingid-adapter-3.2.jar
  - pf-kerberos-adapter-2.1.jar

pf_cluster_nodes:                # list of maps — most common in Ansible tasks
  - name: pf-admin01
    ip: "10.20.1.10"
    role: admin
  - name: pf-engine01
    ip: "10.20.1.11"
    role: engine

The 5 YAML Bugs That Will Catch You

yamlReal YAML Pitfalls from Enterprise PF Projects
# BUG 1: Tab character instead of spaces — YAML prohibits tabs entirely
# Visually identical to spaces but causes parse error:
pf_version: "12.1.0"
	pf_port: 9031   # ← tab here = yaml.scanner.ScannerError: found character '\\t'

# BUG 2: Indentation misalignment silently creates wrong structure
# INTENDED: pf_jvm is a nested map with xms and xmx
pf_jvm:
  xms: 2048m     # ✓ correct — child of pf_jvm
xmx: 2048m       # ✗ wrong — now a TOP-LEVEL key, sibling of pf_jvm!

# BUG 3: Unquoted file permissions — octal numbers parsed as decimal
pf_cert_mode: 0640    # YAML sees: OCTAL 0640 = decimal 416 — WRONG permissions!
pf_cert_mode: "0640"  # CORRECT — quote to preserve leading zero

# BUG 4: Unquoted boolean-like strings
pf_ssl_enabled: yes     # YAML parses as boolean true — may not be intended
pf_ssl_enabled: true    # EXPLICIT boolean — always use this

# BUG 5: Colon in a string value breaks YAML parsing
pf_base_url: https://pf.example.com:9031         # ← colon after https = PARSE ERROR
pf_base_url: "https://pf.example.com:9031"       # ← CORRECT: quote strings with colons
🔐
PF Reality — The File Permission Bug Caused a Security Incident Bug #3 is real. An enterprise PF deployment set the keystore file mode to 0640 without quotes. YAML parsed it as decimal 416, which the file module interpreted as invalid and defaulted to world-readable permissions. PingFederate started successfully — the signing keystore was readable by all OS users. Discovered during a routine security audit. Quote all file modes: "0640", "0750", "0755".
03inv

Inventory Deep Dive

Intermediate

TL;DR — The inventory is Ansible's source of truth for which servers exist and how they are organized. For PF it separates admin from engine nodes. In AWS it is generated dynamically from EC2 tags — no static IP list to maintain.

Static Inventory — On-Premises Pattern

yamlinventory/prod/hosts.yml — Full Annotated PF Inventory
---
# On-premises static inventory for PingFederate cluster
# CRITICAL: group names here MUST match group_vars/ directory names exactly

all:
  children:
    pf_admin:                        # maps to group_vars/pf_admin.yml
      hosts:
        pf-admin01.corp.example.com:
          ansible_host: 10.20.1.10   # use IP if DNS isn't reliable
          pf_node_role: admin         # host variable — used in templates
          pf_cluster_bind_address: 10.20.1.10

    pf_engines:                      # maps to group_vars/pf_engines.yml
      hosts:
        pf-engine01.corp.example.com:
          ansible_host: 10.20.1.11
          pf_node_role: engine
          pf_cluster_bind_address: 10.20.1.11
        pf-engine02.corp.example.com:
          ansible_host: 10.20.1.12
          pf_node_role: engine
          pf_cluster_bind_address: 10.20.1.12

    pf_all:                          # convenience group — both admin and engines
      children:
        pf_admin:
        pf_engines:

  vars:                              # applies to ALL hosts in this inventory
    ansible_user: ansible
    ansible_python_interpreter: /usr/bin/python3
    ansible_ssh_private_key_file: ~/.ssh/ansible_pf_key

AWS Dynamic Inventory

In AWS you don't maintain a static IP list. EC2 instances are identified by tags. The amazon.aws.aws_ec2 inventory plugin queries the AWS API and creates Ansible groups from tags automatically. When Terraform creates a new engine and tags it PFRole=engine, it appears in the pf_engines group on the next Ansible run — no inventory file edit required.

yamlinventory/aws/aws_ec2.yml — Dynamic Inventory for PF on AWS
---
# AWS EC2 dynamic inventory plugin
# Usage: ansible-playbook site.yml -i inventory/aws/aws_ec2.yml
# Requires: boto3, botocore, amazon.aws collection installed

plugin: amazon.aws.aws_ec2
regions:
  - us-east-1

filters:
  instance-state-name: running
  tag:Project: PingFederate
  tag:Environment: prod          # change to staging/dev as needed

# Creates pf_admin group (from tag PFRole=admin)
# Creates pf_engines group (from tag PFRole=engine)
keyed_groups:
  - key: tags.PFRole
    prefix: pf
    separator: "_"

hostnames:
  - private-dns-name              # use private DNS within VPC

compose:
  ansible_host: private_ip_address
  pf_cluster_bind_address: private_ip_address
  pf_node_role: tags.PFRole      # "admin" or "engine"
  pf_az: placement.availability_zone

# Required EC2 tags to set (via Terraform):
#   Project=PingFederate   Environment=prod
#   PFRole=admin           (on the admin instance)
#   PFRole=engine          (on each engine instance)

Inventory Group Variable Flow

How Variables Cascade from Groups to Hosts
🪤
Gotcha — Group Name Must Match group_vars Directory Name Exactly If your inventory has a group called pf_engines but the file is at group_vars/pf_engine.yml (missing the 's'), Ansible silently ignores that file. No error. No warning. Variables simply don't load. This is one of the most common silent bugs in enterprise Ansible projects. Always verify group names match their group_vars directory names character-for-character.
04vars

Variables & Precedence

Intermediate

TL;DR — Ansible has 22 variable precedence levels. Higher sources override lower ones. The most common PF bug is a variable set in multiple places with the wrong one winning silently.

When Ansible encounters a variable name, it checks every possible source and uses the one with the highest precedence. Understanding this tower is what separates engineers who confidently modify PF automation from those who break production accidentally.

The Precedence Tower — Lowest to Highest

1role defaults — roles/pingfederate/defaults/main.ymlSafe baselines — designed to be overridden
2inventory file group vars (inline)Vars defined inline in hosts.yml
3inventory group_vars/allShared across all environments
4inventory group_vars/[groupname]e.g. group_vars/pf_engines.yml
5inventory host_vars/[hostname]Single host overrides
6playbook group_vars/allPlaybook-adjacent all vars
7playbook group_vars/[groupname]Playbook-adjacent group vars
8playbook host_vars/[hostname]Playbook-adjacent host vars
9host facts and cached set_factsGathered by setup module
10play vars: section in playbookInline vars in play definition
11play vars_promptInteractive input at runtime
12play vars_filesLoaded via vars_files: in play
13role vars — roles/pingfederate/vars/main.ymlInternal constants — hard to override
14block varsScoped to a block of tasks
15task vars — vars: on a single taskSingle-task scope only
16include_varsDynamically loaded var files
17set_facts and registered varsComputed during playbook run
18role and include_role paramsPassed at role invocation
19include_tasks paramsPassed to included task files
20extra vars — -e on command lineALWAYS wins. Cannot be overridden.
⚠
The 3 Levels That Matter for PF Projects In practice 95% of PF variable decisions happen at just three levels: (1) role defaults — safe baselines the role author provides; (2) group_vars — environment and group-specific values your team controls; (3) -e extra_vars — emergency overrides that always win. Internalize: defaults < group_vars < extra_vars. Everything else is edge cases.

vars vs defaults — The Most Confused Distinction

yamldefaults/main.yml vs vars/main.yml — When to Use Each
## roles/pingfederate/defaults/main.yml
## USE FOR: values operators SHOULD tune per environment
## Precedence level 1 — everything can override this
pf_https_port: 9031
pf_jvm_xmx: "2048m"           # staging uses 2GB, prod uses 8GB
pf_manage_firewall: true       # AWS environments set false (use SGs instead)
pf_operational_mode: STANDALONE # overridden per group

---
## roles/pingfederate/vars/main.yml
## USE FOR: internal architectural constants operators should NOT change
## Precedence level 13 — group_vars CANNOT override this
pf_required_java_version: "17"   # PF 12.x requires Java 17, not negotiable
pf_startup_jar: "bin/pf-startup.jar"
pf_run_script: "bin/run.sh"

# REAL BUG seen in enterprise projects:
# Engineer puts pf_jvm_xmx in vars/main.yml instead of defaults/main.yml
# Then group_vars/pf_engines.yml sets pf_jvm_xmx: "8192m"
# Result: group_vars silently loses — engines get 2048m not 8192m
# No error, no warning. Production runs out of memory under load.

Variable Shadowing — The Silent Production Bug

🪤
Gotcha — Variable Shadowing Between group_vars and host_vars A host_var silently overrides a group_var with the same name. If group_vars/pf_engines.yml sets pf_jvm_xmx: "4096m" but host_vars/pf-engine02.yml sets pf_jvm_xmx: "2048m", engine02 runs with 2GB heap while engine01 runs with 4GB — silently, with zero warning. This causes incidents where one node in a PF cluster behaves differently from the others and nobody knows why for hours.
bashDebug Variable Shadowing — Find the Winning Value for Any Host
# Most useful debugging command — shows what value Ansible will actually use
# for a specific variable on a specific host, without running the playbook
ansible -i inventory/prod/hosts.yml   pf-engine02.corp.example.com   -m debug -a "var=pf_jvm_xmx"
# Output:
# pf-engine02.corp.example.com | SUCCESS => {
#     "pf_jvm_xmx": "2048m"
# }

# Show ALL variables for a host (pipe to grep to filter)
ansible -i inventory/prod/hosts.yml pf-engine02   -m debug -a "var=hostvars[inventory_hostname]" | grep pf_jvm

# Add this temporarily to a playbook to debug variable values mid-run
# - name: DEBUG - show pf_jvm_xmx for this host
#   ansible.builtin.debug:
#     msg: "pf_jvm_xmx = {{ pf_jvm_xmx }} on {{ inventory_hostname }}"
🎯Knowledge Check — Variables
Your team runs the playbook with -e pf_operational_mode=STANDALONE. The group_vars/pf_engines.yml sets pf_operational_mode: CLUSTERED_ENGINE. Which value wins, and why is this dangerous for a PF cluster?
STANDALONE wins — extra_vars (-e) is precedence level 20 and always beats group_vars (level 4). This is extremely dangerous: STANDALONE mode means each PF engine thinks it is the only node. You get N independent PF instances behind a load balancer instead of a coherent cluster. SSO sessions are not shared between nodes — users get randomly logged out depending on which engine the load balancer routes them to. This exact scenario has caused production incidents on PF migration projects.
05facts

Facts & Fact Gathering

Intermediate

TL;DR — Facts are auto-discovered variables about the target host: OS type, IP addresses, memory, hostname. PF templates use them to generate host-specific config. In large AWS fleets, caching facts saves minutes per run.

Before your tasks run, Ansible SSHes into every target host and executes the setup module, which returns hundreds of variables about that host. These facts are then available in every subsequent task and Jinja2 template on that host for the rest of the playbook run.

Which Facts PF Playbooks Actually Use

yamlPingFederate-Relevant Ansible Facts — Where Each Is Used
# These are automatically available in every PF task and template

ansible_fqdn: "pf-engine01.corp.example.com"
# Used in: run.properties.j2 → pf.host.name={{ ansible_fqdn }}

ansible_default_ipv4:
  address: "10.20.1.11"
# Used in: tcp.xml.j2 → bind_addr="{{ ansible_default_ipv4.address }}"
# Also used as fallback for pf_cluster_bind_address if not set in inventory

ansible_hostname: "pf-engine01"
# Short hostname without domain — used in log file naming

ansible_os_family: "RedHat"
ansible_distribution: "Amazon"
# Used in: java role → when: ansible_os_family == "RedHat" → install corretto
#           common role → when: ansible_os_family == "Debian" → use apt

ansible_memtotal_mb: 16384
# Used to dynamically calculate JVM heap:
# pf_jvm_xmx: "{{ (ansible_memtotal_mb * 0.5) | int }}m"
# On a 16GB host this renders as 8192m

ansible_processor_vcpus: 4
# Used to set thread pool size:
# pf_runtime_threads_max: "{{ ansible_processor_vcpus * 50 }}"

ansible_date_time:
  iso8601: "2025-01-01T10:00:00Z"
# Used in backup tasks and log correlation

Fact Caching for Large AWS Fleets

With 20+ EC2 instances, fact gathering adds 2-4 minutes to every playbook run — Ansible SSHes into each host and waits for the setup module. Fact caching stores the results and reuses them on subsequent runs within the cache TTL.

iniansible.cfg — Configure Fact Caching
[defaults]
# smart: only gather facts if not cached (saves time on repeat runs)
gathering             = smart
fact_caching          = jsonfile
fact_caching_connection = /tmp/ansible_facts_cache
fact_caching_timeout  = 3600   # seconds — 1 hour

# Disable fact gathering entirely for plays that don't need facts
# (saves 30-60 seconds for verification-only plays)
# In the play definition:
# - name: Verify PF heartbeat
#   hosts: pf_engines
#   gather_facts: false   <-- add this when no facts are needed
💡
When to Disable Fact Gathering The verification play that only hits the PF heartbeat endpoint does not need any facts — disable gathering to save time. The configuration play that renders run.properties.j2 absolutely needs ansible_fqdn and ansible_memtotal_mb — leave gathering enabled. Rule: if your tasks or templates reference any ansible_* variable, you need facts. Otherwise, consider disabling.
LAB 1 Trace Variables — Which Value Will Be Used?
Scenario

You are reviewing a PF Ansible project before a production deployment. You need to determine what JVM heap value will actually be used on pf-engine02. Given the four sources below, what is pf_jvm_xmx on that host?

Four Variable Sources
yamlroles/pingfederate/defaults/main.yml
pf_jvm_xmx: "1024m"
yamlgroup_vars/pf_engines.yml
pf_jvm_xmx: "4096m"
yamlhost_vars/pf-engine02.yml
pf_jvm_xmx: "2048m"
bashCommand used to run the playbook
ansible-playbook site.yml -e "pf_jvm_xmx=8192m"
Expected Answer
Answer: 8192m Reason: -e extra_vars (precedence level 20) always wins over everything. Evaluation order for pf-engine02: defaults/main.yml → 1024m (level 1 — lowest) group_vars/pf_engines → 4096m (level 4 — overrides defaults) host_vars/pf-engine02 → 2048m (level 5 — overrides group_vars) -e command line → 8192m (level 20 — overrides everything) Winner: 8192m from the -e flag.
Verification Command
bash
ansible -i inventory/prod/hosts.yml pf-engine02 \
  -m debug -a "var=pf_jvm_xmx" \
  -e "pf_jvm_xmx=8192m"
Common mistake: Choosing 2048m (host_vars). host_vars DO override group_vars — but NOT extra_vars. Without the -e flag, host_vars would win with 2048m. The -e flag changes everything.
06plays

Playbooks & Tasks

Intermediate

TL;DR — A playbook is an ordered list of plays targeting host groups. Tasks are the individual work units. The critical PF patterns are: block/rescue for error handling, wait_for for service startup, delegate_to for cross-node Admin API calls, and run_once for cluster-wide operations.

Annotated PF Playbook

yamlsite.yml — Fully Annotated PingFederate Cluster Playbook
---
# site.yml — Full cluster deployment
# Run: ansible-playbook site.yml -i inventory/prod/hosts.yml --ask-vault-pass

# ── PLAY 1: Admin node first ─────────────────────────────────────────────
- name: Deploy PingFederate Admin Node
  hosts: pf_admin         # only the pf_admin group
  gather_facts: true     # collect OS facts before tasks
  become: true            # use sudo for all tasks
  serial: 1              # one host at a time (only 1 admin anyway)

no_log Audit — Verify Secrets Are Never Logged

🔴
Security Risk — Secrets in Ansible Logs By default Ansible logs the full arguments and output of every task. If a task uses a password variable without no_log: true, that password appears in terminal output, log files, and CI/CD pipeline artifacts. The most commonly leaked PF secrets: LDAP bind passwords in PCV config tasks, PF admin password in Admin API calls, and keystore passwords in cert deployment tasks. Every task touching a secret must have no_log: true.

  grep -v "no_log"

# Find tasks using password/secret keywords without no_log
grep -rn "password\|secret\|keystore\|token" \
  roles/*/tasks/ --include="*.yml" | \
  grep -v "no_log: true"

TL;DR — Collections are namespaced packages of modules. Every module name with a dot (amazon.aws.s3_object) comes from a collection. PF projects use three: amazon.aws, community.general, and ansible.posix.

Before Ansible 2.10 all modules shipped with Ansible itself. Collections split them into separately versioned packages. You need to know which collection provides which module to understand a project's requirements.yml and troubleshoot "module not found" errors.

Reading an Enterprise PF Repository

Advanced

TL;DR — When handed an unfamiliar Ansible PF repo, follow a consistent 7-step entry-point trace methodology. This section applies everything from sections 01-11 in one systematic walkthrough.

You will regularly be handed an Ansible repository you have never seen and asked to understand it quickly — for a design review, a deployment approval, or a production incident. The following methodology works every time.

The 7-Step Trace Methodology

  1. Start at ansible.cfg — Find the default inventory path, remote_user, SSH key, and roles_path. This tells you where everything lives before you look at anything else.
  2. Read the entry-point playbook (site.yml) — Identify the plays, their target host groups, serial strategy, any_errors_fatal setting, and which roles each play applies. This is your complete execution map.
  3. Check meta/main.yml for every role — Role dependencies run before the role itself. Missing this step means you will misread the execution order entirely.
  4. Trace variables top-down for any variable of interest — Check: role defaults → group_vars/all → group_vars/[group] → host_vars → extra_vars. The last definition wins.
  5. Read tasks/main.yml in each role — It is usually a list of include_tasks or import_tasks calls. Follow each include. Pay attention to when: conditions — some tasks only run for specific OS families or node roles.
  6. For each template: reference follow the variables it uses — Find the .j2 file in templates/. For every {{ variable }} in the template, trace back to step 4. This tells you what the rendered file will actually contain.
  7. Identify all handlers — Check handlers/main.yml. Find which tasks notify each handler using grep. Understand what configuration changes trigger a PF service restart.

LAB 5 Determine Execution Order for a 3-Role Playbook
Scenario

A playbook applies only the pingfederate role. That role's meta/main.yml declares dependencies on java and common. The java role also declares a dependency on common. What is the actual task execution order?

Expected Answer
Actual execution order: 1. common role (dependency of both java and pingfederate — runs ONCE) 2. java role (dependency of pingfederate) 3. pingfederate (the role listed in the playbook) Key insight: Ansible deduplicates role dependencies. Even though common appears in both java's and pingfederate's meta/main.yml, it runs exactly once — not twice. This is the execution order even though the playbook only lists: roles: - pingfederate Without reading meta/main.yml you would assume only pingfederate tasks run. This is the single most important reason why Step 3 of the trace methodology (check meta/main.yml) is non-negotiable. Skipping it means you misread the execution order of every playbook in the project.

Scenario: Your CI/CD pipeline runs Terraform first, which creates a new EC2 engine instance tagged PFRole=engine. Immediately after Terraform completes, the pipeline runs ansible-playbook site.yml -i inventory/aws/aws_ec2.yml. The playbook fails with:

"pf-engine03: UNREACHABLE — SSH connection refused (port 22)"

Using only what you learned in Part 1, identify two likely causes and name one Ansible mechanism that should have prevented this. The complete architectural fix is in Part 2, Section 13.
Two likely causes:
1. The EC2 instance is not yet fully booted — Terraform marks it "running" when the hypervisor reports ready, not when the OS has finished initialising SSH. The gap is typically 30-90 seconds.
2. The security group rule allowing port 22 from the control node may not have propagated yet, or the instance has not yet received its private IP routing via the VPC.

The Ansible mechanism that should prevent this:
wait_for_connection as the very first task in the play. It retries SSH with configurable timeout and delay until the connection succeeds before any other task runs.

Why this is not enough on its own — see Part 2:
Even with wait_for_connection there is a deeper architectural question: should Ansible know to wait, or should Terraform guarantee the server is SSH-ready before handing off? Part 2 covers three different handoff patterns and when to use each one.
