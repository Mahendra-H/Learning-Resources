Ecosystem Overview

Ping Identity (acquired by ForgeRock and now part of Thales Group) provides an enterprise IAM platform centered on two flagship products: PingFederate (federation and protocol gateway) and PingDirectory (high-performance LDAP identity store). Together they form the backbone of most large enterprise SSO, federation, and identity management architectures.

Ping Identity Product Ecosystem — Relationship Map
PingFederate

Federation Gateway

Handles all protocol-level federation. Issues SAML assertions, OAuth tokens, and OIDC ID tokens. Acts as both Identity Provider (IdP) and Service Provider (SP). Manages trust relationships and authentication policies.

PingDirectory

Identity Data Store

High-performance, enterprise-grade LDAP server purpose-built for identity. Stores user profiles, credentials, groups, and attributes. Provides replication, entry balancing, and REST APIs. Also offered as PingDataStore (read-only proxy).

PingAccess

Web Access Management

Policy enforcement point protecting web apps and APIs. Works downstream of PingFederate, validating tokens and enforcing fine-grained access control without requiring app-level integration.

PingOne

Cloud IAM Platform

SaaS-based identity platform offering MFA, risk scoring, DaVinci orchestration, and cloud directory. Can federate with on-premises PingFederate for hybrid deployments — key target for cloud migration projects.

PingFederate Architecture & Core Components

PingFederate is a standards-based federation server that acts as both an Identity Provider (IdP) and Service Provider (SP). Its architecture separates administration from runtime, enabling zero-downtime deployments and horizontal scaling of protocol processing.

Dual-Plane Architecture: Admin vs Engine

PingFederate Internal Architecture — Admin & Engine Separation
ℹ
Admin/Engine Separation is Critical The Admin node is NEVER placed behind a load balancer and should NEVER receive end-user traffic. Only Engine nodes handle live authentication. This separation allows you to take the Admin node offline for upgrades without impacting runtime SSO services.

PingDirectory Architecture & Core Components

PingDirectory is a high-throughput, low-latency LDAP directory server purpose-built for identity use cases. Unlike general-purpose LDAP servers (OpenLDAP, AD), PingDirectory is optimized for millions of entries, high concurrency, and real-time identity operations with consistent sub-millisecond response times.

Architecture Overview

PingDirectory Internal Architecture

Directory Information Tree (DIT) Structure

# Typical PingDirectory DIT structure dc=example,dc=com # Root suffix ├── ou=People # User accounts │ ├── uid=jsmith,ou=People,... # Individual user entry │ └── uid=bwilson,ou=People,... ├── ou=Groups # LDAP groups │ ├── cn=AppAdmins,ou=Groups,... │ └── cn=AppUsers,ou=Groups,... ├── ou=ServiceAccounts # Bind accounts for applications └── ou=Tokens # Persisted OAuth tokens (optional) # Key objectClasses for user entries objectClass: inetOrgPerson # Standard: cn, sn, uid, mail, telephoneNumber objectClass: organizationalPerson objectClass: person objectClass: top # Ping-specific extensions objectClass: pingUser # pingIdentityMFAEnabled, pingOTPSecret, etc. objectClass: ds-pwp-password-policy-user # Password policy binding

Topology Components

PingDirectory (Server)

Primary LDAP/REST identity store. Multi-master replication topology. Stores user profiles, credentials, and group memberships. Supports entry balancing for horizontal data partitioning.

PingDataProxy / PingDirectoryProxy

Load-balancing proxy in front of PingDirectory instances. Routes LDAP requests, provides failover, and handles entry balancing across distributed backend servers without client awareness.

PingDataSync

Bidirectional synchronization engine. Syncs identity data between PingDirectory and external systems (Active Directory, databases, cloud directories). Real-time or scheduled sync.

PingDataMetrics

Metrics aggregation server. Collects performance and operational data from all PingDirectory and PingDataProxy instances. Feeds dashboards and alerting systems.

PingDataConsole

Web-based administration UI for PingDirectory. Browse and edit directory entries, manage schemas, configure backends, and monitor replication topology. Replaces the older dsconfig TUI.

dsconfig (CLI)

Primary command-line configuration tool. Interactive or script-friendly. All PingDirectory configuration changes (backends, indexes, password policies, replication) are made via dsconfig or its REST equivalent.

Password Policy Architecture

PingDirectory implements a fine-grained password policy model. Each user entry can be assigned a specific password policy, or policies cascade from the global default. Key capabilities include:

  • Per-entry policy binding — users can have different expiry, lockout, and complexity rules
  • Password history — prevents reuse of previous N passwords (stored as hashed values)
  • Account lockout — configurable thresholds per policy; supports manual unlock via dsconfig or admin API
  • Password encoding — supports PBKDF2, BCrypt, SHA-512, and legacy MD5/SHA-1 schemes for migration compatibility
  • Forced change on reset — ds-pwp-must-change-password operational attribute triggers re-auth flow in PingFederate
  • Idle account disabling — automatic disabling of accounts inactive for N days

PingFederate ↔ PingDirectory Integration

PingFederate and PingDirectory work together through several integration points. PingFederate connects to PingDirectory primarily as a data store for authentication (credential validation) and as an attribute source for enriching tokens and assertions with user profile data.

PingFederate to PingDirectory Integration Points

PingFederate LDAP Data Store Configuration

# PingFederate LDAP Data Store — key parameters (Admin UI / Admin API) Type: LDAP Host: pingdir01.internal.example.com Port: 636 # Use LDAPS always in production SSL: true BindDN: cn=pingfed-svc,ou=ServiceAccounts,dc=example,dc=com BindPassword: [vault-injected or encrypted in pf.jwk keystore] BaseDN: dc=example,dc=com UserBaseDN: ou=People,dc=example,dc=com # Password Credential Validator — LDAP PCV config SearchFilter: uid=${username} # or sAMAccountName for AD BindMethod: bindAsUser # performs actual LDAP bind for auth SearchBase: ou=People,dc=example,dc=com # Attribute Contract — mapping PD attributes to SAML/JWT claims mail → email cn → name givenName → given_name sn → family_name memberOf → groups employeeNumber → employee_id

Reference Token Storage in PingDirectory

When PingFederate uses reference tokens (opaque tokens rather than JWT), the token data must be persisted somewhere. PingDirectory can serve as this store:

  • A dedicated backend (e.g., ou=Tokens,dc=example,dc=com) stores token records as LDAP entries
  • Each token entry has TTL-based expiry enforced by PingDirectory's Entry TTL control
  • Token introspection (/as/introspect) by PingFederate performs an LDAP lookup to validate the token
  • This approach allows token data to be replicated across PF engine nodes via PingDirectory's built-in replication
  • Alternative: In clustered PF environments, JWT tokens eliminate backend storage dependency but require careful key management
✦
Best Practice for AWS Migrations When migrating to AWS, prefer JWT access tokens over reference tokens where possible. JWT tokens are self-contained and eliminate the LDAP round-trip for introspection, reducing latency and simplifying the architecture. Reserve reference tokens for scenarios requiring immediate revocation (e.g., high-security applications).

Clustering, Replication & High Availability

PingFederate Cluster Architecture

PingFederate uses a console/engine cluster model. There is exactly one active Admin (Console) node at any time, and N Engine nodes that handle live traffic. Engine nodes are stateless and pull configuration from the Admin node.

PingFederate HA Cluster Topology

PingFederate Cluster Modes

run.properties SettingModeUse Case
STANDALONESingle node — Admin + Engine combinedDev/test only. Never production.
CLUSTERED_CONSOLEAdmin node in a clusterThe single Admin node. Manages configuration.
CLUSTERED_ENGINEEngine node in a clusterAll runtime nodes. Placed behind load balancer.

Session Affinity Considerations

⚠
Sticky Sessions vs. Shared State PingFederate engine nodes share session state via JGroups-based in-memory clustering. However, session stickiness is still recommended on the load balancer for in-flight authentication flows (the browser-based redirect dance). Post-authentication (after the SSO cookie is set), any engine node can serve requests. Configure load balancer cookie-based affinity during SSO flows, with fallback to round-robin for token endpoint calls.

PingDirectory Replication Topology

PingDirectory uses a multi-master replication model. All replica servers can accept writes simultaneously. Conflict resolution uses Change Sequence Numbers (CSNs) — the most recent write wins.

Replication Topology Options

  • Full mesh — each server replicates directly to all others (recommended for ≤4 nodes)
  • Star/hub-and-spoke — all nodes replicate through a central hub (reduces connections but creates a single point of congestion)
  • Hierarchical — tiered replication for large geographically distributed topologies

Use manage-topology CLI to initialize and view replication status.

Entry Balancing (Sharding)

For very large directories (50M+ entries), PingDirectory supports entry balancing — distributing user entries across backend servers by a balancing attribute (e.g., uid hash). PingDirectoryProxy routes requests to the appropriate backend transparently. This enables horizontal data scaling without denormalizing the DIT.

HA Checklist

PingFederate HA

  • Minimum 2 Engine nodes across 2+ AZs
  • Admin node in a separate AZ from engines
  • Load balancer health check: GET /pf/heartbeat.ping
  • JGroups TCP multicast or unicast configured for engine discovery
  • Shared NFS or object storage for cluster-wide files (optional)
  • Admin node NOT in LB target group
  • SSL offload at LB or end-to-end TLS to engine (prefer end-to-end)

PingDirectory HA

  • Minimum 2 instances for HA; 3+ for write quorum
  • Deploy across multiple AZs
  • Replication monitoring: check cn=monitor for replication lag
  • Load balancer health check: LDAP search on cn=monitor
  • Use PingDirectoryProxy for transparent failover and load balancing
  • Backup: backup tool to S3 via LDAP backend export
  • Replication initialization from a clean backup before adding new replicas

SAML 2.0 Authentication Flows

SAML 2.0 is the primary federation protocol for enterprise SSO. PingFederate supports all standard SAML 2.0 bindings and profiles. Understanding these flows is essential for debugging, migration planning, and configuring trust relationships.

SP-Initiated SSO (Most Common)

The Service Provider (application) redirects the user to PingFederate (IdP) when an unauthenticated user attempts to access a protected resource.

SAML 2.0 SP-Initiated SSO — HTTP POST Binding

IdP-Initiated SSO

The user accesses PingFederate directly (e.g., via a portal or SSO launcher) and is pushed to the SP without a prior AuthnRequest. The flow starts at Step 3 above, skipping Steps 1–2. PingFederate generates the assertion without an inbound request, using a preconfigured default SP target URL.

⚠
IdP-Initiated SSO Security Risk IdP-initiated flows are susceptible to CSRF attacks because there is no AuthnRequest to correlate. Many security standards (NIST 800-63, FAPI) discourage IdP-initiated SAML. If required, use PingFederate's built-in allowIdpInitiated flag and enable RelayState validation. For OAuth/OIDC, avoid IdP-initiated flows entirely.

On-Premises Deployment Patterns

Typical Enterprise On-Prem Reference Architecture

Enterprise On-Premises Deployment — Network Zones

Installation Prerequisites & Steps

PingFederate Prerequisites

  • Java 11 or 17 (OpenJDK or Oracle JDK) — check PF version compatibility matrix
  • Minimum 8 GB RAM per engine node (16 GB recommended for production)
  • 4+ vCPUs per engine node
  • Valid license file (pingfederate.lic)
  • FQDN with valid TLS certificate
  • Outbound LDAP access to PingDirectory (:636)
  • Port 7600 open between engine nodes (JGroups TCP)
  • NTP synchronized across all nodes

PingDirectory Prerequisites

  • Java 11 or 17 (bundled JDK available with PD download)
  • Minimum 16 GB RAM (32+ GB for large directories)
  • Fast NVMe/SSD storage — PD is I/O intensive (Berkeley DB JE)
  • Separate volume for data directory
  • Port 389/636 (LDAP/LDAPS), 8989 (replication), 4444 (admin)
  • Valid license file
  • Low-latency network between replicas (<1ms recommended)

PingFederate Installation Steps

  1. Download & Extract — Obtain PingFederate ZIP from Ping Identity portal. Extract to /opt/pingfederate. Copy license to $PF_HOME/server/default/conf/.
  2. Configure run.properties — Set pf.operational.mode, ports, host name, and cluster bind address. For clustered installs, set mode to CLUSTERED_CONSOLE (admin) or CLUSTERED_ENGINE (engines).
  3. Configure tcp.xml — Set JGroups TCP initial membership list for engine nodes to discover each other (use unicast TCP_PING, avoid UDP MPING in cloud/virtual environments).
  4. Initialize Admin Node — Start PingFederate on admin node: $PF_HOME/bin/run.sh. Access console at https://[host]:9999/pingfederate/app. Complete initial setup wizard (admin credentials, base URL, org name).
  5. Configure Data Stores — Add PingDirectory LDAP data store via Admin Console. Test connectivity. Configure service account bind credentials.
  6. Configure Authentication — Create Password Credential Validator, HTML Form Adapter, Authentication Policy, and connect to PD data store.
  7. Configure SP/IdP Connections — Import SP metadata or manually configure trust. Define attribute contracts and mappings.
  8. Start Engine Nodes — After admin is running, start engine nodes. They will discover admin via JGroups and pull config. Verify cluster membership in Admin Console > System > Server > Cluster Management.
  9. Configure Load Balancer — Add engine nodes to LB target group. Health check: GET /pf/heartbeat.ping → HTTP 200. Enable sticky sessions for auth flows.
  10. Verify & Test — Test SP-initiated SSO, admin API access, log output, and heartbeat endpoint.

AWS Deployment Architecture

Deploying PingFederate and PingDirectory on AWS requires translating the on-premises network zone model to AWS constructs: VPCs, subnets, security groups, load balancers, and managed services. The core architecture principles remain the same, but the implementation uses cloud-native building blocks.

AWS Reference Architecture

PingFederate + PingDirectory — AWS Multi-AZ Reference Architecture

Key AWS Architectural Decisions

EC2 Instance Sizing

PF Engine: m5.xlarge (4 vCPU, 16 GB) minimum; m5.2xlarge for heavy load. PF Admin: m5.large sufficient. PingDirectory: r5.xlarge or r5.2xlarge (memory-optimized) — PD benefits greatly from large heap and page cache.

Storage for PingDirectory

Use EBS io2 volumes for PingDirectory data (/pingdir/data). Provision 3000+ IOPS. Separate volume for logs. Enable EBS encryption. Consider instance store NVMe for maximum throughput at the cost of no persistence (must restore from backup on restart).

Load Balancer Configuration

Use ALB for PingFederate (HTTP/HTTPS, layer 7). Use NLB for PingDirectory/PingDataProxy (TCP/TLS, layer 4 — LDAP requires connection persistence). Configure ALB with sticky sessions (duration-based) for PF auth flows.

JGroups in AWS

Disable UDP multicast (not supported in VPC). Use TCP_PING or S3_PING for JGroups cluster discovery. S3_PING is recommended — engine nodes write their IP to an S3 bucket and discover peers via S3 list operations. No need to hardcode IPs.

Secrets Management

Store LDAP bind credentials, TLS keystores, and PingFederate encryption keys in AWS Secrets Manager. Use IAM roles and instance profiles — never hardcode credentials. Integrate with Vault if your org uses it.

Autoscaling

PingFederate Engine nodes are stateless (config pulled from admin) and can be in an Auto Scaling Group. PingDirectory nodes should NOT be auto-scaled without careful replication initialization procedures — treat them like stateful databases.

Container/ECS/EKS Deployment Option

Ping Identity provides official Docker images for both PingFederate and PingDirectory, managed through the Ping Identity DevOps program (docker.io/pingidentity). For Kubernetes/EKS deployments:

  • Use StatefulSets for PingDirectory (stable network identity, persistent volumes per pod)
  • Use Deployments for PingFederate Engine nodes (stateless, horizontally scalable)
  • Use Ping Identity Helm charts (available on GitHub: pingidentity/helm-charts) for full-stack deployment
  • Mount configuration via ConfigMaps and Secrets; inject via server profiles from S3/GitHub
  • PingFederate supports Server Profiles — a layered configuration system that separates base config, environment config, and application-specific settings, ideal for GitOps

Security Best Practices

Certificate Management

Certificate management is one of the most operationally critical aspects of PingFederate. Expired signing certificates break all SSO flows instantly. Key practices:

  • Use separate certificates for signing (SAML assertions, JWT), SSL/TLS (engine HTTPS), and encryption. Never share keys.
  • Rotate well before expiry — PingFederate supports dual-key configurations (primary + secondary signing cert). Distribute the new cert to all SPs as secondary, wait for propagation, then promote to primary and remove old cert.
  • Monitor cert expiry — PingFederate Admin API exposes cert expiry dates. Build alerting on 90/60/30-day horizons.
  • In AWS: Use AWS Certificate Manager (ACM) for ALB TLS termination. Use KMS for PingFederate JWT signing key material where HSM-grade protection is required.
# Admin API: List all certificates and their expiry dates GET https://pf-admin:9999/pf-admin-api/v1/certificates/signing Authorization: Basic [admin credentials] # Response: check expirationDate for each cert # Set up automated monitoring: alert if expirationDate < now + 60 days # Programmatic cert rotation via Admin API POST /pf-admin-api/v1/certificates/signing/generate POST /pf-admin-api/v1/certificates/signing/{id}/setActive # promote new cert

PingFederate Hardening Checklist

Network & Access

  • Admin port :9999 — accessible ONLY from internal network (VPN, SSM, or bastion). Strict SG rules.
  • Engine port :9031 — accessible from ALB only. No direct internet access.
  • Disable HTTP (non-TLS) on all engine listeners.
  • Restrict JGroups cluster port :7600 to engine SG only.
  • Use WAF rules on ALB to block malformed SAML/OAuth requests.

Authentication & Cryptography

  • Enable MFA for PingFederate Admin Console access.
  • Rotate PingFederate admin account password per policy.
  • Use RSA-2048 or EC-256/384 for signing certs (avoid SHA-1).
  • Enable assertion encryption for SAML assertions containing PII.
  • Require PKCE for all public OAuth clients.
  • Disable ROPC grant type unless absolutely required.

PingDirectory Security

Access Control

  • Use dedicated, least-privilege service accounts for each application (PingFederate PCV, PingDataSync, app bind accounts).
  • Service accounts should have READ-ONLY access to user entries; write only if provisioning is required.
  • Never use cn=Directory Manager (root) in application configuration.
  • Configure per-attribute ACIs to restrict visibility of sensitive attributes (passwords, SSNs).

Transport & Encryption

  • Always use LDAPS (:636) between PingFederate and PingDirectory — never plain LDAP (:389) in production.
  • Enable replication encryption between PD nodes.
  • Use PD's native encryption-at-rest for backend data files (ds-cfg-encryption-settings-cipher-stream-provider).
  • Rotate directory encryption keys per policy using dsconfig.

Common Operational Tasks

  1. Rolling upgrade of PF engines — Remove one engine from LB target group, upgrade, validate health check, add back. Repeat for each engine. Admin node is upgraded last (or separately with downtime window).
  2. Adding a new SP connection — Import SP metadata in Admin Console, configure attribute contract, test with SP-initiated SSO, push config to engines (automatic or manual replication trigger).
  3. Certificate rotation for SAML signing — Generate new cert in PF Admin Console, add as secondary signing cert to all SP connections (update metadata shared with SPs), wait 24–48h, promote new cert to primary, remove old cert.
  4. PingDirectory password reset — ldappasswdmodify -D "cn=Directory Manager" -w [pw] -t "uid=jsmith,ou=People,dc=example,dc=com" -n "newpassword"
  5. Force PF config replication to engines — Admin Console > System > Server > Cluster Management > Replicate Configuration, or via Admin API: POST /pf-admin-api/v1/cluster/replicate
  6. Viewing active sessions — Admin Console > System > OAuth > Token Management for OAuth tokens. For SAML sessions, check server-side session logs or use the Session Revocation API.
  7. Backup PingDirectory — backup --backupDirectory /opt/backup/pd-$(date +%Y%m%d) --backendID userRoot. Copy backup to S3 via Lambda or cron.

Migration Project Guide: On-Prem to AWS

This section synthesizes the previous architecture knowledge into actionable guidance for leading a PingFederate on-premises to AWS migration project.

Discovery & Inventory Checklist

PingFederate Inventory

  • Number and names of all SP connections (SAML, OIDC, OAuth)
  • Number and names of all IdP connections (inbound federation)
  • List of all installed adapters and plugins (with versions)
  • Custom Java plugins or custom authentication adapters
  • Current PF version → target version compatibility
  • SSL/TLS certificates: issuer, expiry, usage (signing vs TLS)
  • OAuth client list (confidential vs public, grant types)
  • Authentication policy tree complexity
  • Current JVM heap settings and sizing
  • Dependencies: LDAP hosts, JDBC data sources, external APIs
  • Integration kits: agent kit, SCIM kit, MFA vendors
  • External IP ranges of partner SPs (for firewall planning)
  • SLAs and maintenance windows

PingDirectory Inventory

  • Total entry count (users, groups, service accounts)
  • Schema customizations (custom objectClasses, attributes)
  • Current PD version → target version
  • DIT structure and base DNs
  • Password policies and their names/bindings
  • Replication topology (number of nodes, ports)
  • All service account bind DNs and their ACIs
  • Data size (GB) for sizing EBS volumes
  • Peak LDAP TPS / average ops/sec (capacity planning)
  • Changelog retention and external consumers (PingDataSync)
  • Existing PingDataSync sync pipes and destinations
  • Virtual attributes defined
  • Backup schedule and recovery time objective (RTO)

Migration Risk Register

RiskImpactMitigation
SP partner metadata/certificates not updated before cutover Critical — SSO broken for partner applications Send new metadata to all SPs 4+ weeks before cutover. Dual-cert signing during transition.
Network latency between AWS PF and on-prem PD during hybrid phase High — Increased auth latency Use Direct Connect or Site-to-Site VPN with sufficient bandwidth. Monitor latency. Migrate PD to AWS first or in parallel.
JGroups cluster not forming in AWS VPC High — Engine nodes won't cluster; config sync fails Switch from UDP multicast to TCP unicast or S3_PING before go-live. Test in staging.
PingDirectory replication lag during migration High — Stale user data, auth failures Monitor replication lag continuously. Set alerting threshold at 5 seconds. Do not cut over if lag > threshold.
Custom plugins not compatible with new PF version High — Authentication flows broken Inventory all custom plugins early. Engage Ping Identity professional services or partners for compatibility testing.
AWS Security Group rules blocking inter-component traffic Medium — Silent auth failures (LDAP bind failures) Map all inter-component ports. Create detailed SG rule matrix before deployment. Test connectivity with ldapsearch / curl from within SG before app traffic.
Certificate expiry during migration project Critical — All SSO breaks Audit all cert expiry dates in discovery phase. Renew any certs expiring within 6 months of project end before migration begins.

Post-Migration Validation Checklist

  • ✓ PingFederate heartbeat endpoint returns HTTP 200 on all engine nodes
  • ✓ All SP connections pass SP-initiated SSO test
  • ✓ OAuth token endpoint returns valid tokens for all registered clients
  • ✓ OIDC discovery document accessible at /.well-known/openid-configuration
  • ✓ SAML metadata accessible and published to all partners
  • ✓ PingFederate Admin Console accessible (from authorized internal sources only)
  • ✓ PingDirectory replication status shows 0 ms lag and all nodes synchronized
  • ✓ LDAP bind operations successful from PingFederate to PingDirectory (check audit.log)
  • ✓ Admin Console inaccessible from public internet (verify via external port scan)
  • ✓ Audit logs streaming to SIEM/CloudWatch
  • ✓ Certificate expiry monitoring alerting configured
  • ✓ PingDirectory backup job running and uploading to S3
  • ✓ Load balancer health checks green for all engine nodes
  • ✓ JGroups cluster shows correct number of engine members in Admin Console
  • ✓ Authentication latency p99 within acceptable SLA (typically <2s for SSO, <200ms for token endpoint)
