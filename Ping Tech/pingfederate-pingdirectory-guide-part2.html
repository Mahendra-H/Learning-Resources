Authentication Policy Trees

The brain of every PingFederate authentication flow — understanding policy trees is what separates an operator from an architect.

Authentication Policies are the orchestration layer inside PingFederate that decides how a user gets authenticated. They replaced the older flat "authentication sources" model and give you a full decision tree — branches, selectors, MFA enforcement, risk scoring, fallback paths, and adapter chaining — all configurable without writing code.

💡
Mental Model Think of an Authentication Policy as a flowchart. Each node in the chart is either an adapter invocation (something that collects or validates a credential), a selector (a conditional branch), or a result (success, failure, or continue). The tree runs top-down and terminates when it reaches a Done node that either passes or fails the authentication.

Core Concepts#

Authentication Source

An adapter or selector node in the policy tree. Each source has a unique ID and is mapped to a specific IdP Adapter instance (HTML Form, Kerberos, X.509, PingID, etc.).

Policy Contract

The set of attributes the policy will produce upon successful completion. Every policy must map its outputs to a contract — this is what the SP Connection's attribute mapping reads from.

Authentication Selector

A conditional node that routes users to different authentication paths based on request context: IP address, user agent, request URL, SAML request attributes, or custom scripted logic.

Execution Mode

Policies run in Interactive mode (browser-based, involves redirects and HTML forms) or Headless mode (machine-to-machine, via password credentials or client credentials).

Step-up authentication is the pattern where low-risk applications skip MFA, but high-value targets (finance apps, admin consoles, HR systems) force a second factor. ⚠
Policy Ordering Gotcha PingFederate evaluates authentication policies in the order they appear in the policy contract list. The first matching policy wins. If you have a default catch-all policy listed before specific policies, it will always win. Always order more specific policies first, and use the drag-handle in the Admin Console to reorder them.

Step-by-step walkthroughs for the adapters you'll configure in every enterprise PingFederate deployment.

HTML Form Adapter — Full Configuration#

The HTML Form Adapter is the most commonly deployed adapter. It renders a login page, collects username and password, and validates them against a Password Credential Validator (PCV). Every field has a performance and security implication.

  1. Create the Adapter Instance — Admin Console → Authentication → Adapters → + New Adapter Instance. Choose type: com.pingidentity.adapters.htmlform.idp.HtmlFormIdpAuthnAdapter. Name it descriptively: HTMLForm-LDAP-Primary.
  2. Configure the Credential Validator — In the adapter's Extended Contract tab, select or create the LDAP PCV (covered next). This is what actually validates the password.
  3. Set Session State — Under Adapter Attributes tab, mark which attributes should be carried in the session cookie (e.g., username, pf.dataSources). Keep this minimal — large sessions degrade performance.
  4. Configure Account Lockout — Lockout & Throttling tab. Set Login Attempt Lockout Threshold and Lockout Duration. This is the adapter-level lockout, separate from PingDirectory's own password policy lockout — both apply.
  5. Customize Login Template — Default template: html.form.login.template.html located at $PF_HOME/server/default/conf/template/. To customize, copy to the same path and edit. Use $base_url, $form_action_url, and $locale Velocity template variables.

Kerberos / IWA Adapter#

Kerberos Integrated Windows Authentication (IWA) allows domain-joined Windows users to authenticate to PingFederate transparently — no username/password prompt. The browser uses the user's existing Kerberos session ticket (TGT) from Windows login.

ℹ
How it works The browser sends a SPNEGO token (base64-encoded Kerberos service ticket) in the Authorization: Negotiate HTTP header. PingFederate, acting as a Kerberos Service Principal, decrypts this ticket using a keytab file and extracts the user's identity — all without touching PingDirectory for the authentication step (though it still queries PD for attributes).
  1. Create a Service Account in Active Directory — Create a dedicated AD user account, e.g., svc-pingfed-krb. This will be the Kerberos service principal.
  2. Register the SPN — On the AD domain controller: setspn -A HTTP/pingfederate.corp.example.com svc-pingfed-krb. The SPN must match the FQDN users use to access PingFederate.
  3. Generate the Keytab file — On the DC: ktpass -princ HTTP/pingfederate.corp.example.com@CORP.EXAMPLE.COM -mapuser svc-pingfed-krb -pass [password] -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -out pingfederate.keytab
  4. Copy keytab to PingFederate server — Place at $PF_HOME/server/default/conf/krb5/pingfederate.keytab. Set file permissions so only the PF process user can read it.
  5. Configure krb5.conf — Create/edit /etc/krb5.conf (Linux) or the equivalent Windows Kerberos configuration to point to your KDC (AD domain controllers).
  6. Configure Kerberos Adapter in PingFederate — Admin Console → Authentication → Adapters → + New → type Kerberos Adapter. Set Service Principal Name, keytab location, and Attribute Contract (will include username from ticket principal).
  7. Add to Policy Tree — Use an IP-range selector to route corporate-IP traffic to the Kerberos adapter and external traffic to the HTML Form adapter (see policy tree diagram above).

Adapter-to-Adapter Chaining#

Adapter chaining allows multiple adapters to run sequentially. The output of the first adapter is available as input to the next. The classic pattern is: HTML Form → Risk Adapter → MFA Adapter, where the MFA adapter receives the username from the HTML Form and the risk score to decide whether to prompt.

Policy Tree ConfigThree-Adapter Chain: Form → Risk → PingID
# Authentication Policy: ChainedMFA
# 
# ADAPTER 1 — HTML Form (collects username+password)
#   Attribute Contract Output: username, pf.dataSources
#
# ADAPTER 2 — PingOne Risk Adapter  [receives username from chain]
#   Input mapping: subject = ${adapter1.username}
#   Output: riskScore (0-100), riskLevel (LOW/MED/HIGH)
#
# SELECTOR — Check risk level
#   riskLevel == HIGH  →  ADAPTER 3 (PingID MFA)
#   riskLevel == LOW   →  Done (Continue)
#
# ADAPTER 3 — PingID Adapter  [receives username from adapter 1]
#   Input mapping: subject = ${adapter1.username}
#   On Success: Done (Continue)
#   On Failure: Done (Fail)
#
# Final Policy Contract Mapping:
#   username       ← adapter1.username
#   email          ← LDAP datastore: mail
#   groups         ← LDAP datastore: memberOf
#   riskLevel      ← adapter2.riskLevel   (carries forward for audit)

# Important: In the Admin Console Policy Tree builder,
# click the SUCCESS node of Adapter 1 and choose "Use Same Adapter Again"
# to add Adapter 2 in the chain. This wires the attribute output forward.

PingFederate Admin REST API

Automate everything — no more clicking through the UI. The Admin API is the foundation for CI/CD pipelines, Terraform, and migration tooling.

Every action you can perform in the Admin Console is exposed via the Admin REST API on port 9999. The OpenAPI specification lives at https://[pf-admin]:9999/pf-admin-api/ and can be imported directly into Postman or Swagger UI. This API is how Terraform, PingCentral, and CI/CD pipelines drive PingFederate.

Authentication Methods#

Basic Auth (default)

Base64-encoded admin:password in the Authorization header. Easiest to set up. Use for local dev and initial automation. Not recommended for production pipelines — rotate passwords via vault.

OAuth2 Bearer Token

PingFederate can be configured to accept OAuth2 access tokens for Admin API calls. Enables service-account-based automation without shared passwords. Configure under System → OAuth Settings → Admin API OAuth settings.

Client Certificate (mTLS)

PF Admin API supports client certificate authentication for highly automated environments. Certificate must be trusted by the PF admin node's JKS truststore. Common in CI/CD pipelines with HSM-backed cert keys.

bashAdmin API — Authentication & Base Setup
#!/bin/bash
# Environment setup — reuse in all scripts
PF_ADMIN="https://pf-admin.internal.example.com:9999"
PF_API="${PF_ADMIN}/pf-admin-api/v1"
PF_CREDS="Administrator:$(aws secretsmanager get-secret-value \
  --secret-id pingfed/admin-password --query SecretString --output text)"

# Helper function — all API calls use this
pf_api() {
  local method=$1 path=$2 data=$3
  local args=(-s -k
    -H "Content-Type: application/json"
    -H "X-XSRF-Header: PingFederate"   # required for all mutating ops
    -u "$PF_CREDS"
    -X "$method"
    "${PF_API}${path}")
  [[ -n $data ]] && args+=(-d "$data")
  curl "${args[@]}"
}

Certificate Lifecycle via API#

bashCertificate Rotation — Automated Workflow
#!/bin/bash
# Automated cert expiry check — run this in CloudWatch Events / Lambda weekly

WARN_DAYS=60
NOW_EPOCH=$(date +%s)

pf_api GET /certificates/signing | \
  jq ".items[]" | \
  jq -r '"\(.id) \(.subjectDN) \(.expires)"' | \
while read id dn expires; do
  exp_epoch=$(date -d "$expires" +%s 2>/dev/null)
  days_left=$(( (exp_epoch - NOW_EPOCH) / 86400 ))
  if [[ $days_left -lt $WARN_DAYS ]]; then
    echo "⚠ CERT EXPIRING in ${days_left}d: $dn (id=$id)"
    # Publish to CloudWatch custom metric or SNS alert
    aws cloudwatch put-metric-data \
      --namespace "PingFederate" \
      --metric-name "CertDaysToExpiry" \
      --value $days_left \
      --dimensions "CertId=$id"
  fi
done

# Generate a new self-signed signing certificate
pf_api POST /certificates/signing/generate '{
  "commonName": "pingfederate-signing-2026",
  "organization": "Example Corp",
  "country": "US",
  "validDays": 730,
  "keyAlgorithm": "RSA",
  "keySize": 2048,
  "signatureAlgorithm": "SHA256withRSA"
}'
# Save the returned cert ID, then distribute the new public cert to all SPs
# BEFORE setting it as active. After SP acknowledgment:
pf_api PUT /certificates/signing/$NEW_CERT_ID/setActive

LDAP Operations — Complete Reference#

🔍
When to use LDAP vs REST Use LDAP for authentication (bind operations), high-throughput attribute lookup, and any code that already has an LDAP client. Use the REST API for provisioning integrations, webhook-driven user management, SCIM 2.0 compliance, and any modern microservice that shouldn't carry an LDAP SDK dependency.
bashLDAP Operations — Copy-Paste Ready (ldapsearch/ldapmodify)
#!/bin/bash
# All examples use PingDirectory's bundled ldap tools at:
# $PD_HOME/bin/ldapsearch, ldapmodify, ldappasswdmodify

export PD_HOME=/opt/pingdirectory
export PD_HOST=pd-01.internal.example.com
export PD_PORT=636
export BIND_DN="cn=Directory Manager"
export BIND_PW="changeme"
export BASE_DN="dc=example,dc=com"

LDAP_ARGS="-h $PD_HOST -p $PD_PORT -Z -X -D '$BIND_DN' -w '$BIND_PW'"

# ── 1. Verify connectivity + get server info
$PD_HOME/bin/ldapsearch $LDAP_ARGS -b "" -s base "(objectClass=*)" +

# ── 2. Find a user by uid
$PD_HOME/bin/ldapsearch $LDAP_ARGS \
  -b "ou=People,$BASE_DN" -s sub \
  "(uid=jsmith)" \
  uid cn mail memberOf pwdChangedTime ds-pwp-account-is-disabled

# ── 3. Compound filter — user by email OR uid
$PD_HOME/bin/ldapsearch $LDAP_ARGS \
  -b "ou=People,$BASE_DN" -s sub \
  "(|(uid=jsmith)(mail=jsmith@example.com))" \
  uid mail cn

# ── 4. Get users in a specific group
$PD_HOME/bin/ldapsearch $LDAP_ARGS \
  -b "ou=People,$BASE_DN" -s sub \
  "(memberOf=cn=Admins,ou=Groups,$BASE_DN)" \
  uid cn mail

# ── 5. Check password policy state for a user
$PD_HOME/bin/ldapsearch $LDAP_ARGS \
  -b "uid=jsmith,ou=People,$BASE_DN" -s base \
  "(objectClass=*)" \
  ds-pwp-account-is-disabled ds-pwp-locked-time ds-pwp-must-change-password \
  ds-pwp-time-before-expiration pwdFailureTime pwdChangedTime

Indexing Strategy — Critical for Performance#

Every attribute used in a search filter should have an equality index at minimum. Without an index, PingDirectory performs a full scan of all entries in the backend — catastrophic at scale. An unindexed search on a 5M-entry directory can take seconds instead of microseconds.

🔥
Unindexed Search Alert PingDirectory logs unindexed search operations in the access log with the note unindexedSearch=true. Check this after deploying a new PCV or attribute lookup — any new search filter that isn't indexed will show here. Watch the access log for 1-2 days after configuration changes.
bashManaging Indexes in PingDirectory
# ── List existing indexes for a backend

$DSCONFIG create-local-db-index $DS_ARGS \
  --backend-name userRoot \
  --index-name mail \
  --set index-type:equality \
  --set index-type:presence     # presence index: is mail set at all?

$DSCONFIG create-local-db-index $DS_ARGS \
  --backend-name userRoot \
  --index-name cn \
  --set index-type:equality \
  --set index-type:substring

Access Token Validators — Resource Server Integration#

Resource Servers (your APIs) need to validate access tokens. There are two patterns:

JWT Local Validation (Fast)

Resource server downloads PingFederate's public JWKS from /ext/one/jwks and validates the token signature locally. No round-trip to PF per request. Cache the JWKS (refresh daily or on kid mismatch). Best for high-throughput APIs.

Introspection Endpoint (Rich)

Resource server calls POST /as/introspect.oauth2 with the token. PF validates it and returns active status + all claims. Supports reference tokens and immediate revocation checking. Adds ~5-20ms latency per request — cache results by token hash.

JWT Signature Validation Failure on Resource Server
API returns 401 after PingFederate token was just issued. "JWT signature verification failed" in logs.
▾
Causes & Resolution
  • Wrong JWKS URI cached — Resource server cached old JWKS before key rotation. Force a JWKS refresh: if using jose or similar library, clear the JWKS cache and retry.
  • kid mismatch — Token header's kid doesn't match any key in JWKS. Check that the signing cert ID in PF's Access Token Manager matches what's published at /ext/one/jwks.
  • Algorithm mismatch — RS vs HS algorithm confusion. Confirm the ATM is configured for RS256 and the RS is validating with the public key (not an HMAC secret).
  • Token from different ATM — Multiple ATMs configured, and token was issued by a different ATM than the RS is validating against. Check the kid header and ensure it matches the correct ATM's signing key.
bash
# 1. Decode the JWT header to get kid
TOKEN="eyJhbGciOiJS..."
echo $TOKEN | cut -d. -f1 | base64 -d 2>/dev/null | jq .
# → {"alg":"RS256","kid":"signing-key-2025","typ":"JWT"}

# 2. Check the JWKS endpoint — does the kid match?
curl -s https://pingfederate.example.com/ext/one/jwks | jq '.keys[] | {kid:.kid, alg:.alg}'
# → [{"kid":"signing-key-2025","alg":"RS256"}, ...]
# If the kid from step 1 doesn't appear here — signing cert mismatch

# 3. Verify the JWT signature manually (using jwt.io or jwt CLI)
# jwt decode --alg RS256 --key public.pem $TOKEN

PingFederate OutOfMemoryError / Heap Dump on Engine
Engine node crashes with OOM. Heap dump file in logs directory. One node drops from cluster.
▾
Triage Checklist
  • Check heap dump with Eclipse MAT or VisualVM — look for the top retained object. Usually: session cache filling up, OAuth token cache leak, or attribute contract producing huge multi-valued attributes.
  • Increase -Xmx in run.properties if heap was at capacity. But also investigate — OOM is usually a symptom of a configuration problem, not simply insufficient memory.
  • Check pf.session.state.max.records — if set too high and SSO load is heavy, the session cache will consume all available heap.
  • Check memberOf attribute — users in hundreds of groups cause extremely large LDAP query results. Cap the number of groups returned via PCV search filter or attribute contract filtering.
  • Verify the GC log: -Xlog:gc*:file=$PF_HOME/logs/gc.log:time,uptime:filecount=5,filesize=10m added to JVM args will capture GC events for analysis.

Log Format Reference — PingFederate audit.log
Each audit log line follows the pattern:
[timestamp] [trackingId] [event] [status] [subject] [app] [connection] [protocol] [role] [description]
Example: 2025-01-01 10:12:33,412 | 47a3b | SSO_REQUEST | SUCCESS | jsmith | SalesforceSSO | salesforce-prod | SAML20 | IDP | Authentication succeeded
The trackingId is the key — use it to correlate entries across audit.log, server.log, and transaction.log for a single SSO event.
